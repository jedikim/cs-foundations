보안

누구를, 무엇을, 어디까지 믿을 것인가

읽는 시간 약 40분먼저 읽으면 좋은 장15장 웹과 HTTP17장 데이터베이스

집에는 문이 있고 열쇠가 있습니다. 열쇠가 있는 사람만 들어올 수 있고, 들어온 손님도 내 방 서랍까지 열어 볼 수는 없습니다. 인터넷에 올린 프로그램도 똑같이 지켜야 합니다. 작은 쇼핑몰을 만들었는데, 주소창에 적힌 주문 번호를 1042에서 1043으로 바꿨더니 남의 주문서가 보인다면 큰일입니다. 누가 들어올 수 있고 들어와서 무엇을 할 수 있는지 정해 두는 일이 보안입니다.

이 장을 마치면
  • "누구인지 확인하는 일"과 "무엇을 해도 되는지 정하는 일"을 구분할 수 있습니다.
  • 비밀번호를 안전하게 보관하는 방법을 설명할 수 있습니다.
  • 남이 보낸 입력을 그대로 믿으면 안 되는 이유를 설명할 수 있습니다.
  • AI가 만든 코드에서 보안을 위해 확인할 점을 알 수 있습니다.

19.1보안의 첫 질문: 무엇을, 누구로부터 지킬까#

건물 경비를 맡았다고 해 봅시다. "전부 완벽하게 지켜라"는 말로는 아무것도 정해지지 않습니다. 금고에 무엇이 있는지, 누가 노리는지, 어느 문으로 들어올 수 있는지부터 적어야 합니다. 이렇게 지킬 것, 상대, 들어오는 길을 적어 둔 것을 위협 모델(threat model)이라고 합니다.

질문 작은 쇼핑몰이라면
무엇을 지키나 회원 비밀번호, 주문과 배송지, 결제 API 키
누구로부터 호기심 많은 회원, 자동으로 찔러 보는 프로그램
어느 길로 로그인 화면, 주문 API, 파일 올리기, 공개된 코드

표를 채웠으면 건물 안과 밖을 가르는 선을 긋습니다. 서버는 건물 안이고, 브라우저와 앱은 건물 밖입니다. 건물 밖에서 벌어지는 일은 내가 통제할 수 없습니다. 사용자는 개발자 도구로 화면을 고칠 수 있고, 화면을 거치지 않고 요청을 직접 만들어 보낼 수도 있습니다. 이 선을 신뢰 경계(trust boundary)라고 부릅니다.

핵심

건물 밖에서 온 값은 사실이 아니라 주장입니다. 가격도, 사용자 번호도, "나는 관리자"라는 표시도 서버가 다시 확인하기 전에는 믿지 않습니다.

19.2인증과 인가: 누구인가, 무엇을 해도 되는가#

비유로 이해하기 · 회사 건물에 들어가기

로비 안내데스크에서 신분증을 보여 주면 출입증을 받습니다. 그런데 출입증이 있다고 모든 층에 갈 수 있는 것은 아닙니다. 층마다 문이 있고, 문은 출입증에 허락된 층에서만 열립니다.

보안에서 가장 먼저 구분할 두 낱말이 여기에 있습니다.

  • 인증(authentication)은 로비의 신분 확인입니다. "이 사람이 누구인가"를 확인합니다. 로그인이 대표적입니다.
  • 인가(authorization)는 층마다 있는 문입니다. "이 사람이 이 일을 해도 되는가"를 확인합니다.
참고

비유와 다른 점이 둘 있습니다. 건물의 문은 몇 개뿐이지만 서비스에서는 API 주소 하나하나가 모두 문입니다. 그리고 서버는 얼굴을 보지 못하고 출입증에 적힌 글자만 봅니다. 출입증을 복사한 사람과 본인을 구분하지 못합니다.

실패했을 때의 응답도 다릅니다. 누구인지 확인되지 않으면 401, 누구인지는 알지만 허락되지 않은 일이면 403을 돌려줍니다(15장).

처음 만든 서비스에서 가장 자주 빠지는 것이 인가입니다. 로비만 지키고 층마다 문은 달지 않은 건물이 됩니다. 장 첫머리에서 본, 주문 번호만 바꿨더니 남의 주문서가 열리는 사고가 바로 그 경우입니다.

19.3비밀번호는 서버도 모르게 보관합니다#

안내데스크가 방문자들의 집 열쇠를 복사해 서랍에 모아 둔다고 상상해 보세요. 서랍이 털리는 날 모든 집이 위험해집니다. 비밀번호를 DB에 그대로 저장하는 것이 이와 같습니다. 사람들은 여러 사이트에 같은 비밀번호를 쓰기 때문에, 내 DB가 새면 회원의 다른 계정까지 위험해집니다.

그래서 비밀번호는 해시(hash)해서 저장합니다. 해시는 입력을 정해진 길이의 값으로 바꾸는 계산인데, 결과에서 원래 값을 되찾을 수 없습니다. 손가락으로 지문은 찍을 수 있어도 지문으로 손가락을 만들 수는 없는 것과 같습니다. 로그인할 때는 입력된 비밀번호를 같은 방법으로 해시해서 저장된 값과 비교합니다. 서버조차 원래 비밀번호를 모릅니다.

여기에 두 가지를 더합니다.

  • 솔트(salt): 회원마다 다른 무작위 값을 비밀번호에 섞습니다. 같은 비밀번호도 저장값이 달라져서, 흔한 비밀번호의 해시를 미리 계산해 둔 표가 쓸모없어집니다.
  • 느린 해시: Argon2id나 bcrypt 같은 비밀번호 전용 방식은 일부러 느리게 만들어져 있습니다. 한 번에 0.1초가 걸리면 로그인하는 사람은 느끼지 못하지만, 후보 1억 개를 넣어 보려는 쪽은 같은 컴퓨터로 약 116일이 걸립니다.
from argon2 import PasswordHasher
ph = PasswordHasher()
stored = ph.hash("apple123")     # 가입할 때: 이 값을 DB에 저장
ph.verify(stored, "apple123")    # 로그인할 때: 틀리면 오류가 난다

hash는 솔트를 알아서 만들어 섞고, 그 솔트를 결과 안에 함께 적어 둡니다. 그래서 verify에는 저장값과 입력만 건네면 됩니다.

주의

해시 방식을 직접 만들거나 SHA-256 한 번으로 끝내지 마세요. 빠른 해시는 공격자에게도 빠릅니다. 검증된 라이브러리를 그대로 씁니다.

비밀번호 하나로 부족할 때

비밀번호는 언젠가 샌다고 가정하는 편이 안전합니다. 다중 인증(MFA, Multi-Factor Authentication)은 종류가 다른 증거를 둘 이상 요구합니다. 아는 것(비밀번호), 가진 것(휴대전화에 뜨는 6자리 코드), 몸의 특징(지문)이 그 종류입니다. 비밀번호와 생년월일은 둘 다 "아는 것"이라 다중 인증이 아닙니다.

패스키(passkey)는 비밀번호를 아예 없앱니다. 기기 안에 열쇠를 만들어 두고, 지문이나 얼굴로 그 열쇠를 쓰도록 허락합니다. 서버에는 훔쳐 가도 쓸모없는 짝 열쇠만 저장되고, 주소가 다른 가짜 사이트에서는 열쇠가 작동하지 않습니다.

19.4로그인 상태 유지: 출입증#

HTTP에서는 요청 하나하나가 서로 남남입니다. 그렇다고 클릭할 때마다 비밀번호를 물을 수는 없으니, 로그인에 성공하면 출입증을 내어 주고 다음 요청부터는 출입증만 확인합니다. 출입증을 만드는 방식은 둘입니다.

  • 세션(session): 서버가 뜻 없는 무작위 번호표를 발급하고, 장부에 "8f3a2c번은 민지"라고 적어 둡니다. 브라우저는 번호표만 쿠키에 담아 들고 다닙니다.
  • 토큰(token): 출입증 자체에 "민지, 14시까지 유효"라고 적고 서버가 서명을 찍습니다. 서명은 서버만 찍을 수 있는 도장이어서, 내용을 한 글자라도 고치면 맞지 않습니다. 서버는 장부 없이 서명만 확인합니다. JWT(JSON Web Token)가 대표적인 형식입니다.

어느 쪽이든 세 가지를 기억합니다.

  1. 출입증은 주운 사람도 쓸 수 있습니다. 비밀번호만큼 조심합니다. 쿠키에 담는다면 HttpOnly(스크립트가 읽지 못함), Secure(HTTPS로만 전송), SameSite(다른 사이트가 시킨 요청에는 붙이기를 제한) 속성을 켭니다.
  2. JWT의 내용은 누구나 읽을 수 있습니다. 서명은 고치지 못하게 할 뿐 가려 주지 않습니다. 비밀을 넣지 말고, 서명을 검증하지 않은 내용은 믿지 않습니다.
  3. 번호표는 추측할 수 없어야 합니다. 1, 2, 3처럼 늘어나는 번호나 시각으로 만들지 않습니다. Python의 secrets 모듈 같은 보안용 난수를 씁니다.
직접 해 보기

로그인한 사이트에서 개발자 도구의 Application(저장소) 탭을 열고 Cookies를 눌러 보세요. 쿠키마다 HttpOnly, Secure, SameSite 칸이 보입니다.

한 걸음 더토큰 수명과 갱신

JWT는 장부가 없어서 만료 전에는 회수하기 어렵습니다. 그래서 수명을 15분처럼 짧게 잡은 액세스 토큰과, 새 액세스 토큰을 받는 데만 쓰는 수명이 긴 리프레시 토큰을 함께 씁니다. 리프레시 토큰은 서버 장부에 적어 두어 언제든 폐기할 수 있게 합니다. 출입증을 도둑맞아도 피해가 15분으로 줄어듭니다.

소셜 로그인: 신분 확인을 남에게 맡기기

"구글로 로그인" 버튼 뒤에는 OAuth라는 약속이 있습니다. 안내데스크가 신분증을 직접 검사하는 대신, 믿을 만한 기관이 떼어 준 확인서를 받는 방식입니다. 정확히는 OAuth가 권한을 넘겨받는 약속이고, 로그인에는 여기에 신원 확인 규칙을 더한 OpenID Connect(OIDC)를 씁니다.

내 서비스는 구글 비밀번호를 한 번도 보지 않습니다. 보관하지 않은 비밀번호는 유출될 수도 없습니다. 다만 구글이 알려 주는 것은 "누구인가"까지입니다. 그 사람이 내 서비스에서 무엇을 할 수 있는지는 여전히 내가 정합니다. 이 흐름은 직접 짜지 말고 검증된 라이브러리에 맡깁니다.

19.5권한 검사는 반드시 서버에서#

흔한 오해 · 관리자 버튼을 화면에서 숨겼으니 안전하다

버튼을 숨기는 것은 문에 "관계자 외 출입 금지" 종이를 붙이는 일입니다. 문은 잠겨 있지 않습니다. 요청은 화면 없이도 만들어 보낼 수 있으므로, 서버가 요청을 받을 때마다 권한을 확인해야 합니다. 화면에서 숨기는 것은 편의이고, 서버에서 막는 것이 보안입니다.

주문 번호 사고를 다시 봅시다. 민지는 정상적으로 로그인했으니 인증은 통과했습니다. 그런데 서버가 "이 주문이 민지의 것인가"를 묻지 않았습니다.

고치는 코드는 세 줄입니다.

order = db.find_order(order_id)
if order.owner_id != session.user_id:
    return 403

session.user_id는 요청에 실려 온 값이 아니라 서버가 세션에서 꺼낸 값이어야 합니다. 이렇게 번호만 바꿔 남의 것에 닿는 문제를 IDOR(Insecure Direct Object Reference)라고 부릅니다. 주문 번호를 길고 복잡하게 만드는 것은 해결이 아닙니다. 조회, 수정, 삭제, 내려받기 모두에 같은 검사를 둡니다.

핵심

"로그인했다"와 "이 데이터를 봐도 된다"는 별개입니다. 요청마다, 대상마다 서버에서 확인합니다.

역할과 최소 권한

사용자마다 규칙을 따로 적으면 금세 감당할 수 없게 됩니다. 그래서 역할을 만들고 역할에 권한을 묶습니다. 이것이 역할 기반 권한(RBAC, Role-Based Access Control)입니다.

역할 내 주문 보기 남의 주문 보기 환불 처리
회원 가능 불가 불가
상담원 가능 가능 불가
운영자 가능 가능 가능

표를 채우는 원칙은 최소 권한(least privilege)입니다. 맡은 일에 필요한 만큼만 주고, 적혀 있지 않은 것은 거부합니다. 청소 업체에 금고 열쇠까지 주지 않는 것과 같습니다. 프로그램에도 똑같이 적용합니다. 글을 읽기만 하는 기능이 쓰는 DB 계정에는 삭제 권한이 없어야 합니다.

한 걸음 더역할만으로 부족할 때: ABAC

"상담원은 자기 지점의 주문만, 근무 시간에만 볼 수 있다" 같은 규칙은 역할 이름만으로 표현하기 어렵습니다. 이럴 때는 사용자의 소속, 주문의 지점, 현재 시각 같은 속성을 조건으로 따지는 ABAC(Attribute-Based Access Control)를 씁니다. 앞의 "주문의 주인인가" 검사도 속성 검사입니다. 보통 역할로 큰 틀을 잡고 속성 조건을 덧붙입니다.

문 앞에서 횟수 세기

비밀번호를 1초에 100개씩 넣어 보는 프로그램도 있습니다. 그래서 "같은 계정에서 5번 틀리면 1분 기다리기"처럼 요청 수 제한(rate limit)을 둡니다. 한도를 넘으면 429로 응답합니다. 호출할 때마다 돈이 드는 AI API나 문자 발송 기능에는 꼭 필요합니다.

19.6암호화의 세 도구와 비밀값#

출입증의 서명, 패스키의 열쇠, HTTPS. 지금까지 나온 것들 뒤에는 같은 도구 셋이 있습니다.

  • 대칭키 암호(symmetric-key): 같은 열쇠로 잠그고 엽니다. 빠르지만, 상대에게 열쇠를 어떻게 안전하게 건넬지가 숙제로 남습니다.
  • 공개키 암호(public-key): 열쇠가 한 쌍입니다. 누구에게나 나눠 주는 공개키와 나만 가지는 개인키입니다. 공개키로 잠근 것은 짝이 되는 개인키로만 열립니다.
  • 해시: 열쇠가 없고 되돌릴 수도 없습니다. 내용이 한 글자만 달라져도 값이 완전히 달라집니다.

열쇠 한 쌍은 도장으로도 씁니다. 개인키로 도장을 찍고, 누구든 공개키로 그 도장이 진짜인지 확인합니다. 이것이 전자 서명(digital signature)입니다. 패스키 로그인과 앱 업데이트 검증이 이 원리입니다. 15장의 HTTPS도 세 도구를 조합합니다. 서명으로 진짜 그 서버인지 확인하고, 공개키 방식으로 열쇠를 정한 뒤, 빠른 대칭키로 본문을 잠급니다.

주의 · 암호화가 해 주지 않는 일

암호화는 엉뚱한 사람이 내용을 읽지 못하게 할 뿐입니다. HTTPS를 써도 남의 주문을 내어 주는 서버는 여전히 잘못된 서버입니다. 그리고 암호 방식은 직접 만들지 않습니다.

한 걸음 더인증서 체인, 봉투 암호화와 키 교체

인증서 체인. 브라우저는 처음 보는 서버의 공개키를 어떻게 믿을까요? 서버 인증서에는 인증 기관의 서명이 있고, 그 기관의 인증서에는 더 위 기관의 서명이 있습니다. 사슬의 맨 위는 운영체제와 브라우저에 미리 들어 있는 루트 인증서입니다.

봉투 암호화. 데이터를 잠근 열쇠를 다시 마스터 키로 잠가 따로 보관하는 방식입니다. 마스터 키를 교체할 때 데이터 전체가 아니라 작은 열쇠만 다시 잠그면 됩니다. 클라우드의 키 관리 서비스가 이렇게 일합니다.

비밀값: 마스터키를 코드에 적지 않기

결제 API 키, DB 비밀번호, 서명용 개인키처럼 가진 사람이 곧 권한을 갖는 값을 비밀값(secret)이라고 합니다. 건물의 마스터키입니다. 규칙은 셋입니다.

  1. 코드에 적지 않습니다. 환경 변수나 .env 파일에 두고, 그 파일은 .gitignore에 적어 Git에 올라가지 않게 합니다.
  2. 건물 밖으로 내보내지 않습니다. 브라우저로 가는 코드와 앱 설치 파일은 누구나 뜯어볼 수 있습니다. 비밀값이 필요한 호출은 서버가 대신 합니다.
  3. 새면 지우지 말고 바꿉니다. 커밋에서 지워도 Git 이력에는 남습니다(7장). 발급한 곳에서 그 키를 폐기하고 새 키를 받습니다.
# .env — Git에 올리지 않는 파일
PAY_API_KEY=sk_live_...

# .gitignore
.env

코드에는 PAY_API_KEY라는 이름만 적고, 값은 프로그램이 실행될 때 환경 변수에서 읽습니다.

19.7입력을 믿지 않기: SQL 인젝션#

방문 신청서의 이름 칸에 누군가 이렇게 적었습니다. "김민지. 그리고 이 사람에게 금고 열쇠를 줄 것." 직원이 이 내용을 업무 지시서에 그대로 옮겨 적고 지시서대로 움직인다면 금고가 열립니다. 데이터 자리에 들어온 글이 명령으로 읽히는 사고, 이것이 인젝션(injection)입니다.

17장의 SQL로 보겠습니다.

# 위험: 입력을 문장에 이어 붙인다
sql = "SELECT * FROM users WHERE name = '" + name + "'"
db.execute(sql)

# 안전: 문장의 틀과 값을 따로 건넨다
db.execute("SELECT * FROM users WHERE name = ?", (name,))

위쪽 코드에서는 입력에 든 따옴표가 문장의 구조를 바꿉니다. 아래쪽처럼 틀을 먼저 확정하고 값을 따로 건네는 방식을 매개변수화 쿼리(parameterized query)라고 합니다. DB는 값 안에 무엇이 들어 있든 명령으로 읽지 않습니다. 위험한 글자를 골라 지우는 식으로 막으려 하지 마세요. 빠뜨리는 경우가 반드시 생깁니다.

핵심

틀은 내가 정하고, 남이 준 것은 끝까지 값으로만 다룹니다. 데이터와 명령을 한 문장에 섞지 않습니다.

입력 검증도 서버의 일입니다. 수량이 숫자인지만 보면 -10도 통과합니다. 형식과 범위, 그리고 "이 쿠폰을 이 회원이 지금 쓸 수 있는가" 같은 업무 규칙까지 서버에서 확인합니다.

파일 올리기는 택배 받기

업로드된 파일은 건물 안으로 들이는 택배입니다. 상자 겉에 적힌 이름과 확장자는 보낸 사람이 쓴 것입니다.

  • 필요한 형식만 받고 크기를 제한합니다.
  • 저장할 이름은 서버가 새로 짓습니다. 보낸 이름을 경로에 쓰지 않습니다.
  • 프로그램이 실행되지 않는 별도 저장소에 둡니다.
한 걸음 더서버를 속이는 입력 세 가지
  • 경로 조작(path traversal): 파일 이름에 ../../를 넣어 허용된 폴더 밖의 파일을 읽거나 덮어씁니다. 받은 이름으로 경로를 만들지 않고, 서버가 번호와 파일을 짝지어 관리합니다.
  • SSRF(Server-Side Request Forgery): "이 주소의 이미지를 가져와 줘" 기능에 내부망 주소를 넣어, 서버가 건물 안쪽을 대신 들여다보게 합니다. 접속해도 되는 주소를 허용 목록으로 제한합니다.
  • 역직렬화(deserialization): 저장했던 데이터를 다시 객체로 되살리는 일입니다. Python의 pickle처럼 되살리는 도중에 코드를 실행할 수 있는 형식에는 남이 준 데이터를 넣지 않습니다. JSON처럼 데이터만 담는 형식을 씁니다.

19.8브라우저를 노리는 공격: XSS와 CSRF#

이번에는 공격 대상이 서버가 아니라 내 사이트를 찾은 다른 방문자입니다.

XSS: 댓글에 섞여 들어온 코드

누군가 댓글 칸에 글 대신 <script> 태그를 써넣었습니다. 서버가 이것을 그대로 페이지에 끼워 넣으면, 그 페이지를 여는 모든 사람의 브라우저가 이 스크립트를 내 사이트의 코드로 알고 실행합니다. 그 사람의 권한으로 주문도 하고 글도 쓸 수 있습니다. 이것이 XSS(Cross-Site Scripting)입니다. SQL 인젝션과 같은 사고가 브라우저에서 난 것입니다.

막는 방법도 같습니다. 데이터를 데이터로만 다룹니다.

el.innerHTML = comment;    // 위험: 태그가 코드로 해석된다
el.textContent = comment;  // 안전: 글자 그대로 보인다

<를 &lt;로 바꾸는 것처럼, 특별한 뜻을 가진 글자를 보통 글자로 바꿔 내보내는 일을 이스케이프(escape)라고 합니다. React 같은 화면 라이브러리는 이것을 기본으로 해 줍니다. 그러니 innerHTML이나 dangerouslySetInnerHTML처럼 기본 보호를 끄는 코드가 보이면 멈춰서 확인하세요. 여기에 CSP(Content Security Policy)를 더하면 이중 잠금이 됩니다. 허락한 출처의 스크립트만 실행하라고 브라우저에 알려 주는 응답 헤더입니다.

CSRF: 출입증을 대신 내밀게 하기

쿠키는 브라우저가 알아서 붙여 줍니다. 민지가 쇼핑몰에 로그인한 채 다른 탭에서 낚시 페이지를 열었다고 합시다. 그 페이지가 쇼핑몰로 배송지 변경 요청을 보내게 하면, 브라우저는 여기에도 쇼핑몰 쿠키를 붙입니다. 서버 눈에는 민지가 직접 보낸 요청과 똑같습니다.

이것이 CSRF(Cross-Site Request Forgery)입니다. 막으려면 쿠키에 SameSite를 명시하고, 프레임워크가 제공하는 CSRF 토큰 기능을 켭니다. 그리고 무언가를 바꾸는 일은 GET 요청으로 처리하지 않습니다.

19.9남의 코드, AI 에이전트, 개인정보#

설치한 패키지도 건물 안에서 일합니다

npm install 한 줄은 외부 업체 직원에게 출입증을 내어 주는 일입니다. 그 코드는 내 코드와 같은 권한으로 실행되고, 그 패키지가 데려온 다른 패키지도 마찬가지입니다. 남의 코드를 통해 들어오는 이런 위험을 공급망(supply chain) 문제라고 합니다.

  • 이름을 한 글자씩 확인합니다. 유명 패키지와 철자가 비슷한 가짜가 있습니다. AI가 추천한 패키지도 실제로 있는 그 패키지인지 확인합니다.
  • 잠금 파일로 버전을 고정하고, npm audit 같은 도구가 알려 주는 보안 결함 경고를 읽습니다.
  • 쓰지 않는 패키지는 지웁니다.

AI 에이전트에게 권한을 줄 때

AI 에이전트는 심부름을 맡긴 신입 직원과 같습니다. 문제는 이 직원이 읽은 글과 받은 지시를 잘 구분하지 못한다는 점입니다.

웹 페이지, 메일, 문서 속에 지시문을 숨겨 에이전트를 조종하는 것을 프롬프트 인젝션(prompt injection)이라고 합니다. 또 인젝션입니다. 다만 이번에는 매개변수화 쿼리 같은 확실한 해법이 없습니다. 그래서 방어의 중심은 권한입니다.

  • 최소 권한: 요약만 시킬 에이전트에게 파일 삭제나 결제 도구를 주지 않습니다.
  • 샌드박스(sandbox): 작업 폴더 밖의 파일과 네트워크에 닿지 못하는 격리된 환경에서 실행합니다.
  • 사람의 확인: 삭제, 결제, 외부 전송처럼 되돌릴 수 없는 일은 실행 전에 묻게 합니다.

AI가 만든 코드와 문장도 건물 밖에서 온 입력으로 다룹니다. 이 이야기는 29장에서 이어집니다.

개인정보: 갖고 있지 않은 것은 새지 않습니다

가장 안전한 개인정보는 모으지 않은 개인정보입니다. 기능에 꼭 필요한 것만 받고, 필요한 기간이 지나면 지웁니다. 로그도 조심합니다. 디버깅하려고 요청을 통째로 찍으면 비밀번호와 토큰이 로그 파일에 쌓입니다(22장).

한 걸음 더백업 암호화와 삭제 요청

백업은 DB의 복사본이므로 원본만큼 조심해야 합니다. 암호화해서 보관하고, 열쇠는 백업과 다른 곳에 둡니다. 열쇠를 잃으면 백업도 열 수 없으니 복원을 실제로 연습해 봅니다. 회원이 탈퇴하며 삭제를 요청하면 DB뿐 아니라 로그, 분석용 사본, 백업에 남은 정보를 어떻게 할지도 미리 정해 둡니다.

실전 사례#

실전 사례 · AI API 키가 웹 페이지 코드에서 발견됐다

AI 챗봇 기능을 급히 붙이면서 유료 API 키를 브라우저에서 도는 코드에 넣었습니다. 며칠 뒤 사용량이 평소의 수십 배로 찍혔습니다.

  1. 먼저 키를 폐기합니다. 발급한 곳에서 키를 무효로 만들고 새 키를 받습니다. 코드에서 지우는 것은 그다음입니다.
  2. 피해 범위를 봅니다. 사용 기록에서 낯선 호출이 언제부터 있었는지 보고, 배포된 파일과 Git 이력, 로그에 키가 남은 곳을 찾습니다.
  3. 구조를 바꿉니다. 브라우저는 내 서버를 부르고, 서버가 환경 변수에 든 키로 AI API를 대신 부릅니다.
  4. 새로 생긴 문을 지킵니다. 그 중계 API에 로그인 확인과 요청 수 제한을 답니다. 없으면 남이 내 서버를 거쳐 공짜로 쓰게 됩니다.
  5. 확인합니다. 새로 배포한 파일에서 키가 검색되지 않는지, 로그인하지 않은 요청이 거부되는지 시험합니다.

키를 코드 안에서 꼬아 숨기는 것은 해결이 아닙니다. 건물 밖에 둔 열쇠는 결국 발견됩니다.

한눈에 정리#

  • 보안은 지킬 것, 상대, 들어오는 길을 정하는 데서 시작합니다. 브라우저에서 온 값은 서버가 다시 확인합니다.
  • 인증은 누구인지, 인가는 해도 되는지를 확인합니다. 인가는 요청마다 서버에서 합니다.
  • 비밀번호는 솔트를 섞은 느린 해시로 저장합니다. 출입증(세션, 토큰)은 비밀번호처럼 보호합니다.
  • 권한은 필요한 만큼만 주고, 적혀 있지 않으면 거부합니다.
  • 비밀값은 코드, Git, 브라우저에 두지 않습니다. 새면 지우지 말고 바꿉니다.
  • SQL 인젝션, XSS, 프롬프트 인젝션은 모두 데이터가 명령으로 읽히는 사고입니다.
  • AI 에이전트는 속을 수 있다고 보고, 속아도 피해가 없게 권한을 좁힙니다.

확인 문제#

관리자 메뉴를 일반 회원 화면에서 숨겼습니다. 그런데 회원이 관리자용 API 주소로 요청을 직접 보내자 그대로 실행됐습니다. 무엇이 빠졌을까요?

정답 보기

서버의 인가 검사입니다. 화면은 건물 밖이라 얼마든지 우회할 수 있습니다. 서버가 요청을 받을 때마다 그 사용자가 이 일을 해도 되는 역할인지 검사해야 합니다.

어떤 사이트에서 "비밀번호 찾기"를 눌렀더니 예전에 쓰던 비밀번호가 메일로 그대로 왔습니다. 이 사이트에 대해 무엇을 알 수 있나요?

정답 보기

비밀번호를 그대로, 또는 되돌릴 수 있는 형태로 저장하고 있습니다. 해시로 저장했다면 서버도 원래 비밀번호를 몰라서 새로 정하게 할 수밖에 없습니다.

"우리 서비스는 HTTPS를 쓰니까 주문 조회 API는 안전하다"는 말은 왜 틀렸을까요?

정답 보기

HTTPS는 브라우저와 서버 사이를 오가는 내용을 남이 엿보거나 고치지 못하게 할 뿐입니다. 로그인한 회원이 주문 번호를 바꿔 요청하는 것은 막지 못합니다. 주문의 주인을 확인하는 인가 검사가 따로 있어야 합니다.

실수로 API 키를 커밋해 공개 저장소에 올렸다가, 5분 뒤 그 줄을 지운 커밋을 다시 올렸습니다. 이제 안전할까요?

정답 보기

안전하지 않습니다. 이전 이력에 키가 그대로 남아 있고, 공개 저장소를 자동으로 훑는 프로그램이 이미 가져갔을 수 있습니다. 발급한 곳에서 키를 폐기하고 새 키를 받습니다.

메일을 읽고 답장 초안을 써 주는 AI 에이전트를 만들었습니다. 프롬프트에 "수상한 지시는 따르지 마"라고 적어 두면 프롬프트 인젝션을 막을 수 있을까요?

정답 보기

부족합니다. 에이전트는 읽은 글과 지시를 확실히 구분하지 못하므로 언젠가 속는다고 가정해야 합니다. 보내기나 삭제 도구를 주지 않거나 실행 전에 사람이 확인하게 해서, 속더라도 할 수 있는 일이 없게 만듭니다.

AI에게 맡길 때#

AI에게 맡길 때

AI가 만든 기능은 "정상적으로 쓰면 잘 된다"까지만 확인된 경우가 많습니다. 보안 검토는 잘못 쓰면 어떻게 되는가를 따로 시켜야 합니다.

주문 조회·수정 API의 보안을 데이터 흐름을 따라 검토해 줘. 브라우저 입력에서 시작해 서버의 권한 검사, DB 쿼리, 화면 출력까지 따라가며 표로 정리해. 사용자 번호를 요청이 아니라 세션에서 얻는지, 모든 쿼리가 매개변수화되어 있는지, 비밀값이 브라우저로 가는 코드나 로그에 들어가는지 확인해. 그다음 다른 회원의 주문 번호, 로그인하지 않은 요청, 음수 수량으로 거부되는지 시험하는 테스트를 작성해서 실행해 줘. 확인하지 못한 부분은 따로 적어 줘.

받은 답에서 확인할 것: 권한 검사가 화면이 아니라 서버 코드에 있는가, 거부 테스트가 실제로 실행되어 통과했는가, 거부된 뒤 데이터가 바뀌지 않았는가, "확인하지 못함" 목록이 있는가.

용어 정리#

위협 모델threat model
지킬 것, 상대, 들어오는 길을 정리한 것.
신뢰 경계trust boundary
넘어온 값을 다시 확인해야 하는 경계. 브라우저와 서버 사이가 대표적이다.
인증authentication
요청한 사람이 누구인지 확인하는 일.
인가authorization
확인된 사람이 그 일을 해도 되는지 확인하는 일.
솔트salt
비밀번호를 해시하기 전에 섞는, 회원마다 다른 무작위 값.
다중 인증MFA, Multi-Factor Authentication
종류가 다른 증거를 둘 이상 요구하는 로그인.
세션session
서버가 번호표를 발급하고 장부로 로그인 상태를 기억하는 방식.
JWTJSON Web Token
내용과 서명을 함께 담은 토큰 형식. 내용은 누구나 읽을 수 있다.
OAuth
다른 서비스의 계정으로 제한된 권한을 넘겨받는 약속. 소셜 로그인의 바탕이다.
IDORInsecure Direct Object Reference
번호만 바꿔 남의 데이터에 닿을 수 있는 문제. 대상별 권한 검사가 빠져서 생긴다.
최소 권한least privilege
맡은 일에 필요한 만큼만 권한을 주는 원칙.
공개키 암호public-key cryptography
공개키와 개인키 한 쌍을 쓰는 암호 방식.
전자 서명digital signature
개인키로 만들고 공개키로 확인하는 도장. 누가 만들었고 바뀌지 않았는지 알려 준다.
SQL 인젝션SQL injection
입력이 SQL 문장의 일부로 해석되는 문제. 매개변수화 쿼리로 막는다.
XSSCross-Site Scripting
남이 넣은 스크립트가 내 사이트 방문자의 브라우저에서 실행되는 문제.
CSRFCross-Site Request Forgery
다른 사이트가 사용자의 브라우저를 시켜 쿠키가 붙은 요청을 보내게 하는 공격.

더 읽을거리#

  • OWASP — Authorization Cheat Sheet — 최소 권한, 기본 거부, 요청마다 하는 권한 검사를 정리했습니다.
  • OWASP — Password Storage — 비밀번호 해시와 솔트, Argon2id 설정 권고를 담고 있습니다.
  • OWASP — SQL Injection Prevention — 매개변수화 쿼리를 언어별 예제로 보여 줍니다.
  • MDN — 웹 보안 — XSS, CSP, 쿠키 속성 등 브라우저 보안 기능을 한국어로 훑어볼 수 있습니다.
  • OWASP — LLM Prompt Injection Prevention — AI 에이전트의 권한과 도구 호출을 보호하는 방법을 다룹니다.
