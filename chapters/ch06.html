개발 환경 꾸리기

패키지·설정·권한·원격 접속

읽는 시간 약 35분먼저 읽으면 좋은 장5장 터미널과 셸

친구에게 받은 게임이 내 컴퓨터에서는 실행되지 않을 때가 있습니다. 게임이 잘못된 것이 아니라, 게임을 돌리는 데 필요한 것이 내 컴퓨터에 없어서입니다. 프로그램은 혼자서는 돌아가지 못하고 여러 도구와 설정에 기대어 돌아갑니다. 이것들을 통틀어 개발 환경이라고 합니다. 이 장에서는 그 환경을 갖추고 살펴보는 법을 배웁니다.

이 장을 마치면
  • 프로그램이 돌아가려면 코드 말고 무엇이 더 필요한지 말할 수 있습니다.
  • 필요한 도구를 설치하고 프로젝트마다 따로 관리하는 방법을 설명할 수 있습니다.
  • "권한이 없다"는 오류가 왜 나는지 설명할 수 있습니다.
  • 멀리 있는 컴퓨터에 접속해서 일하는 방법을 설명할 수 있습니다.

6.1코드는 설계도일 뿐입니다#

의자 설계도를 들고 친구의 작업실에 갔다고 해 봅시다. 설계도는 한 글자도 다르지 않습니다. 그런데 친구의 톱은 규격이 다르고, 선반에는 내가 쓰던 나사가 없고, 벽에 붙여 두었던 치수 메모도 없습니다. 같은 의자는 나오지 않습니다.

프로그램도 그렇습니다. 코드는 설계도일 뿐, 실제로 돌아가려면 코드 바깥에 갖춰져야 할 것이 많습니다. 이것들을 통틀어 개발 환경(development environment), 줄여서 환경이라고 부릅니다. 이 장에서는 환경을 작업실로 생각하겠습니다.

그림의 '공구'인 런타임은 Python이나 Node.js처럼 코드를 실행해 주는 프로그램입니다(4장). 서버에서는 requests라는 부품이 없어서 멈췄습니다. 그것을 설치해도 Python 버전이 낮아 새 문법을 읽지 못할 수 있고, API_KEY 메모가 없어 다음 줄에서 멈출 수 있습니다. 운영체제와 CPU가 다르면 받아야 할 부품부터 달라집니다.

핵심

"내 컴퓨터에서는 되는데요"는 작업실이 다르다는 신호입니다. 코드를 고치기 전에 두 작업실에서 무엇이 다른지부터 비교합니다.

6.2환경 변수: 작업실 벽에 붙인 메모#

같은 프로그램을 내 노트북에서는 연습용 데이터베이스에, 서버에서는 진짜 데이터베이스에 연결하고 싶습니다. 그때마다 코드를 고칠 수는 없고, 비밀번호를 코드에 적어 두는 것도 위험합니다.

그래서 이런 값은 코드 밖, 작업실 벽의 메모판에 붙여 둡니다. 이 메모가 환경 변수(environment variable)입니다. 이름=값 꼴의 글자 한 줄입니다.

$ export MODE=dev
$ echo $MODE
dev
$ python3 server.py

export가 메모를 붙이고, $MODE로 그 값을 꺼내 봅니다. 이 셸에서 켠 server.py도 MODE를 읽을 수 있습니다.

그런데 프로그램은 메모판을 계속 쳐다보지 않습니다. 켜지는 순간 메모판 전체를 자기 수첩에 베껴 가고, 그 뒤로는 수첩만 봅니다. 새 프로세스(3장)가 자기를 켠 프로세스의 환경 변수를 물려받는 것입니다.

그래서 환경 변수를 고쳤다면 그 값을 쓸 프로그램을 다시 켜야 합니다. 터미널 창 두 개도 메모판이 따로여서, 한쪽에서 export한 값은 다른 창에 보이지 않습니다.

주의 · 두 가지 함정

값은 언제나 글자입니다. DEBUG=false라고 붙여도 프로그램이 받는 것은 false라는 글자 다섯 개라서, "비어 있지 않으면 켠다"고 짠 코드는 켜짐으로 읽습니다. 또 프로젝트 폴더의 .env 파일에 이름=값을 모아 두는 일이 많은데, 이 파일은 운영체제가 아니라 프로젝트가 쓰는 도구가 읽어 줍니다. 다른 방법으로 실행하면 값이 없을 수 있습니다.

설정이 여러 곳에 있으면 누가 이길까

값을 건네는 길은 보통 네 군데입니다. 서로 다르면 대개 실행하는 순간에 가까운 쪽이 이깁니다.

힘 값이 적힌 곳 예
가장 약함 코드에 적힌 기본값 timeout = 5
↓ 설정 파일 timeout: 10
↓ 환경 변수 TIMEOUT=20
가장 셈 명령줄 옵션 --timeout 30

네 곳에 모두 값이 있으면 30이 쓰이고, 옵션을 빼면 20입니다. "설정 파일을 고쳤는데 그대로예요"는 대부분 더 센 곳에 다른 값이 있거나, 프로그램을 다시 켜지 않은 것입니다. 이 순서는 흔한 관례일 뿐, 도구마다 다를 수 있습니다.

6.3PATH: 공구를 찾아보는 선반 순서#

터미널에 python3라고 치면 셸은 그 이름의 프로그램 파일을 찾아 실행합니다. 폴더가 수만 개인데 어디에서 찾을까요?

작업실에서 "드라이버 좀 줘"라고 하면 조수는 건물 전체를 뒤지지 않습니다. 정해 둔 선반 몇 개를 정해진 순서로 봅니다. 그 선반 목록이 PATH라는 환경 변수입니다.

$ echo $PATH
/opt/homebrew/bin:/usr/local/bin:/usr/bin

폴더 경로를 쌍점(:)으로 이은 목록입니다. 셸은 앞에서부터 들여다보고, 그 이름의 실행 파일이 처음 나온 곳에서 멈춥니다.

이 규칙으로 두 가지 문제가 설명됩니다.

  • command not found. 어느 선반에도 그 이름이 없다는 뜻입니다. 설치하지 않았거나, 설치한 폴더가 PATH에 없는 것입니다.
  • 엉뚱한 버전이 실행된다. 같은 이름이 두 선반에 있으면 앞 선반의 것이 이깁니다.

어느 파일이 뽑혔는지는 which가 경로로 알려 줍니다.

$ which python3
/opt/homebrew/bin/python3
$ export PATH="$HOME/tools/bin:$PATH"
$ which mytool
/Users/mina/tools/bin/mytool

3행은 PATH 맨 앞에 선반 하나를 끼워 넣습니다($HOME은 내 홈 폴더입니다). 이제 mytool도 찾습니다. "설치되어 있다"와 "지금 그것이 실행된다"는 다른 말입니다.

지금 서 있는 폴더는 PATH에 없습니다. 그래서 내 폴더의 스크립트는 ./deploy.sh처럼 경로를 적어 실행합니다.

한 걸음 더새 터미널에도 남기려면: 셸 시작 파일과 dotfiles

export로 붙인 메모는 터미널 창을 닫으면 사라집니다. 계속 쓸 설정은 셸이 켜질 때마다 읽는 시작 파일에 적습니다. zsh는 ~/.zshrc, bash는 ~/.bashrc입니다. 이름이 점으로 시작하는 이런 설정 파일을 dotfiles라고 부릅니다.

고쳐도 이미 열린 터미널에는 적용되지 않습니다. 그리고 내 ~/.zshrc가 있어야만 돌아가는 프로젝트는 동료의 컴퓨터에서 돌지 않습니다.

6.4패키지와 패키지 매니저: 남이 만든 부품 들여오기#

웹 주소에서 데이터를 받아 오는 코드를 직접 짜는 사람은 드뭅니다. 남이 만들어 공개한 라이브러리(4장)를 가져다 씁니다. 라이브러리를 설치하기 좋게 이름과 버전을 붙여 포장한 것이 패키지(package)입니다. 작업실로 치면 규격이 적힌 부품 상자입니다.

부품을 주문하고 받아서 정리하는 일은 패키지 매니저(package manager)가 맡습니다. 패키지가 모여 있는 인터넷의 부품 가게는 레지스트리(registry)입니다.

구분 Python JavaScript (Node.js)
패키지 매니저 pip npm
레지스트리 PyPI npm 레지스트리
필요한 부품을 적는 파일 requirements.txt package.json

pip install requests 한 줄이면 설치됩니다. 그런데 하나를 시켰는데 다섯 개가 들어옵니다.

requests도 다른 패키지 네 개를 가져다 쓰기 때문입니다. 내가 직접 적은 것을 직접 의존성, 거기에 딸려 온 것을 간접 의존성(transitive dependency)이라고 합니다.

requests>=2.31은 "2.31 이상이면 아무거나"라는 범위입니다. 석 달 뒤에 설치하는 동료에게는 더 새 버전이 올 수 있고, 간접 의존성도 마찬가지입니다. 코드는 그대로인데 "새로 설치하니 안 된다"는 일이 여기서 생깁니다.

그래서 설치된 것 전부의 정확한 버전을 파일로 남겨 둡니다. 그림 왼쪽 아래의 잠금 파일(lock file)이고, npm의 package-lock.json이 대표적입니다. 잠금 파일대로 설치하면 누구의 작업실에나 같은 부품이 들어옵니다. 20장에서 자세히 다룹니다.

참고

pip과 npm은 한 언어의 부품을, macOS의 brew나 우분투의 apt는 Python 자체나 Git 같은 컴퓨터 전체의 공구를 설치합니다.

한 걸음 더설치가 복사로 끝나지 않을 때: 네이티브 패키지

대부분의 패키지는 내려받아 폴더에 풀면 설치가 끝납니다. 그런데 속도 때문에 C 같은 언어로 짠 부분을 품은 패키지는 운영체제와 CPU마다 따로 번역한 것이 필요합니다(4장).

맞는 번역본이 레지스트리에 없으면 패키지 매니저는 소스를 받아 직접 컴파일하려 하고, 컴파일러가 없으면 긴 오류가 쏟아집니다. 맨 처음 오류를 찾아 내려받기에서 막혔는지 컴파일에서 막혔는지부터 가르세요.

6.5가상 환경: 프로젝트마다 따로 두는 부품함#

작년에 만든 AI 프로젝트는 numpy 1.26에 맞춰져 있습니다. 새로 시작한 게임 프로젝트는 2.0이 필요합니다. 그런데 pip install은 따로 손쓰지 않으면 하나뿐인 공용 부품함에 넣습니다. 같은 이름의 부품은 한 버전만 둘 수 있어서, 새것을 넣는 순간 옛것이 덮어써집니다.

프로젝트 폴더마다 따로 두는 이 부품함을 Python에서는 가상 환경(virtual environment)이라고 부릅니다.

$ cd ~/mygame
$ python3 -m venv .venv
$ source .venv/bin/activate
(.venv) $ which python
/Users/mina/mygame/.venv/bin/python
(.venv) $ python -m pip install numpy
  • 2행은 이 프로젝트 전용 Python과 빈 부품함이 든 .venv 폴더를 만듭니다.
  • 3행은 가상 환경을 활성화합니다. 프롬프트 앞에 (.venv)가 붙고, 이제 python도 설치도 .venv의 것을 씁니다.

활성화가 하는 일의 핵심은 PATH 맨 앞에 .venv/bin 선반을 끼워 넣는 것입니다. 그래서 새 터미널 창에서는 다시 활성화해야 합니다. Node.js는 처음부터 이 방식이라, npm install은 프로젝트 폴더 안의 node_modules에 설치합니다.

요령 · pip 대신 python -m pip

pip과 python은 PATH에서 따로 찾는 명령이라 서로 다른 Python의 것이 잡힐 수 있습니다. 그러면 설치는 저쪽 부품함에, 실행은 이쪽에서 합니다. python -m pip install은 "지금 이 python의 부품함에"라는 뜻이라 어긋나지 않습니다.

흔한 오해 · 가상 환경은 컴퓨터 안의 또 다른 컴퓨터다

가상 환경이 나누는 것은 어느 Python과 어느 부품함을 쓸지뿐입니다. 그 안에서 실행한 프로그램도 내 문서 폴더를 지울 수 있습니다. 운영체제까지 따로 띄우는 가상 머신(21장)과는 다릅니다.

한 걸음 더엉뚱한 파일이 불려 올 때: 모듈 이름 충돌

import json을 만나면 Python도 PATH처럼 정해진 폴더 목록을 앞에서부터 뒤집니다. 목록의 맨 앞은 보통 실행한 스크립트가 있는 폴더입니다.

그래서 내 프로젝트에 json.py라는 파일을 만들면 표준 json 대신 내 파일이 불려 와 엉뚱한 오류가 납니다. python -c "import json; print(json.__file__)"로 실제로 불려 온 파일을 확인할 수 있습니다.

6.6편집기와 언어 서버: 빨간 밑줄은 누가 긋나#

코드를 쓰는 편집기(editor)는 작업실의 제도 책상입니다. VS Code 같은 편집기는 틀린 곳에 빨간 밑줄을 긋고, 몇 글자만 쳐도 나머지를 채워 주는 자동 완성을 띄웁니다. 편집기가 수십 가지 언어를 다 아는 것일까요?

아닙니다. 책상 옆에 언어마다 따로 둔 검수 조수가 있습니다. 언어 서버(language server)입니다. 편집기와는 별개의 프로그램으로, 프로젝트의 코드와 설치된 패키지를 읽고 분석합니다. 편집기가 "1행이 바뀌었어요"라고 알리면 언어 서버는 "1행에 문제가 있습니다"라고 답합니다. 이 대화의 규칙이 LSP(Language Server Protocol)입니다. 규칙이 하나라서 언어 서버 하나를 여러 편집기가 함께 씁니다.

그림은 흔한 혼란을 보여 줍니다. 터미널에서는 잘 실행되는데 편집기는 import requests에 밑줄을 긋습니다. 조수가 .venv가 아니라 공용 부품함을 들여다보고 있는 것입니다. 고치는 방법은 두 가지입니다.

  1. 파일 하나가 아니라 프로젝트 폴더 전체를 엽니다. 언어 서버는 열린 폴더에서 설정과 가상 환경을 찾습니다.
  2. 편집기에서 사용할 Python을 .venv의 것으로 고릅니다. VS Code에서는 "Python: Select Interpreter" 명령입니다.
핵심

빨간 밑줄은 언어 서버가 본 환경에서의 판정입니다. 밑줄이 없다고 실행이 보장되지 않고, 있다고 반드시 틀린 것도 아닙니다. 마지막 판정은 실제 실행이 내립니다.

편집기의 "정의로 이동"과 "이름 바꾸기"도 언어 서버의 일입니다. 글자가 같은 곳을 전부 찾는 grep과 달리, 그 이름이 가리키는 바로 그 함수나 변수만 따라갑니다.

한 걸음 더글자가 안 쳐지는 편집기: Vim과 모달 편집

서버에서 설정 파일을 고치다 보면 Vim이라는 편집기를 만납니다. 글자를 쳐도 입력되지 않는데, 모드가 있기 때문입니다. 처음 상태인 Normal 모드에서는 키가 "이동하고 고치는 명령"입니다. i를 눌러 Insert 모드로 가야 글자가 입력되고, Esc로 돌아옵니다. 이런 방식이 모달 편집입니다.

나갈 때는 Normal 모드에서 :wq(저장하고 종료)나 :q!(저장하지 않고 종료)를 칩니다.

6.7사용자와 권한: 누가 이 서랍을 열 수 있나#

컴퓨터 한 대를 여러 사람과 프로그램이 함께 씁니다. 남의 파일이나 시스템 파일을 아무나 고치면 곤란하므로, 운영체제는 모든 일에 "누가 하는가"를 따집니다. 로그인한 사용자(user)가 그 '누구'이고, 내가 실행한 프로그램은 내 이름으로 일합니다.

작업실의 서랍마다 "누가 들여다보고, 넣고, 꺼내 쓸 수 있는지" 적힌 딱지가 붙어 있다고 생각하세요. 이것이 파일과 폴더의 권한(permission)입니다.

$ ls -l deploy.sh
-rwxr-xr--  1 mina  staff  214 Nov 12 10:30 deploy.sh

첫 글자가 -이면 파일, d이면 폴더입니다. 그룹은 사용자 여러 명을 묶은 것입니다. 허락되지 않은 일을 하려 하면 운영체제가 Permission denied로 막습니다. 방금 만든 스크립트에 실행 권한이 없을 때 가장 자주 만납니다.

$ ./deploy.sh
zsh: permission denied: ./deploy.sh
$ chmod +x deploy.sh

chmod는 권한을 바꾸는 명령이고, +x는 실행 권한을 붙이라는 뜻입니다.

sudo: 관리인의 만능열쇠

컴퓨터에는 권한 검사를 거의 받지 않는 관리자 root가 있습니다. 명령 앞에 sudo를 붙이면 그 명령 하나를 root의 이름으로 실행합니다. 관리인의 만능열쇠를 잠깐 빌리는 셈입니다. Permission denied에 sudo를 붙이면 대개 통과합니다. 바로 그래서 위험합니다.

  1. 안전장치가 사라집니다. 오타 하나, 잘못된 경로 하나가 시스템 파일까지 건드립니다.
  2. root의 파일이 남습니다. sudo로 실행한 명령이 만든 폴더는 root 소유가 됩니다. 다음부터 평범한 명령이 거기서 막히고, 또 sudo를 부릅니다.
  3. 원인이 가려집니다. 패키지를 공용 부품함에 넣으려다 막혔다면 답은 sudo가 아니라 가상 환경입니다.

모두에게 모든 권한을 주는 chmod 777도 같은 종류의 덮어 두기입니다.

핵심

Permission denied를 만나면 sudo를 붙이기 전에 묻습니다. 누가, 어느 경로에, 무엇을 하려다 막혔는가.

참고

폴더의 x는 그 폴더를 지나갈 수 있다는 뜻입니다. 가는 길의 폴더 하나에 x가 없으면 파일을 열지 못합니다. 또 서버에 늘 켜 두는 프로그램은 나와 다른 사용자의 이름으로 실행되곤 해서, 내 터미널에서 되던 일이 막힐 수 있습니다.

6.8프로세스 보기와 끝내기: "포트가 이미 사용 중"#

작업실에는 켜 둔 채 잊어버린 기계가 있기 마련입니다. 컴퓨터에서는 3장의 프로세스가 그 기계이고, 저마다 PID라는 번호표를 달고 있습니다.

$ ps aux | grep node
mina   4312   0.0   0.4  ...  node server.js

ps aux는 지금 돌아가는 모든 프로세스를 보여 주고, grep이 그중 node가 든 줄만 남깁니다. 둘째 칸의 4312가 PID입니다. 끝내는 방법은 셋이고, 약한 것부터 씁니다.

  • Ctrl+C: 지금 터미널에서 돌고 있는 프로그램에게 "그만"이라고 알립니다.
  • kill 4312: PID로 지목해 "정리하고 끝내 달라"고 요청합니다. 프로그램은 마무리할 기회를 얻습니다.
  • kill -9 4312: 강제 종료입니다. 마무리 없이 끝나서 쓰던 파일이 깨질 수 있는 마지막 수단입니다.

개발 서버를 켰더니 address already in use가 나올 때 이 지식이 쓰입니다. 포트(port)는 한 컴퓨터 안에서 네트워크 연결을 받을 프로그램을 구분하는 번호입니다(14장). 작업실의 접수창구 번호이고, 한 창구에는 한 프로그램만 앉을 수 있습니다.

터미널 창을 닫아도 그 안에서 켠 프로그램이 남아 있을 수 있습니다. lsof -i :3000은 3000번 포트를 쓰는 프로세스를 보여 줍니다. 끝내기 전에 그것이 정말 내가 켠 서버인지 확인하세요.

한 걸음 더계속 돌려 두려면: 작업 제어, tmux, 서비스 관리자
  • 작업 제어. 명령 끝에 &를 붙이면 뒤에서 실행됩니다. Ctrl+Z는 일시 정지, bg는 뒤에서 이어 가기, fg는 다시 앞으로 가져오기입니다.
  • tmux. 터미널 화면을 서버 쪽에 살려 두는 도구입니다. 접속이 끊겨도 작업은 계속 돌고, tmux attach로 돌아옵니다. 서버가 재부팅되면 사라집니다.
  • 서비스 관리자. 재부팅 뒤에도 자동으로 켜고, 죽으면 다시 살립니다. 리눅스의 systemd가 대표적입니다.

6.9원격 서버와 SSH: 멀리 있는 작업실에서 일하기#

AI 모델을 돌리는 GPU 컴퓨터도, 24시간 켜 둘 웹 서버도 대개 멀리 있고 화면이 없습니다. 이런 컴퓨터의 셸에 내 터미널을 연결해 주는 것이 SSH(Secure Shell)입니다. 오가는 글자는 모두 암호화됩니다.

mina@macbook ~ % ssh mina@203.0.113.10
mina@gpu-server:~$

ssh 사용자@주소 꼴입니다. 접속되면 프롬프트의 컴퓨터 이름이 바뀌고, 이때부터 치는 명령은 저쪽 작업실에서 실행됩니다. ls는 서버의 파일을 보여 주고, python3는 서버의 PATH에서 찾은 서버의 Python입니다. 노트북에 설치한 패키지는 소용이 없습니다. exit를 치면 돌아옵니다.

비밀번호 대신 키, 그리고 서버 지문

SSH는 접속할 때 확인을 두 방향으로 합니다.

먼저 내가 서버를 확인합니다. 처음 접속하는 서버라면 이런 질문이 나옵니다.

ED25519 key fingerprint is SHA256:Xk3f...9QeM.
Are you sure you want to continue connecting (yes/no/[fingerprint])?

서버마다 고유한 키가 있고, 지문(fingerprint)은 그 키를 짧게 줄인 값입니다. 서버 관리자가 알려 준 지문과 같으면 yes라고 답합니다. 노트북은 이 지문을 known_hosts 파일에 적어 두고 다음부터 알아서 대조합니다. 어느 날 지문이 바뀌었다는 경고가 뜬다면 서버를 새로 설치했거나, 누군가 중간에서 서버인 척하는 것입니다. 이유를 알기 전에는 넘어가지 않습니다.

그다음 서버가 나를 확인합니다. 비밀번호는 추측당할 수 있습니다. 그래서 ssh-keygen으로 짝이 맞는 파일 두 개를 만들어 씁니다.

  • 공개 키(public key)는 자물쇠입니다. 서버의 authorized_keys 파일에 등록합니다. 남이 봐도 괜찮습니다.
  • 개인 키(private key)는 열쇠입니다. 내 노트북에만 둡니다. 채팅에도, 코드 저장소에도, AI 대화창에도 붙여 넣지 않습니다.

노트북이 개인 키로 서명을 만들어 보내면, 서버는 등록된 공개 키로 그 서명이 진짜인지 확인합니다. 열쇠 자체는 전선을 타지 않습니다.

포트 포워딩: 두 개의 localhost

서버에서 앱을 8000번 포트로 켰고, 노트북의 브라우저로 보고 싶습니다. 그런데 개발용 서버는 보통 같은 컴퓨터 안에서 온 연결만 받습니다. 그리고 localhost는 언제나 "그 말을 한 컴퓨터 자신"입니다(14장). 노트북 브라우저에 localhost:8000을 치면 노트북의 8000번을 두드릴 뿐입니다.

$ ssh -L 9000:localhost:8000 mina@203.0.113.10

-L 옵션이 만드는 이 연결이 포트 포워딩(port forwarding)입니다. 뒤쪽 localhost를 읽는 쪽은 서버이므로 서버 자신을 가리킵니다. 이제 노트북 브라우저에서 localhost:9000을 열면 서버의 앱이 보입니다.

한 걸음 더파일 옮기기와 원격 편집: scp, rsync
  • scp report.pdf mina@203.0.113.10:~/docs/는 SSH 통로로 파일을 복사합니다. 쌍점 뒤가 서버 안의 경로입니다.
  • rsync는 두 폴더에서 달라진 것만 보냅니다. 받는 쪽 파일을 지우는 옵션도 있으니 --dry-run으로 무엇이 바뀔지 먼저 봅니다.
  • VS Code의 원격 개발 기능은 화면만 노트북에 두고 언어 서버와 터미널은 서버에서 돌립니다. 패키지도 서버에 설치해야 빨간 밑줄이 사라집니다.

실전 사례#

실전 사례 · 패키지를 설치했는데 없다고 한다

AI가 시킨 대로 pip install requests를 실행했고 Successfully installed까지 봤습니다. 그런데 편집기의 실행 버튼을 누르면 ModuleNotFoundError가 납니다.

  1. 다시 설치하지 않습니다. 의심할 것은 "어느 부품함에 넣었고, 어느 Python이 실행했는가"입니다.
  2. 설치한 쪽을 확인합니다. pip --version은 그 pip이 속한 Python의 경로도 보여 줍니다. /opt/homebrew/lib/python3.12/..., 공용 Python입니다.
  3. 실행한 쪽을 확인합니다. 코드 맨 위에 import sys; print(sys.executable)을 넣고 실행하니 /Users/mina/mygame/.venv/bin/python이 찍힙니다. 가상 환경입니다.
  4. 둘을 맞춥니다. 터미널에서 가상 환경을 활성화하고 python -m pip install requests로 설치합니다.
  5. 확인합니다. 터미널과 편집기 양쪽에서 실행해 봅니다.

"설치했다"는 말에는 언제나 어느 부품함에가 빠져 있습니다. 설치한 쪽과 실행한 쪽의 경로를 나란히 놓으면 답이 보입니다.

한눈에 정리#

  • 코드는 설계도이고, 실행 결과는 작업실(환경)이 함께 정합니다. 안 되면 두 작업실의 차이부터 비교합니다.
  • 환경 변수는 프로그램이 켜질 때 복사해 가는 메모입니다. 바꿨으면 프로그램을 다시 켭니다.
  • PATH는 명령을 찾는 폴더 순서입니다. 앞 선반에서 먼저 나온 것이 실행됩니다.
  • 패키지에는 간접 의존성이 딸려 옵니다. 잠금 파일이 그 전부의 정확한 버전을 기록합니다.
  • 가상 환경은 프로젝트마다 따로 두는 부품함입니다. 설치와 실행이 같은 Python인지 봅니다.
  • Permission denied와 "포트가 이미 사용 중"은 sudo, kill -9보다 원인 확인이 먼저입니다.
  • SSH로 접속한 뒤의 명령은 서버에서 실행됩니다. localhost는 그 말을 한 컴퓨터 자신입니다.

설정 파일에서 timeout을 10으로 고치고 서버도 다시 켰는데 여전히 20으로 동작합니다. 어디를 봐야 할까요?

정답 보기

설정 파일보다 센 곳을 봅니다. 서버를 켜는 셸에 TIMEOUT=20이라는 환경 변수가 있거나 실행 명령에 --timeout 20이 붙어 있을 수 있습니다.

ssh -L 9000:localhost:8000 mina@203.0.113.10으로 접속해 둔 채 노트북 브라우저에서 localhost:9000을 열었습니다. 어느 컴퓨터의 몇 번 포트에 닿을까요?

정답 보기

서버의 8000번입니다. 명령 속의 localhost는 서버가 읽으므로 서버 자신입니다. 연결이 거부되면 서버에서 앱이 8000번으로 켜져 있는지부터 봅니다.

AI에게 맡길 때#

AI에게 맡길 때

환경 문제를 만난 AI 도구는 재설치나 sudo로 밀어붙이는 일이 많습니다. 고치기 전에 두 작업실의 차이부터 조사하게 하세요.

터미널에서는 실행되는데 편집기의 실행 버튼으로는 ModuleNotFoundError가 나. 재설치하거나 sudo를 쓰기 전에 조사부터 해 줘. 두 경우의 작업 디렉터리, 실행된 python의 경로와 버전, 패키지가 설치된 위치, 관련 환경 변수를 표로 비교해 줘. 비밀 값은 이름만 보여 줘. 그다음 가장 작은 변경을 제안하고, 같은 방법으로 다시 실행해 확인해 줘. 전역 설치와 시스템 설정 변경은 하지 마.

받은 답에서 확인할 것: 추측이 아니라 which 출력 같은 실제 값을 보여 주는가, 변경이 프로젝트 폴더 안에 머무는가, sudo나 chmod 777, kill -9를 이유 없이 쓰지 않았는가.

용어 정리#

환경 변수environment variable
프로그램이 켜질 때 바깥에서 건네받는 이름=값 꼴의 글자.
PATH
명령의 실행 파일을 찾을 폴더 목록. 앞에서부터 찾는다.
패키지package
남이 만든 코드에 이름과 버전을 붙여 설치하기 좋게 포장한 것.
패키지 매니저package manager
레지스트리(패키지 저장소)에서 패키지를 받아 설치하는 도구. pip, npm 등.
간접 의존성transitive dependency
내가 쓰는 패키지가 필요로 해서 함께 설치되는 패키지.
잠금 파일lock file
설치된 모든 패키지의 정확한 버전을 기록한 파일.
가상 환경virtual environment
프로젝트마다 따로 두는 Python과 패키지 폴더.
언어 서버language server
코드를 분석해 오류 표시와 자동 완성을 해 주는 별도 프로그램.
LSPLanguage Server Protocol
편집기와 언어 서버가 주고받는 메시지의 규칙.
권한permission
누가 그 파일을 읽고, 쓰고, 실행할 수 있는지 정한 것.
sudo
명령 하나를 관리자(root)의 이름으로 실행하는 명령.
SSHSecure Shell
암호화된 연결로 멀리 있는 컴퓨터의 셸을 쓰는 도구.
공개 키와 개인 키public key / private key
짝이 맞는 키 한 쌍. 공개 키는 서버에, 개인 키는 내 컴퓨터에만 둔다.
포트 포워딩port forwarding
내 컴퓨터의 포트로 들어온 연결을 SSH 통로 건너편의 포트로 넘기는 것.
