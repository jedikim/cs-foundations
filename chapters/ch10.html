상태와 프로그램 설계

버그가 덜 생기는 구조

읽는 시간 약 35분먼저 읽으면 좋은 장8장 자료구조

프로필 편집 화면에서 '취소'를 눌렀는데 태그가 이미 바뀌어 있습니다. 장바구니에는 상품이 세 개인데 배지에는 2라고 적혀 있습니다. '서울역'을 검색했는데 잠시 뒤 화면이 '서울' 결과로 돌아갑니다. 셋 다 계산이 틀린 것이 아닙니다. 프로그램이 기억하고 있던 것이 꼬인 것입니다.

이 장을 마치면
  • 화면 뒤에서 어떤 상태가 화면을 정하는지, 그 상태의 주인이 누구인지 말할 수 있습니다.
  • 같은 사실을 두 곳에 적지 않고, 계산하면 나오는 값은 저장하지 않는 구조를 잡을 수 있습니다.
  • "복사했는데 같이 바뀐다", "로딩과 오류가 동시에 뜬다" 같은 버그의 원인을 설명할 수 있습니다.
  • 해제하지 않은 구독, 늦게 도착한 응답처럼 시간이 만드는 버그를 미리 막을 수 있습니다.

10.1상태: 프로그램이 기억하고 있는 것#

계산기에서 2 + 3은 언제 눌러도 5입니다. 쇼핑 앱의 '담기' 버튼은 다릅니다. 처음 누르면 장바구니가 1개, 한 번 더 누르면 2개가 됩니다. 같은 버튼인데 결과가 다릅니다. 프로그램이 앞에서 있었던 일을 기억하고 있기 때문입니다.

프로그램이 지금 기억하고 있는 것을 상태(state)라고 합니다. 장바구니에 담긴 상품, 로그인한 사람, 입력 칸에 친 글자, "지금 불러오는 중인가"까지 모두 상태입니다.

비유로 이해하기 · 가게의 장부

분식집 카운터에 장부가 한 권 있습니다. 직원은 장부에 적힌 주문과 재고를 보고 다음 일을 정합니다. 장부가 틀리면 직원이 아무리 성실해도 가게는 틀리게 돌아갑니다. 이 장에서는 상태를 장부에 빗대겠습니다.

화면은 장부를 보고 그린 그림입니다. 장부가 바뀌면 화면을 다시 그리고, 버튼을 누르면 장부를 고칩니다.

계산은 틀리면 금방 드러납니다. 장부는 다릅니다. 한참 전에 잘못 적힌 한 줄이 나중에 엉뚱한 화면에서 사고를 냅니다. 장부가 꼬이는 길은 크게 네 가지입니다.

  1. 같은 사실을 두 군데에 적고 한쪽만 고쳤다.
  2. 고치면 안 되는 곳에서 몰래 고쳤다.
  3. "조리 중이면서 취소됨"처럼 있을 수 없는 내용이 적혔다.
  4. 늦게 도착한 소식이 최신 내용을 덮어썼다.

이 장은 이 네 가지를 구조로 막는 방법을 다룹니다. 코드는 JavaScript로 적습니다.

한 걸음 더노트북 셀의 숨은 상태

Jupyter 같은 노트북에서 셀을 실행하면, 만든 변수는 커널이라는 실행 프로그램의 메모리에 남습니다(운영체제의 커널과는 이름만 같습니다).

A 셀에서 x = 2를, B 셀에서 print(x * 3)을 실행하면 6이 나옵니다. A 셀의 글자만 x = 10으로 고치고 B만 다시 실행해도 6입니다. 고친 A를 실행한 적이 없으니 커널의 x는 아직 2입니다. 화면의 글자와 커널의 기억은 따로 놉니다.

그래서 결과를 남에게 보여 주기 전에는 커널을 다시 시작해 위에서부터 전부 실행해 봅니다.

10.2함수와 클로저: 기억은 어디에 사는가#

장부를 지키려면 먼저 기억이 어디에 사는지 알아야 합니다.

함수(function)는 입력을 받아 일을 하고 결과를 돌려주는 코드 묶음입니다. 함수 안에서 만든 변수는 그 함수 안에서만 보입니다. 이렇게 이름이 보이는 범위를 스코프(scope)라고 합니다. 직원이 일하는 동안만 쓰는 개인 메모지와 같습니다. 남은 볼 수 없고, 일이 끝나면 버립니다.

그런데 메모지를 버리지 않고 들고 나오는 함수가 있습니다.

function makeCounter() {
  let n = 0;
  return () => ++n;
}
const a = makeCounter();
const b = makeCounter();
a(); a(); b();   // 차례로 1, 2, 1

3행의 () => ++n은 "n을 1 늘려서 돌려주는 이름 없는 함수"입니다. makeCounter는 이 함수를 내보내고 끝나지만 n은 사라지지 않습니다. 내보낸 함수가 계속 쓰기 때문입니다. 이렇게 자기가 만들어진 곳의 변수를 붙잡고 있는 함수를 클로저(closure)라고 합니다.

붙잡힌 n은 밖에서 직접 고칠 길이 없습니다. 상태를 숨기는 가장 작은 금고입니다. 대신 그 함수가 살아 있는 동안에는 n도 사라지지 않습니다.

계산만 하는 함수, 바깥을 바꾸는 함수

순수 함수(pure function)는 입력만 보고 결과만 돌려줍니다. 같은 입력에는 언제나 같은 결과가 나오고, 장부는 건드리지 않습니다. 금액 목록을 받아 합계를 돌려주는 함수가 그렇습니다.

반대로 함수가 자기 바깥의 무언가를 바꾸는 것을 부수 효과(side effect)라고 합니다. 바깥 변수 고치기, 화면 바꾸기, 파일 저장, 결제 요청 보내기가 모두 부수 효과입니다.

부수 효과가 나쁜 것은 아닙니다. 저장도 결제도 못 하는 앱은 쓸모가 없습니다. 문제는 계산인 줄 알았던 함수에 효과가 숨어 있을 때입니다. 화면을 그리는 함수는 필요할 때마다 다시 불립니다. 그 안에 결제 요청이 섞여 있으면 화면이 다시 그려질 때마다 결제가 나갑니다.

핵심

계산은 순수 함수로, 바깥을 바꾸는 일은 눈에 띄는 한곳에서 합니다.

10.3객체와 인터페이스: 장부는 창구로만 고칩니다#

장바구니에는 규칙이 있습니다. 같은 상품을 또 담으면 수량을 합치고, 수량은 1 이상이어야 합니다. 그런데 cart.items 배열을 누구나 직접 고칠 수 있다면 규칙을 모르는 코드가 섞여 듭니다. 장부를 카운터에 펼쳐 두고 아무나 적게 하는 꼴입니다.

그래서 데이터와 그 데이터를 고치는 함수를 한 묶음으로 만듭니다. 이 묶음이 객체(object)이고, 같은 모양의 객체를 찍어 내는 틀이 클래스(class)입니다.

그리고 안쪽 데이터는 숨기고 addItem() 같은 정해진 함수로만 고치게 합니다. 이것이 캡슐화(encapsulation)입니다. 장부를 창구 안쪽에 두고 창구 직원만 적게 하는 것입니다.

밖에 열어 둔 창구의 목록과 약속을 인터페이스(interface)라고 합니다.

비유로 이해하기 · 콘센트 규격

벽의 콘센트는 구멍 모양과 전압만 약속합니다. 약속만 맞으면 어떤 가전제품이든 꽂을 수 있고, 벽 뒤의 배선을 바꿔도 가전제품은 그대로 씁니다. addItem(상품)이라는 약속만 지키면, 안에서 쓰던 배열을 해시 맵으로 바꿔도 부르는 쪽은 고칠 것이 없습니다.

물려받기보다 끼워 넣기

기능을 다시 쓰는 방법은 두 가지입니다. 상속(inheritance)은 기존 클래스의 것을 통째로 물려받고, 조합(composition)은 필요한 기능을 부품으로 만들어 끼워 넣습니다.

게임에서 상속으로 '나는 캐릭터'와 '헤엄치는 캐릭터'를 만들면, 날면서 헤엄치는 캐릭터가 필요할 때 막힙니다. 조합에서는 '날기 부품'과 '헤엄 부품'을 필요한 만큼 꽂습니다. 코드가 겹친다는 이유뿐이라면 상속보다 조합이 먼저입니다.

약속에는 '없음'과 '실패'도 적습니다

회원을 찾는 함수가 null(값이 없다는 표시)을 돌려줬습니다. 그런 회원이 없을 수도, 볼 권한이 없을 수도, 서버가 잠깐 멈췄을 수도 있습니다. 경우마다 다음에 할 일이 다릅니다.

결과 뜻 다음에 할 일
찾음 회원 정보가 있다 화면에 보여 준다
없음 정상인데 그런 회원이 없다 가입을 안내한다
거절 볼 권한이 없다 접근을 막는다
장애 지금은 알 수 없다 잠시 뒤 다시 시도한다

넷을 null 하나로 뭉치면 서버가 멈췄는데 가입 화면이 뜹니다. 없음은 정상 결과이고, 실패는 사고입니다. 결과에 found, not_found 같은 이름표를 붙여 돌려주면 부르는 쪽이 헷갈리지 않습니다.

한 걸음 더다형성과 대체 가능성

같은 인터페이스 뒤에 여러 구현을 둘 수 있습니다. save(data) 뒤에 파일 저장소가 있든 서버 저장소가 있든 부르는 쪽은 save만 부릅니다. 이것이 다형성(polymorphism)입니다.

다만 이름이 같다고 바꿔 끼워도 되는 것은 아닙니다. 파일 저장은 성공 아니면 실패지만, 서버 저장에는 "보냈는데 답이 없어 결과를 모름"이 있습니다. 구현을 바꿔도 부르는 쪽이 기대한 약속이 그대로일 때만 안전합니다. 이 성질이 대체 가능성입니다.

10.4원본은 한 곳에: 주인과 파생 값#

첫머리의 장바구니 버그로 돌아갑시다. 상품은 세 개인데 배지에는 2라고 나옵니다. 코드를 보니 상품 목록 items와 개수 count를 따로 저장하고 있었습니다. 담을 때도 지울 때도 둘을 함께 고칩니다. 그런데 '삭제 취소' 기능을 나중에 붙이면서 count를 되돌리는 줄을 빠뜨렸습니다.

개수는 목록을 세면 나옵니다. 이렇게 다른 상태에서 계산하면 나오는 값을 파생 값(derived value)이라고 합니다. 합계, 걸러 낸 목록, "전부 선택됨" 표시가 모두 파생 값입니다. 필요할 때마다 원본에서 계산하면 어긋날 방법이 없습니다.

핵심

같은 사실은 한 곳에만 적습니다. 계산하면 나오는 것은 저장하지 않습니다.

참고

이미 끝난 주문의 결제 금액은 파생 값이 아닙니다. 나중에 김밥 값이 올라도 그날 낸 돈은 그대로여야 하므로, "그때 일어난 사실"로 따로 적어 둡니다.

더 큰 데이터도 같습니다. 댓글마다 글쓴이의 이름을 복사해 넣으면, 이름을 바꿀 때 댓글 백 개를 찾아 고쳐야 합니다. 댓글에는 userId: 7처럼 8장에서 배운 ID만 적고, 보여 줄 때 7번 회원의 이름을 읽어 옵니다. 이름이 적힌 곳이 하나뿐이니 고칠 곳도 하나입니다.

여러 사본 가운데 "이것이 진짜"라고 정해 둔 한 곳을 기준 데이터(source of truth), 쉽게 말해 원본이라고 합니다. 원본마다 주인을 하나만 둡니다. 주인만 그 값을 고치고, 나머지는 읽기만 하거나 주인에게 고쳐 달라고 부탁합니다.

흔한 오해 · 모든 상태를 어디서나 쓰는 전역 저장소에 넣으면 관리가 쉽다

주인이 하나라는 말은 전부 한 바구니에 담으라는 뜻이 아닙니다. 어디서나 고칠 수 있는 값은 누가 고쳤는지 찾기 어렵습니다. 상태는 그것을 쓰는 가장 좁은 범위에 둡니다. 입력 중인 글자의 주인은 그 입력 화면입니다.

10.5복사했는데 같이 바뀐다: 얕은 복사#

프로필 편집 화면을 만듭니다. 원본을 복사해 초안을 만들고, '취소'를 누르면 초안만 버리면 됩니다. 그런데 취소했는데도 원본의 태그가 바뀌어 있습니다.

const original = { name: "하늘", tags: ["업무"] };
const draft = { ...original };   // 칸들을 새 객체에 옮겨 담는다
draft.name = "바다";             // 원본은 그대로 "하늘"
draft.tags.push("긴급");         // 원본의 tags도 바뀐다

3장에서 본 것처럼, 객체의 칸에는 배열 자체가 아니라 배열이 있는 곳을 적은 쪽지(참조)가 들어 있습니다. 2행은 바깥 상자를 새로 만들고 칸의 내용을 옮겨 적습니다. name 칸의 글자는 값이 그대로 옮겨집니다. 하지만 tags 칸에 든 것은 쪽지입니다. 쪽지만 옮겨 적었으니 두 상자가 같은 배열을 가리킵니다.

이렇게 겉만 새로 만드는 복사가 얕은 복사(shallow copy)입니다. 장부의 표지만 새로 만들고 속지는 같은 것을 끼워 둔 셈입니다. 안쪽까지 전부 새로 만드는 복사는 깊은 복사(deep copy)입니다.

고치는 방법은 두 가지입니다. 고칠 곳만 한 겹 더 복사하거나(tags: [...original.tags]), 통째로 깊은 복사를 합니다(structuredClone(original)). 깊은 복사는 간단하지만 데이터가 크면 그만큼 시간과 메모리가 듭니다. "복사했다"는 말을 들으면 어디까지 따로이고 어디부터 함께 쓰는지 물어보세요.

직접 해 보기

브라우저 개발자 도구(F12)의 콘솔에 위 네 줄을 붙여 넣고 original.tags를 쳐 보세요. 건드린 적 없는 원본에 "긴급"이 들어 있습니다.

10.6고치지 말고 새로 쓰기: 불변 업데이트와 실행 취소#

함께 써서 생기는 사고를 뿌리부터 막는 규칙이 있습니다. 한 번 만든 값은 고치지 않는다는 규칙입니다. 바꿀 일이 생기면 바뀐 내용으로 새 값을 만들어 통째로 갈아 끼웁니다. 이것을 불변 업데이트(immutable update)라고 합니다. 장부에 지우개를 쓰지 않는 것입니다. 고칠 일이 있으면 새 쪽에 다시 적고, 옛 쪽은 그대로 둡니다.

const next = { ...user, name: "바다" };

user에는 손대지 않았고, 이름만 다른 새 객체 next가 생겼습니다. 얻는 것이 세 가지입니다.

  • 옛 값을 들고 있던 다른 코드가 몰래 바뀐 값을 보는 일이 없습니다.
  • 바뀌었는지 알려면 쪽지가 같은지만 보면 됩니다. React 같은 화면 도구가 이 방법을 쓰기 때문에, 객체 안을 직접 고치면 화면이 바뀌지 않는 일이 생깁니다.
  • 옛 쪽이 남아 있으니 되돌리기가 쉽습니다.

실행 취소: 과거, 현재, 미래 세 칸

실행 취소(undo)는 옛 쪽을 다시 펼치는 일입니다. 버전을 과거, 현재, 미래 세 칸에 나눠 담습니다. 고칠 때마다 그전의 현재를 과거 칸에 넣습니다. 취소하면 과거에서 하나를 꺼내 현재로 삼고, 밀려난 것은 미래 칸으로 보냅니다. 다시 실행(redo)은 그 반대입니다.

주의 · 장부 밖의 일은 취소되지 않습니다

실행 취소가 되돌리는 것은 프로그램 안의 상태뿐입니다. 이미 보낸 메일이나 끝난 결제는 환불처럼 반대 방향의 일을 새로 해야 합니다.

한 걸음 더서로 가리키는 객체와 아주 큰 데이터

순환 참조. 부모가 자식을 가리키고 자식이 다시 부모를 가리키면 쪽지를 따라가는 길이 원이 됩니다. 단순하게 짠 깊은 복사는 이 원을 끝없이 돌고, JSON으로 바꾸려 하면 오류가 납니다. 저장할 때는 자식에 parentId만 적어 원을 끊습니다.

구조 공유. 블록이 천 개인 문서에서 한 블록만 고칠 때는 새 목록과 고친 블록 하나만 만들고, 나머지 999개는 옛 버전과 함께 씁니다. 아무도 값을 직접 고치지 않으니 함께 써도 안전합니다. 이것이 구조 공유(structural sharing)입니다.

10.7상태 기계: 있을 수 없는 상태를 못 만들게#

저장 버튼을 눌렀더니 로딩 표시와 "저장 완료"와 오류 문구가 한꺼번에 떴습니다. 코드에는 isLoading, isSuccess, isError라는 참·거짓 값이 세 개 있었습니다.

세 개로 만들 수 있는 조합은 2 × 2 × 2 = 8가지인데, 말이 되는 것은 네 가지뿐입니다. 나머지 네 가지는 값을 되돌리는 코드 한 줄만 빠뜨려도 만들어집니다.

해결은 상태를 이름 하나로 적는 것입니다. status 칸 하나에 "idle"(대기), "saving"(저장 중), "done"(완료), "error"(오류) 중 하나만 적습니다. 주문서에 도장 칸이 하나뿐이면 '조리 중'과 '취소'가 동시에 찍힐 수 없는 것과 같습니다.

이렇게 가능한 상태의 목록과 무슨 일이 생기면 어느 상태로 넘어가는지를 정해 둔 것을 상태 기계(state machine)라고 합니다. 상태가 넘어가는 것은 전이(transition)라고 부릅니다.

상태마다 딸린 데이터도 함께 정합니다. 받아 온 데이터는 완료일 때만, 실패한 이유는 오류일 때만 있습니다. 빈 목록 []도 구분합니다. 성공했는데 결과가 0건인 것은 받는 중인 것과도, 실패한 것과도 다릅니다.

고치는 규칙을 함수 하나에

전이 규칙이 버튼 처리 코드, 타이머, 응답 처리 코드에 흩어져 있으면 서로 다르게 적히기 쉽습니다. 그래서 순수 함수 하나에 모읍니다. 지금 상태와 일어난 일을 받아 다음 상태를 돌려주는 이런 함수를 리듀서(reducer)라고 부릅니다.

function next(state, event) {
  if (state.status === "idle" && event.type === "submit")
    return { status: "saving" };
  if (state.status === "saving" && event.type === "ok")
    return { status: "done", data: event.data };
  if (state.status === "saving" && event.type === "fail")
    return { status: "error", reason: event.reason };
  return state;   // 그 밖의 조합은 무시한다
}

if 하나가 그림의 화살표 하나입니다('다시 시도'도 한 줄 더하면 됩니다). 마지막 줄 덕분에 저장 중에 저장 버튼을 또 눌러도 아무 일이 없습니다. 두 번 저장되는 버그가 구조에서 사라집니다.

부탁과 사실을 구분하기

명령(command)은 "해 주세요"라는 부탁이고, 거절될 수 있습니다. 이벤트(event)는 "이미 일어났습니다"라는 사실입니다. '주문하기' 버튼을 누르자마자 "주문 완료"를 알리면 저장에 실패해도 알림이 나갑니다. 완료 알림은 저장이 끝났다는 답을 받은 뒤에 보냅니다.

한 걸음 더상태 안의 상태: 계층 상태 기계

문서 앱의 '대기', '저장 중', '편집 중' 어느 상태에서든 인터넷이 끊기면 '오프라인'으로 가야 합니다. 상태마다 화살표를 그리면 같은 규칙이 세 번 반복됩니다. 세 상태를 '온라인'이라는 큰 상태로 묶고 화살표를 한 번만 그립니다. 상태 안에 상태를 넣는 이 방식이 계층 상태 기계입니다.

한 걸음 더답을 기다리지 않고 먼저 바꾸기: 낙관적 갱신

'좋아요'를 누르면 하트가 바로 빨개집니다. 서버의 답을 기다리지 않고, 성공하리라 믿고 화면부터 바꾼 것입니다. 이것이 낙관적 갱신(optimistic update)입니다. 실패하면 되돌려야 하는데, 그 사이에 한 다른 변경까지 지우지 않도록 실패한 작업만 되돌립니다. 결제 완료처럼 틀리면 안 되는 것은 서버의 답을 받은 뒤에만 표시합니다.

10.8바뀌면 알려 주기: 구독과 뒷정리#

장바구니가 바뀌면 배지도, 합계도, 주문 버튼도 다시 그려야 합니다. 장바구니 코드가 셋을 하나하나 부르면, 화면이 늘 때마다 장바구니 코드를 고쳐야 합니다.

가게에서는 "떡볶이 다시 나오면 알려 주세요" 하는 손님의 연락처를 명단에 적어 두고, 나오면 명단의 모두에게 알립니다. 프로그램에서는 "바뀌면 이 함수를 불러 달라"고 등록하는 것이 구독(subscribe), 바뀌었을 때 등록된 함수를 모두 부르는 것이 발행(publish)입니다. 알리는 쪽은 누가 듣는지 몰라도 됩니다.

함정이 하나 있습니다. 명단에서 이름을 빼는 일은 저절로 되지 않습니다.

const unsubscribe = cart.subscribe(updateBadge);  // 화면을 열 때
unsubscribe();                                    // 화면을 닫을 때

1행은 구독하면서 해제용 함수를 받아 둡니다. 2행을 빠뜨리면 닫힌 화면의 함수가 명단에 남고, 화면을 다시 열면 하나가 더 등록됩니다.

증상은 "같은 알림이 두 번, 세 번 뜬다", "들어갔다 나올수록 느려진다"입니다. 명단에 남은 함수는 클로저라서 닫힌 화면의 데이터까지 붙잡고 있습니다. 3장에서 본 메모리 누수의 흔한 원인입니다.

타이머, 열어 둔 파일, 서버와의 연결처럼 쓰고 나서 정리해야 하는 것을 통틀어 자원(resource)이라고 합니다. 규칙은 하나입니다. 만든 곳이 치웁니다. 화면을 열 때 만든 것은 그 화면을 닫을 때 정리합니다. 화면을 열 번 열고 닫은 뒤 구독 수가 처음과 같은지 세어 보면 확인할 수 있습니다.

한 걸음 더알아서 다시 계산해 주는 도구: 반응형과 묶어서 갱신하기

요즘 화면 도구는 "합계는 가격과 수량을 읽는다"는 관계를 기억했다가, 둘 중 하나가 바뀌면 합계를 알아서 다시 계산합니다. 이것이 반응형(reactive)이고, 무엇이 무엇을 읽는지가 의존성(dependency)입니다. 의존성을 손으로 적는 도구에서 쿠폰을 빠뜨리면, 쿠폰을 바꿔도 합계가 옛 값으로 남습니다.

이런 도구는 변경 요청을 모았다가 화면을 한 번만 다시 그리기도 합니다. 배칭(batching)입니다. React에서 클릭 한 번에 setCount(count + 1)을 세 번 불러도 1만 늘어납니다. 셋 다 같은 옛 count로 계산했기 때문입니다. setCount(c => c + 1)처럼 함수를 넘기면 3이 늘어납니다.

10.9늦게 도착한 응답: 번호표로 걸러 내기#

검색창에 '서울'을 치자 프로그램이 서버에 검색을 요청했습니다. 이어서 '역'을 치자 '서울역' 요청이 또 나갔습니다. 그런데 서버가 '서울역'에 먼저 답하고, '서울'에는 한참 뒤에 답했습니다. 화면은 '서울역' 결과를 잠깐 보여 주다가 '서울' 결과로 바뀌어 버립니다.

요청은 보낸 순서대로 돌아온다는 보장이 없습니다. "응답이 오면 화면에 반영한다"는 코드는 요청이 하나일 때만 옳습니다.

은행 창구의 번호표가 해결책입니다. 요청마다 번호를 붙이고, 응답이 왔을 때 지금 기다리는 번호가 맞는지 확인합니다.

let latest = 0;
async function search(word) {
  const id = ++latest;
  const result = await fetchResults(word);
  if (id !== latest) return;   // 옛 요청의 응답은 버린다
  show(result);
}

3행에서 번호표를 뽑습니다. 2행의 async와 4행의 await는 응답이 올 때까지 이 함수만 잠시 멈춰 둔다는 표시입니다(11장에서 다룹니다). 기다리는 사이에 search가 또 불리면 latest가 올라갑니다. 5행에서 내 번호 id가 최신 번호와 다르면 조용히 물러납니다. id는 부를 때마다 따로 생기는, 클로저가 붙잡은 값입니다.

화면을 떠난 뒤에 도착한 응답도 같은 방법으로 걸러 냅니다. 필요 없어진 요청은 취소까지 하면 더 좋지만, 취소가 한발 늦을 수 있으므로 번호 확인은 남겨 둡니다.

핵심

기다림이 끼어드는 곳마다 물어보세요. "이 응답이 도착했을 때, 화면은 아직 이 응답을 기다리고 있는가?"

실전 사례#

실전 사례 · 취소를 눌렀는데 프로필이 바뀌어 있다

AI가 만들어 준 프로필 편집 화면입니다. 태그를 추가하고 '취소'를 눌렀는데 프로필에 그 태그가 보입니다. 저장 버튼을 빠르게 두 번 누르면 저장도 두 번 됩니다.

  1. 다시 일으켜 봅니다. 이름만 고치고 취소하면 멀쩡하고, 태그를 고쳤을 때만 문제가 생깁니다. 안쪽에 든 배열이 수상합니다.
  2. 쪽지를 비교합니다. draft.tags === original.tags를 찍어 보니 true입니다. 초안과 원본이 같은 배열을 함께 쓰는 얕은 복사였습니다.
  3. 주인을 정합니다. 초안의 주인은 편집 화면입니다. 편집을 시작할 때 태그 배열까지 복사해 초안을 떼어 내고, 원본은 저장에 성공했을 때만 고칩니다.
  4. 저장 상태에 이름을 붙입니다. 대기, 저장 중, 완료, 오류로 나누고, 저장 중에 또 들어온 요청은 무시합니다. 화면을 떠난 뒤 도착한 응답도 버립니다.
  5. 확인합니다. 태그를 고친 뒤 취소하기, 저장 버튼 연달아 누르기, 저장 중에 화면 떠나기를 각각 해 봅니다.

고친 뒤의 취소는 "되돌리기"가 아닙니다. 애초에 원본을 건드린 적이 없으니 되돌릴 것도 없습니다.

한눈에 정리#

  • 상태는 프로그램이 기억하고 있는 것입니다. 버그의 대부분은 상태가 꼬여서 생깁니다.
  • 계산은 순수 함수로 하고, 부수 효과는 눈에 띄는 한곳에 둡니다.
  • 상태는 숨기고 정해진 창구(인터페이스)로만 고칩니다. '없음'과 '실패'는 구분합니다.
  • 같은 사실은 한 곳에만 적고 주인을 하나 둡니다. 파생 값은 저장하지 않습니다.
  • 얕은 복사는 안쪽을 함께 씁니다. 고치는 대신 새로 만들면(불변 업데이트) 실행 취소도 쉽습니다.
  • 참·거짓 여러 개 대신 상태 기계로 적으면 있을 수 없는 상태를 만들 수 없습니다.
  • 구독과 타이머는 만든 곳이 치웁니다. 늦게 도착한 응답은 번호표로 걸러 냅니다.

확인 문제#

동료가 장바구니 상태에 items와 total(합계)을 둘 다 저장하자고 합니다. 무엇을 먼저 확인해야 할까요?

정답 보기

total이 지금의 items에서 계산하면 나오는 값인지 확인합니다. 그렇다면 파생 값이므로 저장하지 않고 필요할 때 계산합니다. 다만 이미 결제한 주문의 금액이라면 과거의 사실이므로 따로 적어 둡니다.

const draft = { ...profile }로 초안을 만든 뒤 draft.address.city = "부산"을 실행했습니다. profile.address.city는 어떻게 될까요?

정답 보기

"부산"으로 바뀝니다. 얕은 복사라서 address 칸의 쪽지만 옮겨 적었고, 두 객체가 같은 주소 객체를 가리킵니다. address: { ...profile.address }처럼 고칠 곳까지 새로 만들어야 합니다.

화면에 로딩 표시와 오류 문구가 동시에 떠 있습니다. 코드에는 isLoading과 isError가 따로 있습니다. 구조를 어떻게 바꿔야 할까요?

정답 보기

둘 다 참이 되는 조합을 코드가 만들 수 있다는 것이 원인입니다. status 하나에 대기, 불러오는 중, 완료, 오류 중 하나만 적고, 전이 규칙을 함수 하나에 모읍니다.

검색 함수가 네트워크 오류가 나면 빈 배열 []을 돌려줍니다. 화면에는 "검색 결과가 없습니다"가 뜹니다. 무엇이 문제일까요?

정답 보기

'없음'과 '실패'를 하나로 뭉쳤습니다. 사용자는 정말 결과가 없는지 인터넷이 끊겼는지 알 수 없습니다. 성공(결과 0건)과 실패를 구분해 돌려주고, 화면도 따로 보여 줍니다.

채팅방에 다섯 번 들어갔다 나온 뒤부터 새 메시지 알림음이 다섯 번씩 울립니다. 무엇을 의심해야 할까요?

정답 보기

들어갈 때마다 새 메시지 알림을 구독하고, 나갈 때 해제하지 않은 것입니다. 드나들 때마다 구독 수를 찍어 보면 1, 2, 3으로 늘어납니다. 구독할 때 받은 해제 함수를 화면을 닫을 때 부르면 됩니다.

AI에게 맡길 때#

AI에게 맡길 때

AI 코딩 도구는 돌아가는 화면은 금방 만들지만, 상태의 주인과 실패한 경우는 건너뛰기 쉽습니다. 코드를 쓰게 하기 전에 상태 설계부터 글로 적게 하세요.

프로필 편집 화면을 고쳐 줘. 코드를 쓰기 전에 (1) 원본 프로필과 편집 중인 초안의 주인이 각각 어디인지, (2) 저장의 상태(대기, 저장 중, 완료, 오류)와 상태별로 허용되는 동작을 표로 적어 줘. 조건은 세 가지야. 취소하면 원본은 한 글자도 바뀌지 않는다. 저장 중에는 버튼을 다시 눌러도 요청이 한 번만 나간다. 화면을 떠난 뒤 도착한 응답은 반영하지 않는다. 완료 조건은 테스트 세 개 통과야. 태그를 고친 뒤 취소하기, 저장 버튼 연달아 누르기, 저장 중에 화면 떠나기.

받은 답에서 확인할 것: 초안을 만들 때 안쪽 배열까지 따로 복사했는가. 참·거짓 변수 여러 개가 아니라 상태 이름 하나로 적었는가. 응답을 반영하기 전에 최신 요청인지 확인하는가.

용어 정리#

상태state
프로그램이 지금 기억하고 있는 것.
스코프scope
변수 이름이 보이는 범위.
클로저closure
자기가 만들어진 곳의 변수를 붙잡고 있는 함수.
순수 함수pure function
입력만으로 결과를 계산하고 바깥을 바꾸지 않는 함수.
부수 효과side effect
함수가 자기 바깥의 것을 바꾸는 일.
캡슐화encapsulation
안쪽 데이터를 숨기고 정해진 함수로만 고치게 하는 것.
인터페이스interface
밖에서 쓸 수 있게 열어 둔 기능의 목록과 약속.
기준 데이터source of truth
같은 사실의 여러 사본 가운데 진짜로 삼는 한 곳. 원본.
파생 값derived value
다른 상태에서 계산하면 나오는 값.
얕은 복사shallow copy
겉 상자만 새로 만들고 안쪽은 함께 쓰는 복사.
불변 업데이트immutable update
값을 고치지 않고 새 값을 만들어 갈아 끼우는 방식.
상태 기계state machine
가능한 상태의 목록과 상태 사이의 전이 규칙을 정해 둔 것.
리듀서reducer
지금 상태와 일어난 일을 받아 다음 상태를 돌려주는 순수 함수.
발행·구독publish–subscribe
바뀌면 알려 달라고 등록해 두고, 바뀌면 등록된 함수를 모두 부르는 방식.
