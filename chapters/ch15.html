웹과 HTTP

요청·응답·브라우저·실패 다루기

읽는 시간 약 40분먼저 읽으면 좋은 장14장 네트워크

인터넷 주소를 입력하고 엔터를 누르면 화면이 뜹니다. 그 사이에 내 컴퓨터는 멀리 있는 다른 컴퓨터에게 "이 페이지를 보여 주세요"라고 부탁하고, 그 컴퓨터는 답을 보내 줍니다. 식당에서 주문하고 음식을 받는 것과 비슷합니다. 이 장에서는 그 부탁과 답이 어떻게 생겼는지, 답이 오지 않을 때는 어떻게 하는지 배웁니다.

이 장을 마치면
  • 엔터를 누른 뒤 화면이 뜨기까지 일어나는 일을 순서대로 말할 수 있습니다.
  • 부탁(요청)과 답(응답)이 어떻게 생겼는지 읽을 수 있습니다.
  • 사이트가 내가 로그인한 사람이라는 것을 기억하는 방법을 설명할 수 있습니다.
  • 답이 오지 않을 때 같은 부탁을 다시 보내도 괜찮게 만드는 방법을 알 수 있습니다.

15.1엔터를 누르면 생기는 일: 여섯 단계#

피자를 시키려고 가게에 심부름꾼을 보낸다고 합시다. 나는 가게 이름과 원하는 것을 쪽지에 적어 줍니다. 심부름꾼은 가게를 찾아가 주문서를 건네고, 답을 받아 와 상을 차려 줍니다.

웹에서는 브라우저(browser)가 이 심부름꾼입니다. 가게는 14장에서 만난 서버이고, 쪽지는 주소창에 적는 URL(Uniform Resource Locator)입니다.

  1. 주소 읽기. URL을 조각으로 나눕니다. https는 통신 방식인 스킴(scheme), pizza.example.com은 가게 이름인 호스트(host), /menu는 가게 안에서 원하는 것을 가리키는 경로(path), ?size=L은 세부 조건인 쿼리(query)입니다.
  2. 이름을 주소로. DNS에 물어 호스트를 IP 주소로 바꿉니다.
  3. 연결 맺기. 그 주소의 443번 포트와 TCP 연결을 맺고, 내용을 잠글 준비를 합니다.
  4. 요청 보내기. 경로와 쿼리를 적은 주문서를 보냅니다.
  5. 응답 받기. 서버가 처리 결과와 내용물을 돌려줍니다.
  6. 화면 그리기. 받은 문서로 화면을 만듭니다. 문서에 적힌 그림과 스타일 파일도 4~5단계를 되풀이해 받아 옵니다.

2~3단계는 14장에서 배웠고, 이 장의 무대는 4단계부터입니다. 주문서와 답변서를 쓰는 형식을 정한 약속이 HTTP(Hypertext Transfer Protocol)입니다.

15.2요청과 응답: 주문서와 답변서#

HTTP의 규칙은 단순합니다. 브라우저가 요청을 하나 보내면 서버가 응답을 하나 돌려줍니다. 서버가 먼저 말을 걸지는 않습니다. 요청도 응답도 사람이 읽을 수 있는 글자입니다.

주문서 첫 줄에는 무엇을 해 달라는지 나타내는 메서드(method)와 그 대상인 경로를 적습니다. 그 아래 헤더(header)는 이름: 값 꼴로 덧붙이는 메모입니다. Content-Type: application/json은 "내용물은 JSON(8장) 형식"이라는 뜻입니다. 빈 줄 다음의 본문(body)이 내용물이고, 보낼 것이 없으면 비워 둡니다.

메서드 뜻 가게에서라면
GET 보여 주세요 메뉴판 좀 볼게요
POST 새로 만들어 주세요 피자 한 판 주문이요
PUT 이 내용으로 바꿔 주세요 주문 수량을 2로 바꿔 주세요
DELETE 지워 주세요 주문 취소할게요

GET은 읽기만 한다는 약속이 가장 중요합니다. 브라우저는 GET을 안전하다고 믿고 미리 불러 두거나 다시 보냅니다. GET으로 삭제를 하게 만들면 링크를 미리 열어 본 것만으로 주문이 사라집니다.

메뉴판을 보여 달라는 요청과 그 답입니다.

GET /menu?size=L HTTP/1.1
Host: pizza.example.com

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!doctype html>…
  • 위 두 줄이 요청입니다. 조회라서 본문이 없습니다. Host는 어느 가게로 가는지 적은 것입니다.
  • HTTP/1.1 200 OK부터가 응답입니다. Content-Type은 내용물이 HTML이라는 뜻이고, 빈 줄 다음이 본문입니다.
주의

비밀번호 같은 값을 ?pw=1234처럼 URL에 넣지 마세요. URL은 방문 기록과 서버 기록에 그대로 남습니다.

상태 코드: 답변서의 첫 줄

응답 첫 줄의 세 자리 숫자가 상태 코드(status code)입니다. 첫 자리만 봐도 누구 쪽 일인지 알 수 있습니다.

묶음 뜻 자주 보는 코드
2xx 잘 됐습니다 200 성공, 201 새로 만들었음
3xx 다른 곳을 보세요 301 주소가 바뀜, 304 바뀐 것 없음
4xx 주문서가 잘못됐습니다 400 형식 오류, 401 누구인지 모름, 403 권한 없음, 404 그런 것 없음
5xx 가게 사정입니다 500 처리 중 오류, 503 지금은 못 받음, 502·504 안내 데스크(14장)가 뒤쪽 서버의 답을 못 받음

이름을 못 찾았거나 연결이 거부되면 상태 코드 자체가 없습니다. 주문서가 가게에 닿지 못한 것입니다. 그리고 200이 곧 성공은 아닙니다. 200과 함께 본문에 {"ok": false}를 담아 보내는 서버도 있으니 본문까지 읽습니다.

핵심

4xx는 주문서를 고칠 일, 5xx는 가게를 살필 일, 상태 코드가 없으면 14장의 순서대로 가는 길을 살필 일입니다.

15.3HTTPS: 주문서를 잠긴 상자에 넣기#

HTTP 주문서는 엽서와 같습니다. 가는 길의 공유기와 라우터 어디서든 읽고 고칠 수 있습니다. 카페 와이파이에서 HTTP로 로그인하면 비밀번호가 글자 그대로 지나갑니다.

HTTPS는 같은 주문서를 TLS(Transport Layer Security)라는 잠긴 상자에 넣어 주고받는 방식입니다. TLS는 내용을 암호로 바꿔 엿보지 못하게 하고, 중간에서 고치면 알아채게 하고, 상대가 진짜 그 가게인지 확인해 줍니다.

상대를 확인할 때 보는 것이 인증서(certificate)입니다. 가게 벽의 영업 허가증처럼, "이 서버가 pizza.example.com의 주인이 맞다"는 것을 브라우저가 미리 믿기로 한 인증 기관(CA, Certificate Authority)이 보증한 문서입니다. 브라우저는 믿는 기관이 발급했는지, 적힌 이름이 접속하려는 이름과 같은지, 기한이 남았는지를 보고, 하나라도 어긋나면 경고 화면을 띄웁니다.

주의 · 인증서 검사를 끄지 마세요

AI 도구가 인증서 오류를 없애려고 verify=False나 curl -k를 권하기도 합니다. "허가증을 보지 않겠다"는 뜻이라, 가짜 가게에 주문서를 건네도 모르게 됩니다. 인증서의 이름과 기한을 바로잡아야 합니다.

잠긴 상자는 가는 길만 지킵니다. 서버가 받은 비밀번호를 허술하게 보관하면 HTTPS와 상관없이 샙니다. 주소의 https도 "이 이름의 서버와 암호로 통신 중"이라는 뜻일 뿐입니다. 사기 사이트도 인증서를 받을 수 있습니다.

한 걸음 더VPN, HTTPS, 종단 간 암호화는 어디까지 지켜 줄까

셋은 상자가 어디에서 열리느냐가 다릅니다.

  • HTTPS는 브라우저에서 웹 서버까지 잠급니다. 안내 데스크(14장)가 상자를 열어 뒤쪽 서버로 넘긴다면 그 구간은 따로 잠급니다.
  • VPN(Virtual Private Network)은 내 기기에서 VPN 서버까지만 잠급니다. 그 뒤는 원래대로입니다.
  • 종단 간 암호화(E2EE)는 보내는 사람과 받는 사람의 기기에서만 열립니다. 중계 서버도 못 봅니다.

길목에서 패킷을 떠 보는 패킷 캡처 도구(Wireshark 등)로는 HTTPS의 암호문만 보입니다. 내용은 상자를 여는 당사자인 브라우저의 개발자 도구로 봅니다.

15.4HTTP는 손님을 기억하지 못합니다: 쿠키와 세션#

서버는 요청 하나하나를 처음 보는 손님처럼 대합니다. 방금 로그인한 손님과 지금 장바구니를 보여 달라는 손님이 같은 사람인지 모릅니다. 이 성질을 무상태(stateless)라고 합니다. 요청마다 비밀번호를 적어 보낼 수는 없으니 가게는 번호표를 줍니다.

로그인에 성공하면 서버는 짐작할 수 없는 긴 번호를 만들어 응답 헤더 Set-Cookie에 실어 보냅니다. 브라우저는 이 값을 그 사이트 전용 보관함에 넣어 둡니다. 이렇게 서버가 브라우저에 맡겨 두는 작은 값이 쿠키(cookie)입니다.

그 뒤로 브라우저는 같은 사이트로 가는 요청마다 Cookie 헤더에 번호표를 자동으로 붙입니다. 서버는 장부에서 번호를 찾아 손님을 알아봅니다. 서버가 손님 한 명에 대해 적어 둔 이 기록이 세션(session)입니다.

Set-Cookie: sid=k3x9; HttpOnly; Secure; SameSite=Lax
  • sid=k3x9가 번호표입니다. 실제 값은 훨씬 깁니다.
  • HttpOnly는 페이지 안에서 도는 자바스크립트 코드, 곧 스크립트가 읽지 못하게 합니다. Secure는 HTTPS 요청에만 붙이게 합니다.
  • SameSite=Lax는 다른 사이트가 시킨 요청에는 되도록 붙이지 않게 합니다.

번호표는 들고 있는 사람을 주인으로 대접합니다. 훔치면 그 사람 행세를 할 수 있어서 이런 규칙으로 새는 길을 좁힙니다. 공격과 방어는 19장에서 다룹니다.

브라우저에는 localStorage라는 서랍도 있습니다. 다크 모드 같은 설정을 사이트별로 넣어 두는 곳입니다. 쿠키와 달리 서버로 저절로 가지 않고, 스크립트가 꺼내서 보내야 합니다. "브라우저에 저장했다"는 서버에 저장됐다는 뜻이 아닙니다.

15.5출처와 CORS: 막는 쪽은 브라우저입니다#

화면은 localhost:3000에, 데이터를 내주는 서버 창구인 API는 localhost:8000에 띄우고 개발하다 보면 브라우저에 blocked by CORS policy라는 빨간 글씨가 뜹니다. 그런데 터미널에서 curl로 같은 주소를 부르면 멀쩡히 답이 옵니다. 서버는 고장 나지 않았습니다.

번호표가 자동으로 붙는다는 점을 떠올려 보세요. 은행에 로그인해 둔 채 수상한 사이트를 열었다고 합시다. 그 사이트의 스크립트가 내 브라우저에게 "은행에서 잔액을 받아 와"라고 시키면 은행 번호표가 함께 나가고, 은행은 나라고 믿고 답합니다. 그 답을 수상한 사이트가 읽으면 큰일입니다.

그래서 브라우저는 한 출처에서 온 스크립트가 다른 출처의 응답을 읽지 못하게 막습니다. 출처(origin)는 스킴, 호스트, 포트의 묶음이고, 하나만 달라도 다른 출처입니다. localhost:3000과 localhost:8000은 포트가 달라 남남입니다.

내 화면이 내 API를 못 읽으면 곤란하니, API 서버가 응답에 Access-Control-Allow-Origin: http://localhost:3000이라는 헤더로 허락을 적어 줍니다. 브라우저는 이 헤더를 확인한 뒤에야 응답을 스크립트에 넘깁니다. 이 약속이 CORS(Cross-Origin Resource Sharing, 교차 출처 리소스 공유)입니다.

핵심

CORS 오류는 서버의 거절이 아니라 브라우저의 검사입니다. 고치는 곳은 API 서버의 응답 헤더입니다.

브라우저가 아닌 curl에는 이 검사가 없어서 그대로 응답을 받습니다. 그러니 CORS는 서버를 지켜 주지 않습니다. 누구에게 무엇을 내줄지는 서버가 따로 검사합니다.

그림에서 요청은 이미 처리됐습니다. 삭제였다면 곤란합니다. 그래서 브라우저는 JSON 본문을 보내거나 PUT, DELETE를 쓰는 요청 앞에서는 OPTIONS라는 메서드로 "보내도 됩니까?"를 먼저 묻습니다. 이 사전 요청(preflight)이 허락받지 못하면 본 요청은 나가지 않습니다.

주의

AI 도구가 권하는 mode: "no-cors"는 오류 문구만 없앨 뿐 응답은 여전히 못 읽습니다. 모든 출처를 허락하는 Access-Control-Allow-Origin: *도 급한 불만 끕니다. 실제 서비스에서는 내 화면의 출처만 적습니다.

15.6브라우저가 화면을 만드는 법: HTML, DOM, 개발자 도구#

서버가 보낸 HTML(Hypertext Markup Language)은 <ul>, <li> 같은 태그로 문서의 뼈대를 적은 글자입니다. 브라우저는 태그 하나하나를 마디로 삼아 메모리 안에 나무 모양의 구조를 만듭니다. 이것이 DOM(Document Object Model)입니다. 화면은 HTML이 아니라 DOM을 보고 그리며, 자바스크립트는 DOM을 언제든 고칠 수 있습니다.

요즘 웹 앱은 대부분 이렇게 거의 빈 HTML을 먼저 받고, 스크립트가 API를 불러 내용을 채웁니다. 그래서 이런 일이 생깁니다.

  • "페이지 소스 보기"와 화면이 다릅니다. 소스 보기는 1번을, 화면은 3번을 보여 줍니다.
  • HTML만 내려받는 프로그램은 "불러오는 중"만 얻습니다. 스크립트를 실행하지 않기 때문입니다.
  • DOM을 고쳐도 서버는 그대로입니다. 개발자 도구로 화면의 가격을 0원으로 고쳐도 내 화면만 바뀝니다. 그래서 서버는 화면에서 온 값을 그대로 믿으면 안 됩니다.
한 걸음 더웹 페이지의 내용을 프로그램으로 가져오는 세 가지 길

공개된 API가 있으면 그것이 가장 안정적입니다. 내용이 처음 받은 HTML에 들어 있으면 내려받아 태그를 해석하는 스크래핑으로 충분합니다. 스크립트가 채우는 페이지라면 진짜 브라우저를 프로그램으로 조종하는 브라우저 자동화가 필요합니다. 이때 "3초 기다리기"보다 "목록이 나타날 때까지 기다리기"가 덜 깨집니다. 어느 길이든 서비스의 이용 약관 안에서 씁니다.

개발자 도구: 실제로 오간 것을 보는 창

브라우저에서 F12(맥은 Cmd + Option + I)를 누르면 개발자 도구가 열립니다. Elements 탭은 지금의 DOM을, Console 탭은 스크립트의 오류를, Application 탭은 쿠키와 localStorage를 보여 줍니다. 가장 자주 쓰는 것은 오간 요청과 응답을 모두 보여 주는 Network(네트워크) 탭입니다. 코드에 뭐라고 적혀 있든, 여기 찍힌 것이 실제로 보낸 것입니다.

"버튼을 눌러도 아무 일이 없다"면 네트워크 탭을 연 채로 다시 누르고 세 가지를 묻습니다.

  1. 줄이 생겼는가. 없다면 요청이 나가지도 않았습니다. Console의 오류를 봅니다.
  2. 상태가 무엇인가. 4xx면 줄을 눌러 내가 보낸 헤더와 본문을, 5xx면 서버 기록을 봅니다.
  3. 어디서 시간을 썼는가. 그림의 api/menu는 400ms 중 280ms를 서버의 첫 응답을 기다리는 데 썼습니다. 이 시간이 TTFB(Time To First Byte)입니다. 회선이 아니라 서버를 볼 일입니다.
직접 해 보기

아무 사이트에서나 Network 탭을 열고 새로 고침해 보세요. 맨 위 줄이 HTML 문서입니다. 줄을 눌러 Headers에서 메서드와 상태 코드를 찾아보세요.

주의

네트워크 탭의 "Copy as cURL"에는 내 쿠키가 그대로 들어갑니다. AI 도구에 붙여 넣기 전에 가리세요.

15.7HTTP 캐시와 연결 재사용: 같은 일을 두 번 하지 않기#

가게 메뉴판은 어제도 오늘도 같습니다. 갈 때마다 새로 받아 오면 낭비입니다. 그래서 브라우저는 받은 응답의 사본을 보관했다가 다시 씁니다. 이것이 HTTP 캐시입니다. 그사이 메뉴판이 바뀌면 어떡할까요? 서버가 응답 헤더로 규칙을 정해 줍니다.

  • Cache-Control: max-age=3600은 "3,600초 동안은 묻지 말고 사본을 쓰세요"입니다.
  • ETag: "v7"은 내용물의 판 번호입니다. 내용이 바뀌면 이 값도 바뀝니다.

기간이 지나도 브라우저는 사본을 버리지 않고 If-None-Match: "v7"을 붙여 묻습니다. "7판을 갖고 있는데 바뀌었나요?"입니다. 그대로라면 서버는 본문 없이 304 Not Modified만 보내서, 48KB 대신 0.2KB로 끝납니다. 바뀌었다면 200과 새 내용을 보냅니다.

흔한 오해 · no-cache는 캐시하지 말라는 뜻이다

no-cache는 보관하되 쓸 때마다 서버에 확인하라는 뜻입니다. 아예 보관하지 못하게 하는 것은 no-store이고, 개인 정보가 담긴 응답에 씁니다.

캐시는 "배포했는데 옛 화면이 보인다"의 단골 원인입니다. 그래서 빌드 도구는 app.3f9a1c.js처럼 파일 이름에 내용의 지문을 넣습니다. 내용이 바뀌면 이름도 바뀌므로 오래 캐시해도 안전합니다.

참고

서버는 본문을 압축해 보내기도 합니다. 응답의 Content-Encoding: gzip이 그 표시이고 브라우저가 알아서 풉니다.

연결도 다시 씁니다

연결을 맺으려면 TCP 악수와 잠그는 절차로 왕복이 몇 번 듭니다. 그래서 브라우저는 응답을 받은 뒤에도 연결을 끊지 않고 다음 요청에 다시 씁니다.

HTTP/1.1에서는 한 연결이 한 번에 요청 하나만 처리해서, 브라우저가 사이트마다 연결을 여섯 개쯤 엽니다. HTTP/2는 한 연결 안에서 여러 요청과 응답을 잘게 섞어 동시에 주고받습니다.

한 걸음 더HTTP/3는 무엇이 다를까

TCP는 조각 하나를 잃으면 뒤의 조각을 모두 붙잡아 둡니다. HTTP/2로 요청 열 개를 한 연결에 섞어 보내다 조각 하나를 잃으면 열 개가 함께 멈춥니다. HTTP/3는 UDP 위에 만든 QUIC이라는 전송 방식을 써서, 한 요청의 조각을 잃어도 다른 요청은 계속 갑니다. 주문서의 내용은 그대로이고 실어 나르는 방법만 달라졌습니다.

한 걸음 더판 번호의 또 다른 쓸모: 남의 수정을 덮어쓰지 않기

두 사람이 메뉴판 7판을 각자 고쳐 차례로 저장하면 먼저 저장한 수정이 사라집니다. 저장 요청에 If-Match: "v7"을 붙이면 "아직 7판일 때만 저장"이 됩니다. 이미 8판이면 서버는 412로 거절하고, 나중 사람은 최신 내용을 받아 다시 합칩니다.

15.8서버가 먼저 알려야 할 때: 폴링, SSE, WebSocket#

HTTP에서는 브라우저가 물어야 서버가 답합니다. 그러면 새 채팅 메시지처럼 서버 쪽에서 먼저 생기는 소식은 어떻게 전할까요?

  • 폴링(polling)은 5초마다 가서 "나왔나요?"를 묻는 것입니다. 만들기 쉽지만 답은 대부분 "아직요"이고 소식이 최대 5초 늦습니다.
  • SSE(Server-Sent Events)는 한 번 물어 놓고 창구 앞에서 기다리는 것입니다. 서버가 응답을 끝내지 않고 소식이 생길 때마다 한 줄씩 내려보냅니다. 방향은 서버에서 브라우저 쪽뿐입니다. AI 챗봇의 답이 조금씩 흘러나오는 화면이 흔히 이 방식입니다.
  • WebSocket(웹소켓)은 전화를 걸어 놓고 끊지 않는 것입니다. HTTP 요청으로 시작해 약속을 바꾼 뒤 양쪽이 아무 때나 말합니다. 채팅과 게임에 씁니다.

열어 둔 연결은 언젠가 끊기고, 끊긴 사이의 소식은 저절로 돌아오지 않습니다. 다시 연결할 때 "37번까지 받았습니다"라고 알려 그 뒤부터 이어 받는 규칙을 함께 만듭니다.

한 걸음 더조용히 끊긴 연결을 알아채기 (하트비트)

연결을 열어 두고 다시 쓰는 것(keep-alive)과 살아 있는지 확인하는 것은 다른 일입니다. 길목의 공유기가 오래 조용한 연결을 장부에서 지우면, 양쪽은 연결됐다고 믿는데 메시지만 오지 않습니다. 그래서 30초마다 "ping"을 보내 "pong"이 오는지 봅니다. 이것이 하트비트(heartbeat)입니다. 답이 없으면 다시 연결합니다.

15.9답이 오지 않을 때: 시간 제한, 재시도, 멱등성#

주문 버튼을 눌렀는데 10초째 돌기만 합니다. 일어났을 수 있는 일은 셋입니다. 주문서가 가는 길에 사라졌거나, 가게가 아직 처리 중이거나, 주문은 들어갔는데 답변서가 오는 길에 사라졌거나입니다. 브라우저는 이 셋을 구별할 수 없습니다. 11장에서 본 대로 시간 초과는 "실패"가 아니라 "모른다"입니다.

먼저 얼마나 기다릴지 정합니다. 이 한도가 시간 제한(timeout)입니다. 브라우저에서 요청을 보내는 함수 fetch에는 기본값이 없어 직접 넣어야 합니다.

const res = await fetch("/orders", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Idempotency-Key": orderKey,
  },
  body: JSON.stringify(order),
  signal: AbortSignal.timeout(5000),
});
  • method, headers, body가 주문서의 첫 줄, 헤더, 본문입니다.
  • AbortSignal.timeout(5000)은 5,000ms 안에 답이 없으면 그만 기다리라는 뜻입니다.

5초 뒤 같은 주문을 그냥 다시 보내면, 답변서만 사라진 경우에는 피자가 두 판 옵니다.

여러 번 해도 한 번 한 것과 결과가 같은 성질을 멱등성(idempotency)이라고 합니다. "3번 테이블 물잔을 채워 주세요"는 몇 번 말해도 결과가 같지만, "피자 한 판 추가요"는 말할 때마다 한 판씩 늘어납니다. GET, PUT(2로 바꿔 주세요), DELETE(취소해 주세요)는 멱등하고, POST(한 판 주문이요)는 멱등하지 않습니다.

POST를 안전하게 다시 보내려면 주문서에 고유 번호를 적습니다. 버튼을 누를 때 번호를 만들고, 다시 보낼 때도 같은 번호를 씁니다. 서버는 처리한 번호를 적어 두었다가 같은 번호가 또 오면 처음 결과를 다시 알려 줍니다. 이 번호가 멱등 키(idempotency key)이고, 위 코드에서는 Idempotency-Key 헤더에 담았습니다.

다시 보내는 데에도 규칙이 있습니다.

  • 될 만한 것만. 연결 실패, 시간 초과, 5xx는 잠시 뒤 될 수 있습니다. 400이나 404는 백 번 보내도 같은 답입니다.
  • 간격을 늘려서. 1초, 2초, 4초처럼 기다림을 늘리는 것이 백오프(backoff)입니다. 모두가 쉬지 않고 다시 주문하면 힘든 가게는 일어나지 못합니다(18장).
  • 횟수를 정해서. 세 번쯤 해 보고 안 되면 사용자에게 알립니다.
핵심

시간 초과는 "안 됐다"가 아니라 "모른다"입니다. 다시 보내기 전에 두 번 처리돼도 괜찮은 요청인지부터 확인합니다.

한 걸음 더끊긴 내려받기를 이어서 받기 (범위 요청)

1GB 파일을 400MB까지 받다 끊겼다면 요청에 Range: bytes=400000000-을 붙여 "여기부터 주세요"라고 할 수 있습니다. 서버가 지원하면 206과 함께 나머지만 보냅니다. 200으로 전체가 왔다면 이어 붙이면 안 됩니다. 올리기(업로드)를 이어 하려면 서버가 어디까지 받았는지 기록하는 규칙을 따로 만들어야 합니다.

실전 사례#

실전 사례 · 터미널에서는 되는데 브라우저에서만 실패하는 API

AI 도구로 화면(localhost:3000)과 API 서버(localhost:8000)를 만들었습니다. curl로는 메뉴가 잘 오는데 화면은 비어 있습니다.

  1. Console을 봅니다. blocked by CORS policy가 있습니다. 브라우저의 출처 검사입니다.
  2. Network 탭에서 그 줄을 누릅니다. 응답은 왔는데 헤더에 Access-Control-Allow-Origin이 없습니다.
  3. 서버를 고칩니다. API 서버의 CORS 설정에 http://localhost:3000만 허락합니다.
  4. 다시 확인합니다. 메뉴는 나오는데 장바구니 요청이 401입니다. 요청에 Cookie 헤더가 없습니다. fetch는 다른 출처로 쿠키를 보내지 않는 것이 기본입니다. 화면 코드에 credentials: "include"를, 서버 응답에 Access-Control-Allow-Credentials: true를 더합니다.

터미널의 성공은 "서버가 답할 수 있다"까지만 증명합니다. 브라우저의 규칙은 브라우저에서 확인합니다.

한눈에 정리#

  • 엔터 한 번에 주소 읽기 → DNS → 연결 → 요청 → 응답 → 그리기가 일어납니다. 화면은 DOM을 보고 그립니다.
  • 요청은 메서드, 경로, 헤더, 본문, 응답은 상태 코드, 헤더, 본문으로 된 글자입니다. 실제로 오간 것은 네트워크 탭에서 봅니다.
  • 4xx는 보낸 쪽, 5xx는 서버 쪽 문제입니다. 상태 코드가 없으면 가는 길의 문제입니다.
  • HTTPS는 가는 길만 지킵니다. 브라우저는 쿠키라는 번호표를 자동으로 붙이고, 서버는 세션 장부에서 손님을 찾습니다.
  • CORS 오류는 브라우저가 다른 출처의 응답을 스크립트에 넘기지 않은 것입니다. 서버의 헤더로 풉니다.
  • 캐시는 304로 다시 받는 양을 줄이고, 서버 쪽 소식은 폴링, SSE, WebSocket으로 전합니다.
  • 시간 초과는 "모른다"입니다. 멱등 키와 백오프로 안전하게 다시 보냅니다.

확인 문제#

curl로는 API가 잘 되는데 브라우저에서는 CORS 오류가 납니다. 서버가 거절한 것일까요? 어디를 고쳐야 할까요?

정답 보기

거절이 아닙니다. 브라우저가 다른 출처의 응답을 스크립트에 넘기지 않은 것입니다. API 서버가 Access-Control-Allow-Origin 헤더로 화면의 출처를 허락하게 고칩니다.

API를 불렀더니 차례로 401, 404, 502가 나왔습니다. 각각 어디부터 살펴야 할까요?

정답 보기

401은 서버가 나를 모른다는 뜻이니 요청에 쿠키가 실제로 붙었는지 봅니다. 404는 대상이 없다는 뜻이니 경로를 봅니다. 502는 안내 데스크가 뒤쪽 서버의 답을 못 받은 것이니 서버 쪽을 봅니다.

"페이지 소스 보기"에는 상품이 없는데 화면에는 열 개가 보입니다. 이 페이지의 HTML만 내려받는 수집 프로그램은 무엇을 얻을까요?

정답 보기

상품이 없는 빈 뼈대만 얻습니다. 소스 보기는 서버가 처음 보낸 HTML이고, 화면은 스크립트가 고친 뒤의 DOM입니다. 수집 프로그램은 스크립트를 실행하지 않습니다.

카페 와이파이에서 HTTPS 쇼핑몰에 로그인했습니다. 와이파이 주인은 무엇을 볼 수 있을까요? 주소가 https로 시작하면 그 쇼핑몰은 믿어도 될까요?

정답 보기

어느 서버와 얼마나 주고받는지만 보입니다. 경로, 쿠키, 비밀번호는 보이지 않습니다. https는 암호로 통신한다는 뜻일 뿐, 가게가 정직한지는 보증하지 않습니다.

결제 요청이 5초 시간 제한에 걸렸습니다. 곧바로 같은 요청을 다시 보내도 될까요?

정답 보기

안 됩니다. 결제는 끝났는데 응답만 사라졌다면 두 번 결제됩니다. 처음과 같은 멱등 키를 붙여 보내고, 서버가 같은 키를 한 번만 처리해야 안전합니다.

AI에게 맡길 때#

AI에게 맡길 때

"안 돼요" 대신 네트워크 탭에서 본 사실을 주고, 실패했을 때의 동작까지 정해 주세요.

주문 버튼의 API 호출을 안정적으로 만들어 줘. 지금은 네트워크 탭에서 POST /orders가 가끔 10초 넘게 응답 없이 남고, 사용자가 버튼을 다시 눌러 주문이 두 건 생겨. (1) 5초 시간 제한을 넣어 줘. (2) 버튼을 누를 때 멱등 키를 만들어 재시도에도 같은 키를 쓰고, 서버는 같은 키의 주문을 한 번만 만들게 해 줘. (3) 재시도는 연결 실패, 시간 초과, 5xx일 때만 간격을 늘려 최대 3번 해 줘. 서버가 주문을 만든 뒤 응답만 끊기는 상황을 테스트로 재현해, 주문이 한 건만 남으면 완료야.

받은 답에서 확인할 것: 재시도할 때 멱등 키를 새로 만들지 않는가, 4xx까지 재시도하지 않는가, verify=False 같은 우회를 쓰지 않았는가, 응답이 끊기는 경우를 실제로 시험했는가.

용어 정리#

HTTPHypertext Transfer Protocol
브라우저와 서버가 요청과 응답을 주고받는 약속.
URLUniform Resource Locator
스킴, 호스트, 경로, 쿼리로 이루어진 웹 주소.
상태 코드status code
요청의 처리 결과를 알리는 세 자리 숫자.
TLSTransport Layer Security
통신을 암호화하고 상대를 확인해 주는 약속. HTTP를 그 위에서 쓰면 HTTPS다.
인증서certificate
서버가 그 도메인의 주인임을 인증 기관이 보증한 문서.
쿠키cookie
서버가 브라우저에 맡겨 두는 작은 값. 요청에 자동으로 붙는다.
세션session
서버가 손님 한 명에 대해 적어 둔 기록. 쿠키의 번호로 찾는다.
출처origin
스킴, 호스트, 포트의 묶음. 하나만 달라도 다른 출처다.
CORSCross-Origin Resource Sharing
다른 출처의 스크립트가 응답을 읽어도 된다고 서버가 허락하는 약속.
DOMDocument Object Model
브라우저가 HTML을 읽어 메모리에 만든 나무 구조.
WebSocket
연결을 열어 둔 채 양쪽이 아무 때나 메시지를 보내는 방식.
멱등성idempotency
여러 번 보내도 결과가 한 번 보낸 것과 같은 성질.
백오프backoff
다시 보낼 때마다 기다리는 시간을 늘려 가는 방법.
