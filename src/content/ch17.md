::: {.lead}
학교에는 학생 수백 명의 이름, 반, 성적이 적힌 기록이 있습니다. 공책 한 권에 적어 두면 여러 선생님이 동시에 고칠 수 없고, 한 명을 찾으려면 처음부터 넘겨 봐야 합니다. 많은 정보를 여러 사람이 동시에 쓰고, 빨리 찾고, 잃어버리지 않게 보관해 주는 프로그램이 **데이터베이스**입니다.
:::

::: {.goals}
- 데이터베이스가 왜 필요한지 말할 수 있습니다.
- 정보를 표로 나눠 담고 서로 잇는 방법을 설명할 수 있습니다.
- 원하는 정보를 찾는 명령(SQL)을 읽을 수 있습니다.
- 여러 사람이 동시에 고쳐도 정보가 꼬이지 않게 하는 방법을 알 수 있습니다.
:::

## 파일 하나로는 왜 안 될까 {#why}

그러면 컴퓨터 파일 하나에 적으면 어떨까요? 혼자 쓰는 메모라면 그것으로 충분합니다. 그런데 쓰는 사람이 늘면 세 가지 사고가 납니다.

1. **여럿이 동시에 고칩니다.** 두 선생님이 같은 파일을 각자 열어서 고칩니다. 나중에 저장한 쪽이 먼저 저장한 쪽을 덮어씁니다.
2. **쓰다가 꺼집니다.** 반쯤 저장했을 때 전기가 나가면 깨진 파일이 남습니다.
3. **찾기가 느립니다.** 한 명을 찾으려면 첫 줄부터 차례로 읽어야 합니다.

::: {.analogy title="은행 창구"}
은행은 같은 문제를 오래전에 풀었습니다. 손님마다 돈이 얼마 있는지 적어 둔 장부는 금고 안에 있습니다. 손님은 장부를 직접 만지지 못합니다. 하고 싶은 일을 신청서에 적어 내면 **창구 직원**이 대신 고칩니다.

직원은 세 가지를 책임집니다. 손님이 한꺼번에 와도 줄을 세웁니다. 하다가 만 일은 없던 일로 되돌립니다. 장부에 찾아보기를 만들어 원하는 쪽을 바로 폅니다.
:::

::: {.fig src="bank-map.svg"}
은행과 데이터베이스를 나란히 놓은 그림. 앱은 장부를 직접 고치지 않고 직원에게 부탁합니다.
:::

컴퓨터에서도 똑같이 합니다. 그림에서 "데이터베이스에서는"이라고 적힌 줄을 왼쪽부터 봅시다.

- **내 앱**은 손님입니다. 정보(데이터)를 읽고 쓰려는 프로그램입니다.
- **SQL**은 신청서입니다. 부탁할 일을 적는 언어입니다.
- **DBMS**는 창구 직원입니다. 장부를 혼자 맡아 지키는 프로그램입니다.
- **디스크의 표**는 금고 속 장부입니다. [1장](ch01.html)의 창고인 저장장치(디스크)에 적으므로 전원을 꺼도 남습니다.

이 장부 묶음이 **데이터베이스**(database)입니다. 줄여서 DB라고 부릅니다. DBMS는 "데이터베이스 관리 시스템"(Database Management System)을 줄인 말입니다. PostgreSQL, MySQL, SQLite 같은 프로그램이 널리 쓰입니다. 평소에는 장부와 직원을 합쳐서 데이터베이스라고 부를 때가 많습니다.

### 내 앱의 데이터는 어디에 있을까

앱이 정보를 메모리에만 두면 프로그램을 끌 때 사라집니다. 브라우저의 서랍인 `localStorage`([15장](ch15.html#cookie))에 두면 그 브라우저에서만 보입니다. 껐다 켜도 남고 다른 기기에서도 보이려면 데이터베이스에 두어야 합니다. 저장한 것이 새로 고치면 사라진다면 AI에게 "데이터를 어디에 저장하고 있어?"라고 물어보세요.

데이터베이스가 있는 곳은 둘 중 하나입니다.

- **내 컴퓨터의 파일.** SQLite는 장부를 `app.db` 같은 파일 하나에 담습니다. 앱은 이 파일을 직접 고치지 않고 SQLite를 거쳐 읽고 씁니다. 혼자 쓰는 앱과 연습에 알맞습니다.
- **빌려 쓰는 서비스.** 인터넷 건너편에서 DBMS를 대신 돌려 줍니다(예: Supabase, Neon). 여럿이 쓰는 앱에 알맞습니다. 가입하면 받는 접속 주소에는 비밀번호가 들어 있으니 코드에 적지 않고 `.env` 파일에 둡니다([6장](ch06.html#env)).

빌려 쓰는 서비스에는 브라우저로 여는 관리 화면이 있습니다. 표를 엑셀처럼 열어 볼 수 있어서 값이 정말 저장됐는지 확인하기 좋습니다. 다만 여기서 고치거나 지운 것은 진짜 장부에 바로 적용됩니다.

## 표, 행, 열: 칸이 정해진 장부 {#table}

출석부를 떠올려 봅시다. 맨 윗줄에 "번호", "이름" 같은 칸 제목이 있습니다. 그 아래로 학생이 한 줄에 한 명씩 적혀 있습니다. 데이터베이스도 정보를 이런 **표**에 담습니다. 영어로는 테이블(table)이라고 합니다.

표의 가로 한 줄을 **행**(row)이라고 합니다. 출석부에서는 학생 한 명이 한 행입니다.

세로 한 줄은 **열**(column)이라고 합니다. "이름" 열에는 이름만 적듯이, 한 열에는 같은 종류의 값만 들어갑니다.

동네에 컴퓨터 용품을 파는 작은 가게가 있습니다. 가게는 표 두 개를 씁니다. 단골손님을 적는 회원 표와, 누가 무엇을 샀는지 적는 주문 표입니다.

::: {.fig src="two-tables.svg"}
회원 표와 주문 표. 이 장 끝까지 이 두 표를 예로 씁니다.
:::

표와 열의 이름은 보통 영어로 짓습니다. 회원 표 `members`의 열은 번호(`id`), 이름(`name`), 전화번호(`phone`)입니다. 주문 표 `orders`의 열은 주문 번호(`id`), 회원 번호(`member_id`), 물건(`item`), 금액(`amount`)입니다. 서연의 전화번호 칸에 적힌 `NULL`은 비어 있다는 표시이고, 뒤에서 다시 봅니다.

### 행마다 붙이는 번호: 기본 키

한 학교에 김민지가 두 명 있으면 이름만으로는 누구인지 알 수 없습니다. 그래서 학생마다 겹치지 않는 학번을 붙입니다.

표도 행마다 겹치지 않는 번호를 붙여서 "바로 그 행"을 가리킵니다. 이 번호를 **기본 키**(primary key)라고 합니다. 그림에서 파란색으로 칠한 `id` 열입니다.

### 다른 표를 가리키는 번호: 외래 키

주문 표에는 손님 이름이 없습니다. 대신 `member_id` 칸에 회원 표의 `id`를 적습니다. 101번 주문의 `member_id`는 1이므로 키보드를 산 사람은 1번 회원 김민지입니다. 이렇게 다른 표의 기본 키를 적어 두는 칸을 **외래 키**(foreign key)라고 합니다.

외래 키라고 정해 둔 칸은 직원(DBMS)이 지킵니다. 회원 표에 없는 9번을 적은 주문은 거절합니다.

### 칸마다 정해 둔 규칙

표를 만들 때는 어떤 열을 둘지, 칸마다 무엇을 적을 수 있는지 미리 정합니다. 이 양식을 **스키마**(schema)라고 합니다. AI가 "표를 만들었습니다"라고 할 때는 이 양식을 SQL로 적어 보여 줍니다. 주문 표의 스키마는 이렇습니다.

```sql
CREATE TABLE orders (
  id INTEGER PRIMARY KEY,
  member_id INTEGER REFERENCES members(id),
  item TEXT NOT NULL,
  amount INTEGER NOT NULL CHECK (amount >= 0)
);
```

- 첫 줄은 "orders라는 표를 만들어라"입니다. 괄호 안에는 열을 한 줄에 하나씩 적습니다.
- `id`는 정수(`INTEGER`)이고 기본 키(`PRIMARY KEY`)입니다. 겹칠 수 없습니다.
- `member_id`에는 회원 표의 `id`에 있는 번호만 적을 수 있습니다. `REFERENCES`가 외래 키라는 표시입니다.
- `item`은 글자(`TEXT`)이고 비워 둘 수 없습니다(`NOT NULL`).
- `amount`는 비워 둘 수 없고, 0 이상이어야 합니다(`CHECK`).

"비워 둘 수 없음", "0 이상" 같은 규칙은 **제약 조건**(constraint)이라고 합니다. 금액에 -500을 적거나 물건을 비워 두면 직원이 신청서를 오류 글과 함께 돌려보냅니다. SQLite에서는 이렇게 나옵니다.

| 오류 글에 든 말 | 어긴 규칙 |
|---|---|
| `UNIQUE constraint failed` | 겹치면 안 됨 |
| `NOT NULL constraint failed` | 비워 둘 수 없음 |
| `FOREIGN KEY constraint failed` | 다른 표에 있는 번호만 |
| `CHECK constraint failed` | 0 이상 같은 조건 |

이 오류는 고장이 아니라 규칙이 잘못된 값을 막아 낸 것입니다. AI가 오류를 없애려고 규칙을 지우려 하면, 왜 그런 값이 들어오려 했는지부터 찾게 합니다.

::: {.tip title="규칙은 표에 적어 둡니다"}
게임 닉네임이 겹치면 안 된다면 "겹치면 안 됨"을 표의 규칙으로 적어 둡니다. 두 사람이 같은 닉네임을 동시에 신청해도 직원이 적는 순간에 검사하므로 한 명만 통과합니다.
:::

::: {.deep title="사진과 동영상은 어디에 둘까요?"}
사진이나 영상처럼 덩치 큰 파일은 표의 칸에 넣지 않고, 파일을 통째로 맡아 주는 보관함에 따로 둡니다. 이 보관함을 **객체 저장소**(object storage)라고 합니다. 표에는 그 파일이 어디 있는지 주소만 적습니다.
:::

### 쓰던 표의 양식 바꾸기: 마이그레이션

가게가 회원의 생일도 적기로 했다고 합시다. 회원 표에 생일 열을 더해야 합니다. 이렇게 이미 쓰고 있는 표의 양식을 바꾸는 일을 **마이그레이션**(migration)이라고 합니다. SQL로는 `ALTER TABLE members ADD COLUMN birthday TEXT;`처럼 적습니다. "회원 표에 생일 열을 더하라"는 뜻입니다.

열을 더하는 것은 안전한 편입니다. 하지만 열을 지우면 그 열의 값이 모두 사라지고, 그 열을 읽던 프로그램은 오류를 냅니다. 그래서 더하는 일을 먼저 합니다. 지우는 일은 아무도 그 열을 쓰지 않는 것을 확인한 뒤 맨 마지막에 합니다. 자세한 순서는 [20장](ch20.html#compat)에서 봅니다.

앱을 만드는 도구는 대개 양식을 바꾼 내용을 `migrations`라는 폴더에 파일로 차례차례 적어 둡니다. AI가 "마이그레이션 파일을 만들었습니다"라고 하면 이 파일을 말합니다.

::: {.warn title="AI가 표를 지우고 다시 만들겠다고 할 때"}
양식을 바꾸다 막히면 AI는 표를 통째로 지우고 새로 만들곤 합니다. `DROP TABLE`은 표와 그 안의 행을 모두 지우는 SQL입니다. 도구의 명령에 `reset`이 들어 있으면 대개 DB를 비우고 다시 만든다는 뜻입니다. 연습용 데이터뿐일 때만 허락합니다. 진짜 데이터가 들어 있다면 "행은 그대로 두고 양식만 바꿔 줘"라고 말합니다.
:::

## 같은 사실은 한 곳에만: 정규화 {#normalize}

표를 왜 둘로 나눴을까요? 주문 표 하나에 이름과 전화번호까지 적으면 더 편할 것 같습니다. 그렇게 해 봅시다.

::: {.fig src="one-big-table.svg"}
주문 표 하나에 전부 적은 모습. 민지의 전화번호가 주문마다 되풀이됩니다.
:::

이 표에서는 세 가지 탈이 납니다.

1. **고칠 때.** 민지가 전화번호를 바꿨습니다. 민지의 주문은 세 줄인데 첫 줄만 고쳤습니다. 이제 민지의 번호가 두 가지라서 어느 쪽이 맞는지 알 수 없습니다.
2. **지울 때.** 준호의 주문은 102번 하나뿐입니다. 이 주문을 지우면 준호의 연락처도 함께 사라집니다.
3. **넣을 때.** 서연은 회원이지만 아직 아무것도 사지 않았습니다. 주문이 없으니 서연을 적을 줄이 없습니다.

원인은 하나입니다. "민지의 전화번호"라는 사실 하나가 세 군데에 적혀 있습니다.

그래서 사실마다 적을 곳을 한 군데로 정하고 표를 나눕니다. 전화번호는 회원 표에만 적고, 주문 표에서는 회원 번호로 가리킵니다. 이 일을 **정규화**(normalization)라고 합니다. 앞 절의 두 표가 그 결과입니다.

::: {.key}
**한 가지 사실은 한 곳에만 적고, 다른 표에서는 번호(키)로 가리킵니다.** 그러면 고칠 곳도 한 곳입니다.
:::

::: {.tip title="코드보다 표 설계를 먼저 받습니다"}
표의 양식은 데이터가 쌓인 뒤에는 바꾸기 어렵습니다. 앱을 만들어 달라고 할 때 "코드를 쓰기 전에 표를 어떻게 나눌지 `CREATE TABLE`로 먼저 보여 줘"라고 하세요. 받으면 표마다 기본 키가 있는지, 표를 잇는 칸에 `REFERENCES`가 붙어 있는지 봅니다. 같은 사실이 두 표에 적혀 있거나, 한 칸에 "키보드, 마우스"처럼 여러 값을 몰아 적었다면 다시 나누게 합니다.
:::

### 표를 쓰지 않는 데이터베이스: 문서형

지금까지 본, 정보를 표에 담고 키로 잇는 데이터베이스를 **관계형 데이터베이스**(relational database)라고 합니다. PostgreSQL, MySQL, SQLite가 모두 관계형입니다.

**문서형 데이터베이스**(document database)는 표 대신 [8장](ch08.html#exchange)의 JSON처럼 생긴 문서에 정보를 통째로 담습니다(예: MongoDB, Firestore). 양식을 미리 정하지 않아 시작하기 쉽지만, 같은 사실을 여러 문서에 적게 되어 고칠 곳이 늘기 쉽습니다. 관계형이 아닌 데이터베이스를 묶어 **NoSQL**이라고 부릅니다.

AI가 어느 쪽을 왜 골랐는지 물어보세요. 회원과 주문처럼 서로 이어진 정보에는 대개 관계형이 잘 맞습니다.

## SQL: 원하는 것만 적는 신청서 {#sql}

은행 신청서에 "금고 셋째 칸 장부의 40쪽을 펴서"라고 적지는 않습니다. **무엇을 원하는지**만 적습니다. 어떻게 찾을지는 직원이 정합니다.

데이터베이스에 내는 신청서는 **SQL**(Structured Query Language)이라는 언어로 씁니다. "에스큐엘"이라고 읽습니다. SQL로 쓴 부탁 한 문장은 **쿼리**(query)라고 합니다.

"만 원 이상인 주문의 물건과 금액을 보여 줘"를 SQL로 적으면 이렇습니다.

```sql
SELECT item, amount
FROM orders
WHERE amount >= 10000;
```

- `SELECT item, amount`는 "물건 열과 금액 열을 꺼내라"입니다.
- `FROM orders`는 "주문 표에서"입니다.
- `WHERE amount >= 10000`은 "금액이 10000 이상인 행만"입니다. `>=`는 "크거나 같다"는 기호입니다.
- 맨 끝의 `;`은 문장이 끝났다는 표시입니다.

결과는 키보드 45000, 마우스 18000, 충전기 12000 세 줄입니다. 5000원인 케이블은 빠집니다.

금액이 큰 것부터 보고 싶으면 `;` 앞에 `ORDER BY amount DESC`를 덧붙입니다. "금액이 큰 것부터 줄 세워라"라는 뜻입니다. 이렇게 적지 않으면 결과가 어떤 순서로 나올지 알 수 없습니다.

### 묶어서 세기: GROUP BY

"모둠마다 몇 명인지 세어 와"라는 말을 들으면, 같은 모둠끼리 모아 놓고 셉니다. SQL에서도 같은 값끼리 묶어서 세거나 더할 수 있습니다. "회원마다 주문이 몇 건이고 모두 얼마인지"는 이렇게 묻습니다.

```sql
SELECT member_id, COUNT(*), SUM(amount)
FROM orders
GROUP BY member_id;
```

`GROUP BY member_id`는 "회원 번호가 같은 행끼리 묶어라"입니다. `COUNT(*)`는 묶음마다 몇 줄인지 세고, `SUM(amount)`는 금액을 더합니다.

결과는 두 줄입니다. 1번 회원은 3건에 45000 + 12000 + 5000 = 62000입니다. 2번 회원은 1건에 18000입니다. "반마다 몇 명" 같은 통계는 모두 이렇게 냅니다.

### 두 표를 붙이기: 조인

주문 목록에는 "1번 회원"보다 "김민지"라고 보여 주고 싶습니다. 그런데 이름은 회원 표에 있습니다. 두 표를 붙여야 합니다. 이 일을 **조인**(JOIN)이라고 합니다.

::: {.fig src="join-match.svg"}
조인은 주문 표의 member_id와 회원 표의 id가 같은 행끼리 짝지어 한 줄로 만듭니다.
:::

그림 맨 위의 SQL을 읽어 봅시다.

- `orders.item`은 "주문 표의 item 열"입니다. 표 이름 뒤에 점을 찍고 열 이름을 적습니다.
- `JOIN members`는 "회원 표를 붙여라"입니다.
- `ON` 뒤에는 어떤 행끼리 짝인지를 적습니다. 여기서는 회원 표의 `id`와 주문 표의 `member_id`가 같은 행끼리 짝입니다.

주문이 4건이니 결과도 4줄입니다. 민지는 세 번 샀으므로 세 번 나옵니다. 주문이 없는 서연은 짝이 없어서 빠집니다.

### NULL: 0도 빈 글자도 아닌 "모름"

서연은 전화번호를 알려 주지 않아서 그 칸이 비어 있습니다. 이 빈칸을 **NULL**(널)이라고 합니다. 숫자 0이나 빈 글자와는 다릅니다. "값을 모른다"는 표시입니다.

모르는 값은 비교할 수 없습니다. 생일을 모르는 친구와 내 생일이 같을까요? 답은 "예"도 "아니요"도 아닌 "모름"입니다. `WHERE`는 답이 "예"인 행만 남깁니다.

그래서 `WHERE phone = NULL`로 찾으면 아무도 나오지 않습니다. "민지와 번호가 다른 회원"을 찾아도 서연은 빠집니다. 빈칸은 `WHERE phone IS NULL`로 찾습니다. "이 칸이 비어 있는가"를 묻는 말이라서 서연이 나옵니다.

### 넣고, 고치고, 지우기

`SELECT`는 읽기만 하므로 장부가 바뀌지 않습니다. 장부를 바꾸는 SQL은 첫 낱말이 다릅니다. 자주 보는 첫 낱말은 넷입니다.

| 첫 낱말 | 하는 일 | 예 |
|---|---|---|
| `SELECT` | 읽기 | `SELECT name FROM members;` |
| `INSERT` | 새 행 넣기 | `INSERT INTO orders VALUES (105, 2, '헤드셋', 30000);` |
| `UPDATE` | 있는 행 고치기 | `UPDATE orders SET amount = 28000 WHERE id = 105;` |
| `DELETE` | 행 지우기 | `DELETE FROM orders WHERE id = 105;` |

`INSERT`의 괄호 안은 열 순서대로 적은 값이고, 글자는 작은따옴표로 감쌉니다. `UPDATE`의 예는 "105번 주문의 금액을 28000으로 바꿔라", `DELETE`의 예는 "105번 주문을 지워라"입니다. AI가 SQL을 실행하겠다고 하면 첫 낱말부터 봅니다.

::: {.warn title="WHERE가 빠지면 모든 행이 바뀝니다"}
`UPDATE`와 `DELETE`에서 `WHERE`는 "어느 행을"입니다. 이것이 빠진 `DELETE FROM orders;`는 주문을 전부 지웁니다. `UPDATE orders SET amount = 0;`은 모든 주문의 금액을 0으로 만듭니다. 오류도 나지 않습니다.

실행하기 전에 같은 `WHERE`를 `SELECT`에 붙여 먼저 돌려 봅니다. `SELECT * FROM orders WHERE id = 105;`가 한 줄을 보여 주면 `DELETE`도 그 한 줄만 지웁니다. `*`는 "모든 열"입니다.
:::

::: {.try}
맥의 터미널([5장](ch05.html))에 `sqlite3 practice.db`라고 치면 연습용 DB 파일이 생기면서 열립니다. 닫을 때는 `.quit`라고 칩니다. 윈도우라면 브라우저에서 쓰는 SQLite 연습 사이트를 찾아 씁니다.

1. AI 챗봇에게 두 표의 내용을 알려 주고 "SQLite에서 이 표를 만들고 행을 넣는 SQL을 써 줘"라고 합니다. `PRIMARY KEY`와 `REFERENCES`가 있는지 본 뒤 붙여 넣습니다.
2. 이 절의 쿼리를 쳐서 결과가 같은지 봅니다.
3. `PRAGMA foreign_keys = ON;`을 친 뒤, 없는 9번 회원의 주문을 `INSERT`로 넣어 봅니다. `FOREIGN KEY constraint failed`가 나오면 직원이 막은 것입니다.

SQLite는 외래 키 검사가 처음에는 꺼져 있어서 3번처럼 켜야 합니다. AI가 SQLite로 앱을 만들었다면 이 검사를 켰는지 물어보세요.
:::

## 인덱스: 책 뒤의 찾아보기 {#index}

두꺼운 과학책에서 "광합성"이 나오는 곳을 찾고 싶습니다. 첫 쪽부터 넘기면 한참 걸립니다. 그래서 책 맨 뒤에는 **찾아보기**가 있습니다. 낱말이 가나다순으로 늘어서 있고 옆에 쪽수가 적혀 있습니다.

표에서도 같은 일이 생깁니다. 주문 표에는 주문이 들어온 순서대로 쌓입니다. 여기서 7번 회원의 주문만 찾으려면 모든 행을 하나씩 확인해야 합니다. 주문이 8건이면 8줄, 100만 건이면 100만 줄을 봅니다.

그래서 표에도 찾아보기를 만듭니다. 이것을 **인덱스**(index)라고 합니다. 열 하나를 골라 값을 순서대로 늘어놓은 **별도의 장부**입니다. 값마다 그 행이 어디 있는지도 적어 둡니다.

::: {.fig src="index-lookup.svg"}
회원 번호(member_id)로 만든 인덱스. 7이 모인 곳을 찾으면 주문 표의 그 행으로 곧장 갑니다.
:::

그림은 회원과 주문이 늘어난 뒤의 모습입니다. 왼쪽의 인덱스는 회원 번호순이라서 7이 한곳에 모여 있습니다. 옆에 적힌 주문 번호 202, 204, 207을 보고 주문 표의 그 행으로 바로 갑니다. 8줄 대신 3줄만 확인했습니다.

7이 모인 곳도 금방 찾습니다. [8장](ch08.html#tree)의 트리처럼 갈림길을 따라 내려가는데, 갈림길 하나가 수백 갈래로 나뉩니다. 100갈래씩 세 번만 내려가도 100 × 100 × 100 = 100만 곳에 닿으니, 100만 건이어도 갈림길 서너 번이면 됩니다. 이런 트리를 **B-tree**(비 트리)라고 부릅니다.

::: {.photo src="card-catalog.jpg"}
도서관의 카드 목록 서랍. 책은 책장에 그대로 두고, 찾는 데 쓸 카드만 따로 알파벳순으로 정리했습니다.
:::

인덱스는 공짜가 아닙니다. 주문 한 건을 적을 때마다 인덱스에도 한 줄을 끼워 넣어야 합니다. 인덱스가 다섯 개면 장부 여섯 권을 고치는 셈입니다.

::: {.key}
인덱스는 **읽기를 빠르게 하는 대신 쓰기를 느리게** 합니다. 자주 찾는 열에만 만듭니다.
:::

기본 키에는 인덱스가 저절로 생기고, 그 밖의 열에는 대개 `CREATE INDEX`로 시작하는 SQL로 따로 만듭니다. AI가 만든 앱은 행이 적을 때는 빠르다가 행이 늘면 느려지곤 합니다. 자주 찾는 조건에 맞는 인덱스가 있는지 물어보세요.

### 열 두 개로 만든 인덱스: 순서가 중요합니다

열 두 개를 묶어 만든 인덱스를 **복합 인덱스**(composite index)라고 합니다. 그림은 회원 번호(`member_id`)를 앞에, 주문한 날짜(`ordered_at`)를 뒤에 둔 인덱스입니다. 반 순서로 적고, 같은 반 안에서는 번호 순서로 적은 학교 명단과 같습니다.

::: {.fig src="composite-index.svg"}
회원 번호를 앞에, 날짜를 뒤에 두고 정렬한 인덱스. 한 회원의 주문이 한곳에 모입니다.
:::

"7번 회원의 11월 주문"은 11/01, 11/15, 11/30이 나란히 붙어 있어서 한 구간만 읽으면 됩니다. "모든 회원의 11월 주문"은 7번, 8번, 9번 회원의 구간에 흩어져 있어서 여러 곳을 뒤져야 합니다. 날짜로 자주 찾는다면 날짜가 앞에 오는 인덱스를 따로 만듭니다.

## 느릴 때 물어볼 두 가지: 실행 계획과 N+1 {#slow}

화면이 늦게 뜬다면 두 가지를 물어봅니다. **한 번 물을 때 너무 많이 읽는가. 너무 여러 번 묻는가.**

### 한 번이 느릴 때: 직원에게 계획을 묻습니다

직원(DBMS)은 쿼리를 받으면 어떻게 찾을지 계획부터 세웁니다. 이것을 **실행 계획**(query plan)이라고 합니다. 쿼리 앞에 `EXPLAIN`을 붙여 보내면 직원은 찾는 대신 계획을 알려 줍니다(SQLite에서는 `EXPLAIN QUERY PLAN`).

답이 "표를 처음부터 끝까지 훑겠습니다"라면 인덱스를 쓰지 못하고 있는 것입니다. 실제 글자로는 `Seq Scan`(PostgreSQL)이나 `SCAN`(SQLite)이라고 나옵니다. 찾는 조건에 맞는 인덱스를 만들면 `Index Scan`이나 `USING INDEX`로 바뀝니다. "인덱스로 찾겠습니다"라는 뜻입니다.

목록을 통째로 가져오는 것도 너무 많이 읽는 일입니다. 긴 목록은 [9장](ch09.html)에서 본 것처럼 20개씩 끊어서 가져오게 합니다. SQL로는 `LIMIT 20 OFFSET 40`처럼 적습니다. "40줄을 건너뛰고 20줄까지만"이라는 뜻이라서 3쪽이 나옵니다.

### 여러 번 물을 때: N+1 문제

친구 다섯 명의 간식을 사러 매점에 간다고 합시다. 한 명에게 묻고 다녀오고, 또 한 명에게 묻고 다녀오면 다섯 번을 오갑니다. 다섯 명에게 먼저 다 묻고 한 번에 다녀오는 편이 훨씬 빠릅니다.

프로그램도 DB에 물을 때마다 DB까지 다녀옵니다. 주문 100건과 주문한 회원의 이름을 한 화면에 보여 준다고 합시다.

::: {.fig src="n-plus-one.svg"}
쿼리 하나하나는 빠릅니다. 느린 것은 DB까지 다녀오는 횟수입니다.
:::

그림 왼쪽은 하나씩 묻습니다. 먼저 `LIMIT 100`으로 주문 100건을 가져옵니다. 그다음 주문마다 "1번 회원은 누구?", "2번 회원은 누구?" 하고 따로 묻습니다. 모두 1 + 100 = 101번입니다. 목록을 1번 읽고 항목 N개마다 1번씩 더 묻는다고 해서 **N+1 문제**라고 부릅니다.

왕복 한 번에 2ms가 걸린다고 합시다. ms(밀리초)는 1,000분의 1초입니다. 101번이면 101 × 2 = 202ms입니다.

그림 오른쪽은 주문 100건에 나온 회원 번호를 모아서 한 번에 묻습니다. `IN (1, 2, 3, …)`이 "번호가 이 가운데 하나인 회원"이라는 뜻입니다. 두 번만 다녀오면 되니 2 × 2 = 4ms입니다.

요즘은 프로그래밍 언어로 적으면 SQL로 바꿔서 대신 보내 주는 도구를 많이 씁니다. 이런 도구를 **ORM**이라고 합니다(예: Prisma, SQLAlchemy). 편하지만 어느 줄에서 DB에 묻는지 눈에 보이지 않아서 N+1 문제를 놓치기 쉽습니다.

AI가 만든 프로그램에서도 자주 보입니다. "이 화면을 열 때 쿼리가 몇 번 나가는지 세어 줘"라고 시켜 보세요. 목록이 길수록 횟수가 늘어난다면 N+1입니다.

## 트랜잭션: 전부 되거나, 전부 안 되거나 {#transaction}

민지가 준호에게 30,000원을 보냅니다. 민지의 통장에는 50,000원, 준호의 통장에는 20,000원이 있습니다. 은행 장부에서는 두 줄을 고칩니다. 민지에게서 30,000원을 빼고, 준호에게 30,000원을 더합니다.

그런데 첫 줄만 고친 순간 은행의 컴퓨터(서버)가 꺼지면 어떻게 될까요?

::: {.fig src="transfer.svg"}
두 번의 수정 사이에서 멈추면 돈이 사라집니다. 트랜잭션으로 묶으면 중간 상태가 남지 않습니다.
:::

그림 위쪽이 그 사고입니다. 민지는 20,000원이 됐는데 준호는 그대로 20,000원입니다. 둘의 합계가 70,000원에서 40,000원으로 줄었습니다. 30,000원이 사라졌습니다.

이런 사고를 막으려고 여러 작업을 **한 건**으로 묶습니다. 이 묶음을 **트랜잭션**(transaction)이라고 합니다. SQL로는 이렇게 적습니다.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 30000 WHERE id = 1;
UPDATE accounts SET balance = balance + 30000 WHERE id = 2;
COMMIT;
```

- `BEGIN`은 "여기부터 한 묶음"입니다.
- 둘째 줄은 통장 표(`accounts`)에서 1번 통장인 민지의 잔액(`balance`)을 30000 줄입니다.
- 셋째 줄은 2번 통장인 준호의 잔액을 30000 늘립니다.
- `COMMIT`은 "여기까지 확정"입니다. 이 확정을 **커밋**이라고 합니다.

커밋하기 전에 컴퓨터가 꺼지면 묶음 안에서 고친 것은 모두 취소됩니다. 이 취소를 **롤백**(rollback)이라고 합니다. 그림 아래쪽에서 민지의 잔액이 50,000원으로 돌아간 것이 롤백입니다. 반만 된 상태는 남지 않습니다. 반대로 커밋한 것은 전원이 꺼져도 남습니다.

::: {.try}
연습용 DB를 `sqlite3 practice.db`로 다시 열고, 아래를 한 줄씩 칩니다.

1. `BEGIN;`
2. `DELETE FROM orders;`를 칩니다. `WHERE`가 없으니 주문이 모두 지워집니다.
3. `SELECT COUNT(*) FROM orders;`를 치면 0이 나옵니다.
4. `ROLLBACK;`
5. 3번을 다시 치면 4가 나옵니다.

4번에서 `COMMIT;`을 쳤다면 되돌릴 수 없습니다. 장부를 바꾸는 SQL을 손으로 칠 때는 `BEGIN`부터 칩니다.
:::

트랜잭션이 지키는 약속은 넷입니다. 전부 되거나 전부 취소됩니다(원자성). 표의 규칙을 어긴 채로 끝나지 않습니다(일관성). 동시에 하는 묶음끼리 섞이지 않습니다(격리성). 커밋한 것은 꺼져도 남습니다(지속성). 이 넷을 묶어 **ACID**(애시드)라고 부릅니다.

## 동시에 고칠 때: 잠금과 조건 {#concurrency}

가게에 인기 있는 헤드셋이 딱 1개 남았습니다. 상품 번호는 7번입니다. A와 B가 앱으로 동시에 주문합니다. 프로그램은 남은 개수를 **읽고**, 1개 있으면 주문을 만들고, 남은 개수를 0으로 **저장합니다.**

::: {.fig src="stock-race.svg"}
읽기와 저장이 따로이면 둘 다 성공합니다. 확인과 고치기를 한 문장으로 합치면 한 명만 성공합니다.
:::

가게에 남은 개수를 재고라고 하고, 그림에서는 `qty`라고 적었습니다. 그림 위쪽에서 A가 재고를 읽으니 1입니다. A가 저장하기 전에 B도 읽습니다. 아직 1입니다. 둘 다 "살 수 있다"고 판단해 주문을 만들고 0을 저장합니다.

재고는 0인데 주문은 2건입니다. 없는 물건을 팔았습니다. [11장](ch11.html#race)의 칠판 사고가 장부에서 일어난 것입니다.

::: {.myth title="트랜잭션으로 묶었으니 동시에 와도 안전하다"}
트랜잭션이 막는 것은 중간에 멈추는 사고입니다. 묶음끼리 얼마나 엄격하게 떼어 놓을지는 **격리 수준**(isolation level)이라는 설정으로 고릅니다. 많은 DB의 기본값은 "남이 커밋한 것만 보인다"는 정도라서, 두 묶음이 같은 재고를 동시에 읽을 수 있습니다. 그래서 위 사고는 트랜잭션 안에서도 일어납니다.
:::

막는 방법은 두 가지입니다.

**먼저 잠그기.** 재고를 읽을 때 그 행에 자물쇠를 겁니다. A가 먼저 걸면 B는 A의 묶음이 끝날 때까지 기다립니다. 기다린 뒤에 읽으면 재고는 이미 0입니다. 이것을 **잠금**(lock)이라고 합니다. [11장](ch11.html#lock)의 하나뿐인 분필과 같습니다.

**고치는 순간에 확인하기.** 확인과 고치기를 한 문장으로 합칩니다. 그림 아래쪽의 "조건부 UPDATE"가 그것입니다. 풀어 읽으면 "재고 표(`stock`)에서 7번 상품의 재고가 0보다 클 때만 1 줄여라"입니다.

직원은 몇 행이 바뀌었는지 알려 줍니다. A가 먼저 닿으면 재고가 1에서 0이 되고 "1행이 바뀜"이라는 답을 받아 주문을 만듭니다. B가 닿았을 때는 재고가 이미 0이라 조건에 맞는 행이 없습니다. B는 "0행이 바뀜"이라는 답을 받고 품절이라고 안내합니다.

::: {.key}
트랜잭션은 **중간에 멈추는 사고**를, 잠금과 조건을 붙인 UPDATE는 **동시에 고치는 사고**를 막습니다. 서로 다른 문제입니다.
:::

::: {.deep title="창구는 몇 개일까: 커넥션 풀"}
프로그램이 DB와 이야기하는 통로(연결)는 은행으로 치면 창구입니다. 새로 여는 데 시간이 걸려서 몇 개를 미리 열어 두고 돌려 씁니다. 이 묶음을 **커넥션 풀**(connection pool)이라고 합니다. 창구 수는 정해져 있으니 짧게 쓰고 바로 돌려줍니다.
:::

## 사본으로 지키기: 복제, 백업, 캐시 {#operate}

중요한 숙제 파일은 USB에도 복사해 둡니다. 원본이 날아가도 사본이 남기 때문입니다. 데이터베이스도 사본을 둡니다. 사본은 세 종류이고 쓰임이 다릅니다.

::: {.key}
원본은 하나입니다. **사본은 언제나 원본보다 조금 늦습니다.**
:::

### 복제: 지금을 따라가는 사본

원본 DB가 든 컴퓨터가 고장 나면 앱이 통째로 멈춥니다. 그래서 다른 컴퓨터가 원본의 변경을 곧바로 따라 적게 합니다. 이것을 **복제**(replication)라고 하고, 따라 적는 쪽을 복제본이라고 부릅니다. 원본이 고장 나면 복제본이 대신하고, 평소에는 읽기 요청을 나눠 맡습니다.

다만 바뀐 내용이 복제본까지 건너가는 데 시간이 걸립니다. 이 틈을 **복제 지연**(replication lag)이라고 합니다.

::: {.fig src="replica-lag.svg"}
저장은 원본에, 읽기는 복제본에서 했습니다. 방금 고친 것이 안 보일 때 흔한 원인입니다.
:::

그림에서 민지는 닉네임을 "민지"에서 "밍"으로 바꾸고, 0.1초에 프로필을 새로고침했습니다. 변경은 0.5초에야 복제본에 도착하므로 옛 닉네임이 뜹니다. 1.0초에 다시 새로고침하면 "밍"이 보입니다. 방금 고친 사람의 다음 읽기는 원본에서 하게 하면 풀립니다.

### 백업: 과거로 돌아가는 사본

게임에서 어려운 보스 앞에 서면 저장부터 합니다. 지면 그 지점으로 돌아가려는 것입니다. **백업**(backup)이 이런 사본입니다. 어느 시점의 DB를 통째로 복사해 따로 둔 것입니다.

복제본이 있어도 백업은 따로 필요합니다. 누가 실수로 주문을 모두 지우면 복제본도 그대로 따라 지우기 때문입니다.

얼마나 자주 백업할지는 **얼마나 잃어도 되는가**로 정합니다. 매일 밤 12시에만 백업한다면, 다음 날 밤 11시에 사고가 났을 때 23시간 동안 쌓인 주문을 잃습니다. 그리고 백업은 실제로 되살려 봐야 믿을 수 있습니다([21장](ch21.html#ops)).

빌려 쓰는 DB 서비스는 대개 날마다 알아서 백업해 줍니다. 다만 요금제에 따라 없을 수도 있으니 관리 화면에서 확인합니다. SQLite는 앱을 끄고 DB 파일을 복사해 두면 그것이 백업입니다.

### 캐시: 가까이 둔 사본

[1장](ch01.html)의 요리사는 소금을 손 옆 선반에 두었습니다. 자주 읽는 결과를 이렇게 가까이에 복사해 둔 것이 **캐시**(cache)입니다. 하지만 원본이 바뀌어도 사본은 저절로 바뀌지 않습니다. 재고처럼 틀리면 안 되는 것은 원본을 보고 판단합니다.

### 진짜 데이터를 건드리기 전에

앱을 만드는 동안에는 표를 지우고 다시 만드는 일이 잦습니다. 그래서 데이터베이스를 두 벌 둡니다. 마음껏 망가뜨려도 되는 연습용 DB와, 진짜 사용자의 정보가 든 실제 DB입니다([20장](ch20.html#environments)의 개발 환경과 운영 환경). 시험은 연습용에서만 합니다. AI 코딩 도구에게도 연습용 DB의 접속 주소만 줍니다. 실제 DB의 주소를 모르면 실수로도 지울 수 없습니다.

코드와 달리, 지워진 행은 Git([7장](ch07.html))으로 되돌릴 수 없습니다. 실제 DB에서 무언가를 지우거나 양식을 바꿀 때는 이 순서로 합니다.

1. 백업부터 합니다.
2. 실행할 SQL을 글로 받아 읽습니다. `DROP`, `TRUNCATE`(표의 행을 모두 지움), `WHERE` 없는 `DELETE`와 `UPDATE`가 보이면 멈추고 까닭을 묻습니다.
3. 연습용 DB에서 먼저 돌려 봅니다.
4. 실제 DB에서 실행하고, 바뀐 행 수가 예상과 같은지 봅니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 기본 키 / 외래 키 | 내 표의 행을 가리키는 번호 / 다른 표의 행을 가리키는 번호 |
| NULL / 0, 빈 글자 | 값을 모름 / 값이 있고 그 값이 0이나 빈 글자 |
| DELETE / DROP TABLE | 행을 지움 / 표를 양식까지 통째로 지움 |
| 인덱스 / 캐시 | 원본을 빨리 찾는 찾아보기 / 결과를 복사해 둔 사본 |
| 트랜잭션 / 잠금 | 여러 작업을 한 건으로 묶기 / 남이 끼어들지 못하게 막기 |
| 복제 / 백업 | 지금을 따라가는 사본 / 과거로 돌아가는 사본 |

## 실전 사례 {#case}

::: {.case title="'내가 빌린 책' 화면이 3초나 걸린다"}
학교 도서부가 대출 기록을 데이터베이스에 담고 앱을 만들었습니다. '내가 빌린 책' 화면은 한 학생이 빌린 책 30권을 제목과 함께 보여 줍니다. 그런데 뜨는 데 3초가 걸립니다. 인덱스를 두 개 더 만들었지만 그대로입니다.

1. **몇 번 묻는지부터 셉니다.** 화면을 열 때 쿼리가 31번 나갔습니다. 대출 기록 30건을 가져온 뒤 책마다 제목을 따로 묻는 N+1입니다.
2. **한꺼번에 묻게 바꿉니다.** 책 번호 30개를 모아 한 번에 묻도록 고쳤습니다. 쿼리가 2번으로 줄었습니다.
3. **남은 쿼리의 계획을 묻습니다.** `EXPLAIN`을 붙여 보니 "이 학생의 대출 기록"을 찾는 쿼리가 표 전체를 훑고 있었습니다. 만들어 둔 인덱스는 조건과 맞지 않았습니다.
4. **조건에 맞는 인덱스로 바꿉니다.** 학생 번호를 앞에, 빌린 날짜를 뒤에 둔 복합 인덱스를 만들었습니다. 계획이 "인덱스로 찾겠습니다"로 바뀌었습니다.

짐작으로 인덱스부터 늘리지 말고 쿼리 수와 실행 계획부터 봅니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- **데이터베이스**는 창구 직원(DBMS)이 지키는 장부입니다. 동시에 고치기, 쓰다가 꺼지기, 느린 찾기를 직원이 대신 책임집니다.
- 정보는 **표**에 담습니다. **기본 키**로 행을 가리키고 **외래 키**로 표를 잇습니다. 같은 사실은 한 곳에만 적습니다. 표 설계는 코드보다 먼저 받아 봅니다.
- **SQL**의 첫 낱말이 `SELECT`면 읽기이고, `INSERT`·`UPDATE`·`DELETE`면 장부를 바꿉니다. `WHERE`가 빠진 `UPDATE`와 `DELETE`는 모든 행을 바꿉니다.
- **인덱스**는 찾아보기입니다. 읽기는 빨라지고 쓰기는 느려집니다. 느릴 때는 **묻는 횟수**와 **실행 계획**을 봅니다.
- **트랜잭션**은 전부 되거나 전부 안 됩니다. 동시에 고치는 사고는 잠금이나 조건을 붙인 UPDATE로 따로 막습니다.
- 표의 양식을 바꾸는 **마이그레이션**은 더하기를 먼저, 지우기를 맨 나중에 합니다. 표를 지우고 다시 만드는 일은 연습용 DB에서만 합니다.
- 실수로 지운 것은 복제본이 아니라 **백업**으로만 되살립니다. 실제 DB를 고치기 전에 백업하고, 연습용 DB에서 먼저 돌려 봅니다.
:::

## 확인 문제 {#quiz}

::: {.q}
게임에 가입할 때 프로그램이 "같은 닉네임이 있는지 찾아보고, 없으면 저장"합니다. 그런데 닉네임이 똑같은 사람이 두 명 생겼습니다. 왜 그럴까요?

::: {.a}
찾아보는 일과 저장하는 일 사이에 틈이 있습니다. 두 사람이 동시에 신청하면 둘 다 "없음"이라는 답을 받고 저장합니다. 닉네임 열에 "겹치면 안 됨"이라는 제약 조건을 걸면 한 명만 통과합니다.
:::
:::

::: {.q}
반 친구 표에 생일 열이 있습니다. 지우는 생일을 적지 않아서 그 칸이 NULL입니다. "생일이 5월이 아닌 친구"를 찾으면 지우가 나올까요?

::: {.a}
나오지 않습니다. NULL은 "모름"이라서 5월인지 아닌지도 "모름"입니다. 답이 "예"인 행만 남으므로 지우는 빠집니다. 생일이 빈 친구는 `IS NULL`로 따로 찾습니다.
:::
:::

::: {.q}
2번 회원 준호의 주문을 지워 달라고 했더니, AI가 `DELETE FROM orders;`를 실행하겠다고 합니다. 이대로 실행하면 어떻게 될까요? 실행하기 전에 무엇을 해 보면 좋을까요?

::: {.a}
`WHERE`가 없어서 주문 네 건이 모두 지워집니다. `WHERE member_id = 2`를 붙여야 합니다. 실행하기 전에 같은 `WHERE`를 붙인 `SELECT`를 돌려 마우스 한 줄만 나오는지 봅니다. 진짜 데이터라면 백업부터 합니다.
:::
:::

::: {.q}
게임에서 친구에게 아이템을 주려면 내 가방에서 빼고 친구 가방에 넣어야 합니다. AI가 "두 작업을 트랜잭션으로 묶었으니, 하나 남은 아이템을 두 친구에게 동시에 주는 일도 없습니다"라고 합니다. 맞을까요?

::: {.a}
반만 맞습니다. 트랜잭션은 내 가방에서만 빠지고 친구에게는 들어가지 않은 반쪽 상태를 막습니다. 두 요청이 동시에 "1개 있음"을 읽는 일은 막지 못합니다. "남아 있을 때만 줄여라"라는 조건을 붙이거나 그 행을 먼저 잠가야 합니다.
:::
:::

::: {.q}
"복제본이 두 대나 있으니 백업은 없어도 된다"는 말에서 빠진 것은 무엇일까요?

::: {.a}
복제본은 원본이 바뀌는 대로 따라 합니다. 실수로 지운 것은 복제본에서도 지워집니다. 과거로 돌아가려면 백업이 필요합니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI는 혼자 쓸 때만 잘 되는 DB 코드를 만들기 쉽고, 장부를 바꾸는 SQL도 거침없이 실행합니다. **표 설계는 코드보다 먼저 받고, 지우거나 양식을 바꾸는 일은 연습용 DB에서 먼저** 하게 하세요.

> 동네 가게 주문 앱을 만들 거야. 코드를 쓰기 전에 표 설계를 CREATE TABLE로 보여 줘. 기본 키, 외래 키, 비우면 안 되는 칸, 겹치면 안 되는 칸을 적어 줘. 재고는 "남아 있을 때만 줄여라"라는 조건을 붙여서 줄이고, 주문 저장과 한 트랜잭션으로 묶어 줘. 하나 남은 물건을 두 명이 동시에 사는 상황을 연습용 DB에서 돌려 보고 결과를 보여 줘. 표나 열을 지우는 SQL과 WHERE 없는 UPDATE·DELETE는 실행하기 전에 나에게 보여 줘.

**받은 답에서 확인할 것**

- 표마다 기본 키가 있고, 표를 잇는 칸에 `REFERENCES`가 붙어 있는가
- 같은 사실이 두 표에 적혀 있지 않은가
- 바뀐 행이 0개일 때 품절로 처리하는가
- 동시에 사는 상황을 실제로 돌린 결과가 있는가

**AI가 자주 하는 실수**

- 양식을 바꾸다 막히면 표를 지우고 다시 만듭니다. `DROP TABLE`이나 `reset`이 보이면 멈추고, 안에 든 행은 어떻게 되는지 묻습니다.
- 목록의 항목마다 DB에 따로 묻습니다(N+1). 화면 하나에 쿼리가 몇 번 나가는지 세어 달라고 하면 드러납니다.
- "읽고, 있으면 줄인다"처럼 확인과 고치기를 따로 합니다. 두 명이 동시에 오면 어떻게 되는지 묻습니다.
:::

## 용어 정리 {#terms}

::: {.terms}
데이터베이스 (database, DB)
:   많은 정보를 표에 담아 안전하게 보관하는 장부 묶음.

DBMS (Database Management System)
:   데이터베이스를 지키고 부탁을 처리하는 프로그램.

표 (table)
:   칸 제목이 정해진, 정보를 담는 틀.

행 (row)
:   표의 가로 한 줄.

열 (column)
:   표의 세로 한 줄.

SQL (Structured Query Language)
:   데이터베이스에 부탁할 때 쓰는 언어.

쿼리 (query)
:   SQL로 쓴 부탁 한 문장.

스키마 (schema)
:   표의 열과 칸마다 적을 수 있는 값을 정해 둔 양식.

기본 키 (primary key)
:   표에서 행 하나를 가리키는, 겹치지 않는 번호.

외래 키 (foreign key)
:   다른 표의 기본 키를 적어 두어 두 표를 잇는 칸.

제약 조건 (constraint)
:   칸에 적을 값이 지켜야 하는 규칙.

객체 저장소 (object storage)
:   사진과 영상 같은 큰 파일을 통째로 맡기는 보관함.

마이그레이션 (migration)
:   이미 쓰고 있는 표의 양식을 바꾸는 일.

정규화 (normalization)
:   같은 사실이 한 곳에만 적히도록 표를 나누는 일.

관계형 데이터베이스 (relational database)
:   정보를 표에 담고 키로 잇는 데이터베이스.

문서형 데이터베이스 (document database)
:   표 대신 JSON처럼 생긴 문서를 통째로 담는 데이터베이스.

NoSQL
:   관계형이 아닌 데이터베이스를 묶어 부르는 말.

조인 (JOIN)
:   번호가 같은 행끼리 짝지어 두 표를 붙이는 일.

NULL
:   값을 모른다는 표시. 0이나 빈 글자와 다르다.

인덱스 (index)
:   열의 값을 순서대로 늘어놓고 행의 위치를 적어 둔 찾아보기.

B-tree
:   갈림길 하나가 수백 갈래로 나뉘는, 인덱스에 쓰는 트리.

복합 인덱스 (composite index)
:   열 두 개 이상을 묶어 만든 인덱스.

실행 계획 (query plan)
:   DB가 쿼리의 답을 어떻게 찾을지 세운 계획.

N+1 문제 (N+1 query problem)
:   목록을 한 번 읽은 뒤 항목마다 한 번씩 더 묻는 일.

ORM (Object-Relational Mapping)
:   프로그래밍 언어로 적은 것을 SQL로 바꿔 대신 보내 주는 도구.

트랜잭션 (transaction)
:   여러 작업을 전부 하거나 전부 취소하는 한 묶음.

커밋 (commit)
:   트랜잭션에서 고친 것을 확정하는 일.

롤백 (rollback)
:   트랜잭션에서 고친 것을 모두 취소하는 일.

ACID
:   트랜잭션의 네 가지 약속. 원자성, 일관성, 격리성, 지속성.

격리 수준 (isolation level)
:   트랜잭션끼리 얼마나 엄격하게 떼어 놓을지 정하는 설정.

잠금 (lock)
:   한 행을 고치는 동안 남이 끼어들지 못하게 거는 자물쇠.

커넥션 풀 (connection pool)
:   미리 열어 두고 돌려 쓰는 DB 연결 묶음.

복제 (replication)
:   원본 DB의 변경을 다른 컴퓨터가 곧바로 따라 적게 하는 일.

복제 지연 (replication lag)
:   원본에서 바뀐 내용이 복제본에 닿기까지 걸리는 시간.

백업 (backup)
:   어느 시점의 DB를 통째로 복사해 따로 둔 사본.

캐시 (cache)
:   자주 읽는 결과를 가까이에 복사해 둔 사본.
:::
