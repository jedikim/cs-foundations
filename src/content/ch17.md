::: {.lead}
주문을 파일 하나에 저장하던 가게가 커지면 이상한 일이 생깁니다. 동시에 들어온 두 주문 중 하나가 사라지고, 저장하던 중에 서버가 꺼져 파일이 깨지고, 검색이 몇 초씩 걸립니다. 이 세 가지 사고를 대신 막아 주는 프로그램이 **데이터베이스**입니다.
:::

::: {.goals}
- 파일 대신 데이터베이스를 쓰는 이유를 세 가지로 말할 수 있습니다.
- 표 두 개를 키로 잇고, SQL로 원하는 행을 꺼낼 수 있습니다.
- 조회가 느릴 때 인덱스, 실행 계획, 쿼리 횟수 중 어디를 볼지 압니다.
- 트랜잭션, 잠금, 백업이 각각 어떤 사고를 막는지 구분할 수 있습니다.
:::

## 파일 하나로는 왜 안 될까 {#why}

가게의 주문을 `orders.json` 파일 하나에 적는다고 합시다. 손님이 늘면 세 가지 사고가 납니다.

1. **여럿이 동시에 고칩니다.** 두 요청이 같은 파일을 각자 읽어서 고친 뒤 저장하면, 나중에 저장한 쪽이 먼저 저장한 쪽을 덮어씁니다.
2. **쓰다가 꺼집니다.** 파일을 반쯤 썼을 때 전원이 나가면 앞부분만 새 내용인 깨진 파일이 남습니다.
3. **찾기가 느립니다.** 주문 100만 건에서 한 사람의 주문을 찾으려면 처음부터 끝까지 읽어야 합니다.

::: {.analogy title="은행 창구"}
은행은 같은 문제를 오래전에 풀었습니다. 손님은 금고 속 장부를 직접 만지지 못합니다. 원하는 일을 신청서에 적어 내면 **창구 직원**이 장부를 대신 고칩니다. 직원은 손님을 줄 세우고, 처리하다 만 일은 없던 일로 되돌리고, 찾아보기를 두어 원하는 쪽을 바로 폅니다.
:::

::: {.fig src="bank-map.svg"}
은행과 데이터베이스의 대응. 앱은 장부를 직접 고치지 않고 창구 직원에게 요청합니다.
:::

**데이터베이스**(database, 줄여서 DB)는 이 장부 묶음입니다. 장부를 지키는 창구 직원 프로그램은 **DBMS**(Database Management System, 데이터베이스 관리 시스템)라고 하며, PostgreSQL, MySQL, SQLite가 대표적입니다. [1장](ch01.html)의 주방으로 치면 창고 앞에 창구를 하나 차린 셈입니다.

앱은 **SQL**(Structured Query Language)이라는 언어로 쓴 신청서를 DBMS에 보냅니다. 이 장에서는 데이터를 표 모양으로 담는 **관계형 데이터베이스**(relational database)를 다룹니다.

::: {.note}
혼자 쓰는 설정은 파일이면 충분합니다. 작은 앱은 파일 하나에 통째로 담기는 DB인 SQLite로 시작해도 됩니다.
:::

::: {.deep title="사진과 동영상은 어디에 둘까: 객체 저장소"}
사진이나 영상처럼 덩치 큰 파일은 DB에 넣지 않고 **객체 저장소**(object storage)에 둡니다. 이름표(키) 하나에 파일 하나를 통째로 맡기는 큰 보관함입니다. DB에는 그 파일의 주소만 적습니다.

두 곳에 쓰는 일은 한 묶음으로 처리되지 않습니다. 파일만 올라가고 DB 기록이 실패하면 주인 없는 파일이 남습니다. 그래서 파일을 먼저 올린 뒤 DB에 주소를 적고, 주인 없는 파일은 나중에 모아 지웁니다.
:::

## 표, 행, 열: 칸이 정해진 장부 {#table}

장부는 아무렇게나 적는 공책이 아닙니다. 칸의 제목이 미리 인쇄되어 있습니다. DB도 데이터를 칸이 정해진 **테이블**(table, 표)에 담습니다.

표의 세로 칸이 **열**(column), 가로 한 줄이 **행**(row)입니다. 작은 가게의 회원 표와 주문 표를 봅시다.

::: {.fig src="two-tables.svg"}
회원 표와 주문 표. 이 장 끝까지 이 두 표를 예로 씁니다.
:::

표에 어떤 열이 있고 각 열에 어떤 값이 들어갈 수 있는지 정한 양식을 **스키마**(schema)라고 합니다. 주문 표의 스키마는 이렇게 적습니다.

```sql
CREATE TABLE orders (
  id        INTEGER PRIMARY KEY,
  member_id INTEGER NOT NULL REFERENCES members(id),
  item      TEXT    NOT NULL,
  amount    INTEGER NOT NULL CHECK (amount >= 0)
);
```

- `INTEGER`, `TEXT`는 **타입**(type)입니다. 정수 칸에 글자를 적으려 하면 직원이 신청서를 돌려보냅니다. 금액은 원 단위 정수로 둡니다. 소수는 [2장](ch02.html#float)에서 본 것처럼 오차가 생깁니다.
- `PRIMARY KEY`는 **기본 키**(primary key)입니다. 행마다 겹치지 않는 번호를 붙여 "바로 그 행"을 가리킵니다. [8장](ch08.html#map)의 ID입니다.
- `REFERENCES members(id)`는 **외래 키**(foreign key)입니다. 다른 표의 기본 키를 적어 두는 칸입니다. 회원 표에 없는 9번을 적으려 하면 거절됩니다.
- `NOT NULL`(비워 둘 수 없음), `CHECK`(조건을 지켜야 함), `UNIQUE`(같은 값이 둘일 수 없음) 같은 규칙을 **제약 조건**(constraint)이라고 합니다.

::: {.tip title="규칙은 코드가 아니라 장부에"}
"같은 이메일이 있는지 확인하고, 없으면 저장"을 코드로만 하면 두 요청이 동시에 확인을 통과해 둘 다 저장됩니다. `UNIQUE` 제약은 장부에 적는 순간 직원이 판정하므로 하나만 통과합니다.
:::

## 같은 사실은 한 곳에만: 정규화 {#normalize}

표를 왜 둘로 나눴을까요? 주문 표 하나에 이름과 전화번호까지 적으면 편할 것 같습니다. 그렇게 해 봅시다.

::: {.fig src="one-big-table.svg"}
민지의 전화번호가 주문마다 되풀이됩니다. 같은 사실이 여러 곳에 있으면 고칠 때, 지울 때, 넣을 때 모두 탈이 납니다.
:::

민지가 번호를 바꿨는데 한 줄만 고치면 장부에는 번호가 두 가지 남습니다. 준호의 하나뿐인 주문을 지우면 준호의 연락처도 사라집니다. 아직 주문하지 않은 서연은 적을 줄조차 없습니다.

원인은 하나입니다. "민지의 전화번호"라는 사실 하나가 세 군데에 적혀 있습니다. 그래서 사실마다 주인 표를 하나 정하고 표를 나눕니다. 이 일을 **정규화**(normalization)라고 합니다. 앞 절의 두 표가 그 결과입니다.

::: {.key}
**한 가지 사실은 한 곳에만 적고, 다른 표에서는 번호(키)로 가리킵니다.** 그러면 고칠 곳도 한 곳입니다.
:::

::: {.warn title="복사해 둬야 하는 것도 있습니다"}
주문할 때의 배송 주소와 결제 금액은 **그때의 사실**입니다. 회원이 이사하거나 가격이 올라도 지난 주문은 바뀌면 안 됩니다. 이런 값은 주문 표에 따로 적어 둡니다.
:::

## SQL: 원하는 것만 적는 신청서 {#sql}

은행 신청서에 "금고 셋째 칸 장부의 40쪽을 펴서"라고 적지는 않습니다. **무엇을 원하는지**만 적고, 어떻게 찾을지는 직원이 정합니다. SQL도 그렇습니다. DB에 보내는 SQL 한 문장을 **쿼리**(query)라고 합니다.

```sql
SELECT item, amount FROM orders WHERE amount >= 10000;

SELECT member_id, COUNT(*), SUM(amount)
FROM orders GROUP BY member_id;
```

첫 쿼리는 주문 표(`FROM`)에서 금액이 만 원 이상인 행만 걸러(`WHERE`) 상품과 금액 열을 꺼냅니다(`SELECT`). 키보드, 마우스, 충전기 세 줄이 나옵니다. 둘째 쿼리는 회원 번호가 같은 행끼리 묶어(`GROUP BY`) 묶음마다 건수와 합계를 냅니다. 1번 회원은 3건에 62000, 2번 회원은 1건에 18000입니다.

주문 목록에 번호 대신 이름을 보여 주려면 두 표를 붙여야 합니다. **조인**(JOIN)이 그 일을 합니다.

::: {.fig src="join-match.svg"}
JOIN은 주문 표의 member_id와 회원 표의 id가 같은 행끼리 짝지어 한 줄로 만듭니다.
:::

`ON` 뒤에는 어느 열끼리 같아야 짝인지를 적습니다.

::: {.note}
`ORDER BY`로 정렬 기준을 적지 않으면 결과의 순서는 약속되지 않습니다. 그리고 사용자가 입력한 값은 SQL 문자열에 이어 붙이지 말고 따로 넘깁니다. 이유는 [19장](ch19.html)에서 다룹니다.
:::

### NULL: 0도 빈 글자도 아닌 "모름"

서연의 전화번호 칸은 비어 있습니다. 이 빈칸이 **NULL**입니다. 0이나 빈 글자가 아니라 "값을 모른다"는 표시입니다. 모르는 값은 무엇과 비교해도 답이 "모름"이고, `WHERE`는 답이 참인 행만 남깁니다.

```sql
SELECT name FROM members WHERE phone = NULL;    -- 0줄
SELECT name FROM members WHERE phone IS NULL;   -- 박서연
```

`phone <> '010-1111-2222'`처럼 "다르다"로 걸러도 서연은 빠집니다. 같은지 다른지 모르기 때문입니다. 빈칸은 반드시 `IS NULL`로 찾습니다.

::: {.try}
맥에는 `sqlite3`가 들어 있습니다. 터미널에서 실행해 이 장의 두 표를 만들고 JOIN과 `IS NULL`을 쳐 보세요. SQLite는 `PRAGMA foreign_keys = ON;`을 먼저 실행해야 외래 키를 검사합니다.
:::

::: {.deep title="행을 줄이지 않고 합계 붙이기: 윈도 함수"}
`GROUP BY`는 주문 네 줄을 회원별 두 줄로 줄입니다. 네 줄을 그대로 두고 각 줄 옆에 "이 회원의 합계"를 붙이려면 **윈도 함수**(window function)를 씁니다. `SUM(amount) OVER (PARTITION BY member_id)`라고 적으면 민지의 주문 세 줄 옆에 모두 62000이 붙습니다. 순위나 누적 합계를 낼 때 씁니다.
:::

## 인덱스: 책 뒤의 찾아보기 {#index}

주문이 100만 건 쌓였습니다. `WHERE member_id = 7`로 회원 7의 주문을 찾으면, 준비가 없는 직원은 100만 줄을 처음부터 끝까지 넘겨 봅니다. 두꺼운 책에서 낱말 하나를 찾겠다고 첫 쪽부터 읽는 것과 같습니다.

책에는 이럴 때 쓰는 **찾아보기**가 있습니다. 낱말이 순서대로 늘어서 있고 옆에 쪽수가 적혀 있습니다. DB의 **인덱스**(index)가 이것입니다. 열 하나를 골라 값을 순서대로 정렬하고, 값마다 행의 위치를 적어 둔 **별도의 장부**입니다.

::: {.fig src="index-lookup.svg"}
member_id 인덱스. 7이 모인 곳을 찾으면 주문 표의 해당 행으로 곧장 갑니다.
:::

::: {.photo src="card-catalog.jpg"}
도서관의 카드 목록 서랍. 책은 서가에 그대로 두고, 찾는 데 쓸 카드만 따로 알파벳순으로 정리했습니다. 서랍마다 'BAY – BEE'처럼 담긴 범위가 적혀 있어서 서랍 하나만 열면 됩니다.
:::

인덱스는 `CREATE INDEX idx_member ON orders (member_id);` 한 줄로 만듭니다. 정렬되어 있으니 [8장](ch08.html#tree)의 트리처럼 갈림길을 따라 내려가며 찾습니다. 갈림길 하나가 수백 갈래로 나뉘는 트리(B-tree)여서, 100만 건이어도 서너 번 내려가면 닿습니다.

공짜는 아닙니다. 주문 한 건을 추가하면 인덱스에도 한 줄을 끼워 넣어야 합니다. 인덱스가 다섯 개면 장부 여섯 권을 고칩니다.

::: {.key}
인덱스는 **읽기를 빠르게 하는 대신 쓰기를 느리게** 합니다. 자주 쓰는 조건에만 만듭니다.
:::

### 복합 인덱스: 열의 순서가 중요합니다

열 두 개를 묶은 **복합 인덱스**(composite index)는 전화번호부와 같습니다. 성으로 먼저 정렬하고, 성이 같으면 이름순입니다. 김씨는 한곳에 모여 있지만 이름이 민지인 사람은 책 전체에 흩어져 있습니다.

::: {.fig src="composite-index.svg"}
회원 번호가 앞에 오는 인덱스에서는 한 회원의 주문이 한곳에 모입니다. 날짜만으로 찾으면 회원마다 구간을 따로 들여다봐야 합니다.
:::

::: {.deep title="인덱스를 더 깊이: B-tree와 LSM, 커버링·부분 인덱스"}
B-tree는 정렬된 쪽을 제자리에서 고칩니다. **LSM 트리**는 쓰기를 메모리에 모았다가 정렬된 파일로 한꺼번에 내려 적고, 파일들을 나중에 합칩니다. 쓰기가 쏟아지는 곳에 유리하지만 읽을 때 여러 파일을 봐야 할 수 있습니다.

필요한 열이 인덱스에 다 들어 있으면 표를 펴 보지 않고 인덱스만으로 답합니다. 이것이 **커버링 인덱스**(covering index)입니다. **부분 인덱스**(partial index)는 "아직 처리 안 된 주문"처럼 조건에 맞는 행만 담아 크기를 줄입니다.
:::

## 느린 조회 진단하기: 실행 계획과 N+1 {#slow}

화면이 느릴 때 물을 것은 두 가지입니다. **쿼리 하나가 너무 많이 읽는가, 쿼리를 너무 여러 번 보내는가.**

### 하나가 느릴 때: 직원에게 계획을 묻습니다

쿼리 앞에 `EXPLAIN`을 붙이면 직원이 "이렇게 찾겠습니다"라는 **실행 계획**(query plan)을 보여 줍니다. PostgreSQL의 예입니다.

```text
EXPLAIN SELECT * FROM orders WHERE member_id = 7;

Seq Scan on orders  (… rows=52 …)
  Filter: (member_id = 7)
```

`Seq Scan`은 표를 처음부터 끝까지 훑는다는 뜻입니다. `rows=52`는 52줄쯤 나올 것이라는 직원의 **예상**입니다. 인덱스를 만들고 다시 물으면 `Index Scan`처럼 인덱스를 쓰는 계획으로 바뀝니다. 그대로 `Seq Scan`이라면 조건과 인덱스가 맞지 않는다는 신호입니다.

::: {.warn}
`EXPLAIN ANALYZE`는 쿼리를 **실제로 실행**해서 걸린 시간까지 보여 줍니다. `DELETE`나 `UPDATE`에 붙이면 정말로 지워지고 바뀝니다.
:::

### 여러 번 보낼 때: N+1 문제

요즘은 SQL을 직접 쓰는 대신 **ORM**(Object-Relational Mapping, 객체 관계 매핑)을 많이 씁니다. 코드로 `order.member.name`이라고 적으면 ORM이 SQL로 바꿔 보내 줍니다. 편하지만 어느 줄이 쿼리를 보내는지 눈에 보이지 않습니다. Python 웹 프레임워크 Django의 예입니다.

```python
orders = Order.objects.all()[:100]   # 쿼리 1번
for order in orders:
    print(order.member.name)         # 돌 때마다 1번
```

목록을 한 번 읽고, 항목 N개마다 한 번씩 더 묻습니다. 이것이 **N+1 문제**입니다.

::: {.fig src="n-plus-one.svg"}
쿼리 하나하나는 빠릅니다. 느린 것은 DB까지 다녀오는 횟수입니다.
:::

해결책은 한꺼번에 묻는 것입니다. JOIN을 쓰거나, ORM에 "회원도 함께 가져와"라고 알려 줍니다. AI가 만든 코드에서 특히 흔하니, 화면 하나를 열 때 쿼리가 몇 번 나가는지 로그로 세어 보세요. 목록이 10개일 때보다 100개일 때 쿼리 수가 늘었다면 N+1입니다.

::: {.deep title="조인의 실행 방식과 페이지 나누기"}
실행 계획에는 두 표를 맞붙이는 방식도 나옵니다. 한쪽 행마다 다른 쪽을 찾아보는 **중첩 루프**, 한쪽으로 해시 맵을 만들어 맞춰 보는 **해시 조인**, 양쪽을 정렬해 나란히 훑는 **병합 조인**이 있습니다.

목록을 20개씩 끊어 볼 때 `OFFSET 10000`은 앞의 1만 줄을 읽고 버립니다. 뒤로 갈수록 느려지고, 그사이 새 글이 끼어들면 같은 글이 두 번 보입니다. **커서 방식**은 "마지막으로 본 글의 (작성 시각, id) 다음부터 20개"라고 묻습니다. 인덱스로 그 자리에 바로 가므로 깊은 페이지도 빠릅니다.
:::

## 트랜잭션: 전부 되거나, 전부 안 되거나 {#transaction}

민지가 준호에게 30,000원을 보냅니다. 장부에서는 두 줄을 고칩니다. 민지 계좌에서 빼고, 준호 계좌에 더합니다. 첫 줄만 고친 순간 서버가 꺼지면 어떻게 될까요?

::: {.fig src="transfer.svg"}
두 번의 수정 사이에서 멈추면 돈이 사라집니다. 트랜잭션으로 묶으면 중간 상태가 남지 않습니다.
:::

**트랜잭션**(transaction)은 여러 작업을 **한 건**으로 묶는 방법입니다.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 30000 WHERE id = 1;
UPDATE accounts SET balance = balance + 30000 WHERE id = 2;
COMMIT;
```

`BEGIN`으로 묶음을 열고 `COMMIT`으로 확정합니다. 이 확정이 **커밋**입니다. 커밋 전에 오류가 나거나 서버가 꺼지면 묶음 안의 변경은 모두 취소됩니다. 이것이 **롤백**(rollback)입니다.

트랜잭션이 지키는 네 가지 약속을 머리글자를 따서 **ACID**라고 부릅니다.

| 약속 | 뜻 |
|---|---|
| 원자성 (Atomicity) | 전부 반영되거나 전부 취소된다 |
| 일관성 (Consistency) | 제약 조건을 어긴 채로 끝나지 않는다 |
| 격리성 (Isolation) | 동시에 진행해도 서로 섞이지 않는다 |
| 지속성 (Durability) | 커밋된 것은 전원이 꺼져도 남는다 |

### "저장했습니다"의 진짜 뜻

지속성은 어떻게 지킬까요? 커밋할 때마다 장부 여러 권을 디스크에 고쳐 쓰면 너무 느립니다. 그래서 직원은 **일지를 먼저 씁니다.** "1번 계좌 −30000, 2번 계좌 +30000, 확정"이라고 일지 끝에 적고, 이 줄이 디스크에 닿은 것을 확인한 뒤에야 "저장했습니다"라고 답합니다. 장부 본문은 나중에 고칩니다. 도중에 꺼져도 일지를 다시 읽어 되살립니다. 이 방식을 **WAL**(Write-Ahead Log, 로그 먼저 쓰기)이라고 합니다.

::: {.warn title="트랜잭션은 DB 안의 일만 묶습니다"}
트랜잭션 안에서 이메일을 보내거나 외부 결제를 호출했다면, 롤백해도 그 메일과 결제는 취소되지 않습니다. 바깥으로 나가는 일은 커밋한 뒤에 합니다.
:::

## 동시에 고칠 때: 격리와 잠금 {#concurrency}

재고가 1개 남은 상품을 두 사람이 동시에 삽니다. 두 요청 모두 재고가 1임을 확인하고, 주문을 만들고, 재고를 0으로 저장합니다. 주문은 2건인데 물건은 하나입니다. [11장](ch11.html#race)의 칠판 사고가 장부에서 일어난 것으로, **잃어버린 갱신**(lost update)이라고 부릅니다.

::: {.myth title="트랜잭션으로 묶었으니 동시에 들어와도 안전하다"}
동시에 진행 중인 트랜잭션이 서로의 변경을 얼마나 볼 수 있는지는 **격리 수준**(isolation level)이라는 설정이 정합니다. PostgreSQL을 비롯한 많은 DB의 기본값은 "남이 커밋한 것만 보인다"는 수준이어서 위 사고를 막지 못합니다. 가장 엄격한 수준은 한 줄로 세워 처리한 것과 같은 결과를 보장하지만, 충돌하면 한쪽을 실패시킬 수 있어 다시 시도하는 코드가 필요합니다.
:::

그래서 보통 둘 중 하나로 직접 막습니다.

- **비관적 잠금**(pessimistic locking): 부딪힐 것이라 보고 **먼저 잠급니다.** `SELECT … FOR UPDATE`로 읽으면 내 트랜잭션이 끝날 때까지 다른 사람은 그 행을 고치지 못하고 기다립니다. [11장](ch11.html#lock)의 분필입니다.
- **낙관적 잠금**(optimistic locking): 드물게 부딪힐 것이라 보고 잠그지 않습니다. 대신 **쓰는 순간에 조건을 확인합니다.**

::: {.fig src="stock-race.svg"}
아래쪽 UPDATE는 확인과 변경이 한 문장입니다. 바뀐 행이 0개라면 실패로 처리합니다.
:::

`WHERE qty > 0`은 "아직 남아 있을 때만 줄여라"입니다. DB는 몇 행이 바뀌었는지 알려 주며, 0이면 누가 먼저 가져간 것입니다. 글을 고칠 때는 행에 버전 번호를 두고 `WHERE version = 3`처럼 "내가 읽은 뒤로 아무도 안 고쳤을 때만"이라고 조건을 답니다.

::: {.key}
트랜잭션은 **중간에 멈추는 사고**를, 잠금과 조건을 붙인 UPDATE는 **동시에 고치는 사고**를 막습니다. 서로 다른 문제입니다.
:::

### 커넥션 풀: 창구의 수

앱이 DB와 맺는 연결(커넥션)은 창구입니다. 새로 여는 데 시간이 걸리므로 몇 개를 미리 열어 두고 돌려 씁니다. 이 묶음이 **커넥션 풀**(connection pool)입니다. 창구가 10개인데 한 요청이 창구를 붙잡은 채 외부 API를 3초 기다리면, 다른 요청은 CPU가 한가해도 줄을 섭니다. 창구는 짧게 쓰고 바로 돌려줍니다. 서버 5대가 20개씩 열면 DB에는 100개가 몰린다는 것도 계산해 둡니다.

::: {.deep title="읽는 사람은 기다리지 않는다: MVCC, 그리고 교착"}
많은 DB는 행을 고칠 때 덮어쓰지 않고 **새 버전**을 하나 더 만듭니다. 읽는 쪽은 자기가 시작한 시점의 버전을 봅니다. 그래서 누가 고치는 중이어도 읽기는 기다리지 않습니다. 이 방식이 **MVCC**(다중 버전 동시성 제어)입니다. 대신 오래 열어 둔 트랜잭션이 있으면 옛 버전을 치우지 못해 공간이 불어납니다.

A가 1번 계좌를 잠그고 2번을 기다리는데 B는 2번을 잠그고 1번을 기다리면 [교착 상태](ch11.html#deadlock)입니다. DB는 이를 알아채고 한쪽을 실패시킵니다. 앱은 실패한 트랜잭션을 **처음부터** 다시 실행합니다. 번호가 작은 계좌부터 잠그기로 순서를 정해 두면 애초에 생기지 않습니다.
:::

## 운영하며 지키기: 복제, 백업, 캐시, 스키마 변경 {#operate}

서비스가 돌아가는 동안 장부를 지키려면 사본이 필요합니다. 사본은 세 종류이고 쓰임이 다릅니다.

::: {.key}
원본은 하나입니다. **사본은 언제나 원본보다 조금 늦습니다.**
:::

### 복제: 지금을 따라가는 사본

**복제**(replication)는 원본 DB의 변경을 다른 서버가 곧바로 따라 적게 하는 것입니다. 원본이 고장 나면 복제본이 대신하고, 읽기 요청을 나눠 받기도 합니다. 다만 변경이 건너가는 데 시간이 걸립니다. 이 틈이 **복제 지연**(replication lag)입니다.

::: {.fig src="replica-lag.svg"}
저장은 원본에 하고 읽기는 복제본에서 했습니다. 방금 쓴 글이 안 보이는 전형적인 원인입니다.
:::

방금 쓴 사람의 다음 읽기는 원본에서 하게 하면 풀립니다. 여러 서버에 걸친 일관성은 [18장](ch18.html)에서 이어집니다.

### 백업: 과거로 돌아가는 사본

**백업**(backup)은 과거 어느 시점의 사본입니다. 복제본은 백업을 대신하지 못합니다. 실수로 실행한 `DELETE`도 복제본이 그대로 따라 하기 때문입니다.

백업에는 숫자 두 개를 정합니다. **RPO**(Recovery Point Objective)는 "최근 얼마 동안의 데이터까지 잃어도 되는가", **RTO**(Recovery Time Objective)는 "되살리는 데 얼마나 걸려도 되는가"입니다. 매일 자정에만 백업한다면 밤 11시에 난 사고로 23시간치 주문을 잃습니다. 그리고 복원해 보지 않은 백업은 믿을 수 없습니다. 실제로 되살려 보고 걸린 시간을 재 둡니다.

### 캐시: 가까이 둔 사본

**캐시**([1장](ch01.html))는 자주 읽는 결과를 가까이에 복사해 둔 것입니다. 원본이 바뀌어도 사본은 저절로 바뀌지 않으므로 언제 버릴지를 정해야 합니다. 이것을 **무효화**(invalidation)라고 합니다. 상품 설명은 1분쯤 낡아도 괜찮지만, 재고처럼 틀리면 안 되는 판단은 원본을 보고 합니다.

### 영업 중에 양식 바꾸기: 마이그레이션

스키마를 바꾸는 작업을 **마이그레이션**(migration)이라고 합니다. 어려운 점은 가게 문을 닫지 않고 해야 한다는 것입니다. 새 코드를 내보내는 동안에는 옛 코드와 새 코드가 잠시 함께 돕니다. 열 하나를 지우는 순간, 아직 그 열을 읽는 옛 코드는 모두 오류를 냅니다. 그래서 네 걸음으로 나눕니다. **새 열을 추가하고, 기존 값을 옮겨 채우고, 코드가 새 열을 쓰게 바꾸고, 아무도 안 쓰는 것을 확인한 뒤 옛 열을 지웁니다.**

::: {.deep title="일지가 끝없이 길어지지 않게: 체크포인트와 시점 복구"}
일지(WAL)만 쌓으면 재시작할 때 읽을 양이 끝없이 늘어납니다. 그래서 DB는 주기적으로 밀린 변경을 장부 본문에 반영하고 "여기까지 반영함"이라고 표시합니다. 이것이 **체크포인트**(checkpoint)입니다. 복구는 그 표시 뒤부터만 하면 됩니다.

일지를 버리지 않고 모아 두면 **시점 복구**(PITR)를 할 수 있습니다. 어제 백업을 되살린 뒤 그 뒤의 일지를 "오늘 14시 29분"까지만 다시 실행하면, 14시 30분에 벌어진 삭제 사고 바로 앞 상태가 됩니다. RPO를 하루에서 몇 분으로 줄이는 방법입니다.
:::

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 기본 키 / 외래 키 | 내 표의 행을 가리키는 번호 / 다른 표의 행을 가리키는 번호 |
| NULL / 0, 빈 글자 | 값을 모름 / 값이 있고 그 값이 0이나 빈 글자 |
| 인덱스 / 캐시 | 원본을 빨리 찾는 찾아보기 / 결과를 복사해 둔 사본 |
| 트랜잭션 / 잠금 | 여러 변경을 한 건으로 묶기 / 남이 끼어들지 못하게 막기 |
| 복제 / 백업 | 지금을 따라가는 사본 / 과거로 돌아갈 수 있는 사본 |

## 실전 사례 {#case}

::: {.case title="'내 주문' 화면이 3초 걸리는데 인덱스를 늘려도 그대로다"}
'내 주문' 화면은 한 회원의 최근 주문 100건과 주문마다 배송 상태를 보여 줍니다. 느리다고 해서 주문 표에 인덱스를 두 개 더 만들었지만 달라지지 않았습니다.

1. **쿼리 수부터 셉니다.** 쿼리 로그를 켜고 화면을 한 번 열었더니 쿼리가 101번 나갔습니다. 주문마다 배송 상태를 따로 묻는 N+1입니다.
2. **한꺼번에 묻게 바꿉니다.** ORM에 배송 정보를 함께 가져오도록 지정해 쿼리를 2번으로 줄였습니다.
3. **남은 쿼리의 계획을 봅니다.** `EXPLAIN`을 붙였더니 "이 회원의 최근 주문"을 찾는 쿼리가 `Seq Scan`이었습니다. 새로 만든 인덱스는 이 조건과 맞지 않았습니다.
4. **조건에 맞는 인덱스로 바꿉니다.** `(member_id, ordered_at)` 복합 인덱스를 만들어 계획이 `Index Scan`으로 바뀐 것을 확인했습니다. 쓰기만 느리게 하던 처음 두 개는 지웠습니다.

횟수 문제와 한 번의 읽기 비용 문제는 다릅니다. 추측으로 인덱스를 늘리기 전에 쿼리 수와 실행 계획을 먼저 봅니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- **데이터베이스**는 창구 직원(DBMS)이 지키는 장부입니다. 동시에 고치기, 중간에 꺼지기, 느린 찾기를 대신 책임집니다.
- 데이터는 **표**에 담고, **기본 키**로 행을 가리키고, **외래 키**로 표를 잇습니다. 같은 사실은 한 곳에만 적습니다.
- **SQL**은 무엇을 원하는지만 적습니다. NULL은 "모름"이라서 `IS NULL`로 찾습니다.
- **인덱스**는 찾아보기입니다. 읽기는 빨라지고 쓰기는 느려집니다. 느릴 때는 **쿼리 수**와 **실행 계획**을 봅니다.
- **트랜잭션**은 전부 아니면 전무입니다. 동시에 고치는 문제는 조건을 붙인 UPDATE나 잠금으로 따로 막습니다.
- 복제본은 조금 늦고, 백업은 복원해 봐야 믿을 수 있습니다.
:::

## 확인 문제 {#quiz}

::: {.q}
회원 가입 코드가 "같은 이메일이 있는지 조회하고, 없으면 저장" 순서로 되어 있습니다. 그런데 같은 이메일의 계정이 두 개 생겼습니다. 왜 그렇고, 어떻게 막을까요?

::: {.a}
조회와 저장 사이에 틈이 있어서, 동시에 들어온 두 요청이 모두 "없음"을 확인하고 저장했습니다. 이메일 열에 `UNIQUE` 제약을 걸면 DB가 적는 순간에 판정하므로 하나만 성공합니다.
:::
:::

::: {.q}
전화번호를 입력하지 않은 회원을 찾으려고 `WHERE phone = NULL`이라고 썼더니 0명이 나왔습니다. 실제로는 여러 명이 있습니다. 무엇이 문제일까요?

::: {.a}
NULL은 "모름"이라서 `=`로 비교한 답도 "모름"입니다. `WHERE`는 답이 참인 행만 남기므로 아무도 남지 않습니다. `WHERE phone IS NULL`로 써야 합니다.
:::
:::

::: {.q}
주문 표에 `(member_id, ordered_at)` 인덱스가 있습니다. 그런데 "지난주에 들어온 모든 주문"을 조회하는 쿼리가 느립니다. 인덱스에 날짜 열이 들어 있는데 왜 그럴까요?

::: {.a}
이 인덱스는 회원 번호순으로 먼저 정렬되어 있어서 지난주 주문이 회원마다 따로 흩어져 있습니다. `ordered_at`이 앞에 오는 인덱스를 따로 만들고, `EXPLAIN`으로 실제로 쓰이는지 확인합니다.
:::
:::

::: {.q}
AI가 "주문 저장과 결제 호출을 한 트랜잭션에 넣었으니 결제가 두 번 될 일은 없습니다"라고 합니다. 믿어도 될까요?

::: {.a}
부족합니다. 트랜잭션은 DB 안의 변경만 묶습니다. 외부 결제는 롤백으로 취소되지 않고, 같은 요청이 두 번 들어오는 것도 막지 못합니다. 요청마다 고유 번호를 붙여 `UNIQUE` 제약으로 중복을 걸러 내고, 외부 호출은 트랜잭션 밖에서 합니다.
:::
:::

::: {.q}
"복제본이 두 대나 있으니 백업은 없어도 된다"는 말에서 빠진 것은 무엇일까요?

::: {.a}
복제본은 원본의 변경을 그대로 따라 하므로, 실수로 지운 데이터는 복제본에서도 지워집니다. 과거 시점으로 돌아가려면 백업이 필요합니다. 그 백업도 실제로 복원해 보고, 잃어도 되는 구간(RPO)과 복구 시간(RTO)을 확인합니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI는 "혼자 쓸 때는 잘 도는" DB 코드를 만들기 쉽습니다. 동시에 들어오는 경우와 중간에 실패하는 경우를 **직접 지목해서** 시키세요.

> 주문 저장 기능을 검토해 줘. DB는 PostgreSQL이고 격리 수준은 기본값이야. (1) 재고 1개를 두 명이 동시에 사는 경우와 (2) 같은 요청이 두 번 전송되는 경우를 구분해서 각각 어떻게 막는지 설명해 줘. 재고는 조건을 붙인 UPDATE로 줄이고, 주문 저장과 한 트랜잭션으로 묶어 줘. 두 연결로 동시에 실행하는 테스트와, 재고를 줄인 뒤 주문 저장 전에 일부러 실패시키는 테스트를 추가하고 결과를 보여 줘.

**받은 답에서 확인할 것**: 바뀐 행이 0개일 때를 실패로 처리하는가, 트랜잭션 안에 외부 호출이 없는가, 동시 실행 테스트를 실제로 돌린 결과가 있는가.
:::

## 용어 정리 {#terms}

::: {.terms}
DBMS (Database Management System)
:   데이터베이스를 지키고 요청을 처리하는 프로그램.

스키마 (schema)
:   표에 어떤 열이 있고 어떤 값이 들어갈 수 있는지 정한 양식.

기본 키 (primary key)
:   표에서 행 하나를 가리키는, 겹치지 않는 값.

외래 키 (foreign key)
:   다른 표의 기본 키를 적어 두어 두 표를 잇는 열.

정규화 (normalization)
:   같은 사실이 한 곳에만 적히도록 표를 나누는 일.

NULL
:   값을 모르거나 없다는 표시. 0이나 빈 글자와 다르다.

인덱스 (index)
:   열의 값을 정렬하고 행의 위치를 적어 둔 찾아보기.

실행 계획 (query plan)
:   DB가 쿼리를 어떤 방법으로 처리할지 정한 절차. `EXPLAIN`으로 본다.

N+1 문제 (N+1 query problem)
:   목록을 한 번 읽은 뒤 항목마다 쿼리를 한 번씩 더 보내는 패턴.

트랜잭션 (transaction)
:   여러 변경을 전부 반영하거나 전부 취소하는 한 묶음. 확정이 커밋, 취소가 롤백.

격리 수준 (isolation level)
:   동시에 진행 중인 트랜잭션이 서로의 변경을 얼마나 볼 수 있는지 정하는 설정.

커넥션 풀 (connection pool)
:   미리 열어 두고 돌려 쓰는 DB 연결 묶음.

WAL (Write-Ahead Log)
:   장부 본문보다 변경 일지를 먼저 디스크에 적는 방식.

복제 지연 (replication lag)
:   원본의 변경이 복제본에 도착하기까지의 시간 차.

마이그레이션 (migration)
:   기존 데이터를 지키면서 스키마를 바꾸는 작업.
:::
