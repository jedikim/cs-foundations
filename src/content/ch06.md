::: {.lead}
친구에게 받은 게임이 내 컴퓨터에서는 실행되지 않을 때가 있습니다. 게임이 잘못된 것이 아니라, 게임을 돌리는 데 필요한 것이 내 컴퓨터에 없어서입니다. 프로그램은 혼자서는 돌아가지 못하고 여러 도구와 설정에 기대어 돌아갑니다. 이것들을 통틀어 **개발 환경**이라고 합니다. 이 장에서는 그 환경을 갖추고 살펴보는 법을 배웁니다.
:::

::: {.goals}
- 프로그램이 돌아가려면 코드 말고 무엇이 더 필요한지 말할 수 있습니다.
- 필요한 도구를 설치하고 프로젝트마다 따로 관리하는 방법을 설명할 수 있습니다.
- "권한이 없다"는 오류가 왜 나는지 설명할 수 있습니다.
- 새 프로젝트를 처음 돌릴 때 무엇을 어떤 순서로 확인하는지 말할 수 있습니다.
- 멀리 있는 컴퓨터에 접속해서 일하는 방법을 설명할 수 있습니다.
:::

## 코드는 설계도일 뿐입니다 {#why}

친구의 게임이 내 컴퓨터에서만 켜지지 않는 까닭을, 나무로 의자를 만드는 일에 빗대어 봅시다.

의자 설계도를 들고 친구네 작업실에 갔습니다. 설계도는 그대로입니다. 그런데 친구의 톱은 내 것과 크기가 다릅니다. 선반에는 내가 쓰던 나사가 없습니다. 벽에 붙여 두었던 치수 메모도 없습니다. 같은 의자는 나오지 않습니다.

프로그램도 그렇습니다. 코드는 설계도입니다. 설계도대로 만들려면 공구도, 부품도, 메모도 있어야 합니다. 코드 바깥에 갖춰져 있어야 하는 이것들을 **개발 환경**(development environment), 줄여서 **환경**이라고 부릅니다. 이 장에서는 환경을 **작업실**이라고 생각하겠습니다.

민아는 자기 노트북에서 `main.py`라는 프로그램을 만들었습니다. **파이썬**(Python)이라는 프로그래밍 언어로 쓴 코드입니다. 노트북에서는 잘 돌아갑니다.

민아는 이 프로그램을 서버로 옮기려고 합니다. 서버는 늘 켜 두고 여러 사람의 요청을 받는 컴퓨터입니다. 프로그램을 서버에 올려놓는 일을 '배포'라고 합니다.

::: {.fig src="workshop-compare.svg"}
코드는 같은데 작업실이 다릅니다.
:::

그림을 위에서부터 한 줄씩 읽어 봅시다.

- **설계도.** 코드입니다. 두 컴퓨터의 `main.py`는 똑같습니다.
- **공구.** 코드를 실행해 주는 프로그램, 곧 런타임입니다([4장](ch04.html#runtime)). 노트북의 파이썬은 3.12 버전이고, 서버의 파이썬은 오래된 3.9 버전입니다.
- **부품.** 남이 만들어 둔 코드 묶음이고, 패키지라고 부릅니다. 민아의 코드가 쓰는 `requests`라는 부품이 서버에는 없습니다.
- **벽의 메모.** 코드 밖에 따로 적어 두는 값이고, 환경 변수라고 부릅니다. `API_KEY`는 비밀번호 같은 값의 이름이고, 별표(`****`)는 그 값을 가려 둔 것입니다. 서버에는 이 메모가 없습니다.
- **건물.** 운영체제와 CPU입니다. macOS와 Linux는 운영체제의 이름이고, ARM64와 x86-64는 CPU의 종류입니다.

서버에서 실행하면 `ModuleNotFoundError`가 납니다. "부품을 찾지 못했다"는 오류입니다. 부품을 넣어도 공구가 오래되었거나 메모가 없어서 또 멈출 수 있습니다.

::: {.key}
"내 컴퓨터에서는 되는데요"는 작업실이 다르다는 신호입니다. 코드를 고치기 전에 **두 작업실에서 무엇이 다른지**부터 견주어 봅니다.
:::

### 내 작업실의 공구부터 확인하기

AI가 써 준 코드도 사정이 같습니다. 대화창의 AI는 내 작업실을 보지 못한 채 코드를 씁니다. AI가 떠올린 작업실과 내 작업실이 다르면 멀쩡한 코드도 멈춥니다. 그래서 내 작업실에 무엇이 있는지부터 알아 둡니다.

아래는 터미널([5장](ch05.html))에 치는 명령입니다. 줄 앞의 `$`는 명령을 치는 자리라는 표시라서 따라 치지 않습니다.

```bash
$ python3 --version
Python 3.12.2
$ node -v
v22.22.0
```

- 1~2행. 파이썬에게 버전을 묻습니다. 3.12.2라고 답했습니다.
- 3~4행. `node`에게 묻습니다. `node`는 자바스크립트(JavaScript)의 런타임이고, 자바스크립트는 웹사이트를 만들 때 많이 쓰는 프로그래밍 언어입니다.

::: {.try}
터미널에 위의 두 명령을 쳐 보세요. `command not found`가 나오면 그 공구가 없거나, 있어도 찾지 못하는 것입니다. 나온 버전은 적어 두었다가, AI에게 일을 맡길 때 운영체제 이름과 함께 먼저 알려 줍니다.
:::

## 환경 변수: 작업실 벽에 붙인 메모 {#env}

게임에는 연습 모드와 실전 모드가 있곤 합니다. 프로그램도 만드는 동안에는 연습 모드로, 사람들에게 내놓을 때는 실전 모드로 돌립니다.

모드를 바꿀 때마다 코드를 고치면 실수하기 쉽습니다. 비밀번호를 코드에 적어 두면 코드를 본 사람이 모두 알게 됩니다. 그래서 이런 값은 코드 밖에 둡니다. 작업실 벽의 메모판에 쪽지로 붙여 두는 셈입니다.

이 쪽지를 **환경 변수**(environment variable)라고 합니다. `이름=값` 꼴의 글자 한 줄입니다. `MODE=dev`는 `MODE`라는 쪽지에 `dev`라고 적혀 있다는 뜻입니다. `dev`는 '만드는 중'을 뜻하는 줄임말입니다.

터미널에서는 이렇게 붙이고 읽습니다.

```bash
$ export MODE=dev
$ echo $MODE
dev
$ python3 server.py
```

- 1행. `export`는 쪽지를 붙이는 명령입니다. `MODE` 쪽지에 `dev`라고 적습니다.
- 2~3행. 쪽지를 읽어 봅니다. 이름에 바로 붙인 `$`는 '그 쪽지에 적힌 값'이라는 뜻입니다. `echo`가 그 값 `dev`를 화면에 찍었습니다.
- 4행. `server.py`라는 파이썬 프로그램을 켭니다. 이 프로그램은 `MODE` 쪽지를 읽을 수 있습니다.

그런데 프로그램은 메모판을 계속 쳐다보지 않습니다. **켜지는 순간 메모판을 통째로 자기 수첩에 베껴 갑니다.** 그 뒤로는 수첩만 봅니다.

::: {.fig src="env-inherit.svg"}
프로그램은 켜지는 순간의 값을 베껴 갑니다.
:::

그림의 '셸'은 터미널에서 내 명령을 받아 주는 프로그램이고, 메모판을 들고 있습니다. 서버 A는 방금 켠 `server.py`입니다. 요청을 받는 프로그램도 서버라고 부릅니다.

1. 서버 A가 켜지면서 `MODE=dev`를 베껴 갑니다.
2. 셸의 쪽지를 `prod`로 고칩니다. `prod`는 '실제로 쓰는 중'을 뜻합니다. 서버 A의 수첩은 그대로 `dev`입니다.
3. 같은 프로그램을 하나 더 켭니다. 이 서버 B는 `prod`를 베껴 갑니다.

그래서 환경 변수를 고쳤으면 그 값을 쓸 **프로그램을 껐다가 다시 켜야** 합니다. 터미널 창이 둘이면 메모판도 둘이라서, 한 창에서 붙인 쪽지는 다른 창에 보이지 않습니다.

### 쪽지를 모아 두는 파일: .env

쪽지가 여러 장이면 켤 때마다 `export`를 치기가 번거롭습니다. 그래서 프로그램의 파일을 모아 둔 폴더(프로젝트 폴더)에 `.env`라는 파일을 만들고, `이름=값`을 한 줄에 하나씩 적어 둡니다. `API_KEY` 같은 비밀 값과, 모드처럼 컴퓨터마다 달라지는 값을 적습니다.

`.env`는 셸이 알아서 읽는 파일이 아닙니다. 프로젝트에서 쓰는 도구나 코드가 읽어서 쪽지로 붙여 줍니다. 읽어 주는 것이 없으면 프로그램은 받지 못합니다.

쪽지를 못 받은 파이썬 프로그램은 흔히 `KeyError: 'API_KEY'`라고 멈춥니다. "`API_KEY`라는 이름의 값이 없다"는 뜻입니다. 자바스크립트는 값 자리에 `undefined`(정해지지 않음)를 넣은 채 지나가다가 엉뚱한 곳에서 멈춥니다.

::: {.warn title="비밀 값을 두면 안 되는 곳"}
`.env`는 집 열쇠를 넣어 둔 봉투입니다. 그 안의 비밀 값은 아래 네 곳에 두지 않습니다.

- **코드 안.** AI가 시험 삼아 코드에 값을 직접 적어 넣지 않았는지 봅니다.
- **인터넷에 올리는 코드 묶음.** `.env`만 빼고 올리는 방법은 [7장](ch07.html)에서 배웁니다.
- **화면을 그리는 코드.** 보는 사람의 브라우저로 보내져서 누구나 열어 볼 수 있습니다([31장](ch31.html#secret)).
- **메신저와 AI 대화창.** 오류를 물을 때도 값은 지우고 이름만 보여 줍니다.

이미 새어 나갔다면 그 비밀 값부터 새것으로 바꿉니다.
:::

프로젝트를 남에게 건넬 때는 `.env` 대신 `.env.example`을 줍니다. `API_KEY=`처럼 이름만 적고 값은 비운 파일입니다.

`.env`를 올리지 않으니 배포한 서버에는 이 쪽지들이 없습니다. 이 장 첫 그림의 '정해 둔 값 없음'이 그 모습입니다. 서버를 빌려주는 서비스의 설정 화면에 이름과 값을 따로 적어 넣습니다([20장](ch20.html)).

### 설정이 여러 곳에 있으면 누가 이길까

같은 값이 여러 곳에 적혀 있기도 합니다. 게임을 시작할 때의 목숨 수라면 보통 네 군데입니다.

| 힘 | 값이 적힌 곳 | 예 |
|---|---|---|
| 가장 약함 | 코드에 적어 둔 기본값 | `lives = 3` |
| 약함 | 설정 파일(값을 모아 적어 둔 파일) | `lives: 5` |
| 셈 | 환경 변수 | `LIVES=7` |
| 가장 셈 | 켜는 명령 뒤에 붙인 옵션 | `--lives 9` |

값이 서로 다르면 대개 **켜는 순간에 가까운 쪽이 이깁니다.** 네 곳에 모두 적혀 있으면 목숨은 9개이고, 옵션을 빼고 켜면 7개입니다.

"설정 파일을 고쳤는데 그대로예요"라면 더 센 곳에 다른 값이 적혀 있거나, 프로그램을 다시 켜지 않은 것입니다.

## PATH: 공구를 찾아보는 선반 순서 {#path}

작업실에서 "드라이버 좀 줘" 하면 조수는 건물 전체를 뒤지지 않습니다. 정해 둔 선반 몇 개를 정해진 순서로 봅니다.

셸도 그렇게 합니다. 터미널에 `python3`라고 치면 셸은 그 이름의 프로그램 파일을 찾아 실행합니다. 수만 개나 되는 폴더를 다 뒤질 수는 없으니, 찾아볼 선반 목록을 정해 둡니다. 이 목록이 **PATH**라는 환경 변수입니다.

::: {.fig src="path-shelves.svg"}
셸은 앞 선반부터 보고, 처음 나온 곳에서 멈춥니다.
:::

그림 맨 위에 PATH의 값이 적혀 있습니다. 쌍점(`:`)에서 끊으면 폴더 세 개가 나옵니다. 이 셋이 선반입니다. 셸은 **앞 선반부터** 차례로 보고, 찾는 이름이 **처음 나온 선반에서 멈춥니다.**

`python3`는 첫째 선반에도, 셋째 선반에도 있습니다. 셸은 첫째 선반의 3.12 버전을 실행하고, 셋째 선반의 3.9 버전까지는 가 보지도 않습니다. `git`, `docker`, `ssh`는 선반에 놓인 다른 프로그램입니다.

맨 아래의 `~/tools/bin` 폴더는 목록에 없습니다. 그래서 그 안의 `mytool`은 컴퓨터에 있는데도 찾지 못합니다. 이 규칙으로 두 가지 일이 풀립니다.

- **`command not found`가 나올 때.** "그런 명령을 찾지 못했다"는 뜻입니다. 설치하지 않았거나, 설치한 폴더가 PATH에 없는 것입니다.
- **엉뚱한 버전이 켜질 때.** 같은 이름이 두 선반에 있으면 앞 선반의 것이 이깁니다.

어느 선반의 것이 뽑혔는지는 `which` 명령이 알려 줍니다. `which python3`라고 치면 `/opt/homebrew/bin/python3`라고 답합니다. 첫째 선반의 것입니다.

::: {.try}
터미널에 `echo $PATH`를 쳐 보세요. 쌍점에서 끊으면 선반이 몇 개인가요? 이어서 `which python3`를 쳐서 몇째 선반의 것이 잡혔는지 찾아봅니다.
:::

### 선반을 하나 더하기

`mytool`을 찾게 하려면 `~/tools/bin` 폴더를 선반 목록에 더하면 됩니다. 터미널에 치는 명령입니다.

```bash
$ export PATH="$HOME/tools/bin:$PATH"
$ which mytool
/Users/mina/tools/bin/mytool
```

- 1행. PATH 쪽지를 새로 적습니다. `$HOME`은 내 홈 폴더(`~`)이고, `$PATH`는 지금까지의 목록입니다. 새 선반을 맨 앞에 놓고, 쌍점 뒤에 옛 목록을 이어 붙였습니다.
- 2~3행. 이제 셸이 `mytool`을 찾습니다.

프로그램을 방금 설치했는데 `command not found`가 나오면 먼저 터미널 창을 새로 열어 봅니다. 설치하면서 바뀐 PATH는 새로 연 창부터 통할 때가 많습니다. 그래도 안 되면 설치 안내문에서 "이 폴더를 PATH에 더하세요"라는 말을 찾아봅니다.

::: {.key}
"설치되어 있다"와 "지금 그것이 실행된다"는 다른 말입니다.
:::

::: {.deep title="터미널을 새로 열어도 남게 하려면 어떻게 할까요?"}
`export`로 붙인 쪽지는 그 터미널 창을 닫으면 사라집니다. 계속 쓸 쪽지는 셸이 켜질 때마다 읽는 **셸 시작 파일**에 적어 둡니다. 맥의 zsh는 홈 폴더의 `.zshrc`, 리눅스의 bash는 `.bashrc`입니다.

이 파일 맨 아래에 위의 `export` 줄을 적어 두면 셸이 켜질 때마다 그 줄을 대신 쳐 줍니다. 고친 뒤에는 터미널 창을 새로 엽니다.
:::

## 패키지와 패키지 매니저: 남이 만든 부품 들여오기 {#package}

자전거를 만드는 사람이 바퀴와 체인까지 직접 만들지는 않습니다. 잘 만든 부품을 사다 씁니다.

프로그램도 그렇습니다. 인터넷에서 자료를 받아 오는 일처럼 누구에게나 필요한 기능은 누군가 이미 만들어 공개해 두었습니다. 이런 코드 묶음에 이름과 버전 번호를 붙여 설치하기 좋게 포장한 것이 **패키지**(package)입니다. 앞에서 본 `requests`가 자료를 받아 오는 패키지입니다.

부품을 주문하고 받아서 제자리에 넣는 프로그램이 **패키지 매니저**(package manager)입니다. 파이썬에서는 `pip`입니다. 터미널에 `pip install requests`라고 치면 인터넷의 부품 가게에서 `requests`를 받아 설치합니다.

패키지가 모여 있는 이 부품 가게를 **레지스트리**(registry)라고 합니다. 언어마다 가게와 도구의 이름이 다릅니다.

| 구분 | 파이썬 | 자바스크립트 |
|---|---|---|
| 패키지 매니저 | `pip` | `npm` |
| 레지스트리 | PyPI | npm 레지스트리 |
| 필요한 부품을 적는 파일 | `requirements.txt` | `package.json` |
| 적힌 부품을 모두 받는 명령 | `pip install -r requirements.txt` | `npm install` |

마지막 줄은 파일에 적힌 부품을 한꺼번에 받는 명령입니다. 남이 만든 프로젝트를 받으면 이 명령을 치게 됩니다.

::: {.fig src="dep-tree.svg"}
하나를 적었는데 네 개가 딸려 왔습니다.
:::

그림 왼쪽 위의 `requirements.txt`에 민아는 `requests>=2.31` 한 줄만 적었습니다. 그런데 오른쪽에는 다섯 개가 설치됐습니다.

`requests`가 `urllib3`, `certifi`, `idna`, `charset-normalizer`라는 패키지 네 개를 가져다 쓰기 때문입니다. 내가 적지 않았는데 딸려 온 패키지를 **간접 의존성**(transitive dependency)이라고 합니다.

`>=2.31`은 "2.31 버전이거나 그보다 새것이면 된다"는 뜻입니다. 딱 하나가 아니라 **범위**입니다. 민아에게는 오늘 2.32.4가 왔습니다. 석 달 뒤에 설치하는 친구에게는 더 새 버전이 올 수 있습니다. 딸려 오는 네 개도 마찬가지입니다. 코드는 그대로인데 "새로 설치하니까 안 돼요"라는 일이 여기서 생깁니다.

그래서 **실제로 설치된 다섯 개의 정확한 버전**을 파일에 적어 둡니다. 그림 왼쪽 아래의 **잠금 파일**(lock file)입니다. 잠금 파일대로 설치하면 누구의 작업실에나 똑같은 부품이 들어옵니다([20장](ch20.html)). `npm`은 `package-lock.json`이라는 이름으로 이 파일을 알아서 만듭니다. 낯선 파일이라고 지우지 말고 코드와 함께 둡니다.

::: {.note}
`pip`과 `npm`은 **한 언어의 부품**을 들여옵니다. 파이썬 자체나 `git` 같은 **공구**는 맥의 `brew`, 우분투 리눅스의 `apt` 같은 다른 패키지 매니저로 설치합니다.
:::

## 가상 환경: 프로젝트마다 따로 두는 부품함 {#venv}

모둠이 물감 상자 하나를 같이 쓴다고 해 봅시다. 누가 파란 물감을 다른 파랑으로 바꿔 넣으면, 먼저 그리던 친구의 그림은 색이 달라집니다.

민아가 만드는 프로그램(프로젝트) 둘이 그런 처지입니다. 작년에 만든 `old-ai`와 새로 시작한 `mygame`은 둘 다 `numpy`라는 패키지를 씁니다. 숫자 계산을 도와주는 부품입니다. 그런데 `old-ai`는 1.26 버전에 맞춰 만들었고, `mygame`에는 2.0 버전이 필요합니다.

`pip install`은 따로 손쓰지 않으면 컴퓨터 전체가 함께 쓰는 공용 부품함에 넣습니다. 이 부품함에는 같은 이름의 부품을 한 버전만 둘 수 있습니다. 2.0을 넣는 순간 1.26은 덮어써집니다.

::: {.fig src="venv-boxes.svg"}
부품함을 따로 두면 서로 건드리지 않습니다.
:::

그림 왼쪽이 그 모습입니다. 나중에 설치한 `mygame`은 돌아가지만 `old-ai`는 오류를 냅니다.

그림 오른쪽이 해결책입니다. 프로젝트 폴더마다 부품함을 따로 둡니다. 파이썬에서는 이 전용 부품함을 **가상 환경**(virtual environment)이라고 부릅니다. 보통 프로젝트 폴더 안에 `.venv`라는 폴더로 만듭니다. 터미널에서 이렇게 만들고 씁니다.

```bash
$ cd ~/mygame
$ python3 -m venv .venv
$ source .venv/bin/activate
(.venv) $ python -m pip install numpy
```

- 1행. `mygame` 폴더로 들어갑니다.
- 2행. `.venv` 폴더를 만듭니다. 이 프로젝트만 쓰는 파이썬과 빈 부품함이 들어 있습니다.
- 3행. 가상 환경을 켭니다. 줄 앞에 `(.venv)`가 붙으면 켜진 것입니다. 윈도우에서는 이 줄이 `.venv\Scripts\activate`입니다.
- 4행. `numpy`를 설치합니다. `python -m pip`은 "지금 이 `python`의 부품함에 넣어라"라는 뜻입니다.

가상 환경을 켜는 일은 **PATH 맨 앞에 `.venv/bin` 선반을 끼워 넣는 것**이 거의 전부입니다. 그래서 `python`을 치면 그 선반의 것이 먼저 잡힙니다. PATH는 터미널 창마다 따로이므로 새 창에서는 다시 켜야 합니다.

::: {.myth title="가상 환경은 컴퓨터 안의 또 다른 컴퓨터다"}
가상 환경이 나누는 것은 **어느 파이썬과 어느 부품함을 쓸지**뿐입니다. 그 안에서 실행한 프로그램도 내 사진 폴더를 지울 수 있습니다. 컴퓨터 안에 컴퓨터를 한 대 더 띄우는 가상 머신([21장](ch21.html))과는 다릅니다.
:::

### 컴퓨터 전체에 넣을까, 프로젝트 안에 넣을까

공용 부품함에 넣는 것을 **전역 설치**(global install)라고 합니다. 프로젝트 폴더 안에 넣으면 그 프로젝트만 씁니다.

두 언어는 기본이 반대입니다. `npm install`은 프로젝트 폴더 안의 `node_modules` 폴더에 넣고, `-g` 옵션을 붙였을 때만 전역에 넣습니다. `pip install`은 가상 환경을 켜지 않으면 전역에 넣습니다.

프로젝트가 쓰는 부품은 프로젝트 안에 넣습니다. AI가 준 명령에 `npm install -g`나 `sudo pip install`이 보이면 "프로젝트 안에 설치하는 방법은 없어?"라고 묻습니다.

요즘 맥과 리눅스에서는 가상 환경 밖에서 `pip install`을 치면 `externally-managed-environment`라는 오류로 막힐 때가 있습니다. "운영체제가 관리하는 파이썬이니 여기에는 넣지 말라"는 뜻입니다. 억지로 넣는 옵션을 찾지 말고 가상 환경을 켭니다.

`.venv`와 `node_modules`는 다시 만들 수 있는 폴더입니다([5장](ch05.html)). 꼬였으면 지우고 부품을 다시 받습니다. 인터넷에 올리는 코드 묶음에는 넣지 않습니다([7장](ch07.html)).

## 편집기와 언어 서버: 빨간 밑줄은 누가 긋나 {#editor}

문서 프로그램에서 맞춤법이 틀리면 글자 아래에 빨간 밑줄이 생깁니다. 코드를 쓰는 프로그램도 그렇게 합니다.

코드를 쓰는 프로그램을 **편집기**(editor)라고 합니다. 작업실로 치면 설계도를 그리는 책상입니다. VS Code가 널리 쓰입니다. 편집기는 틀린 곳에 빨간 밑줄을 긋고, 몇 글자만 쳐도 나머지를 채워 주는 자동 완성도 띄웁니다.

편집기가 모든 프로그래밍 언어의 규칙을 아는 것은 아닙니다. 책상 옆에 언어마다 검사 도우미가 따로 있습니다. 이 도우미를 **언어 서버**(language server)라고 합니다. 이름에 서버가 붙었지만 내 컴퓨터 안에서 도는 프로그램입니다.

편집기가 "1행이 바뀌었어"라고 알립니다. 언어 서버는 코드와 설치된 패키지를 읽어 보고 "1행에 문제가 있어"라고 답합니다. 이 답이 진단입니다. 둘이 주고받는 말의 규칙은 **LSP**(Language Server Protocol)라고 부릅니다.

::: {.fig src="lsp-talk.svg"}
빨간 밑줄은 언어 서버가 보낸 진단입니다.
:::

그림 속 `main.py`는 세 줄짜리 파이썬 코드입니다. 1행은 `requests` 부품을 가져옵니다. 2행은 그 부품으로 인터넷 주소(`url`)에서 자료를 받아 옵니다. 3행은 잘 받았는지 알려 주는 숫자를 화면에 찍습니다.

그림 아래쪽을 보면, 터미널에서 실행했을 때 "잘 받았다"는 뜻의 숫자 200이 찍힙니다. 그런데도 편집기는 1행에 빨간 밑줄을 긋습니다.

둘이 서로 다른 부품함을 보고 있어서입니다. 터미널은 `.venv`의 파이썬으로 실행했고, 거기에는 `requests`가 있습니다. 언어 서버는 `.venv` 밖의 `/usr/bin/python3`를 들여다보고 있고, 거기에는 `requests`가 없습니다. 고치는 방법은 두 가지입니다.

1. 파일 하나만 열지 말고 **프로젝트 폴더를 통째로** 엽니다. 언어 서버는 열린 폴더 안에서 `.venv`를 찾습니다.
2. 편집기의 설정에서 **쓸 파이썬을 `.venv`의 것으로 고릅니다.**

빨간 밑줄만 보고 AI에게 "고쳐 줘"라고 하면, AI가 멀쩡한 코드를 뜯어고치기도 합니다. 먼저 실행해 봅니다.

::: {.key}
빨간 밑줄은 **언어 서버가 들여다본 부품함을 기준으로 한 의견**입니다. 마지막 답은 실제로 실행해 봐야 나옵니다.
:::

### AI 코딩 도구는 내 폴더에서 무엇을 할 수 있나

편집기에 붙어 있거나 터미널에서 도는 AI 코딩 도구는 대화창의 챗봇과 다릅니다. 챗봇은 말만 해 주지만, 이런 도구는 작업실에 들어와 직접 손을 댑니다. 내가 열어 준 폴더에서 세 가지를 합니다.

- 폴더 안의 파일을 **읽습니다.** `.env`도 거기 있으면 읽을 수 있습니다.
- 파일을 **고치고, 만들고, 지웁니다.**
- 터미널 **명령을 실행합니다.** 명령은 폴더 밖의 파일에도 닿습니다.

그래서 세 가지를 지킵니다.

1. **프로젝트 폴더만 열어 줍니다.** 홈 폴더나 바탕 화면을 통째로 열지 않습니다.
2. **명령은 묻고 나서 실행하게 둡니다.** 지우기, `sudo`, 전역 설치가 보이면 멈춥니다.
3. **맡기기 전에 저장 지점을 만듭니다.** 그래야 되돌릴 수 있습니다([7장](ch07.html)).

권한을 얼마나 줄지는 [30장](ch30.html#permission)에서 다룹니다.

## 사용자와 권한: 누가 이 파일을 열 수 있나 {#permission}

학교 사물함에는 주인이 있습니다. 내 사물함은 내가 열고, 남의 사물함은 열지 못합니다.

컴퓨터도 여럿이 함께 씁니다. 아무나 남의 파일을 고치면 곤란합니다. 그래서 운영체제는 무슨 일이든 '누가 하려는가'를 먼저 따집니다. 그 '누구'가 로그인한 **사용자**(user)입니다.

내가 켠 프로그램은 내 이름으로 일합니다. AI 코딩 도구도 내가 켠 프로그램입니다. 내가 지울 수 있는 파일은 그 도구도 지울 수 있습니다.

파일과 폴더에는 '누가 무엇을 해도 되는지'가 적혀 있습니다. 이것을 **권한**(permission)이라고 합니다. 할 수 있는 일은 읽기(내용 보기), 쓰기(내용 고치기), 실행(프로그램으로 돌리기) 세 가지입니다.

권한은 터미널에서 `ls -l` 명령으로 봅니다. `deploy.sh`는 민아가 명령 몇 줄을 적어 둔 파일입니다.

```bash
$ ls -l deploy.sh
-rwxr-xr--  1 mina  staff  214 Nov 12 10:30 deploy.sh
```

둘째 줄이 답입니다. 맨 앞 열 글자 `-rwxr-xr--`가 권한입니다. 바로 뒤의 `1`은 지금은 넘어가도 됩니다. 이어서 주인 `mina`, 그룹 `staff`, 파일 크기, 고친 날짜와 시각, 파일 이름이 나옵니다. 열 글자는 끊어 읽으면 쉽습니다.

::: {.fig src="perm-bits.svg"}
권한 열 글자를 끊어 읽는 법.
:::

- 첫 글자는 종류입니다. `-`이면 파일, `d`이면 폴더입니다.
- 나머지는 세 글자씩 끊습니다. `r`은 읽기, `w`는 쓰기, `x`는 실행이고, `-`는 그 일을 못 한다는 표시입니다.
- `rwx`는 **소유자**, 곧 파일 주인인 `mina`의 몫입니다. 셋 다 됩니다.
- `r-x`는 **그룹**의 몫입니다. 그룹은 사용자 여럿을 묶은 모둠이고, 여기서는 `staff`입니다. 읽기와 실행만 됩니다.
- `r--`는 그 밖의 모든 사용자의 몫입니다. 읽기만 됩니다.

허락되지 않은 일을 하려고 하면 운영체제가 `Permission denied`라고 막습니다. "권한이 없어서 거절한다"는 뜻입니다. 방금 만든 파일을 실행하려 할 때 자주 봅니다. 새 파일에는 보통 실행 권한이 없기 때문입니다.

그럴 때는 `chmod +x 파일이름`이라고 칩니다. `chmod`는 권한을 바꾸는 명령이고, `+x`는 실행 권한을 더하라는 뜻입니다.

실행할 때는 이름만 치지 않고 `./deploy.sh`라고 칩니다. 지금 서 있는 폴더는 PATH의 선반 목록에 없기 때문입니다. `./`는 '지금 서 있는 폴더에 있는'이라는 뜻입니다([5장](ch05.html)).

### sudo: 관리인의 만능열쇠

학교에는 모든 교실 문을 여는 열쇠 꾸러미가 있습니다. 컴퓨터에도 권한 검사를 거의 받지 않는 관리자가 있습니다. 이름은 **root**입니다. [5장](ch05.html)에서 본 폴더 나무의 꼭대기(`/`)도 루트라고 불렀지만, 여기서는 사용자의 이름입니다.

명령 앞에 `sudo`를 붙이면 그 명령 하나를 root의 이름으로 실행합니다. 만능열쇠를 잠깐 빌리는 셈입니다. 빌려주기 전에 내 로그인 비밀번호를 묻습니다. 이때 치는 글자는 화면에 보이지 않아도 입력되고 있습니다.

`Permission denied`가 나온 명령도 `sudo`를 붙이면 대개 통과합니다. 바로 그래서 위험합니다.

- **안전장치가 사라집니다.** 오타 하나로 컴퓨터에 꼭 필요한 파일까지 지울 수 있습니다.
- **진짜 원인이 가려집니다.** 공용 부품함에 패키지를 넣으려다 막혔다면, 답은 `sudo`가 아니라 가상 환경입니다.

::: {.warn title="chmod 777은 사물함 문을 떼어 버립니다"}
`Permission denied`를 검색하거나 AI에게 물으면 `chmod 777 파일이름`을 치라는 답도 나옵니다. `777`은 소유자, 그룹, 그 밖의 모두에게 읽기·쓰기·실행을 다 주라는 뜻입니다.

오류는 사라지지만, 이 컴퓨터를 쓰는 누구나 그 파일을 고칠 수 있게 됩니다. 꼭 필요한 권한 하나만 더합니다.
:::

::: {.key}
`Permission denied`를 만나면 `sudo`를 붙이기 전에 묻습니다. **누가, 어느 파일에, 무엇을 하려다 막혔는가.**
:::

## 프로세스 보기와 끝내기: "포트가 이미 사용 중" {#process}

방을 나오면서 불을 끄지 않은 적이 있을 겁니다. 컴퓨터에도 켜 둔 채 잊어버린 프로그램이 뒤에서 계속 돌곤 합니다.

실행 중인 프로그램 하나하나를 프로세스라고 합니다([3장](ch03.html#process)). 프로세스마다 PID라는 번호표가 붙습니다. 터미널에 `ps aux`라고 치면 지금 도는 프로세스가 한 줄에 하나씩, 주인의 이름과 PID와 함께 찍힙니다.

프로그램을 끝내는 방법은 세 가지이고, 약한 것부터 씁니다.

- **`Ctrl+C`**: Ctrl 키를 누른 채 C를 누릅니다. 지금 이 터미널에서 도는 프로그램에게 "그만"이라고 알립니다.
- **`kill 4312`**: 번호표가 4312인 프로세스에게 "정리하고 끝내 줘"라고 부탁합니다.
- **`kill -9 4312`**: 억지로 끝냅니다. 쓰던 파일이 망가질 수 있어서 마지막 수단입니다.

인터넷 손님을 받는 프로그램은 번호가 붙은 문을 하나씩 차지합니다. 이 번호를 **포트**(port)라고 합니다([14장](ch14.html#address)). 아파트의 호수와 같습니다. **문 하나는 한 번에 한 프로그램만** 차지할 수 있습니다.

웹사이트를 만들 때는 내 컴퓨터에 연습용 서버 프로그램을 켜 놓고 화면을 확인합니다. 그림에서는 `npm run dev`라는 명령으로 켜고, 3000번 포트를 쓰려고 합니다. 켜지면 브라우저 주소창에 `localhost:3000`이라고 쳐서 봅니다. '내 컴퓨터의 3000번 문'이라는 뜻입니다([14장](ch14.html#localhost)).

::: {.fig src="port-in-use.svg"}
범인은 대개 어제의 나입니다.
:::

그런데 `address already in use`라는 오류가 나옵니다. "그 번호는 이미 쓰는 중"이라는 뜻입니다. 범인은 어제 켠 서버입니다. 터미널 창은 닫았지만 프로그램은 살아남아 3000번을 쥐고 있습니다. 그림의 `node`가 그 프로그램입니다. 아래쪽의 세 걸음으로 풉니다.

1. **찾습니다.** `lsof -i :3000`은 3000번 포트를 쓰는 프로세스를 보여 줍니다. 이름은 `node`, PID는 4312입니다.
2. **끝냅니다.** 내가 켠 프로그램이 맞는지 확인하고 `kill 4312`로 부탁합니다. 버티면 그때 `kill -9`를 씁니다.
3. **다시 켭니다.** 3000번이 비었으므로 이번에는 잘 켜집니다.

::: {.tip title="고쳤다는데 화면이 그대로일 때"}
AI 코딩 도구는 확인하려고 켠 서버를 끄지 않고 둘 때가 있습니다. 3000번이 막혀 있으면 말없이 3001번으로 옮겨 켜지는 서버도 많습니다. 그러면 `localhost:3000`에는 옛 화면이 그대로 보입니다. 터미널에 찍힌 주소의 포트 번호부터 확인합니다.
:::

## 새 프로젝트를 처음 돌릴 때: 네 걸음 {#first-run}

새 보드게임을 사면 설명서를 읽고, 말과 카드가 다 있는지 세어 보고, 판을 편 다음에 시작합니다. AI가 만들어 준 프로젝트나 인터넷에서 받은 프로젝트를 처음 켤 때도 순서가 있습니다. 공구, 부품, 벽의 메모를 차례로 갖춘 다음에 켭니다.

설명서는 프로젝트 폴더의 `README.md` 파일입니다([초코딩 기초](code.html#project)). 필요한 버전과 켜는 명령이 보통 여기에 적혀 있습니다. AI에게 프로젝트를 만들게 했다면 아래 네 걸음을 README에 적어 달라고 합니다.

| 걸음 | 하는 일 | 명령의 예 | 건너뛰면 나오는 글자 |
|---|---|---|---|
| 1. 공구 | 런타임이 있고 버전이 맞는지 봅니다 | `node -v` | `command not found` |
| 2. 부품 | 적힌 패키지를 모두 받습니다 | `npm install` | `Cannot find module`, `ModuleNotFoundError` |
| 3. 메모 | `.env.example`을 보고 `.env`를 채웁니다 | 편집기로 파일을 만듭니다 | `KeyError`, `undefined` |
| 4. 실행 | 켜는 명령을 칩니다 | `npm run dev` | `address already in use` |

표의 명령은 자바스크립트 프로젝트의 것입니다. 파이썬이라면 1걸음은 `python3 --version`, 2걸음은 가상 환경을 켜고 치는 `pip install -r requirements.txt`, 4걸음은 `python main.py` 같은 명령입니다.

`npm run dev`의 `dev`는 `package.json`의 `scripts` 칸에 적어 둔 이름입니다. 켜는 명령을 모르겠으면 그 칸을 봅니다.

네 걸음은 모두 **프로젝트 폴더 안에 서서** 칩니다. 다른 폴더에서 치면 `Could not read package.json`처럼 파일을 못 찾는다는 오류가 납니다([5장](ch05.html)).

오류가 나면 어느 걸음에서 멈췄는지부터 가립니다. 표의 넷째 칸이 단서입니다. 2걸음에서 난 오류는 4걸음의 명령을 되풀이해도 풀리지 않습니다([증상으로 찾기](trouble.html)).

## 원격 서버와 SSH: 멀리 있는 작업실에서 일하기 {#ssh}

온라인 게임을 할 때 내 컴퓨터는 멀리 있는 게임 회사의 컴퓨터와 이어져 있습니다. 개발자도 멀리 있는 컴퓨터를 씁니다. AI를 돌리는 힘센 컴퓨터나 늘 켜 두는 서버는 대개 내 방에 없습니다. 이렇게 멀리 있는 서버가 원격 서버입니다.

이런 컴퓨터는 내 터미널을 그 컴퓨터에 이어서 다룹니다. 이 연결을 맡는 도구가 **SSH**(Secure Shell)입니다. 오가는 글자는 모두 암호로 바뀌어서, 중간에서 엿봐도 읽지 못합니다.

터미널에서 접속하는 모습입니다.

```text
mina@macbook ~ % ssh mina@203.0.113.10
mina@gpu-server:~$
```

첫 줄 끝의 `ssh mina@203.0.113.10`이 내가 친 명령이고, `사용자 이름@서버 주소` 꼴입니다. 둘째 줄에서 컴퓨터 이름이 `macbook`에서 `gpu-server`로 바뀌었습니다. 이제부터 치는 명령은 **저쪽 컴퓨터에서** 실행됩니다.

내 노트북에 설치한 패키지는 거기에 없습니다. 작업실이 통째로 다른 곳이기 때문입니다. `exit`를 치면 노트북으로 돌아옵니다.

### 서로 확인하기: 지문과 열쇠

SSH로 이을 때는 확인을 두 번 합니다.

::: {.fig src="ssh-two-checks.svg"}
①은 내가 서버를, ②는 서버가 나를 확인합니다.
:::

**먼저 내가 서버를 확인합니다.** 서버마다 자기만의 키가 있습니다. 키는 아주 긴 암호 같은 글자 묶음이고, 그것을 짧게 줄인 글자가 **지문**(fingerprint)입니다. 그림의 `SHA256:Xk3f…9QeM`입니다. 처음 가는 서버라면 SSH가 지문을 보여 주고 계속할지 묻습니다. 서버를 관리하는 사람이 알려 준 지문과 같으면 `yes`라고 답합니다.

노트북은 확인한 서버의 키를 `known_hosts` 파일에 적어 두고 다음부터 알아서 견주어 봅니다. 키가 달라졌다는 경고가 뜨면 멈춥니다. 누군가 서버인 척하는 것일 수도 있습니다.

**그다음 서버가 나를 확인합니다.** 비밀번호는 남이 알아맞힐 수 있어서, 짝이 맞는 파일 두 개를 만들어 씁니다.

- **공개 키**(public key)는 자물쇠입니다. 서버의 `authorized_keys` 파일에 미리 등록해 둡니다. 남이 봐도 괜찮습니다.
- **개인 키**(private key)는 열쇠입니다. 그림의 `id_ed25519` 파일이고, 내 노트북에만 둡니다. 메신저에도, AI 대화창에도 붙여 넣지 않습니다.

접속할 때 노트북은 개인 키로 서명을 만들어 보냅니다. 나만 찍을 수 있는 도장입니다. 서버는 공개 키로 그 도장을 확인합니다. 열쇠 자체는 노트북을 떠나지 않습니다.

코드를 인터넷에 올려 두는 서비스([7장](ch07.html))도 이 열쇠 짝으로 나를 확인하곤 합니다. 그때 나오는 `Permission denied (publickey)`는 "짝이 맞는 열쇠를 찾지 못했다"는 뜻입니다. 남이나 AI에게 보여 줘도 되는 것은 이름이 `.pub`로 끝나는 공개 키 파일뿐입니다.

### 포트 포워딩: 두 개의 localhost

원격 서버에서 켠 웹 앱은 보통 같은 컴퓨터 안에서 온 손님만 받습니다. 아래 그림의 '앱 서버'가 그 웹 앱이고, 8000번 포트를 씁니다. 그 화면을 내 노트북의 브라우저로 보려면 SSH로 두 컴퓨터 사이에 통로를 놓습니다. 터미널에 치는 명령입니다.

```bash
$ ssh -L 9000:localhost:8000 mina@203.0.113.10
```

::: {.fig src="port-forward.svg"}
글자는 같은 `localhost`인데 가리키는 컴퓨터가 다릅니다.
:::

`-L` 뒤를 쌍점에서 끊어 읽습니다. 앞의 `9000`은 내 노트북에 여는 문이고, 뒤의 `localhost:8000`은 서버 쪽에서 찾아갈 곳입니다. `localhost`는 언제나 '이 말을 읽는 컴퓨터 자신'이라서, 여기서는 서버 자신입니다.

노트북 브라우저에서 `localhost:9000`을 열면 SSH가 그 연결을 통로 건너편 서버의 8000번에 이어 줍니다. 이번 `localhost`는 노트북 자신입니다. 이 일을 **포트 포워딩**(port forwarding)이라고 합니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 설치된 것 / 실행되는 것 | 컴퓨터 어딘가에 있는 파일 / PATH에서 먼저 잡혀 실제로 켜진 파일 |
| 전역 설치 / 프로젝트 안 설치 | 컴퓨터 전체가 함께 씀 / 그 프로젝트만 씀 |
| 가상 환경 / 가상 머신 | 파이썬과 부품함만 따로 / 컴퓨터 한 대를 통째로 따로 |
| 공개 키 / 개인 키 | 서버에 등록하는 자물쇠 / 내 컴퓨터에만 두는 열쇠 |

## 실전 사례 {#case}

::: {.case title="설치했는데 없다고 합니다"}
민아는 `mygame` 폴더에서 게임을 만들고 있습니다. 터미널에 `pip install requests`를 쳤고, 설치에 성공했다는 글도 봤습니다. 그런데 편집기의 실행 버튼을 누르면 `ModuleNotFoundError`가 납니다.

1. **다시 설치하지 않습니다.** 물어야 할 것은 "어느 부품함에 넣었고, 어느 파이썬이 실행했는가"입니다.
2. **설치한 쪽을 봅니다.** 설치했던 터미널의 줄 앞에 `(.venv)`가 없습니다. 가상 환경을 켜지 않아서 공용 부품함에 들어갔습니다.
3. **실행한 쪽을 봅니다.** 편집기에서 고른 파이썬은 `mygame/.venv` 안의 것입니다. 이쪽 부품함에는 `requests`가 없습니다.
4. **둘을 맞춥니다.** 터미널에서 가상 환경을 켜고 `python -m pip install requests`로 설치합니다. 실행 버튼을 다시 눌러 확인합니다.

"설치했다"는 말에는 흔히 **어느 부품함에**가 빠져 있습니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- 코드는 설계도이고, 결과는 **작업실(환경)**이 함께 정합니다. 안 되면 두 작업실에서 무엇이 다른지부터 봅니다.
- **환경 변수**는 프로그램이 켜질 때 베껴 가는 쪽지입니다. 고쳤으면 프로그램을 다시 켭니다.
- 비밀 값은 **`.env` 파일**에만 두고, 코드와 대화창에는 적지 않습니다.
- **PATH**는 명령을 찾아볼 폴더의 순서입니다. 앞 선반에서 먼저 나온 것이 실행됩니다.
- 패키지를 받으면 **간접 의존성**이 딸려 옵니다. **잠금 파일**은 그 전부의 정확한 버전을 적어 둡니다.
- 프로젝트의 부품은 **프로젝트 안**에 넣습니다. 파이썬에서는 **가상 환경**이 그 부품함입니다.
- AI 코딩 도구는 **내 이름으로** 파일을 고치고 명령을 실행합니다. 프로젝트 폴더만 열어 줍니다.
- `Permission denied`와 "포트가 이미 사용 중"을 만나면 `sudo`나 `kill -9`보다 **까닭 찾기**가 먼저입니다.
- 새 프로젝트는 **공구 확인, 패키지 받기, 환경 변수 채우기, 실행** 순서로 켭니다.
- **SSH**로 접속한 뒤의 명령은 서버에서 실행됩니다.
:::

## 확인 문제 {#quiz}

::: {.q}
칠판에 "체육은 운동장"이라고 적혀 있어서 수첩에 베껴 적었습니다. 그 뒤에 선생님이 "체육관"으로 고쳤습니다. 내 수첩에는 무엇이 적혀 있을까요? 환경 변수와 프로그램에 견주어 보세요.

::: {.a}
여전히 "운동장"입니다. 프로그램도 켜지는 순간에 환경 변수를 베껴 가고 다시 보지 않습니다. 껐다가 다시 켜야 새 값을 받습니다.
:::
:::

::: {.q}
어제 새 버전의 파이썬을 설치했습니다. 그런데 터미널에 `python3`를 치면 여전히 옛 버전이 켜집니다. 왜 그럴까요? 무엇으로 확인할까요?

::: {.a}
옛 버전이 든 폴더가 PATH에서 더 앞에 있어서입니다. `which python3`를 치면 어느 폴더의 것이 잡혔는지 알 수 있습니다.
:::
:::

::: {.q}
친구가 말합니다. "가상 환경을 켜고 AI 코딩 도구를 돌리니까, 이 도구가 내 사진을 지울 걱정은 없어." 맞는 말일까요?

::: {.a}
틀립니다. 가상 환경은 어느 파이썬과 어느 부품함을 쓸지만 나눕니다. 도구는 내 이름으로 일하므로 내가 지울 수 있는 파일은 지울 수 있습니다.
:::
:::

::: {.q}
패키지를 설치하다가 `Permission denied`가 나왔습니다. AI가 명령 앞에 `sudo`를 붙이라고 합니다. 따르기 전에 무엇을 확인해야 할까요?

::: {.a}
누가, 어느 폴더에, 무엇을 하려다 막혔는지 읽습니다. 공용 부품함에 넣으려다 막혔다면 가상 환경을 켜고 설치하는 것이 답입니다.
:::
:::

::: {.q}
AI와 만든 날씨 앱이 내 노트북에서는 잘 됩니다. 인터넷에 올렸더니 "API 키가 없다"며 멈춥니다. 키를 적어 둔 `.env` 파일은 노트북에 그대로 있습니다. 왜 그럴까요?

::: {.a}
`.env`는 올리지 않는 파일이라서 서버에는 그 쪽지가 없습니다. 서버는 다른 작업실입니다. 서버를 빌려준 서비스의 설정 화면에 이름과 값을 따로 넣습니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI는 내 작업실을 모르는 채로 명령을 줍니다. 무엇이 깔려 있는지 먼저 알려 주고, 막혔을 때는 고치기 전에 **두 작업실에서 무엇이 다른지부터 살펴보게** 하세요.

> 내 컴퓨터는 맥이고 node는 v22, python3는 3.12야. 이 프로젝트를 처음 돌리려고 해. 필요한 런타임과 버전, 패키지 받는 명령, 환경 변수의 이름, 켜는 명령을 네 걸음으로 적어 줘. 패키지는 프로젝트 안에만 설치하고, 전역 설치나 sudo가 필요하면 까닭부터 말해 줘. `.env`의 값은 보여 주지 말고 이름만 다뤄 줘. 오류가 나면 다시 설치하기 전에, 어느 python이 실행됐고 패키지가 어느 폴더에 들어갔는지부터 보여 줘.

**받은 답에서 확인할 것**

- 짐작이 아니라 `which`나 `--version`의 답 같은 실제 값을 보여 주는가.
- 설치 명령에 `sudo`나 `-g`가 까닭 없이 붙어 있지 않은가.
- 새로 넣은 패키지가 `requirements.txt`나 `package.json`에 적혔는가.
- 비밀 값이 코드에 적혀 있지 않고 `.env`에만 있는가.

**AI가 자주 하는 실수**

- **막히면 힘으로 넘깁니다.** 다시 설치하기를 되풀이하거나 `sudo`, `chmod 777`, `kill -9`를 씁니다. 멈추고 "왜 막혔는지부터 알려 줘"라고 합니다([30장](ch30.html#stuck)).
- **내 컴퓨터를 넘겨짚습니다.** 윈도우인데 맥의 명령을 주거나, 내게 없는 버전의 문법을 씁니다. 첫 요청에 운영체제와 버전을 적습니다.
- **없는 패키지를 지어냅니다.** 이름만 비슷한 남의 패키지가 깔릴 수도 있습니다. 설치 전에 레지스트리에서 이름을 검색합니다.
:::

## 용어 정리 {#terms}

::: {.terms}
개발 환경 (development environment)
:   프로그램이 돌아가는 데 필요한 코드 바깥의 도구와 설정.

환경 변수 (environment variable)
:   프로그램이 켜질 때 건네받는 `이름=값` 꼴의 쪽지.

.env 파일
:   환경 변수를 모아 적어 둔 파일. 남에게 건네지 않는다.

PATH
:   셸이 명령을 찾아보는 폴더 목록. 앞에서부터 찾는다.

셸 시작 파일
:   셸이 켜질 때마다 읽는 설정 파일. `.zshrc`, `.bashrc` 등.

패키지 (package)
:   남이 만든 코드에 이름과 버전을 붙여 포장한 것.

패키지 매니저 (package manager)
:   패키지를 받아 설치해 주는 프로그램. pip, npm 등.

레지스트리 (registry)
:   패키지가 모여 있는 인터넷의 저장소.

간접 의존성 (transitive dependency)
:   내가 적지 않았는데 딸려 오는 패키지.

잠금 파일 (lock file)
:   설치된 모든 패키지의 정확한 버전을 적어 둔 파일.

가상 환경 (virtual environment)
:   프로젝트마다 따로 두는 파이썬과 부품함.

전역 설치 (global install)
:   패키지를 컴퓨터 전체가 함께 쓰는 곳에 넣는 것.

편집기 (editor)
:   코드를 쓰는 프로그램. VS Code 등.

언어 서버 (language server)
:   코드에서 틀린 곳을 찾아 편집기에 알려 주는 프로그램.

LSP (Language Server Protocol)
:   편집기와 언어 서버가 주고받는 말의 규칙.

사용자 (user)
:   컴퓨터에 로그인한 '누구'. 내가 켠 프로그램은 내 이름으로 일한다.

권한 (permission)
:   누가 그 파일을 읽고, 쓰고, 실행해도 되는지 정해 둔 것.

소유자와 그룹
:   파일의 주인과, 사용자 여럿을 묶은 모둠.

root
:   권한 검사를 거의 받지 않는 관리자.

sudo
:   명령 하나를 root의 이름으로 실행하게 하는 명령.

포트 (port)
:   연결을 받을 프로그램을 가려 주는 번호.

SSH (Secure Shell)
:   멀리 있는 컴퓨터에 내 터미널을 이어 주는 도구.

지문 (fingerprint)
:   서버의 키를 짧게 줄인 글자. 서버를 확인하는 데 쓴다.

공개 키와 개인 키 (public key / private key)
:   짝이 맞는 파일 한 쌍. 공개 키는 서버에 등록하고 개인 키는 나만 갖는다.

포트 포워딩 (port forwarding)
:   내 컴퓨터의 포트로 온 연결을 SSH 통로 건너편으로 넘기는 것.
:::
