::: {.lead}
양말을 서랍에 아무렇게나 넣어 두면 짝을 찾는 데 한참 걸립니다. 칸을 나눠 정리해 두면 금방 찾습니다. 컴퓨터 안의 데이터도 같습니다. 어떻게 담아 두느냐에 따라 찾고 꺼내는 속도가 크게 달라집니다. 데이터를 담아 두는 여러 가지 방식을 **자료구조**라고 합니다.
:::

::: {.goals}
- 자료구조가 무엇이고 왜 여러 종류가 있는지 말할 수 있습니다.
- 배열, 스택, 큐, 해시 맵, 트리, 그래프가 어떤 모양인지 그림으로 설명할 수 있습니다.
- 하려는 일에 맞는 자료구조를 고를 수 있습니다.
- 데이터를 다른 프로그램에 보낼 때 조심할 점을 알 수 있습니다.
:::

## 같은 재료도 그릇에 따라 달라집니다 {#why}

주방을 떠올려 봅시다. 달걀은 칸칸이 나뉜 달걀판에 담고, 접시는 차곡차곡 쌓아 두고, 양념은 이름표를 붙인 통에 넣습니다. 아무 데나 쏟아 놓아도 보관은 되지만, 바쁜 저녁 시간에 소금 하나 찾느라 조리대를 다 뒤져야 합니다.

프로그램도 메모리라는 조리대 위에 데이터를 올려 두고 일합니다. 이때 **데이터를 어떤 모양으로 늘어놓을지 정한 방식**을 **자료구조**(data structure)라고 합니다. 이 장에서는 쉽게 "그릇"이라고 부르겠습니다.

분식집 메뉴 네 개로 확인해 봅시다.

::: {.fig src="three-bowls.svg"}
같은 메뉴 네 개를 세 가지 그릇에 담은 모습. 그릇마다 곧바로 답할 수 있는 질문이 다릅니다.
:::

데이터는 똑같은데 잘 답하는 질문이 다릅니다. 배열은 "몇 번째"에, 해시 맵은 "이름으로 찾기"에, 트리는 "갈래별로 묶기"에 강합니다. 반대로 배열에게 "우동은 얼마?"를 물으면 칸을 처음부터 하나씩 열어 봐야 합니다. 세 그릇 모두 곧 하나씩 살펴봅니다.

이 장에서는 그릇이 일하는 빠르기를 세 가지 말로 나타내겠습니다.

- **한 번에 찾는다.** 데이터가 열 개든 백만 개든 걸리는 시간이 거의 같습니다.
- **절반씩 줄인다.** 한 번 볼 때마다 후보가 반으로 줄어듭니다. 백만 개도 스무 번쯤이면 끝납니다.
- **하나씩 다 본다.** 데이터가 열 배 늘면 시간도 열 배 늘어납니다.

이 차이를 기호로 정확히 적는 법은 [9장](ch09.html)에서 배웁니다.

::: {.key}
만능 그릇은 없습니다. 자료구조를 고른다는 것은 **"이 데이터로 무엇을 가장 자주 할 것인가"**를 정하는 일입니다.
:::

## 배열: 번호 붙은 칸이 나란히 {#array}

가장 기본이 되는 그릇은 달걀판처럼 **같은 크기의 칸이 빈틈없이 붙어 있는** 그릇입니다. 이것이 **배열**(array)입니다. 칸마다 0부터 시작하는 번호가 붙는데, 이 번호를 **인덱스**(index)라고 합니다.

```python
menu = ["라면", "우동", "김밥", "덮밥"]
menu[2]                    # "김밥" — 2번 칸을 바로 꺼냄
menu.insert(0, "떡볶이")    # 맨 앞에 끼워 넣기
menu.append("만두")         # 맨 끝에 붙이기
```

- 2행: 인덱스는 0부터 세므로 `menu[2]`는 세 번째 칸입니다.
- 3~4행: `insert(0, …)`는 맨 앞인 0번 칸에, `append`는 맨 끝에 값을 넣습니다.

배열은 **몇 번째 칸이든 한 번에** 꺼냅니다. 칸 크기가 같고 붙어 있어서 위치를 계산 한 번으로 알 수 있기 때문입니다. 배열이 메모리 주소 1000번지에서 시작하고 한 칸이 8바이트라면, 3번 칸은 1000 + 3 × 8 = 1024번지입니다. 칸이 백만 개여도 계산은 한 번입니다.

대신 **중간에 끼워 넣거나 빼는 일**에는 약합니다. 칸이 붙어 있으니, 자리를 만들려면 뒤의 값을 모두 한 칸씩 밀어야 합니다.

::: {.fig src="array-shift.svg"}
맨 앞에 떡볶이를 넣자 원래 있던 네 개가 모두 한 칸씩 밀렸습니다. 값이 만 개였다면 만 번을 옮겨야 합니다.
:::

맨 끝에 붙이는 일은 아무것도 밀지 않으니 빠릅니다. 끝에 빈 칸이 없으면 어떻게 할까요? Python의 리스트나 JavaScript의 배열은 칸이 다 차면 **더 넓은 자리를 새로 잡고 통째로 이사**합니다. 이런 배열을 **동적 배열**(dynamic array)이라고 합니다. 이사는 비싸지만, 한 번 옮길 때 넉넉하게 넓혀 두므로 자주 일어나지 않습니다.

::: {.warn title="인덱스는 이름표가 아닙니다"}
위 그림에서 김밥은 2번 칸에 있다가 3번 칸으로 밀렸습니다. 인덱스는 "지금 몇 번째 자리에 있나"일 뿐입니다. 화면에서 고른 상품을 "2번"이라고 기억해 두면, 목록 앞에 새 상품이 들어오는 순간 엉뚱한 상품을 가리킵니다.
:::

## 연결 리스트: 다음 쪽지를 따라가는 보물찾기 {#linked}

배열의 약점은 "칸이 붙어 있어야 한다"는 데서 나옵니다. 그렇다면 칸을 붙여 두지 않으면 어떨까요?

보물찾기를 떠올려 봅시다. 첫 쪽지에 "다음 쪽지는 놀이터 벤치 밑에"라고 적혀 있고, 거기에 가면 또 다음 장소가 적혀 있습니다. 쪽지들은 여기저기 흩어져 있지만 순서는 분명합니다.

**연결 리스트**(linked list)가 이 방식입니다. 값 하나와 **다음 값이 있는 곳의 주소**를 한 묶음으로 만들고, 이 묶음을 **노드**(node)라고 부릅니다. 주소는 [2장](ch02.html)에서 본 메모리의 사물함 번호입니다. 노드는 메모리 어디에 놓여도 됩니다.

::: {.fig src="linked-insert.svg"}
연결 리스트에 만두를 끼워 넣는 모습. 뒤의 값을 미는 대신, 주소가 적힌 쪽지 두 장만 고칩니다.
:::

끼워 넣기는 배열보다 훨씬 가볍습니다. 하지만 치르는 값이 있습니다.

- **몇 번째 것을 바로 꺼낼 수 없습니다.** 만 번째 값을 보려면 첫 노드부터 쪽지를 만 번 따라가야 합니다.
- **흩어져 있어서 느립니다.** [1장](ch01.html)에서 CPU는 붙어 있는 데이터를 한 묶음으로 가져온다고 했습니다. 배열은 이 덕을 보지만, 연결 리스트는 노드마다 먼 곳을 다녀와야 합니다.

그래서 실제로는 배열이 더 빠른 경우가 많고, 연결 리스트를 직접 만들 일은 드뭅니다. 그래도 **"주소를 적은 쪽지로 데이터를 잇는다"**는 생각은 기억해 두세요. 뒤에 나올 트리와 그래프가 모두 이 생각 위에 서 있습니다.

## 스택과 큐: 꺼내는 순서가 정해진 그릇 {#stack-queue}

어떤 그릇은 "아무 데서나 꺼내기"를 일부러 막습니다. 넣고 빼는 자리를 정해 두면 순서가 뒤섞일 일이 없기 때문입니다.

- **스택**(stack)은 접시 더미입니다. 맨 위에 올리고 맨 위에서 꺼냅니다. **나중에 넣은 것이 먼저** 나옵니다.
- **큐**(queue)는 계산대 앞의 줄입니다. 맨 뒤에 서고 맨 앞에서 빠집니다. **먼저 넣은 것이 먼저** 나옵니다.

::: {.fig src="stack-queue.svg"}
A, B, C를 차례로 넣었을 때 스택과 큐가 내놓는 순서. 주황색이 다음에 나올 값입니다.
:::

스택은 **방금 한 일부터 거꾸로 되돌릴 때** 씁니다. 편집기의 실행 취소(Ctrl+Z)와 브라우저의 뒤로 가기가 스택입니다. 큐는 **온 순서대로 공평하게 처리할 때** 씁니다. 주문 대기열과 인쇄 대기열이 큐입니다.

Python에서 스택은 리스트면 충분합니다. `append`로 올리고 `pop`으로 내리면 둘 다 끝에서 일하기 때문입니다. 큐는 조금 다릅니다.

```python
from collections import deque

orders = deque(["주문 1", "주문 2"])
orders.append("주문 3")      # 맨 뒤에 섬
orders.popleft()             # "주문 1" — 가장 먼저 온 주문
```

리스트에서 `pop(0)`으로 맨 앞을 꺼내도 결과는 같습니다. 하지만 리스트는 배열이어서, 맨 앞을 뺄 때마다 남은 값을 전부 한 칸씩 당깁니다. 그래서 3행처럼 **덱**(deque)이라는 그릇을 씁니다. 덱은 양쪽 끝 어디서 넣고 빼도 나머지를 옮기지 않습니다.

큐는 넘칠 수도 있습니다. 주문이 1초에 10건 들어오는데 5건씩만 처리하면 큐는 끝없이 길어집니다. 그래서 "최대 몇 개까지 쌓을지, 넘치면 어떻게 할지"를 함께 정합니다.

::: {.deep title="칸을 돌려쓰는 큐: 원형 버퍼"}
칸 수를 처음부터 정해 놓고 둥글게 이어 쓰는 큐를 **원형 버퍼**(ring buffer)라고 합니다. 칸이 4개(0~3번)라면 3번 칸 다음에 쓸 자리는 다시 0번입니다. 계산으로는 (3 + 1)을 4로 나눈 나머지인 0입니다.

꽉 찼을 때는 새 값을 거절할지, 기다릴지, 가장 오래된 값을 덮어쓸지 정해야 합니다. "최근 기록 100줄"은 덮어써도 괜찮지만, 결제 대기열이 조용히 덮어쓰면 주문이 사라집니다. Python의 `deque(maxlen=100)`은 꽉 차면 반대쪽 끝의 값을 버립니다.
:::

## 해시 맵: 이름표로 바로 찾기 {#map}

배열은 번호로는 한 번에 꺼내지만, "회원 번호가 7302인 사람"처럼 **내용으로 찾으라고 하면 하나씩 다 봐야** 합니다. 회원이 만 명이면 최악의 경우 만 번을 비교합니다.

양념통에 이름표를 붙여 두면 "소금"이라는 글자만 보고 바로 집을 수 있습니다. 이렇게 **이름표와 내용물을 짝지어 담는 그릇**이 **해시 맵**(hash map)입니다. 이름표를 **키**(key), 내용물을 **값**(value)이라고 부릅니다. Python에서는 딕셔너리(`dict`), JavaScript에서는 `Map`이나 객체가 이 역할을 합니다.

```python
price = {"라면": 4500, "우동": 5000}
price["우동"]             # 5000 — 키로 바로 꺼냄
price["만두"] = 6000      # 새 짝을 추가
"김밥" in price           # False — 그런 키는 없음
```

어떻게 한 번에 찾을까요? 비결은 **키를 계산해서 넣을 칸의 번호를 정하는 것**입니다. 서랍 4개(0~3번)에 회원을 넣는다고 합시다. 규칙은 "회원 번호를 4로 나눈 나머지와 같은 번호의 서랍에 넣는다"입니다.

::: {.fig src="hash-buckets.svg"}
회원 번호를 4로 나눈 나머지가 서랍 번호가 됩니다. 7과 11은 나머지가 둘 다 3이라 같은 서랍에 들어갑니다.
:::

7번 회원을 찾을 때도 같은 계산을 합니다. 7을 4로 나눈 나머지는 3이므로 3번 서랍만 열면 됩니다. 이렇게 **키를 숫자로 바꿔 주는 계산**을 **해시 함수**(hash function)라고 합니다. 글자로 된 키도 컴퓨터 안에서는 숫자이므로, 그 숫자들을 섞어 큰 수 하나를 만든 뒤 같은 방법을 씁니다.

그림의 7과 11처럼 서로 다른 키가 같은 칸으로 모이는 일을 **충돌**(collision)이라고 합니다. 충돌은 고장이 아니라 늘 있는 일입니다. 해시 맵은 서랍에 둘 다 넣어 두고, 찾을 때 서랍 안에서 **키를 직접 비교**해 진짜 주인을 가려냅니다. 서랍이 넉넉하면 한 서랍에 든 것이 한두 개뿐이라 "거의 한 번에" 찾습니다.

치르는 값도 있습니다. 빈 서랍을 넉넉히 두느라 배열보다 메모리를 더 씁니다. 키를 크기순으로 늘어놓지도 않아서 "4000원에서 5000원 사이의 메뉴" 같은 질문에는 도움이 되지 않습니다.

::: {.deep title="서랍이 꽉 차면: 부하율과 재해싱"}
항목 수를 서랍 수로 나눈 값을 **부하율**(load factor)이라고 합니다. 서랍 4개에 3개가 들었다면 0.75입니다. 부하율이 높을수록 한 서랍에 여럿이 몰려 찾기가 느려집니다.

그래서 부하율이 정해 둔 선을 넘으면 서랍 수를 늘리고 **모든 항목을 새 서랍 번호로 다시 배치**합니다. 이것이 **재해싱**(rehashing)입니다. 서랍이 4개일 때 키 1, 5, 9는 모두 1번에 모입니다. 8개로 늘리면 5는 5번으로 옮겨 가지만 1과 9는 여전히 1번에 함께 있습니다.
:::

### 집합: 있는지 없는지만 기억하기

값은 필요 없고 **"이게 들어 있나?"**만 알면 될 때가 있습니다. 이미 쓴 쿠폰 번호가 그렇습니다. 키만 담는 해시 맵을 **집합**(set)이라고 합니다. 같은 것을 두 번 넣어도 하나만 남습니다.

```python
used = {"A12", "B07"}     # 이미 쓴 쿠폰
"A12" in used             # True — 한 번에 확인
```

리스트에도 `in`을 쓸 수 있지만 그때는 하나씩 다 봅니다. 대신 집합은 "몇 번 나왔는지"와 "어떤 순서였는지"를 버립니다.

### 무엇을 '같다'고 볼까: ID

해시 맵과 집합은 키가 같으면 같은 것으로 칩니다. 그러니 **무엇을 키로 삼느냐**가 중요합니다.

회원을 이름으로 저장하면 `members["김민준"]`에 두 번째 김민준을 넣는 순간 첫 번째 김민준이 덮어써집니다. 이름은 겹칠 수 있고 바뀔 수도 있습니다. 그래서 대상마다 **겹치지 않고 바뀌지 않는 번호**를 하나씩 붙이는데, 이것이 **ID**(식별자, identifier)입니다. 회원 번호와 주문 번호가 ID입니다. 이름, 화면에 보이는 순서, 배열의 인덱스는 ID가 될 수 없습니다.

반대 방향의 실수도 있습니다. "라면 2개" 주문이 두 건 들어왔다면 내용은 같아도 서로 다른 주문입니다. 중복을 걸러 낼 때는 **"내용이 같으면 중복인가, ID가 같아야 중복인가"**를 먼저 정합니다.

## 트리와 힙: 위에서 아래로 갈라지는 그릇 {#tree}

컴퓨터의 폴더를 생각해 봅시다. 폴더 안에 폴더가 있고, 그 안에 또 폴더가 있습니다. 가계도나 회사 조직도도 같은 모양입니다. 이렇게 **하나에서 시작해 아래로 갈라져 내려가는 그릇**을 **트리**(tree)라고 합니다.

맨 위의 노드를 **루트**(root, 뿌리)라고 하고, 위아래로 이어진 두 노드를 부모와 자식이라고 부릅니다. 규칙은 두 가지입니다. 루트를 뺀 모든 노드는 **부모가 정확히 하나**이고, 내려가다가 **위로 되돌아오는 길은 없습니다.** 연결 리스트의 노드가 "다음" 쪽지 한 장을 가졌다면, 트리의 노드는 자식을 가리키는 쪽지를 여러 장 가진 셈입니다.

### 이진 탐색 트리: 갈림길마다 절반을 버린다

트리는 **빨리 찾는 데**에도 씁니다. 1부터 100 사이의 숫자를 맞히는 놀이에서 "50보다 커요?"라고 물으면, 답이 무엇이든 후보가 절반으로 줄어듭니다.

**이진 탐색 트리**(binary search tree)는 이 질문을 그릇 모양으로 굳혀 놓은 것입니다. 노드마다 자식을 둘까지 두고, **왼쪽 아래에는 더 작은 값만, 오른쪽 아래에는 더 큰 값만** 둡니다.

::: {.fig src="bst-search.svg"}
10을 찾는 길. 갈림길마다 한쪽을 통째로 버리므로 일곱 개 중 세 개만 확인합니다.
:::

값이 고르게 퍼진 트리라면 한 층 내려갈 때마다 후보가 절반씩 줄어듭니다. 천 개에서는 열 번쯤, 백만 개에서는 스무 번쯤 비교하면 찾습니다. 게다가 값이 크기순으로 정리되어 있어서, 해시 맵이 못하던 "4000원에서 5000원 사이의 메뉴"도 빨리 찾습니다.

::: {.warn title="한쪽으로 쏠린 트리"}
1, 2, 3, 4를 순서대로 넣으면 모두 오른쪽 아래로만 이어져 한 줄짜리 사슬이 됩니다. 이름은 트리지만 실제로는 연결 리스트여서 하나씩 다 봐야 합니다. "절반씩 줄인다"는 **트리가 고르게 퍼져 있을 때만** 성립합니다.
:::

::: {.deep title="쏠림을 스스로 고치는 균형 트리"}
값을 넣거나 뺄 때마다 한쪽이 너무 길어졌는지 살피고, 노드 몇 개의 위아래를 바꿔 끼워 높이를 낮게 유지하는 트리를 **균형 트리**(balanced tree)라고 합니다. 크기순 규칙은 그대로 지키면서 모양만 고칩니다. 데이터베이스의 인덱스([17장](ch17.html))가 이런 트리의 친척입니다. 직접 만들 일은 거의 없고, 크기순을 유지한 채 자주 넣고 빼야 할 때 골라 쓰면 됩니다.
:::

::: {.deep title="자동 완성의 그릇: 트라이"}
검색창에 "app"을 치면 app, apple, apply가 뜹니다. 이런 일에는 글자 하나가 한 층인 **트라이**(trie)라는 트리를 씁니다. 루트에서 a → p → p로 내려간 뒤 그 아래에 달린 낱말을 모으면 됩니다. cat과 car는 c → a까지 같은 길을 쓰다가 마지막 글자에서 갈라집니다.
:::

### 힙: 가장 급한 것이 항상 맨 위에

응급실은 온 순서대로 진료하지 않습니다. 가장 위급한 환자가 먼저입니다. 이렇게 **온 순서가 아니라 급한 정도로 꺼내는 큐**를 **우선순위 큐**(priority queue)라고 하고, 이것을 만드는 데 쓰는 트리가 **힙**(heap)입니다.

::: {.fig src="heap-er.svg"}
응급실 대기 명단을 힙에 담은 모습. 숫자가 작을수록 급한 환자입니다.
:::

힙의 규칙은 "부모가 자식보다 급하다" 하나뿐입니다. 이 규칙만 지켜도 가장 급한 환자는 언제나 맨 위에 옵니다. 전체를 줄 세우지 않으니 가볍습니다. 환자가 새로 오거나 맨 위 환자가 빠지면, 위아래로 **한 줄기만** 따라가며 자리를 바꿉니다. 환자가 천 명이어도 열 번쯤이면 됩니다.

대신 힙은 "골절 환자가 있나?" 같은 질문에는 약합니다. 맨 위 하나를 빨리 꺼내는 데에만 맞춘 그릇입니다. Python에서는 `heapq`의 `heappush`와 `heappop`으로 리스트를 힙처럼 씁니다.

::: {.note}
여기서 말한 힙은 [3장](ch03.html)의 '힙 메모리'와 이름만 같을 뿐 관계가 없습니다.
:::

## 그래프: 누가 누구와 이어져 있나 {#graph}

지하철 노선도에는 위아래가 없습니다. 한 역이 여러 역과 이어지고, 돌고 돌아 제자리로 오는 길도 있습니다. 친구 관계도 마찬가지입니다. 이렇게 **대상과 대상 사이의 연결을 자유롭게 담는 그릇**이 **그래프**(graph)입니다. 역 같은 대상을 **정점**(vertex), 역과 역을 잇는 선을 **간선**(edge)이라고 부릅니다. 트리는 "부모는 하나, 되돌아오는 길 없음"이라는 규칙을 지키는 특별한 그래프입니다.

간선에는 정보를 더 실을 수 있습니다. 팔로우처럼 한쪽으로만 이어지는 관계라면 **방향**을, 역 사이에 걸리는 시간이 필요하다면 **가중치**라는 숫자를 붙입니다.

그래프를 메모리에 담을 때는 앞에서 배운 그릇을 조합합니다. 역 이름을 키로, 이웃 역의 배열을 값으로 하는 해시 맵을 만들면 됩니다.

::: {.fig src="graph-neighbors.svg"}
왼쪽 노선도를 오른쪽처럼 "역 → 이웃 역 목록"으로 저장합니다. 노란 칸이 키, 초록 칸이 값인 배열입니다.
:::

그래프를 따라다닐 때는 **순환**(cycle)을 조심해야 합니다. 시청 → 대학 → 공원 → 시청처럼 제자리로 돌아오는 길이 있으면, 이웃을 따라가기만 하는 코드는 영원히 끝나지 않습니다. 그래서 **이미 들른 역을 집합에 적어 두고**, 적힌 역은 다시 가지 않습니다. 가장 빠른 길을 찾는 방법은 [9장](ch09.html)에서 다룹니다.

::: {.deep title="빽빽한 표와 듬성듬성한 목록"}
그래프를 "가로 역 × 세로 역" 표로 저장할 수도 있습니다. 이어져 있으면 1, 아니면 0을 적습니다. 역이 1만 개면 칸이 1억 개 필요한데, 실제 연결이 3만 개뿐이라면 표는 거의 다 0입니다. 이럴 때는 이웃 목록처럼 **있는 것만 적는** 편이 훨씬 작습니다.

모든 칸을 다 두는 방식을 밀집 표현, 값이 있는 칸만 적는 방식을 희소 표현이라고 합니다. 대부분이 비어 있으면 희소 표현이, 거의 다 차 있으면 밀집 표현이 유리합니다.
:::

## 무엇을 자주 하느냐로 고릅니다 {#choose}

그릇의 이름을 외울 필요는 없습니다. 먼저 **"이 데이터로 가장 자주 하는 일이 무엇인가"**를 한 문장으로 적어 보세요. 그러면 그릇은 거의 정해집니다.

::: {.fig src="choose-map.svg"}
자주 하는 일에서 출발해 그릇을 고릅니다.
:::

얻는 것이 있으면 치르는 값도 있습니다.

| 그릇 | 잘하는 일 | 치르는 값 |
|---|---|---|
| 배열 | 번호로 꺼내기, 순서대로 훑기 | 중간에 넣고 빼면 뒤를 모두 민다 |
| 스택, 큐 | 정해진 순서로 넣고 꺼내기 | 중간 것은 꺼내지 못한다 |
| 해시 맵, 집합 | 키로 찾기, 포함 여부 확인 | 메모리를 더 쓰고 크기순이 아니다 |
| 힙 | 가장 급한 것 꺼내기 | 나머지는 정렬되어 있지 않다 |
| 탐색 트리 | 크기순 유지, 범위로 찾기 | 고르게 퍼지도록 관리해야 한다 |
| 그래프 | 연결 따라가기 | 순환을 따로 막아야 한다 |

실제 프로그램은 그릇을 섞어 씁니다. 회원을 가입순으로 보여 주면서 ID로도 바로 찾아야 한다면, 순서를 담은 배열과 ID로 찾는 해시 맵을 함께 둡니다. 대신 둘의 내용이 어긋나지 않게 같이 고쳐야 합니다.

::: {.tip title="망설여지면 배열과 해시 맵부터"}
대부분의 앱은 이 두 가지로 충분합니다. 순서대로 보여 주면 배열, ID로 찾으면 해시 맵입니다. 나머지 그릇은 "가장 급한 것부터"처럼 분명한 이유가 생겼을 때 꺼내 씁니다.
:::

AI가 만든 코드도 같은 눈으로 봅니다. **반복문 안에서 배열을 또 처음부터 뒤지는 코드**가 가장 흔한 신호입니다. 데이터가 적을 때는 티가 나지 않다가, 늘어나는 순간 갑자기 느려집니다.

## 그릇 밖으로 내보낼 때 {#exchange}

지금까지의 그릇은 모두 메모리라는 조리대 위에 있었습니다. 그런데 데이터는 파일에 저장되기도 하고 네트워크를 건너가기도 합니다. 그릇을 통째로 배달할 수는 없으니 포장을 해야 합니다.

### 직렬화: 한 줄의 글자로 펴기

메모리 안의 값은 주소가 적힌 쪽지로 서로 이어져 있고, 이 주소는 다른 컴퓨터에서는 아무 의미가 없습니다. 그래서 값을 내보낼 때는 **한 줄로 이어진 글자로 펴는데**, 이것을 **직렬화**(serialization)라고 합니다. 가장 널리 쓰는 포장 규격이 **JSON**입니다.

JSON이 담을 수 있는 것은 여섯 가지뿐입니다. 키와 값의 묶음(객체), 배열, 문자열, 숫자, 참과 거짓, 그리고 '없음'을 뜻하는 `null`입니다. 이 밖의 것은 여섯 가지 중 하나로 바꿔 담아야 하고, 그 과정에서 무언가를 잃습니다.

::: {.fig src="json-roundtrip.svg"}
JSON으로 내보냈다가 다시 읽은 결과. 문자열은 그대로지만 나머지는 종류가 바뀌거나 값이 달라졌습니다.
:::

- **집합과 시각**은 JSON에 없습니다. 배열과 문자열로 바꿔 보내고, 받는 쪽에서 다시 되돌려야 합니다.
- **아주 큰 정수**는 JavaScript가 숫자로 읽으면 끝자리가 달라질 수 있습니다. 주문 번호 같은 ID는 계산할 일이 없으니 처음부터 문자열로 보냅니다.
- **쪽지로 이어진 관계**도 사라집니다. 주문 두 건이 같은 회원 하나를 가리키고 있었다면, 받는 쪽에서는 똑같이 생긴 회원이 둘 생깁니다. 관계는 회원 ID로 적어 보냅니다.

### 시각: UTC로 저장하고 보여 줄 때 바꾸기

"11월 7일 오전 9시"는 서울과 뉴욕에서 서로 다른 순간입니다. 그래서 세계 공통 기준 시각인 **UTC**(협정 세계시)로 바꿔 저장합니다.

```text
2026-11-07T09:00:00+09:00    서울 시각 (+09:00은 UTC보다 9시간 빠름)
2026-11-07T00:00:00Z         같은 순간의 UTC (Z는 UTC라는 표시)
```

::: {.key}
시각은 **UTC로 저장하고 비교**합니다. 사용자에게 보여 줄 때만 그 사람의 시간대로 바꿉니다.
:::

다만 생일 같은 **날짜**는 순간이 아니므로 UTC로 바꾸지 않습니다. 바꾸면 다른 나라에서 하루 앞이나 뒤로 보일 수 있습니다.

### 글자: 같아 보여도 다를 수 있다

화면에는 똑같이 "가"로 보이는데 컴퓨터는 다르다고 할 때가 있습니다. 한글 한 글자는 **완성된 글자 하나**로 저장할 수도 있고, **자음과 모음을 이어 붙인 것**으로 저장할 수도 있기 때문입니다.

```python
import unicodedata
a = "가"                   # 완성된 글자 하나
b = "\u1100\u1161"         # 첫소리 ㄱ + 가운뎃소리 ㅏ
a == b                                    # False
unicodedata.normalize("NFC", b) == a      # True
```

- 3행: `\u1100`과 `\u1161`은 ㄱ과 ㅏ의 글자 번호입니다. 화면에는 `a`와 똑같이 보입니다.
- 5행: 여러 표현을 한 가지로 맞추는 일을 **정규화**(normalization)라고 합니다. `NFC`는 완성된 글자로 합치는 방식입니다.

맥에서 만든 파일의 한글 이름이 윈도우에서 "ㅎㅏㄴㄱㅡㄹ"처럼 풀려 보이는 것이 이 때문입니다. 글자를 해시 맵의 키로 쓰거나 검색할 때는 **비교하기 전에 한 가지 방식으로 정규화**합니다.

### 검증: 모양 검사와 규칙 검사

밖에서 들어온 데이터는 그대로 믿으면 안 됩니다. 검사는 두 단계입니다.

1. **모양 검사.** 필요한 칸이 다 있는지, 종류가 맞는지 봅니다. 수량 칸에 글자가 들어 있으면 여기서 걸립니다.
2. **규칙 검사.** 모양은 맞지만 말이 안 되는 값을 걸러 냅니다. 수량 -2나 1.5는 숫자이지만 주문 수량으로는 틀렸습니다. 합계도 받은 값을 믿지 않고 가격 × 수량으로 다시 계산합니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 배열 / 연결 리스트 | 칸이 붙어 있어 번호로 바로 꺼냄 / 쪽지로 이어져 끼워 넣기가 가벼움 |
| 스택 / 큐 | 나중에 넣은 것이 먼저 / 먼저 넣은 것이 먼저 |
| 해시 맵 / 집합 | 키와 값을 짝지음 / 키만 담아 있는지 없는지만 앎 |
| 인덱스 / ID | 지금 놓인 자리의 번호. 바뀜 / 대상에 붙은 고유 번호. 안 바뀜 |
| 트리 / 그래프 | 부모는 하나, 되돌아오는 길 없음 / 연결이 자유롭고 순환 가능 |

## 실전 사례 {#case}

::: {.case title="회원이 늘자 주문 목록 화면이 몇 초씩 멈춘다"}
주문 500건에 회원 이름을 붙여 보여 주는 화면입니다. 테스트할 때는 빨랐는데, 회원이 1만 명이 되자 열 때마다 멈칫합니다.

1. **반복 횟수를 셉니다.** 주문 하나마다 회원 배열을 처음부터 훑어 ID가 같은 회원을 찾고 있었습니다. 최악의 경우 500 × 10,000 = 500만 번을 비교합니다.
2. **그릇을 바꿉니다.** 회원 배열을 한 번 훑어 "회원 ID → 회원" 해시 맵을 만듭니다(1만 번). 그다음 주문마다 맵에서 바로 꺼냅니다(500번). 합쳐서 약 1만 500번입니다.
3. **빈틈을 정합니다.** 맵에 없는 회원 ID가 나오면 "알 수 없는 회원"으로 표시하고, 같은 ID가 두 번 나오면 오류로 기록합니다.
4. **확인합니다.** 바꾸기 전과 후의 화면 내용이 같은지 비교하고, 회원을 2만 명으로 늘려 시간과 메모리를 다시 잽니다.

그릇만 바꿨는데 비교가 500만 번에서 약 1만 번으로 줄었습니다. 대신 맵이 차지하는 메모리가 늘었습니다. 자료구조를 고르는 일은 언제나 이런 맞바꾸기입니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- **자료구조**는 데이터를 담는 그릇입니다. 가장 자주 하는 일에 맞춰 고릅니다.
- **배열**은 번호로 한 번에 꺼내지만 중간에 넣고 빼면 뒤를 모두 밉니다. **연결 리스트**는 그 반대입니다.
- **스택**은 나중에 넣은 것을, **큐**는 먼저 넣은 것을 먼저 꺼냅니다.
- **해시 맵**은 키를 계산해 칸을 정하므로 거의 한 번에 찾습니다. 키로는 이름이 아니라 **ID**를 씁니다.
- **이진 탐색 트리**는 절반씩 줄여 가며 찾고, **힙**은 가장 급한 것을 맨 위에 두고, **그래프**는 자유로운 연결을 담습니다.
- 내보낼 때는 JSON이 못 담는 것을 챙깁니다. 시각은 **UTC**로 저장하고, 글자는 **정규화**해서 비교합니다.
:::

## 확인 문제 {#quiz}

::: {.q}
AI 코딩 도구가 "배열을 전부 해시 맵으로 바꾸면 빨라집니다"라고 제안했습니다. 받아들이기 전에 무엇을 확인해야 할까요?

::: {.a}
그 데이터로 가장 자주 하는 일이 무엇인지입니다. 키로 반복해서 찾는다면 맵이 맞습니다. 순서대로 훑어 화면에 그리기만 한다면 배열로 충분하고, 맵은 메모리만 더 씁니다.
:::
:::

::: {.q}
대기 주문을 Python 리스트에 담고 `orders.pop(0)`으로 꺼냈더니, 주문이 몰릴 때 눈에 띄게 느려집니다. 이유와 고칠 방법은 무엇일까요?

::: {.a}
리스트는 배열이라서 맨 앞을 빼면 남은 값을 전부 한 칸씩 당깁니다. 양쪽 끝에서 빠르게 넣고 빼는 `deque`로 바꾸고 `popleft()`로 꺼냅니다.
:::
:::

::: {.q}
상품 목록에서 고른 상품을 인덱스로 기억해 두었습니다. 그사이 새 상품이 목록 맨 앞에 추가되자 장바구니에 다른 상품이 담겼습니다. 왜 그럴까요?

::: {.a}
앞에 하나가 끼어들면 모든 상품의 인덱스가 1씩 밀리기 때문입니다. 고른 상품은 바뀌지 않는 상품 ID로 기억해야 합니다.
:::
:::

::: {.q}
1부터 1000까지를 작은 수부터 차례로 이진 탐색 트리에 넣었습니다(균형 트리는 아닙니다). 1000을 찾으려면 비교를 몇 번쯤 해야 할까요?

::: {.a}
약 1000번입니다. 넣을 때마다 오른쪽 아래로만 이어져 한 줄짜리 사슬이 되기 때문입니다. 고르게 퍼진 트리였다면 열 번쯤이면 됩니다.
:::
:::

::: {.q}
회원 가입 시각을 "2026-11-07 09:00"이라는 글자로만 저장했습니다. 해외 사용자가 생기자 가입 순서가 뒤바뀌어 보입니다. 무엇이 빠졌을까요?

::: {.a}
어느 시간대의 9시인지가 빠졌습니다. 서울의 9시와 뉴욕의 9시는 다른 순간입니다. 저장할 때 UTC로 바꾸고, 화면에 보여 줄 때만 사용자의 시간대로 바꿉니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI 코딩 도구에게 "느려요, 빠르게 해 줘"라고만 하면 그릇을 마구 바꿔 놓기 쉽습니다. **지금 어떤 그릇에서 무엇을 몇 번 하는지**부터 설명하게 하세요.

> 주문 목록에 회원 이름을 붙이는 함수가 회원이 1만 명일 때 느려. 먼저 지금 코드가 비교를 몇 번 하는지 설명하고, 자료구조를 어떻게 바꿀지 제안해 줘. 조건: 출력 순서는 그대로 두고, 회원은 이름이 아니라 ID로 찾고, 없는 회원 ID는 '알 수 없는 회원'으로 표시해. 완료 기준: 작은 입력에서 바꾸기 전과 후의 결과가 같다는 테스트, 그리고 회원 1만 명과 2만 명일 때의 시간과 메모리 비교.

**받은 답에서 확인할 것**: 반복문 안에서 배열을 다시 뒤지는 곳이 남아 있지 않은가, 키가 이름이 아니라 ID인가, 없는 키와 중복 키를 처리했는가, 늘어난 메모리도 함께 보여 주는가.
:::

## 용어 정리 {#terms}

::: {.terms}
자료구조 (data structure)
:   데이터를 메모리에 늘어놓는 방식.

배열 (array)
:   같은 크기의 칸이 붙어 있는 그릇. 번호로 한 번에 꺼낸다.

인덱스 (index)
:   배열에서 칸의 자리 번호. 0부터 시작하며, 값이 밀리면 바뀐다.

연결 리스트 (linked list)
:   값과 다음 노드의 주소를 묶은 노드를 줄줄이 이은 그릇.

스택 (stack)
:   나중에 넣은 것을 먼저 꺼내는 그릇.

큐 (queue)
:   먼저 넣은 것을 먼저 꺼내는 그릇.

해시 맵 (hash map)
:   키와 값을 짝지어 담고 키로 바로 찾는 그릇. 딕셔너리.

해시 함수 (hash function)
:   키를 숫자로 바꿔 주는 계산. 이 숫자로 넣을 칸을 정한다.

집합 (set)
:   중복 없이 키만 담아 포함 여부를 답하는 그릇.

ID (identifier)
:   대상마다 하나씩 붙는, 겹치지 않고 바뀌지 않는 번호.

트리 (tree)
:   루트에서 아래로 갈라지는 그릇. 부모는 하나이고 순환이 없다.

이진 탐색 트리 (binary search tree)
:   왼쪽에 작은 값, 오른쪽에 큰 값을 두어 절반씩 줄여 가며 찾는 트리.

힙 (heap)
:   가장 급한 값을 항상 맨 위에 두는 트리. 우선순위 큐를 만든다.

그래프 (graph)
:   정점과 간선으로 대상 사이의 연결을 담는 그릇.

직렬화 (serialization)
:   메모리 안의 값을 저장하거나 보내려고 한 줄의 글자로 펴는 일.
:::
