::: {.lead}
혼자 하는 분식집은 주문도 받고 요리도 하고 계산도 혼자 합니다. 손님이 많아지면 일을 나눠야 합니다. 그런데 나누는 순간 새 문제가 생깁니다. 주문서가 주방에 전달되지 않거나, 같은 주문이 두 번 들어가기도 합니다. 프로그램도 커지면 여러 부분으로 나뉩니다. 이 장에서는 어떻게 나누고, 나눴을 때 생기는 문제를 어떻게 다루는지 배웁니다.
:::

::: {.goals}
- 큰 프로그램을 여러 부분으로 나누는 이유와 방법을 말할 수 있습니다.
- 부탁을 보냈는데 답이 오지 않으면 왜 곤란한지 설명할 수 있습니다.
- 같은 일이 두 번 처리되지 않게 하는 방법을 설명할 수 있습니다.
- 한 부분이 고장 나도 전체가 멈추지 않게 하는 방법을 알 수 있습니다.
- AI에게 설계를 한 장으로 받아 보고, 지금 필요 없는 것을 가려낼 수 있습니다.
:::

## 설계는 선을 긋는 일입니다 {#design}

분식집이 커지는 모습을 세 단계로 따라가 봅시다.

::: {.fig src="restaurant-growth.svg"}
식당이 커지는 세 단계와 프로그램이 커지는 세 단계. 오른쪽으로 갈수록 손님을 더 받지만, 일을 넘기는 방법이 달라지면서 새 숙제가 생깁니다.
:::

그림의 맨 윗줄이 식당입니다.

- **1인 식당.** 사장 혼자 다 합니다. 일을 넘길 필요가 없어서 어긋날 일도 없습니다. 다만 손님이 늘면 일이 뒤엉킵니다.
- **주방과 홀.** 손님을 맞는 사람과 요리하는 사람을 나눕니다. 이제 둘 사이에 **주문서**가 필요합니다. "떡볶이 2, 3번 자리"처럼 약속한 모양으로 적어야 합니다.
- **여러 지점.** 옆 동네에 가게를 하나 더 냅니다. 지점끼리는 **전화**로 일을 넘깁니다. 전화는 늦게 걸리기도 하고 끊기기도 합니다. 끊기면 상대가 내 말을 들었는지 모릅니다.

가운데 줄은 프로그램입니다. 그림의 "시스템"은 프로그램과 컴퓨터가 모여 함께 일하는 전체를 말합니다.

처음에는 프로그램 하나가 모든 일을 합니다. 일은 함수로 시킵니다. 함수는 이름을 붙여 둔 일 묶음이고, 부르면 바로 실행됩니다([초코딩 기초](code.html#function)).

프로그램이 커지면 안쪽을 구역(모듈)으로 나누고 정해진 창구로만 일을 넘깁니다. 더 커지면 프로그램을 여러 개(서비스)로 쪼개 서로 다른 컴퓨터에 둡니다. 이때는 컴퓨터를 잇는 길인 네트워크([14장](ch14.html))로 일을 넘깁니다. 식당의 전화와 같습니다.

맨 아랫줄은 단계마다 새로 생기는 숙제입니다. 혼자 하면 일이 뒤엉키고, 나누면 약속을 지켜야 합니다. 멀리 떨어지면 늦거나 끊기고, 일이 됐는지 모를 때도 생깁니다.

이제부터 가게 하나를 따라갑니다. 학교 동아리가 만든 머그컵을 파는 작은 인터넷 가게입니다. 컵은 12,000원이고 3개가 남아 있습니다. 손님이 "주문하기"를 누르면 가게 프로그램은 네 가지 일을 합니다.

1. **주문**을 적어 둡니다.
2. 12,000원을 받습니다. 이 일이 **결제**입니다.
3. 남은 컵을 3개에서 2개로 줄입니다. 남은 물건의 수가 **재고**입니다.
4. "주문 완료" **알림** 메일을 보냅니다.

이 일들을 어디서 나눌까요? 나눈 곳 사이에는 무엇을 약속할까요? 넘기다 실패하면 어떻게 할까요? 이것을 정하는 일이 **시스템 설계**(system design)입니다.

AI에게 "가게 앱 만들어 줘"라고만 하면 이 세 가지를 AI가 혼자 정합니다. 그래서 코드보다 설계를 먼저 [받아 봅니다](#review).

일을 나눈 자리는 **경계**(boundary)라고 부릅니다. 주방과 홀 사이가 경계입니다.

::: {.key}
좋은 설계는 잘게 많이 나눈 설계가 아닙니다. **알맞은 곳에 경계를 긋고, 경계마다 "실패하면 이렇게 한다"를 정해 둔** 설계입니다.
:::

## 모듈: 한 가게 안에서 구역 나누기 {#module}

학급 회비 장부를 아무나 고칠 수 있다고 해 봅시다. 어느 날 돈이 맞지 않습니다. 누가 틀리게 적었는지 아무도 모릅니다. 그래서 장부는 총무 한 명만 고치고, 다른 사람은 총무에게 부탁합니다.

프로그램도 같습니다. 주문에 관한 코드끼리, 재고에 관한 코드끼리 한데 묶습니다. 이렇게 묶은 코드 덩어리를 **모듈**(module)이라고 합니다. 묶는 기준은 "함께 바뀌는 것끼리"입니다.

머그컵 가게의 재고 모듈에는 **재고표**가 있습니다. 컵 3개, 접시 5개라고 적혀 있습니다.

::: {.fig src="coupling.svg"}
왼쪽은 주문 모듈과 관리 화면이 재고표를 직접 고칩니다. 오른쪽은 재고 모듈이 내놓은 창구로만 부탁합니다.
:::

그림 속 영어 글자는 **파이썬**(Python)이라는 프로그래밍 언어로 쓴 코드입니다. 코드를 처음 본다면 [초코딩 기초](code.html)를 먼저 보세요. 왼쪽부터 읽어 봅시다.

- `stock["컵"] -= 1`은 "재고표(`stock`)에서 컵의 숫자를 1 줄여라"입니다. 주문 모듈이 재고표를 직접 고칩니다.
- `stock["컵"] = 99`는 "컵의 숫자를 99로 바꿔라"입니다. 가게 주인이 쓰는 관리 화면도 재고표를 직접 고칩니다.

재고표를 아무나 고치고 있습니다. 오른쪽은 다릅니다. 재고 모듈이 **창구** 두 개를 내놓았습니다.

- `reserve("컵", 1)`은 "컵 1개를 잡아 주세요"라는 부탁입니다.
- `restock("컵", 96)`은 "컵 96개를 채워 주세요"라는 부탁입니다. 3 + 96 = 99이니 왼쪽과 결과가 같습니다.

이제 재고표를 고치는 것은 재고 모듈뿐입니다. 총무에게 부탁하는 것과 같습니다. 이런 창구가 [10장](ch10.html)에서 배운 인터페이스입니다.

무엇이 좋아질까요? "재고는 0보다 작아질 수 없다"는 규칙을 생각해 봅시다. 왼쪽에서는 재고표를 고치는 곳마다 규칙을 넣어야 합니다. 한 곳이라도 빠뜨리면 재고가 -1개가 됩니다. 오른쪽에서는 `reserve` 한 곳에만 넣으면 됩니다.

재고표의 모양(적는 방식)을 바꿀 때도 다릅니다. 왼쪽은 재고표를 만지던 두 곳이 함께 깨집니다. 오른쪽은 재고 모듈 안만 고치면 됩니다.

### 잘 나눴는지 보는 두 가지

모듈을 잘 나눴는지는 두 가지로 따집니다. 먼저 모듈 **안**을 봅니다.

필통에는 연필, 지우개, 자가 들어 있습니다. 모두 글씨를 쓰고 고치는 데 쓰는 물건입니다. 여기에 양말과 리모컨이 섞이면 필통이라고 부르기 어렵습니다. 한 모듈 안의 코드가 한 가지 일에 모여 있는 정도를 **응집도**(cohesion)라고 합니다. 높을수록 좋습니다.

다음은 모듈 **사이**를 봅니다. 남의 속을 많이 알수록, 그쪽이 바뀔 때 나도 함께 고쳐야 합니다. 다른 모듈의 속을 알아야 하는 정도를 **결합도**(coupling)라고 합니다. 낮을수록 좋습니다. 그림의 왼쪽은 결합도가 높고, 오른쪽은 낮습니다.

::: {.warn}
파일을 여러 개로 쪼갠다고 결합도가 낮아지지는 않습니다. 파일이 100개여도 서로의 속을 들여다보고 고치면 한 덩어리와 같습니다.
:::

### 층으로 쌓기: 화면, 규칙, 저장

모듈을 쌓는 흔한 방법이 있습니다. 분식집에는 손님을 맞는 홀, 요리하는 주방, 재료를 두는 창고가 있습니다. 손님은 홀에 말하고, 홀은 주방에 넘기고, 주방은 창고에서 재료를 꺼냅니다. 손님이 창고에 들어가는 일은 없습니다.

프로그램도 이렇게 세 층으로 나눕니다.

- **화면.** 버튼과 글자를 보여 주고 손님의 부탁을 받습니다. 홀입니다.
- **규칙.** "세 개 사면 10% 할인"처럼 가게가 정한 것을 따지고 계산합니다. 주방입니다.
- **저장.** 주문과 재고를 적어 두고 꺼내 옵니다. 창고입니다.

이렇게 나눈 층 하나하나를 **계층**(layer)이라고 합니다. 화면은 규칙을 부르고, 규칙은 저장을 부릅니다. 거꾸로는 부르지 않습니다.

할인 규칙 안에 버튼 이름이나 저장하는 방법이 섞여 있다고 해 봅시다. 버튼 하나를 바꿀 때마다 할인 규칙까지 고쳐야 합니다. 계층을 나눠 두면 화면을 바꿔도 규칙은 그대로입니다. 규칙만 따로 떼어 맞는지 시험하기도 쉽습니다.

브라우저로 여는 앱(웹 앱)에서는 세 층이 서로 다른 곳에서 돕니다. 화면 쪽을 프런트엔드, 서버 쪽을 백엔드라고도 부릅니다([31장](ch31.html#pieces)).

| 층 | 도는 곳 | 맡는 일 |
|---|---|---|
| 화면 | 손님의 브라우저나 휴대전화 | 보여 주고, 누른 것을 서버에 전한다 |
| 규칙 | 서버(늘 켜 두고 요청에 답하는 컴퓨터) | 값을 계산하고, 해도 되는 부탁인지 따진다 |
| 저장 | 데이터베이스 | 적어 두고 꺼내 준다 |

::: {.warn}
화면의 코드는 손님의 기기에서 돕니다. 그래서 손님이 고쳐서 보낼 수 있습니다. 화면이 보낸 "12,000원"을 서버가 그대로 믿으면 100원으로 고친 주문도 통과합니다. AI는 금액 계산을 화면 코드에만 넣을 때가 있습니다. "금액은 서버가 다시 계산해?" 하고 물어보세요([19장](ch19.html)).
:::

## 한 덩어리로 시작하기: 모놀리스와 마이크로서비스 {#monolith}

주방과 홀을 나눠도 식당은 한 건물입니다. 프로그램도 모듈로 나눈 뒤에 고를 것이 하나 더 있습니다. 전체를 **프로그램 하나**로 돌릴까요, **여러 프로그램**으로 쪼갤까요?

프로그램 하나로 묶어 돌리는 모양을 **모놀리스**(monolith)라고 합니다. 한 덩어리로 된 큰 돌이라는 뜻입니다.

기능마다 작은 프로그램으로 쪼갠 모양은 **마이크로서비스**(microservices)라고 합니다. 쪼갠 프로그램 하나하나가 **서비스**입니다. 서비스끼리는 네트워크로 일을 넘깁니다.

::: {.fig src="mono-vs-micro.svg"}
같은 주문 한 건. 왼쪽은 한 프로그램 안에서 함수를 세 번 부르고, 오른쪽은 네트워크 너머로 세 번 부릅니다.
:::

왼쪽부터 봅시다. 그림의 "호출"은 부른다는 뜻입니다. 주문이 결제, 재고, 알림을 차례로 부릅니다. 한 프로그램 안이라 빠릅니다. 정보를 보관하는 데이터베이스도 하나입니다. 데이터베이스는 줄여서 DB라고 부릅니다([17장](ch17.html)).

DB가 하나면 주문 적기, 결제 기록, 재고 줄이기를 **한 묶음**으로 처리할 수 있습니다. 17장에서 배운 트랜잭션입니다. 전부 되거나, 전부 안 되거나 둘 중 하나입니다. 재고가 모자라면 결제 기록까지 통째로 없던 일이 됩니다.

오른쪽은 서비스가 넷입니다. 주문, 결제, 재고 서비스는 DB를 하나씩 따로 가집니다. 알림 서비스는 메일을 보내는 일(발송)을 맡습니다. 이제는 한 묶음으로 처리할 수 없습니다. 결제는 됐는데 재고 줄이기만 실패할 수 있습니다. 그러면 환불 같은 일을 따로 해서 바로잡아야 합니다.

::: {.deep title="결제는 됐는데 컵이 없으면 어떻게 되돌릴까요?"}
결제 서비스는 이미 12,000원을 받았고, 그 기록은 결제 서비스의 DB에 있습니다. 다른 서비스가 트랜잭션으로 지울 수 없습니다.

그래서 지우는 대신 **반대로 하는 일**을 새로 합니다. 결제의 반대는 환불입니다. 앞에서 한 일을 이렇게 거꾸로 메우는 것을 **보상**(compensation)이라고 합니다.

보상은 지우개가 아닙니다. 통장에는 "결제 12,000원"과 "환불 12,000원" 두 줄이 남습니다.
:::

서비스 사이의 길도 문제입니다. 늦을 수 있고, 끊길 수 있고, 답이 사라질 수 있습니다.

프로그램이 하나여도 이 숙제를 모두 피하지는 못합니다. 실제 가게는 대개 돈 받는 일을 결제 회사에 맡깁니다. 남의 컴퓨터에서 끝난 결제는 내 DB의 트랜잭션으로 되돌릴 수 없습니다.

::: {.myth title="마이크로서비스가 더 발전된 구조다"}
마이크로서비스는 수십 팀이 일하는 큰 회사의 고민을 푸는 모양입니다. 몇 명이 만든다면 모놀리스가 대개 더 빨리 만들어지고 덜 고장 납니다. 먼저 한 프로그램 안에서 모듈을 잘 나눕니다. 따로 떼어야 할 부분이 정말 생기면 그것만 떼어 냅니다.
:::

## API는 약속입니다: 계약과 버전 {#contract}

주방과 홀이 나뉘면 주문서를 건네는 창구가 생깁니다. 프로그램 사이에도 이런 창구가 있습니다. 한 프로그램이 다른 프로그램에게 일을 부탁하는 창구를 **API**(Application Programming Interface)라고 합니다.

주문서에는 정해진 양식이 있습니다. API에도 지키기로 한 약속이 있습니다. 이 약속 전체가 **계약**(contract)입니다. 칸 이름만 약속하는 것이 아닙니다. "도착까지 30"이 30분인지 30초인지도 약속입니다.

계약은 바꾸기 어렵습니다. **양쪽을 한꺼번에 바꿀 수 없기** 때문입니다. 서버의 프로그램은 오늘이라도 바꿀 수 있습니다. 하지만 손님 휴대전화의 앱은 몇 달 전 것 그대로일 수 있습니다. 게임 업데이트를 미루는 친구가 꼭 있는 것과 같습니다.

::: {.fig src="contract-break.svg"}
세 가지 변경이 옛 앱에 미치는 영향. 칸 이름이 그대로여도 뜻이 바뀌면 옛 앱은 틀린 화면을 보여 줍니다.
:::

서버가 돌려주는 답을 응답이라고 합니다. 응답은 흔히 JSON([8장](ch08.html))이라는 방식으로 적습니다. `"칸 이름": 값` 꼴입니다. `"status":"paid"`는 "상태 칸의 값은 결제됨"이라는 뜻입니다. 그림의 세 줄을 위에서부터 봅시다.

1. **칸을 하나 더했습니다.** `"memo":"선물"`이라는 메모 칸이 생겼습니다. 옛 앱은 모르는 칸을 그냥 지나칩니다.
2. **단위를 바꿨습니다.** `eta`는 도착까지 남은 시간입니다. 30분이라는 뜻으로 `30`을 보내다가 초로 바꿔 `1800`을 보냅니다. 30 × 60 = 1800이니 같은 시간입니다. 하지만 옛 앱은 분으로 읽어서 "1800분 뒤 도착"을 보여 줍니다. 30시간입니다.
3. **새 값을 더했습니다.** 상태 칸에 취소됨(`cancelled`)이 생겼습니다. 옛 앱은 처음 보는 값을 어떻게 그릴지 몰라 화면이 멈춥니다.

그래서 세 가지를 지킵니다.

1. **칸을 더하는 것은 대체로 안전합니다.** 받는 쪽은 모르는 칸이나 값을 만나도 멈추지 않게 만듭니다.
2. **뜻은 바꾸지 않습니다.** 단위를 바꾸려면 `eta_seconds`(초로 적은 eta)처럼 새 칸을 만듭니다.
3. **크게 바꿀 때는 창구를 하나 더 엽니다.** 옛 창구는 쓰는 앱이 없어질 때까지 그대로 둡니다. 보통 주소에 번호를 넣어 구별합니다. `/v1/orders`(1번 주문 창구)는 그대로 두고 `/v2/orders`(2번)를 새로 여는 식입니다. 이렇게 창구에 번호를 붙여 함께 열어 두는 것을 **API 버전 관리**(API versioning)라고 합니다.

::: {.tip}
AI에게 서버를 고치게 하면 응답의 칸 이름이 바뀔 때가 있습니다. 화면은 옛 이름을 찾다가 빈칸이나 `undefined`라는 글자를 보여 줍니다. 미리 말해 둡니다. "응답의 칸 이름과 뜻은 바꾸지 마. 꼭 바꿔야 하면 그 칸을 쓰는 곳을 먼저 알려 줘."
:::

## 전화는 끊길 수 있습니다: 원격 호출과 멱등성 {#remote}

프로그램을 여러 서비스로 쪼개면 네트워크로 일을 넘깁니다. 프로그램이 하나뿐이어도 결제 회사, 지도, AI처럼 남이 운영하는 서비스를 빌려 쓰면 마찬가지입니다. 이렇게 다른 컴퓨터의 프로그램에게 일을 시키는 것을 **원격 호출**(remote call)이라고 합니다.

겉으로는 함수를 부르는 것과 똑같아 보입니다. 하지만 훨씬 느리고, 가는 길이 끊겨 실패하기도 합니다. 가장 까다로운 것은 **됐는지 안 됐는지 모를 때**가 있다는 점입니다.

주문 서비스가 결제 서비스에 "12,000원을 결제해 주세요" 하고 요청합니다. 결제 서비스 자리에 결제 회사를 놓아도 이야기는 같습니다. 답은 3초까지만 기다리기로 정해 두었습니다. [11장](ch11.html)에서 배운 시간 제한입니다.

3초를 기다렸는데 답이 없습니다. 정해 둔 시간 안에 답이 오지 않는 것을 **시간 초과**(timeout)라고 합니다. 오류 글에는 흔히 `timeout`이나 `timed out`이라고 찍힙니다.

::: {.note}
전화는 끊기면 "뚜뚜" 소리라도 납니다. 네트워크는 아무 신호 없이 조용할 때가 많습니다. 그래서 몇 초까지 기다릴지를 프로그램이 스스로 정해 둬야 합니다. 정해 두지 않으면 오지 않는 답을 끝없이 기다릴 수도 있습니다.
:::

::: {.fig src="lost-response.svg"}
시간 초과의 세 가지 속사정. 요청이 사라졌을 수도, 결제가 끝난 뒤 응답만 사라졌을 수도, 응답이 늦었을 뿐일 수도 있습니다.
:::

그림의 세 줄은 실제로 일어난 일이 서로 다릅니다.

1. 요청이 가다가 사라졌습니다. 결제는 **안 됐습니다.**
2. 결제 서비스가 12,000원을 승인했습니다. 돈을 받았다는 뜻입니다. 그런데 응답이 오다가 사라졌습니다. 결제는 **됐습니다.**
3. 결제 서비스가 바빠서 응답이 4초 뒤에 왔습니다. 주문 서비스는 3초에 이미 기다리기를 그만뒀습니다. 결제는 **됐습니다.**

주문 서비스의 눈에는 셋이 똑같습니다. 그래서 시간 초과는 "실패"가 아니라 **"모름"**입니다.

"실패했으니 다시 결제하자"고 하면 2번과 3번의 손님은 두 번 냅니다. 24,000원입니다. "실패했으니 주문을 취소하자"고 해도 곤란합니다. 돈은 나갔는데 컵은 오지 않습니다.

### 주문 번호를 불러 주세요

::: {.analogy title="끊긴 전화"}
전화로 머그컵을 주문하다가 전화가 끊겼습니다. 다시 걸어서 "머그컵 하나요"라고 하면 직원은 새 주문으로 받습니다. 컵이 두 개 올 수 있습니다. **"아까 42번 주문, 들어갔나요?"**라고 물어야 한 개만 옵니다.
:::

여러 번 해도 한 번 한 것과 결과가 같은 일이 있습니다. 엘리베이터 버튼은 열 번 눌러도 엘리베이터가 한 번 옵니다. 이런 성질을 **멱등성**(idempotency)이라고 합니다.

결제는 두 번 하면 돈이 두 번 나갑니다. 그래서 요청마다 하나뿐인 번호를 붙입니다. 이 번호가 **멱등 키**(idempotency key)입니다. 끊긴 전화의 "42번"입니다.

::: {.fig src="idempotency-key.svg"}
응답이 사라져서 같은 키로 다시 보냈습니다. 결제 서비스는 장부에서 `ord-42`를 찾아, 적어 둔 답만 돌려줍니다.
:::

그림의 번호를 따라갑시다. `POST /pay`는 "결제(pay) 창구로 보낸다(POST)"는 뜻입니다.

1. 주문 서비스가 `ord-42`라는 키를 붙여 결제를 요청합니다. 결제 서비스는 처음 본 키라서 결제합니다. 장부에는 "ord-42, 12,000원, 승인"이라고 적습니다.
2. "승인" 응답이 오다가 사라집니다.
3. 주문 서비스는 **같은 키**로 다시 보냅니다.
4. 결제 서비스는 장부에서 `ord-42`를 찾습니다. 이미 있는 키입니다. 결제는 하지 않고, 적어 둔 답 "승인"만 돌려줍니다. 장부에 둘째 줄은 생기지 않습니다.

결제는 한 번, 12,000원만 나갔습니다. 키가 없었다면 두 번, 24,000원이 나갔을 것입니다.

키는 **보내는 쪽**이 만들고, 다시 보낼 때 **같은 키**를 씁니다. 보낼 때마다 새 키를 만들면 소용이 없습니다. 손님이 정말로 두 번 주문했다면 키가 다르니 둘 다 처리됩니다.

많은 결제 회사의 API에는 이 키를 적는 자리가 있습니다. AI가 쓴 결제 코드에서 그 자리가 채워져 있는지 봅니다.

## 재시도가 불을 키울 때: 백오프와 차단기 {#retry}

멱등 키가 있으면 다시 보내도 안전합니다. 다시 보내는 것을 **재시도**(retry)라고 합니다. 그러면 될 때까지 마음껏 다시 보내도 될까요?

인기 가수의 공연 예매 날을 떠올려 봅시다. 접속이 안 된다고 모두가 새로고침을 누릅니다. 사이트는 더 느려집니다.

::: {.fig src="retry-storm.svg"}
앱도 3번, 주문 서비스도 3번씩 시도하면 결제 서비스는 9번을 받습니다.
:::

그림에서 주문은 1건입니다. 손님의 앱은 답이 없으면 3번까지 보냅니다. 주문 서비스도 요청 하나마다 결제 서비스에 3번까지 보냅니다. 3 × 3 = 9입니다. 주문 1건이 요청 9번으로 불어났습니다.

결제 서비스가 바빠서 느린 것이라면 어떨까요? 재시도가 일을 9배로 불려 회복을 막습니다. 그래서 규칙을 둡니다.

- **한 층에서만 합니다.** 앱, 주문 서비스처럼 요청이 거쳐 가는 단계를 여기서는 층이라고 합니다. 한 층만 재시도하면 1 × 3 = 3번에서 멈춥니다.
- **마감을 넘기지 않습니다.** 전체가 끝나야 하는 때가 [11장](ch11.html)에서 배운 마감입니다. 손님이 10초만 기다려 준다면, 10초가 지난 뒤에 다시 보내는 것은 쓸모가 없습니다.
- **간격을 늘립니다.** 1초 뒤, 2초 뒤, 4초 뒤처럼 기다리는 시간을 늘려 갑니다. 이 방법을 **백오프**(backoff)라고 합니다.
- **간격을 흩뜨립니다.** 모두가 똑같이 1초, 2초, 4초 뒤에 보내면 같은 순간에 또 몰립니다. 그래서 기다리는 시간에 그때그때 다른 값을 조금 섞습니다. 이것을 **지터**(jitter)라고 합니다.
- **될 것만 다시 보냅니다.** "돈이 모자랍니다"는 백 번 보내도 똑같습니다.

### 차단기: 그만 보내기

"그만 보내는" 규칙도 필요합니다. 집의 전기 차단기는 전기가 너무 많이 흐르면 스위치가 저절로 내려갑니다. 프로그램에도 같은 장치를 둡니다. 상대가 계속 실패하면 스위치를 내리고 한동안 요청을 보내지 않습니다. 이 장치를 **서킷 브레이커**(circuit breaker)라고 합니다. 영어로 차단기입니다.

시간이 조금 지나면 몇 건만 시험 삼아 보내 봅니다. 성공하면 스위치를 다시 올립니다.

머그컵 가게에서 다른 상품을 추천해 주는 서비스가 멈췄다고 합시다. 차단기를 내리고 추천 칸을 비워 둡니다. 추천을 기다리느라 주문 화면까지 느려지는 것보다 낫습니다.

### 남의 서비스를 부를 때 정할 네 가지

결제, 지도, AI 같은 남의 서비스는 내가 고칠 수 없습니다. 내가 정할 수 있는 것은 "안 될 때 내 앱이 어떻게 하나"뿐입니다. AI가 쓴 코드에는 이 부분이 자주 비어 있습니다. 부르는 곳마다 네 가지를 정하게 합니다.

| 정할 것 | 예 |
|---|---|
| 몇 초까지 기다리나 | 지도는 5초 |
| 안 되면 무엇을 보여 주나 | "지도를 불러오지 못했습니다"와 다시 시도 버튼 |
| 다시 보내도 되나 | 지도는 3번까지, 결제는 멱등 키가 있을 때만 |
| 없어도 나머지는 되나 | 지도가 안 떠도 주문은 된다 |

::: {.try}
AI와 만든 앱이 있다면 AI에게 물어보세요. "남의 서비스를 부르는 곳을 모두 찾아 표로 보여 줘. 곳마다 시간 제한, 실패했을 때 화면에 보이는 것, 다시 보내는 횟수를 적어 줘. 코드는 고치지 마." 빈칸이 있는 줄이 손볼 곳입니다.

앱이 없다면 AI 챗봇에게 물어보세요. "배달 앱이 빌려 쓸 만한 남의 서비스를 다섯 가지 알려 줘. 하나씩 멈추면 어디가 안 되는지도."
:::

## 지금 할까, 맡겨 둘까: 큐와 메시지 {#queue}

주문의 네 가지 일을 손님이 전부 기다릴 필요는 없습니다. 결제와 재고 확인은 그 자리에서 답해야 합니다. 하지만 알림 메일은 10초 뒤에 가도 괜찮습니다.

급하지 않은 일은 쪽지에 적어 줄에 꽂아 둡니다. 분식집의 주문서 꽂이를 떠올리면 됩니다. 홀 직원은 주문서를 꽂고 바로 다음 손님에게 갑니다. 요리사는 꽂힌 순서대로 뽑아 만듭니다.

프로그램에서는 이 쪽지를 메시지라고 합니다. 메시지가 차례를 기다리는 줄은 **메시지 큐**(message queue)입니다. 큐는 줄이라는 뜻입니다.

줄에서 메시지를 꺼내 일하는 프로그램은 **작업자**(worker)라고 부릅니다. 요리사의 자리입니다. 큐가 있으면 메일 보내는 쪽이 잠깐 멈춰도 주문은 계속 받습니다.

### 큐의 약속: 적어도 한 번

작업자는 일을 끝내면 큐에 "처리했습니다"라고 알립니다. 이 알림을 **확인 응답**(ack)이라고 합니다. 큐는 확인 응답을 받아야 메시지를 지웁니다.

그런데 작업자가 메일을 보낸 바로 뒤, 확인 응답을 보내기 전에 꺼졌습니다. 큐는 일이 끝났는지 모릅니다. 그래서 같은 메시지를 다시 내줍니다. 메일이 두 통 나갑니다. 결제의 응답이 사라졌을 때와 똑같은 일입니다.

많은 큐는 이렇게 약속합니다. "메시지를 잃어버리지는 않습니다. 하지만 **두 번 갈 수는 있습니다.**" 이 약속을 **적어도 한 번 전달**(at-least-once delivery)이라고 합니다.

받는 쪽이 할 일은 멱등 키 때와 같습니다. 처리한 메시지의 번호를 적어 둡니다. 적힌 번호가 또 오면 건너뜁니다.

큐가 없는 작은 앱도 이 약속을 만납니다. 결제 회사가 내 서버로 보내는 "결제 완료" 알림(웹훅, [15장](ch15.html))도 두 번 올 수 있습니다.

### 발행·구독과 실패 보관함

주문이 끝나면 재고도, 매출(판 돈) 통계도, 알림도 그 사실을 알아야 합니다. 주문 서비스가 셋을 하나씩 부르면 알릴 곳이 늘 때마다 코드를 고쳐야 합니다.

유튜브를 떠올려 봅시다. 채널에 새 영상이 올라오면 구독한 사람 모두에게 알림이 갑니다. 올린 사람은 구독자를 한 명씩 챙기지 않습니다.

주문 서비스도 "주문 완료" 소식을 내기만 합니다. 구독한 서비스들이 각자 한 부씩 받습니다. 소식을 내는 것을 발행이라고 해서, 이 방식을 **발행·구독**(publish-subscribe)이라고 합니다.

::: {.fig src="pubsub-dlq.svg"}
위: 소식 하나를 구독자 셋이 각자 받습니다. 아래: 세 번 해도 안 되는 43번 메시지는 실패 보관함으로 옮깁니다.
:::

그림의 위쪽을 봅시다. 소식에는 "주문 번호 42, 머그컵 1개, 12,000원"이 적혀 있습니다. 재고 서비스는 컵을 3개에서 2개로 줄입니다. 통계 서비스는 오늘 매출에 12,000원을 더합니다. 알림 서비스는 "주문 완료" 메일을 보냅니다.

아래쪽은 알림 서비스의 대기 줄입니다. 43번 메시지는 세 번을 해도 실패합니다. 메일 주소가 비어 있기 때문입니다. 계속 붙잡고 있으면 뒤에 선 44번, 45번이 밀립니다.

그래서 정해 둔 횟수만큼 실패한 메시지는 실패 보관함으로 옮깁니다. 영어로는 **DLQ**(Dead-Letter Queue)라고 합니다. 옮겼다고 해결된 것은 아닙니다. 보관함에 쌓이면 사람에게 알려 까닭을 찾게 합니다.

## 데이터의 주인은 하나: 소유권과 일관성 {#data}

회비 장부는 총무 한 명만 고쳤습니다. 서비스를 여럿으로 나눠도 같습니다. 컴퓨터에 담긴 정보를 데이터라고 하는데, **데이터마다 주인은 하나**입니다.

재고 숫자의 주인은 재고 서비스입니다. 재고 서비스만 그 숫자를 고칩니다. 다른 서비스는 창구(API)로 부탁하거나, 재고 서비스가 발행한 소식을 듣습니다.

주인이 아닌 쪽은 복사본, 곧 사본을 들고 있습니다. 상품 목록 화면의 "남은 수량 3개"는 재고 서비스에서 받아 적은 숫자입니다. 방금 컵이 팔렸어도 소식이 도착하기 전까지는 3개로 보입니다.

교실 게시판의 시간표와 같습니다. 선생님이 시간표를 바꿔도 게시판은 새로 붙이기 전까지 옛것입니다. 하지만 시간이 지나면 새것으로 바뀝니다. "잠깐은 다를 수 있지만 **결국에는** 같아진다"는 이 약속을 **최종 일관성**(eventual consistency)이라고 합니다.

목록의 남은 수량은 몇 초 늦어도 괜찮습니다. 하지만 결제 바로 앞의 재고 확인은 주인에게 직접 물어야 합니다.

### 연결이 끊기면: CAP

가게가 커져서 재고 장부를 서울과 부산의 서버에 한 벌씩 두었습니다. [17장](ch17.html)에서 배운 복제입니다.

어느 날 두 서버를 잇는 길이 끊겼습니다. 둘 다 켜져 있지만 서로 물어볼 수 없습니다. 이 상태를 **네트워크 분할**(partition)이라고 합니다.

::: {.fig src="cap-last-mug.svg"}
연결이 끊긴 동안 마지막 한 개를 두 손님이 주문했습니다. 둘 다 받으면 장부가 어긋나고, 장부를 지키려면 한쪽은 거절해야 합니다.
:::

머그컵은 1개 남았고, 두 서버의 장부에 똑같이 1이라고 적혀 있습니다. 손님 A는 서울 서버에, 손님 B는 부산 서버에 1개씩 주문합니다.

- **둘 다 주문을 받습니다.** 멈추지 않고 답하는 이 성질을 **가용성**(availability)이라고 합니다. 대신 1개뿐인 컵이 2개 팔렸습니다. 나중에 한 명에게 취소를 알려야 합니다.
- **한쪽은 주문을 멈춥니다.** 서울은 팔고 부산은 "주문 불가"라고 답합니다. 장부는 끝까지 맞습니다. 어디서 보든 값이 맞는 이 성질을 **일관성**(consistency)이라고 합니다. 대신 손님 B는 지금 살 수 없습니다.

연결이 끊긴 동안에는 둘 중 하나를 골라야 합니다. 이것을 **CAP 정리**라고 합니다. 일관성(C), 가용성(A), 분할(P)의 영어 첫 글자를 땄습니다.

연결이 멀쩡한 평소에는 둘을 함께 누립니다. 끊겼을 때도 데이터마다 다르게 고릅니다. 재고는 한쪽을 멈추고, 상품 후기는 조금 낡은 것이라도 보여 줍니다.

## 손님이 몰릴 때: 확장과 칸막이 {#scale}

더 많은 손님을 받도록 힘을 늘리는 것을 **확장**(scaling)이라고 합니다. 길은 둘입니다.

- **더 큰 것으로 바꿉니다.** 분식집이 가스불을 큰 것으로 바꾸는 셈입니다. 서버를 더 좋은 컴퓨터로 바꿉니다. 간단하지만 끝이 있습니다. 이 길이 **수직 확장**(scale up)입니다.
- **여러 대를 둡니다.** 요리사를 더 뽑는 셈입니다. 똑같은 서버를 여러 대 두고 요청을 나눠 받습니다. 이 길이 **수평 확장**(scale out)입니다.

여러 대를 두면 요청을 나눠 줄 안내원이 필요합니다. [14장](ch14.html)에서 만난 로드 밸런서입니다.

이때 조심할 것이 있습니다. 손님의 장바구니를 서버 한 대의 메모리에만 적어 두었다고 합시다. 다음 요청이 다른 서버로 가면 장바구니가 비어 보입니다. 그래서 서버들이 함께 알아야 하는 것은 DB처럼 모두가 함께 쓰는 곳에 둡니다.

서버가 한 대여도 조심합니다. 메모리에만 적어 둔 것은 서버를 껐다 켜면 사라집니다.

### 함께 쓰는 것에서 막힙니다

요리사를 4명에서 10명으로 늘려도 냉장고 문은 하나입니다. 다들 냉장고 앞에 줄을 섭니다. 전체를 느리게 만드는 이런 좁은 길목이 [1장](ch01.html)에서 본 병목입니다.

::: {.fig src="shared-bottleneck.svg"}
앱 서버 한 대가 DB 연결을 30개까지 엽니다. 10대로 늘리면 300개를 열려고 하지만 DB는 200개까지만 받습니다.
:::

그림의 앱 서버는 가게 프로그램을 돌리는 서버입니다. 앱 서버는 DB와 이야기할 통로를 엽니다. 이 통로가 연결입니다. 한 대가 30개까지 엽니다.

- 4대면 4 × 30 = 120개입니다. DB가 받을 수 있는 한도 200개 안에 듭니다.
- 10대면 10 × 30 = 300개를 열려고 합니다. DB는 200개까지만 받으니 100개는 거절됩니다.

느려서 서버를 늘렸는데 오히려 고장이 나는 까닭입니다. 이때 오류 글에는 `Too many connections` 같은 말이 보입니다. 요청이 몰리면 서버를 저절로 늘려 주는 곳([21장](ch21.html))에서도 같은 일이 생깁니다.

서버를 늘리기 전에 **모두가 함께 쓰는 것**의 한도를 먼저 봅니다.

::: {.deep title="DB도 여러 대로 늘릴 수 있을까요?"}
앱 서버는 똑같은 것을 여러 대 두면 됩니다. DB는 안에 데이터가 들어 있어서 그렇게 쉽지 않습니다. 길은 둘입니다.

첫째는 앞에서 본 복제입니다. 같은 데이터를 여러 벌 두고 읽는 일을 나눠 맡습니다.

둘째는 데이터를 여러 서버에 나눠 담는 **샤딩**(sharding)입니다. 반마다 출석부를 따로 두는 것과 같습니다. 대신 전체를 한꺼번에 보려면 서버를 모두 돌아야 합니다. DB 한 대로 버틸 수 있는 동안에는 꺼내지 않습니다.
:::

### 칸막이 치기: 벌크헤드

큰 배는 안쪽을 칸막이벽으로 나눕니다. 한 칸에 물이 들어와도 다른 칸으로 번지지 않습니다. 이 칸막이벽이 영어로 **벌크헤드**(bulkhead)입니다. 프로그램에서도 기능마다 쓸 몫을 나눠 두고 같은 이름으로 부릅니다.

가게의 DB 연결이 20개라고 합시다. 2분짜리 매출 보고서 20개를 한꺼번에 돌리면 연결이 모두 묶여 손님의 주문이 멈춥니다. 보고서가 쓸 연결을 2개로 정해 두면 주문은 계속됩니다.

## 설계를 받아 보고 시작하기 {#review}

집을 지을 때는 벽돌부터 쌓지 않습니다. 종이에 방을 먼저 그려 봅니다. 종이 위의 벽은 지우개로 옮기지만, 다 쌓은 벽은 부숴야 옮깁니다.

AI에게 앱을 맡길 때도 코드보다 설계를 먼저 받습니다. **글 한 장과 그림 하나**면 됩니다. 한 장에 다섯 가지가 있는지 봅니다.

1. 어떤 덩어리로 나누고 저마다 무엇을 맡나
2. 덩어리 사이에 무엇이 오가나(API 목록)
3. 무엇을 어떤 표에 적어 두나
4. 남의 서비스가 답하지 않으면 어떻게 하나
5. 지금은 일부러 만들지 않는 것은 무엇인가

::: {.fig src="design-sheet.svg"}
머그컵 가게의 설계 그림. 상자는 덩어리, 화살표는 부탁이 가는 길입니다. 위는 내가 만드는 것, 아래는 빌려 쓰는 남의 서비스입니다.
:::

아래로 내려가는 화살표 옆에는 답이 없을 때의 규칙이 적혀 있습니다. 받은 그림에 이런 글이 없으면 채워 달라고 합니다.

### 지금 필요한 것만 남깁니다

AI는 하루 주문 30건인 가게에도 큰 회사에서나 쓸 구조를 권할 때가 있습니다. 설계에 아래 낱말이 보이면 "이것을 빼면 지금 무슨 일이 생겨?" 하고 묻습니다. 답이 "나중에 손님이 늘면"으로 시작하면 빼고 시작합니다.

| AI가 권한 것 | 정말 필요해지는 때 |
|---|---|
| 서비스 여러 개 | 만드는 팀이 여럿으로 나뉠 때 |
| 메시지 큐 | 손님을 오래 세워 두는 긴 일이 생길 때 |
| 캐시(가까이 둔 사본) | 재 보니 같은 것을 되풀이해 읽느라 느릴 때 |

::: {.try}
AI 챗봇에게 "중고 책 나눔 앱을 설계해 줘. 코드는 쓰지 마."라고 해 보세요. 답에 나온 덩어리가 몇 개인지 셉니다. 이어서 "쓰는 사람은 우리 반 30명뿐이야. 지금 없어도 되는 것을 빼 줘."라고 합니다. 몇 개가 남나요?
:::

### 바꾸기 어려운 결정부터 따집니다

모든 결정을 처음부터 꼼꼼히 할 필요는 없습니다. 나중에 바꾸기 어려운 것만 먼저 따집니다.

| 나중에 바꾸기 어렵다 | 나중에 바꾸기 쉽다 |
|---|---|
| 데이터 구조(어떤 표에 무엇을 적나) | 색, 글꼴, 화면 배치 |
| 로그인 방식 | 안내 글, 버튼 이름 |
| 밖에 열어 둔 API의 칸 이름과 뜻 | 서버를 더 큰 것으로 바꾸는 일 |

왼쪽에는 **이미 쌓인 데이터**나 **이미 쓰고 있는 사람**이 걸려 있습니다. 표의 모양을 바꾸려면 적어 둔 주문을 모두 새 모양으로 옮겨야 합니다. 로그인 방식을 바꾸면 가입한 사람들이 다시 가입해야 할 수도 있습니다. 왼쪽은 만들기 전에 AI와 충분히 따지고, 오른쪽은 일단 만들고 고칩니다.

설계를 받은 뒤 작게 나눠 시키는 순서는 [30장](ch30.html#plan)에서 이어집니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 모듈 / 서비스 | 한 프로그램 안의 구역 / 따로 도는 프로그램 |
| 응집도 / 결합도 | 모듈 안이 한 가지 일에 모인 정도 / 다른 모듈의 속을 알아야 하는 정도 |
| 시간 초과 / 실패 | 됐는지 모름 / 안 된 것이 확실함 |
| 재시도 / 서킷 브레이커 | 다시 보낸다 / 한동안 보내지 않는다 |
| 수직 확장 / 수평 확장 | 더 큰 한 대로 바꾼다 / 같은 것을 여러 대 둔다 |
| 복제 / 샤딩 | 같은 데이터를 여러 벌 둔다 / 데이터를 나눠서 한 벌씩 둔다 |

## 실전 사례 {#case}

::: {.case title="보고서 하나 때문에 가게 전체가 느려진다"}
머그컵 가게 주인이 "이번 달 매출 보고서" 버튼을 누르면 계산에 2분이 걸립니다. 그동안 손님 화면까지 느려집니다. 새로고침을 누르면 계산이 하나 더 시작됩니다. AI는 "서비스 여덟 개로 쪼개자"고 합니다.

1. **무엇을 붙잡고 있는지 봅니다.** 보고서 하나가 DB 연결 하나를 2분 동안 붙잡습니다. 새로고침 다섯 번이면 연결 다섯 개입니다.
2. **받는 일과 하는 일을 나눕니다.** 버튼을 누르면 할 일을 큐에 넣고 번호표만 돌려줍니다. 계산은 작업자가 뒤에서 합니다.
3. **같은 부탁을 알아봅니다.** 같은 사람이 같은 달을 부탁하면 같은 멱등 키로 봅니다. 새로 계산하지 않고 하던 일의 번호표를 다시 줍니다.
4. **칸막이를 칩니다.** 보고서 작업자는 한 번에 2개만 계산합니다.

여덟 개로 쪼갤 필요는 없었습니다. 작업자 하나를 떼어 내는 것으로 충분했습니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- 설계는 **경계를 긋고, 경계마다 약속과 실패했을 때의 규칙을 정하는 일**입니다.
- 모듈은 함께 바뀌는 것끼리 묶고, 남의 속은 창구로 부탁해서 고칩니다. **응집도**는 높게, **결합도**는 낮게 합니다.
- 화면, 규칙, 저장을 **계층**으로 나눕니다. 금액 같은 규칙은 화면이 아니라 서버가 따집니다.
- 처음에는 프로그램 하나로 시작하고, 꼭 필요한 부분만 나중에 떼어 냅니다.
- API는 **계약**입니다. 뜻을 바꾸면 옛 앱이 틀린 화면을 보여 줍니다.
- 시간 초과는 실패가 아니라 **모름**입니다. **멱등 키**가 있어야 안심하고 다시 보냅니다.
- 재시도는 한 층에서만, 마감 안에서, 간격을 늘리고 흩뜨려 가며 합니다. 계속 실패하면 차단기를 내립니다.
- 남의 서비스를 부르는 곳마다 기다릴 시간, 안 될 때 보여 줄 것, 다시 보낼지를 정해 둡니다.
- 큐는 메시지를 **적어도 한 번** 전합니다. 받는 쪽은 두 번 올 때를 대비합니다.
- 데이터의 주인은 하나입니다. 서버를 늘리기 전에 함께 쓰는 것의 한도를 봅니다.
- 코드보다 **설계 한 장**을 먼저 받습니다. 데이터 구조처럼 바꾸기 어려운 결정부터 따집니다.
:::

## 확인 문제 {#quiz}

배달 앱에서 "결제하기"를 눌렀는데 "시간이 초과되었습니다"라고 나옵니다. 결제가 안 됐다고 믿고 새 주문으로 다시 결제해도 될까요?

::: {.a}
안 됩니다. 시간 초과는 "모름"입니다. 결제는 끝났는데 답만 못 받았을 수 있습니다. 새 주문으로 보내면 돈이 한 번 더 나갑니다. 앱은 처음과 같은 멱등 키로 다시 보내야 합니다.
:::
:::

::: {.q}
친구와 둘이서 동아리 물건을 파는 가게 프로그램을 만듭니다. AI가 "처음부터 서비스 여섯 개로 쪼개자"고 합니다. 무엇을 되물어야 할까요?

::: {.a}
왜 지금 쪼개야 하는지 숫자로 보여 달라고 합니다. 쪼개면 넘기다 실패하는 일을 떠안습니다. 둘이서 만든다면 프로그램 하나에서 모듈만 잘 나눠도 됩니다.
:::
:::

::: {.q}
학교 건강 기록 프로그램이 몸무게 칸 `weight`의 단위를 kg에서 g으로 바꾸려 합니다. 칸 이름은 그대로 둡니다. 옛 화면을 쓰는 사람에게는 무슨 일이 생길까요?

::: {.a}
45kg인 학생의 값이 45에서 45000으로 바뀝니다. 옛 화면은 이것을 45000kg으로 읽습니다. 이름이 같아도 뜻이 바뀌면 계약이 바뀐 것입니다. `weight_g` 같은 새 칸을 더하고 옛 칸은 그대로 둡니다.
:::
:::

::: {.q}
인터넷 서점에서 책을 한 권 샀는데 똑같은 "주문 완료" 메일이 두 통 왔습니다. 서점의 큐가 고장 난 것일까요?

::: {.a}
아닙니다. 적어도 한 번 전달하는 큐에서는 생길 수 있는 일입니다. 작업자가 메일을 보낸 뒤 "처리했습니다"라고 알리기 전에 꺼지면, 큐는 같은 메시지를 다시 내줍니다. 작업자가 처리한 번호를 적어 두고 건너뛰어야 합니다.
:::
:::

::: {.q}
AI와 독서 기록 앱을 만들기 시작합니다. 버튼 색, 책과 독후감을 적어 둘 표의 모양, 로그인 방식, 첫 화면의 인사말을 정해야 합니다. 만들기 전에 AI와 꼼꼼히 따져야 할 것은 어느 것일까요?

::: {.a}
표의 모양과 로그인 방식입니다. 독후감이 쌓인 뒤에 표를 바꾸려면 적어 둔 것을 모두 옮겨야 합니다. 로그인 방식을 바꾸면 가입한 친구들이 다시 가입해야 할 수 있습니다. 버튼 색과 인사말은 언제든 고치면 됩니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI는 잘될 때의 흐름을 빠르게 그려 줍니다. 넘기다 실패했을 때의 규칙과 지금은 없어도 되는 것은 따로 물어야 나옵니다. 코드보다 설계를 먼저 받습니다.

> 머그컵을 파는 작은 인터넷 가게를 만들려고 해. 만드는 사람은 2명이고 주문은 하루 30건쯤이야. 코드는 아직 쓰지 말고 설계를 한 장으로 써 줘.
>
> 1. 화면, 서버, 데이터베이스가 맡는 일과 API 목록. 상자와 화살표 그림도 하나 그려 줘.
> 2. 데이터베이스의 표와 칸
> 3. 결제처럼 남의 서비스를 부르는 곳마다 몇 초를 기다리는지, 답이 없으면 결과를 어떻게 확인하는지, 멱등 키를 누가 만드는지
> 4. 지금은 만들지 않을 것과 그 까닭
>
> 나중에 바꾸기 어려운 결정에는 표시를 해 줘.

**받은 답에서 확인할 것**

- 프로그램 하나로 시작하는가. 쪼개자고 한다면 까닭이 유행이 아니라 숫자인가.
- 금액과 재고 같은 규칙을 화면이 아니라 서버가 따지는가.
- 남의 서비스를 부르는 곳마다 시간 제한과 안 될 때 할 일이 적혀 있는가.
- 시간 초과를 실패로 못 박지 않고, 다시 보낼 때 같은 키를 쓰는가.

**AI가 자주 하는 실수**

- 작은 앱에 서비스 여러 개, 큐, 캐시를 처음부터 넣습니다. "이것을 빼면 지금 무슨 일이 생겨?"라고 물어봅니다.
- 남의 서비스가 늘 답한다고 보고 코드를 씁니다. 내 컴퓨터에서 돌리면서 인터넷을 끊고 눌러 보면 드러납니다.
- 횟수도 간격도 정하지 않고 다시 보냅니다. 결제처럼 두 번 되면 안 되는 일도 그렇게 합니다.
- 주문을 서버의 메모리에만 담아 둡니다. 서버를 껐다 켠 뒤에도 주문이 남아 있는지 봅니다.
:::

## 용어 정리 {#terms}

::: {.terms}
시스템 설계 (system design)
:   일을 어디서 나누고, 무엇을 약속하고, 실패하면 어떻게 할지 정하는 일.

경계 (boundary)
:   일을 나눈 자리.

모듈 (module)
:   관련된 일을 묶고 창구만 밖에 내놓은 코드 덩어리.

응집도 (cohesion)
:   한 모듈 안의 코드가 한 가지 일에 모여 있는 정도. 높을수록 좋다.

결합도 (coupling)
:   다른 모듈의 속을 알아야 하는 정도. 낮을수록 좋다.

계층 (layer)
:   화면, 규칙, 저장처럼 맡은 일에 따라 나눈 층.

모놀리스 (monolith)
:   모든 기능을 프로그램 하나로 묶어 돌리는 모양.

마이크로서비스 (microservices)
:   기능마다 작은 프로그램으로 쪼개고 네트워크로 일을 넘기는 모양.

서비스 (service)
:   따로 도는 프로그램. 내가 만든 것도, 남이 빌려주는 것도 이렇게 부른다.

보상 (compensation)
:   이미 끝난 일을 환불처럼 반대되는 일로 메우는 것.

API (Application Programming Interface)
:   한 프로그램이 다른 프로그램에게 일을 부탁하는 창구.

계약 (contract)
:   API에서 지키기로 한 약속 전체.

API 버전 관리 (API versioning)
:   창구에 번호를 붙여 옛것과 새것을 함께 열어 두는 것.

원격 호출 (remote call)
:   다른 컴퓨터의 프로그램에게 네트워크로 일을 시키는 것.

시간 초과 (timeout)
:   정해 둔 시간 안에 답이 오지 않는 것. 실패가 아니라 "모름"이다.

멱등성 (idempotency)
:   여러 번 해도 한 번 한 것과 결과가 같은 성질.

멱등 키 (idempotency key)
:   같은 요청임을 알아보도록 요청에 붙이는 하나뿐인 번호.

재시도 (retry)
:   답을 받지 못한 요청을 다시 보내는 것.

백오프 (backoff)
:   다시 보낼 때마다 기다리는 시간을 늘려 가는 방법.

지터 (jitter)
:   다시 보내는 때가 겹치지 않게 기다리는 시간을 조금씩 흩뜨리는 것.

서킷 브레이커 (circuit breaker)
:   계속 실패하는 상대에게 한동안 요청을 보내지 않는 장치.

메시지 큐 (message queue)
:   할 일을 적은 메시지가 차례를 기다리는 줄.

작업자 (worker)
:   큐에서 메시지를 꺼내 일하는 프로그램.

확인 응답 (ack)
:   일을 끝낸 작업자가 큐에 보내는 "처리했습니다" 알림.

적어도 한 번 전달 (at-least-once delivery)
:   메시지를 잃지는 않지만 두 번 전할 수는 있다는 큐의 약속.

발행·구독 (publish-subscribe)
:   소식 하나를 구독한 쪽들이 각자 한 부씩 받는 방식.

DLQ (Dead-Letter Queue)
:   거듭 실패한 메시지를 따로 옮겨 두는 실패 보관함.

최종 일관성 (eventual consistency)
:   잠깐은 달라도 시간이 지나면 사본이 원본과 같아진다는 약속.

네트워크 분할 (partition)
:   서버들은 켜져 있지만 사이의 길이 끊겨 서로 물어볼 수 없는 상태.

가용성 (availability)
:   멈추지 않고 답해 주는 성질.

일관성 (consistency)
:   어디서 보든 값이 맞는 성질.

CAP 정리 (CAP theorem)
:   연결이 끊긴 동안에는 일관성과 가용성을 둘 다 가질 수 없다는 정리.

확장 (scaling)
:   더 많은 손님을 받도록 힘을 늘리는 것.

수직 확장 (scale up)
:   서버를 더 큰 한 대로 바꿔 힘을 늘리는 것.

수평 확장 (scale out)
:   똑같은 서버를 여러 대 두어 힘을 늘리는 것.

샤딩 (sharding)
:   데이터를 여러 서버에 나눠 담는 것.

벌크헤드 (bulkhead)
:   기능마다 쓸 몫을 나눠, 한 곳의 문제가 번지지 않게 하는 방법.
:::
