::: {.lead}
혼자 하는 분식집은 주문도 받고 요리도 하고 계산도 혼자 합니다. 손님이 많아지면 일을 나눠야 합니다. 그런데 나누는 순간 새 문제가 생깁니다. 주문서가 주방에 전달되지 않거나, 같은 주문이 두 번 들어가기도 합니다. 프로그램도 커지면 여러 부분으로 나뉩니다. 이 장에서는 어떻게 나누고, 나눴을 때 생기는 문제를 어떻게 다루는지 배웁니다.
:::

::: {.goals}
- 큰 프로그램을 여러 부분으로 나누는 이유와 방법을 말할 수 있습니다.
- 부탁을 보냈는데 답이 오지 않으면 왜 곤란한지 설명할 수 있습니다.
- 같은 일이 두 번 처리되지 않게 하는 방법을 설명할 수 있습니다.
- 한 부분이 고장 나도 전체가 멈추지 않게 하는 방법을 알 수 있습니다.
:::

## 설계는 선을 긋는 일입니다 {#design}

이 장에서는 머그컵을 파는 작은 온라인 가게를 따라갑니다. 손님이 "주문하기"를 누르면 네 가지 일이 일어납니다. **주문**을 기록하고, 12,000원을 **결제**하고, **재고**를 3개에서 2개로 줄이고, **알림** 메일을 보냅니다.

이 가게의 시스템은 식당처럼 자랍니다.

::: {.fig src="restaurant-growth.svg"}
식당이 커지는 세 단계와 시스템의 세 모양. 오른쪽으로 갈수록 손님을 더 받지만, 일을 넘기는 방법이 달라지면서 새 숙제가 생깁니다.
:::

1인 식당에서는 사장이 주문을 받고, 계산하고, 요리합니다. 일을 넘길 필요가 없으니 빠르고 어긋날 일도 없습니다. 손님이 늘어 주방과 홀을 나누면 **주문서**라는 약속이 필요해집니다. 지점까지 내면 **전화**로 일을 넘겨야 하는데, 전화는 늦게 연결되고, 끊기고, 상대가 들었는지 확신할 수 없습니다.

**시스템 설계**(system design)는 일을 어디서 나누고, 나뉜 곳 사이에 무엇을 약속하며, 넘기다 실패하면 어떻게 할지를 정하는 일입니다. 일을 나눈 자리를 **경계**(boundary)라고 부릅니다.

::: {.key}
좋은 설계는 상자가 많은 설계가 아닙니다. **경계가 알맞은 곳에 있고, 경계마다 실패했을 때의 규칙이 정해져 있는** 설계입니다.
:::

## 모듈: 한 가게 안에서 구역 나누기 {#module}

1인 식당도 장사가 잘되면 직원을 뽑습니다. 이때 계산대 직원이 창고에 들어가 재고 장부를 직접 고치기 시작하면, 장부가 왜 틀렸는지 아무도 모르게 됩니다.

코드도 같습니다. 관련된 일을 한데 묶고 밖에서 쓸 **창구**만 내놓은 코드 덩어리를 **모듈**(module)이라고 합니다. 창구는 [10장](ch10.html)에서 배운 인터페이스입니다. 모듈을 잘 나눴는지는 두 낱말로 따집니다.

- **응집도**(cohesion): 한 모듈 안의 코드가 한 가지 목적에 모여 있는 정도. 높을수록 좋습니다.
- **결합도**(coupling): 다른 모듈의 속사정을 알아야 하는 정도. 낮을수록 좋습니다.

::: {.fig src="coupling.svg"}
왼쪽은 주문 모듈과 관리 화면이 재고표를 직접 고칩니다. 오른쪽은 재고 모듈이 내놓은 창구 함수만 부릅니다.
:::

왼쪽에서 재고표 모양을 바꾸면 재고표를 만지는 코드를 전부 찾아 고쳐야 합니다. "재고는 0 아래로 내려갈 수 없다"는 규칙도 두 군데에 따로 넣어야 합니다. 오른쪽에서는 `reserve` 함수 한 곳에만 넣으면 됩니다.

::: {.warn}
파일을 여러 개로 쪼갠다고 결합도가 낮아지지는 않습니다. 파일이 100개여도 서로의 속을 들여다보면 한 덩어리입니다. 나누는 기준은 **"함께 바뀌는 것끼리 묶는다"**입니다.
:::

::: {.try}
내 프로젝트에서 DB 표 이름 하나(예: `orders`)를 전체 검색해 보세요. 그 표를 고치는 코드가 몇 개 파일에 흩어져 있나요? 여러 곳이라면 창구가 없다는 신호입니다.
:::

### 계층과 의존 방향

모듈을 쌓는 흔한 방법은 **계층**(layer)입니다. 홀(화면과 요청 받기), 주방(업무 규칙), 창고(DB 저장)로 층을 나누고, 손님 쪽 층이 안쪽 층을 부르게 합니다.

어떤 코드가 다른 코드를 알아야만 동작할 때 "**의존**한다"고 말합니다. 중요한 것은 방향입니다. "세 개 사면 10% 할인"이라는 가격 규칙이 버튼 이름이나 DB 종류에 의존하면, 화면이나 DB를 바꿀 때마다 규칙까지 고쳐야 합니다. 규칙은 "저장해 달라"는 창구만 알게 합니다. 그러면 DB 없이 규칙만 따로 시험할 수 있고, DB를 바꿔도 규칙은 그대로입니다.

::: {.deep title="포트와 어댑터: 규칙이 바깥을 모르게 하는 방법"}
주문 규칙이 "재고를 잡아 둔다"는 일을 시켜야 한다면, 규칙 쪽에서 필요한 창구의 모양만 정해 둡니다. `reserve(상품, 수량)` 같은 것입니다. 이것이 **포트**(port)입니다. 실제 DB에 SQL을 보내는 코드는 그 모양에 맞춰 따로 만들어 끼웁니다. 이것이 **어댑터**(adapter)입니다. 콘센트 규격과 플러그의 관계입니다.

시험할 때는 "재고 부족"을 흉내 내는 가짜 어댑터를 끼울 수 있습니다. 다만 가짜로 통과했다고 진짜 DB에서도 맞는 것은 아니므로 실제 어댑터도 따로 시험합니다. 단순한 기능에까지 이런 층을 둘 필요는 없습니다.
:::

## 한 덩어리로 시작하기: 모놀리스와 마이크로서비스 {#monolith}

모듈을 나누는 것과, 그것을 **한 프로그램으로 내보낼지 여러 프로그램으로 쪼갤지**는 별개의 결정입니다.

- **모놀리스**(monolith): 모든 기능을 한 프로그램으로 묶어 한 번에 배포하는 구조입니다. 배포는 새 버전을 서버에 올려 돌리는 일입니다([20장](ch20.html)). 안이 모듈로 잘 나뉘어 있으면 모듈형 모놀리스라고 합니다.
- **마이크로서비스**(microservices): 기능마다 따로 실행되는 작은 프로그램(**서비스**)으로 나누고, 네트워크로 서로 부르는 구조입니다.

::: {.fig src="mono-vs-micro.svg"}
같은 주문 한 건. 왼쪽은 한 프로그램 안에서 함수를 세 번 부르고, 오른쪽은 네트워크 너머로 세 번 부릅니다.
:::

왼쪽에서는 주문 기록, 결제, 재고 차감을 [17장](ch17.html)의 트랜잭션 하나로 묶을 수 있습니다. 재고가 모자라면 전부 없던 일이 됩니다. 오른쪽은 서비스마다 DB가 따로라서 그렇게 묶을 수 없습니다. 결제는 됐는데 재고 차감만 실패한 **어중간한 상태**가 생기고, 이를 수습하는 코드를 직접 짜야 합니다.

| 구조 | 얻는 것 | 떠안는 것 |
|---|---|---|
| 모듈형 모놀리스 | 단순한 배포, 빠른 호출, 트랜잭션 하나 | 안쪽 경계를 스스로 지키기 |
| 모놀리스 + 작업자 | 오래 걸리는 일만 떼어 따로 늘리기 | 큐, 작업 상태, 중복 처리 |
| 마이크로서비스 | 팀마다 따로 배포, 기능마다 따로 확장 | 네트워크 호출의 실패, 버전 맞추기, 데이터 맞추기 |

가운데 줄의 **작업자**(worker)는 오래 걸리는 일만 넘겨받아 뒤에서 처리하는 별도 프로그램입니다.

::: {.myth title="마이크로서비스가 더 발전된 구조다"}
마이크로서비스는 "여러 팀이 서로 기다리지 않고 배포해야 한다", "이 기능만 부하가 유독 크다" 같은 구체적인 문제를 푸는 구조입니다. 혼자 또는 몇 명이 만든다면 모놀리스가 더 빠르고 안전합니다. 모놀리스는 "배포 단위가 하나"라는 뜻이지 "코드가 엉켜 있다"는 뜻이 아닙니다. 모듈 경계를 먼저 긋고, 따로 늘려야 할 부분이 실제로 생기면 그것만 떼어 냅니다.
:::

## API는 약속입니다: 계약과 버전 {#contract}

주방과 홀이 나뉘면 주문서 양식이 생깁니다. 프로그램 사이의 창구가 **API**(Application Programming Interface)이고, 주문서 양식처럼 그 창구에서 지키기로 한 약속 전체가 **계약**(contract)입니다.

계약에는 칸 이름만 있는 것이 아닙니다.

- **뜻과 단위**: 도착 예정 시간 `eta`는 분인가 초인가.
- **실패**: 재고가 없을 때 어떤 오류를 돌려주는가.
- **완료 시점**: "성공"은 결제까지 끝났다는 뜻인가, 접수만 했다는 뜻인가.

계약을 바꾸기 어려운 까닭은 **양쪽을 동시에 바꿀 수 없기** 때문입니다. 서버는 오늘 새로 배포해도, 손님 휴대전화의 앱은 몇 달 전 버전일 수 있습니다.

::: {.fig src="contract-break.svg"}
세 가지 변경이 옛 앱에 미치는 영향. 칸 이름이 그대로여도 뜻이 바뀌면 깨지는 변경입니다.
:::

그래서 세 가지 규칙을 따릅니다.

1. **더하는 변경은 대체로 안전합니다.** 받는 쪽은 모르는 칸이나 값을 만나도 멈추지 않게 만들어 둡니다.
2. **뜻은 바꾸지 않습니다.** 단위를 바꾸고 싶으면 `eta_seconds`처럼 새 칸을 만듭니다.
3. **크게 바꿀 때는 버전을 나눕니다.** `/v1/orders`를 그대로 둔 채 `/v2/orders`를 열고, 옛 버전을 쓰는 곳이 없어진 것을 확인한 뒤 닫습니다. 이것이 **버전 관리**(versioning)입니다.

## 전화는 끊길 수 있습니다: 원격 호출과 멱등성 {#remote}

지점이 생기면 일을 전화로 넘깁니다. 프로그램이 네트워크 너머의 다른 프로그램에 일을 시키는 것을 **원격 호출**(remote call)이라고 합니다. 코드에서는 `pay(order)` 한 줄이라 함수 호출과 똑같아 보이지만 세 가지가 다릅니다.

1. **느립니다.** [1장](ch01.html)의 속도 사다리에서 함수 호출은 맨 위쪽, 원격 호출은 맨 아래쪽의 일입니다.
2. **실패합니다.** 상대가 꺼져 있거나 가는 길이 끊길 수 있습니다.
3. **됐는지 안 됐는지 모를 때가 있습니다.** 가장 까다로운 차이입니다.

주문 서비스가 결제 서비스에 12,000원 결제를 요청하고 3초를 기다렸는데 답이 없습니다.

::: {.fig src="lost-response.svg"}
시간 초과의 세 가지 속사정. 요청이 사라졌을 수도, 결제가 끝난 뒤 응답만 사라졌을 수도, 응답이 늦었을 뿐일 수도 있습니다.
:::

[11장](ch11.html)에서 본 대로 시간 초과는 "실패"가 아니라 **"모름"**입니다. 여기서 "실패했으니 다시 결제"하면 2번과 3번 경우의 손님은 24,000원을 냅니다. "실패했으니 주문 취소"라고 처리해도 돈은 이미 빠져나갔습니다.

::: {.note}
전화는 끊기면 신호음이라도 납니다. 네트워크는 그런 신호도 없이 조용할 때가 많습니다. 그래서 얼마나 기다릴지를 프로그램이 스스로 정해야 합니다.
:::

### 주문 번호를 불러 주세요

::: {.analogy title="끊긴 전화"}
주문하던 전화가 끊겼습니다. 다시 걸어 "머그컵 하나요"라고 하면 직원은 새 주문으로 받습니다. **"아까 42번 주문, 들어갔나요?"**라고 물어야 한 개만 옵니다.
:::

같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질을 **멱등성**(idempotency)이라고 합니다. 엘리베이터 버튼이 그렇습니다. 열 번 눌러도 엘리베이터는 한 번 옵니다. 결제는 원래 멱등하지 않으므로, 요청마다 고유한 번호인 **멱등 키**(idempotency key)를 붙여 멱등하게 만듭니다.

::: {.fig src="idempotency-key.svg"}
응답이 사라져서 같은 키로 다시 보냈습니다. 결제 서비스는 장부에서 `ord-42`를 찾아, 적어 둔 답만 돌려줍니다.
:::

지킬 것은 세 가지입니다.

- 키는 **보내는 쪽**이 만들고, 재시도할 때 **같은 키**를 씁니다. 재시도마다 새 키를 만들면 소용이 없습니다.
- 받는 쪽은 "키 기록"과 "실제 결제"를 **한 트랜잭션**으로 저장합니다. 따로 저장하면 그 사이에 꺼졌을 때 다시 어긋납니다.
- 손님이 정말로 두 번 주문했다면 키가 다르므로 둘 다 처리됩니다.

::: {.deep title="오류를 받으면: 고칠 것, 기다릴 것, 확인할 것"}
오류를 전부 "서버 오류"로 뭉뚱그리면 받는 쪽은 무엇을 할지 모릅니다. 계약에 오류의 종류를 나눠 담습니다.

| 오류의 종류 | 예 | 받는 쪽이 할 일 |
|---|---|---|
| 요청이 잘못됨 | 수량이 -1, 권한 없음 | 고쳐서 다시 보냄 |
| 업무 규칙상 거절 | 잔액 부족, 품절 | 사용자에게 알림 |
| 잠깐의 장애 | 서버가 바쁨 | 조금 기다렸다가 재시도 |
| 결과를 모름 | 시간 초과 | 같은 키로 결과를 확인 |

오류는 문장이 아니라 `OUT_OF_STOCK`처럼 정해 둔 코드로 알려 줍니다.
:::

## 재시도가 불을 키울 때: 마감, 백오프, 차단기 {#retry}

멱등 키가 있으면 다시 보내도 안전합니다. 그렇다고 마음껏 보내도 될까요? 맛집에 전화가 안 걸린다고 모두가 1초마다 다시 걸면 그 전화는 영영 통화 중입니다.

::: {.fig src="retry-storm.svg"}
앱도 3번, 주문 서비스도 3번씩 시도하면 결제 서비스는 9번을 받습니다. 층이 하나 더 있으면 27번입니다.
:::

결제 서비스가 요청이 몰려서 느려진 것이라면, 재시도는 부하를 9배로 불려 회복을 막습니다. 그래서 재시도에는 규칙을 둡니다.

- **한 층에서만** 재시도합니다.
- [11장](ch11.html)의 **마감**(deadline)을 지킵니다. 손님이 3초만 기다려 준다면 3초 뒤의 재시도는 쓸모가 없습니다.
- **간격을 늘립니다.** 1초, 2초, 4초처럼 기다리는 시간을 늘려 가는 것이 **백오프**(backoff)입니다. 모두가 같은 박자로 몰리지 않게 간격에 무작위 값을 섞는 것을 **지터**(jitter)라고 합니다.
- **될 것만** 재시도합니다. "잔액 부족"은 백 번 보내도 잔액 부족입니다.

### 차단기: 그만 보내기

재시도가 "다시 보내는" 규칙이라면 **서킷 브레이커**(circuit breaker)는 "그만 보내는" 규칙입니다. 집의 누전 차단기처럼, 상대가 계속 실패하면 스위치를 내립니다.

| 상태 | 호출이 오면 | 언제 바뀌나 |
|---|---|---|
| 닫힘 (회로가 이어짐) | 그대로 보낸다 | 실패가 기준을 넘으면 열림으로 |
| 열림 (회로가 끊김) | 보내지 않고 바로 실패로 답한다 | 정해 둔 시간이 지나면 반열림으로 |
| 반열림 (시험) | 몇 건만 보내 본다 | 성공하면 닫힘, 실패하면 다시 열림 |

상품 추천 서비스가 멈췄다면 차단기를 내리고 추천 없는 화면을 보여 주면 됩니다. 추천을 기다리느라 주문 화면까지 느려지는 것보다 낫습니다.

## 지금 할까, 맡겨 둘까: 큐와 메시지 {#queue}

주문의 네 가지 일을 손님이 전부 기다릴 필요는 없습니다. 결제와 재고는 그 자리에서 답해야 하지만, 메일은 10초 뒤에 가도 됩니다.

- **동기**(synchronous) 호출: 답이 올 때까지 기다립니다. 결과가 바로 필요한 짧은 일에 씁니다.
- **메시지 큐**(message queue): 할 일을 적은 쪽지(**메시지**)를 줄에 넣어 두면 작업자가 꺼내 처리합니다. [11장](ch11.html)의 주문서 꽂이를 프로그램 밖에 따로 세운 것입니다.

큐를 쓰면 메일 서버가 잠깐 멈춰도 주문은 계속 받을 수 있습니다. 대신 "접수됨"과 "끝남"이 서로 다른 시점이 되므로, 작업의 상태(대기, 처리 중, 완료, 실패)를 기록해 두어야 합니다.

### 큐의 약속: 적어도 한 번

작업자가 메일을 보낸 직후, 큐에 "처리했습니다"라고 알리기 전에 꺼졌습니다. 이 알림을 **확인 응답**(ack)이라고 합니다. 확인 응답을 못 받은 큐는 그 메시지를 다시 내줍니다. 앞에서 응답이 사라졌을 때와 똑같은 일입니다.

그래서 많은 큐가 **적어도 한 번 전달**(at-least-once delivery)을 약속합니다. 잃어버리지는 않지만 **두 번 올 수는 있다**는 뜻입니다. 받는 쪽은 메시지 번호를 장부에 적어 두고 이미 처리한 번호는 건너뜁니다. 멱등 키와 같은 방법입니다.

순서도 뒤바뀔 수 있습니다. "배송 완료" 뒤에 늦게 온 "배송 준비"가 화면을 되돌리지 않도록, 주문마다 버전 번호를 붙여 낡은 소식은 버립니다.

### 발행·구독과 실패 보관함

주문이 끝나면 재고도, 통계도, 알림도 그 사실을 알아야 합니다. 주문 서비스가 셋을 하나씩 부르면 넷째가 생길 때마다 주문 코드를 고쳐야 합니다. 대신 주문 서비스는 "주문 완료"라는 소식을 내기만 하고, 신문처럼 그 소식을 구독한 쪽이 각자 한 부씩 받게 합니다. 이것이 **발행·구독**(publish-subscribe)입니다.

::: {.fig src="pubsub-dlq.svg"}
위: 소식 하나를 구독자 셋이 각자 받습니다. 아래: 세 번 시도해도 안 되는 43번 메시지는 실패 보관함으로 옮깁니다.
:::

어떤 메시지는 몇 번을 해도 실패합니다. 메일 주소가 비어 있는 주문이 그렇습니다. 끝없이 재시도하면 뒤의 메시지가 전부 밀립니다. 그래서 정해 둔 횟수를 넘긴 메시지는 **DLQ**(Dead-Letter Queue), 곧 실패 보관함으로 옮깁니다. 옮겼다고 해결된 것은 아닙니다. 보관함이 차면 사람에게 알려 원인을 찾게 합니다.

::: {.deep title="아웃박스: DB에 저장한 직후에 꺼지면"}
주문을 DB에 저장하고 이어서 "주문 완료" 메시지를 큐에 보내는 코드가 있습니다. 둘 사이에 프로그램이 꺼지면 주문은 있는데 메일도 재고 차감도 시작되지 않습니다. DB와 큐는 다른 저장소라 한 트랜잭션으로 묶을 수 없기 때문입니다.

**아웃박스**(outbox, 보낼 편지함) 패턴은 주문 행과 "보낼 메시지" 행을 **같은 DB에 한 트랜잭션으로** 저장합니다. 그런 다음 별도의 전달 프로그램이 그 행을 읽어 큐로 옮기고 "보냄"으로 표시합니다. 꺼졌다 켜져도 행이 남아 있어 이어서 보냅니다. 보낸 직후 표시 전에 꺼지면 한 번 더 나가므로 받는 쪽의 중복 처리는 여전히 필요합니다.
:::

## 데이터의 주인은 하나: 소유권과 일관성 {#data}

서비스를 나누면 "이 숫자는 누가 고치는가"가 문제가 됩니다. 원칙은 [10장](ch10.html)과 같습니다. **데이터마다 주인은 하나**입니다. 재고 숫자는 재고 서비스만 고칩니다. 다른 서비스는 API로 부탁하거나 재고 서비스가 발행한 소식을 듣습니다. 여러 서비스가 같은 표를 직접 고치면 모듈 절에서 본 나쁜 예가 서버 규모로 되풀이됩니다.

::: {.note}
이름이 같다고 같은 데이터는 아닙니다. 회원 정보의 "주소"와 주문서의 "배송 주소"는 주인이 다릅니다. 회원이 이사해도 지난 주문의 배송 주소는 바뀌면 안 됩니다.
:::

주인이 하나면 다른 서비스는 사본을 들고 있게 됩니다. 상품 목록의 "남은 수량 3개"는 재고 서비스에서 받아 둔 사본입니다. 방금 한 개가 팔렸어도 소식이 도착하기 전까지는 3으로 보입니다. [17장](ch17.html)의 복제 지연과 같은 현상입니다. 새 변경이 멈추면 사본들이 **결국에는** 원본과 같아진다는 약속을 **최종 일관성**(eventual consistency)이라고 합니다.

목록의 남은 수량은 몇 초 늦어도 괜찮습니다. 하지만 결제 직전의 재고 확인은 주인에게 직접 물어야 합니다.

### 연결이 끊기면: CAP

재고 장부를 서울과 부산 서버에 한 벌씩 두었는데 두 서버 사이의 연결이 끊겼습니다. 둘 다 살아 있지만 서로 물어볼 수 없습니다. 이 상태를 **네트워크 분할**(partition)이라고 합니다.

::: {.fig src="cap-last-mug.svg"}
분할 중에 마지막 한 개를 두 손님이 주문했습니다. 둘 다 받으면 장부가 어긋나고, 장부를 지키려면 한쪽은 거절해야 합니다.
:::

**CAP 정리**가 말하는 것이 이것입니다. 분할(Partition)이 생긴 동안에는 "누구나 같은 최신 값을 본다"는 일관성(Consistency)과 "모든 서버가 요청에 답한다"는 가용성(Availability)을 **둘 다 가질 수 없습니다.**

::: {.myth title="CAP은 셋 중 둘을 고르라는 뜻이다"}
평소에는 고를 일이 없습니다. 연결이 멀쩡하면 일관성과 가용성을 함께 누립니다. 선택은 **분할이 일어난 동안에만**, 그것도 **데이터마다 따로** 합니다. 재고와 잔액은 한쪽을 멈추고, 상품 후기는 조금 낡은 것이라도 보여 주는 식입니다.
:::

::: {.deep title="사가: 롤백할 수 없으면 상쇄합니다"}
결제 서비스가 12,000원을 승인한 뒤 재고 서비스가 "품절"이라고 답했습니다. 두 서비스의 DB는 따로라 한꺼번에 롤백할(없던 일로 되돌릴) 수 없습니다. 대신 **환불**이라는 새 작업으로 앞 단계를 상쇄합니다. 이런 작업이 **보상**(compensation)이고, 단계마다 보상을 짝지어 둔 긴 업무 흐름이 **사가**(saga)입니다.

보상은 롤백과 달리 과거를 지우지 못합니다. 통장에는 "결제 12,000원, 환불 12,000원" 두 줄이 남고, 이미 보낸 메일은 정정 메일로 바로잡습니다. 보상도 실패할 수 있으므로 지금 몇 단계인지 저장해 두고, 보상 요청에도 멱등 키를 붙입니다.
:::

::: {.deep title="서버 여러 대에 데이터 두기: 쿼럼과 샤딩"}
같은 데이터를 서버 5대에 복제해 둡니다. 쓸 때 3대의 확인을 받고 읽을 때도 3대에 물으면, 두 묶음은 반드시 한 대 이상 겹칩니다. 3 + 3이 5보다 크기 때문입니다. 이렇게 정해 둔 수만큼 응답을 모으는 방식이 **쿼럼**(quorum)입니다. 읽기를 2대로 줄이면 빨라지지만 쓴 3대를 모두 비껴갈 수 있습니다. 어느 값이 최신인지는 버전 번호로 가립니다.

**샤딩**(sharding)은 복제와 목적이 다릅니다. 같은 데이터를 여러 벌 두는 것이 아니라 데이터를 **나눠 담습니다.** 회원 번호 같은 **분할 키**로 "이 회원은 2번 서버"를 정합니다. 한 회원의 주문은 한곳에 모이지만 "모든 회원의 최근 주문"은 서버를 전부 돌아야 합니다. DB 한 대로 충분하면 꺼내지 않는 도구입니다.
:::

## 손님이 몰릴 때: 확장과 격리 {#scale}

처리 능력을 늘리는 것을 **확장**(scaling)이라고 합니다. 길은 둘입니다.

- **수직 확장**(scale up): 더 큰 서버로 바꿉니다. 화구를 큰 것으로 바꾸는 셈입니다. 간단하지만 한계가 있습니다.
- **수평 확장**(scale out): 같은 서버를 여러 대 둡니다. 요리사를 더 뽑는 셈입니다. 요청은 [14장](ch14.html)의 로드 밸런서가 나눠 줍니다.

수평 확장에는 조건이 있습니다. 장바구니를 서버 한 대의 메모리에만 두면, 다른 서버로 간 다음 요청에서는 비어 보입니다. 이런 상태는 DB 같은 공용 저장소에 둡니다.

### 함께 쓰는 것이 병목입니다

요리사를 4명에서 10명으로 늘려도 냉장고 문은 하나입니다.

::: {.fig src="shared-bottleneck.svg"}
앱 서버 한 대가 DB 연결을 30개까지 엽니다. 10대로 늘리면 300개를 열려고 하지만 DB는 200개까지만 받습니다.
:::

[17장](ch17.html)의 커넥션 풀은 서버마다 따로 있습니다. 서버를 늘리면 DB 연결의 총합도 그만큼 늘어납니다. 느려서 서버를 늘렸는데 오히려 장애가 나는 이유입니다. 확장하기 전에 **모두가 함께 쓰는 것**(DB, 외부 API, 큐)의 한도를 먼저 확인합니다.

### 칸막이 치기: 벌크헤드

큰 배는 선체를 칸막이벽으로 나눠서, 한 칸에 물이 들어와도 가라앉지 않습니다. 이 생각을 자원에 옮긴 것이 **벌크헤드**(bulkhead)입니다. DB 연결이 20개인 서버에서 관리자가 2분짜리 매출 보고서 20개를 돌리면, 연결을 모두 차지해 손님의 주문이 멈춥니다. 보고서용 연결을 2개로 묶어 두면 보고서는 늦어져도 주문은 계속됩니다. 한도를 넘는 요청은 끝없이 줄 세우지 말고 일찍 거절합니다.

### 캐시가 한꺼번에 비면

"인기 상품 10개"는 계산에 2초가 걸려서 1분 동안 캐시에 넣어 둡니다. 캐시가 만료되는 순간, 요청 1,000개가 동시에 빈 캐시를 보고 저마다 2초짜리 계산을 시작합니다. 이것이 **캐시 스탬피드**(cache stampede)입니다. 미리 끓여 둔 육수가 떨어지자 요리사 열 명이 저마다 새 솥을 올리는 꼴입니다.

막는 방법은 셋입니다. 한 명만 계산하고 나머지는 그 결과를 기다립니다. 만료 시각에 무작위 값을 섞어 한꺼번에 비지 않게 합니다. 새 값이 준비될 때까지 조금 낡은 값을 내줍니다.

::: {.deep title="CQRS와 이벤트 소싱: 쓰는 모양과 읽는 모양"}
**CQRS**(Command Query Responsibility Segregation)는 데이터를 바꾸는 쪽과 조회하는 쪽의 모양을 따로 두는 설계입니다. 주문 원본은 규칙을 지키기 좋은 표에 두고, "회원별 최근 주문 요약"은 화면에 맞춘 조회용 표로 미리 만들어 둡니다. 조회는 빨라지지만 조회용 표는 조금 늦는 사본입니다.

**이벤트 소싱**(event sourcing)은 현재 값 대신 일어난 사건을 순서대로 저장합니다. "입금 100, 출금 30, 입금 20"을 차례로 적용하면 잔액 90이 나옵니다. 이력이 그대로 남는 대신, 옛 사건을 새 코드로 읽어도 같은 결과가 나오게 관리해야 합니다. 둘 다 저장과 조회의 요구가 크게 다를 때만 꺼냅니다.
:::

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 모듈 / 서비스 | 코드의 경계(함수 호출) / 실행의 경계(네트워크 호출) |
| 시간 초과 / 실패 | 결과를 모름 / 안 된 것이 확실함 |
| 재시도 / 서킷 브레이커 | 다시 보낸다 / 당분간 보내지 않는다 |
| 적어도 한 번 전달 / 한 번만 처리 | 큐가 해 주는 약속 / 받는 쪽이 중복을 걸러 만드는 결과 |
| 복제 / 샤딩 | 같은 것을 여러 벌 / 나눠서 한 벌씩 |

## 실전 사례 {#case}

::: {.case title="보고서 하나 때문에 가게 전체가 느려진다"}
관리자가 "월간 매출 보고서"를 누르면 2분이 걸립니다. 그동안 손님 화면도 느려지고, 새로고침을 누르면 계산이 하나 더 시작됩니다. AI는 "마이크로서비스로 나누자"고 합니다.

1. **무엇을 붙잡고 있는지 봅니다.** 보고서 요청 하나가 DB 연결 하나를 2분 동안 쥡니다. 새로고침 다섯 번이면 연결 다섯 개입니다.
2. **접수와 실행을 나눕니다.** 요청은 작업 번호만 돌려주고 끝냅니다. 계산은 큐에서 일을 꺼낸 작업자가 합니다. 화면은 작업 번호로 상태를 묻습니다.
3. **같은 일을 알아봅니다.** "같은 관리자, 같은 달"이면 같은 멱등 키로 보고 진행 중인 작업 번호를 돌려줍니다.
4. **칸막이를 칩니다.** 보고서 작업자는 동시에 2개만 돌리고, 대기 줄이 10개를 넘으면 거절합니다.
5. **일부러 깨뜨려 봅니다.** 계산 도중에 작업자를 껐다 켜서 작업이 사라지거나 두 번 만들어지지 않는지 확인합니다.

서비스를 여덟 개로 쪼갤 필요는 없었습니다. 작업자 하나를 떼어 내는 것으로 충분했습니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- 설계는 **경계를 긋고, 경계마다 약속과 실패 규칙을 정하는 일**입니다.
- 모듈은 함께 바뀌는 것끼리 묶고 서로의 속을 모르게 합니다. 한 프로그램으로 시작해 필요한 부분만 떼어 냅니다.
- API는 **계약**입니다. 더하는 변경은 대체로 안전하고, 뜻을 바꾸는 변경은 깨집니다.
- 시간 초과는 실패가 아니라 **모름**입니다. **멱등 키**가 있어야 안심하고 다시 보냅니다.
- 재시도는 한 층에서, 마감 안에, 간격을 늘려 가며 합니다. 계속 실패하면 차단기를 내립니다.
- 큐는 **적어도 한 번** 전달합니다. 받는 쪽은 중복에 대비하고, 안 되는 메시지는 DLQ로 뺍니다.
- 데이터의 주인은 하나이고 나머지는 조금 늦는 사본입니다. 서버를 늘리기 전에 함께 쓰는 자원의 한도를 봅니다.
:::

## 확인 문제 {#quiz}

::: {.q}
결제 요청이 시간 초과로 끝났습니다. 주문 번호를 새로 만들어 다시 결제를 요청해도 될까요?

::: {.a}
안 됩니다. 시간 초과는 "모름"이라 결제가 이미 끝났을 수 있습니다. 새 번호로 보내면 결제 서비스는 다른 주문으로 보고 한 번 더 결제합니다. 처음과 같은 멱등 키로 다시 보내거나 그 키로 결과를 조회합니다.
:::
:::

::: {.q}
혼자 만드는 서비스인데 AI가 "확장성을 위해 마이크로서비스 여섯 개로 시작하자"고 합니다. 무엇을 되물어야 할까요?

::: {.a}
어떤 기능의 부하나 배포 주기가 실제로 다른지, 지금 병목이 어디인지 근거를 묻습니다. 나누면 원격 호출의 실패, 계약의 버전, 데이터 맞추기를 떠안습니다. 모듈형 모놀리스에서 오래 걸리는 일만 작업자로 떼어 내면 충분한지도 비교하게 합니다.
:::
:::

::: {.q}
서버 응답의 `weight` 값을 kg에서 g으로 바꾸려 합니다. 칸 이름은 그대로 둡니다. 안전한 변경일까요?

::: {.a}
깨지는 변경입니다. 2kg짜리 상품의 값이 2에서 2000으로 바뀌는데, 옛 앱은 이를 2000kg으로 읽습니다. 이름이 같아도 뜻이 바뀌면 계약이 바뀐 것입니다. `weight_g` 같은 새 칸을 추가하고, 옛 칸은 옛 앱이 사라질 때까지 그대로 둡니다.
:::
:::

::: {.q}
알림 작업자가 같은 메시지를 두 번 받아 "주문 완료" 메일이 두 통 나갔습니다. 큐가 고장 난 것일까요?

::: {.a}
아닙니다. 적어도 한 번 전달하는 큐에서는 생길 수 있는 일입니다. 확인 응답이 닿기 전에 작업자가 꺼지면 큐는 같은 메시지를 다시 내줍니다. 작업자가 처리한 메시지 번호를 적어 두고 이미 있는 번호는 건너뛰어야 합니다.
:::
:::

::: {.q}
앱 서버 5대가 각각 DB 연결을 40개까지 엽니다. DB의 한도는 250개입니다. 응답이 느려서 서버를 8대로 늘리려 합니다. 무슨 일이 생길까요?

::: {.a}
지금은 5 × 40 = 200개라 한도 안이지만, 8대가 되면 8 × 40 = 320개를 열려고 해서 70개가 거절됩니다. 먼저 느린 원인이 앱 서버인지 DB인지 잽니다. 늘려야 한다면 서버당 연결을 30개로 줄여 총합을 240개에 맞춥니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI는 잘될 때의 흐름을 빠르게 그려 줍니다. 경계에서 실패했을 때의 규칙은 물어야 나옵니다.

> 주문 → 결제 → 재고 → 알림 흐름을 설계해 줘. 팀은 2명이고 하루 주문은 1,000건이야. 먼저 모듈형 모놀리스로 충분한지 판단하고, 나눠야 한다면 근거를 숫자로 보여 줘. 원격 호출마다 (1) 시간 제한과 전체 마감, (2) 시간 초과 뒤 결과를 확인하는 방법, (3) 멱등 키를 누가 만들고 어디에 저장하는지, (4) 재시도를 맡는 층을 표로 정리해 줘. 각 데이터의 주인도 적어 줘. 끝으로 "결제 응답이 사라짐", "같은 메시지 두 번 도착", "작업자가 처리 도중 종료"를 재현하는 테스트를 만들어 줘.

**받은 답에서 확인할 것**: 나눈 이유가 유행이 아니라 숫자인가, 시간 초과를 실패로 단정하지 않는가, 재시도에 같은 키를 쓰는가, 같은 표를 두 서비스가 고치지 않는가, 실패 테스트가 실제로 돌아가는가.
:::

## 용어 정리 {#terms}

::: {.terms}
모듈 (module)
:   관련된 일을 묶고 창구만 밖에 내놓은 코드 단위.

응집도 (cohesion)
:   모듈 안의 코드가 한 가지 목적에 모여 있는 정도.

결합도 (coupling)
:   다른 모듈의 속사정에 기대는 정도.

모놀리스 (monolith)
:   모든 기능을 한 프로그램으로 묶어 한 번에 배포하는 구조.

마이크로서비스 (microservices)
:   따로 실행하고 따로 배포하는 작은 서비스들이 네트워크로 협력하는 구조.

계약 (contract)
:   API에서 지키기로 한 약속 전체. 뜻, 단위, 실패 방식까지 포함한다.

멱등성 (idempotency)
:   같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질.

멱등 키 (idempotency key)
:   같은 작업임을 알아보도록 요청에 붙이는 고유 번호.

백오프 (backoff)
:   재시도 간격을 점점 늘리는 방법.

서킷 브레이커 (circuit breaker)
:   계속 실패하는 상대로의 호출을 잠시 끊는 장치.

적어도 한 번 전달 (at-least-once delivery)
:   메시지를 잃지는 않지만 두 번 전할 수 있다는 큐의 약속.

발행·구독 (publish-subscribe)
:   소식 하나를 여러 구독자가 각자 받아 가는 방식.

DLQ (Dead-Letter Queue)
:   거듭 실패한 메시지를 따로 옮겨 두는 실패 보관함.

최종 일관성 (eventual consistency)
:   변경이 멈추면 사본들이 결국 원본과 같아진다는 약속.

CAP 정리 (CAP theorem)
:   네트워크 분할 중에는 일관성과 가용성을 함께 지킬 수 없다는 정리.

벌크헤드 (bulkhead)
:   기능별로 자원 한도를 나눠 과부하가 번지지 않게 하는 방법.
:::
