::: {.lead}
AI가 "수정했습니다"라고 했고, 내 노트북에서는 잘 돌아갑니다. 그런데 사용자 화면은 어제 그대로이거나, 올리자마자 서버가 죽습니다. 코드를 고치는 일과 그 코드가 사용자에게 **무사히 도착하는 일**은 별개이기 때문입니다. 이 장에서는 도시락 공장의 생산 라인을 따라가며, 매번 **같은 것을 만들고** 그것을 **안전하게 내보내는** 법을 배웁니다.
:::

::: {.goals}
- 버전 번호 `1.4.2`의 세 자리를 읽고, 잠금 파일이 왜 필요한지 설명할 수 있습니다.
- "CI가 초록불"이 보장하는 것과 아닌 것을 구분할 수 있습니다.
- 한 번에 교체, 롤링, 블루-그린, 카나리 배포 가운데 상황에 맞는 것을 고를 수 있습니다.
- 배포 전에 되돌릴 수 있는 것과 없는 것을 나눠 롤백 계획을 세울 수 있습니다.
:::

## 코드가 사용자에게 가는 길: 공장의 생산 라인 {#line}

도시락 공장을 떠올려 봅시다. 주방장이 레시피에서 간장을 10g에서 8g으로 줄였습니다. 그렇다고 편의점 진열대의 도시락 맛이 바로 바뀌지는 않습니다. 공장이 새 레시피로 도시락을 **만들고**, 출고 전에 **검사하고**, 트럭에 실어 매장에 **진열해야** 손님이 그 맛을 봅니다.

코드도 같은 길을 갑니다.

1. **커밋.** 고친 코드를 저장소에 기록합니다([7장](ch07.html)). 어느 레시피로 만들지가 여기서 정해집니다.
2. **빌드.** 소스 코드와 외부 재료를 모아 실행할 수 있는 결과물로 만듭니다([4장](ch04.html)).
3. **테스트.** 결과물이 기대한 대로 움직이는지 확인합니다([12장](ch12.html)).
4. **배포.** 결과물을 사용자가 쓰는 곳에 가져다 놓고 실행합니다. 이 일을 **배포**(deployment)라고 합니다.

::: {.fig src="factory-line.svg"}
레시피를 고친 뒤 손님이 맛보기까지, 그리고 코드를 고친 뒤 사용자가 쓰기까지. 네 정거장이 하나씩 대응합니다.
:::

AI 도구가 "수정 완료"라고 말하는 지점은 대개 첫 정거장입니다.

이 길에서 사고는 두 군데서 납니다. 하나는 **만들 때**입니다. 같은 레시피인데 어제와 오늘의 도시락이 다르게 나옵니다. 다른 하나는 **내보낼 때**입니다. 전국 매장에 한꺼번에 깔았는데 상한 재료가 들어 있었습니다.

::: {.key}
사용자가 쓰는 것은 내 코드가 아니라 **그 코드로 만든 상자**입니다. 코드가 맞는지와 맞는 상자가 갔는지는 따로 확인합니다.
:::

## 버전 번호 읽기: 1.4.2의 세 자리 {#semver}

도시락에는 공장이 직접 만들지 않는 재료가 들어갑니다. 간장은 다른 업체에서 납품받습니다. 프로그램도 그래프를 그리는 코드 같은 것은 대개 남이 만든 패키지를 가져다 씁니다. 이런 외부 코드를 **의존성**이라고 했습니다([4장](ch04.html)).

납품업체가 간장 맛을 바꾸면 내 레시피가 그대로여도 도시락 맛이 달라집니다. 그래서 재료에는 버전 번호가 붙습니다. 가장 널리 쓰이는 규칙이 **유의적 버전**(Semantic Versioning, 줄여서 semver)입니다. 번호를 세 자리로 쓰고, 자리마다 뜻이 다릅니다.

::: {.fig src="semver-digits.svg"}
`chart-lib 1.4.2`를 읽는 법. 왼쪽 자리가 오를수록 내 코드에 미치는 영향이 큽니다.
:::

간장으로 치면 병뚜껑 불량을 고친 것이 수 버전, 대용량 병이 새로 나온 것이 부 버전입니다. 염도가 바뀌어 레시피의 간장 양을 다시 정해야 한다면 주 버전입니다.

프로젝트에는 필요한 패키지를 적어 두는 선언 파일이 있습니다. JavaScript라면 `package.json`이고, 그 안에 `"chart-lib": "^1.4.2"` 같은 줄이 있습니다. 앞에 붙은 `^`는 "1.4.2 이상, 2.0.0 미만이면 무엇이든 좋다"는 표시입니다.

이렇게 적어 둔 허용 폭을 **버전 범위**라고 합니다. 버그 수정을 저절로 받을 수 있어 편리하지만, 바로 이 편리함이 다음 절의 문제를 만듭니다.

::: {.warn title="버전 번호는 약속이지 검사 결과가 아닙니다"}
수 버전만 올렸는데 내 코드가 깨지는 일은 실제로 일어납니다. 만든 사람이 버그라고 보고 고친 동작에 내 코드가 기대고 있었을 수 있습니다. 숫자가 조금 올랐어도 테스트는 돌립니다.
:::

### 의존성 충돌: 옛 간장과 새 간장이 둘 다 필요할 때

패키지 A는 `chart-lib` 1.x가, 패키지 B는 2.x가 필요하다고 해 봅시다. 한 주방에서 옛 간장과 새 간장을 둘 다 달라는 상황입니다. 이것이 **의존성 충돌**입니다. 도구에 따라 두 버전을 모두 설치하기도 하고, 설치를 거부하기도 합니다.

이때 "무시하고 강제로 설치"하는 옵션이 눈에 띕니다. 하지만 이 옵션은 설치만 통과시키고 문제를 실행 중으로 미룰 뿐입니다. AI가 설치 오류를 `--force` 같은 옵션으로 넘기자고 하면 멈추고, **어느 패키지가 어느 버전을 요구하는지**부터 보여 달라고 하세요.

::: {.deep title="범위 기호는 도구마다 뜻이 다릅니다"}
npm에서 `^2.1.0`은 2.1.0 이상 3.0.0 미만입니다. Python에서 `~=2.1.0`은 2.1.0 이상 2.2.0 미만입니다. 모양이 비슷해도 뜻이 다릅니다.

`0.3.1`처럼 주 버전이 0인 패키지는 아직 틀을 잡는 중이어서, 부 버전만 올라도 쓰는 법이 바뀔 수 있습니다.
:::

## 잠금 파일: 오늘과 내일 같은 재료를 받는 법 {#lockfile}

월요일에 내 노트북에서 `chart-lib`을 설치했더니 1.4.2가 깔렸습니다. 수요일에 1.5.0이 새로 나왔습니다. 금요일에 서버에서 같은 프로젝트를 설치합니다. 선언 파일의 `^1.4.2`는 1.5.0도 허용하므로 서버에는 1.5.0이 깔립니다.

**내 코드는 한 글자도 바뀌지 않았는데 재료가 바뀌었습니다.** 게다가 `chart-lib`도 자기 재료를 따로 납품받습니다. 내가 적은 패키지는 열 개인데 실제로 설치되는 것은 수백 개인 일이 흔합니다.

해결책은 **실제로 받은 것을 전부 적어 두는 것**입니다. 이 기록이 **잠금 파일**(lockfile)입니다. npm은 `package-lock.json`, Python 도구들은 `uv.lock`이나 `poetry.lock` 같은 이름을 씁니다.

::: {.analogy title="발주서와 납품 기록표"}
선언 파일은 발주서입니다. "간장, 1.x대면 됩니다." 잠금 파일은 납품 기록표입니다. "간장 1.4.2, 제조 번호 8841." 내일도 똑같은 도시락을 만들려면 납품 기록표대로 받아야 합니다.
:::

::: {.fig src="lockfile-timeline.svg"}
같은 프로젝트를 월요일과 금요일에 설치한 결과. 잠금 파일이 없으면 그 사이에 나온 새 버전이 섞여 들어옵니다.
:::

설치 명령도 둘로 나뉩니다.

```bash
npm install   # 범위 안에서 고르고, 고른 결과를 잠금 파일에 적는다
npm ci        # 잠금 파일에 적힌 그대로만 설치한다
```

- 1행 — 개발하면서 패키지를 새로 넣거나 버전을 올릴 때 씁니다.
- 2행 — 서버와 자동 검사에서 씁니다. 선언 파일과 잠금 파일이 어긋나 있으면 알아서 고치지 않고 실패합니다.

지킬 것은 세 가지입니다. 잠금 파일은 **Git에 함께 올립니다.** 서버와 자동 검사에서는 **잠금대로만 설치**합니다. 버전을 올릴 때는 **그 일만 담은 커밋**으로 따로 올립니다.

::: {.key}
선언 파일은 "받아도 되는 범위"이고, 잠금 파일은 "실제로 받은 것"입니다.
:::

::: {.note}
잠금 파일이 고정하는 것은 패키지 버전까지입니다. 운영체제와 런타임 버전까지 한 묶음으로 굳히는 방법은 [21장](ch21.html)의 컨테이너입니다.
:::

::: {.try}
내 프로젝트의 잠금 파일을 열어 보세요. 선언 파일에 적은 패키지는 몇 개이고, 잠금 파일에는 몇 개가 적혀 있나요?
:::

::: {.deep title="내가 패키지를 만들어 나눠 주는 쪽이라면"}
잠금 파일은 최종 앱을 위한 도구입니다. 남이 가져다 쓸 라이브러리는 다른 패키지와 함께 설치되어야 하므로 범위를 넉넉히 적습니다.

또 소스 폴더에서 잘 돈다고 포장해 설치해도 잘 도는 것은 아닙니다. 설정 파일이나 이미지가 포장에서 빠지는 실수가 흔합니다. 공개하기 전에 빈 환경에 **포장한 파일을 직접 설치해** 보세요.
:::

## 빌드와 산출물: 밀봉한 상자 {#artifact}

재료가 정해졌으니 생산 라인을 돌릴 차례입니다. 실제 빌드는 [4장](ch04.html)에서 본 번역 말고도 파일 수백 개를 몇 개로 묶고, 이미지를 줄이고, 쓰지 않는 코드를 덜어 냅니다.

빌드가 끝나고 나온, **실제로 내보낼 결과물**을 **산출물**(artifact)이라고 합니다. 웹이라면 한 폴더에 모인 HTML과 JavaScript 파일 묶음이고, 모바일 게임이라면 스토어에 올리는 앱 파일입니다. 공장으로 치면 **밀봉한 도시락 상자**입니다.

개발 중에는 잘 보이던 아이콘이 상자에는 빠져 있을 수 있습니다. 포장 목록에 그 파일을 넣지 않았기 때문입니다. 그래서 마지막 확인은 **내보낼 상자를 직접 실행해서** 합니다.

상자에는 이름표도 필요합니다. `latest`나 `final` 같은 이름은 내일이면 다른 상자를 가리킵니다. 대신 두 가지를 적어 둡니다.

- **어느 커밋으로 만들었는가.** 예를 들어 `a1b2c3d`.
- **상자의 지문.** 파일 내용으로 계산한 짧은 글자열을 **해시**(hash)라고 합니다. 내용이 1바이트만 달라도 전혀 다른 값이 나오므로, 해시가 같으면 같은 상자입니다.

### 바뀐 것만 다시 만들기

간장 양만 바꿨는데 밥까지 새로 지을 필요는 없습니다. 빌드 도구는 **무엇으로 무엇을 만드는지**를 이어 놓은 관계도를 가지고 있습니다. 이 관계도를 따라 바뀐 재료의 영향을 받는 것만 다시 만드는 방식을 **증분 빌드**(incremental build)라고 합니다.

::: {.fig src="build-graph.svg"}
`ui.c`만 고쳤을 때. 주황색으로 칠한 것만 다시 만들고, `player.o`는 지난번 결과를 그대로 씁니다.
:::

이 관계도를 직접 적는 오래된 도구가 `make`입니다.

```makefile
game: player.o ui.o
	cc -o game player.o ui.o

ui.o: ui.c
	cc -c ui.c
```

- 1행 — 쌍점 왼쪽이 만들 것, 오른쪽이 재료입니다. "`game`을 만들려면 `player.o`와 `ui.o`가 필요하다"는 뜻입니다.
- 2행 — 만드는 명령입니다. 줄 앞은 탭으로 들여 씁니다. 4~5행도 같은 모양입니다.

`make`는 결과가 아직 없거나 재료가 결과보다 나중에 고쳐졌을 때만 그 명령을 실행합니다.

::: {.warn title="관계도에서 빠진 재료"}
`ui.c`가 읽는 `colors.h`를 관계도에 적지 않았다면, `colors.h`를 고쳐도 `make`는 옛 결과를 그대로 씁니다. "고쳤는데 반영이 안 되는" 버그의 흔한 원인입니다.
:::

::: {.deep title="다른 기계에서 돌 상자 만들기 (크로스 빌드)"}
ARM64 맥북에서 만든 상자를 x86-64 리눅스 서버에 올리는 것처럼, 빌드하는 컴퓨터와 실행할 컴퓨터가 다를 때가 많습니다. 내 컴퓨터에서 다른 대상용 결과물을 만드는 것을 **크로스 빌드**(cross build)라고 합니다.

내 컴퓨터에 깔린 라이브러리 파일은 내 컴퓨터용 번역본이므로 상자에 그대로 넣으면 안 됩니다. 또 빌드 성공이 대상에서 돈다는 뜻은 아니니, 실제 대상이나 닮은 환경에서 켜 봐야 합니다.
:::

## 한 번 만들어 여러 환경에: 상자는 그대로, 설정만 다르게 {#environments}

도시락 공장은 새 도시락을 먼저 시식 매장에서 팔아 봅니다. 소프트웨어도 프로그램이 돌아가는 무대를 여러 벌 마련합니다. 서버, 데이터베이스, 설정을 한 벌로 묶은 이 무대를 **환경**(environment)이라고 합니다.

| 환경 | 누가 쓰나 | 공장으로 치면 |
|---|---|---|
| 개발 | 개발자 혼자, 내 노트북에서 | 시험 주방 |
| **스테이징**(staging) | 팀 내부. 운영을 닮은 연습 무대 | 시식 매장 |
| 운영 (production) | 실제 사용자 | 본 매장 |

지킬 규칙은 둘입니다.

**첫째, 검사한 그 상자를 그대로 올립니다.** 흔한 실수는 스테이징에 올릴 때 한 번, 운영에 올릴 때 또 한 번 빌드하는 것입니다. 시식 매장에서 합격한 도시락과 본 매장에 깔리는 도시락이 다른 솥에서 나온 셈입니다.

같은 커밋으로 빌드해도 같은 상자가 나온다는 보장은 없습니다. 빌드가 현재 시각을 파일에 적어 넣거나 인터넷에서 가장 새 것을 받아 오면 결과가 달라집니다. 같은 입력이면 언제 만들어도 똑같은 산출물이 나오는 성질을 **재현 가능한 빌드**(reproducible build)라고 합니다. 잠금 파일이 여기에 다가가는 길이지만, 가장 쉬운 길은 **한 번만 만드는 것**입니다.

**둘째, 환경마다 달라야 하는 것은 상자 밖에 둡니다.** 스테이징은 연습용 데이터베이스에, 운영은 진짜 데이터베이스에 붙어야 합니다. 이 주소를 코드에 적어 넣으면 환경마다 상자를 따로 만들어야 합니다. 그래서 이런 값은 프로그램을 켤 때 바깥에서 건넵니다. 가장 흔한 통로가 **환경 변수**(environment variable), 곧 실행할 때 운영체제가 함께 건네주는 이름 붙은 값입니다.

::: {.fig src="build-once.svg"}
상자는 하나, 설정은 환경마다. 두 환경의 상자는 지문까지 같고, 다른 것은 바깥에서 건넨 환경 변수뿐입니다.
:::

```python
import os

DB_URL = os.environ["DB_URL"]
```

- 3행 — 코드에는 "`DB_URL`이라는 이름의 값을 받아 쓴다"는 것만 적습니다. 스테이징에서 켜면 연습용 주소가, 운영에서 켜면 진짜 주소가 들어옵니다.

::: {.warn title="이름만 나눈 환경은 나눈 것이 아닙니다"}
스테이징 서버가 실수로 운영의 결제 키를 읽으면, 연습 삼아 넣은 주문이 진짜로 청구됩니다. 환경을 나눈다는 것은 데이터베이스, 계정, 키까지 **실제로 다른 것을 쓰게** 한다는 뜻입니다.
:::

::: {.tip title="설정이 언제 읽히는지 확인하세요"}
브라우저로 보내는 화면 코드는 빌드할 때 설정값이 **파일 안에 글자 그대로 박힙니다.** 나중에 환경 변수를 바꿔도 이미 만든 파일은 그대로입니다. 또 브라우저로 간 값은 누구나 볼 수 있으니 비밀 키를 넣으면 안 됩니다([19장](ch19.html)).
:::

## CI: 올릴 때마다 도는 출고 검사 {#ci}

"잠금 파일대로 설치하고, 빌드하고, 테스트하고, 통과한 상자를 보관한다." 사람은 이것을 매번 지키지 못합니다.

공장은 컨베이어 벨트 위에 검사대를 놓아 **모든 상자가 반드시 지나가게** 합니다. 소프트웨어에서 이 검사대가 **CI**(Continuous Integration, 지속적 통합)입니다. 누군가 저장소에 코드를 올릴 때마다 깨끗한 컴퓨터 한 대가 자동으로 켜져서, 정해 둔 명령을 차례로 실행합니다. 이렇게 줄지어 선 단계를 **파이프라인**(pipeline)이라고 합니다.

::: {.fig src="pipeline.svg"}
커밋 `a1b2c3d`를 올리자 돌아간 파이프라인. 3번에서 테스트 하나가 실패해 종료 코드 1이 나왔고, 4번은 실행되지 않았습니다.
:::

- **매번 빈 주방에서 시작합니다.** 내 노트북에는 몇 달 전에 깔아 둔 도구가 남아 있지만, CI 컴퓨터에는 저장소에 적힌 것만 있습니다. "내 컴퓨터에서는 되는데요"의 원인인 **적어 두지 않은 재료**가 여기서 드러납니다.
- **종료 코드만 봅니다.** CI는 명령이 0으로 끝나면 초록불을, 아니면 빨간불을 켜고 멈춥니다([5장](ch05.html)). 그 검사가 충분한지는 판단하지 않습니다.

::: {.myth title="CI가 초록불이면 배포해도 안전하다"}
초록불은 "시킨 명령이 모두 0으로 끝났다"는 뜻일 뿐입니다. 테스트가 한 개도 실행되지 않아도 초록불입니다. 그래서 세 가지를 함께 봅니다. **어느 커밋**을 검사했는가, 테스트가 **몇 개** 돌았는가, 상자가 **실제로 만들어졌는가**. AI가 빨간불을 없애려고 실패하는 테스트를 꺼 버리는 일도 있습니다.
:::

CI 뒤에 배포까지 자동으로 이은 것은 **CD**(Continuous Delivery, 지속적 제공)라고 부릅니다.

::: {.deep title="CI를 빠르게, 넓게: 캐시와 매트릭스"}
CI는 지난번에 내려받은 의존성을 캐시로 보관했다가 다시 써서 시간을 줄입니다. 어떤 조건에서 만든 캐시인지 나타내는 이름표가 **캐시 키**이고, 보통 운영체제 이름과 잠금 파일의 해시를 이어 붙여 만듭니다. 키를 늘 `deps`처럼 같은 이름으로 두면 잠금 파일이 바뀌어도 옛 재료를 꺼내 씁니다.

**매트릭스**(matrix)는 같은 검사를 여러 조합에서 돌리는 기능입니다. 운영체제 3종과 런타임 버전 4개를 지원한다면 3 × 4 = 12가지입니다. 조합은 곱으로 늘어나므로, 평소에는 대표 조합만 돌리고 전체는 하루에 한 번 돌립니다.
:::

::: {.deep title="올리기 전에 내 컴퓨터에서 먼저: 묶음 명령과 Git 훅"}
형식 검사, 타입 검사, 핵심 테스트를 `check` 같은 이름 하나로 묶어 두면 사람도 AI도 CI도 같은 명령을 씁니다.

**Git 훅**(hook)은 커밋 직전 같은 때에 자동으로 실행되는 스크립트입니다. 빠른 검사를 걸어 두면 실수를 일찍 잡습니다. 다만 각자 설치해야 하고 건너뛸 수도 있어서 CI를 대신하지는 못합니다.
:::

## 배포 전략: 새 버전을 어떻게 갈아 끼울까 {#rollout}

검사를 통과한 상자가 준비됐습니다. 운영 서버 네 대가 지금 구버전을 돌리고 있습니다. 어떻게 갈아 끼울까요?

::: {.fig src="deploy-strategies.svg"}
칸 하나가 서버 한 대입니다. 파란 칸은 구버전을, 초록 칸은 신버전을 돌리고 있습니다.
:::

- **한 번에 교체.** 모두 끄고 새 버전으로 켭니다. 간단하지만 바꾸는 동안 서비스가 멈추고, 문제가 있으면 모든 사용자가 겪습니다.
- **롤링 배포**(rolling deployment). 한두 대씩 차례로 바꿉니다. 멈추지 않지만, 바꾸는 동안 두 버전이 함께 요청을 받습니다.
- **블루-그린 배포**(blue-green deployment). 지금 서버 묶음(블루) 옆에 새 버전 묶음(그린)을 따로 차려 미리 검사한 뒤, 요청이 들어오는 길을 한 번에 그린으로 돌립니다. 문제가 생기면 길만 다시 블루로 돌립니다. 대신 한동안 서버가 두 배로 필요합니다.
- **카나리 배포**(canary release). 요청의 5%만 새 버전으로 보내고 오류율을 구버전과 비교합니다. 괜찮으면 25%, 50%, 100%로 넓히고 나쁘면 멈춥니다. 탄광에 카나리아를 먼저 들여보내 위험을 살피던 데서 온 이름입니다.

::: {.tip title="멈출 조건은 배포 전에 정합니다"}
"오류율이 1%를 넘으면 중단한다"처럼 숫자로 미리 정해 두세요. 로그에는 `app-57` 같은 버전 이름을 남깁니다([22장](ch22.html)).
:::

### 기능 플래그: 배포와 출시를 떼어 놓기

여기까지는 새 코드를 서버에 올리는 순간이 곧 사용자가 새 기능을 보는 순간이었습니다. 이 둘을 떼어 놓는 장치가 **기능 플래그**(feature flag)입니다. 코드 안에 스위치를 넣어 두고, 켤지 말지는 설정에서 읽어 옵니다.

```python
if flags.is_on("new_search", user):
    show_new_search(user)
else:
    show_old_search(user)
```

- 1행 — `new_search`라는 스위치가 이 사용자에게 켜져 있는지 묻습니다.
- 2~4행 — 켜져 있으면 새 검색 화면을, 아니면 옛 화면을 보여 줍니다.

새 검색 코드는 월요일에 **꺼진 채로** 배포합니다. 수요일에 직원에게만 켜고, 금요일에 사용자 10%에게 켭니다. 문제가 보이면 스위치만 끕니다. 신메뉴를 매장 창고에 미리 가져다 두고, 진열하는 날은 따로 정하는 것과 같습니다.

::: {.key}
**배포**는 코드를 서버에 올리는 일이고, **출시**는 사용자에게 보여 주는 일입니다. 둘을 떼어 놓으면 따로 되돌릴 수 있습니다.
:::

::: {.warn}
스위치마다 길이 둘로 갈라지므로 켠 쪽과 끈 쪽을 모두 테스트해야 합니다. 모두에게 켠 뒤에는 플래그와 옛 코드를 지웁니다.
:::

## 구버전과 신버전이 함께 사는 시간 {#compat}

롤링이든 카나리든 블루-그린이든 **한동안 구버전과 신버전이 함께 살아 있습니다.** 그리고 두 버전은 대개 **같은 데이터베이스**를 봅니다. 가장 아픈 사고가 여기서 납니다.

사용자 표의 `name` 열을 `nickname`으로 바꾸고 싶다고 해 봅시다. 열 이름을 곧바로 바꾸면, 아직 돌고 있는 구버전 서버는 `name`을 찾지 못해 오류를 냅니다. 구버전으로 되돌려도 똑같습니다. 데이터베이스의 구조를 바꾸는 작업을 **마이그레이션**(migration)이라고 하는데([17장](ch17.html)), 안전한 마이그레이션은 세 번에 나눠서 합니다.

::: {.fig src="expand-contract.svg"}
`name`을 `nickname`으로 바꾸는 세 단계. 값이 다 채워진 초록 바탕 구간에서는 두 버전이 함께 돌 수 있습니다.
:::

1. **확장.** 새 열 `nickname`을 **더하기만** 합니다. 구버전은 새 열을 모르는 채로 잘 돕니다.
2. **이전.** 신버전을 배포합니다. 신버전은 당분간 **두 열 모두에** 씁니다. 구버전이 아직 `name`을 읽기 때문입니다. 그 사이 옛 값을 새 열로 옮겨 채우고, 다 채워지면 `nickname`을 읽도록 바꿉니다.
3. **축소.** 구버전이 완전히 사라지고 되돌릴 일도 없다고 확인한 뒤에 `name`을 지웁니다.

::: {.key}
더하는 일은 먼저 하고, **지우는 일은 맨 마지막에** 합니다. 지우기 전까지는 언제든 구버전으로 돌아갈 수 있습니다.
:::

### 이미 설치된 앱은 내가 바꿀 수 없습니다

서버는 내가 원할 때 바꿀 수 있지만, 사용자 휴대전화에 깔린 앱과 게임은 그렇지 않습니다. 업데이트를 몇 달씩 미루는 사용자도 있으니, 서버는 **옛 앱이 보내는 요청도 한동안 받아 줘야** 합니다.

게임 서버가 아이템 번호를 숫자 `1024`에서 글자 `"sword_01"`로 바꿔 보내면, 숫자를 기다리던 옛 앱은 응답을 읽지 못하고 멈춥니다. 규칙은 같습니다. **더하는** 것은 대체로 안전하고, **빼거나 뜻을 바꾸는** 것은 옛 버전 사용자가 충분히 줄어든 뒤에 합니다.

### 롤백: 되돌릴 수 있는 것과 없는 것

배포에 문제가 생겨 이전 상태로 되돌리는 것을 **롤백**(rollback)이라고 합니다. 이전 상자를 보관해 뒀다면 바꿔 끼우는 일은 쉽습니다. 하지만 상자를 되돌린다고 **세상이 되돌아가지는 않습니다.**

::: {.fig src="rollback-scope.svg"}
롤백이 되돌리는 것과 되돌리지 못하는 것. 오른쪽에 속하는 변경이 있다면 배포 전에 따로 계획을 세웁니다.
:::

그래서 배포하기 전에 묻습니다. 이전 상자가 **지금의 데이터를 읽을 수 있는가?** 이번 변경에 삭제, 발송, 결제처럼 **되돌릴 수 없는 일**이 들어 있는가? 그리고 되돌리기는 스테이징에서 한 번 연습해 둡니다.

## 공장 문단속: 공급망과 CI의 열쇠 {#supply}

마지막은 공장 자체의 안전입니다. 내 도시락에는 납품받은 재료, 생산 기계, 검사 라인의 설정처럼 내가 만들지 않은 것이 잔뜩 들어갑니다. 소스 코드에서 산출물까지 이어지는 이 길 전체를 **공급망**(supply chain)이라고 합니다. 한 곳만 오염되어도 **내 코드는 그대로인 채** 산출물이 바뀝니다.

**들어오는 재료.** 패키지는 설치되는 순간에 스크립트를 실행할 수 있습니다. 그래서 꼭 필요한 패키지만 넣고 잠금 파일로 버전을 고정합니다. 잠금 파일에는 해시도 적혀 있어서, 번호는 같고 내용만 바꿔치기한 파일을 걸러 줍니다. AI가 추천한 패키지는 실제로 있는 것인지, 유명한 패키지와 철자만 비슷한 가짜는 아닌지 확인하세요.

**CI가 쥔 열쇠.** CI는 배포를 하려고 서버에 들어갈 열쇠, 곧 비밀값을 가지고 있습니다. 그런데 CI는 저장소에 올라온 코드를 **그대로 실행하는 컴퓨터**입니다. 공개 저장소라면 모르는 사람이 보낸 변경의 테스트 코드도 실행합니다.

::: {.fig src="ci-keys.svg"}
검사와 배포를 한 작업에 넣으면 밖에서 온 코드가 열쇠에 손이 닿습니다. 작업을 나누면 열쇠는 검토를 거친 코드만 만납니다.
:::

원칙은 [19장](ch19.html)의 최소 권한 그대로입니다.

- 검사 작업에는 코드를 읽고 테스트하는 권한만 줍니다.
- 배포 열쇠는 사람이 검토하고 합친 코드만 실행하는 배포 작업에 둡니다.
- CI가 불러 쓰는 외부 도구도 "최신"이 아니라 정확한 버전으로 고정합니다.
- 로그에서 비밀값이 `***`로 가려지는 것은 화면 표시일 뿐입니다. 실행 중인 코드는 그 값을 그대로 읽습니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 버전 범위 / 잠금 파일 | 받아도 되는 범위 / 실제로 받은 정확한 버전 |
| 커밋 / 산출물 | 사람이 쓴 원본의 한 시점 / 그것으로 만들어 내보내는 상자 |
| CI / CD | 올릴 때마다 자동으로 빌드하고 검사 / 검사한 상자를 배포까지 잇기 |
| 배포 / 출시 | 코드를 서버에 올리는 일 / 사용자에게 기능을 보여 주는 일 |
| 블루-그린 / 카나리 | 준비한 새 무대로 전체를 한 번에 넘김 / 일부부터 보내며 조금씩 넓힘 |
| 롤백 / 전진 수정 | 이전 상자로 되돌림 / 고친 새 상자를 서둘러 내보냄 |

## 실전 사례 {#case}

::: {.case title="새 패키지를 넣었더니 내 컴퓨터에서는 되고 CI에서만 실패한다"}
AI가 이미지 크기를 줄이는 기능을 만들며 패키지를 하나 추가했습니다. 내 노트북에서는 잘 되는데, 올리자마자 CI에 빨간불이 켜졌습니다.

1. **어느 단계에서 멈췄는지 봅니다.** 테스트가 아니라 설치 단계(`npm ci`)입니다. 재료 쪽 문제입니다.
2. **선언 파일과 잠금 파일을 함께 봅니다.** 커밋에 `package.json`만 있고 `package-lock.json`은 빠져 있습니다. `npm ci`는 둘이 어긋나면 실패합니다.
3. **잠금 파일을 올리고 다시 돌립니다.** 이번에는 설치 단계의 다른 줄에서 멈춥니다. 이 패키지는 설치하는 동안 C 코드를 컴파일하는데, CI 컴퓨터에는 그 도구가 없습니다. 내 노트북에는 예전에 깔아 둔 것이 있었습니다.
4. **고릅니다.** CI에 도구 설치 단계를 더하거나, 컴파일이 필요 없는 더 작은 패키지로 바꿉니다. 여기서는 뒤쪽을 택했습니다.
5. **빈 폴더에서 확인합니다.** 저장소를 새 폴더에 받아 설치, 빌드, 테스트가 통과하는지 보고 올립니다.

CI의 빨간불은 방해꾼이 아니라 **적어 두지 않은 재료를 찾아 준 검사원**입니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- 코드는 **커밋 → 빌드 → 테스트 → 배포**를 거쳐 사용자에게 갑니다. 사용자가 쓰는 것은 그 코드로 만든 **산출물**입니다.
- 버전 `1.4.2`는 주, 부, 수 세 자리입니다. 주 버전이 오르면 쓰는 법이 바뀐 것입니다.
- **잠금 파일**은 실제로 받은 버전을 모두 적은 기록입니다. Git에 올리고, 서버와 CI는 잠금대로만 설치합니다.
- 상자는 **한 번만 만들어** 검사한 그대로 운영에 올립니다. 환경마다 다른 값은 **환경 변수**로 밖에서 건넵니다.
- **CI**는 올릴 때마다 빈 컴퓨터에서 설치, 빌드, 테스트를 돌립니다. 초록불은 "시킨 검사를 통과했다"는 뜻입니다.
- 새 버전은 **조금씩** 내보내고, 기능은 **플래그**로 따로 켭니다.
- 두 버전이 함께 사는 동안 더하기는 먼저, **지우기는 마지막에** 합니다.
:::

## 확인 문제 {#quiz}

::: {.q}
같은 커밋 `a1b2c3d`를 월요일과 금요일에 각각 빌드했습니다. 두 산출물이 서로 다를 수 있을까요?

::: {.a}
다를 수 있습니다. 잠금 파일이 없으면 그 사이에 나온 새 버전의 의존성이 섞여 들어옵니다. 빌드가 현재 시각을 파일에 적어 넣어도 달라집니다. 그래서 재료를 잠금 파일로 고정하고, 검사한 상자를 그대로 올립니다.
:::
:::

::: {.q}
AI가 올린 변경에서 `chart-lib`이 1.4.2에서 2.0.0으로 바뀌었고 CI는 초록불입니다. 그대로 합쳐도 될까요?

::: {.a}
초록불만으로는 부족합니다. 주 버전이 올랐으니 쓰는 법이 바뀌었을 수 있습니다. 패키지의 변경 기록을 읽고, 테스트가 `chart-lib`을 쓰는 화면을 실제로 지나가는지 확인합니다.
:::
:::

::: {.q}
결제 서버 열 대에 새 버전을 내보냅니다. 서비스를 멈출 수 없고, 문제가 있더라도 소수의 사용자만 겪게 하고 싶습니다. 어떤 방식이 맞을까요?

::: {.a}
카나리 배포가 맞습니다. 요청의 5% 정도만 새 버전으로 보내고 오류율을 구버전과 비교하며 넓힙니다. 다만 두 버전이 같은 데이터베이스를 쓰므로, 데이터를 잘못 바꾸는 버그는 5%에 그치지 않을 수 있습니다.
:::
:::

::: {.q}
새 추천 기능을 기능 플래그로 사용자 10%에게 켰다가 문제가 보여 플래그를 껐습니다. 이제 영향은 모두 사라졌을까요?

::: {.a}
아닙니다. 새 요청이 그 코드로 가는 길은 막았지만, 켜져 있던 동안 저장된 데이터와 이미 보낸 알림은 그대로 남습니다. 따로 조사해 바로잡아야 합니다.
:::
:::

::: {.q}
롤링 배포 중에 새 버전의 마이그레이션이 `name` 열의 이름을 곧바로 `nickname`으로 바꿨습니다. 어떤 일이 벌어지고, 어떻게 했어야 할까요?

::: {.a}
아직 바뀌지 않은 구버전 서버가 `name`을 읽으려다 오류를 냅니다. 롤백해도 열이 없어서 똑같이 실패합니다. 새 열을 더하고(확장), 값을 옮기며 양쪽에 쓰고(이전), 구버전이 모두 사라진 뒤 옛 열을 지우는(축소) 세 단계로 나눴어야 합니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
배포 준비를 맡길 때는 "배포해 줘"라고 하지 말고, **무엇이 바뀌었고, 무엇을 검사했고, 어떻게 되돌릴지**를 적어 오게 하세요.

> 이 변경을 배포할 수 있는 상태로 준비해 줘. 먼저 바뀐 것을 코드, 의존성(잠금 파일 포함), 설정, DB 구조로 나눠 표로 정리해. 그다음 저장소를 빈 폴더에 새로 받아 잠금 파일대로 설치하고 빌드와 테스트를 돌려. 실행한 명령, 돌아간 테스트 개수, 산출물의 이름과 해시를 보여 줘. 구버전 서버와 새 버전이 함께 돌아도 안전한지 판단하고, 되돌릴 수 없는 작업이 있으면 따로 표시해 롤백 순서를 적어 줘. 테스트를 끄거나 강제 설치 옵션으로 오류를 넘기지는 마.

**받은 답에서 확인할 것**: 잠금 파일이 선언 파일과 함께 바뀌었는가, 테스트 개수가 줄지 않았는가, 열을 지우거나 이름을 바꾸는 마이그레이션이 한 번에 들어 있지 않은가, 롤백 계획이 데이터까지 다루는가.
:::

## 용어 정리 {#terms}

::: {.terms}
배포 (deployment)
:   산출물을 사용자가 쓰는 환경에 가져다 놓고 실행하는 일.

유의적 버전 (Semantic Versioning, semver)
:   버전을 주, 부, 수 세 자리로 적어 호환 여부를 알리는 규칙.

잠금 파일 (lockfile)
:   실제로 설치된 의존성의 정확한 버전을 모두 적어 둔 기록.

산출물 (artifact)
:   빌드가 만들어 낸, 실제로 내보내는 결과물.

스테이징 (staging)
:   운영을 닮게 꾸민 연습용 환경. 운영에 올리기 전에 검사하는 곳.

CI (Continuous Integration)
:   지속적 통합. 코드를 올릴 때마다 자동으로 빌드하고 검사하는 방식.

파이프라인 (pipeline)
:   설치, 빌드, 테스트처럼 차례로 이어 실행하는 자동화 단계의 줄.

롤링 배포 (rolling deployment)
:   서버를 몇 대씩 차례로 새 버전으로 바꾸는 방식.

블루-그린 배포 (blue-green deployment)
:   새 버전 환경을 따로 차린 뒤 요청을 한 번에 넘기는 방식.

카나리 배포 (canary release)
:   일부 요청만 새 버전으로 보내 지켜보며 넓혀 가는 방식.

기능 플래그 (feature flag)
:   배포된 코드의 기능을 설정으로 켜고 끄는 스위치.

롤백 (rollback)
:   이전 산출물이나 설정으로 되돌리는 일.

공급망 (supply chain)
:   소스, 패키지, 빌드 도구, 자동화를 거쳐 산출물이 만들어지는 전체 경로.
:::
