::: {.lead}
집에서 만든 쿠키가 맛있다고 바로 가게에서 팔 수는 없습니다. 매번 똑같은 맛으로 만들고, 포장하고, 검사하고, 가게까지 옮겨야 합니다. 프로그램도 같습니다. 내 컴퓨터에서 돌아가는 것과 다른 사람들이 쓸 수 있게 내보내는 것은 다른 일입니다. 이 장에서는 프로그램을 포장하고 검사해서 안전하게 내보내는 과정을 배웁니다.
:::

::: {.goals}
- 프로그램을 포장하는 일(빌드)과 내보내는 일(배포)을 설명할 수 있습니다.
- 버전 번호 `1.4.2`가 무슨 뜻인지 읽을 수 있습니다.
- 내보내기 전에 자동으로 검사하는 방법과, 검사에서 멈췄을 때 읽는 법을 설명할 수 있습니다.
- 새 버전에 문제가 생겼을 때 되돌리는 방법을 알 수 있습니다.
:::

## 코드가 사용자에게 가는 길: 도시락 공장의 네 정거장 {#line}

쿠키 가게보다 조금 큰 곳, 도시락 공장을 떠올려 봅시다. 주방장이 레시피를 고쳤습니다. 간장을 10g에서 8g으로 줄였습니다.

그렇다고 편의점에 놓인 도시락 맛이 바로 바뀌지는 않습니다. 공장이 새 레시피로 도시락을 **만들어야** 합니다. 내보내기 전에 **검사해야** 합니다. 트럭에 실어 매장에 **진열해야** 합니다. 그제야 손님이 새 맛을 봅니다.

프로그램도 똑같은 길을 갑니다. 정거장은 넷입니다.

1. **커밋.** 고친 코드를 저장해 기록으로 남깁니다. [7장](ch07.html)에서 배운 저장 지점입니다. 레시피를 고쳐 적는 일과 같습니다.
2. **빌드.** 코드와 재료를 모아 실행할 수 있는 묶음으로 만듭니다([4장](ch04.html)). 도시락을 만들어 상자에 담는 일입니다.
3. **테스트.** 만든 것이 제대로 움직이는지 확인합니다([12장](ch12.html)). 내보내기 전에 하는 검사입니다.
4. **배포.** 묶음을 사람들이 쓰는 곳에 가져다 놓고 켭니다. 매장에 진열하는 일입니다. 이 일을 **배포**(deployment)라고 합니다.

::: {.fig src="factory-line.svg"}
윗줄은 공장, 아랫줄은 개발입니다. 네 정거장이 하나씩 짝을 이룹니다.
:::

그림 아랫줄을 읽어 봅시다. `a1b2c3d`는 커밋마다 붙는 번호입니다. `app-57.zip`은 빌드로 나온 57번 상자의 이름입니다. "212개 통과"는 테스트 212개를 모두 통과했다는 말입니다.

맨 끝의 "운영 서버"는 사람들이 실제로 접속해서 쓰는 컴퓨터입니다. 게임을 할 때 접속하는 게임 서버가 그런 컴퓨터입니다.

AI 도구에게 코드를 고쳐 달라고 하면 "수정 완료"라고 답합니다. 이 말은 대개 파일을 고쳤다는 뜻입니다. 첫 정거장인 커밋도 아직일 수 있습니다. 네 정거장을 다 지나야 사람들이 바뀐 것을 씁니다.

고쳤는데 그대로이거나 올리다가 실패했을 때도 **어느 정거장에서 멈췄는지**부터 가립니다. 찾는 법은 [CI 절](#ci)에서 봅니다.

이 길에서 사고는 주로 두 군데서 납니다. 하나는 **만들 때**입니다. 레시피는 같은데 어제와 오늘 도시락 맛이 다릅니다. 다른 하나는 **내보낼 때**입니다. 상한 재료가 든 도시락이 전국 매장에 한꺼번에 깔립니다.

::: {.key}
사람들이 쓰는 것은 내 코드가 아니라 **그 코드로 만든 상자**입니다. 코드가 맞는지와, 맞는 상자가 나갔는지는 따로 확인합니다.
:::

## 버전 번호 읽기: 1.4.2의 세 자리 {#semver}

도시락 공장은 재료를 모두 직접 만들지 않습니다. 간장은 다른 회사에서 사 옵니다. 프로그램도 그렇습니다. 그래프를 그리는 코드처럼 남이 잘 만들어 둔 것은 가져다 씁니다. 이렇게 가져다 쓰는 코드 꾸러미를 패키지라고 했습니다([6장](ch06.html)).

간장 회사가 맛을 바꾸면 어떻게 될까요? 내 레시피는 그대로인데 도시락 맛이 달라집니다. 그래서 재료에는 버전 번호를 붙입니다. 게임을 업데이트할 때 보이는 "버전 1.4.2" 같은 숫자입니다.

번호는 점으로 나눈 세 자리로 씁니다. 자리마다 뜻이 다릅니다. `chart-lib`이라는 그래프 패키지의 버전 `1.4.2`를 읽어 봅시다.

::: {.fig src="semver-digits.svg"}
`chart-lib 1.4.2`를 읽는 법. 왼쪽 자리가 오를수록 내 코드가 받는 영향이 큽니다.
:::

- **맨 오른쪽 자리(수 버전).** 잘못된 곳(버그)만 고쳤을 때 올립니다. `1.4.2`가 `1.4.3`이 됩니다. 간장으로 치면 새는 병뚜껑을 고친 것입니다.
- **가운데 자리(부 버전).** 기능이 늘었을 때 올립니다. `1.4.2`가 `1.5.0`이 됩니다. 큰 병이 새로 나온 것입니다. 쓰던 코드는 그대로 돕니다.
- **맨 왼쪽 자리(주 버전).** 쓰는 법이 바뀌었을 때 올립니다. `1.4.2`가 `2.0.0`이 됩니다. 간장이 훨씬 짜져서 레시피를 다시 맞춰야 하는 경우입니다.

그림에 적힌 major, minor, patch는 차례로 주 버전, 부 버전, 수 버전의 영어 이름입니다.

어느 자리가 오르면 그 오른쪽 자리는 0으로 돌아갑니다. 이 규칙의 이름은 **유의적 버전**(Semantic Versioning)입니다. '뜻이 담긴 버전'이라는 말입니다.

::: {.warn title="버전 번호는 약속이지 검사 결과가 아닙니다"}
번호는 만든 사람이 붙인 약속입니다. 맨 오른쪽 자리만 올랐는데 내 프로그램이 고장 나는 일도 있습니다. 숫자가 조금만 올랐어도 테스트는 다시 합니다.

`0.3.1`처럼 맨 왼쪽 자리가 0이면 "아직 틀을 잡는 중"이라는 표시입니다. 이때는 가운데 자리만 올라도 쓰는 법이 바뀔 수 있습니다.
:::

내 프로젝트에는 필요한 패키지를 적어 두는 파일이 있습니다. 공장의 주문서 같은 파일입니다. 이 파일에서 `chart-lib` 옆에 `^1.4.2`라고 적습니다. 앞의 `^` 표시는 "1.4.2부터 2.0.0이 되기 전까지는 무엇이든 좋다"는 뜻입니다.

이렇게 범위로 적어 두면 버그를 고친 새 버전을 저절로 받습니다. 편리합니다. 그런데 이 편리함이 다음 절의 문제를 만듭니다.

::: {.try}
휴대전화에 깔린 앱을 하나 골라 버전 번호를 찾아보세요. 스토어의 앱 화면에 적혀 있습니다. 번호는 몇 자리인가요?
:::

## 잠금 파일: 오늘도 내일도 같은 재료 받기 {#lockfile}

월요일에 내 노트북에 `chart-lib`을 설치했습니다. 1.4.2가 깔렸습니다. 수요일에 새 버전 1.5.0이 나왔습니다. 금요일에는 서버에 같은 프로젝트를 설치합니다.

주문서에는 `^1.4.2`라고만 적혀 있습니다. 1.5.0도 이 범위에 들어갑니다. 그래서 서버에는 1.5.0이 깔립니다.

**내 코드는 한 글자도 안 바뀌었는데 재료가 바뀌었습니다.** 내 노트북에서 잘 되던 것이 서버에서는 다르게 움직일 수 있습니다.

해결책은 **실제로 받은 것을 전부 적어 두는 것**입니다. 이 기록을 **잠금 파일**(lockfile)이라고 합니다. 설치하는 도구가 알아서 만들어 줍니다. 다음에 설치할 때는 여기 적힌 것과 똑같은 것만 받습니다.

::: {.analogy title="주문서와 영수증"}
주문서에는 "간장, 1.4.2부터 2.0.0 전까지"라고 적습니다. 영수증에는 "간장 1.4.2"라고 정확히 찍힙니다. 내일도 똑같은 도시락을 만들려면 영수증대로 받아야 합니다. 잠금 파일이 이 영수증입니다.
:::

::: {.fig src="lockfile-timeline.svg"}
같은 프로젝트를 월요일과 금요일에 설치한 결과. 잠금 파일이 없으면 그 사이에 나온 새 버전이 섞여 들어옵니다.
:::

패키지를 받아 설치해 주는 프로그램을 패키지 매니저라고 했습니다([6장](ch06.html)). 웹사이트를 만들 때는 `npm`이라는 패키지 매니저를 많이 씁니다. `npm`에서는 주문서 파일의 이름이 `package.json`, 잠금 파일의 이름이 `package-lock.json`입니다.

설치하는 명령은 둘입니다. 터미널([5장](ch05.html))에 `npm install chart-lib`이라고 치면 `chart-lib`을 새로 받아 옵니다. 주문서와 잠금 파일에도 알아서 적어 줍니다. 만드는 동안 내 노트북에서 쓰는 명령입니다.

`npm ci`라고 치면 잠금 파일에 적힌 그대로만 설치합니다. 주문서와 잠금 파일이 서로 안 맞으면 고치지 않고 멈춥니다.

지킬 것은 둘입니다. 잠금 파일도 코드와 함께 커밋합니다. 서버에서는 잠금 파일대로만 설치합니다.

::: {.warn title="AI가 주문서를 고쳤는지 봅니다"}
AI는 오류를 고치다가 부탁하지 않은 패키지를 넣거나 버전을 올리기도 합니다. 잠금 파일을 지우고 새로 만들면 재료 수백 개가 한꺼번에 새 버전으로 바뀔 수 있습니다. 커밋하기 전에 터미널에 `git diff package.json`이라고 쳐서 바뀐 줄을 봅니다([7장](ch07.html)). 맨 왼쪽 자리가 바뀐 패키지가 있으면 까닭부터 묻습니다.
:::

### 의존성 충돌: 옛 간장과 새 간장을 둘 다 달라고 할 때

패키지도 다른 패키지를 가져다 씁니다. 내가 넣은 패키지는 몇 개인데 실제로 깔리는 것은 수백 개인 일이 흔합니다. 이렇게 내 프로그램이 기대는 남의 코드를 통틀어 의존성이라고 했습니다([4장](ch04.html)).

내 게임에 패키지 A와 B를 넣었다고 합시다. A는 `chart-lib`이 1로 시작하는 버전이어야 돕니다. B는 2로 시작하는 버전이어야 돕니다. 한 주방에서 옛 간장과 새 간장을 둘 다 달라는 셈입니다. 이런 일을 **의존성 충돌**이라고 합니다.

설치하는 도구에 따라 두 버전을 모두 받기도 하고, 오류를 내며 멈추기도 합니다. `npm`이 멈출 때는 오류 글에 `ERESOLVE`라는 낱말이 보입니다. 그 끝에는 "무시하고 억지로 설치"하는 옵션이 적혀 있습니다. `--force`와 `--legacy-peer-deps`입니다. 하지만 이 옵션은 설치만 통과시킵니다. 문제는 프로그램을 실행할 때로 미뤄질 뿐입니다.

::: {.warn title="억지 설치는 해결이 아닙니다"}
AI가 설치 오류를 `--force`로 넘기자고 하면 멈추세요. **어느 패키지가 어느 버전을 달라고 하는지**부터 보여 달라고 하세요. 오류 글의 `Found:` 줄과 `Could not resolve dependency:` 줄에 적혀 있습니다.
:::

## 빌드와 산출물: 뚜껑을 붙인 상자 {#artifact}

재료가 정해졌으니 이제 만들 차례입니다. 빌드는 코드를 컴퓨터가 실행할 수 있게 바꾸고, 흩어진 파일 수백 개를 몇 개로 묶습니다.

`npm`을 쓰는 프로젝트라면 두 줄이면 됩니다. 아래는 터미널에 치는 명령입니다.

```bash
npm ci
npm run build
```

- 1행 — 잠금 파일에 적힌 그대로 패키지를 받습니다.
- 2행 — 받은 패키지와 내 코드로 빌드합니다. 빌드할 때 무슨 일을 할지는 프로젝트마다 주문서 파일에 `build`라는 이름으로 적어 둡니다. 거기 적힌 일을 하라는 명령입니다.

빌드가 끝나면 내보낼 묶음이 나옵니다. 이것을 **산출물**(artifact)이라고 합니다. 첫 그림의 `app-57.zip`이 산출물입니다. 공장으로 치면 **뚜껑을 붙인 도시락 상자**입니다. 웹 앱에서는 흔히 `dist`나 `build`라는 폴더가 산출물입니다.

AI가 "다 만들었습니다"라고 하면 이 두 줄을 직접 쳐 봅니다. 만드는 동안에는 잘 되던 앱이 빌드에서 멈추는 일이 흔합니다([4장](ch04.html)).

빌드가 끝났어도 만드는 동안 잘 보이던 아이콘이 상자에는 빠져 있을 수 있습니다. 포장 목록에 그 그림 파일을 넣지 않았기 때문입니다. 그래서 마지막 확인은 **내보낼 상자를 직접 실행해서** 합니다.

상자에는 이름표도 필요합니다. '최종', '진짜최종' 같은 이름으로는 며칠 뒤에 어느 것이 진짜인지 모릅니다. 그래서 두 가지를 적어 둡니다.

- **어느 커밋으로 만들었는가.** 예를 들면 `a1b2c3d`입니다.
- **상자의 지문.** 파일 내용으로 계산한 짧은 글자열입니다. 이것을 **해시**(hash)라고 합니다. 내용이 조금만 달라도 전혀 다른 값이 나옵니다. 해시가 같으면 같은 상자입니다.

### 바뀐 것만 다시 만들기

간장 양만 바꿨는데 밥까지 새로 지을 필요는 없습니다. 빌드도 바뀐 것만 다시 만듭니다.

작은 게임의 소스 파일, 곧 사람이 쓴 코드 파일이 `player.c`와 `ui.c` 둘이라고 합시다. 빌드는 먼저 파일을 하나씩 컴퓨터의 말로 번역합니다(컴파일). 그 결과가 그림의 중간 결과 `player.o`와 `ui.o`입니다. 다음으로 둘을 이어 붙여 실행 파일 `game`을 만듭니다(링크). 둘 다 [4장](ch04.html)에서 본 일입니다.

컴파일에 파일 하나당 20초, 링크에 5초가 걸린다고 합시다. 전부 새로 만들면 20 + 20 + 5 = 45초입니다. `ui.c`만 고쳤다면 `player.o`는 지난번 것을 그대로 씁니다. `ui.o`만 다시 컴파일하고(20초) 다시 링크합니다(5초). 20 + 5 = 25초면 끝납니다.

::: {.fig src="build-graph.svg"}
`ui.c`만 고쳤을 때. 주황색으로 칠한 것만 다시 만들고, `player.o`는 지난번 결과를 그대로 씁니다.
:::

::: {.tip title="고쳤는데 그대로일 때"}
빌드 도구는 "무엇으로 무엇을 만드는지"를 적은 관계도를 따라가며 바뀐 것만 다시 만듭니다. 관계도에서 빠진 재료는 고쳐도 지난번 결과가 그대로 쓰입니다. 분명히 고쳤는데 프로그램이 바뀌지 않는다면, 지난번 결과를 지우고 전부 새로 빌드해 보세요.
:::

## 한 번 만들어 여러 무대에: 상자는 그대로, 설정만 다르게 {#environments}

학교 연극은 본 공연 전에 리허설을 합니다. 진짜 무대와 닮은 곳에서 미리 해 봅니다. 도시락 공장도 새 도시락을 시식 매장에서 먼저 팔아 봅니다.

프로그램도 돌아가는 무대를 여러 벌 마련합니다. 이 무대를 **환경**(environment)이라고 합니다. 환경 하나에는 프로그램을 돌릴 컴퓨터, 자료를 모아 두는 데이터베이스([17장](ch17.html)), 설정이 한 벌씩 들어 있습니다. 보통 세 가지를 둡니다.

| 환경 | 누가 쓰나 | 공장으로 치면 |
|---|---|---|
| 개발 | 만드는 사람 혼자, 내 노트북에서 | 시험 주방 |
| **스테이징**(staging) | 만드는 팀. 운영을 닮은 연습 무대 | 시식 매장 |
| 운영(production) | 실제 사용자 | 본 매장 |

지킬 규칙은 둘입니다.

**첫째, 검사한 그 상자를 그대로 올립니다.** 스테이징에 올릴 때 한 번, 운영에 올릴 때 또 한 번 빌드하는 실수가 흔합니다. 시식 매장에서 합격한 도시락과 본 매장에 깔리는 도시락이 다른 솥에서 나온 셈입니다. 같은 커밋으로 만들어도 두 상자가 똑같다는 보장은 없습니다. 빌드 도구가 만든 시각을 적어 넣기도 하고, 그 사이에 나온 새 재료가 섞이기도 합니다. 상자는 **한 번만** 만듭니다.

**둘째, 환경마다 달라야 하는 값은 상자 밖에 둡니다.** 스테이징은 연습용 데이터베이스에, 운영은 진짜 데이터베이스에 이어져야 합니다. 데이터베이스의 주소를 코드 안에 적어 버리면 환경마다 상자를 따로 만들어야 합니다.

그래서 이런 값은 프로그램을 켤 때 밖에서 건네줍니다. 이름을 붙여 건네는 이 값이 **환경 변수**(environment variable)입니다([6장](ch06.html)). 코드에는 "`DB_URL`이라는 이름의 값을 받아서 쓴다"고만 적어 둡니다.

::: {.fig src="build-once.svg"}
상자는 하나, 설정은 환경마다. 다른 것은 밖에서 건넨 환경 변수뿐입니다.
:::

그림에서 상자는 어디서나 `app-57.zip`이고 지문도 `9f2c…e1`로 같습니다. 다른 것은 아래쪽의 환경 변수입니다. `DB_URL`은 데이터베이스(DB)의 주소입니다. 스테이징에는 `staging-db`를, 운영에는 `prod-db`를 건넵니다. `prod`는 운영을 뜻하는 production을 줄인 말입니다.

`PAY_KEY`는 결제를 맡은 회사에 보여 주는 열쇠입니다. 스테이징에는 `test_`로 시작하는 연습용을, 운영에는 `live_`로 시작하는 진짜를 건넵니다.

### 환경 변수를 건네고 받기

건네는 방법은 [6장](ch06.html)에서 본 그대로입니다. 스테이징 서버에서는 프로그램을 켜기 전에 터미널에 `export DB_URL=staging-db`라고 칩니다. 서버를 빌려 쓰는 서비스라면 설정 화면에 이름과 값을 적어 넣습니다.

받는 쪽 코드는 어느 환경에서나 같습니다. 아래는 **파이썬**(Python)이라는 프로그래밍 언어로 쓴 코드입니다. 코드를 처음 본다면 [초코딩 기초](code.html)를 먼저 보세요.

```python
import os

db_url = os.environ["DB_URL"]
```

- 1행 — 운영체제에 물어보는 기능을 모아 둔 `os`를 가져옵니다.
- 3행 — 환경 변수 가운데 이름이 `DB_URL`인 값을 꺼내 `db_url`에 담습니다. `environ`은 환경(environment)을 줄인 말입니다.

코드 어디에도 주소는 적혀 있지 않습니다. 스테이징에서 켜면 연습용 주소가, 운영에서 켜면 진짜 주소가 들어옵니다. 값을 건네지 않은 곳에서 켜면 3행에서 `KeyError: 'DB_URL'`이라는 오류를 내며 멈춥니다.

::: {.warn title="이름만 나눈 환경은 나눈 것이 아닙니다"}
스테이징이 실수로 운영의 진짜 결제 열쇠를 받았다고 해 봅시다. 연습 삼아 눌러 본 결제에서 진짜 돈이 나갑니다. 환경을 나눈다는 것은 데이터베이스와 열쇠까지 **실제로 다른 것을 쓴다**는 뜻입니다.
:::

### 내 컴퓨터와 올린 곳: 달라지는 세 가지

혼자 만드는 앱에는 스테이징이 없을 때가 많습니다. 그래도 환경은 적어도 둘입니다. 내 컴퓨터와, 인터넷에 올린 곳입니다. 둘 사이에서는 세 가지가 달라집니다.

| 달라지는 것 | 내 컴퓨터(개발) | 올린 곳(운영) |
|---|---|---|
| 주소 | `http://localhost:3000` | `https://mygame.example` 같은 진짜 주소 |
| 데이터베이스 | 연습용 | 진짜 사용자의 자료 |
| 환경 변수 | `.env` 파일 | 서비스의 설정 화면 |

`localhost`는 '이 컴퓨터 자신'이라는 뜻입니다([14장](ch14.html)). AI가 만든 코드에 이 주소가 그대로 적혀 있으면, 올린 곳에서는 화면이 서버를 찾지 못합니다. 주소도 환경 변수로 건네게 합니다.

`.env` 파일은 저장소에 올리지 않으니([6장](ch06.html)) 올린 곳에는 값이 저절로 생기지 않습니다. 올린 곳에서만 값이 비어 있다면, 서비스의 설정 화면에 이름과 값을 넣었는지 봅니다. 넣은 뒤에는 다시 배포해야 새 값을 받습니다.

::: {.deep title="웹 화면 코드에 넣은 설정은 언제 읽힐까요?"}
웹사이트의 화면을 그리는 코드는 보는 사람의 브라우저로 보내져서 거기서 돕니다. 브라우저에는 내가 건넨 환경 변수가 없습니다. 그래서 이런 코드는 빌드할 때 설정값을 읽어 **파일 안에 글자 그대로 적어 넣습니다.** 이름이 `VITE_`나 `NEXT_PUBLIC_`으로 시작하는 환경 변수가 흔히 그런 값입니다.

그래서 나중에 환경 변수를 바꿔도 이미 만든 상자 속의 값은 그대로입니다. 바꾸려면 다시 빌드해야 합니다. 또 브라우저로 간 값은 누구나 열어 볼 수 있습니다. 비밀 열쇠는 화면 코드에 넣지 않습니다([19장](ch19.html)).
:::

## CI: 올릴 때마다 도는 출고 검사 {#ci}

"잠금 파일대로 설치하고, 빌드하고, 테스트하고, 통과한 상자를 보관한다." 지금까지 배운 순서입니다. 사람은 이 순서를 매번 지키지 못합니다. 급하면 건너뜁니다.

공장은 컨베이어 벨트 위에 검사대를 놓아 **모든 상자가 반드시 지나가게** 합니다.

프로그램을 만들 때도 이런 검사대를 둡니다. 누군가 저장소([7장](ch07.html))에 코드를 올릴 때마다 깨끗한 컴퓨터 한 대가 자동으로 켜집니다. 그 컴퓨터가 정해 둔 명령을 차례로 실행합니다. 이 방식을 **CI**(Continuous Integration)라고 합니다. 우리말로는 '지속적 통합'입니다. 여럿이 고친 코드를 자주 한데 합쳐서 검사한다는 뜻입니다.

차례로 줄지어 선 단계들은 **파이프라인**(pipeline)이라고 부릅니다. 물이 관을 따라 흐르듯, 앞 단계가 끝나야 다음 단계로 넘어갑니다.

::: {.fig src="pipeline.svg"}
커밋 `a1b2c3d`를 올리자 돌아간 파이프라인. 3번에서 테스트 하나가 실패해 4번은 실행되지 않았습니다.
:::

그림의 1번과 2번은 앞에서 본 두 명령입니다. 3번은 `npm test`로 테스트 212개를 돌립니다. 4번은 검사한 상자를 보관소에 넣습니다.

단계가 잘 끝났는지는 프로그램이 끝날 때 남기는 숫자 하나로 압니다. **0이면 성공, 0이 아니면 실패**입니다. 이 숫자를 종료 코드라고 했습니다([5장](ch05.html)).

그림에서 1번과 2번은 0으로 끝났습니다. 3번은 테스트 212개 중 1개가 실패해서 1로 끝났습니다. 그래서 빨간불이 켜지고 4번은 실행되지 않았습니다.

CI는 **매번 빈 주방에서 시작합니다.** 내 노트북에는 예전에 깔아 둔 도구가 남아 있습니다. CI 컴퓨터에는 저장소에 적힌 것만 있습니다. 그래서 내 노트북에만 있던 **적어 두지 않은 재료**가 여기서 드러납니다.

어떤 명령을 돌릴지는 저장소 안의 설정 파일에 적어 둡니다. GitHub에서는 `.github/workflows` 폴더에 있습니다. AI가 이 폴더의 파일을 고쳤다면 검사대를 고친 것입니다. 무엇을 뺐는지 diff로 읽습니다.

::: {.try}
브라우저에서 GitHub의 공개 저장소를 하나 열고 커밋 목록을 보세요. 커밋 옆의 초록 체크나 빨간 가위표가 CI가 돈 흔적입니다. 눌러서 어떤 단계가 돌았는지 읽어 보세요.
:::

### CD: 진열까지 자동으로

그림의 파이프라인은 검사한 상자를 보관소에 넣는 데서 끝났습니다. 매장에 진열하는 일은 아직 사람이 합니다. 이 일까지 파이프라인 뒤에 이어 자동으로 하는 방식을 **CD**(Continuous Delivery)라고 합니다. 우리말로는 '지속적 제공'입니다.

CI는 **검사**까지, CD는 **배포**까지 자동으로 합니다. 둘을 묶어 흔히 'CI/CD'라고 부릅니다. 운영에 올리는 마지막 단추만은 사람이 누르게 해 두는 팀도 많습니다.

혼자 만드는 웹 앱이라면 이 흐름을 직접 짜지 않아도 됩니다. 앱을 인터넷에 올려 주는 서비스(예: Vercel, Netlify)에 내 원격 저장소를 이어 두면 됩니다. 그 뒤로는 `git push`를 할 때마다 서비스의 컴퓨터가 저장소를 받아 설치하고, 빌드하고, 배포합니다([31장](ch31.html#deploy)). 이렇게 이어 두면 **`main`에 올리는 것이 곧 배포**입니다.

그래서 `main`에 바로 올리지 않고 브랜치([7장](ch07.html))에 먼저 올립니다. 많은 서비스가 `main`이 아닌 브랜치에는 임시 주소를 따로 만들어 줍니다. 진짜 주소는 그대로 두고, 고친 것만 먼저 열어 볼 수 있습니다. 이것을 **미리 보기 배포**(preview deployment)라고 합니다. 혼자 쓰는 스테이징인 셈입니다.

::: {.fig src="push-deploy.svg"}
윗줄은 브랜치 `fix-score`를 올렸을 때, 아랫줄은 `main`에 합쳐 올렸을 때입니다. 주소는 지어낸 것입니다.
:::

미리 보기 주소에서 고친 곳을 직접 눌러 봅니다. 괜찮으면 `main`에 합칩니다. 이때 서비스는 **다시 빌드합니다.** 상자를 한 번만 만든다는 규칙에서는 벗어납니다. 그러니 합친 뒤에는 운영 주소도 한 번 열어 봅니다. 빌드가 실패하면 새 버전은 나가지 않고 옛 버전이 그대로 남습니다.

미리 보기가 진짜 데이터베이스에 이어져 있지 않은지도 봅니다. 이어져 있다면 연습 삼아 지운 것이 진짜로 지워집니다.

### 빨간불이 켜졌을 때: 빌드 로그 읽기

CI나 서비스의 컴퓨터가 설치하고 빌드하는 동안 화면에 찍힌 글은 모두 남습니다. 이 기록을 **빌드 로그**(build log)라고 합니다. "내 컴퓨터에서는 되는데 올리면 실패한다"면 답은 여기에 있습니다.

먼저 **어느 단계**에서 멈췄는지 봅니다. 설치인가, 빌드인가, 테스트인가. 다음으로 그 단계에서 **처음 나온 오류**를 찾습니다. 맨 아랫줄은 대개 "실패했다"는 말뿐이고, 까닭은 그 위에 있습니다.

| 로그에 보이는 글 | 흔한 까닭 | 할 일 |
|---|---|---|
| `Missing: … from lock file` | 잠금 파일을 함께 올리지 않았다 | 잠금 파일을 커밋한다 |
| `Cannot find module`, `Could not resolve` | 파일 이름의 대문자·소문자가 코드와 다르다 | 이름을 똑같이 맞춘다 |
| `Type error`, `error TS2322` | 만드는 동안에는 건너뛴 검사에 걸렸다 | 내 컴퓨터에서 `npm run build`를 돌려 본다 |
| `Unsupported engine` | Node.js 같은 런타임의 버전이 내 컴퓨터와 다르다 | 서비스 설정에서 버전을 맞춘다 |

둘째 줄은 까닭이 눈에 잘 띄지 않습니다. 맥과 윈도우는 보통 `Button.js`와 `button.js`를 같은 파일로 봅니다. 서버가 주로 쓰는 리눅스는 다른 파일로 봅니다.

::: {.tip title="AI에게 빌드 실패를 물을 때"}
멈춘 단계의 로그를 **첫 오류부터** 붙여 넣습니다. "내 컴퓨터에서는 `npm run build`가 된다"는 사실과 `node -v`로 본 버전도 적습니다. 올리기 전에 내 컴퓨터에서 `npm ci`와 `npm run build`를 돌려 보면 표의 첫째와 셋째 줄은 미리 잡힙니다.
:::

빨간불은 읽으면 됩니다. 더 조심할 것은 초록불입니다. CD를 붙이면 초록불이 곧 배포로 이어지기 때문입니다.

::: {.myth title="CI가 초록불이면 내보내도 안전하다"}
CI는 종료 코드만 봅니다. 초록불은 "시킨 명령이 모두 0으로 끝났다"는 뜻일 뿐입니다. 테스트를 돌리는 단계가 빠져 있거나 테스트가 0개여도 초록불이 켜질 수 있습니다. 백지 시험지를 냈는데 "틀린 문제 0개"라고 나오는 것과 같습니다.

그래서 테스트가 **몇 개** 돌았는지, 상자가 **실제로 만들어졌는지**를 함께 봅니다. AI가 빨간불을 없애려고 실패하는 테스트를 꺼 버리는 일도 있습니다([12장](ch12.html#trust)).
:::

## 배포 전략: 새 버전으로 갈아 끼우는 네 가지 방법 {#rollout}

검사를 통과한 상자가 준비됐습니다. 이제 사람들이 쓰는 옛 버전을 새 버전으로 바꿉니다.

마트는 손님이 많으면 계산대를 여러 개 엽니다. 프로그램도 사용자가 많으면 같은 프로그램을 서버 여러 대에서 함께 돌립니다. 지금 서버 네 대가 옛 버전을 돌리고 있습니다. 어떻게 바꿀까요?

::: {.fig src="deploy-strategies.svg"}
칸 하나가 서버 한 대입니다. 파란 칸은 옛 버전(구버전)을, 초록 칸은 새 버전(신버전)을 돌리고 있습니다. '요청'은 사용자의 부탁을 받는 쪽, '대기'는 켜 두고 기다리는 쪽입니다.
:::

- **한 번에 교체.** 네 대를 모두 끄고 새 버전으로 켭니다. 간단하지만 바꾸는 동안 아무도 접속하지 못합니다. 게임의 '서버 점검 시간'이 이것입니다.
- **롤링 배포**(rolling deployment). 한두 대씩 차례로 바꿉니다. 멈추는 시간이 없는 대신, 바꾸는 동안 두 버전이 함께 돌아갑니다.
- **블루-그린 배포**(blue-green deployment). 지금 서버 묶음(블루) 옆에 새 버전 묶음(그린)을 따로 차립니다. 미리 검사한 뒤, 요청이 들어오는 길을 한 번에 그린으로 돌립니다. 문제가 생기면 길만 다시 블루로 돌립니다. 한동안 서버가 두 배로 필요합니다.
- **카나리 배포**(canary release). 요청 100개 중 5개, 곧 5%만 새 버전으로 보냅니다. 나머지 95%는 옛 버전이 받습니다. 오류가 더 많이 나는지 비교해, 괜찮으면 조금씩 넓히고 나쁘면 멈춥니다. 탄광에 카나리아라는 새를 먼저 들여보내 위험을 살피던 데서 온 이름입니다.

혼자 만드는 앱에서는 앱을 올려 주는 서비스가 갈아 끼우기를 대신 합니다. 많은 서비스가 새 상자를 먼저 켜 놓고 길을 돌립니다. 블루-그린과 닮은 방식입니다.

::: {.tip title="망가졌으면 먼저 되돌립니다"}
새 버전을 올린 뒤 고장이 났다면 원인부터 찾지 않습니다. 먼저 바로 앞 버전으로 되돌려 사람들이 다시 쓸 수 있게 합니다. 원인은 그다음에 찾습니다. 되돌리는 법은 [다음 절의 롤백](#compat)에서 봅니다.
:::

### 기능 플래그: 올리는 날과 보여 주는 날을 따로

여기까지는 새 코드를 서버에 올리는 순간, 사용자도 바로 새 기능을 보았습니다. 이 둘을 떼어 놓을 수도 있습니다. 코드 안에 스위치를 넣어 두고, 켤지 끌지는 설정에서 읽어 옵니다. 이런 스위치를 **기능 플래그**(feature flag)라고 합니다.

새 검색 화면을 예로 들어 봅시다. 코드에 "`new_search` 스위치가 켜져 있으면 새 화면을, 꺼져 있으면 옛 화면을 보여 준다"는 갈림길을 넣습니다. 월요일에 **스위치를 끈 채로** 배포합니다. 아직 아무도 새 화면을 보지 못합니다. 며칠 뒤 사용자 열 명 중 한 명에게만 켭니다. 문제가 보이면 스위치만 끕니다.

::: {.key}
**배포**는 코드를 서버에 올리는 일이고, **출시**는 사용자에게 보여 주는 일입니다. 둘을 떼어 놓으면 따로 되돌릴 수 있습니다.
:::

## 옛 버전과 새 버전이 함께 사는 시간 {#compat}

롤링이든 카나리든 블루-그린이든 **한동안은 옛 버전과 새 버전이 함께 돌아갑니다.** 그리고 두 버전은 대개 **같은 데이터베이스**를 봅니다. 가장 아픈 사고가 여기서 납니다.

데이터베이스에 `users`라는 사용자 표가 있습니다. 이 표에는 `name`이라는 세로줄이 있고, 민지와 준호가 적혀 있습니다. 표의 세로줄을 열이라고 했습니다([17장](ch17.html)). 이 열의 이름을 `nickname`으로 바꾸고 싶습니다.

이름을 곧바로 바꾸면 어떻게 될까요? 아직 돌고 있는 옛 버전은 `name`을 찾습니다. 그런데 그 열이 없습니다. 오류가 납니다. 출석부의 칸 이름을 말없이 바꿔 버린 셈입니다. 옛 버전으로 되돌려도 똑같이 실패합니다.

그래서 세 번에 나눠서 바꿉니다.

::: {.fig src="expand-contract.svg"}
`name`을 `nickname`으로 바꾸는 세 단계. 값이 다 채워진 초록 바탕 구간에서는 두 버전이 함께 돌 수 있습니다.
:::

1. **확장.** 새 열 `nickname`을 **더하기만** 합니다. 옛 버전은 새 열을 모르는 채로 잘 돕니다.
2. **이전.** 새 버전을 배포합니다. 새 버전은 당분간 **두 열 모두에** 적습니다. 옛 버전이 아직 `name`을 읽기 때문입니다. 그동안 옛 값을 새 열에도 옮겨 채웁니다. 다 채워지면 새 버전은 `nickname`을 읽습니다.
3. **축소.** 옛 버전이 모두 사라졌는지 확인합니다. 그런 뒤에 `name` 열을 지웁니다. 지우고 나면 옛 코드로는 돌아가지 못합니다.

그림 아래쪽의 두 줄은 단계마다 구버전 코드와 신버전 코드가 제대로 도는지를 보여 줍니다. 둘 다 도는 곳은 2단계뿐입니다.

AI에게 "열 이름을 바꿔 줘"라고만 하면 대개 한 번에 바꿉니다. 사람들이 이미 쓰는 앱이라면 "더하기, 옮기기, 지우기로 나눠 줘"라고 합니다.

::: {.key}
더하는 일은 먼저 하고, **지우는 일은 맨 마지막에** 합니다. 지우기 전까지는 언제든 옛 버전으로 돌아갈 수 있습니다.
:::

### 이미 깔린 앱은 내가 바꿀 수 없습니다

서버는 내가 원할 때 새 버전으로 바꿀 수 있습니다. 사람들의 휴대전화에 깔린 앱과 게임은 그렇지 않습니다. 업데이트를 몇 달씩 미루는 사람도 있습니다. 그래서 서버는 **옛 앱이 보내는 요청도 한동안 받아 줘야** 합니다.

게임 서버가 아이템 번호를 숫자 `1024`로 알려 주다가 어느 날부터 글자 `"sword_01"`로 바꿔 보낸다고 합시다. 숫자를 기다리던 옛 앱은 답을 읽지 못하고 멈춥니다. 규칙은 앞과 같습니다. 새 항목을 **더하는** 것은 대체로 안전합니다. **빼거나 뜻을 바꾸는** 것은 옛 앱을 쓰는 사람이 충분히 줄어든 뒤에 합니다.

### 롤백: 되돌릴 수 있는 것과 없는 것

새 버전에 문제가 생기면 이전 상태로 되돌립니다. 이것을 **롤백**(rollback)이라고 합니다.

되돌리는 길은 둘입니다. 앱을 올려 주는 서비스에는 대개 지난 배포가 차례로 남아 있습니다. 그 목록에서 바로 앞 배포를 골라 다시 내보냅니다. 상자를 새로 만들지 않아서 빠릅니다. 다른 길은 `git revert`로 문제의 커밋을 취소하는 커밋을 만들어 올리는 것입니다([7장](ch07.html)). 급할 때는 앞의 길로 먼저 되돌리고, 코드도 뒤의 길로 맞춥니다. 맞추지 않으면 다음에 올릴 때 같은 문제가 다시 나갑니다.

하지만 상자를 되돌린다고 **이미 벌어진 일까지 되돌아가지는 않습니다.** 단체 대화방에 잘못 올린 글을 지워도, 이미 읽은 친구의 기억은 그대로인 것과 같습니다.

::: {.fig src="rollback-scope.svg"}
롤백하면 돌아오는 것과 그대로 남는 것.
:::

왼쪽은 돌아오는 것입니다. 상자는 `app-57`에서 `app-56`으로 바꿔 끼웁니다. `TIMEOUT`은 대답을 몇 초까지 기다릴지 정한 설정값입니다. 3으로 바꿨던 것을 다시 5로 돌립니다. 기능 플래그 `new_search`는 끄면 됩니다.

오른쪽은 남는 것입니다. 데이터베이스에서 지운 열은 돌아오지 않아서 옛 코드가 읽을 값이 없습니다. 이미 보낸 메일 3,000통은 바로잡는 메일을 따로 보내야 합니다. 두 번 빠져나간 결제는 하나씩 확인해서 돌려줘야 합니다.

그래서 내보내기 전에 묻습니다. 이번 변경에 지우기, 보내기, 결제처럼 **되돌릴 수 없는 일**이 들어 있는가?

## 공장 문단속: 공급망과 CI의 열쇠 {#supply}

마지막은 공장 자체의 안전입니다. 프로그램은 남이 만든 패키지, 빌드 도구, CI를 거쳐서 상자가 됩니다. 코드에서 상자까지 이어지는 이 길 전체를 **공급망**(supply chain)이라고 합니다. 길 어느 한 곳만 더럽혀져도 **내 코드는 그대로인데** 상자가 바뀝니다.

**들어오는 재료.** 패키지는 남이 쓴 코드이고, 설치하는 순간에 내 컴퓨터에서 실행될 수 있습니다. 그래서 꼭 필요한 패키지만 넣습니다. 잠금 파일에는 패키지마다 해시도 적혀 있어서, 내용만 바꿔치기한 가짜를 걸러 줍니다.

AI가 추천한 패키지는 실제로 있는 것인지 확인하세요. 유명한 패키지와 철자만 비슷한 가짜도 있습니다. 설치하기 전에 이름을 검색해, 많은 사람이 쓰는 패키지인지 봅니다.

**CI가 쥔 열쇠.** CI가 배포까지 하려면 서버에 들어갈 열쇠가 필요합니다. 아래 그림의 `DEPLOY_KEY`입니다. 그런데 CI는 저장소에 올라온 코드를 **그대로 실행하는 컴퓨터**입니다. 공개 저장소라면 모르는 사람이 보낸 코드도 실행합니다.

::: {.fig src="ci-keys.svg"}
한 작업에 다 맡길 때와 둘로 나눌 때. 나누면 배포 열쇠는 검토를 거친 코드만 만납니다.
:::

그림 왼쪽처럼 검사와 배포를 한 작업에 맡기면, 밖에서 온 코드가 사람이 살펴보기도 전에 실행되어 같은 작업 안의 열쇠를 읽어 갈 수 있습니다. 그래서 오른쪽처럼 둘로 나눕니다. 검사 작업에는 코드를 읽고 테스트하는 권한만 줍니다. 배포 열쇠는 배포 작업에만 두고, 배포 작업은 사람이 검토하고 합친 코드만 실행합니다.

이것이 [19장](ch19.html)에서 배운 최소 권한입니다. 열쇠는 CI나 서비스의 비밀 값 칸에만 넣고, 저장소의 파일에는 적지 않습니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 빌드 / 배포 | 상자를 만드는 일 / 상자를 사람들이 쓰는 곳에 올려서 켜는 일 |
| 주문서의 범위 / 잠금 파일 | 받아도 되는 범위 / 실제로 받은 정확한 버전 |
| 스테이징 / 운영 | 운영을 닮은 연습 무대 / 실제 사용자가 쓰는 곳 |
| CI / CD | 올릴 때마다 자동으로 빌드하고 검사하는 일 / 검사한 상자를 배포까지 자동으로 잇는 일 |
| 배포 / 출시 | 코드를 서버에 올리는 일 / 사용자에게 기능을 보여 주는 일 |
| 블루-그린 / 카나리 | 새 묶음으로 모두를 한 번에 넘김 / 조금만 먼저 보내고 차츰 넓힘 |

## 실전 사례 {#case}

::: {.case title="내 노트북에서는 되는데 CI에서는 빨간불이 켜진다"}
서연이는 학교 축제에서 선보일 작은 게임을 만들고 있습니다. AI에게 점수 그래프를 넣어 달라고 했습니다. AI는 `chart-lib` 패키지를 추가했습니다. 서연이의 노트북에서는 그래프가 잘 나옵니다. 그런데 저장소에 올리자마자 CI에 빨간불이 켜졌습니다.

1. **어느 단계에서 멈췄는지 봅니다.** 3번 테스트가 아니라 1번 설치(`npm ci`)입니다. 코드가 아니라 재료 쪽 문제입니다.
2. **처음 나온 오류를 읽습니다.** `package.json and package-lock.json … are in sync`라는 글 아래에 `Missing: chart-lib@1.4.2 from lock file`이 보입니다. 잠금 파일에 `chart-lib`이 없다는 말입니다. 올린 커밋을 보니 주문서만 있고 잠금 파일은 빠져 있습니다.
3. **잠금 파일을 함께 올립니다.** 다시 돌리니 설치가 0으로 끝납니다. 빌드와 테스트도 통과해 초록불이 켜집니다.

CI의 빨간불은 방해꾼이 아닙니다. **적어 두지 않은 재료를 찾아 준 검사원**입니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- 코드는 **커밋 → 빌드 → 테스트 → 배포**를 거쳐 사용자에게 갑니다. 사람들이 쓰는 것은 그 코드로 만든 상자, 곧 **산출물**입니다.
- 버전 `1.4.2`는 주, 부, 수 세 자리입니다. 맨 왼쪽 주 버전이 오르면 쓰는 법이 바뀐 것입니다.
- **잠금 파일**은 실제로 받은 버전을 모두 적은 영수증입니다. 코드와 함께 커밋하고, 서버와 CI는 잠금 파일대로만 설치합니다. **의존성 충돌**로 설치가 막혀도 억지로 넘기지 않습니다.
- 상자는 **한 번만 만들어** 검사한 그대로 올립니다. 주소와 열쇠처럼 환경마다 다른 값은 **환경 변수**로 밖에서 건넵니다.
- **CI**는 코드를 올릴 때마다 빈 컴퓨터에서 설치, 빌드, 테스트를 돌립니다. 배포까지 자동으로 이으면 **CD**입니다.
- 빨간불이 켜지면 **빌드 로그**에서 멈춘 단계와 첫 오류를 찾습니다. `main`에 합치기 전에 **미리 보기 배포**로 확인합니다.
- 새 버전은 **조금씩** 내보내고, 기능은 **플래그**로 따로 켭니다.
- 두 버전이 함께 도는 동안 더하기는 먼저, **지우기는 마지막에** 합니다. 옛 앱의 요청도 한동안 받아 줍니다.
- 망가졌으면 먼저 **롤백**하고 원인은 그다음에 찾습니다. 롤백해도 지운 데이터와 보낸 메일은 돌아오지 않습니다.
:::

## 확인 문제 {#quiz}

::: {.q}
AI에게 게임의 버그를 고쳐 달라고 했더니 "수정 완료"라고 답했습니다. 그런데 친구가 접속해 보니 버그가 그대로입니다. 어떻게 된 일일까요?

::: {.a}
"수정 완료"는 대개 코드 파일을 고쳤다는 뜻입니다. 레시피만 고친 셈입니다. 커밋해서 올리고, 빌드로 새 상자를 만들고, 테스트하고, 배포까지 해야 친구가 접속하는 게임이 바뀝니다.
:::
:::

::: {.q}
분식집에 양념을 대 주는 회사가 "양념이 1.4.2에서 2.0.0이 됩니다"라고 알려 왔습니다. "1.4.3이 됩니다"라고 했을 때와 무엇이 다를까요?

::: {.a}
2.0.0은 맨 왼쪽 자리(주 버전)가 오른 것입니다. 쓰는 법이 바뀌었다는 뜻이니 레시피를 다시 맞춰야 할 수 있습니다. 1.4.3은 맨 오른쪽 자리만 올랐으니 잘못된 곳만 고쳤다는 약속입니다. 다만 약속일 뿐이니 어느 쪽이든 맛은 직접 확인합니다.
:::
:::

::: {.q}
월요일에 내 노트북에 설치했을 때는 그래프가 잘 나왔습니다. 금요일에 친구 노트북에 같은 프로젝트를 설치했더니 그래프 모양이 다릅니다. 코드는 한 글자도 바꾸지 않았습니다. 어떻게 된 일이고, 어떻게 막을까요?

::: {.a}
그 사이에 그래프 패키지의 새 버전이 나왔을 가능성이 큽니다. 주문서에는 범위만 적혀 있어서 금요일에는 더 새로운 버전이 깔렸습니다. 잠금 파일을 함께 올리고 그대로만 설치하면, 언제 어디서 설치해도 같은 재료를 받습니다.
:::
:::

::: {.q}
내 컴퓨터에서 `localhost:3000`으로 열면 점수판이 잘 나옵니다. 인터넷에 올린 주소로 열면 점수판만 비어 있습니다. 빌드는 성공했습니다. 무엇부터 확인할까요?

::: {.a}
내 컴퓨터와 올린 곳에서 달라지는 것을 봅니다. 코드에 `localhost` 주소가 그대로 적혀 있지 않은지, 서비스의 설정 화면에 환경 변수를 넣었는지 확인합니다. `.env` 파일은 올리지 않으므로 올린 곳에는 값이 저절로 생기지 않습니다.
:::
:::

::: {.q}
새 버전 `app-57`이 실수로 잘못된 안내 메일 3,000통을 보냈습니다. 얼른 `app-56`으로 롤백했습니다. 이제 다 해결됐을까요?

::: {.a}
아닙니다. 롤백으로 돌아오는 것은 실행하는 상자와 설정입니다. 이미 보낸 3,000통은 그대로 남아 있습니다. 바로잡는 메일을 따로 보내야 합니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
배포를 맡길 때는 "배포해 줘"라고만 하지 않습니다. **무엇이 바뀌었고, 무엇을 검사했고, 어떻게 되돌릴지**를 먼저 적어 오게 합니다. `main`에 올리는 일은 내가 확인한 뒤에 합니다.

> 이 변경을 내보낼 준비를 해 줘. `main`에는 올리지 말고 `fix-score` 브랜치에만 올려 줘. 먼저 바뀐 것을 코드, 패키지(`package.json`과 잠금 파일), 환경 변수, 데이터베이스로 나눠 표로 보여 줘. 그다음 `npm ci`, `npm run build`, `npm test`를 차례로 돌리고 종료 코드와 돌아간 테스트 개수를 알려 줘. 올린 곳에 새로 넣어야 할 환경 변수는 이름만 알려 줘. 지우기, 메일 보내기, 결제처럼 되돌릴 수 없는 일은 따로 표시하고, 되돌리는 순서도 적어 줘. 오류가 나도 테스트를 끄거나 `--force`로 넘기지 말고 멈춰서 알려 줘.

**받은 답에서 확인할 것**

- 주문서가 바뀌었다면 잠금 파일도 함께 바뀌었는가. 부탁하지 않은 패키지나 버전 변경은 없는가.
- 설치, 빌드, 테스트가 모두 종료 코드 0으로 끝났고, 테스트 개수가 줄지 않았는가.
- 코드에 `localhost` 주소나 비밀 값이 그대로 적혀 있지 않은가.
- 데이터베이스의 열을 한 번에 지우거나 이름을 바꾸지 않는가.
- 미리 보기 주소에서 고친 곳이 실제로 고쳐져 있는가.

**AI가 자주 하는 실수**

- **빨간불을 끄는 쪽으로 고칩니다.** 실패한 테스트를 지우거나 설치 오류를 `--force`로 넘깁니다. diff에서 테스트 파일과 CI 설정 파일이 바뀌었는지 봅니다.
- **부탁하지 않은 패키지를 바꿉니다.** 주 버전을 올리거나 잠금 파일을 새로 만듭니다. `git diff package.json`으로 알아챕니다.
- **내 컴퓨터의 값을 코드에 적습니다.** `http://localhost:3000` 같은 주소가 남으면 올린 곳에서는 통하지 않습니다. 환경 변수로 빼게 합니다.
- **"배포했습니다"로 끝냅니다.** push만 하고 빌드가 실패한 줄 모르기도 합니다. 서비스의 배포 기록을 보고, 주소를 직접 열어 봅니다([30장](ch30.html#verify)).
:::

## 용어 정리 {#terms}

::: {.terms}
배포 (deployment)
:   만든 상자를 사람들이 쓰는 곳에 가져다 놓고 켜는 일.

유의적 버전 (Semantic Versioning, semver)
:   버전을 세 자리로 적어 얼마나 크게 바뀌었는지 알리는 약속.

잠금 파일 (lockfile)
:   실제로 설치한 패키지의 정확한 버전을 모두 적어 둔 기록.

의존성 충돌 (dependency conflict)
:   두 패키지가 같은 패키지의 서로 다른 버전을 달라고 하는 상황.

산출물 (artifact)
:   빌드로 만들어진, 실제로 내보내는 묶음.

해시 (hash)
:   파일 내용으로 계산한 짧은 글자열. 내용이 조금만 달라도 값이 달라져 지문처럼 쓴다.

환경 (environment)
:   프로그램이 돌아가는 무대. 컴퓨터, 데이터베이스, 설정이 한 벌씩 들어 있다.

스테이징 (staging)
:   운영에 올리기 전에 검사하는, 운영을 닮은 연습 무대.

환경 변수 (environment variable)
:   프로그램을 켤 때 밖에서 이름을 붙여 건네는 값. 환경마다 다른 설정을 담는다.

CI (Continuous Integration)
:   지속적 통합. 코드를 올릴 때마다 자동으로 빌드하고 검사하는 방식.

CD (Continuous Delivery)
:   지속적 제공. 검사를 통과한 상자를 서버에 올리는 일까지 자동으로 잇는 방식.

파이프라인 (pipeline)
:   설치, 빌드, 테스트처럼 차례로 이어서 자동으로 실행하는 단계들.

미리 보기 배포 (preview deployment)
:   `main`에 합치기 전의 브랜치를 임시 주소에 올려 먼저 확인하는 배포.

빌드 로그 (build log)
:   설치하고 빌드하는 동안 화면에 찍힌 글을 모아 둔 기록.

롤링 배포 (rolling deployment)
:   서버를 한두 대씩 차례로 새 버전으로 바꾸는 방식.

블루-그린 배포 (blue-green deployment)
:   새 버전 서버 묶음을 따로 차려 두고 요청을 한 번에 넘기는 방식.

카나리 배포 (canary release)
:   요청의 일부만 새 버전으로 보내 지켜보며 넓혀 가는 방식.

기능 플래그 (feature flag)
:   서버에 올려 둔 기능을 설정으로 켜고 끄는 스위치.

출시
:   올려 둔 기능을 사용자에게 보여 주는 일.

롤백 (rollback)
:   문제가 생겼을 때 이전 상자나 설정으로 되돌리는 일.

공급망 (supply chain)
:   코드가 패키지, 빌드 도구, CI를 거쳐 상자가 되기까지의 길 전체.
:::
