::: {.lead}
친구에게 편지를 보내려면 주소가 있어야 합니다. 편지는 우체국 여러 곳을 거쳐 친구 집에 도착합니다. 컴퓨터끼리 메시지를 주고받을 때도 똑같습니다. 주소가 있고, 중간에 거쳐 가는 곳이 있습니다. 컴퓨터들이 서로 이어져 메시지를 주고받는 길을 **네트워크**라고 합니다. 인터넷은 전 세계를 잇는 가장 큰 네트워크입니다.
:::

::: {.goals}
- 컴퓨터의 주소가 어떻게 생겼는지 말할 수 있습니다.
- `localhost:3000` 같은 주소를 읽고, 누가 열 수 있는지 말할 수 있습니다.
- 사이트 이름이 주소로 바뀌는 과정을 설명할 수 있습니다.
- 메시지가 여러 곳을 거쳐 도착하는 과정을 설명할 수 있습니다.
- 인터넷이 안 될 때 어디서 막혔는지 차례로 확인할 수 있습니다.
:::

## 네트워크는 컴퓨터 사이의 우편망입니다 {#post}

컴퓨터끼리 이야기할 때는 역할이 둘로 나뉩니다. 먼저 말을 거는 쪽과, 기다리다가 대답하는 쪽입니다.

유튜브를 볼 때를 떠올려 봅시다. 내 휴대전화가 "이 영상 보여 줘" 하고 먼저 말을 겁니다. 유튜브의 컴퓨터는 기다리고 있다가 영상을 보내 줍니다. 먼저 말을 거는 쪽을 **클라이언트**(client), 기다리다가 대답하는 쪽을 **서버**(server)라고 부릅니다.

클라이언트가 보내는 말은 **요청**, 서버가 돌려주는 대답은 **응답**이라고 합니다.

AI에게 앱을 만들어 달라고 해도 이 두 역할이 나옵니다. 화면을 띄우는 크롬 같은 브라우저가 클라이언트이고, 화면이 달라는 자료를 내주는 프로그램이 서버입니다. AI가 "서버를 켰습니다"라고 하면 기다리는 프로그램 하나가 돌기 시작했다는 뜻입니다.

### 왜 잘게 나눠 보낼까

사진 한 장을 통째로 보내는 것은 이삿짐을 아주 긴 트럭 한 대에 다 싣는 것과 같습니다. 트럭이 지나가는 동안 다른 차는 기다려야 합니다. 사고가 나면 짐을 전부 다시 보내야 합니다.

그래서 네트워크는 보낼 것을 작은 조각으로 나눕니다. 조각마다 받는 곳 주소와 번호를 붙여 따로 보냅니다. 번호표가 붙은 작은 소포인 셈입니다. 이 조각을 **패킷**(packet)이라고 합니다.

::: {.fig src="packets.svg"}
사진 한 장이 패킷 4개로 나뉘어 갑니다. 가운데의 '라우터'는 길목에서 패킷을 넘겨 주는 장치로, 뒤에서 다시 만납니다.
:::

그림에서 받는 쪽을 보세요. 패킷들이 두 갈래 길로 나뉘어 가서 2, 1, 4, 3 순서로 도착했습니다. 그래도 괜찮습니다. 받는 쪽이 번호를 보고 1, 2, 3, 4로 다시 맞춥니다.

작게 나누면 길을 여럿이 함께 쓸 수 있습니다. 내 소포 사이사이에 남의 소포가 끼어 갑니다. 하나를 잃어버려도 그 조각만 다시 보내면 됩니다.

패킷이 다니는 길은 대부분 케이블, 곧 통신용 줄입니다. 집 안에서는 랜선이나 와이파이 전파가 패킷을 나릅니다. 도시와 나라 사이에서는 **광섬유**가 나릅니다. 빛으로 신호를 보내는 가느다란 유리 줄입니다.

::: {.photo src="submarine-cable-map.jpg"}
세계 해저 통신 케이블 지도. 붉은 선이 바다 밑에 깔린 케이블입니다. 바다를 건너는 데이터는 대부분 위성이 아니라 이 케이블을 지납니다.
:::

::: {.photos}
::: {.photo src="fiber-optic.jpg"}
**광섬유 케이블.** 색색의 관 끝에 머리카락처럼 가는 유리 줄이 보입니다. 빛이 이 속을 달립니다.
:::

::: {.photo src="ethernet-cable.jpg"}
**랜선.** 투명한 플러그 안에 금색 핀 여덟 개가 보입니다. 공유기와 컴퓨터를 잇습니다.
:::
:::

## IP 주소와 포트: 건물 주소와 호수 {#address}

소포를 보내려면 받는 곳 주소가 있어야 합니다. 네트워크에 이어진 컴퓨터에도 주소가 있습니다. `203.0.113.9`처럼 0부터 255까지의 숫자 네 개를 점으로 이어 씁니다. 이 주소를 **IP 주소**(IP address)라고 합니다. 우편으로 치면 **건물 주소**입니다.

IP는 Internet Protocol을 줄인 말입니다. **프로토콜**(protocol)은 주고받는 양쪽이 지키기로 한 약속을 뜻합니다.

그런데 건물 주소만으로는 모자랍니다. 컴퓨터 한 대에서는 프로그램 여러 개가 함께 돌아갑니다. 게임을 하면서 음성 채팅도 하고 음악도 듣습니다. 소포가 컴퓨터에 도착하면 **어느 프로그램에게** 줄지도 정해야 합니다.

그래서 프로그램마다 번호를 하나씩 맡습니다. 건물 안의 **호수**와 같습니다. 이 번호를 **포트**(port)라고 합니다. 1부터 65535까지 쓸 수 있습니다.

::: {.fig src="ip-port.svg"}
`203.0.113.9:443`은 "203.0.113.9 건물의 443호"라는 뜻입니다. 주소 뒤에 쌍점(:)을 찍고 포트를 적습니다.
:::

그림의 건물은 서버 한 대입니다. 방마다 다른 프로그램이 삽니다.

| 포트 | 사는 프로그램 |
|---|---|
| 22 | SSH 서버. 멀리서 이 컴퓨터에 들어와 일하게 해 줍니다(원격 접속) |
| 443 | 웹 서버. 웹 페이지를 보내 주고, 앱이 자료를 달라는 요청(API)에도 답합니다 |
| 5432 | 데이터베이스. 자료를 모아 둡니다 |
| 8080 | 빈 방. 기다리는 프로그램이 없습니다 |

8080호로 보낸 소포는 건물 주소가 맞아도 받을 사람이 없습니다.

브라우저의 주소창에 포트를 적지 않으면 정해진 호수로 갑니다. 주소가 `https`로 시작하면 443호, `http`로 시작하면 80호입니다.

만드는 동안 내 컴퓨터에 켜는 서버는 3000, 5173, 8000 같은 번호를 흔히 씁니다. 특별한 뜻은 없고, 도구마다 버릇처럼 고르는 호수입니다.

### 소켓: 프로그램이 받는 우편함

방을 차지하려면 프로그램이 먼저 신청해야 합니다. 운영체제([3장](ch03.html))에게 "443호로 오는 것은 저에게 주세요" 하고 말합니다. 그러면 운영체제가 우편함을 하나 내줍니다. 이 우편함을 **소켓**(socket)이라고 합니다. 프로그램은 소켓에서 소포를 꺼내 읽고, 보낼 것은 소켓에 넣습니다.

호수 하나는 한 프로그램만 차지할 수 있습니다. 주인이 있는 호수를 또 신청하면 `address already in use`라는 오류가 뜹니다. "그 주소는 이미 쓰는 중"이라는 뜻입니다. `EADDRINUSE`라고 줄여 찍히기도 합니다. 범인은 대개 아까 켜 놓고 끄지 않은 내 프로그램입니다. 찾아서 끄는 방법은 [6장](ch06.html)에 있습니다.

### IPv4와 IPv6: 주소가 모자라서 만든 긴 주소

숫자 하나는 0부터 255까지 256가지입니다. 그래서 숫자 네 개로 만들 수 있는 주소는 256 × 256 × 256 × 256, 약 43억 개입니다. 세계 인구 80억 명에게 하나씩도 돌아가지 않습니다.

그래서 훨씬 긴 주소를 새로 만들었습니다. `2001:db8::1`처럼 숫자와 알파벳을 쌍점으로 이어 씁니다. 숫자 네 개짜리 주소를 **IPv4**, 긴 새 주소를 **IPv6**라고 합니다. IP 약속의 4번째 판, 6번째 판이라는 뜻입니다. 지금은 둘을 함께 씁니다.

::: {.key}
IP 주소는 **어느 컴퓨터인지**, 포트는 **그 안의 어느 프로그램인지**를 정합니다.
:::

## localhost와 바인딩: 누구의 요청까지 받을까 {#localhost}

편지 받는 곳에 "우리 집"이라고만 썼다고 합시다. 내가 쓰면 내 집이고, 친구가 쓰면 친구네 집입니다. 쓰는 사람에 따라 가리키는 곳이 달라집니다.

네트워크에도 이런 이름이 있습니다. `localhost`입니다. 언제나 **이 이름을 입력한 기기 자신**을 뜻합니다. 숫자 주소로는 `127.0.0.1`이고, IPv6 주소로는 `::1`입니다.

노트북으로 우리 반 퀴즈 게임 사이트를 만든다고 합시다. 만드는 동안에는 서버 프로그램을 내 노트북에 켜 두고 시험합니다. 이렇게 시험하려고 내 컴퓨터에 켜 둔 서버를 **개발 서버**라고 합니다. 이 서버가 3000호에서 기다린다고 합시다.

개발 서버를 켜면 터미널([5장](ch05.html))에 주소가 찍힙니다. AI 코딩 도구가 대신 켜 줘도 같습니다. 도구마다 모양은 조금 다르지만 대개 이런 줄입니다.

```text
Local:   http://localhost:3000/
```

`http://` 뒤를 쌍점에서 끊어 읽습니다. 앞의 `localhost`는 어느 컴퓨터인지, 뒤의 `3000`은 몇 호인지입니다. 노트북 브라우저에 `localhost:3000`을 입력하면 사이트가 열립니다. "나 자신의 3000호"라는 뜻이기 때문입니다.

::: {.tip}
브라우저에는 터미널에 찍힌 주소를 그대로 옮깁니다. 3000호가 이미 쓰이는 중이면 3001호로 옮겨 켜지는 도구도 있습니다. 이때 버릇대로 3000을 열면 아까 켜 둔 옛 서버가 나와서, 고친 것이 화면에 보이지 않습니다.
:::

휴대전화에서 `localhost:3000`을 열면 열리지 않습니다. 휴대전화는 **자기 자신의** 3000호를 두드립니다. 거기에는 아무도 없습니다.

::: {.try}
브라우저 주소창에 `localhost:3999`를 입력해 보세요. 그 호수에 켜 둔 서버가 없으니 연결할 수 없다는 화면이 뜹니다. 크롬은 "연결을 거부했습니다"라는 말 아래에 `ERR_CONNECTION_REFUSED`라고 적어 줍니다. 고장이 아닙니다. "이 기기의 3999호에는 아무도 없다"는 정확한 대답입니다.
:::

그러면 노트북이 와이파이에서 받은 주소 `192.168.0.5`를 써서 `192.168.0.5:3000`을 입력하면 될까요? 서버를 어떻게 켰느냐에 달렸습니다.

서버 프로그램은 켜질 때 **어느 주소로 들어오는 요청을 받을지** 정합니다. 가게로 치면 주문 창구를 어느 쪽으로 내느냐입니다. 이 일을 **바인딩**(binding)이라고 합니다. 서버를 주소에 '묶는다'는 뜻입니다.

- `127.0.0.1`에 묶으면 안쪽으로만 창구를 냅니다. 같은 컴퓨터 안의 프로그램만 접속할 수 있습니다.
- `0.0.0.0`에 묶으면 모든 방향으로 창구를 냅니다. 같은 와이파이를 쓰는 다른 기기도 접속할 수 있습니다.

::: {.fig src="binding.svg"}
위는 `127.0.0.1:3000`에, 아래는 `0.0.0.0:3000`에 묶은 서버입니다. 같은 와이파이의 휴대전화는 아래쪽 서버에만 닿습니다.
:::

개발 서버는 흔히 `127.0.0.1`에만 묶인 채로 켜집니다. 남이 함부로 들어오지 못하게 하려는 것입니다.

### 같은 와이파이의 휴대전화에서 열어 보기

만든 화면을 휴대전화로도 보려면 세 가지를 합니다.

1. **서버를 `0.0.0.0`에 묶어 다시 켭니다.** 켜는 명령에 `--host 0.0.0.0` 같은 옵션을 붙입니다. 옵션 이름은 도구마다 달라서 AI에게 묻습니다.
2. **노트북의 주소를 찾습니다.** 이렇게 켜면 터미널에 `Network: http://192.168.0.5:3000/` 같은 줄이 더 찍히곤 합니다. 없으면 노트북의 와이파이 설정 화면에서 'IP 주소'를 봅니다.
3. **휴대전화 브라우저에 그 주소를 포트까지 입력합니다.** 두 기기가 같은 와이파이에 있어야 합니다.

다 봤으면 원래대로 다시 켭니다.

::: {.warn}
`0.0.0.0`은 서버가 받는 범위를 정하는 표시이지 브라우저에 입력하는 주소가 아닙니다. 터미널에 `http://0.0.0.0:3000`이라고 찍혀도 브라우저에는 `localhost:3000`을 입력합니다. 카페 같은 곳의 와이파이에서 이렇게 열어 두면 모르는 사람도 접속할 수 있습니다.
:::

::: {.key}
`localhost`는 언제나 **입력한 기기 자신**입니다.
:::

## 공유기와 라우터: 집 안 주소, 바깥 주소, 길 찾기 {#router}

아파트 단지마다 101동이 있습니다. 그래도 헷갈리지 않습니다. 그 단지 안에서만 쓰는 이름이기 때문입니다.

방금 본 `192.168.0.5`도 **집 안에서만 통하는 주소**입니다. 옆집 노트북도 같은 주소를 쓸 수 있습니다. 주소는 이렇게 두 가지입니다.

- **사설 IP**(private IP)는 집이나 학교 안에서만 쓰는 주소입니다. 보통 `192.168.`이나 `10.`으로 시작합니다.
- **공인 IP**(public IP)는 인터넷 전체에서 하나뿐인 주소입니다. 통신사가 우리 집 공유기에 하나를 내줍니다.

와이파이를 내보내는 공유기는 아파트로 치면 단지의 **우편실**입니다. 집 안 기기가 바깥으로 소포를 보내면, 공유기는 '보낸 곳'을 자기 공인 IP로 바꿔 적습니다. 바꾼 내용은 장부에 적어 둡니다. 답장이 오면 장부를 보고 원래 기기에 전해 줍니다. 이 주소 바꾸기를 **NAT**(Network Address Translation, 주소 변환)라고 합니다.

::: {.fig src="nat.svg"}
공유기를 지나면 '보낸 곳'이 사설 IP에서 공인 IP로 바뀝니다. 서버에게는 공유기 주소만 보입니다.
:::

그림의 공유기는 주소가 둘입니다. 안쪽은 `192.168.0.1`, 바깥은 공인 IP `198.51.100.7`입니다. 이 장의 주소는 모두 예로 든 숫자입니다.

아래쪽 주소 딱지를 보세요. 노트북이 적은 '보낸 곳' `192.168.0.5:51000`이 공유기를 지나며 `198.51.100.7:62001`로 바뀝니다. 쌍점 뒤의 숫자는 답장을 받을 포트입니다. '받는 곳'인 서버 주소 `203.0.113.9:443`은 그대로입니다.

### 내 화면을 멀리 사는 친구가 못 여는 까닭

장부에는 안에서 먼저 나간 것만 적힙니다. 그래서 바깥에서 **먼저** 집 안 기기에 말을 걸 수는 없습니다. 장부에 적힌 것이 없으니 공유기가 누구에게 줄지 모릅니다.

노트북에서 잘 열리는 퀴즈 게임 주소를 다른 집 친구에게 보내도 열리지 않는 까닭이 이것입니다. 친구가 무엇을 입력해도 내 노트북에는 닿지 않습니다.

| 친구가 입력한 주소 | 찾아가는 곳 | 결과 |
|---|---|---|
| `localhost:3000` | 친구의 기기 자신 | 거기에는 내 서버가 없음 |
| `192.168.0.5:3000` | 친구네 집 안의 기기 | 내 노트북이 아님 |
| `198.51.100.7:3000` | 우리 집 공유기 | 장부에 없어서 버려짐 |

친구에게 보여 주려면 사이트를 인터넷에서 늘 켜져 있는 서버로 옮겨야 합니다. 이 일을 "인터넷에 올린다"고 하고, [31장](ch31.html#deploy)에서 해 봅니다. 잠깐만 보여 줄 때는 내 노트북으로 통하는 임시 주소를 만들어 주는 도구(예: ngrok)도 씁니다. 다 보여 주면 끕니다.

::: {.warn}
공유기 설정에서 문을 하나 열어 바깥 요청을 내 컴퓨터로 넘기는 방법도 있습니다. '포트 포워딩'이라고 합니다. AI가 권해도 따르지 않는 편이 좋습니다. 집 컴퓨터를 인터넷 전체에 내놓는 일이라, 모르는 사람도 그 문을 두드릴 수 있습니다.
:::

### 라우터: 다음 우체국만 정합니다

편지는 받는 집으로 곧장 날아가지 않습니다. 동네 우체국에서 우편 집중국으로 갑니다. 집중국은 편지를 모아 지역별로 나누는 곳입니다. 거기서 다음 집중국으로, 다시 배달 우체국으로 건너갑니다. 단계마다 주소를 보고 **다음에 어디로 넘길지**만 정합니다.

네트워크에서 이 일을 하는 장치를 **라우터**(router)라고 합니다.

내 노트북은 인터넷 지도를 모릅니다. "집 밖으로 가는 것은 전부 공유기에게 준다"는 것만 압니다. 이렇게 바깥으로 나가는 첫 문을 **게이트웨이**(gateway)라고 합니다. 집에서는 공유기가 게이트웨이입니다.

::: {.fig src="hops.svg"}
위는 편지, 아래는 패킷이 가는 길입니다. 그림의 '망'은 네트워크를 뜻합니다. 어느 라우터도 길 전체를 알지 못하지만, 한 칸씩 넘기다 보면 서버에 닿습니다.
:::

아래쪽 상자에 붙은 번호는 패킷이 건넌 칸을 센 것입니다. 여기서는 다섯 칸 만에 서버에 닿았습니다.

::: {.try}
패킷이 거쳐 가는 라우터를 직접 볼 수 있습니다. 터미널에 치는 명령입니다.

```bash
traceroute example.com
```

`traceroute`는 "가는 길을 보여 줘"라는 명령입니다. 윈도우에서는 `tracert`라고 칩니다. 결과의 한 줄이 라우터 하나이고, 첫 줄은 대개 우리 집 공유기입니다. `* * *`만 나오는 줄은 대답하지 않는 라우터일 뿐 고장이 아닙니다.
:::

## DNS: 이름을 주소로 바꿔 주는 안내소 {#dns}

친구에게 전화할 때 번호를 외워서 누르지 않습니다. 연락처에서 이름을 누르면 휴대전화가 번호를 찾아 겁니다.

인터넷도 같습니다. 사람은 `203.0.113.9` 같은 숫자 대신 `example.com` 같은 이름을 씁니다. 이런 사이트 이름을 **도메인**(domain)이라고 합니다.

하지만 패킷에 적을 수 있는 것은 IP 주소뿐입니다. 그래서 이름을 주소로 바꿔 주는 안내소가 있습니다. 이 안내소를 **DNS**(Domain Name System)라고 합니다.

::: {.fig src="dns-lookup.svg"}
이름 하나를 찾는 순서입니다. 가까운 곳에 답이 있으면 ①에서 끝나고, 없을 때만 바깥에 물어봅니다.
:::

- **① 적어 둔 것을 먼저 봅니다.** 브라우저와 운영체제는 얼마 전에 찾은 주소를 적어 둡니다. 이렇게 다시 쓰려고 가까이 적어 두는 곳이 **캐시**(cache)입니다([1장](ch01.html#hierarchy)).
- **② 없으면 대신 찾아 주는 서버에게 묻습니다.** 이 서버를 **리졸버**(resolver)라고 합니다. 보통 통신사가 맡아 돌립니다.
- **③④⑤ 리졸버가 차례로 물어 갑니다.** 맨 위의 루트 서버는 "`.com`은 저쪽에 물어봐"라고 알려 줍니다. `.com` 서버는 "`example.com`은 저쪽에"라고 알려 줍니다. 마지막으로 `example.com` 담당 서버가 "주소는 `203.0.113.9`"라고 답합니다.
- **⑥ 리졸버가 답을 돌려줍니다.** 내 컴퓨터는 그 답을 캐시에 넣어 둡니다.

### TTL: 답의 유통기한

캐시의 답은 언제까지 써도 될까요? 담당 서버가 답에 시간을 붙여 줍니다. "300초 동안은 다시 묻지 말고 이 답을 쓰세요" 하는 식입니다. 이 시간을 **TTL**(Time To Live)이라고 합니다. 우유의 유통기한과 같습니다.

그래서 사이트가 다른 서버로 이사해 주소가 바뀌어도 모두가 곧바로 새 주소로 가지는 않습니다. 캐시에 옛 주소가 남은 사람은 TTL이 끝날 때까지 옛 주소로 갑니다.

### 레코드: 안내소 장부의 한 줄

담당 서버는 장부를 보고 답합니다. 장부에는 "이 이름은 이 주소"라는 줄이 적혀 있습니다. 이 한 줄을 **레코드**(record)라고 합니다. 자주 만나는 종류는 셋입니다.

| 종류 | 뜻 | 예 |
|---|---|---|
| A | 이름 → IPv4 주소 | `example.com` → `203.0.113.9` |
| AAAA | 이름 → IPv6 주소 | `example.com` → `2001:db8::1` |
| CNAME | 별명 → 원래 이름 | `www.example.com` → `example.com` |

A는 주소(Address)의 첫 글자입니다. CNAME은 "그 이름으로 다시 찾아보세요"라는 뜻입니다. `www.example.com`을 물으면 `example.com`을 한 번 더 찾아서 주소를 얻습니다.

### 도메인을 사서 내 사이트에 붙일 때

이 장부를 내 손으로 적는 때가 있습니다. 인터넷에 올린 내 사이트에 이름을 붙일 때입니다.

1. **도메인을 삽니다.** 파는 곳에 해마다 돈을 내고 빌려 씁니다.
2. **적을 값을 받습니다.** 사이트를 올려 둔 서비스가 "이 레코드를 넣으세요" 하고 알려 줍니다. IP 주소를 주면 A 레코드에, 다른 이름을 주면 CNAME 레코드에 적습니다.
3. **도메인을 산 곳의 DNS 설정 화면에 적습니다.** 칸은 대개 종류(Type), 이름(Name 또는 Host), 값(Value), TTL 넷입니다. 이름 칸의 `@`는 산 도메인 그 자체를 뜻합니다.
4. **기다립니다.** 세계 곳곳의 리졸버 캐시에 옛 답이 TTL 동안 남아 있습니다. "그런 이름은 없다"는 답도 남습니다. 그래서 몇 분에서 길면 하루 이틀이 걸립니다.
5. **확인합니다.** 아래의 `nslookup`으로 새 주소가 나오는지 봅니다.

기다리는 동안 값을 이것저것 바꾸면 무엇이 맞는 값이었는지 알 수 없게 됩니다. 철자만 다시 확인하고 기다립니다.

::: {.warn}
DNS가 알려 주는 것은 건물 주소까지입니다. 서버가 켜져 있는지는 알려 주지 않습니다. 가게 주소를 알아도 가게 문은 닫혀 있을 수 있습니다.
:::

::: {.try}
이름을 주소로 바꿔 보는 터미널 명령입니다.

```bash
nslookup example.com
```

`nslookup`은 "이 이름의 주소를 찾아 줘"라는 명령입니다. 결과 맨 위의 `Server`는 내가 쓰는 리졸버입니다. `Name` 아래의 `Address`가 찾아낸 IP 주소, 곧 A 레코드에 적힌 값입니다. 주소가 둘 이상 나오기도 합니다.
:::

## 계층과 캡슐화: 편지를 봉투에, 봉투를 상자에 {#layers}

친구에게 편지를 보낸다고 합시다. 나는 내용만 씁니다. 편지를 넣은 봉투에는 "몇 호 누구에게"를 적습니다. 봉투를 넣은 택배 상자에는 건물 주소를 적습니다. 배달 차는 상자를 다음 정거장까지만 실어다 줍니다.

저마다 자기 일만 합니다. 편지를 쓰는 사람은 배달 차가 어느 길로 가는지 몰라도 됩니다. 네트워크도 일을 이렇게 층층이 나눠 맡깁니다. 이 층 하나하나를 **계층**(layer)이라고 합니다.

::: {.fig src="encapsulation.svg"}
보낼 때는 위에서 아래로 포장이 한 겹씩 늘어납니다. 받는 쪽은 거꾸로 한 겹씩 벗겨 편지를 꺼냅니다.
:::

1. **편지.** 앱이 보낼 내용을 씁니다. 그림의 `GET /cart`는 "장바구니를 보여 줘"라는 요청입니다. 인터넷 가게에 담아 둔 물건 목록을 달라는 말입니다. 이런 내용을 쓰는 규칙을 HTTP라고 하고, [15장](ch15.html)에서 배웁니다.
2. **봉투.** 포트 번호와 순서 번호를 적습니다. 그림에서는 "포트 443, 순서 1"입니다. 이 일을 맡은 약속이 TCP이고, 다음 절에서 만납니다.
3. **택배 상자.** 받는 컴퓨터의 IP 주소 `203.0.113.9`를 적습니다. 이 일을 맡은 약속이 IP입니다.
4. **배달 차.** 랜선이나 와이파이가 상자를 바로 다음 장치까지 실어 나릅니다.

이렇게 겉포장을 한 겹씩 씌우는 것을 **캡슐화**(encapsulation)라고 합니다.

포장마다 붙이는 딱지는 **헤더**(header)입니다. 길목의 라우터는 상자 겉면의 IP 주소를 보고 넘깁니다. 안의 편지는 읽지 않습니다.

### 어디서 막혔나: 오류 글자로 가리기

계층을 알면 고장 난 곳을 찾는 순서가 생깁니다. 상자가 건물에 도착해도 그 호수에 아무도 없을 수 있습니다. 봉투가 전해져도 편지 내용이 거절될 수 있습니다. 막힌 단계마다 보이는 글자가 다릅니다.

| 단계와 확인할 질문 | 막히면 보이는 글자 |
|---|---|
| **이름.** 이름이 주소로 바뀌나 | `DNS_PROBE_FINISHED_NXDOMAIN`, `Could not resolve host`, `ENOTFOUND` |
| **길.** 그 주소까지 닿나 | `ERR_CONNECTION_TIMED_OUT`, `timed out`, `ETIMEDOUT` |
| **문.** 그 포트에서 누가 받나 | `ERR_CONNECTION_REFUSED`, `Connection refused`, `ECONNREFUSED` |
| **내용.** 서버가 뭐라고 답했나 | 404 같은 오류 번호 |

위의 세 줄에서 첫 글자는 크롬의 오류 화면에, 나머지는 터미널에 찍힙니다. 우리말로는 이렇게 부릅니다.

- **주소를 찾지 못함.** 이름의 철자를 봅니다. 방금 연결한 도메인이면 기다립니다.
- **시간 초과.** 답이 없어서 기다리다 포기한 것입니다. 숫자 주소가 맞는지, 그 컴퓨터가 켜져 있는지, 문지기인 방화벽(뒤에서 만납니다)이 막는지 봅니다.
- **연결 거부.** 컴퓨터까지는 갔는데 그 호수에 아무도 없습니다. 서버가 켜져 있는지, 포트 번호가 맞는지, 서버가 `127.0.0.1`에만 묶였는지 봅니다.

이름은 `nslookup`으로, 길은 뒤에서 볼 `ping`으로 확인합니다. 404는 "그런 페이지는 없습니다"라는 서버의 답입니다. 답이 왔으니 이름, 길, 문은 통과한 것입니다. 증상별로 볼 곳은 [증상으로 찾기](trouble.html)에 있습니다.

::: {.try}
이름부터 내용까지 한 번에 확인하는 터미널 명령입니다.

```bash
curl -v https://example.com
```

`curl`은 브라우저 없이 요청을 보내는 명령입니다. `-v`는 지나가는 과정을 모두 보여 달라는 옵션입니다. 윈도우 PowerShell에서는 `curl.exe`라고 칩니다. 여러 줄이 찍히는데, 그 가운데 아래 세 줄을 찾아보세요. 주소 숫자는 다르게 나옵니다.

```text
*   Trying 203.0.113.9:443...
* Connected to example.com (203.0.113.9) port 443
< HTTP/2 200
```

- `Trying`은 이름을 주소로 바꿨고, 이제 443호 문을 두드린다는 뜻입니다.
- `Connected to`는 문이 열렸다는 뜻입니다.
- `<`로 시작하는 줄은 서버가 보낸 답입니다. 200은 "잘 됐다"는 번호입니다.

어느 줄에서 멈추는지 보면 막힌 단계를 알 수 있습니다.
:::

::: {.key}
한 계층이 성공했다고 그 위 계층까지 성공한 것은 아닙니다. **이름 → 길 → 문 → 내용** 순서로 확인합니다.
:::

## TCP와 UDP: 등기 우편과 엽서 {#transport}

IP가 하는 약속은 "힘닿는 데까지 전해 본다"까지입니다. 패킷은 가다가 사라질 수도, 순서가 바뀔 수도 있습니다. 봉투를 맡은 계층이 이 문제를 다루는 방식은 둘입니다.

첫째는 등기 우편 같은 방식입니다. 등기 우편은 받았다는 확인을 받는 우편입니다. 받는 쪽이 "여기까지 잘 받았습니다" 하고 확인을 돌려보냅니다. 확인이 오지 않은 조각은 보내는 쪽이 다시 보냅니다. 받는 쪽은 번호 순서대로 맞춘 뒤에야 앱에 넘깁니다. 이 방식이 **TCP**(Transmission Control Protocol)입니다.

둘째는 엽서 같은 방식입니다. 보내면 끝입니다. 도착했는지도, 순서가 맞는지도 확인하지 않습니다. 대신 기다림이 없습니다. 이 방식이 **UDP**(User Datagram Protocol)입니다.

::: {.fig src="tcp-udp.svg"}
A, B, C 세 조각 가운데 B를 잃어버렸습니다. TCP는 B를 다시 받아(재전송) 순서대로 넘깁니다. UDP는 도착한 A와 C만 넘깁니다.
:::

그림의 TCP 쪽에서 C를 보세요. C는 제때 도착했습니다. 하지만 B가 다시 올 때까지 앱에 넘어가지 못하고 기다립니다. 정확함의 값은 기다림입니다.

파일은 한 군데만 빠져도 못 쓰게 됩니다. 그래서 웹 페이지와 파일은 주로 TCP로 받습니다. 게임 캐릭터의 위치는 다릅니다. 0.1초 전 위치를 다시 받느니 지금 위치를 새로 받는 편이 낫습니다. 그래서 실시간 게임과 음성·영상 통화는 흔히 UDP를 씁니다.

웹사이트를 만들 때는 직접 고를 일이 없습니다. 실시간 게임을 만들 때는 무엇을 어느 방식으로 보낼지 AI에게 먼저 묻습니다([25장](ch25.html)).

### 3방향 악수: 보내기 전에 연결부터

TCP는 내용을 보내기 전에 서로 준비됐는지부터 확인합니다. 전화를 걸어 "여보세요?", "네, 여보세요.", "네, 말씀드릴게요." 하고 시작하는 것과 같습니다.

세 번 주고받아서 **3방향 악수**(three-way handshake)라고 합니다. 이렇게 길을 터 두는 것을 "연결을 맺는다"고 말합니다.

앞 절의 두 오류는 이 첫 "여보세요?"에서 갈립니다. 그 호수에 받는 프로그램이 없으면 상대 운영체제가 곧바로 "아무도 없습니다" 하고 돌려보냅니다. 연결 거부입니다. 아무 대답도 없으면 몇 번 더 불러 보다가 포기합니다. 시간 초과입니다. 그래서 연결 거부는 바로 뜨고, 시간 초과는 한참 뒤에 뜹니다.

::: {.deep title="연결은 어떻게 끝날까요?"}
전화를 끊을 때는 "이만 끊을게", "응, 잘 가" 하고 인사부터 합니다. TCP도 양쪽이 "더 보낼 것이 없습니다" 하고 알린 뒤에 연결을 닫습니다. 이 끝인사를 **FIN**이라고 합니다.

인사 없이 뚝 끊기는 일도 있습니다. 이때 보내는 신호가 **RST**이고, 화면에는 `connection reset`이나 `ECONNRESET`이라는 오류로 보입니다. 이 오류를 만나면 보내던 요청이 어디까지 처리됐는지 알 수 없습니다. 같은 요청을 다시 보내기 전에 앞의 것이 처리됐는지부터 확인합니다.
:::

## 대역폭과 지연: 차선 수와 거리 {#speed}

"인터넷이 빠르다"는 말에는 서로 다른 두 가지 뜻이 섞여 있습니다. 도로로 생각해 봅시다.

하나는 **차선 수**입니다. 차선이 많으면 한꺼번에 많은 차가 지나갑니다. 네트워크에서는 1초에 보낼 수 있는 양입니다. 이것을 **대역폭**(bandwidth)이라고 합니다. 단위는 Mbps(초당 메가비트)입니다. 통신사 광고의 "100메가 인터넷"이 100Mbps입니다.

다른 하나는 **도로의 길이**입니다. 길이 멀면 차 한 대가 도착하는 데 오래 걸립니다. 네트워크에서는 패킷 하나가 도착하는 데 걸리는 시간입니다. 이것을 **지연**(latency)이라고 합니다.

지연은 보통 갔다가 돌아오는 시간으로 잽니다. 이 왕복 시간을 **RTT**(Round-Trip Time)라고 합니다. 단위는 ms(밀리초)이고, 1ms는 1,000분의 1초입니다. 게임에서 '핑'이라고 부르는 숫자가 이것입니다.

차선을 8개로 늘려도 서울에서 부산까지 가는 시간은 줄지 않습니다. 한꺼번에 지나가는 차가 늘 뿐입니다.

거리는 생각보다 큽니다. 빛은 광섬유 속에서 1초에 약 20만 km를 갑니다. 서울에서 미국 서부까지를 약 1만 km로 잡으면 왕복은 2만 km입니다. 2만 ÷ 20만 = 0.1초, 곧 100ms입니다. 아무리 좋은 인터넷을 써도 이보다 빠를 수는 없습니다.

이제 왕복에 100ms가 걸리는 서버에 작은 요청 10개를 보낸다고 합시다. 게임을 켤 때 내 캐릭터, 가방, 친구 목록 같은 것을 하나씩 물어 오는 장면입니다.

::: {.fig src="round-trips.svg"}
답을 받고 나서 다음 요청을 보내면 10 × 100ms = 1,000ms, 곧 1초가 걸립니다. 서로 상관없는 요청이라면 한꺼번에 보내 약 100ms 만에 끝낼 수 있습니다.
:::

::: {.myth title="인터넷 회선이 빠르면 응답도 빠르다"}
회선은 인터넷이 들어오는 줄입니다. 회선을 두 배 굵은 것으로 바꿔도 위의 1,000ms는 그대로입니다. 요청이 작으면 시간의 대부분을 오가며 기다리는 데 쓰기 때문입니다. 줄이려면 요청을 묶거나 한꺼번에 보내서, 차례로 기다리는 **왕복 횟수**를 줄여야 합니다.
:::

::: {.tip}
AI가 만든 화면이 느리게 뜨면 "이 화면을 여는 데 요청을 몇 번 보내? 차례로 기다리는 것이 있어?" 하고 물어보세요.
:::

대역폭은 큰 것을 받을 때 중요합니다. 이때 단위를 조심하세요. Mbps의 b는 비트, MB의 B는 바이트입니다. 1바이트는 8비트입니다([2장](ch02.html)). 그래서 100Mbps는 1초에 100 ÷ 8 = 12.5MB입니다. 1GB(1,000MB)짜리 게임을 받는 데는 1,000 ÷ 12.5 = 80초가 걸립니다.

::: {.try}
왕복 시간을 직접 재 보는 터미널 명령입니다.

```bash
ping example.com
```

`ping`은 작은 패킷을 보내고 답이 돌아오는 시간을 재는 명령입니다. 줄마다 나오는 `time=12.3 ms`가 RTT입니다. 한글 윈도우에서는 `시간=12ms`처럼 나옵니다. 맥과 리눅스에서는 `Ctrl + C`를 눌러 멈춥니다. 우리나라 사이트와 다른 나라 사이트를 견주어 보세요. ping에 답하지 않게 막아 둔 서버도 많으니, 답이 없다고 꺼진 것은 아닙니다.
:::

## 문지기와 안내 데스크: 방화벽, 리버스 프록시, 로드 밸런서 {#front}

큰 병원에 가면 곧장 의사 앞으로 가지 않습니다. 정문 경비실을 지나고, 안내 데스크에서 어느 진료실로 갈지 듣습니다. 많은 사람이 쓰는 서비스도 같습니다. 요청은 일하는 서버에 닿기 전에 몇 군데를 더 거칩니다.

먼저 경비실입니다. 경비실의 명단에는 "어디에서 온 것을 몇 번 포트로 들여보낼지"가 적혀 있습니다. 명단에 없는 것은 막습니다. 이 문지기를 **방화벽**(firewall)이라고 합니다.

아래 그림의 방화벽은 443번 포트만 열어 두었습니다. 서버 프로그램이 8080호에서 잘 기다리고 있어도 바깥에서는 8080으로 들어갈 수 없습니다. 방화벽이 패킷을 말없이 버리면, 보낸 쪽에는 한참 뒤에 시간 초과가 뜹니다.

방화벽은 내 컴퓨터의 운영체제에도, 공유기에도 있습니다. 접속이 안 된다고 통째로 끄면 다른 문까지 모두 열립니다.

다음은 안내 데스크입니다. 방문자는 데스크만 상대합니다. 데스크가 뒤쪽 서버에 요청을 전하고 답을 받아 옵니다. 이 역할을 **리버스 프록시**(reverse proxy)라고 합니다.

뒤쪽에는 같은 일을 하는 서버가 여러 대 있습니다. 한 대로는 몰려드는 요청을 다 받지 못하기 때문입니다. 요청을 여러 서버에 고르게 나눠 주는 역할을 **로드 밸런서**(load balancer)라고 합니다. 서버마다 "살아 있나요?" 하고 틈틈이 물어서, 답이 없는 서버에는 보내지 않습니다. 장치 하나가 안내 데스크와 이 역할을 함께 맡을 때가 많습니다.

::: {.fig src="front-desk.svg"}
바깥 요청이 앱 서버, 곧 실제로 일하는 서버에 닿기까지입니다. 리버스 프록시는 응답 없는 앱 서버 3에는 요청을 보내지 않습니다.
:::

작은 앱을 만들 때는 이 앞쪽을 직접 꾸리지 않습니다. 앱을 인터넷에 올려 주는 서비스가 대신 세워 둡니다. 그래서 내 서버 프로그램이 꺼지면 화면에는 안내 데스크가 대신 보낸 `502` 같은 번호가 뜹니다([15장](ch15.html)). 직접 꾸리는 방법은 [21장](ch21.html)에서 다룹니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| IP 주소 / 포트 | 어느 컴퓨터인가(건물) / 그 안의 어느 프로그램인가(호수) |
| 사설 IP / 공인 IP | 집 안에서만 통하는 주소 / 인터넷 전체에서 하나뿐인 주소 |
| localhost / 0.0.0.0 | 접속할 때 쓰는 "나 자신" / 서버가 "모든 방향에서 받겠다"고 할 때 쓰는 표시 |
| DNS / 라우터 | 이름을 주소로 바꾸기 / 그 주소까지 길 찾기 |
| 연결 거부 / 시간 초과 | 그 호수에 아무도 없어 바로 거절됨 / 답이 없어 기다리다 포기함 |
| TCP / UDP | 빠짐없이 순서대로, 대신 기다림 / 보내면 끝, 대신 빠질 수 있음 |
| 대역폭 / 지연 | 한 번에 얼마나 많이(차선 수) / 한 번 다녀오는 데 얼마나(거리) |

## 실전 사례 {#case}

::: {.case title="내 노트북에서는 열리는데 휴대전화에서는 안 열린다"}
노트북으로 만든 우리 반 퀴즈 게임 사이트가 노트북에서는 `localhost:3000`으로 잘 열립니다. 같은 와이파이를 쓰는 휴대전화에서는 열리지 않습니다. 이름, 문, 경비실 순서로 확인합니다.

1. **이름을 확인합니다.** 휴대전화에 `localhost:3000`을 적었습니다. 휴대전화의 `localhost`는 휴대전화 자신입니다. 노트북의 와이파이 설정 화면에서 주소를 찾으니 `192.168.0.5`입니다.
2. **문을 확인합니다.** `192.168.0.5:3000`을 적어도 "연결이 거부됨"이 뜹니다. 개발 서버가 `127.0.0.1:3000`에만 묶여 있었습니다. `0.0.0.0`으로 다시 켭니다.
3. **경비실을 확인합니다.** 노트북의 방화벽이 "들어오는 연결을 허용할까요?" 하고 묻습니다. 이 프로그램만 허용하고, 방화벽을 통째로 끄지는 않습니다. 이제 휴대전화에서 열립니다.

막힌 곳은 한 군데가 아니었습니다. 차례로 확인했기에 하나씩 풀 수 있었습니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- 보낼 것은 번호가 붙은 작은 **패킷**으로 나뉘어 가고, 받는 쪽에서 다시 합쳐집니다.
- **IP 주소**는 건물 주소, **포트**는 호수입니다. 프로그램은 **소켓**이라는 우편함으로 주고받고, 호수 하나는 한 프로그램만 차지합니다.
- `localhost`는 언제나 입력한 기기 자신입니다. 서버는 **바인딩**한 주소로 온 요청만 받습니다. `127.0.0.1`은 안쪽만, `0.0.0.0`은 모든 방향입니다.
- 집 안에서는 **사설 IP**를 쓰고, 공유기가 **NAT**로 **공인 IP**로 바꿉니다. 바깥에서 먼저 들어올 수는 없어서, 내 컴퓨터에 켠 화면을 다른 집 친구는 열지 못합니다. **라우터**는 다음에 넘길 곳만 정합니다.
- **DNS**는 이름을 주소로 바꿉니다. 이름과 주소의 짝은 **레코드**에 적혀 있습니다. 답은 **TTL** 동안 캐시에 남아서, 바뀐 주소가 늦게 퍼집니다.
- **TCP**는 빠짐없이 순서대로, **UDP**는 기다림 없이 보냅니다.
- 작은 요청이 빠르냐 느리냐는 대역폭보다 **왕복 횟수**가 정합니다.
- 고장은 이름 → 길 → 문 → 내용 순서로 찾습니다. 주소를 찾지 못하면 이름, 시간 초과는 길, 연결 거부는 문입니다.
:::

## 확인 문제 {#quiz}

::: {.q}
친구가 "우리 집 컴퓨터에 게임 서버 열었어. 주소는 192.168.0.5야. 들어와!" 하고 메시지를 보냈습니다. 우리 집에서 그 주소로 들어가려는데 안 됩니다. 왜 그럴까요?

::: {.a}
`192.168.0.5`는 친구네 집 안에서만 통하는 사설 IP입니다. 우리 집에서 이 주소를 적으면 우리 집 안의 기기를 찾습니다.
:::
:::

::: {.q}
어제 산 도메인을 내 사이트에 연결했습니다. 내 컴퓨터에서는 그 이름으로 사이트가 열리는데, 친구는 "주소를 찾을 수 없다"는 화면이 뜬다고 합니다. 설정을 다시 바꿔야 할까요?

::: {.a}
아닙니다. 기다립니다. 친구가 쓰는 리졸버의 캐시에 "그런 이름은 없다"는 옛 답이 남아 있기 때문입니다. DNS의 답은 TTL로 정한 시간 동안 다시 묻지 않고 그대로 씁니다.
:::
:::

::: {.q}
AI가 "서버를 켰습니다. `localhost:3000`을 열어 보세요"라고 했습니다. 열어 보니 `ERR_CONNECTION_REFUSED`가 뜹니다. 이름, 길, 문, 내용 가운데 어디에서 막혔을까요? 무엇부터 확인할까요?

::: {.a}
문에서 막혔습니다. `localhost`는 내 컴퓨터 자신이라 이름과 길은 문제가 없습니다. 3000호에서 기다리는 프로그램이 없다는 뜻입니다. 서버가 정말 켜져 있는지, 터미널에 찍힌 포트 번호가 3000이 맞는지 확인합니다.
:::
:::

::: {.q}
친구와 목소리로 통화하는 앱을 만든다고 합시다. 목소리는 TCP와 UDP 가운데 어느 쪽으로 보내는 것이 맞을까요?

::: {.a}
UDP가 맞습니다. TCP는 잃어버린 조각이 다시 올 때까지 뒤의 조각도 붙잡아 둬서 목소리가 밀립니다. 통화에서는 지나간 소리보다 지금 소리를 바로 들려주는 편이 중요합니다.
:::
:::

::: {.q}
서버가 미국에 있는 게임을 합니다. 핑(RTT)이 150ms라서 반응이 한 박자 늦습니다. 집 인터넷을 100Mbps에서 500Mbps로 바꾸면 핑이 줄어들까요?

::: {.a}
거의 그대로입니다. 100Mbps, 500Mbps는 대역폭, 곧 차선 수입니다. 핑은 미국까지 다녀오는 거리 때문에 생깁니다. 차선을 늘려도 거리는 줄지 않습니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
연결이 안 될 때 "안 돼요"라고만 하면 AI도 짐작으로 답합니다. **입력한 주소, 연 기기, 화면의 오류 글자**를 주고, 고치기 전에 어디까지 됐는지부터 확인하게 하세요.

> 노트북에서 켠 개발 서버를 같은 와이파이의 휴대전화로 열고 싶어. 노트북에서 `localhost:3000`은 잘 열려. 휴대전화에서 `192.168.0.5:3000`을 열면 `ERR_CONNECTION_REFUSED`가 떠. 먼저 서버가 어느 주소와 포트에 묶여 있는지 확인해서 보여 줘. 그다음 휴대전화에서도 열리게 바꿔 줘. 방화벽을 통째로 끄거나 공유기 설정을 바꾸는 방법은 쓰지 마. 끝난 뒤 원래대로 되돌리는 방법도 알려 줘.

**받은 답에서 확인할 것**

- 고치기 전에 서버가 묶인 주소와 포트를 직접 확인해 보여 주었는가.
- 휴대전화에 입력하라는 주소가 `localhost`나 `0.0.0.0`이 아니라 노트북의 `192.168.` 주소인가.
- 방화벽을 끄라는 말 없이, 필요한 프로그램 하나만 허용했는가.
- 되돌리는 방법이 적혀 있는가.

**AI가 자주 하는 실수**

- **오류 글자를 가리지 않고 고칩니다.** 연결 거부인데 DNS를 바꾸라고 하거나, 무엇이든 방화벽부터 끄라고 합니다. 이름 → 길 → 문 → 내용 가운데 어느 단계인지 되묻습니다.
- **코드에 `localhost` 주소를 적어 둡니다.** 화면이 서버를 `http://localhost:3000`으로 부르게 짜면 내 컴퓨터에서만 됩니다. 인터넷에 올리면 보는 사람의 기기 자신을 찾아갑니다. 올리기 전에 코드에서 `localhost`를 모두 찾아 달라고 합니다.
- **포트가 쓰이는 중이면 다른 번호로 서버를 하나 더 켭니다.** 옛 서버가 남아 어느 화면이 새것인지 헷갈립니다. 터미널에 찍힌 포트 번호를 확인하고, 옛 서버는 끄게 합니다.
- **DNS가 퍼지기를 기다리지 않습니다.** 도메인을 연결한 직후 안 열린다고 레코드를 이것저것 바꿉니다. `nslookup` 결과부터 보여 달라고 합니다.
:::

## 용어 정리 {#terms}

::: {.terms}
네트워크 (network)
:   컴퓨터들이 서로 이어져 메시지를 주고받는 길.

클라이언트 (client)
:   먼저 말을 걸어 요청을 보내는 쪽.

서버 (server)
:   기다리다가 요청을 받고 응답을 돌려주는 쪽.

요청과 응답 (request / response)
:   클라이언트가 보내는 말과 서버가 돌려주는 대답.

패킷 (packet)
:   보낼 것을 잘게 나눈 조각. 받는 곳 주소와 번호가 붙는다.

광섬유 (optical fiber)
:   빛으로 신호를 보내는 가느다란 유리 줄.

프로토콜 (protocol)
:   주고받는 양쪽이 지키기로 한 약속.

IP 주소 (IP address)
:   네트워크에서 컴퓨터가 어디 있는지 가리키는 번호.

IPv4
:   숫자 네 개를 점으로 이어 쓰는 IP 주소. 약 43억 개뿐이다.

IPv6
:   IPv4가 모자라서 새로 만든, 훨씬 긴 IP 주소.

포트 (port)
:   한 컴퓨터 안에서 받을 프로그램을 가리키는 번호.

소켓 (socket)
:   프로그램이 주고받으려고 운영체제에게서 받는 우편함.

localhost
:   지금 이 기기 자신을 가리키는 이름. 주소로는 127.0.0.1.

개발 서버
:   만드는 동안 시험하려고 내 컴퓨터에 켜 두는 서버.

바인딩 (binding)
:   서버가 어느 주소와 포트로 온 요청을 받을지 정하는 일.

사설 IP (private IP)
:   집이나 학교 안에서만 통하는 주소.

공인 IP (public IP)
:   인터넷 전체에서 하나뿐인 주소.

NAT (Network Address Translation)
:   공유기가 사설 IP와 공인 IP를 서로 바꿔 주는 일.

라우터 (router)
:   받는 곳 주소를 보고 패킷을 다음에 넘길 곳을 정하는 장치.

게이트웨이 (gateway)
:   바깥 네트워크로 나가는 첫 문. 집에서는 공유기.

도메인 (domain)
:   example.com 같은 사이트 이름.

DNS (Domain Name System)
:   사이트 이름을 IP 주소로 바꿔 주는 안내소.

캐시 (cache)
:   다시 쓰려고 가까이 적어 두는 곳.

리졸버 (resolver)
:   이름의 주소를 대신 찾아 주는 서버.

레코드 (record)
:   DNS 장부의 한 줄. A 레코드에는 이름의 IP 주소가 적힌다.

TTL (Time To Live)
:   DNS의 답을 캐시에 두고 다시 써도 되는 시간.

계층 (layer)
:   네트워크의 일을 층층이 나눠 맡은 한 층.

캡슐화 (encapsulation)
:   보낼 내용에 겉포장을 한 겹씩 씌우는 일.

헤더 (header)
:   포장마다 붙이는 딱지. 주소나 번호가 적힌다.

TCP (Transmission Control Protocol)
:   빠진 조각을 다시 보내고 순서대로 전해 주는 방식.

UDP (User Datagram Protocol)
:   확인 없이 보내기만 하는 방식. 기다림이 없지만 빠질 수 있다.

3방향 악수 (three-way handshake)
:   TCP가 내용을 보내기 전에 세 번 주고받으며 연결을 맺는 일.

FIN과 RST
:   TCP 연결을 끝내는 신호. FIN은 인사하고 끝내기, RST는 바로 끊기.

대역폭 (bandwidth)
:   1초에 보낼 수 있는 양. 도로의 차선 수에 해당한다.

지연 (latency)
:   패킷 하나가 도착하는 데 걸리는 시간.

RTT (Round-Trip Time)
:   패킷이 갔다가 돌아오는 데 걸리는 왕복 시간.

방화벽 (firewall)
:   명단에 있는 것만 들여보내고 나머지는 막는 문지기.

리버스 프록시 (reverse proxy)
:   서버 앞에서 요청을 대신 받아 뒤쪽 서버로 넘겨 주는 장치.

로드 밸런서 (load balancer)
:   요청을 여러 서버에 고르게 나눠 주는 장치.
:::
