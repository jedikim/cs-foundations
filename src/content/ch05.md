::: {.lead}
영화에서 해커가 검은 화면에 글자를 빠르게 치는 장면을 본 적이 있을 겁니다. 그 검은 화면이 **터미널**입니다. 마우스로 누르는 대신 글자로 컴퓨터에게 일을 시키는 창입니다. 어려워 보이지만 규칙은 몇 가지뿐입니다. 이 장을 읽고 나면 터미널에 적힌 한 줄이 무슨 뜻인지 읽을 수 있습니다.
:::

::: {.goals}
- 터미널이 무엇이고 왜 쓰는지 말할 수 있습니다.
- 파일이 컴퓨터 안 어디에 있는지를 '경로'로 적고 읽을 수 있습니다.
- 명령 한 줄을 보고 무엇을 하는 명령인지 알 수 있습니다.
- 파일을 지우는 명령을 실행하기 전에 무엇이 지워질지 확인할 수 있습니다.
:::

## 터미널과 셸: 글로 주문하는 창구 {#terminal}

사진 300장의 이름을 `001.jpg`부터 차례로 바꿔야 한다고 해 봅시다. 마우스로는 수백 번을 클릭해야 합니다. 글로 시킬 수 있다면 한 줄이면 됩니다. 게다가 글로 쓴 명령은 **복사해서 다시 쓸 수 있고, 기록으로 남고, 동료나 AI에게 그대로 전할 수 있습니다.** 화면이 달려 있지 않은 서버는 아예 글로만 다룹니다. 오래된 방식이 지금도 개발자의 기본 도구인 이유입니다.

[1장](ch01.html)에서 컴퓨터를 주방에 비유했습니다. 이 주방에는 글로 주문을 넣는 창구가 있습니다.

- **터미널**(terminal)은 주문 창구입니다. 글자를 입력하고, 결과를 글자로 돌려받는 창입니다.
- **셸**(shell)은 창구 직원입니다. 내가 쓴 주문서를 읽고 해석해서 알맞은 프로그램을 실행시키는 프로그램입니다.

::: {.fig src="terminal-shell.svg"}
명령 한 줄이 지나가는 길. 터미널은 글자가 오가는 창일 뿐이고, 그 글을 해석하는 일은 셸이 합니다.
:::

::: {.photo src="teletype.jpg"}
터미널의 조상. 오른쪽의 기계가 1960~70년대에 쓰던 텔레타이프입니다. 자판으로 글자를 쳐서 왼쪽의 컴퓨터에 보내면, 컴퓨터의 답이 위쪽 종이에 한 줄씩 찍혀 나왔습니다. 지금의 터미널 창은 이 기계를 화면 속에 옮겨 놓은 것입니다. 글자를 한 줄씩 주고받는 방식은 그때와 같습니다.
:::

터미널을 열면 이런 줄이 기다리고 있습니다.

```text
mina@macbook mygame %
```

"주문 받을 준비가 됐습니다"라는 표시이고, **프롬프트**(prompt)라고 부릅니다. 사용자 이름, 컴퓨터 이름, 지금 있는 폴더가 보이고 끝에 `%`나 `$`가 붙습니다. 이 책에서는 프롬프트를 `$` 하나로 줄여 씁니다. 따라 칠 때 `$`는 입력하지 않습니다.

명령을 치고 Enter를 누르면 셸은 그 이름의 프로그램을 찾아 실행합니다. [3장](ch03.html)에서 본 프로세스가 하나 생기는 것입니다. 프로그램이 끝나면 프롬프트가 다시 나타납니다.

::: {.note}
셸에도 종류가 있습니다. macOS는 **zsh**, Linux는 대개 **bash**가 기본이고, 이 장의 예시는 둘 다에서 통합니다. Windows의 기본 셸인 PowerShell은 문법이 다르므로, Windows에서는 Linux 환경을 얹어 주는 WSL에서 따라 하는 편이 쉽습니다. AI가 준 명령이 **어느 셸용인지**부터 확인하세요.
:::

## 파일 시스템과 경로: 나무에서 길 찾기 {#path}

창고(저장장치)에 파일 수십만 개가 한 줄로 쌓여 있다면 아무것도 찾지 못할 것입니다. 그래서 운영체제는 파일을 폴더에 넣고, 폴더 안에 또 폴더를 넣어 정리합니다. 터미널에서는 폴더를 **디렉터리**(directory)라고 부릅니다. 같은 것입니다.

이 구조를 그리면 뒤집힌 나무가 됩니다. 맨 위에 뿌리인 **루트**(root)가 있고 `/` 한 글자로 씁니다. 파일을 이렇게 나무 모양으로 정리하는 체계가 **파일 시스템**(file system)입니다.

파일의 위치는 루트에서부터 지나가는 폴더 이름을 `/`로 이어서 적습니다. 이것이 **경로**(path)입니다. 택배 주소와 같습니다.

주소를 말하는 방법은 두 가지입니다. 셸은 언제나 나무의 어느 한 폴더에 서 있는데, 이 폴더를 **작업 디렉터리**(working directory)라고 합니다.

- **절대 경로**는 루트에서 출발합니다. `/`로 시작하고, 어디에 서 있든 같은 파일을 가리킵니다. "서울시 ○○구 ○○로 12"처럼 주소를 전부 적는 방식입니다.
- **상대 경로**는 작업 디렉터리에서 출발합니다. "여기서 두 번째 골목"처럼 말하는 방식이라 짧지만, 서 있는 곳이 바뀌면 다른 곳을 가리킵니다.

::: {.fig src="path-routes.svg"}
같은 파일로 가는 두 가지 길. 파란 선은 루트에서 출발하는 절대 경로, 주황 선은 지금 서 있는 `mygame`에서 출발하는 상대 경로입니다.
:::

상대 경로에는 줄임 기호 셋이 자주 나옵니다.

| 기호 | 뜻 | 예 (`mygame`에 서 있을 때) |
|---|---|---|
| `.` | 지금 서 있는 폴더 | `./data` → `mygame` 안의 `data` |
| `..` | 한 칸 위 폴더 | `../notes.txt` → `mina` 안의 파일 |
| `~` | 내 홈 폴더 | `~/mygame` → `/Users/mina/mygame` |

여기에 실전에서 가장 자주 밟는 함정이 있습니다. 코드에 `open("data/settings.json")`이라고 쓰면, 프로그램은 **코드 파일이 있는 곳이 아니라 작업 디렉터리**에서 `data` 폴더를 찾습니다. 같은 프로그램도 어디에 서서 실행했느냐에 따라 파일을 찾기도 하고 못 찾기도 합니다.

::: {.key}
상대 경로를 보면 "지금 어디에 서 있지?"를 먼저 물으세요. `pwd` 한 번이면 답이 나옵니다.
:::

::: {.warn title="대문자와 소문자"}
macOS와 Windows는 보통 `Logo.png`와 `logo.png`를 같은 파일로 보지만 Linux는 다른 파일로 봅니다. 내 컴퓨터에서 보이던 그림이 Linux 서버에서만 사라졌다면 파일 이름의 대소문자부터 비교하세요.
:::

::: {.deep title="바로가기처럼 보이는 파일: 심볼릭 링크와 하드 링크"}
**심볼릭 링크**(symbolic link)는 "진짜는 저 경로에 있어요"라고 적힌 쪽지 파일입니다. 링크를 지워도 원본은 남고, 원본을 지우면 링크는 갈 곳을 잃습니다. **하드 링크**(hard link)는 같은 내용물에 이름표를 하나 더 붙이는 것입니다. 이름이 하나라도 남아 있으면 내용은 사라지지 않습니다.

**경로 하나가 독립된 파일 하나라는 보장은 없습니다.** `ls -l`로 보면 링크는 `이름 -> 대상` 모양으로 표시됩니다.
:::

## 명령 한 줄 읽기: 명령, 옵션, 인수 {#command}

주문서에는 순서가 있습니다. "볶음밥, 맵게, 2인분을 3번 테이블로." 메뉴 이름이 먼저 오고 요청 사항과 대상이 뒤따릅니다. 셸에 내는 명령도 같습니다.

::: {.fig src="command-anatomy.svg"}
명령 한 줄의 구조. 맨 앞 낱말이 실행할 프로그램의 이름이고, 나머지는 그 프로그램에 건네는 말입니다.
:::

- **명령**: 맨 앞 낱말. 실행할 프로그램의 이름입니다.
- **옵션**(option): `-`로 시작하는 낱말. 동작 방식을 바꿉니다. `-r`처럼 한 글자짜리도 있고 `--help`처럼 긴 이름도 있습니다.
- **인수**(argument): 명령이 다룰 대상. 주로 파일이나 폴더의 경로입니다.

매일 쓰는 명령은 여덟 개 정도입니다.

| 명령 | 하는 일 | 예 |
|---|---|---|
| `pwd` | 서 있는 폴더의 절대 경로 출력 | `pwd` |
| `ls` | 폴더 안의 목록 보기 | `ls -a` (`.`으로 시작하는 숨김 파일까지) |
| `cd` | 서 있는 폴더 옮기기 | `cd src`, `cd ..` |
| `cat` | 파일 내용을 화면에 출력 | `cat notes.txt` |
| `mkdir` | 새 폴더 만들기 | `mkdir backup` |
| `cp` | 복사 | `cp a.txt b.txt` |
| `mv` | 옮기기, 이름 바꾸기 | `mv old.txt new.txt` |
| `rm` | 지우기 | `rm old.txt` |

이어서 쳐 보면 이렇게 됩니다.

```bash
$ pwd
/Users/mina/mygame
$ ls
data  src
$ mkdir backup
$ cp data/settings.json backup/
$ mv backup/settings.json backup/old.json
$ ls backup
old.json
```

1. `pwd`로 서 있는 곳을 확인하고 `ls`로 둘러봅니다. `mygame` 안에 `data`와 `src` 폴더가 있습니다.
2. `mkdir`로 `backup` 폴더를 만듭니다. 성공하면 아무 말도 하지 않습니다. 터미널에서는 **조용하면 잘된 것**입니다.
3. `cp`로 설정 파일을 `backup` 안에 복사하고, `mv`로 그 복사본의 이름을 바꿉니다.
4. 마지막 `ls backup`으로 결과를 확인합니다.

::: {.tip title="옵션은 외우지 않습니다"}
`man ls`를 치면 `ls`의 설명서가 열립니다(`q`로 닫습니다). `git --help`처럼 `--help` 옵션으로 짧은 도움말을 보여 주는 명령도 많습니다. 모르는 옵션이 든 명령은 실행하기 전에 여기서 찾아보거나, AI에게 옵션 하나하나의 뜻을 물어보세요.
:::

::: {.try}
터미널을 열고 `pwd`, `ls`, `cd ..`, `pwd`를 차례로 쳐 보세요. 두 번째 `pwd`의 결과가 어떻게 달라졌나요? `cd ~`를 치면 언제든 홈 폴더로 돌아옵니다.
:::

::: {.deep title="덜 치고 덜 틀리기: 자동 완성과 명령 기록"}
이름을 몇 글자 치고 **Tab**을 누르면 셸이 나머지를 채워 줍니다. 채워지지 않으면 "그런 이름이 없다"는 신호라서 오타도 미리 잡아 줍니다. **위쪽 화살표**는 이전 명령을 다시 불러오고, `Ctrl+R`은 예전 명령을 검색합니다.

조심할 점도 있습니다. 어제 성공한 명령도 오늘 다른 폴더에서는 다른 파일을 건드리니, 불러온 명령은 Enter 전에 다시 읽으세요. 또 비밀번호 같은 값을 명령 줄에 직접 쓰면 기록에 그대로 남습니다.
:::

## 셸이 먼저 손보는 것: 공백, 따옴표, 별표 {#quote}

`My Game.txt`라는 파일을 지우려고 `rm My Game.txt`라고 쳤습니다. 돌아온 것은 "`My`라는 파일이 없다"는 오류입니다. 왜일까요?

창구 직원인 셸은 주문서를 주방에 넘기기 전에 먼저 손을 봅니다. 가장 먼저 하는 일이 **공백에서 줄을 잘라 낱말 목록으로 만드는 것**입니다. 프로그램은 잘린 낱말만 받습니다. 그래서 `rm`은 `My`와 `Game.txt`라는 파일 두 개를 지우라는 말로 알아듣습니다. 운이 나쁘면 그런 이름의 엉뚱한 파일이 지워집니다.

::: {.fig src="arg-split.svg"}
셸이 줄을 자르는 방식. 공백은 낱말을 나누고, 따옴표는 묶고, 별표는 파일 이름들로 펼쳐집니다.
:::

**따옴표**로 감싸면 그 안의 공백은 자르지 않습니다. `rm "My Game.txt"`는 낱말 하나로 전달됩니다. 공백이 든 경로는 언제나 따옴표로 감싸세요.

셸이 손보는 것이 하나 더 있습니다. 별표 `*`입니다. "아무 글자나 몇 개든"을 뜻하는 **와일드카드**(wildcard)로, 셸은 `*.log`를 지금 폴더에서 `.log`로 끝나는 **실제 파일 이름들로 바꿔 넣은 뒤** 프로그램에 넘깁니다. `rm`은 별표를 구경도 못 합니다.

::: {.warn title="띄어쓰기 하나가 만드는 사고"}
`rm *.log`를 치려다 `rm * .log`처럼 공백이 하나 끼면, 셸은 이것을 `*`(이 폴더의 모든 파일)와 `.log` 두 낱말로 자릅니다. 폴더 안의 파일 전부가 삭제 대상이 됩니다. 별표가 든 명령은 `rm` 자리에 먼저 `ls`를 넣어 **무엇이 걸리는지 눈으로 확인**하세요.
:::

## 흐름을 잇기: 입출력, 리다이렉션, 파이프 {#pipe}

주방에는 완성된 요리가 나오는 배식구가 있고, "재료가 떨어졌어요" 같은 알림은 다른 통로로 전해집니다. 접시에 알림 쪽지가 섞여 나가면 곤란하기 때문입니다.

프로그램도 실행될 때마다 통로 세 개를 받습니다.

- **표준 입력**(stdin): 프로그램이 읽어 들이는 입구. 기본은 키보드입니다.
- **표준 출력**(stdout): 결과가 나가는 출구. 기본은 화면입니다.
- **표준 오류**(stderr): 오류나 진행 상황 같은 "불평"이 나가는 출구. 이것도 기본은 화면입니다.

::: {.fig src="three-streams.svg"}
입구 하나, 출구 둘. 평소에는 두 출구가 모두 화면으로 이어져 있어서 구분되지 않습니다.
:::

출구가 화면에 고정된 것은 아닙니다. 다른 곳으로 바꿔 끼울 수 있고, 이것을 **리다이렉션**(redirection)이라고 합니다.

```bash
$ ls > list.txt
$ echo "빌드 시작" >> build.log
```

- `>`는 표준 출력을 파일로 보냅니다. 화면에는 아무것도 나오지 않습니다. 파일이 이미 있으면 **내용을 지우고 새로 씁니다.**
- `>>`는 기존 내용 뒤에 **이어 씁니다.** 프로그램의 실행 기록인 로그처럼 쌓아야 하는 것에 씁니다.

### 파이프: 명령과 명령을 잇는 컨베이어 벨트

출구를 파일이 아니라 **다른 프로그램의 입구**에 끼울 수도 있습니다. 세로 막대 `|`로 잇고, **파이프**(pipe)라고 부릅니다. 공장의 컨베이어 벨트처럼 앞 명령이 내놓은 것이 곧장 뒤 명령으로 흘러갑니다.

```bash
$ cat app.log | grep ERROR | wc -l
2
```

`cat`이 로그 파일의 내용을 내보내고, `grep`이 그중 `ERROR`가 든 줄만 통과시키고, `wc -l`이 남은 줄 수를 셉니다. "오류가 몇 번 났지?"라는 질문에 프로그램을 새로 짜지 않고 답했습니다.

::: {.fig src="pipeline.svg"}
로그 다섯 줄이 벨트를 타고 가며 걸러지고 세어집니다. 명령 하나는 한 가지 일만 하고, 파이프가 그것들을 잇습니다.
:::

::: {.key}
셸의 힘은 큰 명령 하나가 아니라 **작은 명령을 잇는 방식**에서 나옵니다. `>`는 파일로, `|`는 다음 명령으로 보냅니다.
:::

## 찾기: find는 이름을, grep은 내용을 {#search}

프로젝트가 커지면 "그 파일 어디 있지?"와 "이 설정을 어디서 쓰지?"를 하루에도 몇 번씩 묻게 됩니다. 두 질문은 도구가 다릅니다.

::: {.fig src="find-vs-grep.svg"}
`find`는 이름표를 보고 파일을 골라내고, `grep`은 파일을 열어 글자가 든 줄을 골라냅니다.
:::

```bash
$ find . -name "*.png"
$ grep -rn "timeout" src
```

- 첫 줄은 지금 폴더(`.`) 아래를 전부 뒤져, 이름이 `.png`로 끝나는 파일의 경로를 출력합니다. 따옴표를 붙인 것은 셸이 별표를 먼저 펼치지 않고 `find`에게 그대로 넘기게 하려는 것입니다.
- 둘째 줄은 `src` 폴더 아래의 모든 파일(`-r`)에서 `timeout`이 든 줄을 찾아 줄 번호(`-n`)와 함께 보여 줍니다.

### 정규식 맛보기

"`build-` 뒤에 숫자가 이어지는 이름"처럼 글자 그대로가 아니라 **모양**으로 찾고 싶을 때가 있습니다. 글자의 모양을 적는 표기법이 **정규식**(regular expression)입니다. 네 가지만 먼저 봅시다.

| 기호 | 뜻 | 예 |
|---|---|---|
| `^` | 줄의 맨 앞 | `^ERROR` → ERROR로 시작하는 줄 |
| `$` | 줄의 맨 끝 | `done$` → done으로 끝나는 줄 |
| `.` | 아무 글자 하나 | `a.c` → abc, a1c |
| `[0-9]+` | 숫자가 한 개 이상 | `build-[0-9]+` → build-17 |

`grep -E "^ERROR" app.log`처럼 `-E` 옵션과 함께 씁니다.

::: {.note}
AI 코딩 도구는 `grep`보다 빠른 `rg`(ripgrep)를 자주 씁니다. `rg`는 숨김 파일과, Git([7장](ch07.html))이 무시하도록 설정해 둔 파일을 기본으로 건너뜁니다. 그래서 "검색 결과 0건"이 "그런 코드는 없다"는 뜻이 아닐 수 있습니다. 결과가 없으면 검색 범위부터 의심하세요.
:::

::: {.deep title="찾은 파일을 한꺼번에 처리할 때: 이름 속의 공백"}
`find`가 찾은 파일들을 다른 명령에 넘겨 한꺼번에 처리할 때 `xargs`를 씁니다. 표준 입력으로 들어온 목록을 뒤 명령의 인수로 바꿔 주는 도구입니다. 그런데 `xargs`는 목록을 공백과 줄바꿈에서 자르기 때문에 `My Game.txt`가 또 둘로 쪼개집니다.

```bash
$ find . -name "*.txt" -print0 | xargs -0 wc -l
```

`-print0`과 `-0`은 "이름과 이름 사이를, 파일 이름에는 절대 들어갈 수 없는 특수한 바이트로 구분하자"는 약속입니다. 한번 쪼개진 이름은 나중에 따옴표를 붙여도 되돌릴 수 없습니다.
:::

## 성공과 실패: 종료 코드와 && {#exit}

주방은 주문을 끝낼 때마다 창구에 "완료" 또는 "반려"를 알립니다. 프로그램도 끝날 때 셸에 숫자 하나를 남깁니다. **종료 코드**(exit code)입니다. 규칙은 단순합니다. **0이면 성공, 0이 아니면 실패**입니다. 화면에는 보이지 않지만 `echo $?`로 방금 끝난 명령의 종료 코드를 볼 수 있습니다.

```bash
$ cat nofile.txt
cat: nofile.txt: No such file or directory
$ echo $?
1
```

이 숫자 덕분에 "앞 명령이 성공했을 때만 다음 명령을 실행"할 수 있습니다. `&&`가 그 일을 합니다. 반면 `;`는 성공 여부를 따지지 않고 이어서 실행합니다.

::: {.fig src="exit-chain.svg"}
같은 두 명령도 무엇으로 잇느냐에 따라 결과가 달라집니다. `&&`는 종료 코드가 0일 때만 열리는 문입니다.
:::

`cd build; rm -rf *`에서 `build` 폴더가 없으면 `cd`는 실패하고, 셸은 원래 폴더에 그대로 서 있습니다. 그런데 `;`는 아랑곳하지 않고 `rm -rf *`를 실행합니다. 지워지는 것은 **지금 서 있던 폴더의 내용**입니다. `cd build && rm -rf *`였다면 `cd`가 실패한 순간 멈췄을 것입니다.

### 오류 메시지 읽기

오류 메시지는 대개 `누가: 무엇을: 왜`의 모양입니다. 위의 `cat` 오류도 그렇습니다. 자주 만나는 세 가지는 이렇습니다.

| 메시지 | 뜻 | 먼저 볼 것 |
|---|---|---|
| `command not found` | 그 이름의 프로그램을 못 찾음 | 오타, 설치 여부([6장](ch06.html)) |
| `No such file or directory` | 그 경로에 파일이 없음 | `pwd`와 `ls`로 위치와 이름 |
| `Permission denied` | 권한이 없음 | 파일의 권한([6장](ch06.html)) |

오류가 수십 줄 쏟아질 때는 맨 아래가 아니라 **가장 먼저 나온 오류**를 찾으세요. 뒤의 것들은 첫 실패가 낳은 결과인 경우가 많습니다. AI에게 오류를 넘길 때는 실행한 명령, `pwd`의 결과, 오류 메시지 전체를 함께 주세요.

::: {.deep title="파이프 중간에서 실패하면 (pipefail)"}
파이프로 이은 줄의 종료 코드는 **맨 마지막 명령의 것**입니다. `./build.sh | tee build.log`에서 `tee`는 받은 내용을 화면과 파일에 함께 적는 명령입니다. 빌드가 실패해도 `tee`만 성공하면 줄 전체가 0, 곧 성공으로 보입니다. 로그가 저장된 것과 빌드가 성공한 것은 별개입니다.

bash와 zsh에서 `set -o pipefail`을 켜면 중간 명령이 하나만 실패해도 줄 전체가 실패가 됩니다.
:::

::: {.deep title="같은 오류가 한글로도, 영어로도 나오는 이유 (로케일)"}
언어와 지역 설정을 **로케일**(locale)이라고 합니다. 로케일에 따라 오류 메시지의 언어, 날짜와 숫자의 표기, 글자 정렬 순서가 달라집니다. 내 컴퓨터와 서버에서 같은 명령의 출력이 다르다면 로케일을 의심해 보세요. 스크립트가 화면의 문장이 아니라 **종료 코드**로 성공을 판단해야 하는 이유이기도 합니다.
:::

## 셸 스크립트: 명령을 파일로 묶기 {#script}

같은 명령 다섯 줄을 매일 친다면, 파일에 적어 두고 한 번에 실행하는 편이 낫습니다. 명령을 순서대로 적은 파일이 **셸 스크립트**(shell script)입니다. 주방 벽에 붙여 둔 작업 순서표와 같습니다.

설정 파일을 백업하는 `backup.sh`를 만들어 보겠습니다.

```bash
#!/usr/bin/env bash
set -e
dest="backup"
tmp=$(mktemp)
trap 'rm -f "$tmp"' EXIT

mkdir -p "$dest"
for f in data/*.json; do
  cp "$f" "$dest/"
  echo "$f" >> "$tmp"
done
cat "$tmp" | wc -l
echo "백업 완료"
```

- **1행**은 이 파일을 bash로 실행하라는 표시입니다.
- **2행** `set -e`는 "명령 하나라도 실패하면 그 자리에서 멈춰라"입니다.
- **3행**은 **변수**를 만듭니다. `dest`라는 이름에 `backup`이라는 값을 붙였습니다. `=` 양옆에 공백을 두면 안 됩니다. 꺼내 쓸 때는 `$dest`처럼 앞에 `$`를 붙입니다.
- **4행**의 `mktemp`는 겹치지 않는 이름의 임시 파일을 만들고 그 경로를 출력합니다. `$(...)`는 명령의 출력을 값으로 받는 문법입니다.
- **5행** `trap ... EXIT`는 "성공하든 실패하든, 끝날 때 임시 파일을 지워라"라는 예약입니다. 퇴근 전 뒷정리입니다.
- **7행**의 `-p`는 폴더가 이미 있어도 오류를 내지 않게 합니다.
- **8~11행**은 **반복**입니다. `data` 폴더의 json 파일마다 한 번씩, 복사하고 그 이름을 임시 파일에 적습니다.
- **12~13행**은 복사한 파일 수를 세고 끝을 알립니다.

변수는 `"$f"`처럼 큰따옴표로 감쌌습니다. 값에 공백이 있어도 한 낱말로 유지하기 위해서입니다. 실행은 `bash backup.sh`로 합니다.

`set -e`가 왜 필요한지는 실패하는 날에 드러납니다.

::: {.fig src="script-stop.svg"}
두 번째 복사가 실패했을 때. `set -e`가 없으면 스크립트는 끝까지 달려 "백업 완료"를 출력합니다.
:::

셸은 원래 명령이 실패해도 다음 줄로 넘어갑니다. 그래서 `set -e`가 없는 스크립트에서는 **마지막 줄의 "완료" 메시지가 아무것도 보증하지 않습니다.**

::: {.deep title="쓰다가 멈춰도 파일이 깨지지 않게: 임시 파일과 원자적 저장"}
중요한 파일을 직접 덮어쓰다가 중간에 프로그램이 죽으면 반쯤 쓰인 파일이 남고, 다음 실행은 그 파일을 읽지 못합니다.

안전한 방법은 **같은 폴더의 임시 파일에 끝까지 쓴 다음, 이름을 바꿔 원본 자리에 갈아 끼우는 것**입니다. 같은 파일 시스템 안에서 이름 바꾸기는 "전부 되거나, 전혀 안 되거나" 둘 중 하나로 끝납니다. 이런 성질을 **원자적**(atomic)이라고 합니다. 읽는 쪽은 옛 파일이나 새 파일 중 하나만 보게 됩니다.
:::

## 지우기 전에: 프로젝트 폴더의 네 종류 {#project}

휴지통에 넣은 파일은 되살릴 수 있습니다. 하지만 **`rm`으로 지운 파일은 휴지통을 거치지 않습니다.** 폴더를 통째로, 묻지도 않고 지우는 `rm -rf`는 더 말할 것도 없습니다. 그러니 지우는 명령 앞에서는 "이것은 다시 만들 수 있는가?"를 먼저 물어야 합니다.

프로젝트 폴더 안의 것들은 이 기준으로 네 종류로 나뉩니다.

::: {.fig src="project-layout.svg"}
프로젝트 폴더의 네 종류. 폴더 이름은 프로젝트마다 다르지만 "다시 만들 수 있는가"라는 기준은 같습니다.
:::

**소스**는 사람이 직접 쓴 원본이고, **빌드 결과**는 소스로 만들어 낸 완성품입니다. **캐시**는 다음번에 빨리 하려고 남겨 둔 중간 결과입니다. 내려받은 외부 코드가 든 `node_modules` 같은 폴더도 설치 명령으로 다시 채울 수 있습니다. 반면 세이브 파일, 사용자가 올린 사진, 데이터베이스 같은 **실행 데이터**는 프로그램을 쓰는 동안 쌓인 것이라 어디에서도 다시 만들 수 없습니다.

::: {.warn title="이름을 믿지 마세요"}
폴더 이름이 `build`나 `cache`라고 해서 내용까지 보장되지는 않습니다. 하나뿐인 원본이 캐시 폴더에 섞여 있는 일도 있습니다. "정리" 명령은 실행하기 전에 **무엇을 지우는지** 읽으세요.
:::

지우는 명령 앞에서 지킬 습관은 세 가지입니다.

1. **`pwd`로 서 있는 곳을 확인합니다.** 상대 경로와 별표는 서 있는 곳에 따라 뜻이 달라집니다.
2. **같은 경로로 `ls`를 먼저 해 봅니다.** `rm -rf build/*`를 치기 전에 `ls build/*`.
3. **변수가 든 삭제 명령은 값부터 출력해 봅니다.** `rm -rf "$dir"/*`에서 `dir`이 비어 있으면 `/*`, 곧 컴퓨터 전체를 가리킵니다.

::: {.key}
지우기 전에 묻습니다. **지금 어디에 서 있는가, 무엇이 걸리는가, 다시 만들 수 있는가.**
:::

소스를 지키는 가장 확실한 방법은 변경 이력을 남겨 두는 것입니다. [7장](ch07.html)에서 다룹니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 터미널 / 셸 | 글자가 오가는 창 / 그 글을 해석해 프로그램을 실행시키는 프로그램 |
| 절대 경로 / 상대 경로 | 루트에서 출발, 어디서나 같음 / 작업 디렉터리에서 출발, 서 있는 곳에 따라 달라짐 |
| 코드 파일의 위치 / 작업 디렉터리 | 파일이 저장된 곳 / 실행할 때 서 있던 곳. 상대 경로의 기준은 뒤쪽 |
| 리다이렉션 / 파이프 | 출력을 파일로 / 출력을 다음 명령의 입력으로 |
| 와일드카드 / 정규식 | 파일 이름을 고르는 표기, 셸이 펼침 / 글자의 모양을 적는 표기, `grep` 같은 프로그램이 해석 |

## 실전 사례 {#case}

::: {.case title="편집기에서는 되는데 터미널에서는 설정 파일을 못 찾는다"}
게임을 편집기의 실행 버튼으로 켜면 잘 됩니다. 그런데 터미널에서 `src` 폴더로 들어가 `python3 main.py`로 실행하면 `FileNotFoundError`와 함께 `data/settings.json`이 없다고 나옵니다. 코드는 한 글자도 바꾸지 않았습니다.

1. **오류 메시지에서 경로를 읽습니다.** `data/settings.json`은 `/`로 시작하지 않으니 상대 경로입니다.
2. **서 있는 곳을 확인합니다.** `pwd`의 결과는 `/Users/mina/mygame/src`입니다.
3. **둘을 이어 붙여 봅니다.** 프로그램이 실제로 찾은 곳은 `/Users/mina/mygame/src/data/settings.json`입니다. `ls`로 보면 `src` 안에 `data` 폴더는 없습니다. 진짜 파일은 한 칸 위 `mygame/data`에 있습니다.
4. **차이를 설명합니다.** 편집기는 프로젝트 폴더인 `mygame`을 작업 디렉터리로 삼아 실행했고, 터미널에서는 `src`에 서서 실행했습니다.
5. **고치고 확인합니다.** 급한 대로 `cd ..` 한 뒤 `python3 src/main.py`로 실행하면 됩니다. 제대로 고치려면 코드가 "이 코드 파일이 있는 폴더"를 기준으로 경로를 만들게 하고, 서로 다른 폴더 두 곳에서 실행해 봅니다.

코드 파일이 있는 곳과 프로그램이 실행된 곳은 다를 수 있습니다. 상대 경로는 언제나 실행된 곳을 따라갑니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- **터미널**은 글자가 오가는 창구, **셸**은 그 글을 해석해 프로그램을 실행시키는 직원입니다.
- 파일은 루트 `/`에서 뻗어 나가는 나무에 정리됩니다. **절대 경로**는 루트에서, **상대 경로**는 **작업 디렉터리**에서 출발합니다.
- 명령 한 줄은 **명령, 옵션, 인수**로 읽습니다. 셸은 공백에서 자르고, 따옴표는 묶고, 별표는 파일 이름으로 펼칩니다.
- 프로그램에는 입구 하나(표준 입력)와 출구 둘(표준 출력, 표준 오류)이 있습니다. `>`는 출력을 파일로, `|`는 다음 명령으로 보냅니다.
- **종료 코드** 0은 성공입니다. `&&`는 앞 명령이 성공했을 때만 다음을 실행합니다.
- 스크립트는 `set -e`로 실패한 줄에서 멈추게 합니다. "완료"라는 글자가 아니라 종료 코드를 믿습니다.
- `rm`에는 휴지통이 없습니다. 지우기 전에 `pwd`와 `ls`로 확인합니다.
:::

## 확인 문제 {#quiz}

::: {.q}
작업 디렉터리가 `/Users/mina/mygame/src`일 때 `../data/settings.json`은 어느 파일을 가리킬까요? 절대 경로로 답해 보세요.

::: {.a}
`/Users/mina/mygame/data/settings.json`입니다. `..`은 한 칸 위인 `mygame`을 뜻하고, 거기서 `data` 폴더로 내려갑니다.
:::
:::

::: {.q}
`cd My Project`를 쳤더니 오류가 납니다. 폴더는 분명히 있습니다. 원인은 무엇이고 어떻게 고칠까요?

::: {.a}
셸이 공백에서 줄을 잘라 `My`와 `Project`라는 낱말 두 개로 넘겼기 때문입니다. `cd "My Project"`처럼 따옴표로 감싸면 낱말 하나로 전달됩니다.
:::
:::

::: {.q}
`./build.sh > build.log`로 실행했는데 오류 메시지가 화면에 그대로 나오고 `build.log`에는 없습니다. 왜 그럴까요?

::: {.a}
`>`는 표준 출력만 파일로 돌립니다. 오류 메시지는 표준 오류라는 다른 출구로 나가므로 여전히 화면에 나옵니다. 오류도 파일에 담으려면 `2> error.log`처럼 2번 출구를 따로 돌립니다.
:::
:::

::: {.q}
AI가 빌드 폴더를 비우는 명령으로 `cd build; rm -rf *`를 제안했습니다. 실행하기 전에 무엇을 바꿔 달라고 해야 할까요?

::: {.a}
`;`를 `&&`로 바꿔야 합니다. `build` 폴더가 없어서 `cd`가 실패해도 `;`는 다음 명령을 실행하므로, 지금 서 있는 폴더의 내용이 지워집니다. `rm -rf build/*`처럼 대상 경로를 직접 적으면 더 분명합니다.
:::
:::

::: {.q}
AI가 만들어 준 백업 스크립트를 돌렸더니 마지막에 "백업 완료"가 출력됐습니다. 성공했다고 믿어도 될까요? 무엇을 확인하겠습니까?

::: {.a}
아직 믿을 수 없습니다. `set -e`가 없는 스크립트는 중간에 실패해도 끝까지 달려 마지막 메시지를 출력합니다. 스크립트에 `set -e`가 있는지, 실행 직후 `echo $?`가 0인지, 출력 중간에 오류가 없었는지 확인합니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI 코딩 도구는 터미널 명령을 직접 실행하려 합니다. 특히 파일을 지우거나 옮기는 일은 **실행 전에 무엇이 대상인지 보여 주게** 하세요.

> 프로젝트의 빌드 결과와 캐시를 정리하는 `clean.sh`를 만들어 줘. bash 기준이고 macOS와 Linux 양쪽에서 돌아야 해. 프로젝트 폴더 밖의 경로와 `data/`, `saves/` 폴더는 절대 건드리지 마. `set -e`를 쓰고 경로 변수는 모두 큰따옴표로 감싸 줘. 어느 폴더에서 실행해도 같은 대상을 가리키게 하고, 실제로 지우지 않고 지울 목록만 출력하는 `--dry-run` 옵션을 넣어 줘. 먼저 그 옵션으로 실행한 결과를 나에게 보여 줘.

**받은 답에서 확인할 것**: 삭제 대상이 절대 경로로 출력되는가, 변수가 비었을 때 `rm -rf "$dir"/*` 같은 줄이 엉뚱한 곳을 가리키지 않는가, 명령을 `;`가 아니라 `&&`나 `set -e`로 이었는가.
:::

## 용어 정리 {#terms}

::: {.terms}
터미널 (terminal)
:   글자로 명령을 입력하고 결과를 글자로 돌려받는 창.

셸 (shell)
:   입력한 명령을 해석해 프로그램을 실행시키는 프로그램.

디렉터리 (directory)
:   파일과 다른 디렉터리를 담는 곳. 폴더와 같은 말.

경로 (path)
:   파일이나 폴더의 위치를 `/`로 이어 적은 주소.

작업 디렉터리 (working directory)
:   셸이나 프로그램이 지금 서 있는 폴더. 상대 경로의 기준이 된다.

절대 경로 (absolute path)
:   루트 `/`에서 출발해 전부 적은 경로.

상대 경로 (relative path)
:   작업 디렉터리에서 출발하는 경로.

옵션 (option)
:   명령의 동작 방식을 바꾸는 낱말. `-r`, `--help`처럼 `-`로 시작한다.

인수 (argument)
:   명령에 건네는 대상. 주로 파일이나 폴더의 경로.

와일드카드 (wildcard)
:   여러 파일 이름을 한꺼번에 가리키는 기호. 셸이 실제 이름들로 펼친다.

표준 출력 / 표준 오류 (stdout / stderr)
:   프로그램의 두 출구. 결과는 표준 출력으로, 오류와 진행 상황은 표준 오류로 나간다.

리다이렉션 (redirection)
:   입구나 출구를 파일로 바꿔 끼우는 것. `>`는 덮어쓰고 `>>`는 이어 쓴다.

파이프 (pipe)
:   앞 명령의 표준 출력을 뒤 명령의 표준 입력에 잇는 연결. `|`로 쓴다.

종료 코드 (exit code)
:   프로그램이 끝나며 남기는 숫자. 0은 성공, 그 밖은 실패.

정규식 (regular expression)
:   글자의 모양을 적는 표기법. 검색 조건으로 쓴다.

셸 스크립트 (shell script)
:   셸 명령을 순서대로 적어 한 번에 실행하는 파일.
:::
