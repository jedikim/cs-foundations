::: {.lead}
컴퓨터 안에는 숫자도, 글자도, 사진도 들어 있습니다. 그런데 컴퓨터가 실제로 다룰 수 있는 것은 '켜짐'과 '꺼짐' 두 가지뿐입니다. 전등 스위치처럼요. 스위치만으로 어떻게 숫자를 적고, 한글을 적고, 사진까지 담을까요? 이 장에서는 그 방법을 하나씩 알아봅니다.
:::

::: {.goals}
- 비트와 바이트가 무엇인지 말할 수 있습니다.
- 컴퓨터가 0과 1만으로 숫자를 적는 방법을 설명할 수 있습니다.
- 글자와 사진도 컴퓨터 안에서는 숫자로 저장된다는 것을 설명할 수 있습니다.
- 글자가 이상하게 깨져 보이거나 계산 결과가 살짝 어긋나는 이유를 알 수 있습니다.
- AI에게 숫자, 글자, 파일을 맡길 때 무엇을 정해 줘야 하는지 말할 수 있습니다.
:::

## 비트: 켜거나 끄거나, 스위치 하나 {#bit}

전등 스위치를 다시 떠올려 봅시다. 스위치는 꺼져 있거나 켜져 있습니다. 그 중간은 없습니다.

컴퓨터 안에도 이런 스위치가 있습니다. 눈에 보이지 않을 만큼 작고, 수가 엄청나게 많습니다. 1장에서 본 CPU 칩 하나에만 수십억 개가 들어 있습니다. 컴퓨터는 **아주 작은 스위치를 엄청나게 많이 모아 놓은 기계**입니다.

이제 약속을 하나 합시다. 꺼짐은 0, 켜짐은 1이라고 적습니다. 이렇게 0 아니면 1인 스위치 하나를 **비트**(bit)라고 부릅니다. 컴퓨터가 다루는 가장 작은 정보입니다.

왜 하필 두 가지일까요? 밤에 멀리 있는 친구에게 손전등으로 신호를 보낸다고 해 봅시다. "켰다"와 "껐다"만 쓰면 헷갈릴 일이 없습니다. 밝기를 열 단계로 나눠 보내면 6단계인지 7단계인지 알아보기 어렵습니다. 컴퓨터 속 전기 신호도 같습니다. 둘로만 나누면 조금 흔들려도 틀리지 않습니다.

스위치 하나로는 "예"와 "아니요"밖에 적지 못합니다. 하지만 두 개를 나란히 놓으면 00, 01, 10, 11로 네 가지를 적을 수 있습니다.

::: {.fig src="bit-switches.svg"}
스위치가 하나 늘 때마다 만들 수 있는 가짓수가 두 배가 됩니다. 여덟 개를 나란히 놓으면 256가지입니다.
:::

1개면 2가지, 2개면 4가지, 3개면 8가지입니다. 8개면 2를 여덟 번 곱한 256가지입니다. 수학에서는 이것을 $2^8$이라고 쓰고 "2의 8제곱"이라고 읽습니다.

컴퓨터는 비트를 여덟 개씩 묶어서 다룹니다. 이 묶음 하나를 **바이트**(byte)라고 부릅니다. 1바이트로는 256가지를 구분할 수 있습니다. 파일의 크기나 메모리의 넓이를 잴 때 이 바이트로 셉니다.

::: {.photo src="punch-card.jpg"}
옛날 컴퓨터는 종이 카드에 구멍을 뚫어 정보를 적었습니다. 자리마다 구멍이 "있다" 아니면 "없다" 두 가지뿐이라는 점이 스위치와 같습니다. 맨 윗줄의 글자는 사람이 읽으라고 찍어 둔 것입니다.
:::

::: {.key}
컴퓨터 안의 모든 것은 스위치 줄입니다. 그 줄을 **어떤 약속으로 읽느냐**에 따라 숫자도, 글자도, 그림도 됩니다.
:::

## 2진수와 16진수: 스위치 줄을 숫자로 읽기 {#binary}

스위치 여덟 개가 `01000001` 모양으로 놓여 있다고 합시다. 이 줄을 숫자로 읽는 약속부터 알아봅시다.

우리가 늘 쓰는 숫자에서 345는 "100이 3개, 10이 4개, 1이 5개"라는 뜻입니다. 왼쪽으로 한 칸 갈 때마다 자리의 값, 곧 자릿값이 열 배가 됩니다. 한 자리에 0부터 9까지 열 가지를 쓰기 때문입니다. 이렇게 적는 수를 10진수라고 합니다.

스위치는 한 자리에 0과 1, 두 가지만 씁니다. 그래서 왼쪽으로 한 칸 갈 때마다 값이 **두 배**가 됩니다. 오른쪽부터 1, 2, 4, 8, 16, 32, 64, 128입니다. 이렇게 0과 1만으로 적는 수를 **2진수**(binary)라고 합니다.

읽는 법은 하나뿐입니다. **켜진 자리의 값만 더합니다.**

::: {.fig src="binary-place.svg"}
스위치 여덟 개 `01000001`을 읽는 법. 아래쪽의 16진수는 바로 뒤에서 설명합니다.
:::

`01000001`에서 켜진 곳은 64 자리와 1 자리입니다. 그래서 64 + 1 = 65입니다. 여덟 개를 모두 켠 `11111111`은 128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = 255입니다. 모두 끄면 0입니다. 1바이트에 0부터 255까지의 수가 담기는 까닭입니다.

::: {.try}
한 손으로 31까지 셀 수 있습니다. 엄지는 1, 집게손가락은 2, 가운뎃손가락은 4, 약손가락은 8, 새끼손가락은 16입니다. 편 손가락의 값만 더합니다. 13은 어떻게 펴야 할까요? (엄지, 가운뎃손가락, 약손가락입니다. 1 + 4 + 8 = 13)
:::

### 16진수: 길어서 줄여 적기

2진수는 너무 깁니다. 255 하나를 적는 데 여덟 글자가 듭니다. 그래서 사람이 읽고 쓸 때는 **네 칸씩 묶어 한 글자로** 줄여 적습니다.

네 칸으로 만들 수 있는 값은 0부터 15까지 16가지입니다. 그런데 숫자는 9까지밖에 없습니다. 그래서 10부터 15까지는 알파벳 A, B, C, D, E, F로 적습니다. A가 10이고 F가 15입니다. 이렇게 한 자리에 16가지를 쓰는 수를 **16진수**(hexadecimal)라고 합니다.

1바이트는 네 칸짜리 묶음 두 개이니 16진수 **두 글자**로 딱 떨어집니다. `0100 0001`에서 앞 묶음 `0100`은 4, 뒤 묶음 `0001`은 1입니다. 이어 적으면 41입니다. 10진수 41(마흔하나)과 헷갈리지 않게 앞에 `0x`를 붙여 `0x41`이라고 적습니다.

16진수 두 글자에서 앞 글자는 "16이 몇 개", 뒤 글자는 "1이 몇 개"라는 뜻입니다. `0x41`은 16이 4개, 1이 1개이니 64 + 1 = 65입니다.

| 2진수 | 10진수 | 16진수 |
|---|---|---|
| `0000 1010` | 10 | `0x0A` |
| `1111 1111` | 255 | `0xFF` |

그림 그리는 앱에서 색을 고를 때 나오는 `#FF8800` 같은 값이 16진수입니다. 오류를 알리는 글에 나오는 `0x`로 시작하는 값도 그렇습니다. 암호가 아니라 바이트를 짧게 적은 것뿐입니다.

## 정수: 칸이 꽉 차면 처음으로 돌아갑니다 {#integer}

공책에는 숫자를 얼마든지 길게 쓸 수 있습니다. 컴퓨터는 다릅니다. 숫자 하나에 **스위치를 몇 개 쓸지 미리 정해 둡니다.** 숫자 칸이 세 개뿐인 점수판과 같습니다. 그 점수판에는 999까지만 적을 수 있습니다.

1, 28, −5처럼 소수점이 없는 수를 **정수**(integer)라고 합니다. 컴퓨터는 정수를 보통 8비트, 16비트, 32비트, 64비트 칸 가운데 하나에 담습니다. 칸 수가 정해지면 담을 수 있는 범위도 정해집니다.

| 칸 수 | 0 이상만 담을 때 | 음수도 담을 때 |
|---|---|---|
| 8비트 | 0 ~ 255 | −128 ~ 127 |
| 16비트 | 0 ~ 65,535 | −32,768 ~ 32,767 |
| 32비트 | 0 ~ 약 43억 | 약 −21억 ~ 21억 |
| 64비트 | 0 ~ 약 1844경 | 약 −922경 ~ 922경 |

0보다 작은 수(음수)도 담을 수 있습니다. 그러려면 맨 앞 스위치 하나를 "음수인가?"를 표시하는 데 씁니다. 그래서 가장 큰 수가 절반쯤으로 줄어듭니다. 표의 '경'은 조의 만 배입니다.

칸이 넓으면 큰 수를 담지만 메모리도 그만큼 더 씁니다. 그래서 담을 값에 맞춰 칸을 고릅니다. 흔히 쓰는 칸은 32비트입니다. 약 21억까지 담으니 게임 점수나 전교생 수에는 넉넉합니다. 하지만 약 80억 명인 세계 인구는 담지 못합니다. 이럴 때는 64비트 칸을 씁니다.

범위를 넘기면 어떻게 될까요? 칸이 세 개뿐인 점수판은 999점 다음에 000으로 돌아갑니다. 1000을 적을 자리가 없기 때문입니다.

컴퓨터도 똑같습니다. 8비트 칸에 255가 들어 있을 때 1을 더하면 256이 아니라 **0**이 됩니다. 이렇게 칸이 넘쳐서 값이 엉뚱해지는 일을 **오버플로**(overflow)라고 합니다.

::: {.fig src="overflow-ring.svg"}
칸 수가 정해진 정수는 고리 모양입니다. 끝에 닿으면 시계처럼 처음으로 돌아갑니다.
:::

오버플로는 알림도 없이 조용히 일어날 때가 많아서 무섭습니다. 체력을 8비트 칸에 담는 게임이 있다고 합시다. 체력이 250인 캐릭터가 회복약으로 10을 얻었습니다. 260이 되어야 하는데 칸은 255까지입니다. 255를 지나 0, 1, 2, 3, 4로 넘어가서 체력이 4가 되어 버립니다. 계산으로는 260 − 256 = 4입니다.

::: {.note}
유튜브는 조회수를 32비트 정수로 세었습니다. 그런데 '강남스타일' 뮤직비디오의 조회수가 그 한계인 약 21억 회에 다가갔습니다. 그래서 칸을 64비트로 넓혔다고 밝혔습니다.
:::

컴퓨터에게 일을 시킬 때 쓰는 말을 **프로그래밍 언어**라고 합니다. 여러 가지가 있고, 정수를 담는 방식도 언어마다 조금씩 다릅니다. 칸을 직접 고르는 언어에서는 `int32`, `int64`, `uint8` 같은 글자가 보입니다. `int`는 정수, 뒤의 숫자는 비트 수입니다. 앞에 `u`가 붙으면 0 이상만 담는 칸입니다.

::: {.tip title="계속 커지는 값은 넉넉한 칸에"}
**파이썬**(Python)이라는 프로그래밍 언어는 정수 칸을 알아서 늘려 주어서 넘치지 않습니다. 칸 크기가 정해진 언어에서는 조회수나 점수처럼 계속 커지는 값을 처음부터 64비트처럼 넉넉한 칸에 담습니다. AI에게는 "이 값은 21억을 넘을 수 있어"라고 알려 줍니다.
:::

### 날짜와 시각도 정수 하나입니다

달리기 기록은 "출발하고 몇 초 지났나"로 적습니다. 컴퓨터도 시각을 이렇게 적을 때가 많습니다. 출발선은 1970년 1월 1일 0시이고, 그때부터 지난 초를 정수 하나로 셉니다. 2025년 11월은 약 17억 6천만 초째입니다. `1762905600` 같은 열 자리 숫자를 보면 날짜일 수 있습니다.

이것을 알면 이상한 날짜도 읽을 수 있습니다.

- 화면에 뜬금없이 **1970년 1월 1일**이 보이면 날짜 칸에 0이나 빈 값이 들어갔기 쉽습니다.
- 초가 아니라 1000분의 1초로 세는 프로그램도 있습니다. 둘을 헷갈리면 오늘이 1970년 1월이나 수만 년 뒤로 나옵니다.
- 32비트 칸에 초를 세면 약 21억 초째인 2038년 1월 19일에 넘칩니다. 그래서 요즘은 64비트 칸에 셉니다.

날짜를 주고받는 방법은 [8장](ch08.html)에서 다룹니다.

### 나머지 연산: 일부러 돌게 만들기

끝에 닿으면 처음으로 돌아가는 성질은 쓸모도 있습니다. 시계가 그렇습니다. 10시에서 5시간이 지나면 15시가 아니라 3시입니다. 15를 12로 나누면 몫이 1이고 **나머지**가 3이기 때문입니다.

이렇게 나머지를 구하는 계산을 **나머지 연산**(modulo)이라고 합니다. 프로그래밍 언어에서는 대개 `%` 기호로 적습니다. 백분율의 %와 모양만 같고 뜻은 다릅니다. `15 % 12`는 "15를 12로 나눈 나머지"이고 답은 3입니다. 위 그림의 `(10 + 5) % 12 = 3`이 이 계산입니다.

보드게임의 차례도 이렇게 정합니다. 민지, 준호, 서연, 태윤 네 명에게 0번, 1번, 2번, 3번을 붙입니다. 다음 차례는 "지금 번호에 1을 더하고 4로 나눈 나머지"입니다.

- 민지(0번) 다음은 (0 + 1) % 4 = 1, 곧 준호입니다.
- 태윤(3번) 다음은 (3 + 1) % 4 = 0, 곧 다시 민지입니다.

`% 4`가 4를 0으로 되돌려 줍니다. 요일처럼 "끝 다음이 처음"인 것은 모두 이렇게 계산합니다.

::: {.deep title="차례를 거꾸로 돌리려면 어떻게 할까요?"}
차례가 거꾸로 돈다면 1을 더하는 대신 뺍니다. 그런데 민지(0번)에서 1을 빼면 −1이고, `-1 % 4`의 답은 프로그래밍 언어마다 다릅니다. 파이썬은 3이라고 답합니다. 자바스크립트(JavaScript)를 비롯한 여러 언어는 −1이라고 답합니다. −1번인 사람은 없으니 프로그램이 엉뚱하게 움직입니다.

어느 언어에서나 통하는 방법은 빼기 전에 한 바퀴만큼인 4를 먼저 더하는 것입니다. (0 − 1 + 4) % 4 = 3, 곧 태윤입니다.
:::

## 실수: 0.1 + 0.2가 0.3이 아닌 이유 {#float}

공책에 1 ÷ 3을 소수로 적어 봅시다. 0.3333… 하고 3이 끝없이 이어집니다. 다 적을 수는 없으니 어디선가 끊어야 합니다. 끊은 값은 진짜 3분의 1보다 아주 조금 작습니다.

컴퓨터 안에서도 같은 일이 벌어집니다. 그런데 컴퓨터에서는 뜻밖에도 **0.1**이 그런 수입니다.

아래는 앞에서 말한 프로그래밍 언어 파이썬에게 덧셈을 시켜 본 모습입니다. 이렇게 프로그래밍 언어로 적은 글을 코드라고 합니다. 코드를 처음 본다면 [초코딩 기초](code.html)를 먼저 보아도 좋습니다.

```python
>>> 0.1 + 0.2
0.30000000000000004
```

- 첫 줄의 `>>>`는 파이썬이 입력을 기다린다는 표시입니다. 그 뒤의 `0.1 + 0.2`가 사람이 입력한 것입니다.
- 둘째 줄은 파이썬의 대답입니다. 0.3이 아니라 끝에 4가 붙은 수가 나왔습니다.

파이썬이 고장 난 것이 아닙니다. 다른 프로그래밍 언어 대부분에서도 똑같은 답이 나옵니다.

컴퓨터는 소수도 스위치로 적습니다. 2진수에서 소수점 아래 자리의 값은 2분의 1, 4분의 1, 8분의 1, 16분의 1…입니다. 컴퓨터는 이 가운데 몇 개를 골라 더해서 소수를 만듭니다. 0.5는 2분의 1 하나면 됩니다. 0.75는 2분의 1과 4분의 1을 더하면 됩니다. 그런데 0.1은 아무리 골라 더해도 딱 맞출 수 없습니다.

눈금이 새겨진 자를 떠올리면 쉽습니다. 컴퓨터의 소수는 **눈금 위의 값만** 가질 수 있습니다. 0.1은 눈금과 눈금 사이에 떨어집니다. 그래서 가장 가까운 눈금으로 옮겨 적습니다.

::: {.fig src="float-ruler.svg"}
2진수로 소수점 아래 네 자리만 쓰면 눈금 간격이 16분의 1인 자가 됩니다. 0.1에 딱 맞는 눈금이 없어서 가장 가까운 눈금 0.125에 적습니다.
:::

실제 컴퓨터의 눈금은 그림보다 훨씬 촘촘합니다. 그래도 0.1에 딱 맞는 눈금은 없습니다. 컴퓨터에 저장된 0.1은 사실 0.1000000000000000055511…입니다. 0.2도 살짝 어긋나 있습니다. 어긋난 둘을 더하니 끝에 4가 붙은 것입니다.

0.1이나 3.14처럼 소수점이 있는 수를 컴퓨터에서는 **실수**라고 부릅니다.

실수를 이렇게 **가장 가까운 값**으로 담는 방식을 **부동소수점**(floating point)이라고 합니다. 프로그램을 쓸 때는 이 영어 이름에서 따온 `float`라는 낱말로 실수를 가리킬 때가 많습니다.

어긋나는 정도는 아주 작아서 앞에서부터 15자리쯤까지는 맞습니다. 키, 온도, 달리기 기록처럼 **재서 얻은 값**에는 넉넉합니다. 문제는 **딱 맞아야 하는 값**에 쓸 때 생깁니다.

### 돈은 실수로 계산하지 않습니다

딱 맞아야 하는 값의 대표가 돈입니다. 용돈 기입장 프로그램이 돈을 "천 원" 단위의 소수로 적는다고 합시다. 100원은 0.1입니다. 100원을 열 번 저금하면 1.0, 곧 천 원이 되어야 합니다. 그런데 컴퓨터가 0.1을 열 번 더한 값은 0.9999999999999999입니다. "딱 천 원인가요?" 하고 물으면 컴퓨터는 "아니요"라고 대답합니다.

해결하는 방법은 간단합니다. **가장 작은 단위의 정수로 적습니다.** 100원을 0.1이 아니라 100이라고 적습니다. 100을 열 번 더하면 정확히 1000입니다. 정수끼리의 덧셈은 범위만 넘지 않으면 언제나 정확합니다.

소수점이 있는 돈도 마찬가지입니다. 미국 돈 1달러는 100센트입니다. 19.99달러짜리 게임 값은 19.99가 아니라 1999센트로 적습니다. 화면에 보여 줄 때만 다시 19.99달러로 바꿉니다.

AI가 만든 프로그램도 돈을 실수로 계산할 때가 많습니다. 화면에 `0.30000000000000004`처럼 **꼬리가 긴 숫자**가 보이면 그 신호입니다. 정수로 바꾸는 순간도 조심합니다. 19.99에 100을 곱하면 컴퓨터는 1998.9999999999998이라고 답합니다. 곱한 뒤에 반올림해서 1999로 만들어야 합니다.

나눗셈에는 정해 줄 것이 있습니다. 1000원을 셋이 나누면 333원씩 내고 1원이 남습니다. 이 1원을 어떻게 할지는 컴퓨터가 정해 주지 않습니다. 할인이나 나눠 내기가 있으면 "1원 미만은 버려 줘"처럼 규칙을 말해 줍니다.

::: {.warn title="실수끼리는 '같은가'로 묻지 않습니다"}
0.1을 열 번 더한 값은 1.0과 같지 않았습니다. 그래서 "값이 1.0과 같으면"이라는 조건은 영영 맞지 않을 수 있습니다. 실수를 견줄 때는 "1.0 이상이면"처럼 범위로 묻거나 "두 값의 차이가 아주 작으면"으로 묻습니다. 횟수를 세는 일이라면 정수로 세는 것이 가장 확실합니다.
:::

### 긴 번호와 0으로 시작하는 번호

실수 칸에는 정수도 담을 수 있습니다. 하지만 여기서도 15자리쯤까지만 맞습니다. 웹 페이지를 움직이는 프로그래밍 언어인 자바스크립트는 숫자를 보통 실수 칸에 담습니다. 그래서 1234567890123456789 같은 긴 번호를 넣으면 끝자리가 바뀌어 1234567890123456800이 됩니다.

전화번호도 탈이 납니다. 01012345678을 숫자로 담으면 맨 앞의 0이 사라져 1012345678이 됩니다.

::: {.tip title="계산하지 않는 번호는 글자로"}
전화번호, 학번, 주문 번호는 더하거나 곱할 일이 없습니다. 이런 번호는 숫자가 아니라 **글자**로 담아 달라고 합니다. 코드에서는 따옴표로 감싼 `"01012345678"`이 글자입니다. 받은 결과에서는 긴 번호의 끝이 00으로 바뀌지 않았는지, 앞의 0이 사라지지 않았는지 봅니다. [8장](ch08.html)에서 다시 다룹니다.
:::

## 글자: 번호를 붙이고 바이트로 적기 {#text}

학교에서는 이름 대신 번호로 부를 때가 있습니다. 선생님이 "7번, 나와서 풀어 보세요." 하면 누구인지 다 압니다. 반 전체가 같은 출석부를 쓰기 때문입니다.

컴퓨터가 글자를 적는 방법도 같습니다. 스위치로는 숫자만 적을 수 있으니 **글자마다 번호를 붙입니다.** "A는 65번, B는 66번" 하는 식입니다. 같은 번호표를 쓰는 컴퓨터끼리는 65를 보고 모두 A라고 읽습니다.

처음에는 영어 알파벳과 숫자, 기호 128개에만 번호를 붙였습니다. 이 번호표의 이름이 **아스키**(ASCII)입니다. 128가지는 1바이트에 넉넉히 들어가서 한 글자가 딱 1바이트였습니다.

아스키에는 한글이 들어갈 자리가 없었습니다. 그래서 나라마다 번호표를 따로 만들었습니다. 한국에서 널리 쓴 한글 번호표가 **CP949**입니다. 한국어 윈도우의 메뉴에 'ANSI'나 'EUC-KR'이라고 적힌 것도 이 번호표 쪽입니다. 그런데 번호표가 다른 컴퓨터끼리는 글이 엉뚱하게 보였습니다. 같은 번호가 나라마다 다른 글자였기 때문입니다.

이 혼란을 끝내려고 세계의 모든 글자를 번호표 하나에 모았습니다. 이것이 **유니코드**(Unicode)입니다. 한글, 한자, 이모지까지 글자마다 번호가 하나씩 있습니다. 아스키에 있던 글자는 번호를 그대로 물려받아서 A는 여기서도 65번입니다. '가'는 44032번입니다.

유니코드가 글자 하나에 붙인 번호를 **코드 포인트**(code point)라고 합니다. 코드 포인트는 보통 16진수로 적고 앞에 `U+`를 붙입니다. 44032는 16진수로 AC00이므로 '가'는 `U+AC00`입니다. A는 65가 16진수로 41이니 `U+0041`입니다. 빈 앞자리는 0으로 채웁니다.

번호를 정했다고 끝이 아닙니다. 그 번호를 **바이트로 어떻게 적을지**도 정해야 합니다. 44032는 255보다 커서 1바이트에 들어가지 않기 때문입니다. 번호를 바이트로 적는 규칙을 **인코딩**(encoding)이라고 합니다.

요즘 가장 널리 쓰는 인코딩은 **UTF-8**입니다. 글자에 따라 1바이트에서 4바이트까지 길이를 다르게 적습니다.

::: {.fig src="utf8-bytes.svg"}
글자가 저장되는 두 단계. 유니코드가 번호를 붙이고, UTF-8이 그 번호를 1~4바이트로 적습니다.
:::

'A'는 65번이고 1바이트 `41`로 적습니다. 앞에서 본 `0x41`입니다. '가'는 44032번이고 3바이트 `EA B0 80`으로 적습니다. 웃는 얼굴 이모지는 128512번(`U+1F600`)이고 4바이트입니다. 영문과 숫자는 1바이트, 한글은 3바이트, 이모지는 대부분 4바이트입니다.

그래서 **글자 수와 바이트 수는 다릅니다.** "ABC"는 3글자, 3바이트입니다. "가나다"는 3글자이지만 3 × 3 = 9바이트입니다. "닉네임은 12바이트까지"인 게임이라면 한글로는 12 ÷ 3 = 4글자까지만 됩니다.

길이 제한을 만들 때는 **글자 수로 셀지 바이트 수로 셀지**부터 정합니다. "닉네임은 10자까지"라고만 하면 어느 쪽으로 셀지 AI가 고릅니다. 한글 열 글자와 이모지를 넣어 보면 어떻게 세는지 드러납니다.

### 글자가 깨지는 이유

친구가 보낸 파일을 열었는데 "寃뚯엫" 같은 이상한 글자가 보일 때가 있습니다. 흔히 "글자가 깨졌다"고 말합니다.

바이트에는 "나는 UTF-8로 적혔어요"라는 꼬리표가 없습니다. 그래서 적을 때 쓴 규칙과 읽을 때 쓴 규칙이 다르면, 같은 바이트가 엉뚱한 글자로 바뀝니다.

::: {.fig src="mojibake.svg"}
같은 여섯 바이트가 읽는 규칙에 따라 다른 글자가 됩니다.
:::

"게임"을 UTF-8로 저장하면 한 글자에 3바이트씩, 모두 여섯 바이트입니다. 그림 가운데 줄이 그 여섯 바이트입니다. CP949는 한글 한 글자를 2바이트로 적는 규칙입니다. 그래서 CP949로 읽으면 여섯 바이트를 둘씩 끊습니다. 그 결과가 "寃뚯엫"이라는 엉뚱한 세 글자입니다.

::: {.key}
글자가 깨졌어도 **데이터는 멀쩡합니다.** 틀린 것은 읽는 규칙뿐이므로, 올바른 규칙으로 다시 읽으면 됩니다.
:::

### 깨진 글자를 만났을 때 할 말

깨진 모양을 보면 어느 규칙이 틀렸는지 짐작할 수 있습니다.

| 화면에 보이는 모양 | 일어난 일 |
|---|---|
| "寃뚯엫"처럼 낯선 한자와 한글이 섞임 | UTF-8로 적은 글을 CP949로 읽음 |
| "����"처럼 물음표가 든 마름모가 늘어섬 | CP949로 적은 글을 UTF-8로 읽음 |

프로그램은 깨진 글자 대신 오류를 내기도 합니다. 파이썬은 이런 글을 내고 멈춥니다.

```text
UnicodeDecodeError: 'cp949' codec can't decode byte 0xec in position 14: illegal multibyte sequence
```

"CP949 규칙으로 읽다가 바이트 `0xec`를 글자로 바꾸지 못했다"는 뜻입니다. 파일이 망가진 것이 아니라 읽는 규칙이 틀렸다는 말입니다. 한국어 윈도우에서는 따로 정해 주지 않으면 CP949로 읽는 프로그램이 있어서 자주 만납니다.

어느 쪽이든 AI에게 할 말은 같습니다. **"파일을 읽고 쓸 때 인코딩을 UTF-8로 정해 줘."** 받은 코드에서는 파일을 여는 줄에 `utf-8`이라는 글자가 있는지 봅니다.

::: {.tip title="엑셀에서 열 파일이라면"}
표를 쉼표로 나눠 적은 CSV 파일은 UTF-8로 저장해도 엑셀에서 한글이 깨질 때가 많습니다. 엑셀이 CP949로 읽으려 하기 때문입니다. 이럴 때는 파일 맨 앞에 "UTF-8로 적었음"이라는 표시 3바이트를 붙입니다. 이 표시를 **BOM**이라고 합니다. "엑셀에서 열 거니까 BOM을 붙인 UTF-8로 저장해 줘"라고 말합니다.
:::

::: {.deep title="똑같아 보이는 글자가 다를 수도 있을까요?"}
맥(Mac) 컴퓨터에서 보낸 파일의 이름이 윈도우에서 'ㅎㅏㄴㄱㅡㄹ'처럼 풀려 보일 때가 있습니다. 유니코드에는 한글을 적는 방법이 두 가지 있기 때문입니다. '가'를 완성된 한 글자(`U+AC00`)로 적을 수도 있고, ㄱ과 ㅏ 두 조각을 이어 적을 수도 있습니다. 맥은 파일 이름을 조각으로 적을 때가 많습니다. 두 방법은 화면에 똑같이 보여도 번호와 바이트가 다릅니다. 그래서 분명히 있는 이름인데 검색되지 않는 일이 생깁니다.

견주기 전에 양쪽을 한 가지 모양으로 맞추면 됩니다. 이 일을 유니코드 **정규화**(normalization)라고 합니다. 완성된 글자 쪽으로 모으는 방식의 이름은 NFC입니다. AI에게는 "이름을 견주기 전에 NFC로 정규화해 줘"라고 말합니다.
:::

## 색과 그림: 점 하나에 숫자 세 개 {#pixel}

휴대전화 화면에 물방울이 떨어지면 그 자리가 알록달록한 작은 점으로 보입니다. 물방울이 돋보기 노릇을 한 것입니다. 화면은 이런 작은 점이 바둑판처럼 빽빽이 늘어선 것입니다. 이 점 하나를 **픽셀**(pixel)이라고 합니다.

::: {.photo .half src="pixels-closeup.jpg"}
여러 종류의 화면을 크게 확대한 모습. 점의 모양은 달라도 빨강, 초록, 파랑 세 가지 빛으로 이루어진 것은 같습니다. 오른쪽 아래의 LCD가 요즘 모니터에 많이 쓰는 방식입니다.
:::

픽셀 하나는 빨강, 초록, 파랑 세 가지 빛을 섞어 색을 냅니다. 빛마다 밝기를 0부터 255까지의 숫자로 적습니다. 0은 꺼짐이고 255는 가장 밝음입니다. 0부터 255까지는 딱 1바이트이니 **점 하나에 3바이트**가 듭니다.

이 방식을 빨강(Red), 초록(Green), 파랑(Blue)의 머리글자를 따서 **RGB**라고 합니다. 셋 다 0이면 검정이고, 셋 다 255이면 흰색입니다.

::: {.fig src="pixel-rgb.svg"}
그림은 점의 색을 차례로 적은 숫자 목록입니다.
:::

그림의 주황색 점은 빨강 255, 초록 136, 파랑 0입니다. 색 코드 `#FF8800`은 이 세 바이트를 16진수로 이어 적은 것입니다. FF는 255, 88은 136, 00은 0입니다.

색 코드는 앞에서부터 두 글자씩 빨강, 초록, 파랑입니다. `rgb(255, 136, 0)`이라고 적힌 것도 같은 색을 10진수로 적은 것입니다. AI에게 "조금 더 진한 주황으로"라고 하면 AI가 짐작해서 고릅니다. "`#FF8800`으로 바꿔 줘"라고 하면 딱 그 색이 됩니다.

::: {.try}
`#FF0000`과 `#FFFF00`은 각각 무슨 색일까요? 먼저 짐작한 다음, 검색 사이트나 AI 챗봇에 색 코드를 넣어 확인합니다. (빨강과 노랑입니다. 빨간빛과 초록빛을 함께 켜면 노랑이 됩니다.)
:::

### 그림과 영상의 크기 어림

그림이 숫자 목록이니 크기도 계산할 수 있습니다. 가로 8점, 세로 8점짜리 그림은 점이 8 × 8 = 64개입니다. 점마다 3바이트이니 64 × 3 = 192바이트입니다.

휴대전화 사진은 가로 4000점, 세로 3000점쯤 됩니다. 점이 4000 × 3000 = 1200만 개이고, 점마다 3바이트이니 3600만 바이트, 곧 36MB입니다. 그런데 실제 사진 파일은 3MB쯤입니다.

사진 파일은 이 숫자 목록을 꾹꾹 눌러 줄여 둔 것이기 때문입니다. 이렇게 줄이는 일을 **압축**이라고 합니다. 화면에 그릴 때는 다시 점 하나하나로 펼칩니다. 그래서 3MB짜리 사진도 열면 메모리를 36MB쯤 씁니다.

그림 파일에는 JPEG(`.jpg`)와 PNG(`.png`)가 많습니다. JPEG는 눈에 잘 띄지 않는 부분을 조금 버려서 많이 줄이므로 사진에 알맞습니다. PNG는 하나도 버리지 않아서 글자가 든 화면 캡처에 알맞습니다.

영상은 훨씬 큽니다. 가로 1920점, 세로 1080점짜리 화면 한 장이 약 6MB입니다. 1초에 30장이니, 누르지 않으면 1분에 약 11GB입니다. 그래서 영상은 훨씬 세게 눌러 담습니다.

::: {.tip title="그림은 화면에 보일 크기만큼만"}
AI가 만든 웹 화면이 느리게 뜨면 그림 크기부터 봅니다. 손톱만 한 자리에 4000점짜리 원본 사진을 넣는 일이 흔합니다. "그림을 화면에 보이는 크기에 맞게 줄여서 넣어 줘"라고 말합니다.
:::

## 파일: 같은 바이트, 다른 약속 {#file}

숫자, 글자, 색을 차례로 보았습니다. 셋 다 결국 바이트였습니다.

쪽지에 "0312"라고만 적혀 있다고 합시다. 3월 12일일까요, 비밀번호일까요? 쪽지만 봐서는 알 수 없습니다. 바이트도 그렇습니다.

::: {.key}
바이트는 자기가 무엇인지 스스로 말하지 않습니다.
:::

::: {.fig src="same-bytes.svg"}
같은 바이트 세 개가 읽는 약속에 따라 글자도, 숫자도, 색도 됩니다.
:::

그림의 `EA B0 80`은 앞에서 본 '가'의 세 바이트입니다. 그 아래의 0과 1은 같은 세 바이트를 2진수로 적은 것입니다. 숫자로 읽으면 234, 176, 128입니다. 빨강, 초록, 파랑의 밝기로 읽으면 연한 주황색 점입니다. 어느 쪽이 맞는지는 **읽는 쪽의 약속**이 정합니다. 이 약속을 **형식**(format)이라고 합니다.

**파일**은 바이트를 한 줄로 늘어놓고 이름을 붙인 것입니다. 파일은 크게 두 가지로 나뉩니다.

- **텍스트 파일**은 처음부터 끝까지 글자로 읽으면 되는 파일입니다. 메모장으로 쓴 `.txt` 파일이 그렇습니다. AI가 만들어 주는 코드 파일도 텍스트 파일이라서 메모장으로 열어 볼 수 있습니다.
- **바이너리 파일**(binary file)은 그 밖의 모든 파일입니다. 사진, 음악, 동영상, 게임 프로그램이 여기에 듭니다. 그 형식을 아는 프로그램으로 열어야 합니다.

PNG라는 형식의 그림 파일은 언제나 똑같은 여덟 바이트로 시작합니다. 그 가운데 세 바이트 `50 4E 47`은 아스키로 읽으면 P, N, G입니다. 그림을 여는 프로그램은 이 첫머리를 보고 형식을 확인합니다.

파일 이름 끝의 `.png`, `.txt`를 **확장자**라고 합니다. 컴퓨터는 확장자를 보고 어떤 프로그램으로 열지 고릅니다.

::: {.warn title="확장자는 이름표일 뿐입니다"}
`photo.png`의 이름을 `photo.jpg`로 바꿔도 내용은 한 바이트도 달라지지 않습니다. 이름표만 바꿔 단 것입니다. 형식을 정말 바꾸려면 그림 프로그램으로 열어서 다른 형식으로 다시 저장해야 합니다.
:::

이름표와 내용물이 다른 파일도 있습니다. `.jpg` 그림이 어떤 프로그램에서만 열리지 않거나 "지원하지 않는 형식"이라는 말이 뜨면 이것을 의심합니다. 맥과 리눅스에서는 [5장](ch05.html)에서 배울 터미널에 `file photo.jpg`라고 치면 속의 진짜 형식을 알려 줍니다.

AI에게 "사진 올리기" 기능을 맡겼을 때도 같습니다. 이름이 `.png`로 끝나는지만 확인하는 코드가 흔합니다. "확장자만 믿지 말고 파일 첫머리로 진짜 그림인지 확인해 줘"라고 덧붙입니다.

::: {.try}
사진 파일 하나를 복사해서, 복사본을 메모장 같은 글 편집기로 열어 봅니다. 알아볼 수 없는 글자가 가득합니다. 바이너리 파일을 글자로 읽었기 때문입니다. 맨 앞쪽에서 `PNG`, `JFIF`, `Exif` 같은 글자를 찾아보세요. 저장하지 말고 닫습니다.
:::

### 용량 단위: GB와 GiB

1000m를 1km라고 부르듯이, 바이트도 많아지면 묶어서 부릅니다. 그런데 묶는 방식이 두 가지라서 헷갈립니다.

| 1000씩 묶는 단위 | 1024씩 묶는 단위 |
|---|---|
| 1KB(킬로바이트) = 1000바이트 | 1KiB(키비바이트) = 1024바이트 |
| 1MB(메가바이트) = 1000KB | 1MiB(메비바이트) = 1024KiB |
| 1GB(기가바이트) = 1000MB | 1GiB(기비바이트) = 1024MiB |

1024는 2를 열 번 곱한 수입니다. 스위치로 세는 컴퓨터에게는 1000보다 딱 떨어지는 수입니다. 그래서 예전부터 1024바이트를 "1킬로바이트"라고 불러 왔습니다. 나중에 KiB, MiB, GiB라는 이름을 따로 만들었지만 지금도 섞어 씁니다.

::: {.fig src="units-ruler.svg"}
같은 디스크를 눈금 간격이 다른 두 자로 잰 모습. 바이트 수는 같고 숫자만 다릅니다.
:::

1TB(테라바이트)는 1000GB, 곧 1조 바이트입니다. 저장장치 회사는 1000씩 묶어 "1TB"라고 적습니다. 윈도우는 1024씩 묶어 센 값에 "GB"를 붙여 보여 줍니다. 그래서 새로 산 1TB 디스크가 931GB로 보입니다. 고장도 속임수도 아닙니다.

## 메모리 주소: 번호 붙은 사물함 {#address}

학교 복도에 길게 늘어선 사물함을 떠올려 봅시다. 사물함마다 번호가 붙어 있어서 번호만 알면 바로 찾아갑니다.

컴퓨터의 메모리도 이렇게 생겼습니다. **1바이트짜리 칸이 한 줄로 길게 늘어서 있고,** 칸마다 0번부터 차례로 번호가 붙어 있습니다. 이 번호를 **주소**(address)라고 합니다.

프로그램은 값을 메모리에 넣어 두고 이름을 붙여 씁니다. 아래 그림에서는 10에 `a`, 20에 `b`라는 이름을 붙였습니다. 32비트 정수 하나는 32 ÷ 8 = 4바이트라서 사물함을 네 칸씩 씁니다. `a`는 1000번부터 1003번까지, `b`는 1004번부터 1007번까지입니다.

::: {.fig src="lockers.svg"}
주소는 사물함 번호, 값은 사물함에 든 내용물입니다. 포인터는 번호를 적어 둔 쪽지입니다.
:::

사람은 "`b`의 값"이라고 말합니다. 컴퓨터는 이것을 "1004번부터 네 칸에 든 값"으로 알아듣습니다. 이름은 사람을 위한 별명이고, 컴퓨터는 주소로 찾아갑니다.

주소는 화면에도 나옵니다. 파이썬 프로그램이 `<__main__.Player object at 0x10170e330>` 같은 글자를 찍을 때가 있습니다. `0x` 뒤의 16진수가 주소입니다. 내용물 대신 사물함 번호가 찍힌 것입니다. AI에게 "주소 말고 안에 든 값을 보여 줘"라고 하면 됩니다.

주소도 숫자이니 어딘가에 적어 둘 수 있습니다. 사물함 번호를 쪽지에 적어 두는 것과 같습니다. 이렇게 **주소를 적어 둔 쪽지**를 **포인터**(pointer)라고 부릅니다. 그림의 `p`가 포인터입니다. `p`에 적힌 것은 20이 아니라, 20이 든 곳의 번호 1004입니다.

민지가 자기 사물함 번호를 쪽지에 적어 준호에게 한 장 베껴 주었다고 합시다. 쪽지는 두 장이 되었지만 사물함은 여전히 하나입니다. 준호가 그 사물함에 책을 넣으면, 민지가 열어도 그 책이 보입니다.

프로그램에서도 같은 일이 생깁니다. 목록을 복사했다고 생각했는데 사실은 쪽지만 베낀 경우입니다. 이때 한쪽을 고치면 다른 쪽도 바뀌어 보입니다. [3장](ch03.html)에서 다시 다룹니다.

### 32비트와 64비트

쪽지에도 칸 수가 정해져 있습니다. 주소를 32비트 칸에 적는 프로그램을 **32비트 프로그램**이라고 합니다. 32비트로 만들 수 있는 번호는 약 43억 개입니다. 사물함 하나가 1바이트이니 약 43억 바이트, 곧 4GiB까지만 가리킬 수 있습니다. 주소를 64비트 칸에 적으면 번호가 사실상 바닥나지 않습니다. 요즘 컴퓨터와 스마트폰은 대부분 64비트입니다.

::: {.myth title="64비트는 32비트보다 두 배 빠르다"}
64는 빠르기가 아니라 주소를 적는 칸 수입니다. 더 넓은 메모리를 쓸 수 있을 뿐, 계산이 두 배로 빨라지지는 않습니다.
:::

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 비트 / 바이트 | 스위치 하나 / 스위치 여덟 개 묶음 |
| 글자 수 / 바이트 수 | 눈에 보이는 글자의 개수 / 저장하는 데 드는 칸 수. "가나다"는 3글자, 9바이트 |
| 아스키 / 유니코드 | 영어 글자와 기호 128개의 번호표 / 세계 모든 글자의 번호표 |
| 유니코드 / UTF-8 | 글자에 붙인 번호표 / 그 번호를 바이트로 적는 규칙 |
| 정수 / 실수 | 범위 안에서는 정확함 / 가장 가까운 눈금 값이라 살짝 어긋날 수 있음 |
| 확장자 / 형식 | 파일 이름 끝의 이름표 / 바이트를 읽는 진짜 약속 |
| GB / GiB | 1000씩 묶은 단위 / 1024씩 묶은 단위 |
| 주소 / 값 | 사물함 번호 / 사물함에 든 내용물 |

## 실전 사례 {#case}

::: {.case title="친구가 보낸 메모가 이상한 글자로 보일 때"}
준호가 게임 공략을 메모 파일에 적어 보내 주었습니다. 그런데 내 컴퓨터에서 열었더니 첫 줄의 "게임"이 "寃뚯엫"으로 보입니다. 파일이 망가진 걸까요?

1. **파일이 망가졌는지, 읽기만 틀렸는지 가립니다.** 준호 컴퓨터에서는 멀쩡하게 보인다고 합니다. 바이트는 멀쩡하다는 뜻입니다.
2. **적을 때 쓴 규칙을 알아봅니다.** 준호의 메모 프로그램은 UTF-8로 저장했습니다.
3. **읽을 때 쓴 규칙을 알아봅니다.** 내 프로그램은 이 파일을 CP949로 읽었습니다. 그래서 "寃뚯엫"이 되었습니다.
4. **규칙을 맞춰 다시 엽니다.** 메모장 같은 프로그램에는 대개 파일을 열 때 인코딩을 고르는 메뉴가 있습니다. 거기서 UTF-8을 골라 다시 열면 "게임"이 제대로 보입니다.
5. **깨진 채로 저장하지 않습니다.** 깨져 보이는 채로 저장하면 엉뚱한 글자가 진짜로 파일에 적힙니다. 그러면 되돌리기 어렵습니다.

글자가 깨졌을 때 파일을 지우고 새로 받기부터 하면 원인을 놓칩니다. **적은 규칙과 읽은 규칙을 따로** 알아보는 것이 먼저입니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- **비트**는 스위치 하나, **바이트**는 스위치 여덟 개 묶음입니다.
- **2진수**는 켜진 자리의 값을 더해 읽습니다. **16진수**는 2진수를 네 칸씩 묶어 한 글자로 줄여 적은 것입니다.
- **정수**는 칸 수(8, 16, 32, 64비트)에 따라 담을 수 있는 범위가 정해집니다. 칸이 꽉 차면 처음으로 돌아갑니다. 이것이 오버플로입니다.
- **실수**는 가장 가까운 눈금 값이라 0.1조차 딱 맞지 않습니다. 돈처럼 딱 맞아야 하는 값은 가장 작은 단위의 정수로 계산합니다. 전화번호처럼 계산하지 않는 번호는 글자로 담습니다.
- **글자**마다 번호가 있습니다. 아스키는 영어 글자와 기호 128개의 번호표이고, 유니코드는 세계 모든 글자의 번호표입니다. 유니코드의 번호를 코드 포인트라고 합니다.
- 코드 포인트는 UTF-8 규칙으로 바이트가 됩니다. 적은 규칙과 읽는 규칙이 다르면 글자가 깨집니다. 그럴 때는 UTF-8로 맞춥니다.
- **그림**은 점마다 빨강, 초록, 파랑 세 숫자를 적은 목록입니다.
- 바이트는 자기가 무엇인지 스스로 말하지 않습니다. **읽는 약속**이 뜻을 정합니다. 확장자는 이름표일 뿐입니다.
- **주소**는 사물함 번호, **포인터**는 그 번호를 적은 쪽지입니다. 쪽지를 베껴도 사물함은 하나입니다.
:::

## 확인 문제 {#quiz}

::: {.q}
우리 반은 28명입니다. 스위치를 켜고 끈 모양으로 한 명 한 명을 구분하려고 합니다. 스위치가 적어도 몇 개 있어야 할까요?

::: {.a}
5개입니다. 4개로는 2 × 2 × 2 × 2 = 16가지뿐이라 모자랍니다. 5개면 32가지이니 28명을 모두 구분할 수 있습니다.
:::
:::

::: {.q}
오래된 게임에서 금화를 255개 모은 뒤 하나를 더 주웠더니 금화가 0개가 되었습니다. 왜 그랬을까요? 어떻게 하면 막을 수 있을까요?

::: {.a}
금화 수를 8비트 칸에 담았기 때문입니다. 8비트 칸은 255까지만 담습니다. 1을 더하면 처음인 0으로 돌아갑니다. 이것이 오버플로입니다. 255에서 멈추게 하거나 더 큰 칸을 쓰면 막을 수 있습니다.
:::
:::

::: {.q}
초시계 프로그램이 시간을 0.1초씩 더해 갑니다. "시간이 1.0과 같으면 종을 울려라"라고 시켰는데 종이 울리지 않습니다. 왜 그럴까요? 어떻게 고치면 될까요?

::: {.a}
컴퓨터 안의 0.1은 살짝 어긋난 값입니다. 열 번 더하면 1.0이 아니라 0.9999999999999999가 됩니다. 그래서 "1.0과 같으면"이라는 조건이 영영 맞지 않습니다. 더한 횟수를 정수로 세어 열 번째에 울리게 하면 됩니다. "1.0 이상이면 울려라"로 바꿔도 울리기는 하지만, 한 번 늦은 열한 번째에 울립니다.
:::
:::

::: {.q}
상태 메시지를 "UTF-8로 30바이트까지" 받는 메신저가 있습니다. "오늘은떡볶이먹는날"을 쓸 수 있을까요? 뒤에 느낌표 네 개(!!!!)를 붙이면 어떨까요?

::: {.a}
쓸 수 있습니다. 한글 아홉 글자는 9 × 3 = 27바이트입니다. 느낌표는 하나에 1바이트입니다. 네 개를 붙이면 27 + 4 = 31바이트라서 넘칩니다. 세 개까지만 붙일 수 있습니다.
:::
:::

::: {.q}
서연이는 자기 사물함 번호를 쪽지에 적어 태윤이에게 한 장 베껴 주었습니다. 태윤이가 그 사물함에 체육복을 넣었습니다. 서연이가 사물함을 열면 무엇이 보일까요? 프로그램에서 "복사해 둔 목록까지 같이 바뀌는" 일과 어떻게 닮았을까요?

::: {.a}
체육복이 보입니다. 쪽지는 두 장이지만 사물함은 하나이기 때문입니다. 프로그램에서도 주소를 적은 쪽지(포인터)만 베끼면 두 이름이 같은 곳을 가리킵니다. 그래서 한쪽에서 바꾸면 다른 쪽에서도 바뀌어 보입니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
숫자, 글자, 파일을 다루는 프로그램을 맡길 때는 **어떤 칸에, 어떤 규칙으로 담을지**를 요청문에 적습니다. 적지 않으면 AI가 알아서 고릅니다. 요청문 쓰는 법은 [30장](ch30.html)에서 다룹니다.

> 용돈 기입장 프로그램을 만들어 줘. 돈은 실수(float)가 아니라 원 단위 정수로 계산하고, 1원 미만은 버려 줘. 전화번호는 숫자가 아니라 글자로 저장해 줘. 기록은 UTF-8 CSV 파일로 저장하되, 엑셀에서 열 거니까 BOM을 붙여 줘. 한글과 이모지가 든 메모를 저장했다가 다시 읽어서, 처음과 똑같은지 확인한 결과도 보여 줘.

**받은 답에서 확인할 것**

- 돈과 개수를 계산하는 곳에 `float`나 소수점 있는 숫자가 섞이지 않았는가
- 파일을 읽고 쓰는 줄마다 `utf-8`이라고 적혀 있는가
- 전화번호 같은 번호가 따옴표로 감싼 글자로 담겼는가
- 저장했다가 다시 읽은 결과를 실제로 돌려서 보여 주는가

**AI가 자주 하는 실수**

- 돈을 실수로 계산합니다. 화면에 `0.30000000000000004`처럼 꼬리가 긴 숫자가 보이면 알 수 있습니다.
- 인코딩을 적지 않습니다. 내 컴퓨터에서는 멀쩡한데 다른 컴퓨터나 엑셀에서 한글이 깨지면 이것입니다.
- 글자 수 제한을 엉뚱한 단위로 셉니다. 한글과 이모지를 넣어 보면 드러납니다.
:::

## 용어 정리 {#terms}

::: {.terms}
비트 (bit)
:   0 아니면 1인 스위치 하나로, 컴퓨터가 다루는 가장 작은 정보.

바이트 (byte)
:   비트 여덟 개를 묶은 것으로, 용량을 잴 때 쓰는 단위.

2진수 (binary)
:   0과 1만으로 적은 수.

16진수 (hexadecimal)
:   2진수를 네 칸씩 묶어 0~9와 A~F로 줄여 적은 수.

정수 (integer)
:   1, 28, −5처럼 소수점이 없는 수.

오버플로 (overflow)
:   계산한 값이 정해진 칸에 다 들어가지 않아 엉뚱한 값이 되는 일.

프로그래밍 언어 (programming language)
:   컴퓨터에게 일을 시킬 때 쓰는 말.

나머지 연산 (modulo)
:   나눗셈의 나머지를 구하는 계산.

실수 (float)
:   0.1이나 3.14처럼 소수점이 있는 수.

부동소수점 (floating point)
:   소수점이 있는 수를 정해진 칸 안에 가장 가까운 값으로 담는 방식.

아스키 (ASCII)
:   영어 알파벳과 숫자, 기호 128개에 번호를 붙인 번호표.

CP949 (Code Page 949)
:   한국에서 널리 쓴 한글 번호표로, 한글 한 글자를 2바이트로 적는다.

유니코드 (Unicode)
:   세계의 모든 글자에 번호를 하나씩 붙인 번호표.

코드 포인트 (code point)
:   유니코드가 글자 하나에 붙인 번호로, U+AC00처럼 적는다.

인코딩 (encoding)
:   글자의 번호를 바이트로 적는 규칙.

UTF-8 (8-bit Unicode Transformation Format)
:   유니코드 번호를 1~4바이트로 적는, 가장 널리 쓰는 인코딩.

BOM (Byte Order Mark)
:   파일 맨 앞에 붙여 어떤 규칙으로 적었는지 알리는 표시.

유니코드 정규화 (Unicode normalization)
:   똑같아 보이지만 번호가 다른 글자를 한 가지 모양으로 맞추는 일.

픽셀 (pixel)
:   화면과 그림을 이루는 작은 점 하나.

RGB (Red, Green, Blue)
:   빨강, 초록, 파랑 세 빛의 밝기로 색을 적는 방식.

압축 (compression)
:   데이터를 눌러서 더 적은 바이트로 줄여 담는 일.

형식 (format)
:   바이트를 무엇으로 읽을지 정해 둔 약속.

파일 (file)
:   바이트를 한 줄로 늘어놓고 이름을 붙인 것.

확장자 (file extension)
:   파일 이름 끝에 붙어 형식을 알려 주는 이름표.

텍스트 파일 (text file)
:   처음부터 끝까지 글자로 읽으면 되는 파일.

바이너리 파일 (binary file)
:   글자로 읽을 수 없어서 형식을 아는 프로그램으로 열어야 하는 파일.

주소 (address)
:   메모리의 1바이트짜리 칸마다 붙은 번호.

포인터 (pointer)
:   주소를 적어 둔 쪽지.

32비트 프로그램 (32-bit program)
:   주소를 32비트 칸에 적는 프로그램.
:::
