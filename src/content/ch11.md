::: {.lead}
채팅 앱은 사진을 올리는 중에도 글자가 계속 쳐집니다. 그런데 내가 만든 앱은 버튼 하나만 눌러도 화면이 통째로 굳어 버립니다. 더 이상한 일도 있습니다. 하나 남은 상품이 두 사람에게 팔리고, 백 번에 한 번꼴로 숫자가 틀립니다. 모두 **여러 일을 한꺼번에 진행할 때** 생기는 일입니다.
:::

::: {.goals}
- 동시성과 병렬성, 동기와 비동기, 블로킹과 논블로킹을 구분해 설명할 수 있습니다.
- `async`/`await`가 줄여 주는 시간과 줄여 주지 못하는 시간을 가려낼 수 있습니다.
- 경쟁 상태가 생기는 순서를 타임라인으로 그리고, 락으로 막는 방법을 말할 수 있습니다.
- 일이 밀려들 때, 취소될 때, 실패할 때 무엇을 미리 정해 둬야 하는지 압니다.
:::

## 번갈아 하기와 함께 하기: 동시성과 병렬성 {#concurrent}

[1장](ch01.html)의 주방으로 돌아가 봅시다. 주문이 두 개 들어왔습니다. 파스타와 스테이크입니다.

요리사가 한 명이면 파스타를 조금 만들다가 스테이크로 넘어가고, 다시 파스타로 돌아옵니다. 한 순간에 만지는 요리는 하나뿐이지만 두 요리가 **같은 시간대에 함께 진행**됩니다. 이것이 **동시성**(concurrency)입니다. 요리사가 두 명이면 **같은 순간에** 한 명은 파스타를, 다른 한 명은 스테이크를 만듭니다. 이것이 **병렬성**(parallelism)입니다.

::: {.fig src="concurrent-parallel.svg"}
동시성은 일을 번갈아 진행하는 방식이고, 병렬성은 실제로 같은 순간에 하는 것입니다. 번갈아 한다고 해서 끝나는 시간이 저절로 줄지는 않습니다.
:::

1장에서는 코어를 요리사라고 했습니다. 프로그램 쪽에서 요리사에 해당하는 것은 **스레드**(thread)입니다. 스레드는 프로그램 안에서 명령을 차례로 따라가는 실행 흐름 하나이고, 운영체제가 스레드를 코어에 올려 실행합니다([3장](ch03.html)). 이 장에서는 "요리사 한 명 = 스레드 하나"로 부르겠습니다.

### 기다리는 일과 손이 바쁜 일

위 그림에서 혼자 번갈아 한 쪽은 조금도 빨라지지 않았습니다. 칼질처럼 **손이 계속 바쁜 일**이었기 때문입니다. 하지만 요리에는 **기다림**도 많습니다. 면이 삶아지는 8분 동안 냄비만 바라볼 이유는 없습니다. 그 사이에 스테이크를 구우면 혼자서도 훨씬 일찍 끝납니다.

프로그램의 일도 이 두 가지로 나뉩니다. 디스크나 네트워크 같은 바깥과 데이터를 주고받는 일을 **I/O**(입출력, Input/Output)라고 하는데, I/O는 대부분 기다림입니다. 1장에서 본 것처럼 CPU에게 서버 응답은 몇 년짜리 기다림입니다.

| 일의 종류 | 예 | 빨라지는 방법 |
|---|---|---|
| 기다리는 일 (I/O) | 서버 응답, 파일 읽기, 데이터베이스 조회 | 기다리는 동안 다른 일을 진행한다 (동시성) |
| 손이 바쁜 일 (계산) | 이미지 변환, 큰 목록 정렬, 압축 | 여러 코어에 나눠 준다 (병렬성) |

::: {.key}
느린 프로그램을 만나면 먼저 물어보세요. **지금 기다리는 중인가, 계산하는 중인가?** 처방이 완전히 다릅니다.
:::

## 앞에서 기다릴까, 진동벨을 받을까: 동기와 비동기 {#async}

푸드코트에서 음식을 주문하는 방법은 두 가지입니다.

- 카운터 앞에 서서 음식이 나올 때까지 기다렸다가 받아 갑니다. 일을 시킨 그 자리에서 결과를 받는 이 방식이 **동기**(synchronous)입니다.
- 진동벨을 받아 자리로 돌아갑니다. 결과는 나중에 벨이 울리면 받습니다. 이 방식이 **비동기**(asynchronous)입니다.

::: {.fig src="buzzer.svg"}
조리 시간은 두 경우 모두 3분입니다. 달라지는 것은 그 3분 동안 손님이 무엇을 할 수 있느냐입니다.
:::

카운터 앞에 서 있는 동안 손님은 아무것도 못 합니다. 이렇게 기다리느라 다음 일을 못 하는 상태를 **블로킹**(blocking)이라고 합니다. 반대로 맡기자마자 바로 돌아와 다른 일을 할 수 있으면 **논블로킹**(non-blocking)입니다.

코드로 옮기면 손님은 함수를 **호출한 스레드**이고, 주방은 파일이나 네트워크처럼 느린 일을 맡은 쪽입니다. 화면을 그리는 스레드가 파일 읽기를 블로킹으로 2초 기다리면, 그 2초 동안 버튼도 스크롤도 반응하지 않습니다. 앱이 "굳었다"고 느끼는 순간이 대개 이것입니다.

::: {.note}
두 쌍은 묻는 것이 조금 다릅니다. 동기와 비동기는 "결과를 **어떻게** 받는가", 블로킹과 논블로킹은 "기다리는 동안 **묶여 있는가**"입니다. 보통은 그림처럼 짝지어 나타나지만 어긋나기도 합니다. 진동벨 없이 10초마다 카운터에 가서 "다 됐나요?" 하고 묻는 손님은 묶여 있지 않지만 오가느라 바쁩니다. 이런 반복 확인을 **폴링**(polling)이라고 합니다.
:::

JavaScript에서 진동벨 역할을 하는 것이 **프로미스**(Promise)입니다. "결과는 아직 없지만 준비되면 알려 주겠다"는 약속을 담은 물건입니다. 비동기 함수를 부르면 결과 대신 이 진동벨이 먼저 돌아옵니다.

## 혼자서 여러 주문 받기: 이벤트 루프와 async/await {#eventloop}

브라우저와 Node.js에서 JavaScript 코드를 실행하는 요리사는 기본적으로 **한 명**입니다. 그런데도 수많은 클릭과 요청을 동시에 다룹니다. 비결은 일하는 순서에 있습니다.

요리사 앞에 주문서 꽂이가 있습니다. 요리사는 쪽지를 하나 뽑아 **끝까지** 처리합니다. 도중에 오븐에 넣고 기다려야 하는 일이 나오면 오븐에 맡기고 손을 뗍니다. 오븐이 다 되어 벨이 울리면 "이어서 할 일" 쪽지가 꽂이에 새로 꽂힙니다. 요리사는 하던 쪽지를 끝내는 대로 다음 쪽지를 뽑습니다. 이 반복이 **이벤트 루프**(event loop)입니다.

::: {.fig src="event-loop.svg"}
이벤트 루프. 기다림은 브라우저나 운영체제에 맡기고, 요리사는 꽂이의 쪽지를 하나씩 처리합니다.
:::

### await: 벨이 울릴 때까지 이 함수만 멈추기

JavaScript에서는 진동벨을 기다리는 일을 `async`와 `await`로 씁니다.

```javascript
async function showPage() {
  const user = await loadUser();
  const notice = await loadNotice();
  render(user, notice);
}
```

- `async`는 "이 함수는 진동벨을 돌려준다"는 표시입니다. 안에서 `await`를 쓸 수 있습니다.
- `await`는 "벨이 울릴 때까지 **이 함수의 다음 줄**을 미뤄 둔다"는 뜻입니다. 요리사는 멈추지 않고 꽂이의 다른 쪽지를 처리하러 갑니다.

요청 하나가 2초씩 걸린다면 이 코드는 4초가 걸립니다. 사용자 정보를 다 받은 뒤에야 공지를 주문하기 때문입니다. 두 요청이 서로 상관없다면 **둘 다 먼저 주문해 놓고** 벨 두 개를 함께 기다리면 됩니다.

```javascript
const [user, notice] = await Promise.all([loadUser(), loadNotice()]);
```

::: {.fig src="await-overlap.svg"}
중요한 것은 `await`의 개수가 아니라 일을 **언제 시작했느냐**입니다. 함께 시작하면 기다림이 겹칩니다.
:::

다만 공지를 불러오는 데 사용자 정보가 필요하다면 겹칠 수 없습니다. 앞의 결과가 있어야 뒤의 일을 시작할 수 있기 때문입니다.

::: {.myth title="async를 붙이면 빨라진다"}
`await`는 **기다림**을 겹쳐 줄 뿐, **계산**을 다른 코어로 옮겨 주지 않습니다. `async` 함수 안에서 큰 목록을 0.5초 동안 정렬하면 요리사는 그 0.5초 내내 그 쪽지에 붙잡혀 있습니다. 그 사이에 도착한 클릭과 응답은 꽂이에서 기다리고, 화면은 굳습니다. 긴 계산은 다른 요리사에게 넘겨야 합니다. 브라우저의 웹 워커(Web Worker), Node.js의 워커 스레드(worker thread)가 그 역할을 합니다.
:::

::: {.try}
브라우저 개발자 도구(F12)의 콘솔에 아래 코드를 붙여 넣어 보세요.

```javascript
setTimeout(() => console.log("벨!"), 1000);
const end = Date.now() + 3000;
while (Date.now() < end) {}
```

첫 줄은 1초 뒤에 "벨!"을 찍어 달라고 맡기고, 나머지 두 줄은 3초 동안 계산만 합니다. "벨!"은 1초 뒤가 아니라 3초 뒤에 찍힙니다. 벨은 제때 울렸지만 요리사가 바쁜 쪽지를 놓지 못했기 때문입니다.
:::

## 같은 칠판을 둘이 고치면: 경쟁 상태 {#race}

이제 요리사가 여러 명인 주방입니다. 손이 늘면 일은 빨라지지만 새로운 문제가 생깁니다. **함께 쓰는 것**이 있기 때문입니다.

주방 벽 칠판에 가게 잔액이 적혀 있습니다. 지금은 10,000원입니다. 직원 A는 5,000원을, 직원 B는 3,000원을 입금하려 합니다. 두 사람 모두 같은 순서로 일합니다. 칠판을 **읽고**, 머릿속으로 **더하고**, 지우고 새 숫자를 **씁니다**. 한 사람씩 차례로 하면 18,000원이 됩니다. 그런데 두 사람의 동작이 아래처럼 엇갈리면 어떻게 될까요?

::: {.fig src="race-timeline.svg"}
두 사람 모두 틀린 행동을 하지 않았습니다. 그런데도 B가 옛날 값으로 계산한 결과를 덮어쓰면서 A의 입금이 사라졌습니다.
:::

코드로는 한 줄이지만 컴퓨터는 이 한 줄을 읽기, 더하기, 쓰기의 세 단계로 나눠 실행합니다.

```python
balance = balance + amount
```

이렇게 **누가 먼저 실행되느냐에 따라 결과가 달라지는 상황**을 **경쟁 상태**(race condition)라고 합니다. 경쟁 상태가 까다로운 이유는 대부분의 경우 멀쩡하기 때문입니다. 두 사람의 동작이 우연히 겹칠 때만 틀립니다. 그래서 혼자 테스트할 때는 통과하고, 사용자가 몰리는 날에만 숫자가 어긋납니다.

### 요리사가 한 명이어도 생깁니다

스레드가 하나뿐인 JavaScript는 안전할까요? 아래는 하나 남은 상품을 파는 코드입니다.

```javascript
if (stock > 0) {
  await pay(order);
  stock = stock - 1;
}
```

1행에서 재고를 확인합니다. 1개 남았으니 통과합니다. 2행에서 결제를 기다리는 동안 요리사는 다른 주문의 쪽지를 처리합니다. 재고가 아직 1이라 그 주문도 1행을 통과합니다. 결국 두 주문이 모두 3행을 실행해 재고는 -1이 됩니다. `await` 때문에 **확인과 변경 사이에 틈**이 생긴 것입니다.

::: {.key}
경쟁 상태의 재료는 두 가지입니다. **함께 쓰는 값**, 그리고 **확인과 변경 사이의 틈**. 둘 중 하나를 없애면 사라집니다.
:::

## 분필은 하나만: 락과 임계 구역 {#lock}

문제는 "읽기 → 더하기 → 쓰기" 사이에 다른 사람이 끼어든 것이었습니다. 그렇다면 이 세 단계를 **끼어들 수 없는 한 덩어리**로 만들면 됩니다. 더 쪼갤 수 없는 원자처럼, 중간 모습이 남에게 보이지 않는 이 성질을 **원자성**(atomicity)이라고 합니다. 그리고 한 번에 한 명만 들어가야 하는 코드 구간을 **임계 구역**(critical section)이라고 부릅니다.

주방에서는 간단한 약속으로 해결합니다. 칠판 옆에 **분필을 하나만** 둡니다. 분필을 쥔 사람만 칠판을 읽고 고칠 수 있습니다. 다 쓰면 분필을 제자리에 돌려놓습니다. 이 분필이 **락**(lock)입니다. 그중에서 한 번에 딱 한 명만 쥘 수 있는 락을 **뮤텍스**(mutex)라고 합니다.

::: {.fig src="lock-timeline.svg"}
B는 분필을 기다렸다가 A가 고친 15,000을 읽습니다. 두 사람이 어떤 순서로 도착해도 결과는 18,000입니다.
:::

```python
import threading

balance = 10000
lock = threading.Lock()

def deposit(amount):
    global balance
    with lock:
        balance = balance + amount
```

`threading.Lock()`이 분필 하나를 만듭니다. `with lock:`은 분필을 쥐는 줄입니다. 남이 쥐고 있으면 돌아올 때까지 기다립니다. 그 아래 들여 쓴 줄이 임계 구역이고, 이 부분을 벗어나면 분필은 자동으로 돌아갑니다.

락을 쓸 때는 세 가지를 지킵니다.

1. **모두가 같은 분필을 씁니다.** 한 명이라도 분필 없이 칠판을 고치면 약속이 무너집니다. 읽기만 하는 쪽도 마찬가지입니다.
2. **짧게 쥡니다.** 분필을 쥔 채 서버 응답을 기다리면 다른 사람은 모두 줄을 섭니다.
3. **반드시 돌려놓습니다.** 중간에 오류가 나도 마찬가지입니다. 위의 `with`가 그 일을 대신 해 줍니다.

### 세마포어: 한 명이 아니라 세 명까지

오븐에는 판이 세 개까지 들어갑니다. 네 번째 판은 하나가 나올 때까지 기다려야 합니다. 이렇게 **남은 자리 수를 세어** 동시에 들어갈 수 있는 수를 제한하는 도구가 **세마포어**(semaphore)입니다.

::: {.fig src="oven-slots.svg"}
한 번에 내려받는 파일 수나 데이터베이스에 동시에 여는 연결 수를 제한할 때 세마포어를 씁니다.
:::

::: {.deep title="락 없이 한 번에 바꾸기: 비교 후 교환(CAS)"}
CPU에는 "읽고, 더하고, 쓰기"를 끼어들 틈 없이 한 번에 해 주는 명령이 있습니다. 이런 것을 원자적 연산이라고 합니다. 그중 **비교 후 교환**(CAS, Compare-and-Swap)은 "칠판 값이 아직 내가 본 10,000이면 15,000으로 바꾸고, 아니면 아무것도 하지 마"라는 명령입니다. 앞 절의 타임라인에서 B가 "10,000이면 13,000으로"를 시도하면, 칠판은 이미 15,000이라 실패합니다. B는 다시 읽고(15,000) 다시 계산해(18,000) 한 번 더 시도합니다. **실패하면 다시 확인하는 것까지가 한 세트**입니다. 값 하나에는 잘 맞지만, 여러 값을 함께 맞춰야 한다면 락이 더 안전합니다.
:::

::: {.deep title="읽기·쓰기 락과 조건 변수"}
메뉴판처럼 읽는 사람은 많고 고치는 일은 드문 데이터에는 **읽기·쓰기 락**(read-write lock)을 씁니다. 읽기끼리는 함께 들어가고, 쓰기는 혼자 들어갑니다. 다만 읽는 사람이 끊이지 않으면 쓰려는 사람이 한참 기다릴 수 있습니다.

**조건 변수**(condition variable)는 "꽂이에 주문서가 생길 때까지"처럼 조건이 맞을 때까지 잠들어 기다리게 해 주는 도구입니다. 깨어난 뒤에는 조건을 **다시 확인**해야 합니다. 그사이 다른 요리사가 주문서를 먼저 가져갔을 수 있습니다.
:::

::: {.deep title="하드웨어가 만드는 함정: 메모리 가시성과 거짓 공유"}
컴파일러와 CPU는 속도를 위해 명령의 순서를 바꾸거나 한 번 읽은 값을 다시 쓰기도 합니다. 그래서 한 스레드가 바꾼 값이 다른 스레드에 **곧바로, 코드에 적힌 순서대로** 보인다는 보장이 없습니다. 이것이 **메모리 가시성**(visibility) 문제입니다. 락, 큐, 원자적 연산 같은 정식 도구를 거치면 보장됩니다. 잠깐 쉬는 코드(sleep)로 때우면 안 됩니다.

**거짓 공유**(false sharing)는 서로 다른 변수가 우연히 같은 캐시 묶음(보통 64바이트, [1장](ch01.html))에 놓여 느려지는 현상입니다. 결과는 맞는데 코어를 늘릴수록 효율이 떨어진다면 의심해 봅니다.
:::

## 서로 기다리다 멈추기: 교착 상태 {#deadlock}

락이 두 개 이상이 되면 새로운 함정이 생깁니다. 스테이크를 구우려면 하나뿐인 화구와 하나뿐인 프라이팬이 **둘 다** 필요합니다. 요리사 A는 화구부터 차지했고, 요리사 B는 프라이팬부터 집었습니다.

::: {.fig src="deadlock.svg"}
왼쪽에서는 각자 하나를 쥔 채 상대가 쥔 것을 기다립니다. 오른쪽처럼 잡는 순서를 통일하면 B는 빈손으로 기다리므로 A가 일을 끝낼 수 있습니다.
:::

A는 프라이팬이 나올 때까지 화구를 놓지 않고, B는 화구가 빌 때까지 프라이팬을 놓지 않습니다. 둘 다 영원히 기다립니다. 이것이 **교착 상태**(deadlock)입니다.

증상이 독특합니다. 아무도 일하지 않으니 **CPU 사용률은 낮은데 요청은 끝나지 않습니다.** 오류 메시지도 없습니다. 게다가 두 요청이 딱 그 순서로 겹칠 때만 생기므로 평소에는 멀쩡합니다.

피하는 방법은 다음과 같습니다.

- **잡는 순서를 통일합니다.** 모두가 "화구 먼저, 그다음 프라이팬"을 지키면 서로 물고 물릴 수 없습니다.
- **쥔 채로 오래 기다리지 않습니다.** 락을 쥐고 네트워크 응답을 기다리는 코드는 교착의 단골 재료입니다.
- **기다림에 시간 제한을 둡니다.** 정해진 시간 안에 못 잡으면 쥔 것을 내려놓고 처음부터 다시 시도합니다.

::: {.deep title="멈춘 것은 아닌데 진행이 안 될 때: 기아, 우선순위 역전, 라이브락"}
**기아**(starvation)는 전체는 잘 돌아가는데 특정 작업만 계속 차례를 받지 못하는 상태입니다. 새로 온 사람이 계속 앞에 끼어드는 줄과 같습니다.

**우선순위 역전**(priority inversion)은 가장 급한 일이 가장 늦어지는 현상입니다. 급한 일이 느긋한 일이 쥔 락을 기다리는데, 중간쯤 급한 일이 느긋한 일을 밀어내고 계속 실행됩니다. 락이 풀리지 않으니 급한 일은 계속 기다립니다.

**라이브락**(livelock)은 좁은 복도에서 마주친 두 사람이 계속 같은 쪽으로 비켜서는 상황입니다. 둘 다 바쁘게 움직이지만 진전이 없습니다. 교착 상태와 달리 CPU는 바쁩니다. 다시 시도하는 간격을 서로 다르게 주면 풀립니다.
:::

## 주문서 꽂이와 요리사 팀: 작업 큐와 역압력 {#queue}

주문이 들어올 때마다 요리사를 새로 뽑고, 요리가 끝나면 내보내는 식당은 없습니다. 스레드도 만들 때마다 시간과 메모리가 듭니다. 그래서 요리사를 정해진 수만큼 미리 두고 돌려 씁니다. 이 팀이 **스레드 풀**(thread pool)입니다. 동시에 진행되는 일의 수가 요리사 수를 넘지 않는다는 장점도 있습니다.

할 일은 주문서 꽂이에 꽂아 둡니다. [8장](ch08.html)에서 본 큐, 곧 먼저 넣은 것이 먼저 나오는 줄입니다. 이렇게 나중에 할 일을 모아 두는 큐를 **작업 큐**(task queue)라고 합니다. 주문서를 꽂는 홀 직원이 **생산자**(producer), 뽑아서 요리하는 쪽이 **소비자**(consumer)입니다.

한 가지는 꼭 기억하세요. **주문서가 꽂혔다고 음식이 나온 것은 아닙니다.** 영상 변환 요청에 "접수되었습니다"라고 답했다면, 그 뒤의 처리 중, 완료, 실패 상태를 따로 기록하고 알려 줘야 합니다.

### 밀려드는 주문: 역압력

점심시간에 주문이 초당 100건 들어오는데 주방은 초당 80건을 처리합니다. 꽂이에는 초당 20건씩 쌓입니다. 200칸짜리 꽂이는 10초 만에 가득 찹니다.

꽂이를 2,000칸으로 늘리면 어떨까요? 100초를 버틸 뿐입니다. 그동안 꽂이에는 한참 전에 들어온 주문만 가득하고, 손님은 이미 떠났으며, 주문서는 메모리를 차지합니다. **큰 큐는 잠깐의 폭주를 받아 줄 뿐, 처리 속도를 올려 주지 않습니다.**

::: {.fig src="queue-backpressure.svg"}
들어오는 속도가 처리 속도보다 빠르면 큐는 반드시 찹니다. 그러니 큐에는 상한을 두고, 가득 찼을 때의 규칙을 미리 정합니다.
:::

가득 찼을 때 고를 수 있는 길은 셋입니다. 그중 받는 쪽의 속도에 맞춰 보내는 쪽을 늦추는 첫 번째 방법을 **역압력**(backpressure)이라고 합니다. 무엇을 고를지는 데이터의 뜻에 달려 있습니다. 결제 요청은 몰래 버리면 안 되므로 기다리게 하거나 분명히 거절합니다. 마우스 위치처럼 최신 값만 의미가 있는 데이터는 오래된 것을 버려도 됩니다.

::: {.deep title="아예 함께 쓰지 않기: 액터와 메시지 전달"}
칠판을 여럿이 고치는 대신 **칠판 담당을 한 명** 두는 방법도 있습니다. 나머지 사람은 "5,000원 더해 주세요"라는 쪽지를 담당자의 수신함에 넣기만 합니다. 담당자가 쪽지를 하나씩 처리하므로 칠판에는 락이 필요 없습니다. 이런 담당자를 **액터**(actor), 이런 방식을 **메시지 전달**(message passing)이라고 합니다. 게임 방의 참가자 목록을 그 방 담당 하나만 고치게 하는 식입니다.

대신 쪽지가 늦거나, 순서가 바뀌거나, 두 번 도착하는 경우를 다뤄야 합니다. 수신함도 큐이므로 상한이 필요합니다.
:::

## 끝까지 책임지기: 취소, 시간 제한, 실패 {#finish}

일을 시작시키기는 쉽습니다. 어려운 것은 **끝을 책임지는 일**입니다. 맡긴 일마다 세 가지를 정해 둡니다. 필요 없어지면? 너무 오래 걸리면? 실패하면?

### 취소는 부탁입니다

홀에서 "취소요!" 하고 외쳐도, 요리사가 그 말을 듣고 불을 꺼야 요리가 멈춥니다. **취소**(cancellation)는 강제 종료가 아니라 "그만해 달라"는 요청입니다. 작업 쪽에서 틈틈이 확인하고 스스로 멈춰야 합니다.

또 취소는 **되돌리기가 아닙니다.** 검색어를 바꾸면서 이전 요청을 취소해도 서버는 그 검색을 끝까지 할 수 있습니다. 저장 요청을 취소했더라도 이미 저장됐을 수 있습니다.

### 시간 제한과 전체 마감

**시간 제한**(timeout)은 "이 일 하나를 얼마나 기다릴지"이고, **마감**(deadline)은 "전체가 언제까지 끝나야 하는지"입니다. 단계마다 넉넉한 시간 제한을 따로 주면 전체는 생각보다 훨씬 길어집니다.

::: {.fig src="timeout-budget.svg"}
전체 예산이 3초인데 1단계가 2.5초를 썼다면 2단계가 쓸 수 있는 시간은 0.5초입니다. 남은 시간을 다음 단계에 넘겨줘야 마감을 지킵니다.
:::

```javascript
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 3000);
try {
  const res = await fetch(url, { signal: controller.signal });
  return await res.json();
} finally {
  clearTimeout(timer);
}
```

- 1~2행: 취소 버튼(`controller`)을 만들고, 3초 뒤에 눌리도록 예약합니다.
- 4행: 요청을 보낼 때 "이 버튼이 눌리면 그만둬"라는 신호를 함께 넘깁니다.
- 6~7행: `finally`는 성공해도, 실패해도, 취소돼도 실행됩니다. 타이머, 파일, 락처럼 빌린 것은 여기서 돌려줍니다.

::: {.warn}
시간 초과는 "실패했다"가 아니라 "**결과를 모른다**"입니다. 상대는 일을 끝냈는데 답만 늦었을 수 있습니다. 결제 같은 요청을 무작정 다시 보내면 두 번 처리될 수 있습니다. 다시 보내도 안전하게 만드는 방법은 [15장](ch15.html)에서 다룹니다.
:::

### 실패를 놓치지 않기

```javascript
saveLog(data);
await saveLog(data);
```

비동기 작업의 실패는 **진동벨을 통해** 전해집니다. 첫 줄처럼 `await` 없이 부르기만 하면 벨을 받자마자 버린 셈이라, 실패해도 아무도 모릅니다. 둘째 줄처럼 벨을 쥐고 기다려야 실패가 그 자리에서 오류로 드러납니다. `Promise.all`은 하나가 실패하면 곧바로 실패를 알리지만, **나머지 작업을 멈춰 주지는 않습니다.** 모두 끝난 뒤 성공과 실패를 하나씩 확인하고 싶으면 `Promise.allSettled`를 씁니다.

::: {.key}
시작한 작업에는 반드시 **주인**이 있어야 합니다. 주인은 그 작업의 완료, 실패, 취소를 끝까지 받아서 정리하는 코드입니다.
:::

::: {.deep title="구조화된 동시성: 시작한 곳에서 끝낸다"}
"주인"을 규칙으로 못 박은 것이 **구조화된 동시성**(structured concurrency)입니다. 어떤 블록 안에서 시작한 작업들은 그 블록을 벗어나기 전에 모두 끝나야 합니다. 하나가 실패하면 나머지 형제 작업에 취소를 요청하고, 정리가 끝날 때까지 기다린 뒤에야 실패를 위로 알립니다. 그래서 주인 없이 떠도는 작업이 남지 않습니다.

Python 3.11부터 있는 `asyncio.TaskGroup`이 이 방식입니다. 반면 `asyncio.gather`는 기본 설정에서 하나가 실패해도 나머지를 취소하지 않습니다. 비슷해 보이는 도구라도 "하나가 실패하면 나머지는 어떻게 되는가"를 꼭 확인하세요.
:::

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 동시성 / 병렬성 | 번갈아 진행해 기간이 겹침 / 같은 순간에 여러 코어가 계산함 |
| 동기 / 비동기 | 시킨 자리에서 결과를 받음 / 나중에 알림으로 받음 |
| 블로킹 / 논블로킹 | 기다리는 동안 묶여 있음 / 바로 돌아와 다른 일을 함 |
| 동기 / 동기화 | 결과를 받는 방식 / 락처럼 여러 스레드의 차례를 맞추는 일. 이름만 비슷함 |
| 접수 / 완료 | 큐에 넣었음 / 결과까지 만들어졌음 |

## 실전 사례 {#case}

::: {.case title="사용자가 몰리면 서버가 메모리 부족으로 꺼진다"}
이미지 업로드를 받을 때마다 변환 작업을 바로 시작하는 서버가 사용자가 몰리면 꺼집니다.

1. **세어 봅니다.** 변환 하나가 메모리를 300MB 씁니다. 동시에 도는 변환 수에는 제한이 없었습니다. 40개가 겹치면 12GB입니다.
2. **동시 실행 수에 상한을 둡니다.** 세마포어나 스레드 풀로 한 번에 4개까지만 변환합니다.
3. **큐에도 상한을 둡니다.** 대기가 50건을 넘으면 "잠시 후 다시 시도해 주세요"라고 답합니다.
4. **접수와 완료를 나눕니다.** 업로드에는 작업 번호만 바로 돌려주고, 상태는 따로 조회하게 합니다.
5. **확인합니다.** 처리 속도보다 빠르게 요청을 보내, 메모리 최고 사용량이 상한 아래에 머무는지 봅니다.

큐는 일을 잠시 숨겨 줄 뿐 없애 주지 않습니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- **동시성**은 한 명이 번갈아, **병렬성**은 여러 명이 같은 순간에 하는 것입니다. 기다리는 일은 동시성으로, 계산하는 일은 병렬성으로 빨라집니다.
- **비동기**는 진동벨입니다. `await`는 벨이 울릴 때까지 그 함수만 멈춥니다. 긴 계산은 여전히 요리사를 붙잡습니다.
- **경쟁 상태**는 함께 쓰는 값을 읽고 고치는 사이에 남이 끼어들 때 생깁니다. 스레드가 하나여도 `await` 사이에서 생깁니다.
- **락**은 하나뿐인 분필입니다. 모두가 같은 분필을, 짧게 쥐고, 반드시 돌려놓습니다. **세마포어**는 자리가 N개인 오븐입니다.
- **교착 상태**는 서로 상대의 것을 기다리는 것입니다. 잡는 순서를 통일하면 막을 수 있습니다.
- 큐에는 **상한**을, 기다림에는 **시간 제한**을, 시작한 작업에는 **주인**을 둡니다.
:::

## 확인 문제 {#quiz}

::: {.q}
서로 상관없는 요청 세 개가 각각 1초씩 걸립니다. `await` 세 줄로 차례로 기다리면 모두 몇 초일까요? 함께 시작하고 `Promise.all`로 기다리면요? 세 번째 요청에 첫 번째의 결과가 필요하다면요?

::: {.a}
차례로 기다리면 약 3초, 함께 시작하면 약 1초입니다. 세 번째에 첫 번째의 결과가 필요하면 첫 번째와 두 번째만 함께 시작하고(1초) 그 뒤에 세 번째를 시작하므로(1초) 약 2초입니다. 겹칠 수 있는 것은 서로 기대지 않는 일뿐입니다.
:::
:::

::: {.q}
`async` 함수이고 안에 `await`도 있는데, 버튼을 누르면 화면이 2초 동안 굳습니다. 있을 수 있는 일일까요? 무엇부터 확인해야 할까요?

::: {.a}
있을 수 있습니다. `await`는 기다리는 동안에만 요리사를 놓아줍니다. 함수 안의 긴 계산은 화면을 그리는 스레드를 그대로 붙잡습니다. 기다린 시간과 계산한 시간을 따로 재 보고, 계산이 길면 워커로 옮깁니다.
:::
:::

::: {.q}
"좋아요" 버튼을 100명이 거의 동시에 눌렀는데 숫자는 97만 올랐습니다. 서버 코드는 "현재 값을 읽고, 1을 더해, 저장한다"입니다. 원인은 무엇이고 어느 방향으로 고쳐야 할까요?

::: {.a}
경쟁 상태입니다. 읽기와 저장 사이에 다른 요청이 끼어들어, 여러 요청이 같은 옛날 값에 1을 더해 덮어썼습니다. 읽기부터 저장까지를 끼어들 수 없는 한 덩어리로 만들어야 합니다. 락으로 감싸거나, 저장소가 제공하는 "1 증가" 같은 원자적 연산을 씁니다.
:::
:::

::: {.q}
작업이 초당 100건 들어오는데 처리는 초당 80건입니다. 큐 크기를 10배로 늘리면 문제가 해결될까요?

::: {.a}
해결되지 않습니다. 초당 20건씩 계속 쌓이므로 가득 차는 시점이 10배 늦어질 뿐이고, 그동안 대기 시간과 메모리 사용량은 오히려 커집니다. 처리 능력을 늘리거나, 큐에 상한을 두고 넘칠 때의 규칙을 정해야 합니다.
:::
:::

::: {.q}
서버가 응답하지 않습니다. 그런데 CPU 사용률은 2%이고 오류 로그도 없습니다. 무엇을 의심하고 어떻게 확인할까요?

::: {.a}
교착 상태를 의심합니다. 계산이 밀렸다면 CPU가 바빠야 하는데, 지금은 모두 기다리며 서 있습니다. 멈춘 스레드마다 "무엇을 쥐고 무엇을 기다리는지" 적어 보면 서로 물고 물리는 원이 보입니다. 응답 없는 외부 서버를 시간 제한 없이 기다릴 때도 같은 증상이 나타나니 함께 확인합니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI 코딩 도구는 잘 돌아갈 때의 코드는 금방 만들지만, 요청이 몰릴 때와 실패할 때의 규칙은 빠뜨리기 쉽습니다. 이 장의 점검 항목을 그대로 요청문에 적어 검토를 맡겨 보세요.

> 이 서버 코드가 동시에 여러 요청을 받을 때 문제가 될 곳을 찾아 줘. (1) 여러 요청이 함께 읽고 고치는 값, (2) 확인과 변경 사이에 await가 끼어 있는 곳, (3) await 없이 호출만 한 비동기 함수, (4) 상한 없이 쌓이는 큐와 한꺼번에 시작하는 작업, (5) 시간 제한이 없는 외부 호출을 표로 정리해 줘. 고치기 전에 요청 200건을 동시에 보내는 테스트부터 만들고, 고친 뒤 같은 테스트의 결과를 나란히 보여 줘.

**받은 답에서 확인할 것**: 문제마다 "어떤 순서로 실행되면 틀리는지"를 설명했는가. 락을 넣었다면 그 값을 다루는 모든 코드가 같은 락을 쓰는가. 정리 코드가 `finally`에 있는가. 테스트가 요청을 **동시에** 보내는가(하나씩 차례로 보내는 테스트는 경쟁 상태를 잡지 못합니다).
:::

## 용어 정리 {#terms}

::: {.terms}
동시성 (concurrency)
:   여러 일을 번갈아 진행해 진행 기간이 겹치게 하는 것. 코어가 하나여도 가능하다.

병렬성 (parallelism)
:   같은 순간에 여러 코어가 실제로 함께 계산하는 것.

스레드 (thread)
:   프로그램 안에서 명령을 차례로 따라가는 실행 흐름 하나. 이 장의 요리사.

비동기 (asynchronous)
:   일을 맡겨 두고 결과는 나중에 알림으로 받는 방식. 반대는 동기.

블로킹 (blocking)
:   결과를 기다리느라 호출한 스레드가 다음 일을 못 하는 상태.

프로미스 (Promise)
:   아직 없는 결과를 나중에 전해 주겠다는 약속을 담은 객체. 이 장의 진동벨.

이벤트 루프 (event loop)
:   대기 중인 할 일을 하나씩 꺼내 끝까지 처리하기를 반복하는 구조.

경쟁 상태 (race condition)
:   여러 작업의 실행 순서에 따라 결과가 달라지는 상황.

원자성 (atomicity)
:   여러 단계가 끼어들 틈 없이 한 덩어리로 일어나는 성질.

임계 구역 (critical section)
:   한 번에 한 작업만 들어가야 하는 코드 구간.

락 (lock)
:   임계 구역에 들어갈 차례를 정하는 장치. 한 번에 하나만 허용하는 락이 뮤텍스(mutex).

세마포어 (semaphore)
:   남은 자리 수를 세어 동시에 실행되는 작업 수를 N개로 제한하는 도구.

교착 상태 (deadlock)
:   작업들이 서로 상대가 쥔 것을 기다리느라 아무도 진행하지 못하는 상태.

역압력 (backpressure)
:   받는 쪽의 처리 속도에 맞춰 보내는 쪽을 늦추는 조절.
:::
