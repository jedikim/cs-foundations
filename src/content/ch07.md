::: {.lead}
게임을 하다가 어려운 보스를 만나기 전에는 저장을 해 둡니다. 지면 저장한 곳으로 돌아가면 됩니다. 코드를 쓸 때도 똑같은 것이 필요합니다. 잘 되던 코드를 고치다가 망가뜨리면 잘 되던 때로 돌아가고 싶어집니다. 코드의 '저장 지점'을 만들고 관리해 주는 도구가 **Git**입니다.
:::

::: {.goals}
- Git이 왜 필요한지 설명할 수 있습니다.
- 저장 지점(커밋)을 만들고, 무엇이 바뀌었는지 볼 수 있습니다.
- 실수했을 때 예전 상태로 돌아가는 방법을 고를 수 있습니다.
- 여러 사람이 같은 코드를 함께 고치는 방법을 설명할 수 있습니다.
:::

## 저장 지점 만들기: 복사본을 쌓는 대신 {#why}

미나는 방학 동안 캐릭터가 뛰어다니는 작은 게임을 만들고 있습니다. 게임의 파일은 모두 `mygame`이라는 폴더에 들어 있습니다.

미나는 코드를 고칠 때마다 불안해서 폴더를 통째로 복사해 둡니다. 며칠 뒤에는 이런 압축 파일이 쌓입니다. `mygame_최종.zip`, `mygame_진짜최종.zip`, `mygame_진짜최종_수정.zip`, `mygame_이게진짜.zip`.

마음은 놓이지만 곤란한 점이 있습니다. 두 복사본 사이에 **무엇이 바뀌었는지** 알 수 없습니다. **왜 바꿨는지**도 적혀 있지 않습니다. 친구 준호와 각자 고친 복사본을 하나로 합칠 방법도 없습니다.

Git은 복사본 대신 저장 지점을 하나씩 쌓습니다. 이 저장 지점 하나를 **커밋**(commit)이라고 부릅니다. 커밋 하나에는 세 가지가 담깁니다.

- **그 순간 폴더 전체의 모습.** 사진을 한 장 찍어 두는 것과 같습니다.
- **누가, 언제, 왜 바꿨는지.** '왜'는 사람이 직접 한 줄로 적습니다. 이 한 줄이 **커밋 메시지**입니다.
- **바로 앞 커밋이 무엇인지.** 그래서 커밋들은 차례대로 이어집니다. 이렇게 이어진 기록이 이력입니다.

::: {.fig src="save-points.svg"}
복사본 쌓기와 커밋의 차이. 커밋마다 번호와 메시지, 만든 사람과 날짜가 남습니다.
:::

그림의 오른쪽을 봅시다. 월요일에 미나가 "플레이어 이동 추가"라는 커밋을 만들었습니다. 화요일에는 "점프 기능 추가"를 쌓았습니다. 수요일에는 준호가, 착지(땅에 내려앉기) 직후 점프가 안 되던 잘못을 고쳤습니다. 프로그램의 이런 잘못을 **버그**(bug)라고 합니다.

`a1b2c3d` 같은 글자는 커밋마다 붙는 번호입니다. **커밋 ID**라고 합니다. 원래는 40글자인데 보통 앞의 일곱 글자만 씁니다.

이렇게 바뀌어 온 기록을 남기는 일을 **버전 관리**(version control)라고 합니다. Git은 이 일에 가장 널리 쓰입니다.

커밋이 쌓이는 곳은 **저장소**(repository)입니다. [5장](ch05.html)에서 본 터미널에서 만듭니다. `mygame` 폴더로 가서 `git init`이라고 치면 `.git`이라는 숨은 폴더가 생깁니다. 커밋은 모두 그 안에 들어갑니다.

::: {.note}
게임은 저장 칸을 덮어쓰지만 **Git은 덮어쓰지 않고 계속 쌓습니다.** 그래서 열 번 전의 커밋으로도 돌아갈 수 있습니다.
:::

## 세 구역: 고치는 곳, 담는 곳, 쌓이는 곳 {#stage}

게임은 저장 버튼 한 번으로 전부 저장합니다. Git은 한 단계를 더 둡니다. **이번 커밋에 무엇을 담을지 먼저 고르게** 합니다. 점프를 고치다가 배경색도 건드렸다면 커밋을 둘로 나누고 싶을 테니까요.

택배를 보낼 때를 떠올려 봅시다. 책상 위의 물건 중 보낼 것만 상자에 담고, 상자를 닫아 창고로 보냅니다. Git에도 이런 곳이 셋 있습니다.

- **작업 폴더**(working tree)는 책상입니다. 지금 눈에 보이고 고치는 파일들입니다.
- **스테이지**(staging area)는 상자입니다. 다음 커밋에 담을 내용을 올려 둡니다.
- **저장소**는 창고입니다. 지금까지 만든 커밋이 쌓여 있습니다.

아래는 터미널에 치는 명령입니다.

```bash
git status
git add config.py
git commit -m "달리기 속도를 10에서 11로 올림"
```

- **첫째 줄**은 지금 상태를 묻습니다. 어느 파일이 바뀌었고 무엇이 상자에 담겼는지 알려 줍니다.
- **둘째 줄**은 `config.py`의 **지금 내용**을 상자에 담습니다. `config.py`는 게임의 설정값을 모아 둔 파일입니다.
- **셋째 줄**은 상자를 닫아 새 커밋을 만듭니다. `-m` 뒤의 따옴표 안이 커밋 메시지입니다.

"지금 내용"이라는 말이 중요합니다. `config.py`에는 `SPEED = 10`이라는 줄이 있습니다. 달리는 빠르기가 10이라는 뜻입니다. 미나가 10을 11로 고치고 `git add`를 했습니다. 그런데 마음이 바뀌어 12로 또 고쳤습니다.

::: {.fig src="three-areas.svg"}
같은 파일이 세 구역에서 서로 다른 값을 가진 순간. 이대로 커밋하면 11이 기록되고, 12는 작업 폴더에만 남습니다.
:::

상자에는 담던 순간의 11이 들어 있습니다. 저장소의 마지막 커밋은 아직 10이고, 책상 위의 파일만 12입니다. 이때 게임을 실행하면 12로 돕니다. 그런데 커밋에는 11이 들어갑니다. **확인한 것과 저장한 것이 달라집니다.** 그래서 다시 고쳤으면 `git add`도 다시 합니다.

::: {.key}
커밋에 들어가는 것은 작업 폴더의 파일이 아니라 **스테이지에 올려 둔 내용**입니다.
:::

커밋 하나에는 **한 가지 일**만 담습니다. 메시지에는 **무엇을 해결했는지** 적습니다. "수정"이라고만 적으면 석 달 뒤의 나는 알아볼 수 없습니다. "착지 직후 점프가 안 되던 문제 수정"이면 충분합니다.

### 담지 않을 것 정하기: .gitignore

모든 파일을 커밋하지는 않습니다. 커밋할 것은 사람이 직접 쓴 **소스**입니다([5장](ch05.html#project)). 소스로 다시 만들 수 있는 것은 담지 않습니다. 비밀번호를 적어 둔 파일도 담으면 안 됩니다.

담지 않을 이름은 `.gitignore`라는 파일에 한 줄씩 적습니다. 그러면 Git이 못 본 척합니다. 예를 들어 `.env`라고 적으면 비밀 값을 적어 둔 `.env` 파일은 커밋에 담기지 않습니다.

::: {.warn title=".gitignore는 지우개가 아닙니다"}
`.gitignore`는 **아직 한 번도 커밋하지 않은 파일**에만 통합니다. 이미 커밋한 파일은 지난 커밋 속에 그대로 남습니다. 비밀번호를 실수로 커밋했다면 **그 비밀번호부터 바꿉니다.**
:::

## diff: 무엇이 바뀌었는지 읽기 {#diff}

틀린 그림 찾기에서는 그림 두 장을 나란히 놓고 다른 곳을 찾습니다. 코드는 눈으로 찾지 않아도 됩니다. Git이 두 상태를 비교해 달라진 줄만 보여 줍니다. 이것을 **diff**라고 합니다. '차이'를 뜻하는 영어 difference를 줄인 말입니다.

미나가 `config.py`에서 점프 높이 `JUMP`를 2에서 3으로 고쳤습니다. 터미널에 `git diff`라고 치면 그림의 왼쪽 같은 글이 나옵니다.

::: {.fig src="diff-read.svg"}
`git diff`가 보여 주는 글 읽기. `config.py`에서 `JUMP` 값을 2에서 3으로 고쳤습니다.
:::

- 맨 위 두 줄은 **어느 파일**인지 알려 줍니다. `a`는 바뀌기 전, `b`는 바뀐 뒤입니다.
- `@@`가 붙은 줄은 **어디쯤**인지 알려 줍니다. 첫째 줄부터 3줄을 보여 준다는 뜻입니다.
- 앞에 표시가 없는 줄은 **그대로인 줄**입니다. `SPEED = 10`과 `GRAVITY = 9.8`(중력의 세기)이 그렇습니다.
- `-`가 붙은 줄은 **사라진 줄**, `+`가 붙은 줄은 **새로 생긴 줄**입니다.

한 줄을 고치면 사라진 줄 하나와 생긴 줄 하나로 나타납니다. `JUMP = 2`가 사라지고 `JUMP = 3`이 생겼습니다.

diff를 볼 때는 **어느 둘을 비교하는지**부터 정합니다. 앞 절 그림의 아래쪽 점선이 그 이야기입니다.

| 명령 | 비교하는 둘 | 알 수 있는 것 |
|---|---|---|
| `git diff` | 작업 폴더와 스테이지 (12와 11) | 아직 담지 않은 변경 |
| `git diff --staged` | 스테이지와 마지막 커밋 (11과 10) | 다음 커밋에 들어갈 변경 |
| `git show a1b2c3d` | 그 커밋과 바로 앞 커밋 | 그 커밋이 바꾼 것 |

::: {.warn}
한 번도 `git add`하지 않은 새 파일은 `git diff`에 나오지 않습니다. 새 파일은 `git status`로 확인합니다.
:::

AI와 일할 때 diff는 영수증과 같습니다. AI가 "점프 높이만 바꿨습니다"라고 말해도 커밋하기 전에 `git diff --staged`로 직접 봅니다. 부탁한 일과 **관계없는 파일**이 끼어 있지 않은지 살핍니다.

::: {.try}
연습용 폴더를 만들어 `git init`을 쳐 보세요. 파일 하나를 만들어 커밋합니다. 그 파일을 한 줄 고치고 `git diff`를 치면 빨간 줄과 초록 줄이 보입니다.
:::

## 브랜치: 커밋에 붙이는 이름표 {#branch}

미나는 공중에서 한 번 더 뛰는 2단 점프를 넣어 보고 싶습니다. 잘될지 모르는 실험입니다. 그래서 멀쩡한 게임은 그대로 두고 **평행 세계**에서 해 보려 합니다. 폴더를 통째로 복사해야 할까요? Git에서는 이름표 한 장이면 됩니다.

커밋은 저마다 바로 앞 커밋을 기억한다고 했습니다. 커밋을 동그라미로 그리고 앞뒤를 선으로 이으면 한 줄이 됩니다. 이 줄에서 **커밋 하나를 가리키는 이름표**가 **브랜치**(branch)입니다. 파일을 복사한 것이 아니라 이름표일 뿐입니다. 저장소를 만들면 보통 `main`이라는 브랜치가 하나 있습니다.

이름표가 여럿이면 내가 지금 어느 것을 쓰는지도 알아야 합니다. 그 표시가 **HEAD**입니다. 지도 앱의 "현재 위치" 핀과 같습니다.

::: {.fig src="branch-label.svg"}
브랜치를 만들고 커밋할 때 움직이는 것. 동그라미는 커밋, 네모는 이름표입니다. 오른쪽일수록 새 커밋입니다.
:::

그림을 번호대로 봅시다.

1. 처음에는 `main` 이름표가 커밋 B에 붙어 있습니다. HEAD도 `main`에 붙어 있습니다.
2. `git switch -c jump`라고 칩니다. `jump`라는 이름표를 B에 하나 더 붙이고 HEAD를 그쪽으로 옮기는 명령입니다.
3. 2단 점프 코드를 쓰고 `git commit`을 합니다. 새 커밋 C가 B 뒤에 생기고, `jump` 이름표만 C로 따라갑니다.

::: {.key}
새 커밋을 만들면 **HEAD가 붙어 있는 이름표만** 새 커밋으로 옮겨 갑니다.
:::

3번에서 `main`은 B에 그대로 있습니다. 실험이 실패해도 `main`의 세계는 멀쩡합니다.

이제 `git switch main`이라고 치면 HEAD가 `main`으로 옮겨 갑니다. 이때 **작업 폴더의 파일이 B 때의 모습으로 바뀝니다.** 방금 쓴 2단 점프 코드는 화면에서 사라집니다. 지워진 것은 아닙니다. C 안에 안전하게 들어 있고, `git switch jump`라고 치면 다시 나타납니다.

## 병합과 충돌: 두 세계를 하나로 {#merge}

2단 점프 실험이 성공했습니다. 그 사이 `main`에서는 배경을 바꾸는 커밋 D도 생겼습니다. 이제 갈라진 두 줄기를 하나로 합칠 차례입니다. 이 일을 **병합**(merge)이라고 합니다. 터미널에 이렇게 칩니다.

```bash
git switch main
git merge jump
```

- **첫째 줄**은 받는 쪽인 `main`으로 갑니다.
- **둘째 줄**은 `jump`에서 바뀐 것을 지금 브랜치로 가져옵니다.

::: {.fig src="merge-graph.svg"}
병합 전과 후. 새로 생긴 커밋 M은 앞 커밋이 둘입니다. 이름표는 `main`만 M으로 옮겨 갑니다.
:::

Git은 먼저 두 줄기가 갈라지기 직전의 커밋을 찾습니다. 그림에서는 B입니다. 이 커밋을 **공통 조상**이라고 합니다.

그다음 B에서 D까지 바뀐 것과 B에서 C까지 바뀐 것을 비교합니다. D는 배경을, C는 점프를 고쳤습니다. 서로 다른 곳이니 둘 다 받아들이고, 두 줄기를 잇는 새 커밋 M을 만듭니다. 이것이 **병합 커밋**입니다. 바로 앞 커밋을 '부모'라고도 하는데, M은 부모가 D와 C 둘입니다.

### 충돌: Git이 고르지 못할 때

양쪽이 **같은 줄을 서로 다르게** 고쳤다면 이야기가 달라집니다. `JUMP = 2`였던 줄을 `main`에서는 4로, `jump`에서는 3으로 고쳤다고 합시다. 4와 3 중 어느 쪽이 맞는지 Git은 알 수 없습니다. 그래서 병합을 멈추고 사람에게 묻습니다. 이 상태가 **충돌**(conflict)입니다.

::: {.fig src="conflict.svg"}
충돌이 생기고 풀리는 과정. `<<<<<<<`, `=======`, `>>>>>>>`로 시작하는 세 줄은 Git이 끼워 넣은 표시입니다.
:::

충돌은 고장이 아니라 질문입니다. Git은 파일 안에 양쪽 내용을 나란히 적어 둡니다. `=======`의 위쪽이 지금 브랜치인 `main`의 내용이고, 아래쪽이 합치려는 `jump`의 내용입니다. 푸는 순서는 이렇습니다.

1. `git status`로 충돌한 파일을 확인합니다.
2. 파일을 열어 위와 아래를 읽고 남길 내용을 정합니다. 그림에서는 3을 골랐습니다. 둘을 섞어 새로 써도 됩니다.
3. 표시 세 줄을 모두 지우고 저장합니다.
4. `git add config.py`로 다 풀었다고 알리고 `git commit`으로 병합을 마칩니다.

엄두가 나지 않으면 `git merge --abort`라고 칩니다. 병합하기 전으로 돌아갑니다.

::: {.warn title="조용히 합쳐졌다고 맞는 것은 아닙니다"}
모둠 보고서로 생각해 봅시다. 한 친구는 1쪽에서 모둠 이름을 '번개'에서 '태풍'으로 바꿨습니다. 다른 친구는 3쪽에 "우리 번개 모둠은"이라고 새로 썼습니다. 고친 줄이 달라 충돌 없이 합쳐지지만 글은 앞뒤가 맞지 않습니다.

Git은 글자를 볼 뿐 뜻은 모릅니다. 코드도 같습니다. **병합한 뒤에는 게임을 다시 실행해 확인합니다.** 이 확인을 컴퓨터에게 맡기는 것이 테스트이고, [12장](ch12.html)에서 배웁니다.
:::

## 리베이스: 내 커밋을 옮겨 심기 {#rebase}

병합을 하면 갈라졌다가 합쳐진 자국이 이력에 남습니다. 이력을 한 줄로 두고 싶을 때는 다른 방법을 씁니다. 내 가지를 잘라 줄기 끝에 옮겨 심는 것입니다. 이것을 **리베이스**(rebase)라고 합니다.

앞 절에서 병합하기 직전으로 돌아가 봅시다. `main`에는 D가, `jump`에는 C가 있습니다. `jump` 브랜치로 가서 터미널에 `git rebase main`이라고 칩니다. "`jump`에만 있는 커밋을 떼어 `main`의 맨 끝 커밋 뒤에 다시 붙여라"라는 뜻입니다.

::: {.fig src="rebase.svg"}
리베이스 전과 후. C가 옮겨 간 것처럼 보이지만 실제로는 새 커밋 C′가 만들어졌습니다.
:::

**커밋은 옮겨지지 않고 새로 만들어집니다.** 커밋은 바로 앞 커밋도 기억한다고 했습니다. C의 앞 커밋은 B였는데 옮겨 심으면 D로 바뀝니다. 고친 내용은 같아도 다른 커밋이 됩니다. 그래서 커밋 ID도 `e4f5a6b`에서 `9d8c7b6`으로 바뀝니다. 옛 커밋 C는 이름표를 잃은 채 남습니다.

혼자 쓰는 커밋이라면 문제가 없습니다. 하지만 C를 이미 준호와 공유했다면 다릅니다. 준호는 C 뒤에 자기 커밋을 쌓고 있는데, 내 쪽에서는 C가 사라지고 C′가 생겼습니다. 두 사람의 이력이 어긋나 엉뚱한 충돌이 납니다.

::: {.key}
**이미 공유한 커밋은 리베이스하지 않습니다.** 리베이스는 아직 내 컴퓨터에만 있는 커밋을 정리할 때 씁니다.
:::

## 되돌리기 세 가지: restore, revert, reset {#undo}

"되돌려 줘." 이 말은 서로 다른 세 가지 부탁일 수 있습니다.

- 저장하지 않은 진행을 버려 달라.
- 지난 저장의 실수를 바로잡아 달라.
- 저장 자체를 없던 일로 해 달라.

명령도 셋입니다. 고르기 전에 **무엇을 남겨야 하는지**부터 정합니다.

::: {.fig src="undo-three.svg"}
세 가지 되돌리기의 전과 후. 그림의 B, C 자리에는 실제로는 커밋 ID를 씁니다.
:::

**restore: 커밋하지 않은 수정 버리기.** 미나가 장난으로 `SPEED`를 99로 고쳤습니다. `git restore config.py`라고 치면 파일이 마지막 커밋의 모습인 10으로 돌아갑니다. 커밋 이력은 그대로입니다. 다만 버린 수정은 저장한 적이 없으므로 **되살릴 수 없습니다.**

**revert: 취소하는 커밋 덧붙이기.** `git revert C`는 커밋 C가 한 일을 거꾸로 하는 **새 커밋**을 만듭니다. C가 2를 3으로 바꿨다면 3을 2로 바꾸는 커밋이 뒤에 붙습니다. 그림의 `-C`입니다. 지난 이력이 지워지지 않으므로 이미 공유한 커밋을 취소할 때 씁니다.

**reset: 이름표를 과거로 옮기기.** `git reset --hard B`는 브랜치 이름표를 B로 되돌려 놓습니다. C는 이력에서 보이지 않게 됩니다. 리베이스와 같은 까닭으로, 공유한 커밋에는 쓰지 않습니다. `--hard`는 작업 폴더의 파일까지 B의 내용으로 덮어쓰라는 뜻입니다. **커밋하지 않은 수정도 함께 지워집니다.**

::: {.warn title="AI에게 '되돌려 줘'라고만 하면"}
AI는 이 말을 듣고 `git reset --hard`를 치곤 합니다. 커밋하지 않은 작업을 묻지도 않고 지우는 명령입니다. "네가 바꾼 `player.py`만 되돌리고 내가 고친 `config.py`는 남겨"처럼 **되돌릴 것과 남길 것**을 말해 주세요.
:::

## 원격 저장소: 저장소를 인터넷에도 두기 {#remote}

지금까지의 일은 전부 미나의 컴퓨터 안에서 일어났습니다. 노트북이 고장 나면 커밋도 함께 사라집니다. 준호는 미나의 커밋을 볼 수도 없습니다.

그래서 같은 저장소를 인터넷의 서버에도 하나 둡니다. 이렇게 멀리 둔 저장소를 **원격 저장소**(remote repository)라고 합니다. 게임의 클라우드 저장과 같습니다.

::: {.myth title="Git과 GitHub는 같은 것이다"}
Git은 내 컴퓨터에서 도는 프로그램입니다. GitHub는 Git 저장소를 인터넷에 올려 둘 수 있게 해 주는 서비스입니다. GitHub가 없어도 Git은 잘 돕니다.
:::

원격 저장소와 주고받는 명령은 넷입니다.

- `git clone 주소`는 원격 저장소를 이력까지 통째로 내려받습니다. 이때 그 원격 저장소에 `origin`이라는 별명이 붙습니다.
- `git push`는 내 커밋을 원격 저장소로 올립니다.
- `git fetch`는 원격 저장소의 새 커밋을 내려받기만 합니다.
- `git pull`은 내려받은 다음 내 브랜치에 합치기까지 합니다.

`fetch`와 `pull`의 차이를 알려면 이름표가 하나 더 필요합니다. `origin/main`입니다. "**마지막으로 확인했을 때** 서버의 `main`이 있던 자리"를 내 컴퓨터에 적어 둔 이름표입니다. 확인한 지 오래됐다면 낡은 정보입니다.

::: {.fig src="remote-sync.svg"}
준호가 C를 올린 뒤 미나의 저장소에서 일어나는 일. `fetch`는 `origin/main`만, `pull`은 `main`과 작업 폴더의 파일까지 움직입니다.
:::

그림의 '동료'는 준호입니다. 준호가 방금 커밋 C를 서버에 올렸습니다. 미나의 컴퓨터를 번호대로 봅시다.

1. 받기 전에는 `main`도 `origin/main`도 B에 있습니다. 서버에 C가 생긴 줄 아직 모릅니다.
2. `git fetch`를 하면 C를 받아 오고 `origin/main`만 C로 옮겨 갑니다. 내 `main`과 파일은 B 그대로입니다.
3. `git pull`을 하면 `main`과 작업 폴더의 파일까지 C로 옵니다.

서버의 `main`에 내가 아직 받지 않은 커밋이 있으면 `push`는 거절됩니다. 그대로 올리면 준호의 커밋이 밀려나기 때문입니다. 먼저 `pull`로 합치고 다시 `push`합니다.

::: {.warn title="강제 push는 덮어쓰기입니다"}
`git push --force`는 서버의 이력을 내 것으로 **덮어씁니다.** 친구의 커밋이 사라질 수 있으니 여럿이 쓰는 브랜치에는 쓰지 않습니다. AI가 "push가 거절되니 강제로 올리겠습니다"라고 하면 멈춰 세우세요.
:::

## 함께 일하기: 풀 리퀘스트, 리뷰, 태그 {#review}

모둠 보고서를 만들 때를 떠올려 봅시다. 내가 쓴 부분을 곧바로 최종본에 붙이지 않습니다. 친구에게 먼저 보여 주고, 괜찮다고 하면 붙입니다.

여럿이 코드를 쓸 때도 같습니다. `main`은 모두가 믿고 출발하는 기준이어서 곧바로 push하지 않습니다. 브랜치에서 작업해 그 브랜치를 push합니다. 그리고 "이 변경을 `main`에 합쳐 주세요"라는 요청을 올립니다. 이 요청을 **풀 리퀘스트**(pull request)라고 하고, 줄여서 PR이라고 부릅니다. 그림의 번호를 따라가 봅시다.

::: {.fig src="pr-flow.svg"}
풀 리퀘스트 한 건이 지나가는 길. 위쪽의 주황색 커밋 C와 D가 친구가 살펴볼 대상입니다.
:::

1. 준호가 `fix-jump` 브랜치에서 커밋 C를 만들고 push합니다.
2. 풀 리퀘스트를 엽니다. 무엇이 **문제**였는지, 어떻게 **변경**했는지, 무엇을 해 보고 **확인**했는지 적습니다.
3. 미나가 바뀐 내용을 읽고 묻습니다. "공중에서도 점프가 되지는 않나요?"
4. 준호가 그 부분을 고쳐 커밋 D를 만들고 다시 push합니다.
5. 미나가 D를 확인하고 승인합니다. `main`에 병합되어 M이 생깁니다.

그림의 2번 상자에서 '변경'에 적힌 말은, 땅에 닿았는지를 먼저 따지고 그다음에 버튼을 살피게 했다는 뜻입니다. '확인'의 테스트는 컴퓨터에게 맡긴 확인을 말합니다.

3번처럼 남이 쓴 코드의 diff를 읽고 의견을 주는 일을 **코드 리뷰**(code review)라고 합니다.

리뷰는 "실행이 되는가"만 보는 일이 아닙니다. 착지 직후 점프는 고쳐졌습니다. 그런데 고치다가 공중에서도 점프가 되게 만들었을 수 있습니다. 리뷰하는 사람은 이렇게 **원래 바라던 대로 됐는지**를 따져 봅니다. AI가 쓴 코드라도 PR을 올린 사람은 어떻게 돌아가는지 설명할 수 있어야 합니다.

### 태그: 움직이지 않는 이름표

브랜치 이름표는 커밋할 때마다 움직입니다. 그래서 "친구들에게 나눠 준 바로 그 버전"을 표시하기에는 맞지 않습니다. 이럴 때는 **움직이지 않는 이름표**를 붙입니다. 이것이 **태그**(tag)입니다. 그림에서는 M에 `v1.0.0`이라는 태그가 붙어 있습니다.

한 번 사람들에게 내놓은 버전 이름은 다시 쓰지 않습니다. 급히 고칠 것이 생겨도 `v1.0.0`을 몰래 바꾸지 않고 `v1.0.1`을 새로 냅니다. 그래야 "1.0.0에서 버그가 나요"라는 말이 어느 코드를 가리키는지 분명합니다. 내놓는 과정은 [20장](ch20.html)에서 다룹니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 파일 저장 / 커밋 | 파일에 적어 두기 / 그 순간을 이력에 남기기 |
| 브랜치 / 태그 | 커밋할 때마다 움직이는 이름표 / 한자리에 붙어 있는 이름표 |
| fetch / pull | 내려받기만 / 내려받고 합치기까지 |
| merge / rebase | 갈라진 자국을 남긴 채 잇기 / 새 커밋으로 다시 만들어 한 줄로 |
| revert / reset | 취소하는 커밋을 덧붙이기 / 이름표를 과거로 옮기기 |

## 실전 사례 {#case}

::: {.case title="AI에게 '되돌려 줘'라고 했더니 이틀 치 작업이 사라졌다"}
목요일에 미나는 AI에게 배경색을 바꿔 달라고 했습니다. 결과가 마음에 들지 않아 "되돌려 줘"라고만 말했습니다. AI는 `git reset --hard HEAD~2`를 실행했습니다. `HEAD~2`는 "지금보다 두 커밋 앞"이라는 뜻입니다. 화요일과 수요일의 커밋이 이력에서 사라졌습니다. 커밋하지 않고 고치던 `config.py`도 예전 내용으로 돌아갔습니다.

1. **멈춥니다.** 명령을 더 치지 말고 `git status`로 지금 상태만 봅니다.
2. **일지를 봅니다.** Git은 HEAD가 지나온 자리를 일지에 적어 둡니다. `git reflog`라고 치면 나옵니다. 방금 한 `reset` 바로 아래 줄에 수요일 커밋의 ID `c7d8e9f`가 보입니다.
3. **이름표부터 붙입니다.** `git branch rescue c7d8e9f`라고 쳐서 그 커밋에 `rescue`라는 브랜치를 붙입니다. 수요일 커밋은 바로 앞의 화요일 커밋을 기억하니 둘 다 돌아옵니다.
4. **확인하고 합칩니다.** `git show rescue`로 내용을 본 뒤 `git merge rescue`를 합니다. `main`이 수요일 커밋으로 돌아옵니다.
5. **잃은 것을 가려냅니다.** 커밋하지 않았던 `config.py` 수정은 일지에도 없습니다. 다시 써야 합니다.

커밋해 둔 것은 웬만하면 살릴 수 있습니다. 그러니 **작게, 자주 커밋합니다.** 되돌리기를 시킬 때는 **무엇을 되돌리고 무엇을 남길지** 말합니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- **커밋**은 폴더 전체의 저장 지점입니다. 누가, 언제, 왜 바꿨는지도 함께 남습니다.
- 파일은 **작업 폴더 → 스테이지 → 저장소**를 거칩니다. 커밋에는 `git add`하던 순간의 내용이 들어갑니다.
- **diff**는 사라진 줄을 `-`로, 새로 생긴 줄을 `+`로 보여 줍니다.
- **브랜치**는 커밋을 가리키는 이름표이고 **HEAD**는 지금 쓰는 이름표를 알려 줍니다.
- **병합**은 갈라진 두 줄기를 합칩니다. 같은 줄을 다르게 고치면 **충돌**이 나고 사람이 정합니다.
- **리베이스**와 **reset**은 이력을 고쳐 쓰므로 공유한 커밋에는 쓰지 않습니다. 그런 커밋은 **revert**로 취소합니다.
- **fetch**는 `origin/main`만, **pull**은 내 브랜치와 파일까지 움직입니다.
- 커밋하지 않은 수정은 Git도 살리지 못합니다. 작게, 자주 커밋합니다.
:::

## 확인 문제 {#quiz}

::: {.q}
수행평가 보고서를 `보고서_최종`, `보고서_진짜최종`처럼 복사해 가며 썼습니다. 선생님이 "두 파일 사이에 무엇을 왜 바꿨니?" 하고 묻습니다. 왜 대답하기 어려울까요? 커밋이었다면 무엇이 남아 있을까요?

::: {.a}
복사본에는 무엇을 왜 바꿨는지가 적혀 있지 않기 때문입니다. 커밋이었다면 바꾼 까닭을 적은 커밋 메시지와 만든 사람, 날짜가 남습니다.
:::
:::

::: {.q}
택배 상자에 편지를 넣었습니다. 그 뒤 책상에 남은 초안에 한 줄을 더 썼지만 상자는 그대로 닫아 보냈습니다. 받는 사람은 어떤 편지를 읽을까요? `git add`와 비교해 보세요.

::: {.a}
상자에 넣던 순간의 편지를 읽습니다. Git도 같습니다. `git add`하던 순간의 내용이 커밋에 들어가고, 그 뒤에 고친 것은 작업 폴더에만 남습니다. 다시 고쳤으면 `git add`도 다시 합니다.
:::
:::

::: {.q}
모둠 발표 자료의 같은 줄을 두 친구가 따로 고쳤습니다. 한 친구는 발표 날짜를 '목요일'로, 다른 친구는 '금요일'로 적었습니다. Git으로 병합하면 어떻게 될까요?

::: {.a}
같은 줄을 서로 다르게 고쳤으므로 충돌이 납니다. Git은 양쪽 내용을 표시와 함께 파일에 적어 두고 멈춥니다. 사람이 맞는 날짜를 정하고 표시 줄을 지운 뒤 `git add`와 `git commit`으로 마칩니다.
:::
:::

::: {.q}
반 단체 대화방에 올린 공지의 시간이 틀렸습니다. 친구들은 이미 읽었습니다. 공지를 몰래 지우는 것과 "3시가 맞습니다"라고 새로 올리는 것 중 어느 쪽이 덜 헷갈릴까요? Git에서는 어떤 명령과 닮았을까요?

::: {.a}
새로 올리는 쪽입니다. 이미 읽은 친구들도 무엇이 바뀌었는지 알 수 있습니다. 취소하는 커밋을 덧붙이는 `git revert`와 닮았습니다. 몰래 지우는 것은 `git reset`과 닮았습니다.
:::
:::

::: {.q}
교실 게시판에 붙인 종이에 내 사물함 비밀번호가 적혀 있었습니다. "앞으로는 비밀번호를 적은 종이를 붙이지 않는다"는 규칙을 정하면 충분할까요? `.gitignore`와 비교해 보세요.

::: {.a}
충분하지 않습니다. 이미 붙인 종이는 누가 봤을지 모르니 비밀번호부터 바꿔야 합니다. `.gitignore`도 앞으로 담지 않게 해 줄 뿐이고, 이미 커밋한 비밀번호는 지난 커밋에 남습니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI에게 커밋을 맡길 때는 **계획을 먼저 보여 주게** 합니다. **되돌릴 수 없는 명령은 미리 막아** 둡니다.

> 바뀐 것을 커밋하려고 해. 먼저 `git status`와 `git diff`를 읽고, 어떤 커밋으로 나눌지 계획만 보여 줘. 내가 부탁한 '착지 직후 점프 버그 수정'과 관계없는 변경은 따로 알려 줘. `.env`는 커밋에 넣지 마. `reset --hard`나 `push --force`처럼 되돌릴 수 없는 명령은 내가 허락하기 전에는 쓰지 마.

**받은 답에서 확인할 것**: 부탁과 관계없는 파일이 섞이지 않았는가. 새로 만든 파일이 빠지지 않았는가. 커밋 메시지가 무엇을 해결했는지 말하는가.
:::

## 용어 정리 {#terms}

::: {.terms}
버전 관리 (version control)
:   파일이 바뀌어 온 기록을 남겨, 비교하고 되돌릴 수 있게 하는 일.

저장소 (repository)
:   커밋이 모두 쌓여 있는 곳. 프로젝트 폴더의 `.git` 안에 있다.

커밋 (commit)
:   그 순간 폴더 전체의 모습을 담은 저장 지점. 누가, 언제, 왜 바꿨는지도 담는다.

작업 폴더 (working tree)
:   지금 눈에 보이고 고치는 파일들.

스테이지 (staging area)
:   다음 커밋에 담을 내용을 올려 두는 곳.

diff (difference)
:   두 상태를 비교해 사라진 줄과 새로 생긴 줄을 보여 주는 것.

브랜치 (branch)
:   커밋 하나를 가리키는 이름표. 커밋하면 새 커밋으로 옮겨 간다.

HEAD
:   내가 지금 쓰고 있는 브랜치를 알려 주는 표시.

병합 (merge)
:   갈라진 두 줄기의 변경을 하나로 합치는 일.

충돌 (conflict)
:   같은 줄을 서로 다르게 고쳐서 Git이 혼자 합치지 못한 상태.

리베이스 (rebase)
:   내 커밋을 다른 커밋 뒤에 옮겨 심어 새 커밋으로 다시 만드는 일.

원격 저장소 (remote repository)
:   인터넷의 서버처럼 멀리 둔 저장소. 보통 `origin`이라는 별명으로 부른다.

풀 리퀘스트 (pull request)
:   내 브랜치의 변경을 살펴본 뒤 합쳐 달라고 올리는 요청.

태그 (tag)
:   커밋에 붙이는 움직이지 않는 이름표. 버전을 표시할 때 쓴다.
:::
