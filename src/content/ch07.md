::: {.lead}
게임을 하다가 어려운 보스를 만나기 전에는 저장을 해 둡니다. 지면 저장한 곳으로 돌아가면 됩니다. 코드를 쓸 때도 똑같은 것이 필요합니다. 잘 되던 코드를 고치다가 망가뜨리면 잘 되던 때로 돌아가고 싶어집니다. 코드의 '저장 지점'을 만들고 관리해 주는 도구가 **Git**입니다.
:::

::: {.goals}
- Git이 왜 필요한지 설명할 수 있습니다.
- 저장 지점(커밋)을 만들고, 무엇이 바뀌었는지 볼 수 있습니다.
- 실수했을 때 예전 상태로 돌아가는 방법을 고를 수 있습니다.
- 여러 사람이 같은 코드를 함께 고치는 방법을 설명할 수 있습니다.
:::

## 버전 관리: 프로젝트에 세이브 포인트 만들기 {#why}

Git을 모르는 사람의 폴더에는 이런 파일이 쌓입니다. `mygame_최종.zip`, `mygame_진짜최종.zip`, `mygame_진짜최종_수정.zip`. 통째로 복사해 두니 안심은 되지만, 두 복사본 사이에 **무엇이 바뀌었는지**, **왜 바꿨는지** 알 길이 없습니다. 친구와 각자 고친 복사본을 하나로 합칠 방법도 없습니다.

게임을 떠올려 봅시다. 보스 방 앞에서 세이브해 두면, 지더라도 그 자리에서 다시 시작합니다. 코드에도 이런 **세이브 포인트**가 있다면 마음 놓고 실험할 수 있습니다.

이 일을 해 주는 도구가 **버전 관리 시스템**(version control system)이고, 그중 가장 널리 쓰이는 것이 **Git**입니다.

Git의 세이브 포인트는 **커밋**(commit)이라고 부릅니다. 커밋 하나에는 세 가지가 담깁니다.

- **그 순간 프로젝트 전체의 모습.** 사진 한 장을 찍는 셈이라 **스냅샷**(snapshot)이라고 합니다.
- **누가, 언제, 왜 바꿨는지.** '왜'는 사람이 직접 적는 **커밋 메시지**입니다.
- **바로 앞 커밋이 무엇인지.** 그래서 커밋들은 줄줄이 이어진 이력이 됩니다.

::: {.fig src="save-points.svg"}
복사본 쌓기와 커밋의 차이. 커밋에는 고유한 번호와 메시지, 만든 사람과 시각이 함께 남습니다.
:::

그림의 `a1b2c3d` 같은 글자는 커밋마다 붙는 고유 번호인 **커밋 ID**입니다. 원래는 40글자인데 보통 앞의 일곱 글자쯤만 줄여 씁니다.

커밋이 쌓이는 곳이 **저장소**(repository)입니다. 프로젝트 폴더에서 `git init`을 실행하면 `.git`이라는 숨김 폴더가 생기고, 세이브 기록이 전부 그 안에 들어갑니다.

::: {.note}
비유가 어긋나는 곳이 하나 있습니다. 게임은 세이브 칸을 덮어쓰지만 **Git은 덮어쓰지 않고 계속 쌓습니다.** 그래서 열 번 전의 세이브로도 돌아갈 수 있습니다.
:::

::: {.deep title="커밋마다 전체를 찍으면 용량이 넘치지 않을까 (Git의 내부 객체)"}
Git은 내용이 같은 파일을 두 번 저장하지 않습니다. 저장소 안에는 세 종류의 객체가 있습니다.

- **blob**: 파일 내용 한 덩어리. 파일 이름은 들어 있지 않습니다.
- **tree**: 폴더 하나. "이 이름은 저 blob"이라고 적은 목록입니다.
- **commit**: 맨 위 tree 하나와 부모 커밋, 작성자, 메시지.

객체의 ID는 내용을 **해시**(hash)라는 계산에 넣어 얻습니다. 해시는 내용이 한 글자만 달라도 전혀 다른 값이 나오는 계산입니다. 내용이 같으면 ID도 같으므로, 파일 100개 중 1개만 고친 커밋은 그 파일의 blob과 그 위의 tree, commit만 새로 만들고 나머지 99개는 예전 것을 그대로 가리킵니다.
:::

## 세 구역: 고치는 곳, 담는 곳, 쌓이는 곳 {#stage}

게임은 세이브 버튼 하나로 전부 저장합니다. Git은 한 단계를 더 둡니다. **이번 세이브에 무엇을 담을지 먼저 고르게** 합니다. 점프를 고치다가 배경색도 건드렸다면 둘을 다른 커밋으로 나누고 싶을 테니까요.

그래서 파일이 머무는 곳이 셋입니다.

- **작업 폴더**(working tree)는 책상입니다. 지금 눈에 보이고 편집하는 파일들입니다.
- **스테이지**(staging area)는 포장 상자입니다. 다음 커밋에 담을 내용을 올려 둡니다. 인덱스(index)라고도 합니다.
- **저장소**는 커밋이 쌓인 보관함입니다.

`git add`는 파일을 상자에 담고, `git commit`은 상자를 봉해 보관함에 넣습니다.

```bash
git status
git add config.py
git commit -m "달리기 속도를 10에서 11로 올림"
```

- **1행**은 어느 파일이 바뀌었고 무엇이 상자에 담겼는지 보여 줍니다.
- **2행**은 `config.py`의 **지금 내용**을 스테이지에 올립니다.
- **3행**은 스테이지에 올라온 것으로 새 커밋을 만듭니다. `-m` 뒤가 커밋 메시지입니다.

"지금 내용"이라는 말이 중요합니다. `SPEED = 10`을 11로 고쳐 `git add`한 다음, 마음이 바뀌어 12로 또 고쳤다고 합시다.

::: {.fig src="three-areas.svg"}
같은 파일이 세 구역에서 서로 다른 값을 갖는 순간. 이대로 커밋하면 11이 기록되고, 12는 작업 폴더에만 남습니다.
:::

상자에는 담던 순간의 11이 들어 있습니다. 이때 게임을 실행하면 작업 폴더의 12로 돌기 때문에 **확인한 것과 커밋한 것이 달라집니다.** 다시 고쳤으면 다시 `git add`합니다.

::: {.key}
커밋에 들어가는 것은 작업 폴더의 파일이 아니라 **스테이지에 올려 둔 내용**입니다.
:::

커밋 하나에는 **한 가지 목적**만 담습니다. 그래야 나중에 그 변경만 골라 살펴보거나 취소할 수 있습니다. 메시지에는 바꾼 파일 이름보다 **해결한 문제**를 적습니다. "수정"은 석 달 뒤의 나에게 아무것도 알려 주지 않습니다. "착지 직후 점프가 안 되던 문제 수정"이면 충분합니다.

### .gitignore: 담지 않을 것 정하기

[5장](ch05.html#project)에서 프로젝트 폴더를 네 종류로 나눴습니다. 커밋할 것은 **소스**입니다. 빌드 결과와 캐시는 다시 만들 수 있으니 담지 않습니다. 비밀번호나 API 키가 든 `.env` 파일도 담으면 안 됩니다. 이런 이름을 `.gitignore` 파일에 한 줄씩 적어 두면 Git이 못 본 척합니다.

```text
build/
__pycache__/
.env
```

::: {.warn title=".gitignore는 지우개가 아닙니다"}
`.gitignore`는 **아직 한 번도 커밋하지 않은 파일**에만 통합니다. 이미 커밋한 파일은 목록에 적어도 계속 관리되고, 지난 커밋 속에도 그대로 남아 있습니다. API 키를 실수로 커밋했다면 숨기려 애쓰기 전에 **그 키를 폐기하고 새로 발급받는 것**이 먼저입니다.
:::

## diff: 무엇이 바뀌었는지 읽기 {#diff}

AI가 "점프 높이만 바꿨습니다"라고 말합니다. 정말일까요? 말을 믿을 필요 없이 직접 보면 됩니다. 두 상태의 차이를 줄 단위로 보여 주는 것이 **diff**입니다.

::: {.fig src="diff-read.svg"}
`git diff`의 출력 읽기. `config.py`에서 `JUMP` 값을 2에서 3으로 고친 변경입니다.
:::

`-`로 시작하는 줄은 사라졌고, `+`로 시작하는 줄은 새로 생겼습니다. 한 줄을 고치면 사라진 줄 하나와 생긴 줄 하나로 나타납니다.

diff를 볼 때는 **어느 둘을 비교하는지**부터 정해야 합니다. 앞 절 그림의 아래쪽 점선이 바로 그 이야기입니다.

| 명령 | 비교하는 둘 | 알 수 있는 것 |
|---|---|---|
| `git diff` | 작업 폴더와 스테이지 | 아직 담지 않은 변경 |
| `git diff --staged` | 스테이지와 마지막 커밋 | 다음 커밋에 들어갈 변경 |
| `git show a1b2c3d` | 그 커밋과 바로 앞 커밋 | 그 커밋이 바꾼 것 |

::: {.warn title="새 파일은 git diff에 나오지 않습니다"}
한 번도 `git add`하지 않은 새 파일은 Git이 아직 관리하지 않아서 `git diff`에 보이지 않습니다. 그래서 `git status`를 함께 봅니다. AI가 새로 만든 파일은 거기에서만 드러납니다.
:::

AI와 일할 때 diff는 영수증입니다. 커밋 전에 `git diff --staged`를 훑으며 두 가지를 묻습니다. 요청한 일과 **관계없는 파일**이 끼어 있지 않은가. 패키지 목록이나 설정처럼 **영향이 큰 파일**이 바뀌지 않았는가. AI는 `git add .`으로 폴더 안의 것을 한꺼번에 담는 일이 잦으니 더욱 그렇습니다.

::: {.try}
연습용 폴더에서 `git init`을 실행하고 파일 하나를 만들어 커밋해 보세요. 그 파일을 한 줄 고치고 `git diff`를 치면 빨간 줄과 초록 줄이 보입니다.
:::

## 브랜치: 커밋에 붙이는 이름표 {#branch}

2단 점프를 넣어 보고 싶습니다. 잘될지 모르는 실험이라, 멀쩡한 게임은 그대로 두고 **평행 세계**에서 해 보고 싶습니다. 폴더를 통째로 복사해야 할까요? Git에서는 이름표 한 장이면 됩니다.

커밋은 저마다 바로 앞 커밋을 기억한다고 했습니다. 커밋을 동그라미로, 그 연결을 선으로 그리면 **커밋 그래프**가 됩니다. **브랜치**(branch)는 이 그래프에서 **커밋 하나를 가리키는 이름표**입니다. 파일 복사본이 아닙니다. 저장소를 만들면 보통 `main`이라는 브랜치가 하나 있습니다(오래된 저장소에서는 `master`).

이름표가 여럿이면 내가 지금 어느 것을 쓰는지도 알아야 합니다. 그 표시가 **HEAD**입니다. 지도의 "현재 위치" 핀이라고 생각하세요.

::: {.fig src="branch-label.svg"}
브랜치를 만들고 커밋할 때 움직이는 것. 동그라미는 커밋, 네모는 이름표이고 오른쪽일수록 최신입니다.
:::

::: {.key}
새 커밋을 만들면 **HEAD가 붙어 있는 이름표만** 새 커밋으로 옮겨 갑니다.
:::

그림의 ③에서 `jump`는 C로 갔지만 `main`은 B에 그대로 있습니다. 실험이 실패해도 `main`의 세계는 멀쩡합니다.

`git switch main`을 치면 HEAD가 `main`으로 옮겨 가고, **작업 폴더의 파일이 B 시점의 모습으로 바뀝니다.** 방금 쓴 2단 점프 코드는 화면에서 사라지지만 C 안에 안전하게 들어 있고, `git switch jump`로 돌아가면 다시 나타납니다. 브랜치가 20개여도 늘어나는 것은 이름표 20장뿐입니다.

::: {.note}
평행 세계로 나뉘는 것은 **Git이 관리하는 파일**뿐입니다. 데이터베이스나 `.gitignore`로 제외한 파일은 브랜치를 바꿔도 그대로입니다. 두 브랜치가 같은 개발용 데이터베이스를 쓰면 데이터는 섞입니다.
:::

::: {.tip title="checkout이라는 옛 명령"}
옛 문서와 AI 도구는 `git checkout`을 자주 씁니다. 브랜치 바꾸기와 파일 되돌리기를 한 명령이 다 맡아 헷갈렸기에 나중에 `git switch`와 `git restore`로 나뉘었습니다.
:::

::: {.deep title="하던 일을 잠깐 치워 두기: stash와 worktree"}
커밋하기에는 이른데 급한 버그를 봐야 할 때가 있습니다.

- `git stash`는 커밋하지 않은 수정을 임시 보관함에 넣어 작업 폴더를 깨끗하게 만들고, `git stash pop`으로 다시 꺼냅니다. 새로 만든 파일은 기본으로는 보관되지 않습니다.
- `git worktree`는 같은 저장소를 **다른 폴더에 한 벌 더** 펼칩니다. 폴더마다 다른 브랜치를 열 수 있어서 AI 에이전트 여럿에게 다른 작업을 동시에 맡길 때도 씁니다. 다만 데이터베이스와 서버 포트는 여전히 하나입니다.
:::

## 병합과 충돌: 두 세계를 하나로 {#merge}

2단 점프 실험이 성공했습니다. 그 사이 `main`에서는 배경을 바꾸는 커밋 D도 만들었습니다. 이제 갈라진 두 흐름을 합칠 차례입니다. 이 일이 **병합**(merge)입니다.

```bash
git switch main
git merge jump
```

- **1행**은 받을 쪽인 `main`으로 갑니다.
- **2행**은 `jump`의 변경을 지금 브랜치로 가져옵니다.

::: {.fig src="merge-graph.svg"}
병합 전과 후. 병합 커밋 M은 부모가 둘이고, 이름표는 `main`만 M으로 옮겨 갑니다.
:::

Git은 먼저 두 브랜치가 갈라지기 직전의 커밋인 **공통 조상** B를 찾습니다. 그리고 B에서 D까지 바뀐 것과 B에서 C까지 바뀐 것을 비교합니다. 서로 다른 곳을 고쳤다면 둘 다 받아들여 **병합 커밋**을 만듭니다.

::: {.note}
`main`이 그동안 움직이지 않았다면 Git은 병합 커밋 없이 `main` 이름표만 C로 당겨 옵니다. 이것을 **빨리 감기**(fast-forward)라고 합니다.
:::

### 충돌: Git이 고르지 못할 때

양쪽이 **같은 줄을 서로 다르게** 고쳤다면 이야기가 달라집니다.

::: {.fig src="conflict.svg"}
충돌이 생기고 풀리는 과정. `<<<<<<<`, `=======`, `>>>>>>>`로 시작하는 세 줄은 Git이 끼워 넣은 표시입니다.
:::

이것이 **충돌**(conflict)입니다. 고장이 아니라 질문입니다. 푸는 순서는 이렇습니다.

1. `git status`로 충돌한 파일을 확인합니다.
2. 파일을 열어 `=======` 위(지금 브랜치)와 아래(합치려는 브랜치)를 읽고 최종 내용을 정합니다. 둘을 섞어 새로 써도 됩니다.
3. 표시 세 줄을 모두 지우고 저장합니다.
4. `git add`로 해결했다고 알리고 `git commit`으로 병합을 마칩니다.

엄두가 나지 않으면 `git merge --abort`로 병합을 시작하기 전으로 돌아갈 수 있습니다.

::: {.warn title="조용히 합쳐졌다고 맞는 것은 아닙니다"}
한 브랜치는 `JUMP`의 단위를 '칸'에서 '픽셀'로 바꿨고, 다른 브랜치는 다른 파일에서 '칸'이라 믿고 `JUMP`를 썼습니다. 같은 줄이 아니니 Git은 충돌 없이 합칩니다. 하지만 캐릭터는 3칸이 아니라 3픽셀을 뜁니다. Git은 글자를 볼 뿐 뜻은 모릅니다. **병합한 뒤에는 테스트([12장](ch12.html))를 다시 돌립니다.**
:::

::: {.deep title="브랜치는 얼마나 오래 살려 둘까 (브랜치 전략)"}
브랜치가 오래 갈라져 있을수록 양쪽이 서로 모르는 변경을 쌓아 병합이 어려워집니다. 2주 치 작업을 마지막 날 합치면 충돌이 없더라도 전체를 다시 확인해야 합니다. 그래서 많은 팀이 **브랜치를 짧게 쓰고 자주 합칩니다.** 큰 기능은 작은 변경 여러 개로 쪼갭니다.
:::

## 리베이스: 내 커밋을 옮겨 심기 {#rebase}

병합을 자주 하면 이력에 갈래와 병합 커밋이 늘어납니다. 이력을 한 줄로 두고 싶을 때는 병합 대신 **리베이스**(rebase)를 씁니다. 가지를 잘라 다른 줄기 끝에 옮겨 심는 것과 같습니다. 앞 절의 병합 직전으로 돌아가 해 봅시다.

```bash
git switch jump
git rebase main
```

- **1행**은 옮겨 심을 브랜치인 `jump`로 갑니다.
- **2행**은 "`jump`에만 있는 커밋을 떼어, `main`의 최신 커밋 위에 다시 붙여라"입니다.

::: {.fig src="rebase.svg"}
리베이스 전과 후. C가 옮겨 간 것처럼 보이지만 실제로는 새 커밋 C′가 만들어졌습니다.
:::

중요한 것은 **커밋이 옮겨지지 않고 새로 만들어진다**는 점입니다. 커밋 ID는 내용과 부모를 함께 넣어 계산합니다. 부모가 B에서 D로 바뀌었으니 변경 내용이 같아도 ID가 달라집니다. 그림에서 `e4f5a6b`가 `9d8c7b6`이 된 이유입니다.

혼자 쓰는 커밋이라면 문제될 것이 없습니다. 하지만 C를 이미 동료와 공유했다면 다릅니다. 동료는 C 위에 자기 커밋을 쌓고 있는데 내 쪽에서는 C가 사라지고 C′가 생겼습니다. 두 사람의 이력이 어긋나서 같은 변경이 두 번 나타나거나 엉뚱한 충돌이 납니다.

::: {.key}
**이미 공유한 커밋은 리베이스하지 않습니다.** 리베이스는 아직 내 컴퓨터에만 있는 커밋을 정리할 때 씁니다.
:::

리베이스 도중 충돌이 나면 병합 때처럼 풀고 `git rebase --continue`로 이어 갑니다. C′는 C와 다른 커밋이므로 **C에서 통과한 테스트도 다시 돌려야** 합니다.

## 되돌리기 세 가지: restore, revert, reset {#undo}

"되돌려 줘." 이 말은 전혀 다른 세 가지 부탁일 수 있습니다. 세이브하지 않은 진행을 버리라는 것인지, 지난 세이브의 실수를 바로잡으라는 것인지, 세이브 자체를 없던 일로 하라는 것인지. 고르기 전에 **무엇을 남겨야 하는지**부터 정합니다.

::: {.fig src="undo-three.svg"}
세 가지 되돌리기의 전과 후. 그림의 B, C 자리에는 실제로는 커밋 ID를 씁니다.
:::

- **restore.** `git restore 파일`은 커밋하지 않은 수정을 버리고 파일을 마지막 커밋의 모습으로 돌립니다(`git add`해 둔 내용이 있으면 그 내용으로). 버린 수정은 세이브된 적이 없으므로 **되살릴 수 없습니다.**
- **revert.** `git revert 커밋`은 그 커밋이 한 일을 거꾸로 하는 **새 커밋**을 만듭니다. 2를 3으로 바꾼 커밋이라면 3을 2로 바꾸는 커밋이 뒤에 붙습니다. 과거가 지워지지 않으므로 이미 공유한 커밋을 취소할 때 씁니다.
- **reset.** `git reset 커밋`은 브랜치 이름표를 과거 커밋으로 옮깁니다. 그 뒤의 커밋은 이력에서 보이지 않게 됩니다. 리베이스와 같은 이유로 공유한 커밋에는 쓰지 않습니다.

`reset`에는 세기가 있습니다. 옵션 없이 쓰면 이름표와 스테이지만 되돌리고 작업 폴더의 파일은 그대로 둡니다. `--hard`를 붙이면 작업 폴더까지 그 커밋의 내용으로 덮어써서 **커밋하지 않은 수정도 함께 지웁니다.**

::: {.warn title="AI에게 '되돌려 줘'라고만 하면"}
AI 도구는 이 말을 `git reset --hard`나 `git checkout .`으로 옮기곤 합니다. 둘 다 커밋하지 않은 작업을 묻지 않고 지웁니다. "네가 바꾼 `player.py`만 되돌리고 내가 고친 `config.py`는 남겨"처럼 **대상과 남길 것**을 말해 주세요.
:::

::: {.deep title="사라진 커밋 살리기: reflog"}
`reset`이나 리베이스로 이름표를 잃은 커밋은 곧바로 지워지지 않습니다. Git은 HEAD가 지나온 자리를 **reflog**라는 일지에 적어 둡니다.

```text
$ git reflog
9a8b7c6 HEAD@{0}: reset: moving to HEAD~1
c7d8e9f HEAD@{1}: commit: 2단 점프 추가
```

첫 줄은 방금 한 `reset`이고, 둘째 줄의 `c7d8e9f`가 그 직전에 있던 커밋입니다. `git branch rescue c7d8e9f`로 이름표를 다시 붙이면 살아납니다. 다만 reflog는 **내 컴퓨터에만** 있고 오래된 기록은 정리됩니다. **한 번도 커밋하지 않은 수정**은 여기에도 없습니다.
:::

## 원격 저장소: 세이브를 서버에도 두기 {#remote}

지금까지의 일은 전부 내 컴퓨터 안에서 일어났습니다. 노트북을 잃어버리면 세이브도 사라지고, 동료는 내 커밋을 볼 수 없습니다. 그래서 같은 저장소를 서버에도 하나 둡니다. 이것이 **원격 저장소**(remote repository)입니다. 게임의 클라우드 세이브와 같습니다.

::: {.myth title="Git과 GitHub는 같은 것이다"}
Git은 내 컴퓨터에서 도는 버전 관리 프로그램이고, GitHub는 Git 저장소를 인터넷에 올려 두는 서비스입니다. GitHub 없이도 Git은 온전히 동작합니다.
:::

오가는 명령은 넷입니다.

- `git clone 주소`는 원격 저장소를 이력째 통째로 내려받습니다. 이때 그 원격에 `origin`이라는 별명이 붙습니다.
- `git push`는 내 커밋을 원격으로 올립니다.
- `git fetch`는 원격의 새 커밋을 내려받기만 합니다.
- `git pull`은 내려받은 다음 내 브랜치에 합치기까지 합니다.

`fetch`와 `pull`의 차이를 알려면 이름표가 하나 더 필요합니다. `origin/main`은 "**마지막으로 확인했을 때** 서버의 `main`이 있던 자리"를 내 컴퓨터에 적어 둔 이름표입니다. **원격 추적 브랜치**라고 합니다. 서버를 실시간으로 비추는 거울이 아니라서, 확인한 지 오래됐다면 낡은 정보입니다.

::: {.fig src="remote-sync.svg"}
동료가 C를 올린 뒤 내 저장소에서 일어나는 일. `fetch`는 `origin/main`만, `pull`은 `main`과 작업 폴더의 파일까지 움직입니다.
:::

`fetch`는 내 파일을 건드리지 않으니, 받아 두고 무엇이 새로 왔는지 살핀 뒤 합칠지 정할 수 있습니다. `pull`은 두 단계를 한 번에 하므로 충돌이 날 수 있습니다.

서버의 `main`에 내가 아직 받지 않은 커밋이 있으면 `push`는 거절됩니다. 그대로 올리면 동료의 커밋이 밀려나기 때문입니다. 먼저 `pull`로 합치고 다시 `push`합니다.

::: {.warn title="강제 push는 덮어쓰기입니다"}
`git push --force`는 서버의 이력을 내 것으로 **덮어씁니다.** 동료의 커밋이 사라질 수 있으므로 여럿이 쓰는 브랜치에는 쓰지 않습니다. AI가 "push가 거절되니 강제로 올리겠습니다"라고 하면 멈춰 세우세요.
:::

::: {.deep title="큰 파일과 다른 저장소 품기: LFS와 서브모듈"}
이미지, 소리, 3D 모델 같은 큰 파일은 고칠 때마다 통째로 저장되어 저장소가 금세 무거워집니다. **Git LFS**(Large File Storage)는 Git에는 "진짜 파일은 저기 있다"는 작은 쪽지만 넣고 실제 파일은 따로 보관합니다. 다만 두 사람이 같은 그림을 동시에 고쳤을 때 합쳐 주지는 못합니다.

**서브모듈**(submodule)은 저장소 안에 다른 저장소를 "딱 이 커밋"이라고 못 박아 품는 기능입니다. 바깥 저장소만 받으면 안쪽 폴더가 비어 있을 수 있습니다.
:::

## 함께 일하기: 풀 리퀘스트, 리뷰, 태그 {#review}

팀에서는 `main`에 곧바로 push하지 않습니다. `main`은 모두가 믿고 출발하는 기준이어서, 누군가 한 번 더 보고 나서 합칩니다. 브랜치에서 작업해 그 브랜치를 push한 뒤, "이 변경을 `main`에 합쳐 주세요"라는 요청을 엽니다. 이 요청이 **풀 리퀘스트**(pull request, 줄여서 PR)입니다. Git 자체가 아니라 GitHub 같은 서비스가 주는 기능입니다.

::: {.fig src="pr-flow.svg"}
풀 리퀘스트 한 건이 지나가는 길. 위쪽 그래프의 주황색 커밋 C와 D가 리뷰 대상입니다.
:::

PR이 열리면 동료가 diff를 읽고 의견을 답니다. 이것이 **코드 리뷰**(code review)입니다. 좋은 PR 설명에는 세 가지가 있습니다. **무엇이 문제였는지, 바꾼 뒤 어떻게 동작하는지, 무엇을 실행해 확인했는지.**

리뷰는 테스트가 통과했는지만 보는 일이 아닙니다. "관리자만 글을 지울 수 있다"는 요구에, 일반 사용자 화면에서 삭제 버튼을 숨기는 코드만 들어 있다고 합시다. 화면 테스트는 통과합니다. 하지만 서버가 권한을 확인하지 않으면 버튼 없이도 삭제 요청을 보낼 수 있습니다. 리뷰어는 **요구가 정말 충족됐는지**를 따라가 봅니다. AI가 쓴 코드라도 PR을 올린 사람이 어떻게 동작하는지 설명할 수 있어야 합니다.

### 태그와 릴리스

브랜치는 커밋할 때마다 움직입니다. 그래서 "사용자에게 내보낸 바로 그 버전"을 표시하기에는 맞지 않습니다. **태그**(tag)는 커밋 하나에 붙이는 **움직이지 않는 이름표**입니다. 보통 `v1.0.0` 같은 버전 이름을 붙입니다.

**릴리스**(release)는 그 태그에 설치 파일과 변경 설명을 묶어 공개하는 일입니다. 한 번 공개한 버전 이름은 다시 쓰지 않습니다. 급히 고칠 것이 있어도 `v1.0.0`을 몰래 바꾸지 않고 `v1.0.1`을 새로 냅니다. 그래야 "1.0.0에서 버그가 나요"라는 신고가 어느 코드를 말하는지 분명합니다. 설치 파일을 만들어 내보내는 과정은 [20장](ch20.html)에서 다룹니다.

::: {.deep title="저장소의 얼굴: README와 라이선스"}
저장소 맨 위의 `README` 파일은 처음 온 사람에게 설치와 실행 방법을 알려 주는 안내문입니다. 적어 둔 명령은 깨끗한 환경에서 그대로 따라 해 봐야 빠진 준비물이 드러납니다.

`LICENSE` 파일은 남이 이 코드를 쓰고 고치고 배포해도 되는 조건을 적은 문서입니다. **공개 저장소에서 읽을 수 있다는 것과 가져다 써도 된다는 것은 다릅니다.** 라이선스 파일이 없으면 허락된 것으로 여기지 않습니다. 코드와 그림, 글꼴, 음악의 조건은 서로 다를 수 있습니다.
:::

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 파일 저장 / 커밋 | 디스크에 쓰기 / 그 순간을 이력에 남기기 |
| 브랜치 / 태그 | 커밋할 때마다 움직이는 이름표 / 한자리에 박아 두는 이름표 |
| fetch / pull | 내려받기만 / 내려받고 합치기까지 |
| merge / rebase | 갈래를 남긴 채 잇기 / 새 커밋으로 다시 만들어 한 줄로 |
| revert / reset | 취소하는 커밋을 덧붙이기 / 이름표를 과거로 옮기기 |

## 실전 사례 {#case}

::: {.case title="AI에게 '되돌려 줘'라고 했더니 오전 작업이 사라졌다"}
AI가 만든 변경이 마음에 들지 않아 "되돌려 줘"라고 했더니 AI가 `git reset --hard HEAD~2`를 실행했습니다. `HEAD~2`는 "지금보다 두 커밋 앞"입니다. 오전에 만든 커밋 두 개가 `git log`에서 사라졌고, 커밋하지 않고 고치던 `config.py`도 예전 내용으로 돌아갔습니다.

1. **멈춥니다.** 당황해서 명령을 더 치면 단서가 흐려집니다. `git status`로 지금 상태만 봅니다.
2. **HEAD의 일지를 봅니다.** `git reflog`에 `reset: moving to HEAD~2` 줄이 있고, 바로 아래 줄에 사라지기 직전의 커밋 ID `c7d8e9f`가 보입니다.
3. **이름표부터 붙입니다.** `git branch rescue c7d8e9f`를 실행해 그 커밋을 붙잡아 둡니다.
4. **내용을 확인하고 합칩니다.** `git show rescue`로 오전 작업이 맞는지 본 뒤 `git merge rescue`를 합니다. `main`은 빨리 감기로 제자리에 돌아옵니다.
5. **잃은 것을 가려냅니다.** 커밋하지 않았던 `config.py` 수정은 reflog에 없습니다. 다시 써야 합니다.

커밋해 둔 것은 웬만하면 살릴 수 있으니 **작게, 자주 커밋합니다.** 그리고 되돌리기를 시킬 때는 **무엇을 되돌리고 무엇을 남길지** 말합니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- **커밋**은 프로젝트 전체의 세이브 포인트입니다. 누가, 왜 바꿨는지와 바로 앞 커밋을 함께 기억합니다.
- 파일은 **작업 폴더 → 스테이지 → 저장소**를 거칩니다. 커밋에는 `git add`하던 순간의 내용이 들어갑니다.
- **브랜치**는 커밋을 가리키는 이름표이고 **HEAD**는 지금 쓰는 이름표를 가리킵니다. 커밋하면 그 이름표만 전진합니다.
- **병합**은 갈라진 두 변경을 합칩니다. 같은 줄을 다르게 고치면 **충돌**이 나고 사람이 정합니다.
- **리베이스**와 **reset**은 이력을 고쳐 쓰므로 공유한 커밋에는 쓰지 않습니다. 공유한 커밋은 **revert**로 취소합니다.
- **fetch**는 `origin/main`만, **pull**은 내 브랜치까지 움직입니다. 강제 push는 남의 커밋을 지울 수 있습니다.
- 커밋하지 않은 수정은 Git도 살리지 못합니다.
:::

## 확인 문제 {#quiz}

::: {.q}
`SPEED = 10`을 11로 고쳐 `git add`한 뒤 다시 12로 고쳤습니다. 이 상태에서 `git commit`을 하면 어떤 값이 기록될까요?

::: {.a}
11이 기록됩니다. `git add`는 그 순간의 내용을 스테이지에 올리고, 커밋은 스테이지에 있는 것으로 만들어지기 때문입니다. 12를 기록하려면 커밋하기 전에 `git add`를 한 번 더 합니다.
:::
:::

::: {.q}
동료가 새 커밋을 올렸다기에 `git fetch`를 했는데 내 폴더의 파일은 하나도 바뀌지 않았습니다. 고장일까요?

::: {.a}
정상입니다. `fetch`는 새 커밋을 내려받고 `origin/main` 이름표만 옮깁니다. 내 `main`과 작업 폴더는 건드리지 않습니다. 파일까지 바꾸려면 `git pull`로 합쳐야 합니다.
:::
:::

::: {.q}
어제 push한 커밋에 버그가 있어 취소하려 합니다. 동료들은 이미 그 커밋을 받아 갔습니다. `git reset --hard` 뒤 강제 push하는 방법과 `git revert` 중 무엇을 골라야 할까요?

::: {.a}
`git revert`입니다. 취소하는 새 커밋을 덧붙일 뿐이라 동료들의 이력과 어긋나지 않습니다. `reset`과 강제 push는 서버의 이력을 고쳐 쓰므로, 그 커밋 위에 작업하던 동료의 이력과 갈라집니다.
:::
:::

::: {.q}
API 키가 든 `.env`를 실수로 커밋하고 push했습니다. 뒤늦게 `.gitignore`에 `.env`를 적었습니다. 이것으로 충분할까요?

::: {.a}
충분하지 않습니다. `.gitignore`는 아직 커밋하지 않은 파일에만 통하므로 `.env`는 계속 관리되고, 지난 커밋에도 키가 그대로 남아 있습니다. 가장 먼저 할 일은 그 키를 폐기하고 새로 발급받는 것입니다.
:::
:::

::: {.q}
두 브랜치가 충돌 없이 병합됐는데, 게임을 실행하니 점프 높이가 이상합니다. 어떻게 이런 일이 생길까요?

::: {.a}
Git은 같은 줄이 겹쳤는지만 볼 뿐 코드의 뜻은 모릅니다. 한쪽이 값의 단위를 바꾸고 다른 쪽이 옛 단위를 믿고 새 코드를 썼다면, 충돌 없이 합쳐져도 동작은 어긋납니다. 그래서 병합한 뒤에는 테스트를 다시 돌립니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI 도구에게 커밋을 맡길 때는 **계획을 먼저 보여 주게 하고, 되돌릴 수 없는 명령은 금지**해 두세요.

> 지금 작업 폴더의 변경을 커밋하려고 해. 먼저 `git status`와 `git diff`를 읽고, 변경을 목적별로 묶어 어떤 커밋으로 나눌지 계획만 보여 줘. 내가 요청한 '착지 직후 점프 버그 수정'과 관계없는 변경은 따로 표시해. `.env`와 `build/`는 커밋에 넣지 마. `reset --hard`, `push --force`처럼 되돌릴 수 없는 명령은 내 확인 없이 실행하지 마. 내가 계획을 승인하면 커밋마다 `git diff --staged`를 보여 준 다음 커밋해.

**받은 답에서 확인할 것**: 요청과 관계없는 파일이 커밋에 섞이지 않았는가, 새로 만든 파일이 빠지지 않았는가, 커밋 메시지가 해결한 문제를 말하는가.
:::

## 용어 정리 {#terms}

::: {.terms}
버전 관리 (version control)
:   파일이 바뀐 이력을 기록해 비교하고 되돌릴 수 있게 하는 일.

저장소 (repository)
:   커밋이 모두 쌓여 있는 보관함. 프로젝트 폴더의 `.git` 안에 있다.

커밋 (commit)
:   그 순간 프로젝트 전체의 스냅샷. 작성자, 메시지, 부모 커밋을 함께 담는다.

작업 폴더 (working tree)
:   지금 눈에 보이고 편집하는 파일들.

스테이지 (staging area, index)
:   다음 커밋에 담을 내용을 올려 두는 곳.

diff (difference)
:   두 상태 사이에 사라진 줄과 생긴 줄을 보여 주는 비교.

브랜치 (branch)
:   커밋 하나를 가리키는 이름표. 커밋하면 앞으로 옮겨 간다.

HEAD
:   지금 쓰고 있는 브랜치를 가리키는 표시.

병합 (merge)
:   갈라진 두 흐름의 변경을 하나로 합치는 일.

충돌 (conflict)
:   같은 곳을 서로 다르게 고쳐 Git이 자동으로 합치지 못한 상태.

리베이스 (rebase)
:   내 커밋을 다른 커밋 위에 다시 적용해 새 커밋으로 만드는 일.

원격 저장소 (remote repository)
:   다른 곳(보통 서버)에 있는 같은 프로젝트의 저장소. 복제해 온 곳의 별명이 `origin`.

원격 추적 브랜치 (remote-tracking branch)
:   마지막으로 확인한 원격 브랜치의 위치를 적어 둔 이름표. `origin/main` 등.

풀 리퀘스트 (pull request)
:   내 브랜치의 변경을 검토한 뒤 합쳐 달라고 올리는 요청.

태그 (tag)
:   커밋에 붙이는 움직이지 않는 이름표. 버전 표시에 쓴다.
:::
