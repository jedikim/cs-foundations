::: {.lead}
컴퓨터가 느려지면 답답합니다. 그런데 왜 느려졌을까요? 컴퓨터 안에는 맡은 일이 서로 다른 부품들이 있습니다. 계산하는 부품, 일하는 동안 물건을 펼쳐 두는 부품, 오래 보관하는 부품입니다. 이 셋이 무슨 일을 하는지 알면 컴퓨터가 왜 느린지도 짐작할 수 있습니다.
:::

::: {.goals}
- CPU, 메모리, 저장장치가 각각 무슨 일을 하는지 말할 수 있습니다.
- 저장 공간이 남아도 컴퓨터가 느려질 수 있는 이유를 설명할 수 있습니다.
- 컴퓨터 사양표에 적힌 숫자가 무슨 뜻인지 읽을 수 있습니다.
- GPU가 무엇을 잘하는 부품인지 말할 수 있습니다.
:::

## 컴퓨터는 하나의 주방입니다 {#kitchen}

식당 주방을 떠올려 봅시다. **요리사**는 레시피를 한 줄씩 읽으며 손을 움직입니다. 요리사 앞에는 **조리대**가 있어서 지금 쓰는 재료와 그릇을 펼쳐 놓습니다. 주방 뒤편에는 **창고**가 있어서 당장 쓰지 않는 재료를 오래 보관합니다.

컴퓨터도 똑같이 세 주인공으로 이루어져 있습니다.

- **CPU**(중앙처리장치, Central Processing Unit)는 요리사입니다. 프로그램에 적힌 명령을 하나씩 읽고 계산합니다.
- **메모리**(RAM, Random Access Memory)는 조리대입니다. 지금 실행 중인 프로그램과 그 프로그램이 다루는 데이터를 올려 둡니다.
- **저장장치**(SSD나 하드디스크)는 창고입니다. 전원을 꺼도 파일을 그대로 보관합니다.

::: {.fig src="kitchen-map.svg"}
주방의 세 요소와 컴퓨터의 세 부품. 하는 일이 서로 다르기 때문에, 하나가 아무리 넉넉해도 다른 하나가 모자라면 전체가 느려집니다.
:::

이 비유 하나만 기억해도 많은 문제가 풀립니다. 창고가 아무리 커도 조리대가 좁으면 한 번에 펼칠 수 있는 요리 수는 늘지 않습니다. 마찬가지로 **SSD를 큰 것으로 바꿔도 동시에 띄울 수 있는 프로그램 수는 늘지 않습니다.** 그것은 메모리가 정하는 일이기 때문입니다.

::: {.photo src="pc-inside.jpg"}
데스크톱 본체의 옆판을 연 모습. 왼쪽 위의 커다란 은색 방열판 아래에 CPU가 있고, 그 오른쪽에 세로로 꽂힌 막대 네 개가 메모리입니다. 가운데에 가로로 꽂힌 판이 그래픽카드, 왼쪽 아래 상자가 전원 공급 장치입니다.
:::

::: {.note}
노트북과 스마트폰에도 같은 부품이 들어 있습니다. 다만 얇게 만들기 위해 여러 부품을 칩 하나에 모아 두었을 뿐입니다. 이런 칩을 **SoC**(System on a Chip)라고 부릅니다.
:::

## CPU: 명령을 하나씩 처리하는 요리사 {#cpu}

CPU가 하는 일은 놀랄 만큼 단순합니다. 아래 네 단계를 끝없이 되풀이할 뿐입니다.

::: {.fig src="cpu-cycle.svg"}
CPU의 기본 박자. 실제 CPU는 여러 명령을 겹쳐서 처리하는 등 훨씬 정교하지만, 큰 흐름은 이 네 단계입니다.
:::

예를 들어 `3 + 4`를 계산한다면 ① '더하기' 명령을 가져오고 ② 더할 값이 3과 4라는 것을 알아낸 뒤 ③ 덧셈 회로로 7을 구하고 ④ 그 7을 정해진 자리에 적어 둡니다. 그러고는 곧장 다음 명령으로 넘어갑니다.

CPU가 할 줄 아는 명령은 "더해라", "비교해라", "저쪽으로 옮겨라", "몇 번째 명령으로 건너뛰어라" 같은 아주 작은 것뿐입니다. 동영상 재생도, 게임도, AI도 결국 이런 작은 명령 수십억 개를 이어 붙인 결과입니다. 대신 CPU는 그 일을 **상상하기 어려울 만큼 빠르게** 합니다.

### 사양표의 GHz와 코어

- **클럭 속도(GHz)**는 요리사의 손놀림 박자입니다. 3GHz는 1초에 약 30억 번 박자를 친다는 뜻입니다.
- **코어**(core)는 요리사의 수입니다. 8코어 CPU에는 독립적으로 일하는 요리사가 8명 있습니다.

여기서 흔히 놓치는 점이 있습니다. 요리사가 8명이어도 **한 사람만 할 수 있게 짜인 레시피**라면 나머지 7명은 서서 구경만 합니다.

::: {.myth title="코어가 많으면 무조건 빠르다"}
프로그램이 일을 여러 갈래로 나눠 주지 않으면 코어 하나만 바쁩니다. 8코어 PC에서 코어 하나만 100%로 일하면 전체 CPU 사용률은 약 12.5%(= 1 ÷ 8)로 표시됩니다. "사용률이 12%밖에 안 되는데 왜 느리지?" 싶을 때는 **코어별 사용률**을 확인하세요. 일을 여러 코어로 나누는 방법은 [11장](ch11.html)에서 다룹니다.
:::

::: {.photo .half src="cpu-chip.jpg"}
CPU 칩의 아랫면. 금색 점 하나하나가 메인보드와 전기 신호를 주고받는 접점입니다. 손톱 몇 개 크기의 이 칩 안에 수십억 개의 스위치(트랜지스터)가 들어 있습니다.
:::

::: {.deep title="CPU마다 알아듣는 말이 다릅니다 (x86-64와 ARM64)"}
CPU가 알아듣는 명령의 목록과 규칙을 **명령어 집합**(ISA, Instruction Set Architecture)이라고 합니다. 요리사가 읽을 수 있는 레시피의 언어라고 생각하면 됩니다.

대부분의 윈도우 PC와 서버는 **x86-64**, 스마트폰과 최근의 맥은 **ARM64**라는 명령어 집합을 씁니다. 한국어 레시피를 프랑스 요리사에게 건네면 읽지 못하듯, x86-64용으로 만든 실행 파일은 ARM64 CPU에서 그대로 돌아가지 않습니다. 프로그램을 내려받을 때 "Intel용 / Apple Silicon용"을 고르는 이유가 이것입니다. 이 이야기는 [4장](ch04.html)에서 이어집니다.
:::

## 메모리(RAM): 지금 쓰는 것을 올려 두는 조리대 {#ram}

요리사는 창고에 있는 재료로 바로 요리하지 못합니다. 먼저 조리대로 꺼내 와야 합니다. CPU도 마찬가지여서, **저장장치에 있는 프로그램과 데이터는 메모리로 올라온 뒤에야 쓸 수 있습니다.**

메모리의 특징은 두 가지입니다.

1. **빠릅니다.** 요리사 손이 바로 닿는 곳이라 저장장치보다 수백~수천 배 빨리 꺼낼 수 있습니다.
2. **전원이 꺼지면 내용이 사라집니다.** 영업이 끝나면 조리대를 싹 치우는 것과 같습니다. 이런 성질을 **휘발성**이라고 합니다.

저장하지 않은 문서가 정전 한 번에 날아가는 이유가 여기에 있습니다. 화면에 보이던 글은 메모리(조리대) 위에만 있었고, 아직 저장장치(창고)에는 들어가지 않았던 것입니다.

::: {.photo src="ram-module.jpg"}
데스크톱용 메모리 모듈. 검은 칩 하나하나가 데이터를 담는 메모리 칩이고, 아래쪽 금색 단자를 메인보드의 슬롯에 꽂습니다.
:::

조리대가 좁으면 어떻게 될까요? 요리사는 재료를 창고에 도로 갖다 놓고, 필요할 때 다시 꺼내 오는 일을 반복해야 합니다. 컴퓨터도 메모리가 모자라면 당장 쓰지 않는 내용을 저장장치로 내보냈다가 다시 불러옵니다. 이때부터 모든 것이 눈에 띄게 굼떠집니다. 브라우저 탭을 수십 개 열었을 때 컴퓨터가 버벅거리는 전형적인 원인입니다.

::: {.key}
메모리 용량은 "얼마나 많이 보관하느냐"가 아니라 **"한 번에 얼마나 많이 펼쳐 놓고 일할 수 있느냐"**를 정합니다.
:::

## 저장장치: 전원을 꺼도 남는 창고 {#storage}

**저장장치**는 사진, 문서, 설치한 프로그램처럼 오래 두고 쓸 것을 **파일**로 보관합니다. 메모리보다 훨씬 크고 전원을 꺼도 내용이 남지만, 꺼내 오는 데 시간이 더 걸립니다.

::: {.photos}
::: {.photo src="ssd-nvme.jpg"}
**SSD.** 움직이는 부품 없이 반도체 칩에 전기로 기록합니다. 빠르고 조용합니다.
:::

::: {.photo src="hdd-open.jpg"}
**하드디스크(HDD).** 회전하는 원판 위를 바늘 같은 헤드가 오가며 읽고 씁니다. 느리지만 같은 값에 용량이 큽니다.
:::
:::

그렇다면 바탕화면의 아이콘을 더블클릭할 때 무슨 일이 벌어질까요?

::: {.fig src="load-run.svg"}
프로그램이 실행되는 길. 파일은 창고에 있다가 조리대로 올라온 뒤에야 요리사의 손에 닿습니다.
:::

1. **불러오기(로드).** 저장장치에 파일로 있던 프로그램을 메모리로 읽어 옵니다. 큰 게임을 켤 때 나오는 로딩 화면이 바로 이 과정입니다.
2. **실행.** CPU가 메모리에서 명령과 데이터를 꺼내 처리하고, 결과를 다시 메모리에 적습니다.
3. **저장.** 작업 결과는 저장하기 전까지 메모리에만 있습니다. 저장 버튼을 눌러야 저장장치의 파일로 기록됩니다.

::: {.note}
같은 프로그램이라도 **저장장치에 놓인 파일**과 **메모리에서 실행 중인 상태**는 전혀 다른 것입니다. 실행 중인 프로그램을 **프로세스**라고 부르는데, [3장](ch03.html)의 주인공입니다.
:::

## 왜 셋으로 나눴을까: 속도의 사다리 {#hierarchy}

하나로 합치면 편할 텐데 왜 굳이 메모리와 저장장치를 따로 둘까요? 답은 간단합니다. **빠른 것은 비싸고 작으며, 싼 것은 크고 느리기** 때문입니다. 그래서 컴퓨터는 빠르고 작은 것부터 느리고 큰 것까지를 사다리처럼 쌓아 두고 섞어 씁니다.

숫자만 봐서는 감이 오지 않으니, CPU 안에서 값 하나를 꺼내는 시간(약 1나노초)을 **1초**로 늘려서 비교해 보겠습니다.

::: {.fig src="speed-ladder.svg"}
속도의 사다리. 위로 갈수록 빠르고 작으며 비싸고, 아래로 갈수록 느리고 크며 쌉니다.
:::

CPU 입장에서 메모리는 "2분 걸리는 옆방", SSD는 "하루 걸리는 옆 도시", 바다 건너 서버는 "5년 걸리는 여행"입니다. 프로그램이 느릴 때 "지금 어디까지 다녀오고 있는가"를 먼저 묻는 이유가 이것입니다. 계산을 조금 줄이는 것보다 **먼 곳에 다녀오는 횟수를 줄이는 쪽**이 훨씬 큰 차이를 만듭니다.

### 캐시: 자주 쓰는 것은 손 닿는 곳에

사다리 맨 위에 있는 **캐시**(cache)는 CPU 안에 들어 있는 아주 작고 빠른 보관함입니다. 요리사가 소금과 후추를 창고가 아니라 손 옆 선반에 두는 것과 같습니다. 방금 쓴 것, 그리고 그 근처에 있던 것을 캐시에 미리 가져다 놓으면 대부분의 일을 "1초 거리"에서 끝낼 수 있습니다.

"가까이 있는 것을 자주 쓴다"는 이 아이디어는 CPU에만 있지 않습니다. 브라우저 캐시, 서버 캐시처럼 이 책 곳곳에서 같은 이름으로 다시 만나게 됩니다.

::: {.deep title="데이터를 나란히 놓으면 왜 빨라질까 (지역성)"}
CPU는 값 하나가 필요할 때 그 값만 달랑 가져오지 않고, **주변 값까지 한 묶음(보통 64바이트)**으로 캐시에 가져옵니다. 이 묶음을 캐시 라인이라고 합니다.

그래서 데이터가 메모리에 나란히 놓여 있으면 한 번 가져온 묶음으로 여러 개를 연달아 처리할 수 있습니다. 반대로 여기저기 흩어져 있으면 값을 볼 때마다 "2분 걸리는 옆방"에 다녀와야 합니다. 같은 개수의 데이터라도 **나란히 늘어선 배열**이 **이리저리 연결된 구조**보다 빠른 경우가 많은 이유입니다. 이렇게 가까운 것을 이어서 쓰는 성질을 **지역성**(locality)이라고 합니다. [8장](ch08.html)에서 자료구조를 고를 때 다시 나옵니다.
:::

## GPU: 같은 일을 수천 개 동시에 {#gpu}

화면에는 수백만 개의 점(픽셀)이 있고, 게임은 그 점 하나하나의 색을 1초에 60번 이상 새로 계산해야 합니다. 계산 하나하나는 단순하지만 양이 어마어마합니다. 이런 일을 위해 만든 부품이 **GPU**(그래픽처리장치, Graphics Processing Unit)입니다.

::: {.fig src="cpu-vs-gpu.svg"}
CPU는 솜씨 좋은 요리사 몇 명, GPU는 한 가지 동작만 하는 일꾼 수천 명에 가깝습니다.
:::

요리사 8명에게 감자 만 개를 깎게 하는 것보다, 감자 깎기만 할 줄 아는 일꾼 수천 명에게 하나씩 나눠 주는 편이 훨씬 빨리 끝납니다. 화면 그리기, 영상 처리, 그리고 AI 계산이 바로 이런 "똑같은 단순 계산을 엄청나게 많이" 하는 일입니다. AI 이야기에 GPU가 빠지지 않는 까닭입니다.

GPU는 자기만의 조리대인 **VRAM**(비디오 메모리)을 따로 가지고 있는 경우가 많습니다. 그래서 "RAM은 남는데 VRAM이 부족하다"는 상황이 얼마든지 생깁니다.

::: {.photo src="gpu-card.jpg"}
그래픽카드. 큰 팬 세 개 아래에 GPU 칩과 VRAM이 있습니다. 수천 개의 코어가 동시에 일하면 열이 많이 나기 때문에 냉각 장치가 본체보다 큽니다.
:::

::: {.warn title="GPU가 항상 빠른 것은 아닙니다"}
GPU에게 일을 시키려면 데이터를 메모리에서 VRAM으로 **옮겨 주고**, 결과를 다시 **받아 와야** 합니다. 계산할 양이 적으면 옮기는 시간이 계산 시간보다 길어집니다. 사진 한 장을 살짝 보정하는 일은 CPU가 더 빨리 끝낼 수 있습니다. 또한 조건에 따라 갈래가 복잡하게 나뉘는 일은 GPU에 잘 맞지 않습니다.
:::

## 부품을 잇는 길: 메인보드 {#board}

지금까지 만난 부품들은 **메인보드**(mainboard)라는 큰 기판에 꽂혀 서로 연결됩니다. 주방으로 치면 바닥과 통로입니다.

::: {.fig src="data-path.svg"}
부품 사이의 길. 모든 길의 넓이가 같지는 않습니다. CPU와 메모리 사이가 가장 넓고 빠릅니다.
:::

여기서 기억할 것은 하나입니다. **부품이 빨라도 길이 좁으면 소용없다**는 점입니다. 요리사 손이 아무리 빨라도 창고로 가는 통로가 한 사람만 겨우 지나갈 너비라면 재료가 제때 도착하지 못합니다. 이렇게 전체 속도를 붙잡는 가장 좁은 지점을 **병목**(bottleneck)이라고 합니다. 병의 목이 좁아서 물이 천천히 나오는 것에 빗댄 말입니다.

성능 문제를 푼다는 것은 대부분 **병목이 어디인지 찾는 일**입니다. 병목이 아닌 곳을 아무리 빠르게 만들어도 전체는 빨라지지 않습니다.

::: {.photo src="raspberry-pi.jpg"}
신용카드 크기의 컴퓨터 '라즈베리 파이'. 가운데 은색 칩이 CPU, 그 옆 검은 칩이 메모리입니다. 크기는 달라도 구성은 데스크톱과 같습니다.
:::

## 사양표를 증상과 연결하기 {#spec}

이제 컴퓨터 사양표의 숫자가 무슨 뜻인지 읽을 수 있습니다.

| 사양표의 표기 | 뜻 | 모자랄 때 나타나는 증상 |
|---|---|---|
| CPU 8코어 3.2GHz | 요리사 8명, 초당 32억 박자 | 계산이 오래 걸림, 팬 소리가 커짐 |
| RAM 16GB | 조리대 넓이 | 여러 프로그램을 띄우면 전체가 버벅임, 프로그램이 갑자기 꺼짐 |
| SSD 512GB | 창고 넓이 | "디스크 공간이 부족합니다", 파일을 저장하지 못함 |
| VRAM 8GB | GPU 전용 조리대 | 고해상도 게임이나 큰 AI 모델이 실행되지 않음 |

::: {.tip title="용량 단위 한눈에"}
1KB(킬로바이트)는 대략 글자 천 개, 1MB는 그 천 배, 1GB는 다시 그 천 배, 1TB는 또 그 천 배입니다. 사진 한 장이 몇 MB, 영화 한 편이 몇 GB쯤 됩니다. 바이트가 정확히 무엇인지는 바로 다음 [2장](ch02.html)에서 다룹니다.
:::

::: {.try}
지금 쓰는 컴퓨터에서 직접 확인해 보세요.

- **윈도우**: `Ctrl + Shift + Esc`로 작업 관리자를 열고 '성능' 탭을 봅니다.
- **맥**: '활성 상태 보기' 앱을 열고 CPU·메모리 탭을 봅니다.

브라우저 탭을 열 개쯤 더 열어 보면서 CPU, 메모리, 디스크 중 어느 숫자가 움직이는지 관찰해 보세요.
:::

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 메모리(RAM) / 저장장치 | 작업 중에 펼쳐 두는 곳 / 꺼도 남는 보관 장소 |
| 파일 크기 / 메모리 사용량 | 창고에서 차지하는 자리 / 펼쳐 놓았을 때 차지하는 자리. 서로 크게 다를 수 있음 |
| RAM / VRAM | CPU가 쓰는 조리대 / GPU가 쓰는 조리대 |
| 코어 수 / 클럭 속도 | 요리사의 수 / 요리사 한 명의 손 빠르기 |
| CPU / GPU | 복잡한 일을 차례로 / 단순한 일을 한꺼번에 |

## 실전 사례 {#case}

::: {.case title="저장 공간은 넉넉한데 '메모리 부족'으로 꺼지는 앱"}
사진 100장을 한꺼번에 불러와 크기를 줄여 주는 앱을 만들었습니다. 그런데 실행하면 얼마 못 가 꺼집니다. SSD에는 수백 GB가 남아 있습니다.

1. **파일 크기와 메모리 사용량을 구분합니다.** 사진 파일은 압축되어 있습니다. 20MB짜리 파일도 화면에 그릴 수 있게 압축을 풀면 200MB가 될 수 있습니다.
2. **복사본을 셉니다.** 원본, 편집용 복사본, 화면용 데이터가 동시에 살아 있으면 한 장이 600MB를 차지합니다.
3. **곱합니다.** 100장을 동시에 열면 60GB가 필요합니다. 16GB 메모리로는 감당할 수 없습니다.
4. **한 번에 펼치는 양을 줄입니다.** 네 장씩만 열어서 처리하고, 끝난 사진은 메모리에서 치운 뒤 다음 네 장을 엽니다.
5. **확인합니다.** 같은 100장을 다시 처리하면서 메모리 최고 사용량과 전체 걸린 시간을 기록해 비교합니다.

교훈은 조리대 비유 그대로입니다. 창고(SSD)가 아무리 넓어도 조리대(RAM)에 한꺼번에 다 펼칠 수는 없습니다.
:::

::: {.fig src="unpack-size.svg"}
파일로 있을 때의 크기와 실행 중에 차지하는 메모리는 다릅니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- **CPU**는 요리사입니다. 가져오기 → 해석 → 실행 → 기록을 1초에 수십억 번 반복합니다.
- **메모리(RAM)**는 조리대입니다. 빠르지만 전원이 꺼지면 비워집니다. 한 번에 펼칠 수 있는 양을 정합니다.
- **저장장치**는 창고입니다. 느리지만 크고, 꺼도 남습니다. 프로그램은 여기서 메모리로 올라온 뒤에야 실행됩니다.
- CPU에서 멀어질수록 느려집니다. 성능은 **먼 곳에 몇 번 다녀오느냐**에 크게 좌우됩니다.
- **GPU**는 단순한 계산을 한꺼번에 처리하는 일꾼 수천 명입니다. 데이터를 옮기는 비용이 따로 듭니다.
- 전체 속도는 가장 좁은 길인 **병목**이 정합니다.
:::

## 확인 문제 {#quiz}

::: {.q}
노트북의 SSD를 256GB에서 1TB로 바꿨습니다. 브라우저 탭을 많이 열면 느려지던 문제가 해결될까요?

::: {.a}
해결되지 않습니다. 탭을 많이 열 때 모자라는 것은 조리대인 메모리(RAM)입니다. SSD는 창고라서, 커져도 한 번에 펼칠 수 있는 양은 그대로입니다.
:::
:::

::: {.q}
문서를 쓰다가 저장하지 않은 채 정전이 됐습니다. 내용이 사라지는 이유를 부품 이름으로 설명해 보세요.

::: {.a}
작성 중인 내용은 메모리에만 있었습니다. 메모리는 전원이 끊기면 내용이 사라지는 휘발성 장치입니다. 저장 버튼을 눌러야 꺼져도 남는 저장장치에 파일로 기록됩니다.
:::
:::

::: {.q}
8코어 PC에서 프로그램이 한참 걸리는데 CPU 사용률은 13% 근처에 머뭅니다. 무엇을 의심할 수 있을까요?

::: {.a}
코어 하나만 일하고 있을 가능성이 큽니다(1 ÷ 8 = 12.5%). 프로그램이 일을 여러 코어로 나누도록 짜여 있지 않으면 나머지 코어는 놀게 됩니다. 코어별 사용률을 확인해 보면 알 수 있습니다.
:::
:::

::: {.q}
사진 한 장의 밝기를 조금 올리는 작업을 GPU로 옮겼더니 오히려 느려졌습니다. 왜 그럴 수 있을까요?

::: {.a}
GPU를 쓰려면 데이터를 VRAM으로 보내고 결과를 다시 받아 와야 합니다. 계산량이 적으면 이 왕복 시간이 계산 시간보다 길어집니다. GPU는 같은 계산을 아주 많이 할 때 이득을 봅니다.
:::
:::

::: {.q}
20MB짜리 사진 파일을 열었는데 메모리를 200MB나 씁니다. 버그일까요?

::: {.a}
버그가 아닐 가능성이 높습니다. 파일은 압축된 상태이고, 화면에 그리려면 압축을 풀어 픽셀 하나하나의 색을 메모리에 펼쳐야 합니다. 파일 크기와 메모리 사용량은 다른 숫자입니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI 코딩 도구에게 성능 문제를 맡길 때는 "느려요"라고만 하지 말고 **어느 부품이 모자라는지 측정부터** 하게 하세요.

> 사진 일괄 변환 기능이 중간에 꺼지는 원인을 조사해 줘. 대상 PC는 RAM 8GB, VRAM 4GB야. 먼저 사진 한 장을 처리할 때 압축 해제, 복사, GPU 전송 단계별로 메모리를 얼마나 쓰는지 측정해서 표로 보여 줘. 그다음 동시에 처리하는 장수를 제한하는 방법을 제안해 줘. 100장을 끝까지 처리하는 것, 그리고 변경 전후의 메모리 최고 사용량과 걸린 시간을 비교해 보여 주는 것을 완료 조건으로 해.

**받은 답에서 확인할 것**: RAM과 VRAM을 따로 측정했는가, 추측이 아니라 실제 측정값을 보여 주는가, 변경 전후를 같은 사진으로 비교했는가.
:::

## 용어 정리 {#terms}

::: {.terms}
CPU (Central Processing Unit)
:   중앙처리장치. 프로그램의 명령을 읽고 계산하는 부품.

코어 (core)
:   CPU 안에서 명령을 독립적으로 처리하는 단위. 요리사 한 명에 해당.

클럭 속도 (clock speed)
:   CPU가 1초에 치는 박자 수. 단위는 GHz(기가헤르츠, 초당 10억 번).

메모리 (RAM, Random Access Memory)
:   실행 중인 프로그램과 데이터를 올려 두는 작업 공간. 전원이 꺼지면 내용이 사라진다.

휘발성 (volatile)
:   전원이 끊기면 내용이 사라지는 성질.

저장장치 (storage)
:   전원을 꺼도 파일을 보관하는 부품. SSD, 하드디스크가 대표적.

SSD (Solid State Drive)
:   반도체 칩에 기록하는 저장장치. 움직이는 부품이 없어 빠르다.

캐시 (cache)
:   자주 쓰는 것을 더 빠른 곳에 미리 가져다 두는 보관함, 또는 그런 방법.

GPU (Graphics Processing Unit)
:   단순한 계산을 대량으로 동시에 처리하는 부품. 그래픽과 AI 계산에 쓰인다.

VRAM (Video RAM)
:   GPU가 쓰는 전용 메모리.

메인보드 (mainboard)
:   부품을 꽂고 서로 연결해 주는 기판. 마더보드라고도 한다.

병목 (bottleneck)
:   전체 속도를 붙잡고 있는 가장 느린 지점.

명령어 집합 (ISA, Instruction Set Architecture)
:   CPU가 알아듣는 명령의 목록과 규칙. x86-64, ARM64 등이 있다.

SoC (System on a Chip)
:   CPU, GPU, 메모리 제어 등 여러 기능을 하나로 합친 칩. 스마트폰과 얇은 노트북에 쓰인다.
:::
