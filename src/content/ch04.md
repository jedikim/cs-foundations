::: {.lead}
프로그램은 사람이 글로 씁니다. 이 글을 **코드**라고 합니다. 그런데 컴퓨터의 두뇌인 CPU는 사람의 글을 읽지 못합니다. 0과 1로 된 자기만의 말만 알아듣습니다. 그래서 사람이 쓴 코드를 CPU의 말로 옮겨 주는 '번역'이 필요합니다. 이 장에서는 코드가 번역되어 실제로 움직이기까지를 따라갑니다.
:::

::: {.goals}
- 사람이 쓴 코드가 실행되기까지 거치는 단계를 순서대로 말할 수 있습니다.
- 미리 한꺼번에 번역하는 방식과 그때그때 번역하는 방식의 차이를 설명할 수 있습니다.
- 오류가 번역할 때 난 것인지 실행하는 중에 난 것인지 구분할 수 있습니다.
- 같은 프로그램이 어떤 컴퓨터에서는 되고 다른 컴퓨터에서는 안 되는 이유를 짐작할 수 있습니다.
:::

## 요리사는 한 가지 말만 알아듣습니다 {#machine-code}

[1장](ch01.html)에서 CPU는 레시피를 한 줄씩 읽는 요리사였습니다. 그런데 이 요리사는 **자기 나라 말로 쓴, 아주 잘게 쪼갠 지시만** 알아듣습니다. "양파를 볶는다"는 못 알아듣고, "3번 통을 연다", "꺼낸 것을 팬에 붓는다", "불을 켠다"처럼 써 줘야 합니다.

CPU가 알아듣는 이 말을 **기계어**(machine code)라고 합니다. "이 값을 가져와라", "더해라", "저기에 적어라" 같은 작은 명령을 숫자로 적은 것입니다. 사람 눈에는 `10001101 01000100`처럼 0과 1이 늘어선 것으로만 보입니다.

::: {.photo src="eniac.jpg"}
1940년대의 컴퓨터 ENIAC. 왼쪽 벽면에 어지럽게 늘어진 전선을 보세요. 이 시절에는 전선을 바꿔 꽂고 스위치를 맞추는 일이 곧 프로그래밍이었습니다. 사람이 기계의 말에 맞춰야 했습니다.
:::

기계의 말을 사람이 직접 쓰기는 너무 힘들었습니다. 그래서 방법을 바꿨습니다. **사람이 읽기 쉬운 말로 먼저 쓰고, 기계어로 옮기는 일은 프로그램에게 시키기로** 한 것입니다. 사람이 읽고 쓰는 이 글을 **소스 코드**(source code)라고 합니다. Python이나 JavaScript 같은 프로그래밍 언어는 이 글을 쓰는 규칙입니다.

```python
total = price * 2 + 1
```

사람은 이 한 줄을 "가격을 두 배 하고 1을 더해 total에 넣어라"로 읽습니다. 하지만 CPU는 이 글을 한 글자도 이해하지 못합니다. 누군가 기계어로 옮겨 줘야 합니다.

::: {.fig src="translate-why.svg"}
레시피를 요리사의 말로 옮겨야 요리가 시작되듯, 소스 코드도 기계어로 옮겨야 CPU가 실행합니다. 이 장은 가운데 칸, 곧 '옮기는 일'을 다룹니다.
:::

::: {.photo .half src="hamilton-apollo-code.jpg"}
아폴로 우주선의 비행 소프트웨어 개발을 이끈 마거릿 해밀턴과, 그 소스 코드를 인쇄해 쌓은 종이 더미(1969년). 사람 키만 한 이 글이 번역을 거쳐 우주선의 컴퓨터에서 실행되었습니다.
:::

## 번역가와 통역사: 컴파일러와 인터프리터 {#two-ways}

한국어 레시피를 외국인 요리사에게 전하는 방법은 두 가지입니다.

- **번역가**에게 맡깁니다. 번역가는 레시피 책 전체를 미리 옮겨 번역본을 만들어 줍니다. 요리사는 번역본만 들고 혼자 요리합니다.
- **통역사**를 주방에 세웁니다. 통역사는 원문을 한 줄 읽고 그 자리에서 요리사에게 전한 뒤 다음 줄로 넘어갑니다.

프로그램을 실행하는 방법도 이 둘입니다.

**컴파일러**(compiler)는 번역가입니다. 소스 코드 전체를 미리 기계어로 옮겨 실행 파일을 만듭니다. 이렇게 옮기는 일을 **컴파일**이라고 합니다. C, C++, Rust, Go, Swift가 주로 이 방식을 씁니다.

**인터프리터**(interpreter)는 통역사입니다. 번역본을 따로 만들지 않고, 실행하는 그 순간에 소스 코드를 읽어 가며 그 뜻대로 움직입니다. Python, JavaScript, Ruby가 이 방식에서 출발했습니다.

::: {.fig src="two-ways.svg"}
가로 방향이 시간입니다. 컴파일러는 처음에 한 번 오래 기다리고, 인터프리터는 실행할 때마다 통역 시간을 다시 씁니다.
:::

| 비교할 점 | 컴파일러 (번역가) | 인터프리터 (통역사) |
|---|---|---|
| 시작하기까지 | 번역이 끝나야 실행 | 바로 실행 |
| 실행 속도 | 빠름 | 통역하는 만큼 느림 |
| 코드를 고치면 | 다시 번역해야 함 | 다시 실행만 하면 됨 |
| 실행할 컴퓨터에 필요한 것 | 번역본(실행 파일)만 | 통역사와 원문 |

표의 마지막 줄을 눈여겨보세요. Python으로 만든 프로그램을 남에게 주면 "먼저 Python을 설치하세요"라는 말이 따라붙습니다. 통역사가 그 주방에도 있어야 하기 때문입니다. 그리고 화면에 뜨는 "빌드 중…"은 번역가가 일하는 시간입니다.

::: {.note}
비유와 다른 점이 하나 있습니다. 통역사는 요리사에게 말을 전하지만, 인터프리터는 기계어를 만들어 CPU에 건네지 않습니다. 인터프리터 자신이 이미 기계어로 된 프로그램이어서, 소스 코드를 읽고 그 뜻에 해당하는 일을 직접 합니다.
:::

## 둘을 섞은 길: 바이트코드, 가상 머신, JIT {#bytecode}

번역본에는 약점이 있습니다. 요리사의 나라가 바뀌면 처음부터 다시 번역해야 합니다. 통역은 어디서나 통하지만 느립니다. 그래서 둘을 섞은 방법이 나왔습니다.

먼저 레시피를 어느 나라 말도 아닌 **간결한 공용 표기**로 한 번 옮겨 둡니다. "꺼냄: 양파 / 가열: 중불 3분"처럼 기계적으로 읽기 쉬운 표기입니다. 그리고 주방마다 이 표기를 읽어 주는 통역사를 둡니다. 원문을 통역할 때보다 훨씬 빠르고, 표기는 하나만 만들면 됩니다.

- 이 공용 표기가 **바이트코드**(bytecode)입니다. 진짜 CPU의 기계어는 아니지만 기계어처럼 작은 명령으로 되어 있습니다.
- 바이트코드를 읽어 실행하는 프로그램이 **가상 머신**(VM, virtual machine)입니다. 소프트웨어로 흉내 낸 CPU라고 생각하면 됩니다.

Java가 대표적입니다. Java 소스 코드를 컴파일하면 바이트코드가 나오고, 윈도우든 맥이든 **JVM**(Java 가상 머신)이 설치된 곳이면 그대로 실행됩니다.

::: {.fig src="bytecode-vm.svg"}
바이트코드는 한 번만 만들고, 가상 머신만 기기마다 따로 준비합니다.
:::

사실 Python도 소스 코드를 먼저 바이트코드로 옮긴 다음, 자기 안의 가상 머신으로 실행합니다. 프로젝트 폴더에 생기는 `__pycache__` 폴더의 `.pyc` 파일이 그 바이트코드를 저장해 둔 것입니다.

::: {.try}
Python이 설치되어 있다면 터미널에서 `python3`를 실행하고 아래 두 줄을 입력해 보세요.

```python
import dis
dis.dis("price * 2 + 1")
```

`LOAD_NAME`처럼 "price를 가져와라, 2를 가져와라, 곱해라"에 해당하는 바이트코드 명령이 한 줄씩 나옵니다. 명령 이름은 Python 버전마다 조금씩 다릅니다.
:::

### JIT: 자주 쓰는 대목은 아예 번역해 둔다

일 잘하는 통역사는 같은 문장이 수백 번 나오면 매번 새로 통역하지 않습니다. 요리사의 말로 옮긴 쪽지를 벽에 붙여 두고, 다음부터는 요리사가 쪽지를 직접 읽게 합니다.

이것이 **JIT 컴파일**(just-in-time compilation)입니다. 실행하는 도중에, 자주 실행되는 부분만 골라 기계어로 번역해 두는 방식입니다. 브라우저의 JavaScript 엔진과 JVM이 이렇게 합니다. 통역 방식에서 출발한 JavaScript가 꽤 빠른 까닭입니다.

대신 JIT에는 **예열 시간**이 있습니다. 처음에는 통역으로 느리게 돌다가, 자주 쓰이는 부분을 파악해 번역을 마친 뒤에야 빨라집니다. 서버를 막 켠 직후의 첫 요청 몇 개가 유독 느린 이유 가운데 하나입니다.

::: {.myth title="Python은 인터프리터 언어, Java는 컴파일 언어다"}
언어가 한쪽으로 정해져 있는 것은 아닙니다. 컴파일할지 통역할지는 그 언어를 **실행해 주는 프로그램**이 정하고, 요즘은 대부분 섞어 씁니다. "이 언어는 무슨 방식인가"보다 **"지금 내 코드는 어떤 단계를 거쳐 실행되는가"**를 묻는 편이 정확합니다.
:::

## 번역가의 작업 순서: 컴파일의 네 단계 {#stages}

번역가는 문장을 단번에 옮기지 않습니다. 낱말을 끊어 읽고, 문장 구조를 파악하고, 말이 되는지 따져 본 다음에야 옮겨 씁니다. 컴파일러도 네 단계를 거칩니다. `price * 2 + 1`을 따라가 봅시다.

::: {.fig src="compile-stages.svg"}
컴파일러의 네 단계. 앞의 세 단계는 '이해하기', 마지막 단계가 '옮겨 쓰기'입니다. 인터프리터도 앞의 단계들은 똑같이 거칩니다.
:::

1. **토큰 나누기.** 글자의 나열을 뜻이 있는 가장 작은 낱말로 자릅니다. 이 낱말을 **토큰**(token)이라고 합니다. `price`, `*`, `2`, `+`, `1` 다섯 개가 나옵니다.
2. **구조 세우기.** 토큰을 문법에 맞춰 묶습니다. 곱셈이 덧셈보다 먼저이므로 `price * 2`를 먼저 묶고, 그 결과에 `1`을 더하는 구조가 됩니다. 이 구조를 나무 모양으로 나타낸 것이 **구문 트리**(AST, abstract syntax tree)입니다.
3. **뜻 검사하기.** 구조가 맞아도 말이 안 될 수 있습니다. `price`라는 이름이 정말 있는지, 곱셈을 할 수 있는 종류의 값인지 확인합니다. 값의 종류를 **타입**(type)이라 하고, 이 확인을 **타입 검사**라고 합니다.
4. **기계어 쓰기.** 트리를 따라가며 CPU의 작은 명령으로 옮겨 적습니다.

### 구문 트리는 왜 중요할까

같은 낱말이라도 묶는 방법이 다르면 뜻이 달라집니다.

::: {.fig src="ast-compare.svg"}
트리는 아래쪽 가지부터 계산합니다. 괄호 하나가 트리의 모양을 바꾸고, 결과를 201에서 300으로 바꿉니다.
:::

컴파일러는 글자가 아니라 이 **트리**를 다룹니다. 코드 편집기의 '이름 바꾸기' 기능도 그렇습니다. 글자 찾아 바꾸기로 `price`를 `cost`로 바꾸면 `unit_price`까지 망가지지만, 트리를 이해하는 도구는 **그 변수를 가리키는 자리만** 바꿉니다. AI에게 이름 변경을 시킬 때도 "글자 치환 말고 편집기의 이름 바꾸기 기능을 써 줘"라고 하는 편이 안전합니다.

::: {.deep title="중간 표현(IR)과 트랜스파일"}
실제 컴파일러는 트리에서 곧장 기계어로 가지 않고, 그 사이에 **중간 표현**(IR, intermediate representation)을 둡니다. `t1 = price * 2`, `t2 = t1 + 1`처럼 계산을 한 걸음씩 풀어 쓴 형태입니다. 여러 언어가 같은 중간 표현으로 모이고, 거기서 여러 CPU용 기계어로 갈라질 수 있습니다. 바이트코드도 중간 표현의 한 종류입니다.

번역의 도착지가 기계어가 아니라 **다른 소스 코드**인 경우도 있습니다. 이를 **트랜스파일**(transpile)이라고 합니다. TypeScript가 대표적입니다. `let count: number = 3`을 트랜스파일하면 타입 표기 `: number`가 지워진 JavaScript 코드가 나옵니다. 타입 검사는 번역할 때만 하고, 실행할 때는 타입 표기가 남아 있지 않습니다.
:::

## 오류는 언제 드러날까 {#errors}

오류 메시지를 만나면 내용보다 먼저 **어느 단계에서 났는지**를 보세요. 고칠 곳이 완전히 달라집니다.

::: {.fig src="error-gates.svg"}
오류가 드러나는 시점. 왼쪽 두 가지는 실행 전에 걸러지고, 오른쪽은 실행해 봐야 압니다.
:::

**① 문법 오류.** 구조 세우기 단계에서 걸립니다. 괄호를 닫지 않았거나 따옴표의 짝이 맞지 않는 경우입니다. 트리를 세울 수 없으니 **그 파일은 한 줄도 실행되지 않습니다.** Python에서는 `SyntaxError`라고 나옵니다.

::: {.tip}
문법 오류가 가리키는 줄에 잘못이 안 보이면 **그 윗줄**을 보세요. 괄호를 닫지 않은 곳은 위인데, 번역가는 더 읽은 뒤에야 말이 안 된다는 것을 알아챕니다.
:::

**② 타입 오류.** 뜻 검사 단계에서 걸립니다. 숫자가 와야 할 자리에 글자가 온 경우입니다. 여기서 언어가 두 갈래로 나뉩니다.

- **정적 타입** 언어(TypeScript, Java, C, Rust, Go 등)는 실행 전에 타입을 검사합니다. 번역가가 책 전체를 미리 읽고 "이 문장은 말이 안 됩니다" 하며 돌려보내는 것입니다.
- **동적 타입** 언어(Python, JavaScript 등)는 실행하다가 그 줄에 닿았을 때 검사합니다. 통역사는 그 문장을 읽기 전에는 문제를 모릅니다.

```python
price = "100"
total = price * 2 + 1
```

첫 줄은 `price`에 숫자 100이 아니라 글자 `"100"`을 넣습니다. Python은 일단 실행을 시작하고, 둘째 줄에서 글자에 1을 더하려는 순간에야 `TypeError`로 멈춥니다. 그 줄이 사용자가 가끔 누르는 버튼 안에 있다면 오류는 몇 주 뒤에야 나타날 수도 있습니다.

**③ 실행 중 오류.** 문법도 타입도 맞지만 실제 값 때문에 생깁니다. `total / count`는 숫자끼리의 나눗셈이라 어떤 검사도 통과합니다. 그러나 `count`가 0인 날 프로그램은 멈춥니다. 없는 파일을 열 때, 네트워크가 끊겼을 때도 마찬가지입니다.

마지막으로, 아무 메시지 없이 **결과만 틀리는** 경우가 있습니다. `+ 1`을 `- 1`로 잘못 썼다면 어떤 단계도 이를 잡아내지 못합니다.

::: {.key}
"빌드에 성공했다"는 말은 **번역이 가능했다**는 뜻일 뿐, **프로그램이 올바르다**는 뜻이 아닙니다. AI가 "오류 없이 빌드됩니다"라고 보고해도, 실제로 실행해 결과를 확인하기 전에는 끝난 것이 아닙니다.
:::

## 링크: 남이 만든 코드와 이어 붙이기 {#link}

레시피에 "사골 육수를 붓는다"라고만 쓰여 있다고 합시다. 육수 내는 법은 이 레시피가 아니라 《육수 대백과》라는 다른 책에 있습니다. 번역가는 일단 "(육수 대백과의 사골 육수 참조)"라는 빈칸을 남긴 채 번역을 끝냅니다. 빈칸을 실제 쪽 번호로 채우는 일은 그다음 단계입니다.

프로그램도 모든 것을 직접 쓰지 않습니다. 이미지 파일을 여는 기능 같은 것은 남이 미리 만들어 둔 코드를 가져다 씁니다. 이렇게 가져다 쓰도록 묶어 둔 코드가 **라이브러리**(library)입니다.

컴파일러는 내 코드를 번역하면서 "여기서 `load_image`를 부름(위치는 아직 모름)"이라는 빈칸을 남깁니다. 이 빈칸들을 실제 코드의 위치로 채워 하나의 실행 파일로 묶는 일이 **링크**(link)이고, 그 일을 하는 프로그램이 **링커**(linker)입니다. 빈칸을 채울 코드를 끝내 찾지 못하면 **링크 오류**가 납니다.

```text
undefined reference to `load_image'
```

"`load_image`를 부르는 곳은 있는데 그 본체가 어디에도 없다"는 뜻입니다. 부르는 쪽의 문법을 고칠 일이 아닙니다. 그 함수가 들어 있는 파일이나 라이브러리가 **빌드에 포함되었는지**를 확인해야 합니다.

### 정적 링크와 동적 링크

라이브러리를 잇는 방법은 두 가지입니다.

::: {.fig src="link-static-dynamic.svg"}
정적 링크는 필요한 쪽을 복사해 함께 제본하고, 동적 링크는 "그 책을 보시오"라는 메모만 남깁니다.
:::

- **정적 링크**(static linking)는 라이브러리의 코드를 실행 파일 안에 복사해 넣습니다. 파일은 커지지만 어디에 가져가도 혼자 실행됩니다.
- **동적 링크**(dynamic linking)는 "실행할 때 이 라이브러리가 필요함"이라는 메모만 실행 파일에 남깁니다. 실제 연결은 프로그램을 켤 때 이루어집니다. 파일이 작고, 여러 프로그램이 라이브러리 하나를 함께 쓸 수 있습니다. 이런 라이브러리 파일의 확장자는 윈도우에서 `.dll`, 리눅스에서 `.so`, 맥에서 `.dylib`입니다.

대가도 분명합니다. **그 주방의 책장에 그 책이 없으면 요리를 시작조차 못 합니다.**

```text
error while loading shared libraries: libpng16.so.16:
cannot open shared object file: No such file or directory
```

윈도우의 "○○.dll을 찾을 수 없습니다"라는 오류 창도 같은 뜻입니다. 내 컴퓨터에는 개발하면서 설치해 둔 덕에 그 라이브러리가 있었고, 친구 컴퓨터에는 없는 것입니다. Python의 `ModuleNotFoundError`도 성격이 같습니다. 코드가 틀린 것이 아니라 **필요한 것이 그 자리에 없는** 오류입니다.

### 라이브러리 곁의 낱말들

- **API**(Application Programming Interface)는 라이브러리를 부르는 약속입니다. 함수의 이름, 넣을 값, 돌려받는 값을 정합니다. 《육수 대백과》의 차례에 해당합니다. 약속을 안다고 책이 내 책장에 있는 것은 아닙니다.
- **SDK**(Software Development Kit)는 특정 운영체제나 서비스에 맞춘 개발에 필요한 라이브러리, 도구, 문서를 묶은 꾸러미입니다. "안드로이드 SDK"처럼 무엇을 위한 것인지가 이름에 붙습니다.
- **의존성**(dependency)은 내 프로그램이 돌아가려면 꼭 있어야 하는 외부 코드입니다. 의존성이 또 다른 의존성을 끌고 와서 금세 수십 개로 불어납니다. 관리하는 방법은 [6장](ch06.html)에서 다룹니다.

::: {.deep title="ABI: 번역본끼리의 약속"}
API가 소스 코드 수준의 약속이라면, **ABI**(Application Binary Interface)는 **번역된 기계어끼리의 약속**입니다. 함수를 부를 때 값을 어느 자리에 놓고 건넬지, 결과는 어디로 돌려받을지, 숫자 하나가 몇 바이트를 차지하는지 같은 것들입니다. 이 가운데 값을 건네고 돌려받는 방법을 **호출 규약**(calling convention)이라고 합니다.

주방으로 치면 "재료는 왼쪽 선반에 놓고, 완성품은 오른쪽 창구로 내보낸다"는 동선 규칙입니다. 두 번역본의 규칙이 다르면 이름은 맞게 찾아도 엉뚱한 선반에서 재료를 집습니다. 링크에는 성공했는데 실행하면 이상한 값이 나오거나 갑자기 죽습니다. 다른 언어로 만든 라이브러리를 불러 쓸 때 주로 만납니다.
:::

## 실행 버튼을 누른 뒤: 로딩과 런타임 {#runtime}

실행 파일이 만들어졌다고 끝이 아닙니다. 아이콘을 더블클릭하면 운영체제가 다음 일을 합니다.

1. 실행 파일을 저장장치에서 메모리로 올립니다.
2. 실행 파일에 적힌 "필요한 라이브러리" 메모를 보고, 동적 라이브러리를 찾아 함께 올린 뒤 빈칸을 채웁니다.
3. 프로그램의 첫 명령으로 CPU를 보냅니다.

이 과정이 **로딩**(loading)입니다. [3장](ch03.html)에서 본 프로세스가 바로 이때 만들어집니다. 앞에서 본 "라이브러리를 찾을 수 없습니다" 오류는 2번에서 난 것입니다.

::: {.fig src="journey.svg"}
미리 컴파일하는 언어의 전체 여정. 앞의 두 단계는 개발자의 컴퓨터에서, 뒤의 두 단계는 사용자의 컴퓨터에서 일어납니다. 인터프리터 방식은 ①과 ②에 해당하는 일을 실행할 때로 미룹니다.
:::

### 런타임이라는 말의 두 가지 뜻

**런타임**(runtime)은 두 가지 뜻으로 쓰이므로 문맥으로 가려야 합니다.

첫째는 **시점**입니다. 프로그램이 실행되고 있는 동안을 가리킵니다. "런타임 오류"는 실행 중에 난 오류라는 말입니다. 반대말은 번역하는 시점인 **컴파일 타임**입니다.

둘째는 **실행을 곁에서 돕는 프로그램**입니다. 주방에는 다 쓴 그릇을 치우고, 사고가 나면 수습하고, 기본 도구를 건네주는 주방 보조가 필요합니다. 프로그램에도 실행되는 동안 다 쓴 메모리를 정리하고, 오류를 처리하고, 기본 기능을 제공해 주는 조력자가 필요합니다.

- Python 인터프리터, JavaScript를 실행하는 Node.js와 브라우저, Java의 JVM, C#의 .NET 런타임이 모두 여기에 듭니다. 통역사나 가상 머신이 주방 보조까지 겸하는 셈입니다.
- 미리 컴파일하는 C나 C++에도 작은 런타임 라이브러리가 있습니다. 윈도우의 "VCRUNTIME140.dll을 찾을 수 없습니다"는 C++ 런타임이 그 PC에 없다는 뜻입니다.

::: {.tip title="런타임에도 버전이 있습니다"}
"Node.js 20 이상 필요", "Python 3.11에서 동작"이라는 문구는 통역사의 버전을 지정한 것입니다. 옛 버전의 통역사는 새 문법을 알아듣지 못합니다. AI에게 코드를 부탁할 때는 **내가 쓰는 런타임과 버전**을 먼저 알려 주세요.
:::

## 같은 코드, 다른 결과물: 빌드 대상과 빌드 모드 {#build}

소스 코드, 라이브러리, 이미지 같은 재료를 모아 실행하거나 배포할 수 있는 결과물로 만드는 전체 과정을 **빌드**(build)라고 합니다. 컴파일과 링크가 빌드의 핵심 단계입니다. 그런데 같은 소스 코드라도 빌드 결과물은 하나가 아닙니다.

### 빌드 대상: 어느 주방, 어느 요리사를 위한 번역본인가

번역본은 특정 요리사와 특정 주방에 맞춰 만들어집니다.

- **CPU 종류.** [1장](ch01.html)에서 보았듯 x86-64 CPU와 ARM64 CPU는 알아듣는 기계어가 다릅니다.
- **운영체제.** 윈도우, 맥, 리눅스는 실행 파일의 형식이 서로 다릅니다. 파일을 열거나 화면을 그릴 때 운영체제에 부탁하는 방법도 다릅니다.

이 둘의 조합을 **빌드 대상**(build target) 또는 플랫폼이라고 합니다. 대상이 다르면 빌드도 따로 해야 합니다. 내려받기 페이지에 "Windows용", "Mac Apple Silicon용", "Mac Intel용"이 따로 있는 이유입니다.

::: {.fig src="build-targets.svg"}
소스 코드는 한 벌이지만 결과물은 대상마다 하나씩 나옵니다. 파일 이름은 설명을 위해 지은 것입니다.
:::

Python이나 JavaScript는 소스 코드를 그대로 가져가므로 이 문제에서 자유로워 보이지만, 절반만 맞습니다. 통역사(런타임) 자신이 대상마다 따로 빌드된 프로그램입니다. 또 속도를 위해 미리 컴파일한 부분을 품은 라이브러리가 많은데, 이 부분은 대상마다 다른 번역본이 필요합니다.

### 빌드 모드: 디버그와 릴리스

좋은 번역가는 직역만 하지 않습니다. "양파를 꺼낸다. 썬다. 양파를 또 꺼낸다. 또 썬다."를 "양파 두 개를 꺼내 한 번에 썬다"로 다듬습니다. 결과는 같고 동선은 짧아집니다. 컴파일러가 하는 이런 다듬기를 **최적화**(optimization)라고 합니다.

::: {.fig src="debug-release.svg"}
같은 세 줄을 두 가지 모드로 빌드한 모습. 최적화는 미리 계산할 수 있는 것을 계산해 두고, 쓰이지 않는 계산을 지웁니다.
:::

최적화를 거의 하지 않고 만든 결과물을 **디버그 빌드**, 최적화를 켜고 만든 결과물을 **릴리스 빌드**라고 합니다.

| 비교할 점 | 디버그 빌드 | 릴리스 빌드 |
|---|---|---|
| 실행 속도 | 느림 | 빠름 |
| 소스 코드와의 대응 | 줄마다 그대로 | 순서가 바뀌고 사라지기도 함 |
| 쓰는 때 | 개발하며 원인을 찾을 때 | 사용자에게 내보낼 때 |

디버그 빌드에는 보통 "기계어의 이 위치는 소스 코드의 몇 번째 줄"이라는 대응표인 **디버그 정보**도 들어갑니다. 덕분에 프로그램을 한 줄씩 멈춰 가며 살펴볼 수 있습니다. 이 방법은 [12장](ch12.html)에서 다룹니다.

::: {.warn title="성능은 릴리스 빌드에서 잽니다"}
디버그 빌드의 속도는 사용자가 겪을 속도가 아닙니다. 느리다고 곧장 코드를 뜯어고치지 말고 릴리스 빌드로 다시 재 보세요. 릴리스 빌드에서만 나타나는 버그도 있으므로, 내보내기 전의 마지막 확인도 릴리스 빌드로 합니다.
:::

빌드를 자동으로 되풀이하는 방법은 [20장](ch20.html)에서 다룹니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 컴파일러 / 인터프리터 | 미리 통째로 번역해 둠 / 실행하면서 그때그때 옮김 |
| 컴파일 타임 / 런타임 | 번역하는 시점 / 실행 중인 시점 |
| 컴파일 오류 / 링크 오류 | 내 코드의 문법이나 타입이 틀림 / 불러 쓸 코드의 본체를 못 찾음 |
| 정적 링크 / 동적 링크 | 라이브러리를 실행 파일에 넣어 둠 / 실행할 때 찾아서 이음 |
| 라이브러리 / API | 가져다 쓰는 코드 실물 / 그 코드를 부르는 약속 |

## 실전 사례 {#case}

::: {.case title="내 맥에서는 되던 프로그램이 서버에서는 켜지지도 않는다"}
사진 크기를 줄여 주는 Python 프로그램을 AI와 함께 만들었습니다. 내 맥북에서는 잘 돌았는데, 리눅스 서버에 폴더째 복사해 실행하니 시작하자마자 오류를 내고 꺼집니다.

1. **오류 메시지에서 단계를 가립니다.** 문법 오류도 계산 중의 오류도 아닙니다. 이미지 라이브러리를 불러오는 `import` 줄에서 멈췄습니다. 필요한 것을 **불러오지 못한** 오류입니다.
2. **두 컴퓨터의 빌드 대상을 비교합니다.** 터미널에서 `uname -sm`을 실행하니 맥북은 `Darwin arm64`, 서버는 `Linux x86_64`입니다. 운영체제도 CPU도 다릅니다.
3. **복사해 온 폴더 속의 번역본을 의심합니다.** 이미지 라이브러리는 속도를 위해 미리 컴파일한 부분을 품고 있습니다. 프로젝트 안의 라이브러리 폴더에는 맥에서 설치한 맥, ARM64용 번역본이 들어 있었고, 그것까지 통째로 서버에 복사한 것입니다.
4. **대상 컴퓨터에서 다시 설치합니다.** 복사해 온 라이브러리 폴더를 지우고, 서버에서 의존성을 새로 설치해 리눅스, x86-64용 번역본을 받습니다.
5. **확인합니다.** 설치부터 실행까지 다시 해 보고, 사진 한 장이 실제로 변환되는지 봅니다.

소스 코드는 어디든 가져갈 수 있지만 **번역본은 대상을 가립니다.** "내 컴퓨터에서는 되는데"라는 말이 나오면 코드보다 먼저 운영체제, CPU, 런타임 버전, 설치된 라이브러리를 비교하세요.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- CPU는 **기계어**만 실행합니다. 사람이 쓴 **소스 코드**는 반드시 번역을 거칩니다.
- **컴파일러**는 미리 통째로 번역하는 번역가, **인터프리터**는 실행하면서 옮기는 통역사입니다. **바이트코드**와 **JIT**는 둘을 섞은 방식입니다.
- 컴파일은 토큰 나누기 → 구문 트리 세우기 → 뜻 검사 → 기계어 쓰기 순서로 진행됩니다.
- 오류는 **어느 단계에서 났는지**부터 가립니다. 문법, 타입, 링크, 로딩, 실행 중 오류는 고칠 곳이 서로 다릅니다.
- **링크**는 내 코드와 라이브러리를 잇는 일입니다. 동적 링크한 라이브러리와 **런타임**은 실행하는 컴퓨터에도 있어야 합니다.
- 번역본은 **빌드 대상**(운영체제와 CPU)마다 따로 만들고, 성능은 **릴리스 빌드**에서 잽니다.
:::

## 확인 문제 {#quiz}

::: {.q}
200줄짜리 Python 파일의 150번째 줄에 닫지 않은 괄호가 있습니다. 이 파일을 실행하면 10번째 줄의 `print`는 출력될까요?

::: {.a}
출력되지 않습니다. 문법 오류는 실행 전에 파일 전체의 구조를 세우는 단계에서 걸립니다. 트리를 만들지 못했으므로 한 줄도 실행되지 않습니다.
:::
:::

::: {.q}
C 프로그램을 빌드하는데 컴파일은 끝났고 마지막에 ``undefined reference to `resize'``라는 오류가 났습니다. AI가 `resize`를 부르는 줄의 문법을 계속 고치고 있습니다. 방향이 맞을까요?

::: {.a}
맞지 않습니다. 이것은 링크 오류입니다. 부르는 쪽의 문법은 이미 통과했고, `resize`의 본체를 찾지 못한 것입니다. 그 함수가 든 파일이나 라이브러리가 빌드에 포함되었는지 확인해야 합니다.
:::
:::

::: {.q}
직접 만든 윈도우 프로그램을 친구에게 보냈더니 "○○.dll을 찾을 수 없습니다"라며 실행되지 않습니다. 내 PC에서는 잘 됩니다. 원인과 해결 방법을 말해 보세요.

::: {.a}
동적 링크한 라이브러리가 친구 PC에 없습니다. 내 PC에는 개발 도구와 함께 설치되어 있었던 것입니다. 그 라이브러리나 런타임을 함께 배포하거나, 정적 링크로 실행 파일 안에 넣습니다.
:::
:::

::: {.q}
게임을 디버그 빌드로 실행했더니 화면이 1초에 25번밖에 갱신되지 않습니다. 곧바로 코드를 뜯어고쳐야 할까요?

::: {.a}
먼저 릴리스 빌드로 다시 재야 합니다. 디버그 빌드는 최적화를 거의 하지 않아 느린 것이 정상입니다. 사용자가 겪는 속도는 릴리스 빌드의 속도입니다.
:::
:::

::: {.q}
AI 코딩 도구가 "타입 오류 0건, 빌드 성공"이라고 보고했습니다. 장바구니 합계 기능이 올바르게 동작한다고 믿어도 될까요?

::: {.a}
아직 믿을 수 없습니다. 빌드 성공은 문법과 타입이 맞아 번역이 가능했다는 뜻입니다. 0으로 나누는 경우나 더하기를 빼기로 쓴 실수는 어떤 검사도 통과합니다. 실제 값으로 실행해 결과를 확인해야 합니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
빌드 오류나 실행 오류를 고쳐 달라고 할 때는 오류 전문과 함께 **실행 환경**을 알려 주고, 고치기 전에 **어느 단계의 오류인지부터** 말하게 하세요.

> 아래 오류를 고쳐 줘. 먼저 이 오류가 문법, 타입 검사, 링크, 라이브러리 로딩, 실행 중 가운데 어느 단계에서 났는지와 그렇게 판단한 근거를 말해 줘. 실행 환경은 Ubuntu 22.04, x86-64, Python 3.11이야. 타입 검사를 끄거나 오류를 무시하는 방법은 쓰지 마. 고친 다음에는 새로 만든 환경에서 설치부터 실행까지 다시 해 보고, 사용한 명령과 출력 결과를 보여 줘.

**받은 답에서 확인할 것**: 단계 분류가 오류 메시지와 맞는가, 검사를 꺼서 오류만 안 보이게 하지 않았는가, 내가 알려 준 환경에서 실제로 실행했는가, "빌드 성공"이 아니라 **실행 결과**를 보여 주는가.
:::

## 용어 정리 {#terms}

::: {.terms}
소스 코드 (source code)
:   사람이 프로그래밍 언어로 읽고 쓰는 프로그램의 원문.

기계어 (machine code)
:   CPU가 직접 실행하는 명령을 숫자로 적은 것. CPU 종류마다 다르다.

컴파일러 (compiler)
:   소스 코드를 실행 전에 통째로 기계어 등으로 번역하는 프로그램.

인터프리터 (interpreter)
:   번역본을 만들지 않고, 실행하면서 코드를 읽어 그 뜻대로 움직이는 프로그램.

바이트코드 (bytecode)
:   어느 CPU의 기계어도 아닌 중간 표기. 가상 머신이 읽어 실행한다.

가상 머신 (VM, virtual machine)
:   바이트코드를 실행하는 프로그램. 소프트웨어로 흉내 낸 CPU.

JIT 컴파일 (just-in-time compilation)
:   실행하는 도중에 자주 쓰이는 부분을 기계어로 번역해 두는 방식.

구문 트리 (AST, abstract syntax tree)
:   코드의 낱말이 어떻게 묶이는지를 나무 모양으로 나타낸 구조.

타입 검사 (type checking)
:   값의 종류(타입)가 그 자리에 맞는지 확인하는 일.

라이브러리 (library)
:   가져다 쓰도록 미리 만들어 묶어 둔 코드.

링크 (link)
:   번역된 코드 조각과 라이브러리를 이어 하나의 실행 파일로 묶는 일.

동적 링크 (dynamic linking)
:   라이브러리를 실행 파일에 넣지 않고 실행할 때 찾아 잇는 방식. 미리 넣어 두면 정적 링크.

런타임 (runtime)
:   프로그램이 실행 중인 시점. 또는 실행을 곁에서 돕는 프로그램.

빌드 대상 (build target)
:   결과물이 실행될 운영체제와 CPU의 조합.

API (Application Programming Interface)
:   코드의 기능을 부르는 약속. 이름, 넣을 값, 돌려받는 값을 정한다.

의존성 (dependency)
:   내 프로그램이 동작하려면 있어야 하는 외부 코드.
:::
