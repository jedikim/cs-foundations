::: {.lead}
프로그램은 사람이 글로 씁니다. 이 글을 **코드**라고 합니다. 그런데 컴퓨터의 두뇌인 CPU는 사람의 글을 읽지 못합니다. 0과 1로 된 자기만의 말만 알아듣습니다. 그래서 사람이 쓴 코드를 CPU의 말로 옮겨 주는 '번역'이 필요합니다. 이 장에서는 코드가 번역되어 실제로 움직이기까지를 따라갑니다.
:::

::: {.goals}
- 사람이 쓴 코드가 실행되기까지 거치는 단계를 순서대로 말할 수 있습니다.
- 미리 한꺼번에 번역하는 방식과 그때그때 번역하는 방식의 차이를 설명할 수 있습니다.
- 오류가 번역할 때 난 것인지 실행하는 중에 난 것인지 구분할 수 있습니다.
- 같은 프로그램이 어떤 컴퓨터에서는 되고 다른 컴퓨터에서는 안 되는 이유를 짐작할 수 있습니다.
- AI가 "빌드해야 한다", "버전이 맞지 않는다"고 할 때 무슨 말인지 알아들을 수 있습니다.
:::

## 요리사는 한 가지 말만 알아듣습니다 {#machine-code}

[1장](ch01.html)에서 CPU는 레시피를 한 줄씩 읽는 요리사였습니다. 그런데 이 요리사는 까다롭습니다. 자기 나라 말로, 그것도 아주 잘게 쪼개 준 지시만 알아듣습니다.

"라면을 끓인다"라고 쓰면 못 알아듣습니다. "냄비를 꺼낸다", "물을 붓는다", "불을 켠다"처럼 한 동작씩 써 줘야 합니다.

CPU도 똑같습니다. "이 값을 가져와라", "더해라", "저기에 적어라" 같은 작은 명령만 알아듣습니다. 게다가 이 명령은 글자가 아니라 숫자로 적혀 있습니다. 사람 눈에는 `10001101 01000100`처럼 0과 1이 늘어선 것으로만 보입니다. CPU가 알아듣는 이 말을 **기계어**(machine code)라고 합니다.

::: {.photo src="eniac.jpg"}
1940년대의 컴퓨터 에니악(ENIAC)입니다. 왼쪽 벽에 어지럽게 늘어진 전선을 보세요. 이때는 전선을 바꿔 꽂고 스위치를 맞추는 일이 곧 프로그램을 짜는 일이었습니다.
:::

0과 1을 사람이 직접 쓰기는 너무 힘듭니다. 그래서 방법을 바꿨습니다. **사람이 읽기 쉬운 말로 먼저 쓰고, 기계어로 옮기는 일은 프로그램에게 시키기로** 했습니다.

사람이 읽고 쓰는 이 글을 **소스 코드**(source code)라고 합니다. 앞에서 코드라고 부른 것의 정식 이름입니다. 소스 코드를 쓰는 규칙이 프로그래밍 언어입니다.

아래는 **파이썬**(Python)이라는 프로그래밍 언어로 쓴 코드 한 줄입니다. 코드를 처음 본다면 [초코딩 기초](code.html)를 먼저 봐도 좋습니다.

```python
total = price * 2 + 1
```

게임 상점에서 물약을 산다고 생각해 봅시다. 물약 2개를 사고 수수료 1골드를 더 냅니다.

- `price`는 영어로 '값'입니다. 물약 하나의 값에 붙인 이름입니다.
- `*`는 곱하기, `+`는 더하기입니다.
- `=`는 "오른쪽을 계산해서 왼쪽 이름에 담아라"라는 뜻입니다. `total`은 '합계'입니다.

이 줄은 "값을 두 배 하고 1을 더해서 `total`에 담아라"입니다. 물약이 100골드라면 `total`은 201이 됩니다.

하지만 CPU는 이 글을 한 글자도 알아듣지 못합니다. 누군가 기계어로 옮겨 줘야 합니다.

::: {.fig src="translate-why.svg"}
레시피를 요리사의 말로 옮겨야 요리를 시작할 수 있습니다. 소스 코드도 기계어로 옮겨야 CPU가 실행합니다. 가운데 칸의 '옮기는 일'을 지금부터 살펴봅니다.
:::

::: {.photo .half src="hamilton-apollo-code.jpg"}
달에 간 아폴로 우주선의 프로그램을 만드는 일을 이끈 마거릿 해밀턴입니다(1969년). 옆에 쌓인 종이는 그 소스 코드를 찍은 것입니다. 사람 키만 한 이 글이 번역을 거쳐 우주선의 컴퓨터에서 실행되었습니다.
:::

## 번역가와 통역사: 컴파일러와 인터프리터 {#two-ways}

한국어 레시피를 외국인 요리사에게 전하는 방법은 두 가지입니다.

- **번역가**에게 맡깁니다. 번역가는 레시피 책을 통째로 미리 옮겨서 번역본을 만들어 줍니다. 요리사는 번역본만 들고 혼자 요리합니다.
- **통역사**를 주방에 세웁니다. 통역사는 레시피를 한 줄 읽고 그 자리에서 요리사에게 말해 줍니다. 그리고 다음 줄로 넘어갑니다.

프로그램을 실행하는 방법도 이 둘입니다.

첫째는 번역가 방식입니다. 소스 코드 전체를 미리 기계어로 옮겨 둡니다. 이렇게 옮기는 일을 컴파일이라고 합니다. 컴파일을 하는 프로그램이 **컴파일러**(compiler)입니다.

번역해서 나온 파일은 **실행 파일**입니다. 기계어가 들어 있어서 CPU가 바로 실행할 수 있습니다. 윈도우에서 이름이 `.exe`로 끝나는 파일이 실행 파일입니다. C나 C++ 같은 언어가 주로 이 방식을 씁니다.

둘째는 통역사 방식입니다. 번역본을 따로 만들지 않습니다. 실행하는 그 순간에 소스 코드를 한 줄씩 읽으면서 그 뜻대로 움직입니다. 이 일을 하는 프로그램을 **인터프리터**(interpreter)라고 합니다. 파이썬이 이 방식에서 출발했습니다. 웹 페이지를 움직이게 하는 언어인 자바스크립트(JavaScript)도 그렇습니다.

::: {.fig src="two-ways.svg"}
가로 방향이 시간입니다. 컴파일러는 처음에 한 번 오래 기다립니다. 인터프리터는 바로 시작하지만 실행할 때마다 통역 시간을 다시 씁니다.
:::

| 비교할 점 | 컴파일러 (번역가) | 인터프리터 (통역사) |
|---|---|---|
| 시작하기까지 | 번역이 끝나야 실행 | 바로 실행 |
| 실행 속도 | 빠름 | 통역하는 만큼 느림 |
| 코드를 고치면 | 다시 번역해야 함 | 다시 실행만 하면 됨 |
| 실행할 컴퓨터에 필요한 것 | 번역본(실행 파일)만 | 통역사와 소스 코드 |

표의 마지막 줄을 눈여겨보세요. 파이썬으로 만든 프로그램을 친구에게 주면 "먼저 파이썬을 설치해"라는 말이 따라붙습니다. 통역사가 친구의 주방에도 있어야 하기 때문입니다.

## 둘을 섞은 길: 바이트코드와 가상 머신 {#bytecode}

두 방식에는 저마다 약점이 있습니다.

번역본은 요리사의 나라가 바뀌면 쓸 수 없습니다. 처음부터 다시 번역해야 합니다. CPU도 종류마다 알아듣는 기계어가 다릅니다. 윈도우 PC에 많이 들어가는 x86-64와, 스마트폰과 요즘 맥에 들어가는 ARM64가 대표입니다. 한쪽을 위해 번역한 것은 다른 쪽에서 그대로 실행되지 않습니다.

통역은 어디서나 통합니다. 대신 느립니다.

그래서 둘을 섞은 방법이 나왔습니다. 레시피를 어느 나라 말도 아닌, 모두가 함께 쓰는 **공용 표기**로 한 번 옮겨 둡니다. "꺼냄: 양파 / 가열: 중불 3분" 같은 식입니다. 그리고 주방마다 이 표기를 읽어 주는 통역사를 둡니다. 표기는 짧고 규칙이 뚜렷해서 통역이 훨씬 빠릅니다. 옮긴 것은 한 벌만 있으면 됩니다.

이 공용 표기가 **바이트코드**(bytecode)입니다. 소스 코드와 기계어의 중간쯤에 있습니다. 진짜 CPU의 기계어는 아니지만, 기계어처럼 작은 명령으로 이루어져 있습니다.

바이트코드를 읽어서 실행하는 프로그램은 **가상 머신**(virtual machine)입니다. 프로그램으로 흉내 낸 CPU라고 생각하면 됩니다.

::: {.fig src="bytecode-vm.svg"}
바이트코드는 한 번만 만듭니다. 가상 머신만 컴퓨터 종류마다 따로 준비합니다.
:::

**자바**(Java)라는 언어가 이 방식의 대표입니다. 자바 소스 코드를 컴파일하면 이름이 `.class`로 끝나는 바이트코드 파일이 나옵니다. 윈도우든 맥이든 리눅스든 자바 가상 머신이 깔려 있으면 이 파일이 그대로 실행됩니다.

게임 마인크래프트의 '자바 에디션'은 이름처럼 자바로 만들었습니다. 그래서 세 운영체제에서 모두 할 수 있습니다.

파이썬도 사실 같은 일을 합니다. 소스 코드를 먼저 바이트코드로 옮기고, 자기 안의 가상 머신으로 실행합니다. 파이썬이 만들어 두는 `.pyc` 파일이 그 바이트코드입니다.

::: {.myth title="파이썬은 통역하는 언어, 자바는 번역하는 언어다"}
언어가 한쪽으로 딱 정해져 있지는 않습니다. 번역할지 통역할지는 그 언어를 **실행해 주는 프로그램**이 정합니다. 요즘은 대부분 섞어 씁니다.
:::

## 번역가의 작업 순서: 컴파일의 네 단계 {#stages}

영어 문장을 우리말로 옮길 때를 떠올려 봅시다. 단번에 옮겨지지 않습니다. 먼저 낱말로 끊어 읽습니다. 어느 낱말끼리 묶이는지 봅니다. 말이 되는지 따져 봅니다. 그런 다음에야 우리말로 옮겨 씁니다.

컴파일러도 똑같이 네 단계를 거칩니다. 앞에서 본 `price * 2 + 1`을 따라가 봅시다.

::: {.fig src="compile-stages.svg"}
앞의 세 단계는 '이해하기', 마지막 단계가 '옮겨 쓰기'입니다. 파이썬 같은 인터프리터도 실행하기 전에 1번과 2번은 똑같이 거칩니다.
:::

1. **토큰 나누기.** 죽 이어진 글자를 뜻이 있는 가장 작은 낱말로 자릅니다. 이 낱말 하나하나를 **토큰**(token)이라고 합니다. 여기서는 `price`, `*`, `2`, `+`, `1` 다섯 개가 나옵니다.
2. **구조 세우기.** 어느 토큰끼리 먼저 묶이는지 정합니다. 수학 시간에 배운 대로 곱셈이 덧셈보다 먼저입니다. 그래서 `price * 2`를 먼저 묶고, 그 결과에 `1`을 더합니다. 이 묶음을 나뭇가지 모양으로 그린 것이 **구문 트리**(AST, abstract syntax tree)입니다.
3. **뜻 검사하기.** 모양이 맞아도 말이 안 될 수 있습니다. `price`라는 이름이 정말 있는지 확인합니다. 그 값이 곱셈을 할 수 있는 종류인지도 확인합니다. 숫자인지 글자인지 같은 값의 종류를 **타입**(type)이라고 합니다. 그래서 이 확인을 타입 검사라고 부릅니다.
4. **기계어 쓰기.** 트리를 따라가며 CPU의 작은 명령으로 옮겨 적습니다. "`price`를 가져와라, 2를 곱해라, 1을 더해라"가 됩니다.

### 괄호 하나가 트리를 바꿉니다

같은 낱말이라도 묶는 방법이 다르면 뜻이 달라집니다. 물약이 100골드일 때를 봅시다.

- `price * 2 + 1`은 곱하기가 먼저입니다. 100 × 2 = 200이고, 200 + 1 = 201입니다.
- `price * (2 + 1)`은 괄호 안이 먼저입니다. 2 + 1 = 3이고, 100 × 3 = 300입니다.

::: {.fig src="ast-compare.svg"}
트리는 아래쪽 가지부터 계산합니다. 괄호 하나가 답을 201에서 300으로 바꿉니다.
:::

컴퓨터는 이렇게 트리를 먼저 세우고, 트리를 보고 계산합니다.

## 오류는 언제 드러날까 {#errors}

편지를 번역가에게 맡겼다고 합시다. 짝이 안 맞는 따옴표나 말이 안 되는 문장은 번역가가 옮기다가 찾아냅니다. 하지만 "토요일에 운동장에서 만나자"라고 썼는데 그날 비가 올지는 번역가도 모릅니다. 그날이 되어 봐야 압니다.

프로그램의 오류도 그렇습니다. 실행하기 전에 걸러지는 오류가 있고, 실행해 봐야 드러나는 오류가 있습니다. 오류를 알리는 글을 만나면 **어느 단계에서 났는지**부터 보세요. 고칠 곳이 달라집니다.

::: {.fig src="error-gates.svg"}
왼쪽 두 가지 오류는 실행하기 전에 걸러지고, 오른쪽은 실행해 봐야 압니다. 아래의 점선 화살표는 파이썬 같은 언어에서는 타입 오류도 실행 중에야 드러난다는 표시입니다.
:::

**① 문법 오류.** 구조 세우기 단계에서 걸립니다. 괄호를 닫지 않았거나 따옴표의 짝이 맞지 않는 경우입니다. `(price * 2 + 1`처럼 쓰면 트리를 세울 수 없습니다. 그러면 **그 파일은 한 줄도 실행되지 않습니다.** 파이썬은 이때 `SyntaxError`라고 알려 줍니다. '문법 오류'라는 뜻입니다.

**② 타입 오류.** 뜻 검사하기 단계에서 걸립니다. 숫자가 와야 할 자리에 글자가 온 경우입니다. 파이썬 코드로 적으면 이렇습니다.

```python
price = "100"
total = price * 2 + 1
```

- 첫 줄은 `price`에 `"100"`을 담습니다. 따옴표로 감싸면 숫자 100이 아니라 글자로 다룹니다.
- 둘째 줄은 앞에서 본 계산입니다. 그런데 글자에 숫자 1을 더할 수는 없습니다.

이 오류가 언제 드러나는지는 언어마다 다릅니다.

- 자바나 C 같은 언어는 **실행하기 전에** 타입을 검사합니다. 번역가가 책 전체를 미리 읽고 "이 문장은 말이 안 됩니다" 하며 돌려보내는 것과 같습니다. 이런 언어를 **정적 타입**(static typing) 언어라고 합니다.
- 파이썬 같은 언어는 **실행하다가 그 줄에 닿았을 때** 검사합니다. 통역사는 그 문장을 읽기 전에는 문제를 모릅니다. 이런 언어를 **동적 타입**(dynamic typing) 언어라고 합니다.

정적은 '멈춰 있는', 동적은 '움직이는'이라는 뜻입니다. 프로그램이 멈춰 있을 때 검사하느냐, 움직이는 중에 검사하느냐로 붙인 이름입니다.

파이썬은 동적 타입 언어라서 위 코드를 일단 실행하기 시작합니다. 둘째 줄에서 글자에 1을 더하려는 순간에야 `TypeError`(타입 오류)를 내고 멈춥니다. 그 줄이 게임의 마지막 보스 방에서만 실행된다면 어떨까요? 거기까지 가 본 사람만 오류를 만납니다. 정적 타입 언어였다면 이 실수는 게임을 실행해 보기도 전에 걸러졌을 것입니다.

**③ 실행 중 오류.** 문법도 타입도 맞는데, 그때 들어온 값 때문에 생깁니다. `total / count`를 봅시다. `/`는 나누기입니다. 반 간식비 `total`을 모인 사람 수 `count`로 나누는 계산입니다. 숫자끼리의 나눗셈이니 어떤 검사도 통과합니다. 그런데 아무도 오지 않아 `count`가 0인 날, 파이썬은 `ZeroDivisionError`(0으로 나눈 오류)를 내고 멈춥니다. 0으로는 나눌 수 없기 때문입니다.

마지막으로, 아무 말 없이 **답만 틀리는** 경우가 있습니다. `+ 1`을 `- 1`로 잘못 썼다면 어떤 단계도 잡아내지 못합니다.

::: {.key}
"오류 없이 번역됐다"는 말은 **옮길 수 있었다**는 뜻일 뿐입니다. **프로그램이 맞게 움직인다**는 뜻이 아닙니다. AI가 "오류 없이 만들어졌습니다"라고 알려 와도 아직 끝난 것이 아닙니다. 실제로 실행해서 결과를 눈으로 확인하세요.
:::

### 자바스크립트와 타입스크립트

자바스크립트도 동적 타입 언어입니다. 게다가 타입이 맞지 않아도 멈추지 않고 넘어갈 때가 많습니다. `"100" + 1`은 오류를 내지 않습니다. 글자를 이어 붙인 `"1001"`이 됩니다. 화면의 입력 칸에 적은 숫자는 글자로 들어옵니다. 그래서 AI가 만든 계산기에서 100 + 1이 1001로 나오는 일이 실제로 생깁니다.

이 약점을 메우려고 만든 언어가 **타입스크립트**(TypeScript)입니다. 자바스크립트에 타입 표시를 덧붙여 씁니다. `let price: number = 100`이라고 쓰면 `price`라는 이름에 100을 담습니다. 가운데의 `: number`가 "여기에는 숫자만 담는다"는 표시입니다.

다음 줄에서 이 `price`에 글자 `"100"`을 담으려 하면, 타입스크립트는 실행하기 전에 이렇게 알려 줍니다.

```text
shop.ts:2:1 - error TS2322: Type 'string' is not assignable to type 'number'.
```

"글자(string)는 숫자(number) 자리에 담을 수 없다"는 말입니다. 맨 앞은 `shop.ts` 파일의 둘째 줄 첫 글자라는 뜻입니다.

브라우저는 타입스크립트를 알아듣지 못합니다. 그래서 검사가 끝나면 타입 표시를 지운 자바스크립트 코드로 바꿉니다. 실제로 실행되는 것은 이 자바스크립트입니다. 이렇게 소스 코드를 **다른 언어의 소스 코드로** 옮기는 일을 **트랜스파일**(transpile)이라고 합니다.

### 오류 글에서 종류 알아보기

오류가 어느 종류인지는 화면에 뜬 글에 적혀 있습니다. 앞에서 본 파이썬 타입 오류 코드 두 줄 위에 `print("게임 시작!")`을 한 줄 더 넣어 봅시다. `print`는 화면에 글자를 찍으라는 명령입니다. 실행하면 이렇게 나옵니다.

```text
게임 시작!
Traceback (most recent call last):
  File "C:\game\shop.py", line 3, in <module>
    total = price * 2 + 1
            ~~~~~~~~~~^~~
TypeError: can only concatenate str (not "int") to str
```

- **맨 아래 줄이 결론입니다.** 쌍점(`:`) 앞의 `TypeError`가 오류의 종류이고, 뒤는 까닭입니다. "글자(str)에는 글자만 이어 붙일 수 있다. 숫자(int)는 안 된다"는 말입니다.
- `line 3`은 `shop.py` 파일의 셋째 줄에서 멈췄다는 뜻입니다. 그 아래의 `^` 표시가 문제가 된 `+`를 가리킵니다.
- 맨 위에 `게임 시작!`이 찍혀 있습니다. 앞의 줄들은 실행됐으니, 실행 중에 드러난 오류입니다.

종류를 알리는 낱말은 몇 개만 알아도 됩니다.

| 오류 글에 보이는 낱말 | 뜻 | 드러나는 때 |
|---|---|---|
| `SyntaxError` | 문법이 틀렸다 | 실행 전. 한 줄도 실행되지 않음 |
| `error TS`와 숫자 | 타입스크립트가 찾은 타입 오류 | 실행 전 |
| `TypeError` | 값의 종류가 그 자리에 맞지 않는다 | 실행 중, 그 줄에서 |
| `NameError`, `ReferenceError` | 그런 이름이 없다. 오타일 때가 많다 | 실행 중, 그 줄에서 |
| `ZeroDivisionError` | 0으로 나눴다 | 실행 중, 그런 값이 들어온 때만 |

오류 글을 더 꼼꼼히 읽는 법은 [초코딩 기초](code.html#error)와 [12장](ch12.html)에 있습니다.

::: {.try}
AI 챗봇에게 이렇게 부탁해 보세요. "문법 오류, 타입 오류, 실행 중 오류가 나는 파이썬 코드를 하나씩 보여 줘. 어느 것이 어느 오류인지는 말하지 말고, 실행하면 나오는 오류 글만 보여 줘." 오류 글의 맨 아래 줄만 보고 종류를 맞혀 본 다음, 답을 물어보세요.
:::

## 링크: 남이 만든 코드와 이어 붙이기 {#link}

레시피에 "사골 육수를 붓는다"라고만 쓰여 있다고 합시다. 육수 내는 법은 이 레시피에 없고, 《육수 대백과》라는 다른 책에 있습니다. 번역가는 일단 "(육수 대백과를 볼 것)"이라는 빈칸을 남기고 번역을 끝냅니다. 빈칸에 실제 쪽 번호를 채우는 일은 그다음입니다.

프로그램도 모든 것을 직접 쓰지 않습니다. 그림 파일을 여는 기능 같은 것은 남이 미리 만들어 둔 코드를 가져다 씁니다. 이렇게 가져다 쓰라고 묶어 둔 코드를 **라이브러리**(library)라고 합니다. 예를 들어 `libpng`는 PNG 그림 파일을 읽는 라이브러리입니다.

컴파일러는 내 코드를 번역하면서 빈칸을 남깁니다. "여기서 그림 여는 기능을 부름(어디 있는지는 아직 모름)" 같은 빈칸입니다. 이 빈칸을 실제 코드가 있는 자리로 채웁니다. 그리고 모두 이어서 실행 파일 하나로 묶습니다. 이 일이 **링크**(link)입니다.

링크는 컴파일러가 아닌 **링커**(linker)라는 프로그램이 맡습니다.

빈칸을 채울 코드를 끝내 못 찾으면 링커가 링크 오류를 냅니다. "부르는 곳은 있는데 불러올 것이 어디에도 없다"는 뜻입니다. 이때는 부르는 줄을 고칠 일이 아닙니다. 필요한 라이브러리를 **빠뜨리지 않았는지** 확인해야 합니다. 오류 글에 linker라는 낱말이 보이면 이 단계에서 난 오류입니다.

### 정적 링크와 동적 링크

라이브러리를 잇는 방법은 두 가지입니다.

::: {.fig src="link-static-dynamic.svg"}
정적 링크는 필요한 쪽을 복사해 한 권으로 묶습니다. 동적 링크는 "그 책을 보시오"라는 메모만 남깁니다.
:::

- 라이브러리의 코드를 실행 파일 안에 복사해 넣는 방법이 있습니다. **정적 링크**(static linking)라고 합니다. 파일은 커집니다. 대신 어디에 가져가도 혼자 실행됩니다.
- "실행할 때 이 라이브러리가 필요함"이라는 메모만 남기는 방법도 있습니다. **동적 링크**(dynamic linking)라고 합니다. 진짜 연결은 프로그램을 켤 때 합니다. 파일이 작고, 여러 프로그램이 라이브러리 하나를 함께 쓸 수 있습니다. 윈도우에서는 이런 라이브러리 파일의 이름이 `.dll`로 끝납니다.

동적 링크에는 대가가 있습니다. **그 주방의 책장에 그 책이 없으면 요리를 시작도 못 합니다.**

게임을 새로 깔고 켰는데 "○○.dll을 찾을 수 없습니다"라는 창이 뜨는 일이 있습니다. 게임을 만든 사람의 컴퓨터에는 그 라이브러리가 있었고, 내 컴퓨터에는 없는 것입니다. 코드가 틀린 것이 아닙니다. **필요한 것이 그 자리에 없는** 오류입니다.

파이썬에서 자주 만나는 `ModuleNotFoundError`도 같은 종류입니다. 가져다 쓰려는 라이브러리를 내 컴퓨터에서 찾지 못했다는 뜻입니다. 자바스크립트에서는 `Cannot find module`이라는 글로 나옵니다. 둘 다 대개는 코드를 고칠 일이 아니라 라이브러리를 설치할 일입니다.

이렇게 내 프로그램이 돌아가려면 꼭 있어야 하는 남의 코드를 **의존성**(dependency)이라고 합니다. 의존성을 챙기는 방법은 [6장](ch06.html)에서 다룹니다.

### 라이브러리를 부르는 약속: API와 SDK

분식집에 가면 메뉴판이 있습니다. 손님은 주방에서 떡볶이를 어떻게 만드는지 몰라도 됩니다. 메뉴판에 적힌 이름대로 주문하면 음식이 나옵니다.

라이브러리에도 이런 메뉴판이 있습니다. 어떤 기능이 있는지, 부를 때 무엇을 건네야 하는지, 무엇을 돌려받는지 정해 둔 약속입니다. 이 약속을 **API**(Application Programming Interface)라고 합니다.

API는 약속일 뿐 라이브러리 자체가 아닙니다. 메뉴판을 외웠다고 떡볶이가 내 앞에 놓이지는 않습니다. 라이브러리는 따로 챙겨야 합니다.

인터넷 너머에 있는 다른 컴퓨터에 일을 부탁하는 약속도 API라고 부릅니다. "날씨 API"라고 하면 날씨 정보를 받아 오는 방법을 정해 둔 것입니다.

과학 시간에 받는 실험 꾸러미에는 재료, 도구, 설명서가 한 상자에 들어 있습니다. 프로그램을 만들 때도 이런 꾸러미를 받아 씁니다. 어떤 운영체제나 서비스에 맞는 프로그램을 만들 때 쓰라고 라이브러리, 도구, 설명서를 묶어 둔 것입니다. 이 꾸러미를 **SDK**(Software Development Kit)라고 합니다. '안드로이드 SDK'처럼 무엇을 위한 꾸러미인지가 이름 앞에 붙습니다.

### 메뉴판에 없는 메뉴: AI가 지어낸 기능

AI는 가끔 메뉴판에 없는 메뉴를 주문하는 코드를 씁니다. 있을 법한 이름을 지어내기도 하고, 라이브러리의 옛 버전에만 있던 이름을 쓰기도 합니다([27장](ch27.html)). 그러면 실행하다가 그 줄에서 이런 글이 뜹니다. 첫 줄은 파이썬, 둘째 줄은 자바스크립트의 오류 글입니다.

```text
AttributeError: module 'random' has no attribute 'pick'
TypeError: cards.shuffle is not a function
```

- `has no attribute`는 "그런 것은 갖고 있지 않다"는 말입니다.
- `is not a function`은 "그것은 부를 수 있는 기능(함수)이 아니다"라는 말입니다. 자바스크립트는 이 오류에도 `TypeError`라는 이름을 붙이니, 뒤의 설명까지 읽어야 합니다.

둘 다 **부른 기능이 거기에 없다**는 뜻입니다. 이 글을 만나면 AI에게 오류 글 전체와 라이브러리의 버전을 주세요. 그리고 **그 기능이 정말 있는지 공식 문서에서 확인하게** 하세요. 공식 문서는 라이브러리를 만든 곳이 올려 둔 설명서입니다. 타입스크립트를 쓰면 이런 실수도 대개 실행하기 전에 걸러집니다.

## 실행 버튼을 누른 뒤: 로딩과 런타임 {#runtime}

실행 파일이 생겼다고 끝이 아닙니다. 게임 아이콘을 두 번 누르면 [3장](ch03.html)의 지배인, 운영체제가 다음 일을 합니다.

1. 실행 파일을 저장장치에서 메모리로 올립니다. 창고에 있던 것을 조리대에 펼치는 일입니다.
2. 실행 파일에 적힌 "필요한 라이브러리" 메모를 봅니다. 그 라이브러리를 찾아 함께 올리고 빈칸을 채웁니다.
3. CPU에게 프로그램의 첫 명령부터 읽게 합니다.

이 과정이 **로딩**(loading)입니다. 3장에서 본 프로세스가 이때 만들어집니다. 앞에서 본 "○○.dll을 찾을 수 없습니다"는 2번에서 난 오류입니다.

이제 처음부터 끝까지 이어 봅시다. 소스 코드를 실행 파일로 만드는 과정 전체를 **빌드**(build)라고 합니다. 컴파일과 링크가 빌드의 큰 두 단계입니다.

::: {.fig src="journey.svg"}
미리 컴파일하는 언어가 거치는 길입니다. 앞의 두 단계는 만드는 사람(개발자)의 컴퓨터에서 일어납니다. 뒤의 두 단계는 쓰는 사람(사용자)의 컴퓨터에서 일어납니다. 인터프리터 방식은 ①과 ②에 해당하는 일을 실행할 때로 미룹니다.
:::

### 런타임이라는 말의 두 가지 뜻

그림 아래쪽에 **런타임**(runtime)이라는 낱말이 있습니다. 이 말은 두 가지 뜻으로 쓰입니다.

첫째는 **때**입니다. 프로그램이 실행되고 있는 동안을 가리킵니다. "런타임 오류"는 실행 중에 난 오류라는 말입니다. 반대로 번역하는 때는 컴파일 타임이라고 합니다.

둘째는 **실행을 곁에서 돕는 프로그램**입니다. 주방 보조는 다 쓴 그릇을 치우고 기본 도구를 건네줍니다. 프로그램에도 이런 도우미가 필요합니다. 다 쓴 메모리를 치우고, 오류를 처리하고, 기본 기능을 내어 줍니다.

- 파이썬 인터프리터, 자바 가상 머신, 자바스크립트를 실행하는 웹 브라우저가 모두 런타임입니다. 통역사가 주방 보조까지 겸하는 셈입니다.
- 자바스크립트를 브라우저 밖에서 실행해 주는 런타임도 있습니다. **Node.js**가 대표입니다.
- 미리 컴파일하는 C나 C++에도 작은 런타임 라이브러리가 있습니다. 윈도우의 "VCRUNTIME140.dll을 찾을 수 없습니다"는 C++ 런타임이 그 컴퓨터에 없다는 뜻입니다.

AI가 만들어 준 파일을 실행할 때는 이 런타임에게 파일을 건넵니다. 터미널(글자로 명령을 치는 창, [5장](ch05.html))에 `python3 game.py`나 `node game.js`라고 치는 것이 그 일입니다. "파이썬아, `game.py`를 읽어서 실행해 줘"라는 뜻입니다.

### AI가 자주 고르는 세 언어

AI에게 무엇을 만들어 달라고 하면 언어는 AI가 고릅니다. 자주 고르는 셋은 이렇게 다릅니다.

| 언어 | 파일 이름의 끝 | 실행해 주는 런타임 | 주로 쓰이는 곳 |
|---|---|---|---|
| 파이썬 | `.py` | 파이썬 인터프리터 | 파일 정리, 계산, AI 다루기 |
| 자바스크립트 | `.js` | 웹 브라우저, Node.js | 웹 페이지, 웹 앱 |
| 타입스크립트 | `.ts`, `.tsx` | 자바스크립트로 바꾼 뒤 위와 같음 | 조금 큰 웹 앱 |

웹 브라우저가 바로 실행하는 언어는 자바스크립트입니다. 그래서 브라우저에서 여는 앱, 곧 웹 앱은 자바스크립트나 타입스크립트로 만듭니다.

어느 언어가 좋은지 몰라도 괜찮습니다. 대신 AI에게 두 가지를 물어보세요. 무슨 언어와 런타임을 골랐는지, 실행하려면 내 컴퓨터에 무엇을 깔아야 하는지입니다. 이미 만들던 것이 있다면 "지금 쓰는 언어 그대로 해 줘"라고 말해 주세요.

### 런타임에도 버전이 있습니다

프로그램 설명에 "파이썬 3.11 이상 필요"라고 적혀 있을 때가 있습니다. 통역사의 버전을 정해 둔 것입니다. 옛 버전의 통역사는 새로 생긴 문법과 기능을 모릅니다. 그래서 멀쩡한 코드인데 `SyntaxError`가 나거나, 있는 기능인데 "그런 기능은 없다"는 오류가 납니다.

AI는 내 컴퓨터에 어떤 버전이 깔려 있는지 모릅니다. 너무 새로운 문법을 쓰기도 하고, 지금은 없어진 옛 사용법을 쓰기도 합니다. 그러니 코드를 부탁할 때 **내가 쓰는 런타임과 버전**을 먼저 알려 주세요. 터미널에 `python3 --version`이나 `node -v`를 치면 `Python 3.12.2`, `v22.22.0`처럼 버전이 나옵니다([6장](ch06.html)).

## 같은 코드, 다른 결과물: 빌드 대상과 빌드 모드 {#build}

게임이나 프로그램을 내려받는 곳에 가면 "Windows용", "Mac용" 버튼이 따로 있습니다. 같은 프로그램인데 왜 파일이 여러 개일까요? 같은 소스 코드로 빌드해도 결과물은 하나가 아니기 때문입니다.

### 빌드 대상: 누구를 위한 번역본인가

번역본은 정해진 요리사와 정해진 주방에 맞춰 만듭니다.

- **CPU 종류.** x86-64 CPU와 ARM64 CPU는 알아듣는 기계어가 다릅니다.
- **운영체제.** 윈도우, 맥, 리눅스는 실행 파일의 모양도, 운영체제에 일을 부탁하는 방법도 서로 다릅니다.

이 둘을 짝지은 것을 **빌드 대상**(build target)이라고 합니다. 대상이 다르면 빌드도 따로 해야 합니다. CPU 2가지에 운영체제 3가지면 2 × 3 = 6, 번역본이 여섯 개 나옵니다.

::: {.fig src="build-targets.svg"}
소스 코드는 한 벌이지만 결과물은 대상마다 하나씩 나옵니다. 파일 이름의 win, mac, linux는 운영체제입니다. x64(x86-64)와 arm64는 CPU 종류입니다. 설명하려고 지은 이름입니다.
:::

빌드 대상은 흔히 **플랫폼**(platform)이라고도 부릅니다. 게임 소개에 "지원 플랫폼: 윈도우, 맥"이라고 적혀 있다면, 윈도우용과 맥용을 따로 빌드해 두었다는 뜻입니다.

파이썬 같은 통역 방식도 예외가 아닙니다. 통역사(런타임) 자신이 대상마다 따로 빌드된 프로그램입니다. 그 컴퓨터에 맞는 통역사를 깔아야 합니다.

::: {.try}
자주 쓰는 프로그램의 내려받기 페이지에서 버튼이 몇 가지로 나뉘어 있는지 세어 보세요. 맥용은 "Apple Silicon"과 "Intel"로 나뉘기도 합니다. 앞의 것이 ARM64, 뒤의 것이 x86-64입니다.
:::

### 빌드 모드: 디버그와 릴리스

좋은 번역가는 글자 그대로만 옮기지 않습니다. "양파를 꺼낸다. 썬다. 양파를 또 꺼낸다. 또 썬다."를 "양파 두 개를 꺼내 한 번에 썬다"로 다듬습니다. 결과는 같고 움직임은 줄어듭니다. 컴파일러가 하는 이런 다듬기를 **최적화**(optimization)라고 합니다.

::: {.fig src="debug-release.svg"}
같은 세 줄을 두 가지 방법으로 빌드한 모습입니다. 가운데가 소스 코드이고, 왼쪽과 오른쪽이 결과물입니다.
:::

소스 코드 세 줄의 뜻은 이렇습니다.

- `r = 2 * 3`은 2 × 3을 계산해 `r`에 담습니다.
- `tmp = price * 100`은 값에 100을 곱해 `tmp`에 담습니다. 그런데 `tmp`는 그 뒤로 아무 데도 쓰이지 않습니다.
- `total = price * r + 1`은 값에 `r`을 곱하고 1을 더합니다.

최적화를 켜면 컴파일러는 2 × 3을 미리 계산해 6으로 적어 둡니다. 쓰이지 않는 둘째 줄은 지웁니다. 남는 일은 "값 × 6 + 1" 하나뿐입니다.

프로그램 속의 잘못을 버그, 버그를 찾아 고치는 일을 디버그(debug)라고 합니다.

버그를 찾을 때는 소스 코드와 줄마다 딱 맞는 결과물이 편합니다. 그래서 최적화를 거의 하지 않고 빌드합니다. 이것이 **디버그 빌드**입니다. 프로그램을 한 줄씩 멈춰 가며 살펴보기에도 좋습니다([12장](ch12.html)).

다 만든 프로그램을 사람들에게 내보낼 때는 빨라야 합니다. 그래서 최적화를 켜고 빌드합니다. 이것이 **릴리스 빌드**입니다. 릴리스(release)는 '내보낸다'는 뜻입니다.

디버그로 빌드할지 릴리스로 빌드할지를 빌드 모드라고 합니다. 프로그램을 만드는 도구에는 흔히 Debug와 Release 가운데 하나를 고르는 칸이 있습니다. 만드는 동안에는 Debug로 두고, 내보낼 때 Release로 바꿉니다.

::: {.warn title="속도는 릴리스 빌드에서 잽니다"}
직접 만든 게임이 디버그 빌드에서 뚝뚝 끊긴다고 곧장 코드를 뜯어고치지 마세요. 사용자가 겪을 속도가 아닙니다. 릴리스 빌드로 다시 재 보세요. 릴리스 빌드에서만 나타나는 버그도 있으니, 내보내기 전의 마지막 확인도 릴리스 빌드로 합니다.
:::

### 웹 앱에서 말하는 빌드

AI와 웹 앱을 만들다 보면 "빌드해야 합니다", "빌드가 실패했습니다"라는 말을 자주 듣습니다. 웹 앱에는 `.exe` 같은 실행 파일이 없는데 무엇을 만든다는 말일까요?

여기서 빌드는 **고치기 좋게 나눠 둔 소스 파일을 브라우저에 보낼 결과물로 바꾸는 일**입니다.

::: {.fig src="web-build.svg"}
`shop.ts`, `cart.ts`처럼 나뉜 소스 파일이 세 단계를 지나 결과물이 됩니다. 1번에서 타입 오류가 나오면 결과물은 만들어지지 않습니다.
:::

타입을 검사하고, 타입스크립트를 자바스크립트로 옮기고, 여러 파일을 몇 개로 묶어 작게 줄입니다. 결과물은 흔히 `dist`나 `build`라는 폴더에 담깁니다. 이 폴더의 파일은 직접 고치지 않습니다. 다음에 빌드하면 덮어써져 사라지기 때문입니다.

자바스크립트로 만드는 앱에서는 `npm`이라는 도구([6장](ch06.html))로 흔히 두 명령을 씁니다. 명령 이름은 앱마다 다를 수 있습니다.

- `npm run dev`는 만드는 동안 씁니다. 내 컴퓨터에 개발 서버를 켭니다. 개발 서버는 코드를 고칠 때마다 화면에 바로 보여 주는 프로그램입니다([31장](ch31.html#local)).
- `npm run build`는 인터넷에 올리기 전에 씁니다. 그림의 세 단계를 거쳐 결과물을 만듭니다.

`npm run dev`로 볼 때는 잘 되던 앱이 `npm run build`에서 멈추는 일이 흔합니다. 개발 서버는 빨리 보여 주려고 타입 검사를 건너뛸 때가 많기 때문입니다. AI가 "다 만들었습니다"라고 하면 **빌드도 통과했는지** 물어보세요. 인터넷에 올리는 일은 [20장](ch20.html)에서 다룹니다.

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 컴파일러 / 인터프리터 | 미리 통째로 번역해 둠 / 실행하면서 그때그때 옮김 |
| 문법 오류 / 실행 중 오류 | 실행 전에 걸러져 한 줄도 실행되지 않음 / 실행하다가 그 줄에서 멈춤 |
| 컴파일 타임 / 런타임 | 번역하는 때 / 실행하고 있는 때 |
| 정적 타입 / 동적 타입 | 실행하기 전에 타입을 검사함 / 실행하다가 그 줄에서 검사함 |
| 정적 링크 / 동적 링크 | 라이브러리를 실행 파일 안에 넣어 둠 / 실행할 때 찾아서 이음 |
| 라이브러리 / API | 가져다 쓰는 코드 그 자체 / 그 코드를 부르는 약속 |
| 디버그 빌드 / 릴리스 빌드 | 버그를 찾기 좋게 그대로 옮김 / 빠르게 다듬어 내보냄 |

## 실전 사례 {#case}

::: {.case title="내 컴퓨터에서는 되던 게임이 친구 컴퓨터에서는 켜지지 않는다"}
방학 동안 AI와 함께 작은 게임을 만들었습니다. 내 윈도우 노트북에서는 잘 됩니다. 실행 파일 `game.exe`를 친구 민준이와 서연이에게 보냈는데, 둘 다 켜지지 않는다고 합니다.

1. **화면에 뜬 글을 그대로 받아 적습니다.** 민준이는 "○○.dll을 찾을 수 없습니다"라는 창이 뜬다고 합니다. 서연이는 파일이 아예 열리지 않는다고 합니다.
2. **두 친구의 컴퓨터를 묻습니다.** 민준이는 나와 같은 윈도우 노트북입니다. 서연이는 맥북입니다.
3. **서연이 쪽은 빌드 대상이 다릅니다.** `.exe`는 윈도우용 번역본이라 맥에서는 실행되지 않습니다. 맥용으로 따로 빌드해서 보내야 합니다.
4. **민준이 쪽은 라이브러리가 없습니다.** 내 컴퓨터에는 게임 만드는 도구를 깔 때 함께 깔렸지만 민준이 컴퓨터에는 없습니다. 라이브러리 파일을 게임 폴더에 함께 넣어 보내거나, 정적 링크로 다시 빌드합니다.
5. **확인합니다.** 두 친구의 컴퓨터에서 정말 켜지는지 물어봅니다.

소스 코드는 어디든 가져갈 수 있지만 **번역본은 대상을 가립니다.** "내 컴퓨터에서는 되는데"라는 말이 나오면 코드보다 먼저 두 컴퓨터를 비교하세요. 운영체제, CPU, 런타임 버전, 깔려 있는 라이브러리입니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- CPU는 **기계어**만 알아듣습니다. 사람이 쓴 **소스 코드**는 반드시 번역을 거쳐야 합니다.
- **컴파일러**는 미리 통째로 옮기는 번역가입니다. **인터프리터**는 실행하면서 옮기는 통역사입니다. **바이트코드**와 가상 머신은 둘을 섞은 방법입니다.
- 컴파일은 토큰 나누기 → 구조 세우기 → 뜻 검사하기 → 기계어 쓰기 순서로 합니다.
- 오류는 **어느 단계에서 났는지**부터 봅니다. 문법 오류는 실행 전에 걸러지고, 실행 중 오류는 그 줄에 닿아야 드러납니다. 종류는 오류 글 맨 아래 줄에 적혀 있습니다.
- 타입 오류는 **정적 타입** 언어에서는 실행하기 전에, **동적 타입** 언어에서는 실행하다가 드러납니다. **타입스크립트**는 자바스크립트에 실행 전 타입 검사를 덧붙인 언어입니다.
- **링크**는 내 코드와 라이브러리를 잇는 일입니다. 동적 링크한 라이브러리와 **런타임**은 실행하는 컴퓨터에도 있어야 하고, 버전도 맞아야 합니다.
- **API**는 라이브러리의 기능을 부르는 약속입니다. **SDK**는 라이브러리, 도구, 설명서를 묶은 꾸러미입니다. AI는 없는 기능을 지어내기도 하니 공식 문서로 확인하게 합니다.
- 번역본은 **빌드 대상**(운영체제와 CPU)마다 따로 만듭니다.
- 만드는 동안에는 **디버그 빌드**를, 내보낼 때는 **릴리스 빌드**를 씁니다. 속도는 릴리스 빌드에서 잽니다.
- 웹 앱의 빌드는 소스 파일을 검사하고 묶어 브라우저에 보낼 결과물을 만드는 일입니다.
:::

## 확인 문제 {#quiz}

::: {.q}
친구가 파이썬으로 200줄짜리 퀴즈 게임을 만들었습니다. 그런데 150번째 줄에 닫지 않은 괄호가 있습니다. 실행하면 첫 줄의 "게임 시작!" 인사말은 화면에 나올까요?

::: {.a}
나오지 않습니다. 문법 오류는 실행하기 전, 파일 전체의 구조를 세우는 단계에서 걸립니다. 그래서 한 줄도 실행되지 않습니다.
:::
:::

::: {.q}
파이썬으로 만든 구구단 프로그램 파일을 친구에게 보냈습니다. 친구는 "파일은 받았는데 실행이 안 돼"라고 합니다. 친구의 컴퓨터는 내 것과 똑같은 윈도우 노트북입니다. 친구 컴퓨터에 무엇이 빠져 있을까요?

::: {.a}
파이썬 인터프리터입니다. 내가 보낸 것은 번역본이 아니라 소스 코드입니다. 소스 코드를 실행하려면 통역사인 인터프리터가 그 컴퓨터에도 깔려 있어야 합니다.
:::
:::

::: {.q}
AI가 만든 카드 게임을 실행했습니다. 화면에 "게임 시작!"이 나온 뒤 `TypeError: cards.shuffle is not a function`이라는 글이 뜨고 멈췄습니다. 문법 오류일까요? AI에게는 무엇을 확인하게 해야 할까요?

::: {.a}
문법 오류가 아닙니다. 문법 오류였다면 "게임 시작!"도 나오지 않았을 것입니다. 실행하다가 드러난 오류이고, `cards`에 `shuffle`이라는 기능이 없다는 뜻입니다. AI가 없는 기능을 지어냈을 수 있으니, 그 기능이 정말 있는지 공식 문서에서 확인하게 합니다.
:::
:::

::: {.q}
AI와 만든 웹 앱이 `npm run dev`로 볼 때는 잘 됩니다. 그런데 인터넷에 올리려고 `npm run build`를 했더니 `error TS2322`라는 글이 나오고 멈췄습니다. AI는 "타입 검사를 끄면 올릴 수 있습니다"라고 합니다. 그대로 따라도 될까요?

::: {.a}
따르지 않는 편이 좋습니다. `error TS`는 타입스크립트가 실행하기 전에 찾아 준 타입 오류입니다. 검사를 꺼도 잘못은 남아서, 사용자가 쓰는 중에 드러납니다. 오류 글이 가리키는 줄을 고치게 해야 합니다.
:::
:::

::: {.q}
반 간식비를 사람 수로 나누는 프로그램을 AI에게 부탁했습니다. AI가 "오류 없이 만들어졌습니다"라고 알려 왔습니다. 계산이 맞다고 믿어도 될까요?

::: {.a}
아직 믿을 수 없습니다. 그 말은 문법과 타입이 맞아서 번역할 수 있었다는 뜻일 뿐입니다. 사람 수가 0인 경우나 더하기를 빼기로 쓴 실수는 어떤 검사도 통과합니다. 실제 숫자를 넣어 실행해 봐야 합니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
오류를 고쳐 달라고 할 때는 화면에 뜬 오류 글 전체와 **내 운영체제, 런타임, 버전**을 함께 주세요. 그리고 고치기 전에 **어느 단계의 오류인지부터** 말하게 하세요.

> 아래 오류를 고쳐 줘. 내 컴퓨터는 윈도우 11이고 파이썬 3.12를 써. 고치기 전에 이 오류가 어느 단계에서 났는지 먼저 말해 줘. 문법, 타입 검사, 링크, 라이브러리 찾기, 실행 중 가운데 하나로 골라 줘. 없는 기능을 부른 오류라면, 내 버전에 정말 있는 기능인지 공식 문서에서 확인해 줘. 검사를 끄거나 오류를 안 보이게 숨기는 방법은 쓰지 마. 고친 다음에는 직접 실행해 보고, 화면에 나온 결과를 그대로 보여 줘.

**받은 답에서 확인할 것**

- AI가 말한 단계가 오류 글 맨 아래 줄의 낱말과 맞는가.
- 내 운영체제와 런타임 버전에 맞는 명령과 코드를 썼는가.
- 검사를 끄거나 오류만 안 보이게 숨기지 않았는가.
- "오류 없이 만들어졌다"로 끝내지 않고 실행한 결과를 보여 주는가([30장](ch30.html)).

**AI가 자주 하는 실수**

- 없는 기능이나 없는 라이브러리 이름을 지어냅니다. `has no attribute`, `is not a function`, `ModuleNotFoundError`가 보이면 이것부터 의심하세요. 라이브러리는 설치하기 전에 그 이름이 정말 있는지 검색해 봅니다.
- 내 런타임 버전과 맞지 않는 코드를 씁니다. 버전을 먼저 알려 주면 줄어듭니다.
- 빌드를 통과시키려고 타입 검사를 끕니다. 타입스크립트 코드에 `any`("아무 타입이나 된다")나 `@ts-ignore`("다음 줄은 검사하지 마라")가 갑자기 늘었다면 까닭을 물어보세요.
:::

## 용어 정리 {#terms}

::: {.terms}
소스 코드 (source code)
:   사람이 프로그래밍 언어로 읽고 쓰는 프로그램의 글.

기계어 (machine code)
:   CPU가 바로 알아듣는, 숫자로 적힌 명령. CPU 종류마다 다르다.

컴파일러 (compiler)
:   소스 코드를 실행하기 전에 통째로 기계어로 옮겨 주는 프로그램.

실행 파일 (executable)
:   기계어가 들어 있어서 CPU가 바로 실행할 수 있는 파일.

인터프리터 (interpreter)
:   번역본을 만들지 않고, 실행하면서 코드를 읽어 그 뜻대로 움직이는 프로그램.

바이트코드 (bytecode)
:   어느 CPU의 기계어도 아닌 중간 표기. 가상 머신이 읽어서 실행한다.

가상 머신 (VM, virtual machine)
:   바이트코드를 실행하는 프로그램. 프로그램으로 흉내 낸 CPU.

토큰 (token)
:   코드를 잘랐을 때 나오는, 뜻이 있는 가장 작은 낱말.

구문 트리 (AST, abstract syntax tree)
:   코드의 낱말이 어떻게 묶이는지를 나뭇가지 모양으로 나타낸 것.

타입 검사 (type checking)
:   값의 종류(타입)가 그 자리에 맞는지 확인하는 일.

정적 타입 (static typing)
:   실행하기 전에 타입을 미리 검사하는 방식.

동적 타입 (dynamic typing)
:   실행하다가 그 줄에 닿았을 때 타입을 검사하는 방식.

타입스크립트 (TypeScript)
:   자바스크립트에 타입 표시를 덧붙인 언어. 실행하기 전에 타입을 검사한다.

트랜스파일 (transpile)
:   소스 코드를 기계어가 아니라 다른 언어의 소스 코드로 옮기는 일.

라이브러리 (library)
:   가져다 쓰라고 미리 만들어 묶어 둔 코드.

링크 (link)
:   번역된 내 코드와 라이브러리를 이어 실행 파일 하나로 묶는 일.

링커 (linker)
:   링크를 맡아 하는 프로그램.

동적 링크 (dynamic linking)
:   라이브러리를 실행 파일에 넣지 않고, 실행할 때 찾아서 잇는 방법. 미리 넣어 두면 정적 링크.

의존성 (dependency)
:   내 프로그램이 돌아가려면 꼭 있어야 하는 남의 코드.

API (Application Programming Interface)
:   다른 코드의 기능을 부를 때 지키는 약속. 기능의 이름, 건넬 값, 돌려받는 값을 정한다.

SDK (Software Development Kit)
:   어떤 운영체제나 서비스에 맞는 프로그램을 만들 때 쓰는 라이브러리, 도구, 설명서 꾸러미.

로딩 (loading)
:   실행 파일과 라이브러리를 메모리에 올려 실행할 준비를 하는 일.

런타임 (runtime)
:   프로그램이 실행되고 있는 때. 또는 실행을 곁에서 돕는 프로그램.

Node.js
:   자바스크립트를 웹 브라우저 밖에서 실행해 주는 런타임.

빌드 (build)
:   소스 코드와 재료를 모아 실행할 수 있는 결과물로 만드는 과정 전체.

빌드 대상 (build target)
:   결과물이 실행될 운영체제와 CPU의 짝. 플랫폼이라고도 한다.

최적화 (optimization)
:   결과는 그대로 두고 더 빨리 끝나도록 컴파일러가 명령을 다듬는 일.

디버그 빌드 (debug build)
:   버그를 찾기 쉽도록 최적화를 거의 하지 않고 만든 결과물.

릴리스 빌드 (release build)
:   사람들에게 내보내려고 최적화를 켜서 빠르게 만든 결과물.
:::
