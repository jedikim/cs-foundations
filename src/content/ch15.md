::: {.lead}
인터넷 주소를 입력하고 엔터를 누르면 화면이 뜹니다. 그 사이에 내 컴퓨터는 멀리 있는 다른 컴퓨터에게 "이 페이지를 보여 주세요"라고 부탁하고, 그 컴퓨터는 답을 보내 줍니다. 식당에서 주문하고 음식을 받는 것과 비슷합니다. 이 장에서는 그 부탁과 답이 어떻게 생겼는지, 답이 오지 않을 때는 어떻게 하는지 배웁니다.
:::

::: {.goals}
- 엔터를 누른 뒤 화면이 뜨기까지 일어나는 일을 순서대로 말할 수 있습니다.
- 부탁(요청)과 답(응답)이 어떻게 생겼는지 읽을 수 있습니다.
- 사이트가 내가 로그인한 사람이라는 것을 기억하는 방법을 설명할 수 있습니다.
- 답이 오지 않을 때 같은 부탁을 다시 보내도 괜찮게 만드는 방법을 알 수 있습니다.
- 화면이 뜨지 않을 때 브라우저의 개발자 도구에서 무엇을 볼지 알 수 있습니다.
:::

## 엔터를 누르면 생기는 일: 여섯 단계 {#journey}

피자가 먹고 싶은데 직접 갈 수 없어서 동생에게 심부름을 시킨다고 합시다. 쪽지에 가게 이름과 원하는 것을 적어 줍니다. 동생은 가게에 주문서를 내고, 받은 것을 들고 돌아옵니다.

인터넷에서는 크롬이나 사파리 같은 프로그램이 이 심부름을 합니다. 이런 프로그램을 **브라우저**(browser)라고 부릅니다.

가게는 [14장](ch14.html)에서 만난 서버입니다. 기다리다가 부탁이 오면 답해 주는 컴퓨터입니다. 브라우저가 보내는 부탁을 요청, 서버가 돌려주는 답을 응답이라고 합니다. 가게로 치면 주문서와 답변서입니다.

쪽지는 주소창에 적는 주소입니다. 이 주소를 **URL**(Uniform Resource Locator)이라고 합니다. 여기서는 피자 가게의 주소 `https://pizza.example.com/menu?size=L`을 예로 씁니다. "L 크기 메뉴판을 보여 주세요"라는 주소입니다.

::: {.fig src="enter-journey.svg"}
엔터 한 번에 일어나는 여섯 단계. 색을 따라가면 주소의 각 조각이 어느 단계에서 쓰이는지 보입니다.
:::

그림의 1번 칸에서 브라우저는 주소를 네 조각으로 나눕니다.

| 조각 | 이름 | 뜻 |
|---|---|---|
| `https://` | 방식(스킴) | 어떤 방식으로 주고받을지 |
| `pizza.example.com` | 호스트 | 가게 이름 |
| `/menu` | 경로 | 가게 안에서 원하는 것 |
| `?size=L` | 쿼리 | 덧붙이는 조건. 여기서는 "크기는 L" |

여섯 단계를 차례로 보면 이렇습니다.

1. **주소 읽기.** 위 표처럼 주소를 나눕니다.
2. **이름을 주소로.** 가게 이름을 숫자 주소로 바꿉니다. 이름을 말하면 주소를 알려 주는 안내소인 DNS에 묻습니다. 그림에서는 `203.0.113.9`를 받았습니다.
3. **연결 맺기.** 그 주소의 443번 문을 두드려 길을 엽니다. 이 문 번호가 포트입니다. `https` 주소는 적지 않아도 443번으로 가고, 14장의 `localhost:3000`처럼 직접 적기도 합니다. 내용을 잠글 준비도 이때 합니다.
4. **요청 보내기.** 주문서를 건넵니다. 그림의 `GET /menu?size=L`이 주문서의 첫 줄입니다.
5. **응답 받기.** 답변서가 돌아옵니다. `200 OK`는 "잘 됐습니다"라는 뜻입니다. 함께 온 HTML 문서가 메뉴판입니다. HTML은 뒤에서 배웁니다.
6. **화면 그리기.** 받은 문서로 화면을 만듭니다. 문서에는 더 받아야 할 파일도 적혀 있습니다. 꾸밈 파일 `style.css`, 프로그램 `app.js`, 사진 `pizza.jpg`입니다. 이 파일들도 4번과 5번을 되풀이해 받아 옵니다.

2번과 3번은 14장에서 배웠습니다. 이 장은 4번부터 봅니다. 주문서와 답변서를 쓰는 방법은 약속으로 정해져 있습니다. 이 약속을 **HTTP**(Hypertext Transfer Protocol)라고 합니다.

## 요청과 응답: 주문서와 답변서 {#message}

HTTP의 규칙은 간단합니다. **브라우저가 요청을 하나 보내면 서버가 응답을 하나 돌려줍니다.** 서버가 먼저 말을 걸지는 않습니다.

요청과 응답은 사람이 읽을 수 있는 글자 몇 줄입니다. 아래 그림은 L 크기 피자 한 판을 주문할 때 오가는 글자입니다.

::: {.fig src="message-anatomy.svg"}
피자를 주문하는 요청과 그 응답. 둘 다 첫 줄, 헤더, 빈 줄, 본문 순서입니다.
:::

왼쪽 주문서를 위에서부터 읽어 봅시다.

- **시작줄.** `POST /orders HTTP/1.1`입니다. `POST`는 "새로 만들어 주세요", `/orders`는 주문을 받는 경로입니다. 끝의 `HTTP/1.1`은 약속의 판 번호입니다.
- **헤더**(header). `이름: 값` 꼴로 덧붙이는 메모입니다. `Host`에는 가게 이름을 적습니다. `Content-Type: application/json`은 "내용물을 JSON이라는 방식으로 적었습니다"라는 뜻입니다. JSON은 바로 아래 본문에 나옵니다.
- **빈 줄.** 메모가 끝났다는 표시입니다.
- **본문**(body). 실제 내용물입니다. `{"menu":"pizza","size":"L"}`은 "메뉴는 피자, 크기는 L"입니다. 이렇게 이름과 값을 짝지어 적는 방식이 [8장](ch08.html)에서 본 JSON입니다.

오른쪽 답변서도 순서가 같습니다. 첫 줄인 상태줄 `HTTP/1.1 201 Created`는 "새로 만들었습니다"입니다. 헤더 `Location: /orders/1042`는 새 주문이 있는 경로입니다. 본문은 "주문 번호는 1042번이고, 접수했습니다"라는 뜻입니다.

시작줄 맨 앞의 `POST`처럼 무엇을 해 달라는지 나타내는 낱말을 **메서드**(method)라고 합니다. 자주 쓰는 것은 다섯 가지입니다. 요청은 메서드와 경로를 짝지어 읽습니다. 메서드는 **어떻게 할지**, 경로는 **무엇을**입니다.

| 메서드 | 뜻 | 요청의 예 |
|---|---|---|
| `GET` | 보여 주세요 | `GET /orders/1042` 1042번 주문을 보여 주세요 |
| `POST` | 새로 만들어 주세요 | `POST /orders` 주문을 하나 넣어 주세요 |
| `PUT` | 통째로 바꿔 주세요 | `PUT /orders/1042` 1042번 주문서를 이것으로 바꿔 주세요 |
| `PATCH` | 일부만 고쳐 주세요 | `PATCH /orders/1042` 1042번의 크기만 M으로 바꿔 주세요 |
| `DELETE` | 지워 주세요 | `DELETE /orders/1042` 1042번 주문을 취소해 주세요 |

**GET은 보기만 한다**는 약속이 있습니다. 메뉴판은 백 번을 봐도 가게에서 달라지는 것이 없습니다. 그래서 브라우저는 GET 요청을 마음 놓고 다시 보냅니다. 새로 고침이 그런 예입니다.

서버가 "이런 요청을 받습니다" 하고 열어 둔 창구의 목록을 **API**라고 합니다. 위 표처럼 경로에는 대상의 이름을, 메서드에는 할 일을 적는 방식은 흔히 **REST**라고 부릅니다. AI가 "REST API를 만들었습니다"라고 하면 이런 목록이 있다는 말입니다.

::: {.tip}
AI가 서버를 만들었다면 "API 목록을 메서드와 경로의 표로 보여 줘"라고 하세요. 지우거나 바꾸는 일이 `GET`으로 되어 있으면 고치게 합니다. 브라우저와 메신저는 `GET`이 보기만 한다고 믿고 주소를 미리 열어 보기도 합니다. 그때마다 지워질 수 있습니다.
:::

### 실제로 오가는 글자

그림에서 설명 딱지를 떼면 글자 몇 줄만 남습니다. 실제 브라우저는 헤더를 여러 줄 더 붙일 뿐입니다. 직접 받아 봅시다.

::: {.try}
글자로 명령을 치는 창인 터미널([5장](ch05.html))에 `curl -i https://example.com`이라고 쳐 보세요. 윈도우에서는 `curl.exe`라고 칩니다. `curl`은 브라우저 없이 요청을 보내는 프로그램이고, `-i`는 헤더도 보여 달라는 옵션입니다. 첫 줄 `HTTP/2 200`에서 `HTTP/2`는 약속의 새 판 번호, `200`은 "잘 됐습니다"입니다. 그 아래에서 헤더, 빈 줄, HTML 본문을 차례로 찾아보세요. 주소 끝에 `/none`을 붙이면 첫 줄의 숫자가 어떻게 바뀌나요?
:::

::: {.warn}
비밀번호 같은 값은 `?pw=1234`처럼 주소에 적지 않습니다. 주소는 브라우저의 방문 기록과 서버의 기록에 글자 그대로 남습니다.
:::

### 상태 코드: 답변서의 첫 줄

응답 첫 줄의 세 자리 숫자를 **상태 코드**(status code)라고 합니다. 위에서 본 `200`과 `201`입니다. 첫 자리만 봐도 **누구 쪽 일인지** 알 수 있습니다.

| 첫 자리 | 뜻 | 자주 보는 코드 |
|---|---|---|
| 2 | 잘 됐습니다 | `200` 성공, `201` 새로 만들었음 |
| 3 | 다른 곳을 보세요 | `301` 주소가 바뀜, `304` 바뀐 것 없음 |
| 4 | 주문서가 잘못됐습니다 | `400`·`422` 보낸 값이 틀림, `401` 누구인지 모름, `403` 허락되지 않음, `404` 그런 것 없음, `429` 너무 자주 보냄 |
| 5 | 가게 사정입니다 | `500` 처리 중 오류, `502`·`504` 뒤쪽 서버의 답을 못 받음, `503` 지금은 못 받음 |

없는 주소를 열었을 때 화면에 뜨던 404가 이 상태 코드입니다.

큰 사이트에서는 [14장](ch14.html)에서 본 안내 데스크가 요청을 먼저 받아 뒤쪽 서버에 전합니다. `502`와 `504`는 이 안내 데스크가 대신 보내는 답입니다. `502`는 뒤쪽 서버가 꺼졌거나 알아들을 수 없는 답을 보냈다는 뜻이고, `504`는 너무 오래 답하지 않았다는 뜻입니다.

상태 코드가 아예 없을 때도 있습니다. 인터넷이 끊겼거나 가게 이름을 찾지 못해서, 주문서가 가게에 닿지도 못한 경우입니다.

::: {.key}
4로 시작하면 **주문서를 고칠 일**, 5로 시작하면 **가게를 살필 일**입니다. 상태 코드가 없으면 14장의 순서대로 **가는 길을 살필 일**입니다.
:::

내가 만든 앱에서도 같습니다. 4로 시작하면 **보낸 요청**의 주소, 메서드, 보낸 값을 봅니다. 5로 시작하면 **서버를 켜 둔 터미널**에 찍힌 오류 글을 봅니다. 코드마다 먼저 볼 곳은 [증상으로 찾기](trouble.html)에 모아 두었습니다.

## HTTPS: 주문서를 잠긴 상자에 넣기 {#https}

엽서에는 봉투가 없습니다. 배달하는 사람 누구나 읽을 수 있습니다. HTTP로 보내는 주문서가 이런 엽서입니다. 메시지는 공유기를 비롯한 여러 장비를 거쳐 갑니다. 그 길목에서 누군가 읽을 수도, 고칠 수도 있습니다.

**HTTPS**는 같은 주문서를 잠긴 상자에 넣어 주고받는 방식입니다. 상자는 세 가지 일을 합니다.

- 내용을 암호로 바꿔 **엿보지 못하게** 합니다.
- 중간에서 **고치면 알아채게** 합니다.
- **상대가 진짜 그 가게인지** 확인합니다.

이 잠금 방식의 이름이 **TLS**(Transport Layer Security)입니다.

::: {.fig src="https-envelope.svg"}
같은 로그인 요청을 길목에서 본 모습. HTTPS에서는 경로와 본문이 모두 잠깁니다.
:::

그림 위쪽은 민아가 HTTP로 로그인하는 모습입니다. 본문 `id=mina&pw=1234`에 아이디와 비밀번호가 글자 그대로 적혀 있습니다. 카페 와이파이를 쓰고 있다면 그 와이파이의 주인이 읽을 수 있습니다.

아래쪽은 HTTPS입니다. 내용은 `x9$Kq2…`처럼 알아볼 수 없는 글자가 되어 지나갑니다. 길목에서 보이는 것은 가게 이름 `pizza.example.com`, 그리고 주고받은 양과 시각뿐입니다.

상대가 진짜인지는 가게 벽의 영업 신고증 같은 문서로 확인합니다. "이 서버가 `pizza.example.com`의 진짜 주인입니다"라고 적힌 문서입니다. 이것을 **인증서**(certificate)라고 합니다. 브라우저가 미리 믿기로 한 기관이 확인하고 내줍니다.

브라우저는 인증서에서 세 가지를 봅니다. 믿는 기관이 내준 것인지, 적힌 이름이 가려는 이름과 같은지, 기한이 남았는지입니다. 하나라도 어긋나면 경고 화면을 띄웁니다. 이 경고를 무시하고 들어가면 가짜 가게에 비밀번호를 건네도 모릅니다.

::: {.myth title="주소가 https로 시작하면 믿어도 되는 사이트다"}
잠긴 상자는 **가는 길**만 지킵니다. `https`는 "이 이름의 서버와 잠긴 채로 주고받는 중"이라는 뜻일 뿐입니다. 사기 사이트도 자기 이름으로 인증서를 받을 수 있습니다. 주소의 이름이 내가 아는 그 이름인지 살펴봅니다.
:::

::: {.tip}
내 컴퓨터에서 연습할 때 쓰는 `http://localhost`는 요청이 밖으로 나가지 않으니 잠그지 않아도 됩니다. 인터넷에 올릴 때는 `https`로 엽니다. 인증서는 사이트를 올려 주는 서비스가 대신 받아 주는 곳이 많습니다([21장](ch21.html)).
:::

## 서버는 손님을 기억하지 못합니다: 쿠키와 세션 {#cookie}

서버는 **요청 하나하나를 처음 보는 손님처럼** 대합니다. 방금 로그인한 민아와, 지금 장바구니를 보여 달라는 사람이 같은지 모릅니다. 그렇다고 요청마다 비밀번호를 보낼 수는 없습니다.

::: {.analogy}
짐 보관소에 가방을 맡기면 번호표를 줍니다. 나중에 번호표를 내밀면 직원은 장부에서 그 번호를 찾아 내 가방을 내줍니다. 내 얼굴을 기억할 필요가 없습니다.
:::

웹 사이트도 로그인한 손님에게 번호표를 줍니다.

::: {.fig src="cookie-session.svg"}
서버가 번호표를 주면 브라우저는 그 가게로 가는 모든 요청에 번호표를 붙입니다.
:::

1. 민아가 아이디와 비밀번호를 보냅니다. 그림의 `POST /login`입니다.
2. 서버는 짐작하기 어려운 번호 `k3x9`를 만들어 장부에 "k3x9는 민아"라고 적습니다. 그리고 응답 헤더 `Set-Cookie: sid=k3x9`에 번호표를 실어 보냅니다. 실제 번호는 훨씬 깁니다.
3. 브라우저는 번호표를 그 사이트 전용 보관함에 넣어 둡니다. 그 뒤로 같은 사이트에 보내는 요청마다 `Cookie: sid=k3x9`를 **알아서** 붙입니다. `GET /cart`는 "장바구니를 보여 주세요"입니다.
4. 서버는 장부에서 `k3x9`를 찾아 민아의 장바구니를 돌려줍니다.

서버가 브라우저에 맡겨 두는 이 작은 값을 **쿠키**(cookie)라고 합니다. 번호표가 쿠키입니다.

서버의 장부에는 손님마다 기록이 한 줄씩 있습니다. 준호의 번호는 `p7m2`입니다. 서버가 손님 한 명에 대해 적어 둔 이 기록을 **세션**(session)이라고 합니다.

번호표는 **들고 있는 사람을 주인으로 대접**합니다. 남이 내 번호표를 손에 넣으면 비밀번호를 몰라도 내 행세를 할 수 있습니다.

그래서 서버는 번호표를 줄 때 "이렇게 다뤄 주세요"라는 당부를 뒤에 붙입니다. 실제 헤더는 `Set-Cookie: sid=k3x9; HttpOnly; Secure; SameSite=Lax`처럼 생겼습니다. `;` 뒤의 세 낱말이 당부입니다. 로그인 기능을 만들었다면 이 세 가지가 붙어 있는지 확인합니다. 하나하나의 뜻과 번호표를 훔치는 수법은 [19장](ch19.html)에서 다룹니다.

::: {.warn}
PC방이나 학교 컴퓨터에서는 다 쓴 뒤 꼭 로그아웃합니다. 그러지 않으면 번호표가 그 브라우저에 남아, 다음 사람이 내 계정을 쓸 수 있습니다.
:::

### 브라우저의 서랍: localStorage

브라우저에는 쿠키 보관함 말고 서랍이 하나 더 있습니다. 사이트가 "어두운 화면으로 보기" 같은 설정이나 게임의 최고 점수를 넣어 두는 곳입니다. 브라우저를 껐다 켜도 남아 있습니다. 이 서랍을 **localStorage**(로컬 스토리지)라고 합니다.

쿠키는 요청마다 알아서 서버로 갑니다. localStorage에 넣은 값은 저절로 가지 않습니다. 페이지에 딸려 온 프로그램이 꺼내서 보내야 서버가 압니다.

그래서 localStorage에만 넣어 둔 것은 그 브라우저에서만 보입니다. 집 컴퓨터에서 세운 최고 점수가 휴대전화에서는 보이지 않습니다. "브라우저에 저장했다"는 "서버에 저장했다"와 다른 말입니다. AI가 저장 기능을 만들었다고 하면 **어디에** 저장하는지 묻습니다.

## 출처와 CORS: 막는 쪽은 브라우저입니다 {#cors}

웹 페이지에는 작은 프로그램도 함께 옵니다. 내 브라우저 안에서 돌면서 버튼을 움직이고 새 내용을 받아 옵니다. 이런 프로그램을 **스크립트**(script)라고 합니다. 앞에서 본 `app.js`가 스크립트입니다.

번호표가 **알아서** 붙는다는 점이 여기서 위험해집니다.

민아가 피자 가게에 로그인해 둔 채로 수상한 사이트를 열었다고 합시다. 그 사이트의 스크립트가 민아의 브라우저에게 시킵니다. "피자 가게에서 주문 내역을 받아 와." 요청에 민아의 번호표가 붙으면 가게는 민아라고 믿고 답합니다. 그 답을 수상한 사이트가 읽으면 민아의 집 주소가 새어 나갑니다.

그래서 브라우저는 **스크립트가 자기가 온 곳이 아닌 다른 곳의 응답을 읽지 못하게** 막습니다. '온 곳'을 따지는 기준이 **출처**(origin)입니다. 주소의 방식, 호스트, 포트 세 가지를 묶은 것입니다. 하나만 달라도 다른 출처입니다.

다른 출처끼리 꼭 주고받아야 할 때는 응답을 주는 서버가 허락합니다. 응답 헤더에 "이 출처의 스크립트는 읽어도 됩니다"라고 적습니다. 브라우저는 이 허락 헤더를 확인한 뒤에야 응답을 스크립트에 넘깁니다. 이 약속을 **CORS**(Cross-Origin Resource Sharing)라고 합니다.

::: {.fig src="cors-block.svg"}
CORS 오류가 날 때 일어나는 일. 응답은 돌아왔지만 브라우저가 스크립트에 넘기지 않았습니다.
:::

그림은 사이트를 만드는 사람이 자주 겪는 장면입니다. 자기 컴퓨터에서 연습하면서 프로그램 두 개를 띄웠습니다. 하나는 화면을 내주고, 하나는 메뉴 데이터를 내줍니다. 그림의 API 서버가 데이터를 내주는 쪽입니다.

`localhost`는 "지금 이 컴퓨터 자신"을 가리키는 이름입니다. 뒤의 3000과 8000은 포트입니다. 이름은 같아도 포트가 달라서 둘은 다른 출처입니다.

1. `localhost:3000`에서 온 스크립트가 `localhost:8000`에 메뉴를 달라고 합니다.
2. 요청 `GET /menu`는 서버로 갑니다.
3. 서버는 잘 처리하고 `200 OK`를 보냅니다. 그런데 허락 헤더가 없습니다.
4. 브라우저는 응답을 스크립트에 넘기지 않습니다. 화면에 메뉴는 뜨지 않고, 브라우저의 오류 기록에 `blocked by CORS policy`라는 빨간 글씨가 남습니다. 이 기록은 다음 절에서 열어 봅니다.

맨 아래 줄의 `curl`은 앞에서 써 본 프로그램입니다. 브라우저가 아니니 출처 검사가 없어서, 같은 주소에서 답을 그대로 받습니다. "터미널에서는 되는데 화면에서는 안 된다"면 CORS를 의심합니다.

::: {.key}
CORS 오류는 서버의 거절이 아니라 **브라우저의 검사**입니다. 고치는 곳은 **서버의 응답 헤더**입니다.
:::

### CORS 오류를 만났을 때

오류 기록에는 아래와 같은 글이 찍힙니다.

```text
Access to fetch at 'http://localhost:8000/menu' from origin
'http://localhost:3000' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested resource.
```

`from origin` 뒤가 스크립트가 온 출처, `at` 뒤가 읽으려던 주소입니다. 끝 문장은 "응답에 `Access-Control-Allow-Origin` 헤더가 없습니다"입니다. 이것이 허락 헤더의 이름입니다.

API 서버가 응답에 아래 헤더를 붙여야 풀립니다. 값은 허락할 출처입니다.

```text
Access-Control-Allow-Origin: http://localhost:3000
```

::: {.warn}
AI는 이 오류를 흔히 값 `*`로 풉니다. "어느 사이트의 스크립트든 읽어도 됩니다"라는 뜻입니다. 누구에게나 보여 줄 데이터만 주는 서버라면 괜찮습니다. 로그인이 있는 서버라면 **내 화면의 주소만** 적게 합니다. 화면 코드에 `no-cors`를 붙이자는 답도 받지 않습니다. 빨간 글씨만 사라지고 응답은 여전히 읽지 못합니다.
:::

::: {.deep title="지워 달라는 요청도 보낸 뒤에야 검사할까요?"}
그림에서 서버는 요청을 이미 처리했습니다. 주문을 지우는 요청이었다면 검사하기도 전에 지워집니다. 그래서 브라우저는 `PUT`, `PATCH`, `DELETE`를 쓰는 요청, JSON 본문을 실은 요청 앞에서는 `OPTIONS`라는 메서드로 "보내도 됩니까?" 하고 먼저 묻습니다. 이것을 **사전 요청**(preflight)이라고 합니다. 서버가 허락하지 않으면 진짜 요청은 나가지 않습니다. 네트워크 탭에 내가 보낸 적 없는 `OPTIONS` 줄이 있으면 이것입니다.
:::

## 브라우저가 화면을 만드는 법: HTML과 DOM {#render}

사이트를 열면 "불러오는 중"이라는 글자가 먼저 보일 때가 있습니다. 내용은 잠시 뒤에야 채워집니다. 왜 그럴까요?

서버가 보낸 문서는 **HTML**(Hypertext Markup Language)이라는 방식으로 적은 글자입니다. `<li>`처럼 꺾쇠로 감싼 표시로 문서의 뼈대를 적습니다. 이 표시를 **태그**(tag)라고 합니다.

::: {.fig src="html-dom.svg"}
서버가 보낸 HTML에는 "불러오는 중"뿐입니다. 스크립트가 DOM에 마디 세 개를 끼워 넣어야 화면에 메뉴가 보입니다.
:::

**1번은 서버가 보낸 HTML입니다.** `<ul>`은 목록, `<li>`는 목록의 한 줄입니다. `id="menu"`는 이 목록에 붙인 이름표입니다. 지금은 "불러오는 중" 한 줄뿐입니다. `<script src="app.js">`는 "`app.js`라는 스크립트를 받아서 돌리세요"라는 뜻입니다.

**2번은 브라우저가 만든 나무입니다.** 브라우저는 태그 하나를 마디 하나로 삼아, 나뭇가지처럼 이어진 구조를 메모리에 만듭니다. 이 나무를 **DOM**(Document Object Model)이라고 합니다. 그림의 `ul#menu`는 "이름표가 menu인 ul"을 짧게 적은 것입니다. 화면은 HTML이 아니라 **DOM을 보고** 그립니다.

**3번은 스크립트가 고친 나무입니다.** 스크립트가 서버에서 메뉴를 받아 와 DOM을 고쳤습니다. "불러오는 중" 대신 마르게리타, 페퍼로니, 고르곤졸라 세 마디가 달렸습니다. 화면도 따라 바뀝니다.

AI가 만들어 주는 화면도 대개 이렇게 움직입니다. 그래서 알아 둘 것이 세 가지 있습니다.

- **"페이지 소스 보기"와 화면이 다릅니다.** 페이지 소스 보기는 화면을 마우스 오른쪽 버튼으로 누르면 나오는 메뉴입니다. 소스 보기는 1번을, 화면은 3번을 보여 줍니다.
- **DOM을 고쳐도 서버는 그대로입니다.** 내 브라우저에서 피자 값을 0원으로 고쳐도 내 화면만 바뀝니다. 가게의 장부는 그대로입니다. 그래서 서버는 화면에서 온 값을 믿지 않고 자기 장부로 계산해야 합니다.
- **브라우저로 온 것은 누구나 볼 수 있습니다.** 스크립트에 적힌 글자도, 스크립트가 보낸 요청도 숨길 수 없습니다. AI 서비스처럼 돈을 내고 쓰는 서비스는 "이 사람 앞으로 요금을 답니다" 하고 긴 암호 글자를 내줍니다. 이 글자를 **API 키**라고 합니다. 화면 코드에 넣으면 방문자 누구나 꺼내 쓸 수 있습니다. 키는 서버에만 두고, 화면은 내 서버에 부탁하게 합니다([19장](ch19.html), [31장](ch31.html#secret)).

### 개발자 도구: 실제로 오간 것을 보는 창

컴퓨터에서 `F12`(맥은 `Cmd + Option + I`)를 누르면 브라우저의 속을 들여다보는 창이 열립니다. 이 창을 **개발자 도구**라고 합니다.

위쪽에 탭이 여럿 있습니다. 자주 쓰는 것은 네 개입니다. 이름은 크롬의 것이고, 다른 브라우저도 비슷합니다.

- Elements 탭은 지금의 DOM, 곧 그림의 3번을 보여 줍니다.
- Console(콘솔) 탭에는 스크립트가 낸 오류가 빨간 글씨로 찍힙니다. 앞 절의 CORS 오류도 여기에 나옵니다.
- Application 탭은 쿠키와 localStorage에 든 값을 보여 줍니다. 로그인이 자꾸 풀리면 번호표가 들어 있는지 여기서 봅니다.
- **Network**(네트워크) 탭은 오간 요청과 응답을 모두 보여 줍니다.

::: {.try}
아무 사이트나 열고 Elements 탭에서 글자 하나를 두 번 눌러 다른 말로 고쳐 보세요. 화면이 바로 바뀝니다. 새로 고침하면 원래대로 돌아옵니다. 고친 것은 내 브라우저의 DOM뿐이기 때문입니다.
:::

::: {.fig src="network-tab.svg"}
네트워크 탭을 단순하게 그린 모습. 한 줄이 요청 하나입니다.
:::

칸은 왼쪽부터 이름, 상태 코드, 크기, 걸린 시간입니다. ms는 1,000분의 1초이니 400ms는 0.4초입니다. '폭포' 칸의 막대는 언제 시작해 얼마나 걸렸는지 보여 줍니다.

- `menu`는 처음 받은 HTML 문서입니다.
- `app.js`는 스크립트입니다. `304`는 "갖고 있던 사본을 쓰세요"라는 뜻이고, 다음 절에서 배웁니다.
- `api/menu`는 스크립트가 받아 온 메뉴 데이터입니다. 400ms로 가장 오래 걸렸습니다.
- `pizza.jpg`는 `404`입니다. 사진이 서버에 없어서 화면에 깨진 그림이 보입니다.

`api/menu` 줄을 누르고 Timing(시간) 탭을 열면 400ms를 어디에 썼는지 나옵니다. 연결 준비 40ms, 서버의 첫 응답을 기다린 시간 280ms, 내려받기 80ms입니다. 기다린 시간이 가장 깁니다. 이럴 때는 인터넷 선(회선)보다 서버가 답을 만드는 시간을 살핍니다. 이 기다린 시간을 **TTFB**(Time To First Byte)라고 부릅니다.

::: {.try}
컴퓨터로 아무 사이트나 열고 Network 탭을 켠 뒤 새로 고침해 보세요. 줄을 하나 눌러 메서드와 상태 코드를 찾아보세요. 상태가 200이 아닌 줄도 있는지 살펴보세요.
:::

### 화면이 뜨지 않을 때 보는 순서

AI가 "다 만들었습니다"라고 했는데 하얀 화면만 보일 때가 있습니다. 아래 순서로 봅니다.

1. **주소창.** 주소와 포트가 AI가 알려 준 것과 같은지 봅니다. "사이트에 연결할 수 없음"이 뜨면 서버가 꺼져 있는 것입니다. 서버를 켠 터미널에 오류 글이 있는지 봅니다.
2. **Console 탭.** 빨간 글이 있으면 맨 위의 것부터 봅니다. `Uncaught`로 시작하면 스크립트가 돌다가 멈췄다는 뜻입니다. 줄 끝의 `app.js:12`는 `app.js` 파일의 12번째 줄을 가리킵니다([초코딩 기초](code.html#error)).
3. **Network 탭.** 탭을 연 채로 새로 고침합니다. 빨간 줄이 있으면 눌러서 메서드, 주소, 상태 코드, 응답 본문을 봅니다. 상태 칸에 숫자 대신 `(failed)` 같은 글자가 있으면 응답을 받지 못한 것입니다. 버튼을 눌러도 아무 일이 없을 때도 이 탭을 연 채로 눌러 봅니다. 줄이 생기지 않으면 요청이 나가지도 못한 것이니 Console 탭을 봅니다.
4. **상태 코드.** 4로 시작하면 보낸 요청을, 5로 시작하면 서버를 켠 터미널을 봅니다.

AI에게는 "안 떠요" 대신 여기서 본 것을 그대로 줍니다.

::: {.warn}
요청 헤더를 통째로 복사해 남에게 줄 때는 `Cookie`와 `Authorization`의 값을 지웁니다. 번호표와 API 키가 들어 있는 자리입니다.
:::

## 같은 일을 두 번 하지 않기: 캐시 {#cache}

가게 메뉴판은 어제도 오늘도 같습니다. 갈 때마다 새로 받아 오면 시간도 데이터도 아깝습니다. 그래서 브라우저는 한 번 받은 응답의 사본을 보관했다가 다시 씁니다. 이 보관함을 **캐시**(cache)라고 합니다.

그사이 메뉴판이 바뀌면 어떡할까요? 서버가 응답 헤더로 규칙을 정해 줍니다.

- `Cache-Control: max-age=3600`은 "3,600초, 곧 1시간 동안은 묻지 말고 사본을 쓰세요"입니다. 그림에는 뒤쪽만 적었습니다.
- `ETag: "v7"`은 내용물의 **판 번호**입니다. 내용이 바뀌면 이 값도 바뀝니다.

::: {.fig src="cache-304.svg"}
같은 메뉴판을 세 번 여는 동안 내려받은 양. 기간이 지나면 바뀌었는지만 묻습니다.
:::

1. **첫 방문.** 사본이 없어서 메뉴판 48KB를 모두 내려받습니다.
2. **10분 뒤.** 아직 1시간이 지나지 않았습니다. 서버에 묻지도 않고 사본을 씁니다. 내려받은 양은 0KB입니다.
3. **2시간 뒤.** 기간이 지났습니다. 그래도 사본을 버리지 않고 `If-None-Match: "v7"`을 붙여 묻습니다. "7판을 갖고 있는데 바뀌었나요?"입니다. 그대로라면 서버는 본문 없이 `304 Not Modified`만 보냅니다. 0.2KB로 끝납니다. 바뀌었다면 `200`과 새 내용을 보냅니다.

::: {.tip}
AI가 고쳤다는데 화면이 그대로라면 내 브라우저가 옛 사본을 쓰고 있을 수 있습니다. 크롬에서는 `Ctrl + Shift + R`(맥은 `Cmd + Shift + R`)을 누르면 사본을 쓰지 않고 모두 새로 받아 옵니다. 그래도 그대로라면 그때 코드를 의심합니다.
:::

::: {.note}
서버는 응답의 본문을 이불 압축 팩처럼 눌러서 작게 보내기도 합니다. 이 일을 **압축**이라고 합니다. 응답 헤더의 `Content-Encoding: gzip`이 그 표시입니다. 푸는 일은 브라우저가 알아서 합니다([16장](ch16.html)).
:::

## 서버가 먼저 알려야 할 때: 폴링, SSE, WebSocket {#realtime}

친구가 메신저로 보낸 말은 내가 묻지 않아도 화면에 뜹니다. 그런데 HTTP에서는 브라우저가 물어야 서버가 답합니다. 서버 쪽에서 먼저 생긴 소식은 어떻게 전할까요? 방법이 세 가지 있습니다.

::: {.fig src="realtime.svg"}
파란 화살표는 브라우저가, 나머지는 서버가 보낸 것입니다.
:::

- **폴링**(polling)은 자꾸 가서 묻는 방법입니다. 분식집 카운터에 5초마다 가서 "제 떡볶이 나왔나요?" 하고 묻는 것과 같습니다. 그림에서는 네 번 물어 세 번이 "없음"이고 한 번만 "새 글"을 받았습니다. 만들기 쉽지만 헛걸음이 많고, 소식이 길게는 5초 늦습니다. 몇 초 늦어도 되는 알림이라면 이것으로 충분합니다.
- **SSE**(Server-Sent Events)는 한 번 묻고 카운터 앞에서 기다리는 방법입니다. 서버는 응답을 끝내지 않고 소식이 생길 때마다 한 줄씩 내려보냅니다. 그림에서는 "20%, 50%, 80%, 완료" 하고 진행 상황을 알려 줍니다. 방향은 서버에서 브라우저 쪽뿐입니다. AI 챗봇의 답이 조금씩 흘러나오는 화면이 흔히 이 방식입니다.
- **WebSocket**(웹소켓)은 전화를 걸어 놓고 끊지 않는 방법입니다. 양쪽이 아무 때나 말합니다. 채팅과 온라인 게임에 씁니다.

### 남의 서버가 내 서버를 부를 때: 웹훅

택배를 보낼 때 전화번호를 적어 두면, 도착했을 때 택배 회사가 문자를 보내 줍니다. 내가 자꾸 조회하지 않아도 됩니다.

서버끼리도 이렇게 합니다. 앱에서 돈을 받을 때는 결제를 대신 해 주는 서비스를 빌려 씁니다. 그 서비스에 내 서버의 주소를 적어 두면, 결제가 끝났을 때 그 주소로 `POST` 요청을 보내 알려 줍니다. 이번에는 **내 서버가 요청을 받는 쪽**입니다. 이 방식을 **웹훅**(webhook)이라고 합니다.

웹훅을 받는 기능을 AI에게 맡겼다면 세 가지를 확인합니다.

- **인터넷에서 닿는 주소인가.** `localhost`는 저쪽 서버가 찾아올 수 없습니다.
- **진짜 그 서비스가 보냈는지 확인하는가.** 주소만 알면 누구나 "결제 끝났어요"라고 보낼 수 있습니다. 서비스가 요청에 찍어 보내는 도장(서명)을 확인하게 합니다.
- **같은 알림이 두 번 와도 한 번만 처리하는가.** 저쪽도 답을 못 받으면 다시 보냅니다.

## 답이 오지 않을 때: 시간 제한, 다시 보내기, 멱등성 {#retry}

피자 주문 버튼을 눌렀는데 동그라미만 10초째 돕니다. 일어났을 만한 일은 셋입니다.

- 주문서가 가는 길에 사라졌습니다.
- 가게가 아직 처리하고 있습니다.
- 주문은 들어갔는데 **답변서가 오는 길에 사라졌습니다.**

브라우저는 이 셋을 구별하지 못합니다. [11장](ch11.html)에서 본 대로 답이 없다는 것은 "실패"가 아니라 "**모른다**"입니다.

먼저 얼마나 기다릴지를 정합니다. "5초 안에 답이 없으면 그만 기다린다"는 식입니다. 이 한도를 **시간 제한**(timeout), 한도를 넘긴 것을 시간 초과라고 합니다.

5초 뒤에 같은 주문을 그냥 다시 보내면 어떻게 될까요?

::: {.fig src="retry-idempotency.svg"}
주문서에 고유 번호가 있으면 서버가 같은 주문임을 알아봅니다.
:::

그림 위쪽을 보세요. 서버는 주문 #1042를 만들고 `201 Created`를 보냈습니다. 그런데 이 응답이 오는 길에 사라졌습니다. 브라우저가 주문서를 다시 보내자 서버는 새 주문인 줄 알고 #1043을 또 만듭니다. 피자가 두 판 옵니다.

엘리베이터 버튼은 다릅니다. 세 번 눌러도 한 번 누른 것과 같습니다. 이렇게 여러 번 해도 한 번 한 것과 결과가 같은 성질을 **멱등성**(idempotency)이라고 합니다. `GET`(보여 주세요), `PUT`(이걸로 바꿔 주세요), `DELETE`(취소해 주세요)가 그렇습니다. `POST`(한 판 주문이요)는 보낼 때마다 한 판씩 늘어납니다.

그림 아래쪽이 POST를 마음 놓고 다시 보내는 방법입니다. 주문서에 **고유 번호** `a1b2`를 적습니다. 번호는 버튼을 누를 때 만들고, 다시 보낼 때도 **같은 번호**를 씁니다. 서버는 처리한 번호를 적어 둡니다. 같은 번호가 또 오면 새로 만들지 않고 #1042를 다시 알려 줍니다. 피자는 한 판만 옵니다. 이 번호를 **멱등 키**(idempotency key)라고 합니다.

화면에서는 답이 올 때까지 버튼도 잠급니다([11장](ch11.html)). 그래도 시간 초과 뒤에 다시 보내는 일은 남으니 번호는 필요합니다.

다시 보내는 데에도 규칙이 있습니다.

- **될 만한 것만.** 답이 없었거나 5로 시작하는 코드를 받았다면 잠시 뒤에는 될 수 있습니다. `400`이나 `404`는 백 번을 보내도 같은 답입니다.
- **간격을 늘려서.** 1초, 2초, 4초처럼 기다리는 시간을 늘려 갑니다. 이것을 **백오프**(backoff)라고 합니다. 모두가 쉬지 않고 다시 주문하면 바쁜 가게는 더 밀립니다([18장](ch18.html)).
- **횟수를 정해서.** 세 번쯤 해 보고 안 되면 사람에게 알립니다.

::: {.key}
시간 초과는 "안 됐다"가 아니라 "모른다"입니다. 다시 보내기 전에 **두 번 처리돼도 괜찮은 요청인지**부터 확인합니다.
:::

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| GET / POST | 보기만 하니 다시 보내도 됨 / 보낼 때마다 새로 만들어질 수 있음 |
| PUT / PATCH | 통째로 바꿈 / 일부만 고침 |
| 401 / 403 | 누구인지 모르겠다 / 누구인지는 알지만 허락되지 않는다 |
| 쿠키 / 세션 | 브라우저가 들고 다니는 번호표 / 서버가 적어 둔 장부의 기록 |
| 쿠키 / localStorage | 요청마다 알아서 서버로 감 / 브라우저에만 남고, 꺼내 보내야 서버가 앎 |

## 실전 사례 {#case}

::: {.case title="버튼을 네 번 눌렀더니 티셔츠가 네 장"}
준호가 AI 도구로 동아리 티셔츠 주문 사이트를 만들었습니다. 민아가 '주문' 버튼을 눌렀는데 동그라미만 돕니다. 답답해서 세 번을 더 눌렀더니 티셔츠 네 장이 주문됐습니다.

1. **네트워크 탭을 연 채로 다시 눌러 봅니다.** 누를 때마다 `POST /orders` 줄이 하나씩 생깁니다. 요청이 네 번 나간 것입니다.
2. **상태를 봅니다.** 네 줄 모두 `201`입니다. 서버는 같은 주문인지 알아볼 방법이 없어서 네 번 다 새로 만들었습니다.
3. **고칩니다.** 버튼을 누를 때 고유 번호를 만들어 주문서에 붙입니다. 서버는 같은 번호의 주문을 한 번만 만듭니다. 답이 올 때까지 버튼도 잠급니다.

화면이 멈춘 것처럼 보여도 요청은 이미 나갔을 수 있습니다. 짐작하지 말고 네트워크 탭을 봅니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- 엔터 한 번에 **주소 읽기 → DNS → 연결 → 요청 → 응답 → 그리기**가 일어납니다. 화면은 **DOM**을 보고 그립니다.
- **요청**은 메서드, 경로, 헤더, 본문으로, **응답**은 상태 코드, 헤더, 본문으로 된 글자입니다. 메서드와 경로를 짝지은 목록이 **API**입니다.
- 상태 코드가 **4**로 시작하면 보낸 요청을, **5**로 시작하면 서버를 봅니다. 없으면 가는 길의 일입니다.
- **HTTPS**는 가는 길만 지킵니다. 브라우저는 **쿠키**라는 번호표를 알아서 붙이고, 서버는 **세션** 장부에서 손님을 찾습니다.
- **localStorage**의 값은 서버로 가지 않고 그 브라우저에만 남습니다.
- **CORS** 오류는 브라우저가 다른 출처의 응답을 스크립트에 넘기지 않은 것입니다. 서버의 허락 헤더로 풉니다.
- 브라우저로 온 것은 누구나 볼 수 있습니다. **API 키**는 화면 코드에 넣지 않습니다.
- 화면이 뜨지 않으면 **주소창 → Console → Network → 상태 코드** 순서로 봅니다.
- **캐시**는 같은 것을 다시 받지 않게 합니다. 서버 쪽 소식은 **폴링, SSE, WebSocket**으로, 남의 서버의 소식은 **웹훅**으로 받습니다.
- 시간 초과는 "모른다"입니다. **멱등 키**와 **백오프**로 탈 없이 다시 보냅니다.
:::

## 확인 문제 {#quiz}

::: {.q}
AI가 만든 메모 앱에서 '저장'을 눌렀더니 Network 탭에 `POST /notes` 줄이 `404`로 찍혔습니다. AI가 고친 뒤에는 같은 줄이 `500`으로 바뀌었습니다. 각각 어디부터 살펴야 할까요?

::: {.a}
`404`는 4로 시작하니 보낸 요청부터 봅니다. 경로의 철자가 맞는지, 서버의 API 목록에 `POST /notes`가 있는지 확인합니다. `500`은 5로 시작하니 서버 쪽입니다. 서버를 켠 터미널에 찍힌 오류 글을 AI에게 줍니다.
:::
:::

::: {.q}
카페 와이파이로 주소가 `https`로 시작하는 게임 사이트에 로그인했습니다. 와이파이 주인은 무엇을 볼 수 있을까요? 그 사이트는 믿어도 될까요?

::: {.a}
어느 서버와 언제, 얼마나 주고받았는지만 보입니다. 비밀번호와 쿠키는 잠겨서 보이지 않습니다. 하지만 `https`는 잠긴 채로 주고받는다는 뜻일 뿐, 사이트가 정직한지는 알려 주지 않습니다.
:::
:::

::: {.q}
PC방에서 게임 사이트에 로그인했다가 로그아웃하지 않고 자리를 떴습니다. 다음 사람이 그 브라우저로 같은 사이트를 열면 어떻게 될까요?

::: {.a}
내 계정으로 로그인된 화면이 뜹니다. 브라우저에 남은 내 쿠키(번호표)가 요청마다 알아서 붙기 때문입니다.
:::
:::

::: {.q}
친구가 피자 값이 0원으로 적힌 화면을 보여 줍니다. "개발자 도구로 고쳤으니 공짜로 살 수 있어"라고 합니다. 맞는 말일까요?

::: {.a}
아닙니다. 친구가 고친 것은 자기 브라우저 안의 DOM뿐이고, 서버의 장부는 그대로입니다. 제대로 만든 서버는 화면에서 온 값을 믿지 않고 자기 장부의 값으로 계산합니다.
:::
:::

::: {.q}
떡볶이 배달 앱에서 주문 버튼을 눌렀는데 5초가 지나도 답이 없습니다. 곧바로 한 번 더 눌러도 될까요?

::: {.a}
바로 누르지 말고 주문 내역부터 확인합니다. 주문은 들어갔는데 답만 사라졌다면 떡볶이가 두 번 옵니다. 주문서에 고유 번호(멱등 키)를 붙이는 앱이라면 다시 보내도 괜찮습니다. 서버가 같은 번호를 한 번만 처리하기 때문입니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
"안 돼요" 대신 **개발자 도구에서 본 것**을 알려 주세요. Console의 첫 빨간 글, 그리고 실패한 요청의 메서드, 주소, 상태 코드입니다. 고칠 곳이 화면인지 서버인지도 짚어 줍니다.

> 메뉴 화면이 "불러오는 중"에서 멈춰 있어. 화면은 http://localhost:3000, API 서버는 http://localhost:8000이야. 터미널에서 curl로 부르면 메뉴가 잘 오는데, 화면에서는 Console에 "blocked by CORS policy: No 'Access-Control-Allow-Origin' header"라고 나와. 화면 코드는 그대로 두고 API 서버의 응답에 허락 헤더를 달아 줘. 모든 출처(*)가 아니라 내 화면의 주소만 허락해 줘. 고친 뒤 응답 헤더에 무엇이 보여야 하는지도 알려 줘.

**받은 답에서 확인할 것**

- 고친 파일이 화면 쪽이 아니라 서버 쪽인가.
- 응답 헤더 `Access-Control-Allow-Origin`의 값이 `*`가 아니라 내 화면의 주소인가.
- 새로 고침했을 때 Console의 빨간 글이 사라지고 메뉴가 보이는가.
- 화면 코드에 API 키나 비밀번호가 적혀 있지 않은가.

**AI가 자주 하는 실수**

- CORS를 통째로 풉니다. 모든 출처를 허락하거나, 화면 코드에 `no-cors`를 붙여 빨간 글만 없앱니다. 응답 헤더의 값을 직접 보면 압니다.
- API 키를 화면 코드에 넣습니다. Network 탭에서 요청을 눌렀을 때 주소나 헤더에 키가 보이면 방문자에게도 보입니다.
- 화면 코드에 서버 주소를 `http://localhost:8000`으로 적어 둡니다. 인터넷에 올리면 방문자 자신의 컴퓨터를 찾아가 실패합니다([20장](ch20.html)).
- 실패를 다루지 않습니다. 응답이 `404`나 `500`이어도 화면이 "불러오는 중"에서 멈춰 있습니다. 다시 보내게 했다면 고유 번호 없는 `POST`까지 다시 보내지 않는지 봅니다.
:::

## 용어 정리 {#terms}

::: {.terms}
브라우저 (browser)
:   서버에 요청을 보내고 받은 응답으로 화면을 그리는 프로그램.

URL (Uniform Resource Locator)
:   방식, 호스트, 경로, 쿼리로 이루어진 웹 주소.

HTTP (Hypertext Transfer Protocol)
:   브라우저와 서버가 요청과 응답을 주고받는 약속.

메서드 (method)
:   요청 맨 앞에 적어 무엇을 해 달라는지 나타내는 낱말. GET, POST 등이 있다.

API (Application Programming Interface)
:   서버가 받아 주는 요청의 목록.

REST
:   경로에는 대상을, 메서드에는 할 일을 적어 API를 짜는 방식.

헤더 (header)
:   요청과 응답에 "이름: 값" 꼴로 덧붙이는 메모.

상태 코드 (status code)
:   요청이 어떻게 됐는지 알리는 세 자리 숫자.

HTTPS
:   요청과 응답을 TLS로 잠가서 주고받는 방식.

TLS (Transport Layer Security)
:   내용을 잠그고 상대가 진짜인지 확인해 주는 약속.

인증서 (certificate)
:   서버가 그 이름의 진짜 주인임을 믿을 만한 기관이 확인한 문서.

쿠키 (cookie)
:   서버가 브라우저에 맡겨 두는 작은 값. 요청마다 알아서 붙는다.

세션 (session)
:   서버가 손님 한 명에 대해 적어 둔 기록. 쿠키의 번호로 찾는다.

localStorage
:   사이트가 브라우저 안에 값을 넣어 두는 서랍. 쿠키와 달리 서버로 저절로 가지 않는다.

스크립트 (script)
:   웹 페이지에 딸려 와 브라우저 안에서 도는 작은 프로그램.

출처 (origin)
:   방식, 호스트, 포트의 묶음. 하나만 달라도 다른 출처다.

CORS (Cross-Origin Resource Sharing)
:   다른 출처의 스크립트가 응답을 읽어도 된다고 서버가 허락하는 약속.

사전 요청 (preflight)
:   조심스러운 요청을 보내기 전에 브라우저가 서버에 먼저 물어보는 요청.

HTML (Hypertext Markup Language)
:   태그로 문서의 뼈대를 적는 방식.

태그 (tag)
:   HTML에서 꺾쇠로 감싼 표시.

DOM (Document Object Model)
:   브라우저가 HTML을 읽어 메모리에 만든 나무 구조.

API 키 (API key)
:   돈을 내고 쓰는 서비스가 이용자에게 내주는 긴 암호 글자.

개발자 도구 (developer tools)
:   DOM, 오류, 오간 요청과 응답을 들여다보는 브라우저의 창.

TTFB (Time To First Byte)
:   요청을 보낸 뒤 서버의 첫 응답이 오기까지 기다린 시간.

캐시 (cache)
:   한 번 받은 응답의 사본을 넣어 두었다가 다시 쓰는 보관함.

압축 (compression)
:   본문을 눌러서 크기를 줄여 보내는 일. gzip 방식이 널리 쓰인다.

폴링 (polling)
:   새 소식이 있는지 정해진 간격으로 서버에 묻는 방법.

SSE (Server-Sent Events)
:   한 번 요청해 두면 서버가 소식을 계속 내려보내는 방식.

WebSocket
:   연결을 열어 둔 채 양쪽이 아무 때나 말을 주고받는 방식.

웹훅 (webhook)
:   일이 생기면 다른 서비스가 내 서버의 주소로 요청을 보내 알려 주는 방식.

시간 제한 (timeout)
:   답을 기다리는 한도. 넘기면 그만 기다린다.

멱등성 (idempotency)
:   여러 번 보내도 결과가 한 번 보낸 것과 같은 성질.

멱등 키 (idempotency key)
:   같은 요청임을 서버가 알아보도록 요청에 붙이는 고유 번호.

백오프 (backoff)
:   다시 보낼 때마다 기다리는 시간을 늘려 가는 방법.
:::
