::: {.lead}
책상 위에 있는 연필은 바로 집을 수 있습니다. 창고에 있는 연필은 가지러 다녀와야 합니다. 컴퓨터도 같습니다. 계산은 눈 깜짝할 사이에 하지만, 파일을 읽거나 인터넷에서 무언가를 받아 오는 일은 훨씬 오래 걸립니다. 프로그램이 느릴 때는 대개 계산이 아니라 이 '다녀오는 시간' 때문입니다. 이 장에서는 그 시간이 어디서 생기고 어떻게 줄이는지 배웁니다.
:::

::: {.goals}
- 프로그램이 계산하느라 느린지 기다리느라 느린지 구분할 수 있습니다.
- 파일을 열고 읽고 저장할 때 컴퓨터 안에서 일어나는 일을 설명할 수 있습니다.
- 같은 파일을 두 번째 읽을 때 더 빠른 이유를 설명할 수 있습니다.
- 큰 파일을 조금씩 나눠 처리하는 방법을 알 수 있습니다.
:::

## 느린 프로그램은 대부분 기다리는 중입니다 {#io}

[1장](ch01.html)의 '속도의 사다리'를 떠올려 봅시다. CPU 안에서 값 하나를 꺼내는 시간을 1초로 늘리면 메모리는 2분, SSD는 하루, 바다 건너 서버는 5년이었습니다. 요리사의 칼질이 아무리 빨라도 재료가 창고에서 오는 데 하루가 걸리면 요리는 하루 뒤에 나옵니다.

CPU와 메모리 바깥, 곧 디스크나 네트워크와 데이터를 주고받는 일을 **입출력**(I/O, Input/Output)이라고 합니다. 주방으로 치면 창고에 다녀오거나 바깥 거래처에 주문을 넣는 일입니다. 버튼을 누르고 결과가 나오기까지 5초가 걸린 작업 하나를 뜯어 보겠습니다.

::: {.fig src="wait-timeline.svg"}
5초 가운데 CPU가 계산한 시간은 파란 조각 두 개, 0.2초뿐입니다. 나머지는 기다린 시간입니다.
:::

시계가 두 개입니다. 벽시계로 잰 **경과 시간**(elapsed time)은 5초이고, 그중 CPU가 실제로 계산한 **CPU 시간**(CPU time)은 0.2초입니다. 나머지 4.8초 동안 요리사는 창고 문 앞에 서 있었습니다.

계산 코드를 두 배 빠르게 고쳐도 5초가 4.9초가 될 뿐입니다. 서버를 기다리는 시간을 절반으로 줄이면 3.5초가 됩니다.

::: {.key}
느리다고 느껴지면 먼저 물으세요. **경과 시간 가운데 CPU 시간은 얼마인가?** 둘의 차이가 크다면 범인은 계산이 아니라 기다림입니다.
:::

## 파일을 연다는 것: 번호표와 책갈피 {#open}

창고에는 아무나 들어가지 못합니다. [3장](ch03.html)에서 본 것처럼 프로그램은 지배인인 커널에게 **시스템 호출**로 부탁해야 합니다. 파일을 읽으려면 세 번 부탁합니다. 열기, 읽기, 닫기입니다.

열어 달라고 하면 커널은 파일과 권한을 확인한 뒤 대여 장부에 한 줄을 적고 번호표를 내줍니다. 이 번호표가 **파일 디스크립터**(FD, file descriptor)이고, 3이나 4 같은 작은 정수입니다. 0·1·2번은 [5장](ch05.html)의 표준 입력, 표준 출력, 표준 오류가 이미 쓰고 있어서 처음 연 파일은 보통 3번을 받습니다.

장부에는 **어디까지 읽었는지**를 나타내는 책갈피도 함께 적힙니다.

::: {.fig src="fd-bookmark.svg"}
프로그램이 쥔 것은 3이라는 숫자뿐입니다. 어느 파일인지, 어디까지 읽었는지는 커널의 장부가 기억합니다.
:::

```python
f = open("memo.txt")   # 번호표를 받음. 책갈피는 0
f.read(2)              # "AB" — 책갈피가 2로 이동
f.read(2)              # "CD" — 이어서 읽음
f.close()              # 번호표 반납
```

`read(2)`를 똑같이 두 번 불렀는데 다른 글자가 나옵니다. 프로그램은 "두 글자 주세요"라고만 하고, 어디서부터인지는 장부의 책갈피가 정하기 때문입니다.

번호표는 꼭 돌려줘야 합니다. 장부의 줄 수에는 한도가 있어서 닫지 않은 파일이 쌓이면 `Too many open files` 오류가 납니다. 네트워크 연결도 같은 번호표를 쓰므로 새 연결도 열지 못하게 됩니다. 3장에서 배운 `with open(...) as f:`처럼 **실패해도 닫히는 문법**을 쓰세요.

## 이름표와 내용물은 따로 보관됩니다 {#inode}

창고 선반의 상자에는 이름이 적혀 있지 않습니다. 입구의 **이름표 목록**에 "report.txt는 1042번 카드"라고만 적혀 있습니다. 1042번 **관리 카드**를 보면 크기, 주인, 권한, 그리고 내용물이 선반의 몇 번 칸에 있는지가 나옵니다.

리눅스와 맥의 파일 시스템이 이렇게 일합니다. 관리 카드를 **아이노드**(inode), 내용물이 담긴 선반 칸을 **블록**(block)이라고 부릅니다. 디렉터리는 "이름 → 아이노드 번호"를 적은 목록일 뿐입니다.

::: {.fig src="inode-map.svg"}
이름표, 관리 카드, 내용물은 서로 다른 곳에 있습니다. `report.txt`와 `backup.txt`처럼 이름표 두 개가 같은 카드를 가리킬 수도 있습니다.
:::

이 구조를 알면 풀리는 수수께끼가 셋 있습니다.

- **이름 바꾸기는 순식간입니다.** 10GB짜리 파일도 목록의 한 줄만 고치면 됩니다. 반면 복사는 내용물을 전부 새로 써야 합니다.
- **지웠는데 공간이 늘지 않을 수 있습니다.** 삭제는 이름표를 떼는 일입니다. 내용물은 남은 이름표가 없고 그 파일을 열어 둔 프로그램도 없을 때 치워집니다. 서버가 열어 놓고 쓰는 로그 파일은 지워도 서버가 닫을 때까지 공간이 돌아오지 않습니다.
- **용량이 남았는데 파일을 못 만들 수 있습니다.** 관리 카드의 장수는 파일 시스템을 만들 때 정해지는 경우가 많습니다. 아주 작은 파일이 수백만 개 쌓이면 선반보다 카드가 먼저 떨어집니다.

```bash
$ df -h /data     # 용량
Filesystem   Size  Used  Avail  Use%
/dev/sdb1    100G   38G    62G   38%
$ df -i /data     # 아이노드 수
Filesystem    Inodes    IUsed  IFree  IUse%
/dev/sdb1    6553600  6553600      0   100%
```

용량은 62GB가 남았지만 아이노드는 100% 찼습니다. 이때 파일을 만들면 `No space left on device` 오류가 납니다. "디스크가 찼다"는 메시지를 보면 두 명령을 모두 확인하세요.

::: {.deep title="파일처럼 보이지만 창고에 없는 것들 (/proc, /dev, FUSE)"}
리눅스에서 경로가 있다고 모두 디스크의 파일은 아닙니다. `/proc`과 `/sys`는 커널이 지금 상태를 파일 모양으로 보여 주는 창구입니다. `/dev`의 파일은 디스크나 터미널 같은 장치로 통하는 문입니다. 이런 경로에 값을 쓰면 문서가 아니라 시스템 설정이 바뀔 수 있습니다.

**FUSE**(Filesystem in Userspace)는 파일 요청을 일반 프로그램이 대신 처리하게 해 줍니다. 원격 서버를 내 폴더처럼 붙일 때 씁니다. 겉은 폴더여도 속은 네트워크라서, 작은 파일 100개를 읽는데 파일마다 왕복 20ms가 들면 기다림만 2초입니다.
:::

::: {.deep title="파일 크기가 두 가지일 때 (희소 파일)"}
크기는 10GB라고 나오는데 디스크에서는 1GB만 차지하는 파일이 있습니다. 아직 쓰지 않은 구간에는 선반 칸을 주지 않기 때문입니다. 이런 파일이 **희소 파일**(sparse file)입니다. `ls -l`은 보이는 길이를, `du`는 실제로 차지한 양을 보여 줍니다. 빈 구간을 살리지 않는 도구로 복사하면 사본은 10GB를 다 차지합니다.
:::

## 창고의 빠르기를 읽는 세 숫자 {#metrics}

"이 식당은 빠르다"는 말은 모호합니다. 음식이 금방 나온다는 뜻일까요, 한 시간에 손님을 많이 받는다는 뜻일까요? 저장장치의 사양표에도 서로 다른 세 숫자가 나옵니다.

| 숫자 | 뜻 | 창고에 빗대면 |
|---|---|---|
| **지연 시간**(latency) | 요청 하나가 끝나기까지 걸린 시간 | 한 번 다녀오는 데 걸린 시간 |
| **처리량**(throughput) | 1초에 옮긴 데이터의 양 | 1초에 나른 재료의 양 |
| **IOPS** | 1초에 처리한 읽기·쓰기 횟수 | 1초에 다녀온 횟수 |

IOPS(Input/Output Operations Per Second)와 처리량은 **한 번에 나르는 양**으로 이어집니다. 한 번에 4KB씩 1,000 IOPS라면 4KB × 1,000 = 초당 4MB입니다. 한 번에 1MB씩이라면 같은 1,000 IOPS가 초당 1,000MB입니다. IOPS만 적힌 숫자는 반쪽짜리입니다.

### 순차 접근과 랜덤 접근

같은 양을 읽어도 **읽는 순서**가 속도를 바꿉니다. 붙어 있는 칸을 차례로 읽는 것이 **순차 접근**(sequential access), 떨어진 칸을 오가며 읽는 것이 **랜덤 접근**(random access)입니다.

::: {.fig src="seq-random.svg"}
칸 안의 숫자는 읽는 순서입니다. 순차 접근은 한 번 찾아가면 끝이지만, 랜덤 접근은 칸마다 새로 찾아가야 합니다.
:::

차이가 가장 큰 장치가 하드디스크입니다.

::: {.photo src="hdd-open.jpg"}
덮개를 연 하드디스크. 은색 원판이 돌아가고, 오른쪽에서 뻗은 팔 끝의 헤드가 그 위를 오가며 읽습니다. 떨어진 곳을 읽으려면 팔이 움직여야 합니다.
:::

팔이 자리를 한 번 옮기는 데 약 10ms가 걸리므로 1초에 100번쯤이 한계입니다. 4KB 조각을 여기저기서 읽으면 초당 0.4MB인데, 한자리에서 이어 읽으면 초당 100MB를 넘깁니다. SSD는 움직이는 팔이 없어 차이가 훨씬 작지만, 요청 하나하나에 드는 고정 비용은 남습니다. **작은 파일 10만 개**가 같은 용량의 **큰 파일 하나**보다 한참 느린 이유입니다. 파일마다 이름표를 찾고 번호표를 받았다 반납하는 일이 10만 번 되풀이됩니다.

::: {.deep title="줄이 길다고 일을 잘하는 것은 아닙니다 (대기열 깊이)"}
저장장치에 보냈지만 아직 끝나지 않은 요청의 수가 **대기열 깊이**(queue depth)입니다. SSD는 여러 요청을 한꺼번에 처리할 수 있어서 동시 요청을 1개에서 4개로 늘리면 처리량이 늘어납니다. 하지만 한계에 닿으면 32개로 늘려도 처리량은 그대로이고 요청마다 기다리는 시간만 늘어납니다. 동시 요청 수를 바꿔 가며 처리량과 지연 시간을 **함께** 기록해야 알맞은 지점이 보입니다.
:::

## 두 번째 실행은 왜 빠를까: 페이지 캐시 {#pagecache}

1GB짜리 파일을 읽는 프로그램을 돌렸더니 2초가 걸렸습니다. 곧바로 다시 돌리니 0.2초입니다. 코드는 한 글자도 바꾸지 않았습니다.

지배인의 습관 때문입니다. 지배인은 창고에서 가져온 재료를 요리사에게 건넨 뒤에도, 조리대에 빈자리가 있으면 **사본을 그대로 놓아둡니다.** 누가 같은 재료를 또 찾으면 창고에 가지 않고 바로 건넵니다. 운영체제가 남는 메모리에 파일 내용을 보관해 두는 이 공간이 **페이지 캐시**(page cache)입니다.

::: {.fig src="page-cache.svg"}
두 번째 실행에서는 디스크에 다녀오지 않습니다. 빨라진 것은 SSD도 코드도 아니고, 읽어 오는 곳입니다.
:::

페이지 캐시를 알면 두 가지 오해를 피합니다.

첫째, **"메모리가 거의 찼다"는 숫자에 놀라지 않습니다.** 리눅스의 `free -h`에서 `buff/cache`로 나오는 양은 잠시 빌려 쓰는 자리입니다. 프로그램이 메모리를 달라고 하면 지배인은 이 자리부터 비워 줍니다. 실제 여유는 `available` 열에 나옵니다.

둘째, **속도를 잴 때 속지 않습니다.** 두 번째 실행이 빨랐다고 코드가 좋아진 것은 아닙니다. 앱을 처음 켠 사용자가 겪는 것은 캐시가 빈 **첫 실행**의 속도입니다.

::: {.deep title="캐시 주변의 기술들 (미리 읽기, mmap, 직접 I/O, DMA)"}
- **미리 읽기**(read-ahead): 파일을 차례로 읽고 있으면 커널이 다음 구간을 미리 가져다 둡니다.
- **메모리 매핑**(mmap): 파일을 프로세스의 메모리 주소에 이어 붙여 배열처럼 읽습니다. 건드린 페이지만 그때그때 올라옵니다.
- **직접 I/O**(direct I/O): 페이지 캐시를 거치지 않고 읽고 씁니다. 자기 캐시를 따로 가진 데이터베이스가 씁니다. 디스크에 안전하게 기록됐다는 뜻은 아닙니다.
- **DMA**(Direct Memory Access): 장치가 메모리에 데이터를 직접 옮겨 놓는 하드웨어 기능입니다. CPU가 바이트를 하나하나 나르지 않아도 됩니다.
:::

## 모아서 한 번에 나르기: 버퍼링 {#buffer}

양파 100개가 필요한 요리사가 하나 쓸 때마다 창고에 다녀오지는 않습니다. 쟁반에 담아 한 번에 나릅니다.

프로그램도 그렇습니다. 한 줄 쓸 때마다 커널을 부르면 부탁 한 번에 드는 고정 비용이 줄 수만큼 되풀이됩니다. 그래서 대부분의 언어는 쓸 내용을 메모리의 작은 공간에 모았다가 가득 차면 한 번에 넘깁니다. 이 공간이 **버퍼**(buffer), 이렇게 모아서 처리하는 방식이 **버퍼링**(buffering)입니다.

::: {.fig src="buffer-tray.svg"}
버퍼가 100줄을 담는다면 커널을 부르는 횟수가 1,000번에서 10번으로 줄어듭니다.
:::

파이썬의 `open()` 같은 파일 도구에는 버퍼가 이미 들어 있습니다. 문제는 쟁반의 대가입니다. **쟁반에 담긴 것은 아직 창고에 가지 않았습니다.**

- 로그를 썼는데 파일을 열어 보면 비어 있습니다. 버퍼가 아직 차지 않아서입니다.
- 프로그램이 갑자기 죽으면 버퍼에 남은 마지막 몇 줄이 사라집니다. 하필 그 몇 줄이 가장 필요한 줄입니다.

쟁반이 차지 않았어도 "지금 넘겨"라고 시키는 것이 **flush**(플러시)입니다. 파이썬에서는 `f.flush()`, 화면 출력이라면 `print(..., flush=True)`입니다. 파일을 닫을 때는 자동으로 flush됩니다.

::: {.tip title="모으기는 처리량과 지연 시간의 맞바꿈입니다"}
많이 모을수록 전체는 빨리 끝나지만 먼저 온 것은 쟁반이 찰 때까지 기다립니다. 사진 100장을 한꺼번에 처리하면 10초 뒤에 모두 나오고, 한 장씩 처리하면 전체는 12초여도 첫 장은 0.1초 만에 나옵니다. 버퍼에는 "100줄이 차거나 1초가 지나면 내보낸다"처럼 **크기와 시간의 상한**을 함께 두세요.
:::

## "저장했습니다"는 어디까지 갔다는 뜻일까 {#durable}

flush를 했으니 이제 안전할까요? 정거장이 하나 더 있습니다. 앞에서 본 페이지 캐시입니다. 커널은 넘겨받은 데이터를 페이지 캐시에 올려놓고 "받았습니다"라고 답한 뒤, 창고에는 **잠시 뒤 틈날 때** 내려놓습니다. 쓰기도 모아서 하는 편이 빠르기 때문입니다.

::: {.fig src="save-stations.svg"}
데이터가 어느 정거장까지 갔느냐에 따라, 사고가 났을 때 남는 것이 달라집니다.
:::

"쓰기 성공"에는 그래서 세 가지 뜻이 섞여 있습니다. ①에만 있으면 프로그램이 죽을 때 함께 사라집니다. ②까지 갔으면 프로그램이 죽어도 커널이 마저 기록하지만, 그 전에 전원이 나가면 사라집니다. ③까지 가야 정전에도 남습니다.

②에서 ③으로 "지금 내려놓고, 끝나면 알려 주세요"라고 부탁하는 시스템 호출이 **fsync**입니다. 안전한 대신 느립니다. 로그 한 줄마다 부르면 줄마다 창고 왕복을 기다립니다. 디버그 로그라면 ②로 충분하고, 결제 기록이라면 ③이 필요합니다.

::: {.key}
**"썼다"와 "디스크에 있다"는 다른 말입니다.** 이 데이터가 어떤 사고까지 견뎌야 하는지 먼저 정하세요.
:::

### 파일을 안전하게 바꿔 쓰기

설정을 저장하는 가장 흔한 코드는 원래 파일을 열어 새 내용으로 덮어쓰는 것입니다. 쓰는 도중에 프로그램이 죽으면 반쯤 쓰인 파일만 남습니다. 옛 설정은 지워졌고 새 설정은 완성되지 않았습니다.

해법은 앞에서 본 이름표입니다. 이름 바꾸기는 목록의 한 줄만 고치므로 **중간 상태가 없습니다.**

::: {.fig src="safe-replace.svg"}
위: 원본을 직접 고치다 죽으면 반쪽 파일이 남습니다. 아래: 임시 파일을 완성한 뒤 이름표만 바꿔 답니다.
:::

```python
import os

with open("settings.json.tmp", "w") as f:
    f.write(new_text)        # ① 임시 파일에 전부 쓴다
    f.flush()                #    프로그램 버퍼 → 커널
    os.fsync(f.fileno())     # ② 커널 → 디스크
os.replace("settings.json.tmp", "settings.json")   # ③ 이름 바꾸기
```

어느 줄에서 죽어도 `settings.json`은 온전한 옛 파일이거나 온전한 새 파일입니다. 이렇게 "전부 아니면 전무"로 일어나는 성질을 **원자적**(atomic)이라고 합니다. 임시 파일은 **같은 폴더**에 만드세요. 다른 디스크에 있으면 이름표만 바꿔 달 수가 없습니다.

::: {.deep title="파일 시스템은 자기 장부를 어떻게 지킬까 (저널링)"}
파일 하나를 만들 때도 이름표 목록, 관리 카드, 빈 칸 목록을 차례로 고쳐야 합니다. 그 사이에 전원이 나가면 장부끼리 말이 맞지 않습니다. 그래서 파일 시스템은 고칠 내용을 **저널**(journal)이라는 일지에 먼저 적고, 다시 켜지면 일지를 보고 하다 만 작업을 마무리하거나 되돌립니다. 이것이 **저널링**(journaling)입니다.

저널링이 지키는 것은 주로 **파일 시스템 자신의 장부**이지, 내 앱이 방금 쓴 내용이 아닙니다. 그것은 여전히 fsync와 안전한 교체의 몫입니다. 위 코드도 정전까지 견디려면 이름을 바꾼 뒤 폴더에 fsync를 해야 합니다. 직접 짜기보다 검증된 라이브러리의 '원자적 쓰기' 기능을 쓰세요.
:::

## 다 올릴까, 흘려보낼까: 스트리밍과 압축 {#stream}

10GB짜리 로그 파일에 `ERROR`가 몇 번 나오는지 세려고 합니다.

```python
with open("access.log") as f:        # 통째로 올리기
    count = f.read().count("ERROR")

count = 0                            # 한 줄씩 흘려보내기
with open("access.log") as f:
    for line in f:
        count += line.count("ERROR")
```

위의 두 줄은 10GB를 전부 조리대에 올립니다. RAM이 8GB라면 올리다가 죽습니다. 아래 코드는 한 줄을 읽어 세고 버린 뒤 다음 줄로 넘어갑니다. 조리대에는 언제나 한 줄과 작은 버퍼만 있습니다. 이렇게 조금씩 읽어 처리하고 넘어가는 방식이 **스트리밍**(streaming)입니다. [5장](ch05.html)의 파이프도 이렇게 일합니다.

::: {.fig src="load-vs-stream.svg"}
통째로 올리면 필요한 메모리가 파일 크기를 따라 커집니다. 흘려보내면 파일이 아무리 커도 한 줄 몫이면 됩니다.
:::

스트리밍은 **조각마다 따로 처리할 수 있을 때** 통합니다. 낱말 세기는 되지만, 전체 정렬처럼 멀리 떨어진 줄끼리 비교해야 하는 일은 흘려보내기만으로 끝나지 않습니다. 확인법은 간단합니다. 입력을 10배로 키워도 메모리 최고 사용량이 비슷하면 됩니다.

::: {.warn}
AI 도구는 작은 예제를 기준으로 `read()`나 `json.load()`처럼 통째로 올리는 코드를 자주 씁니다. 시험 파일에서는 잘 돌다가 실제 데이터 5GB를 만나면 죽습니다. 입력 크기에 상한이 없다면 스트리밍을 요청하세요.
:::

### 압축: CPU 시간을 주고 용량을 삽니다

**압축**(compression)은 데이터를 더 짧게 바꿔 적는 일입니다. 나를 짐은 줄지만 싸고 푸는 데 요리사의 손이 듭니다. 이득인지는 **어디가 좁은 길인지**에 달렸습니다. 100MB 로그를 20MB로 압축해 보낸다고 합시다. 압축에 2초, 푸는 데 1초가 듭니다.

| 회선 속도 | 그냥 보내기 | 압축해서 보내기 |
|---|---|---|
| 초당 10MB | 100 ÷ 10 = 10초 | 2 + (20 ÷ 10) + 1 = **5초** |
| 초당 100MB | 100 ÷ 100 = **1초** | 2 + (20 ÷ 100) + 1 = 3.2초 |

길이 좁으면 압축이 이기고, 길이 넓으면 압축이 오히려 발목을 잡습니다. 또 JPEG 사진이나 MP4 영상처럼 **이미 압축된 파일**은 다시 압축해도 거의 줄지 않고 CPU만 씁니다.

## 느린 곳 찾기: 추측하지 말고 재기 {#measure}

기다림이 생기는 곳을 여럿 봤습니다. 실제 문제 앞에서는 그중 **어디가** 범인인지 알아야 합니다. [1장](ch01.html)에서 본 대로 전체 속도는 가장 좁은 곳인 병목이 정하기 때문입니다.

먼저 가를 것은 첫 절의 질문입니다. **CPU가 바쁜가, I/O를 기다리는가?** 리눅스 서버라면 `top`과 `iostat -x 1` 두 명령으로 봅니다.

::: {.fig src="cpu-or-wait.svg"}
같은 "느리다"라도 숫자의 모양이 다릅니다. 코어가 하나일 때의 예이며, 코어가 여럿이면 숫자가 그만큼 나뉘어 작게 보입니다.
:::

- `us`는 CPU가 프로그램의 계산에 쓴 시간의 비율입니다.
- `wa`는 CPU가 쉬고 있었는데 그동안 **디스크의 답을 기다리는 일이 걸려 있던** 시간의 비율입니다.
- `%util`은 디스크가 요청을 처리하느라 바빴던 시간의 비율입니다.

A라면 계산을 줄이거나 여러 코어에 나눕니다. B라면 읽고 쓰는 횟수와 양을 줄입니다. 이 장에서 본 버퍼링, 캐시, 순차 접근이 그 처방입니다.

::: {.warn title="셋 다 낮은데 느릴 때"}
서버 응답 같은 **네트워크 기다림은 `wa`에 잡히지 않고** 그냥 한가한 시간으로 보입니다. CPU도 디스크도 노는데 느리다면 외부 서버나 데이터베이스, [11장](ch11.html)의 락을 기다리는 중일 수 있습니다. 단계마다 시작과 끝 시각을 로그로 남겨 어느 구간이 긴지 직접 재세요.
:::

::: {.try}
터미널에서 명령 앞에 `time`을 붙여 보세요.

```bash
$ time python3 report.py
real    0m5.012s
user    0m0.184s
sys     0m0.031s
```

`real`이 경과 시간, `user`와 `sys`의 합이 CPU 시간입니다. 맥의 기본 셸에서는 한 줄로 나오고, `total`이 경과 시간입니다.
:::

### 재는 사람이 지킬 세 가지

1. **고치기 전에 잽니다.** 어느 함수가 시간을 쓰는지 기록하는 도구가 **프로파일러**(profiler)입니다. 다만 CPU 프로파일러는 계산 시간만 보여 주므로, 기다림은 경과 시간으로 따로 잽니다.
2. **같은 조건으로 비교합니다.** 같은 입력, 같은 컴퓨터로 고치기 전과 후를 여러 번 잽니다. 한 번씩만 재면 우연한 차이를 개선으로 착각합니다. 잰 값을 요약하는 법은 [13장](ch13.html)에서 배웠습니다.
3. **캐시 상태를 적습니다.** 고치기 전은 첫 실행, 고친 뒤는 두 번째 실행으로 쟀다면 페이지 캐시의 효과를 본 것입니다.

### 조리대가 모자라면 디스크가 바빠집니다

`wa`가 높다고 늘 파일 탓은 아닙니다. [3장](ch03.html)의 **스왑**이 범인일 수 있습니다. 메모리가 모자라면 운영체제는 한동안 안 쓴 페이지를 디스크로 내보내고, 필요해지면 다시 불러옵니다.

RAM이 8GB인 서버에서 영상 하나를 변환하는 데 1.5GB가 든다고 합시다. 4개를 함께 돌리면 6GB라 괜찮습니다. 빨리 끝내려고 20개를 돌리면 30GB가 필요합니다. 운영체제는 방금 내보낸 페이지를 곧바로 다시 불러와야 하고, 그러려면 다른 페이지를 또 내보내야 합니다. 요리사는 요리는 못 하고 조리대와 창고 사이에서 재료만 나릅니다. 이 상태가 **스래싱**(thrashing)입니다. 동시 작업을 늘렸는데 끝나는 작업은 오히려 줄어듭니다. 처방은 **한꺼번에 펼치는 양에 상한을 두는 것**입니다.

::: {.key}
병목이 아닌 곳을 고치면 시간은 그대로입니다. **고치기 전에 재고, 고친 뒤에 다시 잽니다.**
:::

::: {.deep title="가장 좁은 구간이 전체 속도를 정합니다"}
디스크는 초당 500MB를 읽는데 네트워크는 초당 100MB만 보낸다면, 파일 전송 전체는 초당 100MB를 넘지 못합니다. 디스크를 두 배 빠른 것으로 바꿔도 그대로입니다. 장치 하나의 최고 속도가 아니라 **경로에서 가장 좁은 구간**을 찾으세요. 그곳을 넓히면 다음으로 좁은 곳이 새 병목이 됩니다.
:::

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 경과 시간 / CPU 시간 | 벽시계로 잰 전체 시간 / 그중 CPU가 실제로 계산한 시간 |
| 처리량 / IOPS | 1초에 옮긴 양 / 1초에 다녀온 횟수. 한 번의 크기를 곱해야 이어짐 |
| 버퍼 / 캐시 | 내보낼 것을 잠시 모아 두는 곳 / 다시 쓸 것을 가까이 남겨 두는 곳 |
| flush / fsync | 프로그램 버퍼에서 커널로 넘기기 / 커널에서 디스크까지 기록을 마치기 |
| 이름 바꾸기 / 복사 | 이름표 한 줄 고치기 / 내용물을 전부 새로 쓰기 |

## 실전 사례 {#case}

::: {.case title="최신 SSD인데 메모 10만 개를 검색하면 40초가 걸린다"}
메모 하나를 작은 텍스트 파일 하나로 저장하는 앱입니다. 큰 영상은 초당 2GB로 복사되는 SSD인데, 메모 10만 개에서 낱말을 찾는 데 40초가 걸립니다.

1. **계산인지 기다림인지 가릅니다.** `time`으로 재니 40초 가운데 CPU 시간은 6초입니다. 대부분 기다림입니다.
2. **단계를 나눠 잽니다.** 파일 열고 닫기, 읽기, 낱말 찾기를 따로 재니 열고 닫는 데 가장 오래 걸립니다. 메모는 평균 2KB라 다 합쳐도 200MB인데, 열고 닫기를 10만 번 되풀이하고 있었습니다.
3. **맞는 숫자를 봅니다.** "초당 2GB"는 큰 파일을 순차로 읽을 때의 처리량입니다. 이 작업은 작은 요청을 1초에 몇 번 처리하느냐에 달렸습니다.
4. **왕복 횟수를 줄입니다.** 메모 본문을 검색용 파일 하나에 모아 두고 순차로 읽게 바꿉니다.
5. **같은 조건으로 확인합니다.** 첫 실행과 반복 실행을 따로 잽니다. 첫 실행이 40초에서 3초로 줄었습니다. 검색 결과가 예전과 같은지도 비교합니다.

사양표의 최고 속도는 내 작업의 속도가 아닙니다. 내 프로그램이 **어떤 크기의 요청을 몇 번** 보내는지가 먼저입니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- 프로그램이 느린 이유는 대개 계산이 아니라 **I/O를 기다리는 시간**입니다. 경과 시간과 CPU 시간을 비교하면 드러납니다.
- 파일을 열면 번호표인 **파일 디스크립터**를 받습니다. 파일 시스템은 **이름표와 내용물을 따로** 관리해서, 이름 바꾸기는 빠르고 아이노드가 떨어지면 용량이 남아도 파일을 못 만듭니다.
- 저장장치의 빠르기는 **지연 시간, 처리량, IOPS**로 나눠 읽습니다. 흩어진 작은 요청은 이어진 큰 요청보다 훨씬 느립니다.
- **페이지 캐시와 버퍼**는 창고 왕복을 줄여 주지만 "썼다"와 "디스크에 있다" 사이에 틈을 만듭니다. 그 틈을 메우는 것이 flush와 fsync, 임시 파일에 쓴 뒤 이름 바꾸기입니다.
- 큰 입력은 통째로 올리지 말고 **스트리밍**으로 흘려보냅니다. 압축은 CPU 시간을 주고 용량을 사는 거래입니다.
- **추측하지 말고 잽니다.** 같은 조건으로, 캐시 상태를 구분해서, 고치기 전과 후를 비교합니다.
:::

## 확인 문제 {#quiz}

::: {.q}
요청 하나가 5초 걸리는데 CPU 시간은 0.2초입니다. 동료가 "함수 A가 CPU 프로파일의 절반을 차지하니 A를 고치자"고 합니다. A를 아예 없애면 얼마나 빨라질까요?

::: {.a}
0.1초입니다. A는 CPU 시간 0.2초의 절반을 쓸 뿐입니다. 나머지 4.8초는 기다림이니 무엇을 기다리는지부터 찾아야 합니다.
:::
:::

::: {.q}
같은 파일을 읽는 속도를 두 번 쟀더니 두 번째가 10배 빨랐습니다. "이 SSD는 충분히 빠르다"고 결론 내려도 될까요?

::: {.a}
안 됩니다. 두 번째는 디스크가 아니라 페이지 캐시, 곧 RAM에서 읽었을 가능성이 큽니다. SSD의 속도는 캐시가 빈 첫 실행으로 판단해야 합니다.
:::
:::

::: {.q}
서버 디스크가 꽉 차서 20GB짜리 로그 파일을 지웠습니다. 그런데 `df -h`의 여유 공간이 그대로입니다. 왜 그럴까요?

::: {.a}
삭제는 이름표를 떼는 일입니다. 서버 프로그램이 그 파일을 아직 열어 두고 있다면 내용물은 치워지지 않습니다. 프로그램이 파일을 닫아야 공간이 돌아옵니다.
:::
:::

::: {.q}
프로그램이 오류로 죽었는데, 죽기 직전의 로그 몇 줄이 파일에 없습니다. 원인은 무엇이고, 줄마다 fsync를 부르는 해법은 왜 지나칠까요?

::: {.a}
마지막 줄들이 프로그램 버퍼에 남아 있다가 프로세스와 함께 사라졌습니다. 프로그램이 죽는 사고는 flush로 커널에 넘기기만 해도 막습니다. fsync는 정전에 대비하는 수단이라, 줄마다 부르면 매번 디스크를 기다리느라 크게 느려집니다.
:::
:::

::: {.q}
영상 변환 서버의 동시 작업 수를 4에서 20으로 올렸더니 한 시간에 끝나는 작업 수가 오히려 줄고 `wa`가 치솟았습니다. 무슨 일일까요?

::: {.a}
작업들이 쓰는 메모리의 합이 RAM을 넘어, 페이지를 내보내고 불러오기를 되풀이하는 스래싱에 빠졌습니다. 스왑 사용량을 확인하고 동시 작업 수에 상한을 둡니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI 코딩 도구는 입력이 커지거나 도중에 죽는 상황을 시키지 않으면 따져 보지 않습니다. 성능 조사를 맡길 때는 **무엇을 어떤 조건에서 잴지**를 요청문에 넣으세요.

> 대용량 로그 검색이 느린 원인을 조사해 줘. 같은 입력 파일로 읽기, 검색, 출력 단계의 시간을 나눠 재고, 경과 시간과 CPU 시간, 메모리 최고 사용량을 표로 보여 줘. 첫 실행과 반복 실행은 따로 기록해. 그다음 파일을 통째로 읽는 방식과 한 줄씩 스트리밍하는 방식을 비교해 줘. 검색 결과가 이전과 완전히 같을 것, 입력을 10배로 키워도 메모리가 비슷할 것, 시간이 실제로 줄어들 것을 완료 조건으로 해.

**받은 답에서 확인할 것**: 추측이 아니라 측정값이 있는가, 첫 실행과 반복 실행을 구분했는가, 고치기 전후를 같은 입력으로 쟀는가, `read()`처럼 통째로 올리는 코드가 남아 있지 않은가.
:::

## 용어 정리 {#terms}

::: {.terms}
입출력 (I/O, Input/Output)
:   CPU와 메모리 바깥(디스크, 네트워크 등)과 데이터를 주고받는 일.

경과 시간 (elapsed time)
:   시작부터 끝까지 벽시계로 잰 시간. 그중 CPU가 계산한 몫이 CPU 시간이다.

파일 디스크립터 (FD, file descriptor)
:   열린 파일이나 연결을 가리키는 번호표. 작은 정수다.

아이노드 (inode)
:   파일의 크기, 권한, 내용물의 위치를 적어 둔 관리 카드. 이름은 디렉터리에 따로 있다.

처리량 (throughput)
:   1초에 처리한 데이터의 양.

IOPS (Input/Output Operations Per Second)
:   저장장치가 1초에 처리한 읽기·쓰기 횟수.

순차 접근 (sequential access)
:   붙어 있는 위치를 차례로 읽고 쓰는 방식. 떨어진 곳을 오가는 랜덤 접근보다 빠르다.

페이지 캐시 (page cache)
:   운영체제가 남는 메모리에 파일 내용을 보관해 두는 공간.

버퍼 (buffer)
:   데이터를 내보내기 전에 잠시 모아 두는 메모리 공간.

flush (플러시)
:   버퍼에 모인 데이터를 지금 바로 다음 단계로 넘기는 일.

fsync
:   커널이 맡아 둔 변경을 디스크에 기록하고 끝날 때까지 기다리는 시스템 호출.

원자적 (atomic)
:   중간 상태 없이 전부 일어나거나 전혀 일어나지 않는 성질.

스트리밍 (streaming)
:   입력을 통째로 올리지 않고 조금씩 읽어 처리하는 방식.

스래싱 (thrashing)
:   메모리가 모자라 페이지를 내보내고 불러오는 데 시간을 다 쓰는 상태.
:::
