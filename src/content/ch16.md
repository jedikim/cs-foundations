::: {.lead}
책상 위에 있는 연필은 바로 집을 수 있습니다. 창고에 있는 연필은 가지러 다녀와야 합니다. 컴퓨터도 같습니다. 계산은 눈 깜짝할 사이에 하지만, 파일을 읽거나 인터넷에서 무언가를 받아 오는 일은 훨씬 오래 걸립니다. 프로그램이 느릴 때는 대개 계산이 아니라 이 '다녀오는 시간' 때문입니다. 이 장에서는 그 시간이 어디서 생기고 어떻게 줄이는지 배웁니다.
:::

::: {.goals}
- 프로그램이 계산하느라 느린지 기다리느라 느린지 구분할 수 있습니다.
- 파일을 열고 읽고 저장할 때 컴퓨터 안에서 일어나는 일을 설명할 수 있습니다.
- 같은 파일을 두 번째 읽을 때 더 빠른 이유를 설명할 수 있습니다.
- 큰 파일을 조금씩 나눠 처리하는 방법을 알 수 있습니다.
- 파일을 못 찾는다는 오류를 읽고, 남이 올리는 파일을 받을 때 정할 것을 말할 수 있습니다.
:::

## 느린 프로그램은 대부분 기다리는 중입니다 {#io}

[1장](ch01.html)에서 컴퓨터를 식당 주방에 빗댔습니다. CPU는 요리사, 메모리는 조리대, 저장장치는 창고였습니다. 요리사의 칼질은 아주 빠릅니다. 하지만 재료가 창고에 있으면 가지러 다녀와야 합니다.

1장의 '속도의 사다리'를 떠올려 봅시다. CPU가 바로 곁에서 값 하나를 꺼내는 시간을 1초로 늘리면 메모리는 2분, SSD는 하루가 걸렸습니다. 바다 건너 컴퓨터는 5년이었습니다.

CPU와 메모리 바깥에서 데이터를 가져오거나 내보내는 일을 **입출력**이라고 합니다. 영어 Input/Output을 줄여 I/O라고도 씁니다. 파일을 읽는 일, 인터넷으로 무언가를 주고받는 일이 모두 입출력입니다.

게임에서 '랭킹 보기' 버튼을 눌렀더니 5초 뒤에야 화면이 떴다고 합시다. 그 5초를 펼쳐 보면 이렇습니다.

::: {.fig src="wait-timeline.svg"}
5초 가운데 CPU가 계산한 시간은 파란 조각 두 개, 0.2초뿐입니다. 나머지는 기다린 시간입니다.
:::

띠를 왼쪽부터 읽습니다. 0.1초 계산하고, 내 기록 파일을 읽느라 디스크를 1.8초 기다립니다. **디스크**(disk)는 저장장치를 흔히 부르는 말입니다. 다시 0.1초 계산하고, 게임 회사의 서버에 순위를 물어봅니다. 서버는 1장에서 본, 부탁을 받아 처리해 주는 컴퓨터입니다. 대답이 올 때까지 3.0초를 기다립니다. 그림의 '응답'은 대답이라는 뜻입니다.

이 5초를 재는 시계는 두 개입니다. 하나는 벽시계입니다. 버튼을 누른 순간부터 화면이 뜬 순간까지 잽니다. 이 시간을 **경과 시간**(elapsed time)이라고 합니다. 여기서는 5초입니다.

다른 하나는 CPU가 계산한 시간만 잽니다. 이 시간을 **CPU 시간**(CPU time)이라고 합니다. 0.1 + 0.1 = 0.2초입니다. 나머지 5 − 0.2 = 4.8초 동안 요리사는 창고 문 앞에서 기다렸습니다.

계산을 두 배 빠르게 고치면 0.2초가 0.1초로 줄어듭니다. 전체는 5.0초에서 4.9초가 됩니다. 거의 그대로입니다. 서버를 기다리는 3.0초를 절반으로 줄이면 1.5초가 줄어듭니다. 전체는 3.5초가 됩니다.

AI가 만들어 준 앱이 느릴 때도 같습니다. 화면이 늦게 뜬다면 대개 파일을 읽거나 다른 컴퓨터의 대답을 기다리는 중입니다. 그래서 "코드를 더 빠르게 짜 줘"보다 "무엇을 기다리는지 찾아 줘"가 먼저입니다.

::: {.key}
프로그램이 느리면 먼저 물어봅니다. **경과 시간 가운데 CPU 시간은 얼마인가?** 둘의 차이가 크면 범인은 계산이 아니라 기다림입니다.
:::

## 파일을 연다는 것: 번호표와 책갈피 {#open}

식당 창고에는 아무나 들어가지 못합니다. 열쇠를 가진 지배인에게 부탁해야 합니다. 컴퓨터에서 이 지배인이 [3장](ch03.html)에서 본 커널(kernel)입니다. 운영체제의 핵심 부분이고, 저장장치는 커널만 직접 다룹니다.

프로그램이 커널에게 하는 부탁이 3장에서 본 시스템 호출(system call)입니다. 파일 하나를 읽으려면 적어도 세 가지를 부탁합니다. 열기, 읽기, 닫기입니다.

"열어 주세요" 하면 커널은 대여 장부에 한 줄을 적고 번호표를 내줍니다. 이 번호표를 **파일 디스크립터**(file descriptor)라고 합니다. 줄여서 FD라고 씁니다. 3이나 4 같은 작은 숫자입니다.

0번, 1번, 2번은 처음부터 키보드 입력, 화면 출력, 오류 출력에 쓰입니다. 그래서 처음 연 파일은 보통 3번을 받습니다.

장부에는 **어디까지 읽었는지**를 나타내는 책갈피도 함께 적힙니다.

::: {.fig src="fd-bookmark.svg"}
프로그램이 쥔 것은 3이라는 숫자뿐입니다. 어느 파일인지, 어디까지 읽었는지는 커널의 장부가 기억합니다.
:::

그림의 `memo.txt`에는 ABCDEF 여섯 글자가 들어 있습니다. 이 파일을 두 글자씩 읽어 봅시다. 아래는 파이썬(Python)이라는 프로그래밍 언어로 쓴 코드입니다. 코드를 처음 본다면 [초코딩 기초](code.html)를 먼저 보세요.

`#` 뒤의 글은 사람이 읽으라고 달아 둔 메모입니다. 주석이라고 하고, 컴퓨터는 건너뜁니다.

```python
f = open("memo.txt")   # 번호표를 받음. 책갈피는 0
f.read(2)              # "AB" — 책갈피가 2로 이동
f.read(2)              # "CD" — 이어서 읽음
f.close()              # 번호표 반납
```

- 첫째 줄의 `open`은 "열어 주세요"입니다. 열린 파일에 `f`라는 이름을 붙입니다. 번호표는 `f` 안에 들어 있습니다. 아직 읽은 것이 없어 책갈피는 0입니다.
- 둘째 줄의 `read(2)`는 "두 글자 주세요"입니다. `AB`를 받고 책갈피는 2로 갑니다. 그림이 이 순간입니다.
- 셋째 줄도 똑같이 `read(2)`인데 `CD`가 나옵니다. 어디서부터 읽을지는 책갈피가 정하기 때문입니다.
- 넷째 줄의 `close`는 번호표를 돌려주는 부탁입니다.

번호표는 꼭 돌려줘야 합니다. 장부의 줄 수에는 한도가 있습니다. 돌려주지 않은 번호표가 쌓이면 새 파일을 열지 못합니다. 이때 나오는 오류가 [3장](ch03.html)에서 본 `Too many open files`입니다. "열어 둔 파일이 너무 많다"는 뜻입니다.

3장에서 이름만 본 `with` 문법이 이럴 때 쓰입니다. `with open("memo.txt") as f:`처럼 열면 일이 끝날 때 저절로 닫힙니다. 도중에 오류가 나도 닫힙니다.

### 파일을 못 찾을 때: 지금 폴더부터 봅니다

"열어 주세요" 했는데 커널이 그 이름의 파일을 찾지 못할 때가 있습니다. AI가 만든 프로그램을 처음 돌릴 때 자주 겪는 일입니다. 파이썬은 이런 글을 내고 멈춥니다.

```text
FileNotFoundError: [Errno 2] No such file or directory: 'data/settings.json'
```

`No such file or directory`는 "그런 파일이나 폴더가 없다"는 뜻입니다. 끝의 따옴표 안이 프로그램이 찾으려던 경로입니다. 자바스크립트라는 언어로 쓴 프로그램에서는 같은 일이 `ENOENT: no such file or directory`로 나옵니다.

파일이 분명히 있는데도 이 오류가 날 때가 많습니다. `data/settings.json`은 [5장](ch05.html#path)에서 본 상대 경로입니다. 상대 경로는 코드 파일이 놓인 폴더가 아니라 **프로그램을 실행한 폴더**에서 출발합니다. 게임 폴더 `mygame` 안에서 실행하면 `mygame/data/settings.json`을 찾습니다. 한 칸 위 폴더에서 실행하면 거기서 `data` 폴더를 찾다가 실패합니다.

이 오류를 만나면 세 가지를 차례로 봅니다.

1. **오류 글 끝의 경로.** 철자, 대문자와 소문자, 확장자가 실제 파일과 같은지 견줍니다.
2. **지금 폴더.** 터미널에 `pwd`를 치면 나옵니다.
3. **그 폴더에서 출발한 길.** `ls data`처럼 쳐서 파일이 정말 있는지 봅니다.

AI에게는 오류 글 전체와 `pwd`의 결과를 함께 줍니다. 같은 오류가 되풀이되면 "어느 폴더에서 실행해도 되게, 코드 파일이 있는 폴더를 기준으로 경로를 잡아 줘"라고 부탁합니다.

::: {.try}
터미널에 아래 명령을 칩니다. 없는 파일을 열어 보는 한 줄짜리 파이썬 프로그램입니다. 읽으려고만 하니 바뀌는 것은 없습니다. 윈도우에서는 `python3` 대신 `python`이라고 칩니다.

```bash
python3 -c "open('nofile.txt')"
```

맨 아랫줄에 `No such file or directory: 'nofile.txt'`가 보입니다. 이어서 `pwd`를 쳐 봅니다. 프로그램은 거기 적힌 폴더에서 `nofile.txt`를 찾았습니다.
:::

## 이름표와 내용물은 따로 보관됩니다 {#inode}

10GB짜리 영상 파일의 이름을 바꾸면 눈 깜짝할 사이에 끝납니다. 그런데 USB 메모리에 복사하면 한참 걸립니다. 왜 이렇게 다를까요?

창고는 파일 하나를 세 군데에 나눠 적어 둡니다.

- **이름표 목록.** "`report.txt`는 1042번 카드"처럼 이름과 카드 번호만 적혀 있습니다.
- **관리 카드.** 크기, 주인, 누가 읽고 쓸 수 있는지(권한), 마지막으로 고친 시각이 적혀 있습니다. 내용물이 선반의 몇 번 칸에 있는지도 적혀 있습니다.
- **내용물.** 선반의 칸에 들어 있는 진짜 데이터입니다.

::: {.fig src="inode-map.svg"}
이름표, 관리 카드, 내용물은 서로 다른 곳에 있습니다. `report.txt`와 `backup.txt`처럼 이름표 두 개가 같은 카드를 가리킬 수도 있습니다.
:::

`report.txt`를 열려면 먼저 왼쪽 목록에서 이름을 찾습니다. 1042라고 적혀 있습니다. 가운데의 1042번 카드를 봅니다. 크기는 12KB이고 내용물은 88, 89, 90번 칸에 있습니다. 오른쪽 선반에서 그 세 칸을 읽습니다. `photo.jpg`도 같은 식으로 1043번 카드를 거칩니다.

리눅스와 맥이 파일을 이렇게 보관합니다. 그림 맨 위에는 셋을 부르는 이름도 적혀 있습니다. 관리 카드는 **아이노드**(inode)라고 부릅니다.

내용물이 담긴 칸은 **블록**(block)이라고 부릅니다.

이름표 목록은 우리가 아는 폴더입니다. [5장](ch05.html)에서는 디렉터리라고도 불렀습니다. 폴더는 상자처럼 보이지만 실제로는 "이름 → 카드 번호"를 적은 목록입니다.

이제 궁금증이 풀립니다.

- **이름 바꾸기**는 왼쪽 목록의 글자만 고칩니다. 10GB짜리도 금방 끝납니다.
- **복사**는 내용물을 처음부터 끝까지 새 칸에 다시 적습니다. 그래서 오래 걸립니다.
- **옮기기**는 어디로 옮기느냐에 따라 다릅니다. 같은 저장장치 안에서는 이름표만 다른 목록으로 옮겨 적어서 금방 끝납니다. USB 메모리 같은 다른 저장장치로 옮기면 내용물을 새로 적어야 해서 복사만큼 걸립니다.
- **삭제**는 이름표를 떼는 일입니다. 그림의 1042번 카드에는 이름표가 두 개 붙어 있습니다. `report.txt`를 지워도 `backup.txt`가 남아 있으니 내용물은 그대로입니다.

내용물이 치워지는 것은 이름표가 하나도 안 남고, 그 파일을 열어 둔 프로그램도 없을 때입니다.

## 창고의 빠르기를 읽는 세 숫자 {#metrics}

"저 분식집은 빠르다"는 말은 두 가지로 들립니다. 떡볶이가 금방 나온다는 뜻일 수도 있고, 한 시간에 손님을 많이 받는다는 뜻일 수도 있습니다.

저장장치의 빠르기도 숫자 하나로는 말할 수 없습니다. 보통 세 숫자로 나타냅니다. 앞의 둘은 [13장](ch13.html)에서 본 것입니다.

| 숫자 | 뜻 | 창고에 빗대면 |
|---|---|---|
| **지연 시간**(latency) | 부탁 하나가 끝나기까지 걸린 시간 | 한 번 다녀오는 데 걸린 시간 |
| **처리량**(throughput) | 1초에 옮긴 데이터의 양 | 1초에 나른 재료의 양 |
| **IOPS** | 1초에 읽거나 쓴 횟수 | 1초에 다녀온 횟수 |

횟수와 양은 다릅니다. 똑같이 1초에 100번 다녀와도 한 번에 4KB씩 나르면 0.4MB, 1MB씩 나르면 100MB입니다. 횟수는 **한 번에 얼마씩** 나르는지와 함께 봐야 합니다.

### 차례로 읽기와 여기저기 읽기

교과서를 1쪽부터 8쪽까지 차례로 읽기는 쉽습니다. 17쪽, 3쪽, 25쪽처럼 흩어진 여덟 쪽을 읽으려면 쪽을 찾느라 더 오래 걸립니다.

저장장치도 같습니다. 붙어 있는 칸을 차례로 읽는 것을 **순차 접근**(sequential access)이라고 합니다.

떨어진 칸을 오가며 읽는 것은 **랜덤 접근**(random access)이라고 합니다.

::: {.fig src="seq-random.svg"}
칸 안의 숫자는 읽는 순서입니다. 순차 접근은 한 번 찾아가면 끝이지만, 랜덤 접근은 칸마다 새로 찾아가야 합니다.
:::

차이가 가장 큰 장치가 하드디스크입니다.

::: {.photo src="hdd-open.jpg"}
덮개를 연 하드디스크입니다. 은색 원판이 돌고, 오른쪽에서 뻗은 팔의 끝이 그 위를 오가며 읽습니다. 떨어진 곳을 읽으려면 팔이 움직여야 합니다.
:::

팔이 자리를 한 번 옮기는 데 약 10ms(밀리초), 곧 0.01초가 걸립니다. 그러니 1초에 100번쯤 옮길 수 있습니다. 흩어진 4KB 조각을 읽으면 1초에 100번 × 4KB = 0.4MB입니다. 한자리에서 쭉 읽으면 팔을 옮기지 않아도 되어 1초에 약 100MB를 읽습니다. 250배 차이입니다.

SSD는 움직이는 팔이 없어서 차이가 훨씬 작습니다. 그래도 부탁 한 번마다 드는 수고는 남습니다. 그래서 **작은 파일 여러 개**는 다 합친 크기가 같은 **큰 파일 하나**보다 느립니다. 파일마다 이름표를 찾고 번호표를 받았다 돌려주는 일을 되풀이하기 때문입니다.

앱을 만들다 보면 이 차이를 곧 겪습니다. 프로젝트 폴더에는 가져다 쓰는 남의 코드가 `node_modules` 같은 폴더에 쌓입니다. 작은 파일이 수만 개나 되기도 합니다. 다 합쳐도 영화 한 편보다 작은데, 복사하거나 지우는 데는 훨씬 오래 걸립니다. 멈춘 것이 아니라 파일마다 다녀오는 중입니다.

::: {.deep title="폴더처럼 보이는데 왜 이렇게 느릴까요?"}
폴더라고 모두 내 컴퓨터의 저장장치에 있는 것은 아닙니다. 학교 컴퓨터실의 공유 폴더는 다른 컴퓨터의 저장 공간을 내 폴더처럼 보여 줍니다. 속은 [14장](ch14.html)에서 본 네트워크라서, 파일 하나를 열 때마다 다른 컴퓨터에 다녀옵니다.

폴더 내용을 인터넷의 저장 공간과 맞춰 주는 프로그램(예: 클라우드 드라이브)도 있습니다. 그런 폴더에 프로젝트를 두면 작은 파일 수만 개를 하나하나 올리느라 컴퓨터가 바빠집니다. 프로젝트는 그런 폴더 밖에 둡니다.
:::

## 두 번째 실행은 왜 빠를까: 페이지 캐시 {#pagecache}

큰 게임을 처음 켜면 로딩이 깁니다. 껐다가 곧바로 다시 켜면 더 빨리 뜹니다. 게임도 컴퓨터도 그대로인데 왜 그럴까요?

1GB짜리 파일 `data.bin`을 읽는 프로그램을 처음 돌리니 2.0초가 걸렸습니다. 곧바로 다시 돌리니 0.2초입니다.

지배인의 습관 때문입니다. 지배인은 창고에서 꺼낸 재료를 요리사에게 건넵니다. 그리고 조리대에 빈자리가 있으면 **사본을 놓아둡니다.** 누가 같은 재료를 또 찾으면 창고에 가지 않고 사본을 건넵니다.

컴퓨터에서는 운영체제가 한 번 읽은 파일 내용을 남는 메모리에 보관해 둡니다. 이 자리를 **페이지 캐시**(page cache)라고 합니다.

::: {.fig src="page-cache.svg"}
두 번째 실행에서는 디스크에 다녀오지 않습니다. 빨라진 것은 SSD도 코드도 아니고, 읽어 오는 곳입니다.
:::

윗줄이 첫 번째 실행입니다. 디스크에서 읽으면서 사본을 남깁니다. 아랫줄이 두 번째 실행입니다. 디스크에 가지 않고 메모리(RAM)의 사본을 받습니다.

그러니 속도를 잴 때 속지 않아야 합니다. **두 번째 실행이 빨랐다고 프로그램이 좋아진 것은 아닙니다.** 컴퓨터를 켜고 앱을 처음 여는 사람은 캐시가 빈 첫 실행의 속도를 겪습니다.

페이지 캐시는 남는 메모리를 잠시 빌려 쓰는 자리라서, 다른 프로그램이 메모리를 달라고 하면 바로 비워 줍니다.

## 모아서 한 번에 나르기: 버퍼링 {#buffer}

분식집에서 떡볶이 네 접시를 한 접시씩 네 번 나르지 않습니다. 쟁반에 담아 한 번에 나릅니다.

프로그램이 파일에 쓸 때도 같습니다. 한 줄 쓸 때마다 커널에게 부탁하면 부탁하는 수고가 줄 수만큼 듭니다. 그래서 쓸 내용을 메모리의 작은 자리에 모았다가 한 번에 넘깁니다. 쟁반 노릇을 하는 이 자리를 **버퍼**(buffer)라고 합니다.

이렇게 모아서 넘기는 방식은 **버퍼링**(buffering)이라고 합니다.

프로그램은 일하면서 "몇 시에 무슨 일이 있었다"를 한 줄씩 파일에 적어 둡니다. 이 기록을 **로그**(log)라고 합니다. 로그 1,000줄을 쓰는 경우를 봅시다.

::: {.fig src="buffer-tray.svg"}
버퍼가 100줄을 담는다면 커널을 부르는 횟수가 1,000번에서 10번으로 줄어듭니다.
:::

위쪽처럼 한 줄(80바이트)씩 바로 쓰면 시스템 호출이 1,000번 일어납니다. 아래쪽처럼 100줄이 찰 때마다 넘기면 1,000 ÷ 100 = 10번입니다. 커널을 한 번 부르는 수고는 한 줄이든 100줄이든 비슷합니다. 그러니 부르는 횟수를 줄일수록 빨라집니다. 파이썬의 `open()`에는 버퍼가 이미 들어 있습니다.

대신 **쟁반에 담긴 것은 아직 도착하지 않았습니다.** 프로그램은 돌고 있는데 로그 파일이 한참 비어 보일 수 있습니다. 고장이 아니라 쟁반이 아직 차지 않은 것입니다. 프로그램이 갑자기 꺼지면 쟁반에 남은 마지막 몇 줄이 사라집니다.

쟁반이 차지 않았어도 "지금 넘겨"라고 시킬 수 있습니다. 이 일을 **flush**(플러시)라고 합니다. 파이썬에서는 `f.flush()`라고 적습니다. 꼭 남겨야 하는 줄을 쓴 뒤에는 flush를 해 둡니다. 파일을 닫을 때는 저절로 flush됩니다.

## "저장했습니다"는 어디까지 갔다는 뜻일까 {#durable}

게임에서 "저장 중입니다. 전원을 끄지 마세요"라는 글을 본 적이 있을 것입니다. 왜 저장이 바로 끝나지 않을까요? 쓴 데이터가 디스크에 닿기 전에 두 곳을 거치기 때문입니다.

첫 번째는 버퍼입니다. flush를 하면 커널로 넘어갑니다. 그런데 커널도 받은 것을 일단 페이지 캐시에 올려놓습니다. 그러고는 "받았습니다" 하고 대답합니다. 디스크에는 **잠시 뒤에** 모아서 적습니다.

::: {.fig src="save-stations.svg"}
데이터가 어디까지 갔느냐에 따라, 사고가 났을 때 남는 것이 달라집니다.
:::

- **① 프로그램 버퍼.** 쟁반입니다. 그림의 '프로세스'는 실행 중인 프로그램을 뜻합니다.
- **② 페이지 캐시.** 커널이 맡아 둔 메모리(RAM)입니다.
- **③ 디스크.** 창고 선반입니다. 여기까지 와야 기록이 끝납니다.

그림 아래의 두 줄을 봅시다. ①에 있던 데이터는 프로그램이 꺼지면 함께 사라집니다. ②까지 갔으면 프로그램이 꺼져도 커널이 마저 적어 줍니다. 하지만 아직 메모리에 있어서, 디스크에 적기 전에 전원이 나가면 사라집니다. ③까지 가야 전원이 꺼져도 남습니다. "전원을 끄지 마세요"는 아직 ③에 닿지 않았다는 뜻입니다.

②에서 ③으로 가는 일은 커널이 잠시 뒤 스스로 합니다. "지금 바로 적고, 끝나면 알려 주세요" 하고 부탁할 수도 있습니다. 이 시스템 호출이 **fsync**입니다. 안전한 대신 디스크를 기다려야 해서 느립니다. 게임 채팅 기록은 ②로 충분합니다. 몇 달 키운 캐릭터의 저장 파일은 ③까지 가야 합니다.

::: {.key}
**"썼다"와 "디스크에 있다"는 다른 말입니다.** 이 데이터가 어떤 사고까지 견뎌야 하는지 먼저 정합니다.
:::

### 파일을 안전하게 바꿔 쓰기

게임의 소리 크기를 7에서 9로 바꾼다고 합시다. 설정 파일 `settings.json`에는 `{"volume": 7}`이라고 적혀 있습니다. volume은 소리 크기입니다.

이 파일을 열어 바로 덮어쓴다고 합시다. 쓰는 도중에 프로그램이 꺼지면 `{"volu`까지만 적힌 반쪽 파일이 남습니다. 게임을 다시 켜면 설정을 읽지 못합니다.

해법은 이름표입니다. 이름 바꾸기는 목록의 글자만 고치므로 '반쯤 바뀐' 순간이 없습니다.

::: {.fig src="safe-replace.svg"}
위: 원본을 바로 고치다 꺼지면 반쪽 파일이 남습니다. 아래: 임시 파일을 다 쓴 뒤 이름표만 바꿔 답니다.
:::

1. 원본은 그대로 두고, 잠깐 쓸 임시 파일 `settings.json.tmp`에 `{"volume": 9}`를 씁니다.
2. 다 쓰고 fsync로 디스크까지 닿게 합니다.
3. 임시 파일의 이름을 `settings.json`으로 바꿉니다. 한순간에 끝납니다.

언제 꺼져도 `settings.json`은 온전한 옛 파일이거나 온전한 새 파일입니다. 반쪽은 없습니다. 이렇게 **전부 되거나, 하나도 안 되거나** 하는 성질을 **원자적**(atomic)이라고 합니다.

임시 파일은 원본과 **같은 폴더**에 만듭니다. 다른 저장장치에 있으면 이름표만 바꿔 달 수 없기 때문입니다.

::: {.tip title="저장 기능을 맡길 때"}
AI가 써 준 저장 코드는 원본을 바로 덮어쓸 때가 많습니다. 게임 저장 파일이나 설정 파일처럼 깨지면 곤란한 파일이라면 "임시 파일에 다 쓴 뒤 이름을 바꾸는 방식으로 저장해 줘"라고 덧붙입니다. 받은 코드에서는 임시 파일의 이름과, 이름을 바꾸는 `rename`이나 `replace`가 있는지 봅니다.
:::

## 다 올릴까, 흘려보낼까: 스트리밍과 압축 {#stream}

유튜브는 영상을 끝까지 받은 다음에 틀지 않습니다. 조금 받아서 보여 주고, 또 조금 받아서 보여 줍니다.

파일도 그렇게 다룰 수 있습니다. 10GB짜리 로그 파일 `access.log`가 있습니다. 이 안에 `ERROR`(오류)라는 낱말이 몇 번 나오는지 세려고 합니다. 메모리(RAM)는 8GB입니다.

파이썬에서 숫자 없이 `f.read()`라고 쓰면 파일을 통째로 메모리에 올립니다. 10GB를 8GB짜리 조리대에 올리려는 셈입니다. 2GB가 넘칩니다. 컴퓨터가 몹시 느려지다가, 다 올리기도 전에 프로그램이 꺼집니다.

한 줄씩 읽으면서 세면 됩니다. 파이썬 코드로 적으면 이렇습니다.

```python
count = 0
with open("access.log") as f:
    for line in f:
        count += line.count("ERROR")
```

- 첫째 줄은 센 값을 담을 `count`를 0으로 둡니다.
- 둘째 줄은 파일을 열고 `f`라고 부릅니다. `with`로 열었으니 일이 끝나면 저절로 닫힙니다.
- 셋째 줄은 파일에서 한 줄을 꺼내 `line`이라고 부르고 아래 줄을 합니다. 줄이 남아 있는 동안 되풀이합니다.
- 넷째 줄은 그 줄에 `ERROR`가 나온 횟수를 `count`에 더합니다.

조리대에는 언제나 지금 읽는 한 줄, 몇백 바이트만 있습니다. 이렇게 조금씩 읽어 처리하고 넘어가는 방식이 [9장](ch09.html)에서 본 **스트리밍**(streaming)입니다.

::: {.fig src="load-vs-stream.svg"}
통째로 올리면 필요한 메모리가 파일 크기를 따라 커집니다. 흘려보내면 파일이 아무리 커도 한 줄 몫이면 됩니다.
:::

스트리밍은 조각마다 따로 처리할 수 있는 일에 통합니다. 낱말 세기는 됩니다. 모든 줄을 가나다순으로 줄 세우는 일은 안 됩니다. 멀리 떨어진 줄끼리 비교해야 하기 때문입니다.

::: {.warn}
AI는 `read()`나 `readlines()`처럼 통째로 올리는 코드를 자주 씁니다. 작은 파일에서는 잘 돌다가 큰 파일을 만나면 꺼집니다. 파일이 얼마나 커질지 모르면 "한 줄씩 읽어서 처리해 줘"라고 부탁합니다.
:::

### CSV와 JSON 파일에서 자주 걸리는 곳

앱이 데이터를 파일에 담을 때 가장 많이 쓰는 모양이 둘입니다. 표를 쉼표로 나눠 적는 CSV([2장](ch02.html))와, 중괄호로 묶어 적는 JSON([8장](ch08.html))입니다. 걸리는 곳은 거의 정해져 있습니다.

| 걸리는 곳 | 나타나는 모습 | AI에게 할 말 |
|---|---|---|
| 글자 적는 규칙(인코딩)을 안 정함 | 한글이 깨지거나 `UnicodeDecodeError` | "읽고 쓸 때 UTF-8로 정해 줘" |
| CSV 값 안의 쉼표 | `맵게, 치즈 추가` 한 칸이 두 칸으로 갈라짐 | "쉼표로 직접 자르지 말고 CSV 라이브러리로 읽어 줘" |
| 반쪽이 된 JSON | 읽을 때 `JSONDecodeError` | "임시 파일에 쓰고 이름을 바꿔서 저장해 줘" |
| 계속 커지는 JSON | 저장할 때마다 조금씩 느려짐 | "한 줄에 기록 하나씩 이어 적어 줘" |

라이브러리는 남이 만들어 둔 코드 묶음입니다. `JSONDecodeError`는 손으로 고치다 쉼표나 따옴표 하나를 틀려도 납니다. 오류 글에는 `line 1 column 14`처럼 자리가 적혀 있습니다. "1번째 줄 14번째 글자"라는 뜻이니 그 자리를 봅니다.

JSON 파일은 첫 괄호부터 끝 괄호까지가 한 덩어리입니다. 기록 하나를 보태려 해도 전부 읽고 전부 다시 써야 합니다. 그래서 일기나 채팅처럼 계속 쌓이는 기록은 한 줄에 하나씩 적습니다. 새 기록은 파일 끝에 한 줄만 이어 쓰면 되고, 읽을 때도 한 줄씩 흘려보낼 수 있습니다. 이 방식을 JSON Lines라고 하고, 파일 이름은 `.jsonl`로 끝납니다. 기록이 더 늘고 찾을 일이 많아지면 [17장](ch17.html)의 데이터베이스로 옮깁니다.

### 압축: CPU의 수고를 주고 크기를 줄입니다

zip 파일은 파일을 묶으면서 크기를 줄인 것입니다. 이렇게 데이터를 더 짧게 바꿔 적는 일을 **압축**(compression)이라고 합니다. 싸고 푸는 데는 CPU의 손이 듭니다.

100MB짜리 파일을 친구에게 보낸다고 합시다. 압축하면 20MB가 됩니다. 압축에 2초, 푸는 데 1초가 듭니다. 압축해서 보내는 시간은 이 3초에 20MB를 보내는 시간을 더한 값입니다.

| 인터넷 속도 | 그냥 보내기 | 압축해서 보내기 |
|---|---|---|
| 1초에 10MB | 100 ÷ 10 = 10초 | 2 + (20 ÷ 10) + 1 = **5초** |
| 1초에 100MB | 100 ÷ 100 = **1초** | 2 + (20 ÷ 100) + 1 = 3.2초 |

인터넷이 느리면 압축이 이깁니다. 빠르면 싸고 푸는 시간이 오히려 손해입니다. JPEG 사진이나 MP4 영상처럼 **이미 압축된 파일**은 다시 압축해도 거의 줄지 않습니다.

## 남이 올린 파일, 화면에 보낼 그림 {#upload}

프로필 사진을 올려 본 적이 있을 것입니다. 사진을 고르고 버튼을 누르면 내 휴대전화의 파일이 그 서비스의 서버로 건너가 저장됩니다. 이 일을 업로드(upload)라고 합니다.

AI에게 "사진 올리기 기능을 만들어 줘"라고 하면 금방 만들어 줍니다. 하지만 정해 주지 않으면 빠지는 것이 넷 있습니다.

| 정할 것 | 정하지 않으면 | AI에게 할 말 |
|---|---|---|
| 크기 한도 | 누가 4GB짜리 영상을 올려 저장 공간이 바닥남 | "파일 하나에 5MB까지만 받고, 넘으면 알려 줘" |
| 종류 | 그림 자리에 아무 파일이나 올라옴 | "JPEG와 PNG만 받고, 확장자 말고 내용도 확인해 줘" |
| 이름 | 두 사람이 올린 `photo.jpg`가 서로 덮어씀 | "올린 이름을 쓰지 말고 겹치지 않는 새 이름을 붙여 줘" |
| 둘 곳 | 새 버전을 올릴 때 사진이 사라짐 | "코드 폴더 밖에 저장하고, 누가 올린 파일인지 기록해 줘" |

종류를 내용으로 확인하는 까닭은 [2장](ch02.html#file)에 있습니다. 이름을 새로 붙이는 까닭은 하나 더 있습니다. 이름에 `../`를 넣어 엉뚱한 폴더를 노리는 사람이 있기 때문입니다([19장](ch19.html)).

내 컴퓨터에서 시험할 때는 올린 파일을 `uploads` 같은 폴더 하나에 모아도 됩니다. 인터넷에 올린 앱은 다릅니다. 새 버전을 올릴 때마다 서버의 폴더를 비우고 새로 시작하는 서비스가 많습니다([21장](ch21.html#disposable)). 그래서 사진 같은 파일은 파일만 따로 맡아 주는 보관 서비스에 둡니다. 이런 곳을 객체 저장소라고 하고, [17장](ch17.html)에서 만납니다. 앱의 데이터를 어디에 둘지는 [31장](ch31.html#data)에서 한데 모아 봅니다.

### 큰 그림은 화면을 느리게 합니다

휴대전화로 찍은 사진은 한 장에 3MB쯤입니다. 친구 20명의 프로필 사진을 한 화면에 그대로 늘어놓으면 20 × 3MB = 60MB를 받아야 합니다. 1초에 10MB를 받는 인터넷이라면 6초가 걸립니다. 화면에는 엄지손톱만 하게 보이는데 받는 것은 원본입니다.

그래서 올릴 때 **줄인 사본**을 함께 만들어 둡니다. 이 사본을 **섬네일**(thumbnail)이라고 합니다. 한 장에 50KB쯤이면 20장이 1,000KB, 곧 1MB입니다. 0.1초면 받습니다. 목록에서는 섬네일을 보여 주고, 사진을 눌렀을 때만 원본을 보냅니다.

확인은 [15장](ch15.html#render)에서 본 Network 탭에서 합니다. 크기 칸에 MB 단위의 그림이 줄줄이 보이면 느린 까닭은 그림입니다. AI에게는 "목록에는 가로 400픽셀로 줄인 사본을 보여 줘"라고 말합니다.

## 느린 곳 찾기: 추측하지 말고 재기 {#measure}

병원에서는 약을 주기 전에 체온부터 잽니다. 느린 프로그램도 고치기 전에 먼저 잽니다. [1장](ch01.html)에서 전체 속도를 붙잡는 가장 좁은 곳을 병목이라고 했습니다. 병목이 아닌 곳은 고쳐도 빨라지지 않습니다.

먼저 가를 것은 맨 앞의 물음입니다. **CPU가 바쁜가, 입출력을 기다리는가?** 리눅스에서는 터미널에 `top`과 `iostat -x`를 치면 알 수 있습니다. 숫자 세 개만 봅니다. 앞의 둘은 `top`에, 마지막은 `iostat -x`에 나옵니다.

- `us`는 CPU가 계산에 쓴 시간의 비율입니다.
- `wa`는 디스크의 대답을 기다리느라 CPU가 쉬고 있던 시간의 비율입니다.
- `%util`은 디스크가 바빴던 시간의 비율입니다.

::: {.fig src="cpu-or-wait.svg"}
똑같이 느려도 숫자의 모양이 다릅니다. 코어(요리사)가 하나일 때의 예입니다. 코어가 여럿이면 숫자가 그만큼 나뉘어 작게 보입니다.
:::

A는 `us`가 97%입니다. 병목은 CPU입니다. 계산을 줄이거나 여러 코어에 나눕니다.

B는 `wa`가 71%, `%util`이 98%입니다. 병목은 디스크입니다. 읽고 쓰는 횟수를 줄입니다. 앞에서 본 버퍼링, 캐시, 순차 접근이 그 방법입니다.

윈도우의 작업 관리자와 맥의 '활성 상태 보기'([1장](ch01.html))도 CPU, 메모리, 디스크 가운데 무엇이 바쁜지 보여 줍니다.

::: {.warn title="셋 다 낮은데 느릴 때"}
서버의 대답을 기다리는 시간은 `wa`에 잡히지 않고 한가한 시간으로 보입니다. 이럴 때는 단계마다 시작과 끝 시각을 로그에 적어 어느 단계가 긴지 봅니다.
:::

::: {.try}
맥이나 리눅스의 터미널에서 두 명령을 차례로 칩니다. 앞에 붙인 `time`이 걸린 시간을 재 줍니다.

```bash
time sleep 2
time python3 -c "print(sum(range(100000000)))"
```

첫째는 2초 동안 기다리기만 합니다. 둘째는 0부터 1억 바로 앞까지 더합니다. 첫째의 결과는 이런 모양입니다.

```text
real    0m2.016s
user    0m0.001s
sys     0m0.003s
```

`real`은 경과 시간입니다. `user`는 프로그램이 스스로 계산한 시간, `sys`는 커널이 부탁을 들어주느라 계산한 시간입니다. 둘을 더하면 CPU 시간입니다. 첫째는 CPU 시간이 0에 가깝습니다. 내내 기다렸습니다. 둘째는 `real`과 `user`가 거의 같습니다. 내내 계산했습니다.

맥에서는 한 줄로 나옵니다. `user`와 `system` 앞의 숫자를 더하면 CPU 시간이고, `total` 앞의 숫자가 경과 시간입니다.
:::

`time`으로 계산과 기다림을 갈랐으면 한 걸음 더 들어갑니다. CPU 시간이 대부분이라면 [12장](ch12.html#perf)에서 본 **프로파일러**(profiler)로 코드의 어느 부분이 오래 걸리는지 찾습니다.

기다림이 대부분이라면 단계마다 걸린 시간을 따로 잽니다. 프로파일러 가운데는 CPU가 계산한 시간만 재는 것이 있습니다. 4.8초를 기다린 프로그램을 그런 도구로 재면 0.2초의 속사정만 보입니다.

### 조리대가 모자라면 디스크가 바빠집니다

`wa`가 높다고 늘 파일을 읽고 쓰느라 그런 것은 아닙니다. 메모리가 모자랄 때도 디스크가 바빠집니다.

[3장](ch03.html)에서 조리대가 꽉 차면 지배인이 한동안 안 쓴 것을 창고로 내려보낸다고 했습니다. 이 일이 **스왑**(swap)입니다. 다시 필요해지면 도로 올립니다. 창고는 조리대보다 훨씬 느려서, 스왑이 잦으면 컴퓨터가 굼떠집니다. 인터넷 탭을 수십 개 열어 둔 컴퓨터가 버벅거리는 까닭입니다.

숫자로 봅시다. 메모리가 8GB인 컴퓨터에서 동영상의 크기를 줄입니다. 영상 하나에 메모리 1.5GB가 듭니다. 4개를 함께 돌리면 4 × 1.5 = 6GB라서 괜찮습니다. 20개를 함께 돌리면 20 × 1.5 = 30GB가 필요합니다. 8GB로는 턱없이 모자랍니다.

이제 지배인은 방금 내려보낸 것을 곧바로 다시 올려야 합니다. 그러려면 다른 것을 또 내려보내야 합니다. 지배인은 조리대와 창고 사이를 오가기만 하고, 요리사는 기다리기만 합니다. 이 상태를 **스래싱**(thrashing)이라고 합니다. 한꺼번에 하는 일을 늘렸는데 끝나는 일은 오히려 줄어듭니다.

고치는 방법은 **한꺼번에 펼치는 양에 한도를 두는 것**입니다. 20개를 4개씩 다섯 번에 나눠 돌립니다.

### AI에게 "느려요"라고 말하기 전에

AI에게 "느려, 빠르게 해 줘"라고만 하면 AI는 재지 않고 짐작으로 고칩니다. 흔히 계산하는 코드를 손보고 "빨라졌습니다"라고 답합니다. 병목이 기다림이었다면 달라진 것이 없습니다. 먼저 재서 세 가지를 함께 줍니다.

- **무엇을 했을 때 몇 초인가.** "검색 버튼을 누르면 8초"처럼 적습니다.
- **자료가 얼마나 되는가.** "일기 2,000개, 모두 4MB"처럼 적습니다.
- **어느 단계가 긴가.** 웹 화면이면 Network 탭에서 가장 오래 걸린 줄을 봅니다. 프로그램이면 "단계마다 걸린 시간을 찍어 줘"라고 먼저 시킵니다.

### 재는 사람이 지킬 세 가지

1. **고치기 전에 잽니다.** 어디가 느린지 모르고 고치면 엉뚱한 곳을 고칩니다.
2. **같은 조건으로 여러 번 잽니다.** 한 번씩만 재면 우연한 차이에 속습니다.
3. **첫 실행인지 적습니다.** 고친 뒤만 두 번째 실행으로 쟀다면 페이지 캐시 덕을 본 것입니다.

AI가 "빨라졌습니다"라고 할 때도 고치기 전과 후에 잰 숫자를 달라고 합니다.

::: {.key}
병목이 아닌 곳을 고치면 시간은 그대로입니다. **고치기 전에 재고, 고친 뒤에 다시 잽니다.**
:::

## 헷갈리기 쉬운 짝 {#pairs}

| 짝 | 차이 |
|---|---|
| 경과 시간 / CPU 시간 | 벽시계로 잰 전체 시간 / 그중 CPU가 실제로 계산한 시간 |
| 처리량 / IOPS | 1초에 옮긴 양 / 1초에 다녀온 횟수. 한 번에 나른 양을 곱해야 이어짐 |
| 버퍼 / 캐시 | 내보낼 것을 잠깐 모아 두는 곳 / 또 쓸 것을 가까이 남겨 두는 곳 |
| flush / fsync | 프로그램 버퍼에서 커널로 넘기기 / 커널에서 디스크까지 다 적기 |
| 이름 바꾸기 / 복사 | 이름표 목록의 글자만 고치기 / 내용물을 전부 새로 쓰기 |
| 스왑 / 스래싱 | 안 쓰는 것을 디스크로 잠깐 내려보내는 일 / 그 일만 되풀이하느라 일이 나아가지 않는 상태 |

## 실전 사례 {#case}

::: {.case title="글은 4MB뿐인데 일기 검색에 40초가 걸린다"}
코딩 동아리에서 일기장 프로그램을 만들었습니다. 일기 하나를 작은 파일 하나로 저장합니다. 동아리 컴퓨터는 오래돼서 저장장치가 하드디스크입니다. 일기가 2,000개 쌓이자, 컴퓨터를 켜고 처음 검색할 때 40초가 걸립니다.

1. **계산인지 기다림인지 가릅니다.** `time`으로 재니 40초 가운데 CPU 시간은 1초입니다. 거의 다 기다림입니다.
2. **단계를 나눠 잽니다.** 파일 열고 닫기, 읽기, 낱말 찾기를 따로 잽니다. 열고 닫는 데 가장 오래 걸립니다.
3. **맞는 숫자를 봅니다.** 일기는 하나에 2KB쯤이라 다 합쳐도 4MB입니다. 이 하드디스크는 1초에 100MB를 읽지만, 그것은 한자리에서 쭉 읽을 때의 숫자입니다. 이 프로그램은 흩어진 파일 2,000개를 하나씩 찾아다닙니다.
4. **다녀오는 횟수를 줄입니다.** 일기를 저장할 때 검색용 파일 하나에도 이어 적습니다. 검색은 이 파일 하나를 차례로 읽습니다.
5. **같은 조건으로 확인합니다.** 고친 뒤에도 컴퓨터를 켜고 처음 검색할 때를 잽니다. 40초가 1초쯤으로 줄었습니다. 검색 결과가 전과 같은지도 비교합니다.

저장장치에 적힌 최고 속도는 내 프로그램의 속도가 아닙니다. 내 프로그램이 **얼마만 한 조각을 몇 번** 읽고 쓰는지가 먼저입니다.
:::

## 한눈에 정리 {#summary}

::: {.summary}
- 프로그램이 느린 까닭은 대개 계산이 아니라 **입출력을 기다리는 시간**입니다. 경과 시간과 CPU 시간을 비교하면 드러납니다.
- 파일을 열면 번호표인 **파일 디스크립터**를 받습니다. 어디까지 읽었는지는 커널의 장부가 기억합니다.
- `No such file or directory`가 나오면 경로와 지금 폴더를 봅니다. 상대 경로는 **프로그램을 실행한 폴더**에서 출발합니다.
- 컴퓨터는 **이름표와 내용물을 따로** 보관합니다. 그래서 이름 바꾸기는 금방 끝나고 복사는 오래 걸립니다.
- 흩어진 작은 조각을 읽는 일은 이어진 큰 덩어리를 읽는 일보다 훨씬 느립니다.
- **페이지 캐시와 버퍼**는 창고에 다녀오는 횟수를 줄여 줍니다. 대신 "썼다"와 "디스크에 있다" 사이에 틈이 생깁니다. flush와 fsync가 그 틈을 메웁니다.
- 큰 파일은 통째로 올리지 말고 **스트리밍**으로 흘려보냅니다. 깨지면 곤란한 파일은 임시 파일에 쓰고 이름을 바꿉니다.
- 남이 올리는 파일은 **크기, 종류, 이름, 둘 곳**을 정해 줍니다. 목록에는 줄인 그림을 보여 줍니다.
- 메모리가 모자라면 **스왑** 때문에 디스크가 바빠지고, 심해지면 **스래싱**에 빠집니다. 한꺼번에 하는 일에 한도를 둡니다.
- **추측하지 말고 잽니다.** 계산이 느리면 **프로파일러**로 어느 부분인지 좁힙니다. 같은 조건으로, 고치기 전과 후를 비교합니다.
:::

## 확인 문제 {#quiz}

::: {.q}
게임에서 '상점 열기'를 누르면 5초가 걸립니다. 그중 CPU가 계산한 시간은 0.2초입니다. 친구가 "CPU를 두 배 빠른 것으로 바꾸면 2.5초가 될 거야"라고 합니다. 실제로는 몇 초가 될까요?

::: {.a}
약 4.9초입니다. 두 배 빨라지는 것은 계산 0.2초뿐이라 0.1초만 줄어듭니다. 나머지 4.8초는 기다린 시간입니다. 무엇을 기다리는지부터 찾아야 합니다.
:::
:::

::: {.q}
컴퓨터를 켜고 게임을 처음 실행하니 로딩에 20초가 걸렸습니다. 게임만 껐다가 바로 다시 켜니 4초입니다. "이 컴퓨터의 SSD는 충분히 빠르다"고 말해도 될까요?

::: {.a}
안 됩니다. 두 번째는 디스크가 아니라 메모리에 남아 있던 사본, 곧 페이지 캐시에서 읽었을 가능성이 큽니다. SSD의 빠르기는 캐시가 빈 첫 실행으로 따져야 합니다.
:::
:::

::: {.q}
AI가 만들어 준 게임이 있습니다. `mygame` 폴더 안에서 `python3 main.py`로 실행하면 잘 됩니다. 한 칸 위 폴더에서 `python3 mygame/main.py`로 실행하니 `No such file or directory: 'data/settings.json'`이 나옵니다. 파일은 지우지 않았습니다. 왜 못 찾을까요? AI에게 뭐라고 부탁하면 될까요?

::: {.a}
`data/settings.json`은 상대 경로라서 프로그램을 실행한 폴더에서 출발합니다. 한 칸 위 폴더에는 `data` 폴더가 없습니다. 코드 파일이 있는 폴더를 기준으로 경로를 잡아 달라고 부탁합니다.
:::
:::

::: {.q}
게임이 갑자기 꺼졌습니다. 게임이 남긴 로그 파일을 열어 보니 꺼지기 직전의 몇 줄이 없습니다. 그 줄들은 어디에 있다가 사라졌을까요?

::: {.a}
프로그램 버퍼에 담겨 있다가 프로그램과 함께 사라졌습니다. 중요한 줄을 쓴 뒤 flush로 커널에 넘겨 두면 프로그램이 꺼져도 남습니다.
:::
:::

::: {.q}
메모리가 8GB인 컴퓨터에서 12GB짜리 채팅 기록 파일에 "ㅋㅋ"가 몇 번 나오는지 세려고 합니다. AI가 써 준 코드에 `f.read()`가 들어 있습니다. 무슨 일이 생길까요? 어떻게 고쳐 달라고 하면 될까요?

::: {.a}
`f.read()`는 파일을 통째로 메모리에 올립니다. 12GB는 8GB에 다 들어가지 않아서 올리다가 꺼집니다. 한 줄씩 읽어서 세는 스트리밍 방식으로 바꿔 달라고 합니다.
:::
:::

## AI에게 맡길 때 {#ai}

::: {.ai}
AI는 시키지 않으면 "파일이 없으면?", "아주 커지면?", "쓰는 도중에 꺼지면?"을 따져 보지 않습니다. 이 세 물음의 답을 요청문에 적습니다. 느린 까닭을 찾게 할 때는 **무엇을 어떤 조건에서 잴지**도 적습니다.

> 일기장 앱에 저장과 검색을 만들어 줘. 일기는 코드 파일이 있는 폴더의 `data/diary.jsonl`에 UTF-8로, 한 줄에 하나씩 이어 적어 줘. 파일이 없으면 오류를 내지 말고 새로 만들어 줘. 검색은 파일을 통째로 읽지 말고 한 줄씩 읽어 줘. 설정 파일은 임시 파일에 쓴 뒤 이름을 바꾸는 방식으로 저장해 줘. 다 만들면 일기 10,000개를 넣고, 검색에 걸린 시간을 첫 실행과 두 번째 실행으로 나눠 재서 보여 줘.

**받은 답에서 확인할 것**

- 파일을 여는 줄마다 `utf-8`이 적혀 있는가
- 경로가 실행한 폴더가 아니라 코드 파일이 있는 폴더를 기준으로 잡혔는가
- 큰 파일을 읽는 곳에 `read()`, `readlines()`처럼 통째로 올리는 코드가 없는가
- 설정을 저장하는 곳에 임시 파일과 이름 바꾸기가 있는가
- 짐작이 아니라 잰 숫자가 있고, 첫 실행과 두 번째 실행이 나뉘어 있는가

**AI가 자주 하는 실수**

- 파일을 통째로 읽습니다. 작은 시험 파일로는 드러나지 않으니, 큰 파일을 만들어 돌려 보게 합니다.
- 상대 경로를 그대로 씁니다. 다른 폴더에서 실행해 보면 `No such file or directory`로 드러납니다.
- 올리는 파일에 크기 한도를 두지 않습니다. 한도보다 큰 파일을 올려 보면 드러납니다.
- 재지 않고 "빨라졌습니다"라고 합니다. 고치기 전과 후의 숫자를 달라고 합니다.

일을 시키는 순서 전체는 [30장](ch30.html)에서 다룹니다.
:::

## 용어 정리 {#terms}

::: {.terms}
입출력 (I/O, Input/Output)
:   CPU와 메모리 바깥에서 데이터를 가져오거나 내보내는 일.

디스크 (disk)
:   저장장치를 흔히 부르는 말.

경과 시간 (elapsed time)
:   시작부터 끝까지 벽시계로 잰 시간. 그중 CPU가 계산한 몫이 CPU 시간이다.

파일 디스크립터 (FD, file descriptor)
:   파일을 열 때 커널이 내주는 번호표. 3, 4 같은 작은 숫자다.

아이노드 (inode)
:   파일의 크기, 권한, 내용물이 있는 칸을 적어 둔 관리 카드.

블록 (block)
:   저장장치에서 파일의 내용물이 담기는 칸.

지연 시간 (latency)
:   부탁 하나가 끝나기까지 걸린 시간.

처리량 (throughput)
:   1초에 옮긴 데이터의 양.

IOPS (Input/Output Operations Per Second)
:   저장장치가 1초에 읽거나 쓴 횟수.

순차 접근 (sequential access)
:   붙어 있는 칸을 차례로 읽고 쓰는 방식. 떨어진 칸을 오가는 랜덤 접근보다 빠르다.

페이지 캐시 (page cache)
:   운영체제가 한 번 읽은 파일 내용을 남는 메모리에 보관해 두는 자리.

버퍼 (buffer)
:   내보낼 데이터를 잠깐 모아 두는 메모리 속 자리. 이렇게 모았다가 한 번에 넘기는 방식이 버퍼링이다.

로그 (log)
:   프로그램이 일하면서 무슨 일이 있었는지 한 줄씩 적어 두는 기록.

flush (플러시)
:   버퍼에 모인 데이터를 지금 바로 다음 곳으로 넘기는 일.

fsync
:   커널이 맡아 둔 데이터를 디스크에 다 적을 때까지 기다리는 시스템 호출.

원자적 (atomic)
:   반쯤 된 상태 없이, 전부 되거나 하나도 안 되는 성질.

스트리밍 (streaming)
:   파일을 통째로 올리지 않고 조금씩 읽어 처리하는 방식.

압축 (compression)
:   데이터를 더 짧게 바꿔 적어 크기를 줄이는 일.

섬네일 (thumbnail)
:   목록에 보여 주려고 원본 그림을 작게 줄여 만든 사본.

프로파일러 (profiler)
:   프로그램의 어느 부분이 시간을 얼마나 쓰는지 재 주는 도구.

스왑 (swap)
:   메모리가 모자랄 때 한동안 안 쓴 내용을 저장장치로 내려보냈다가 다시 올리는 일.

스래싱 (thrashing)
:   메모리가 너무 모자라 내려보내고 올리기만 되풀이하느라 일이 나아가지 않는 상태.
:::
